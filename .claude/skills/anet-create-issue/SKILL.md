# 課題の起票

開発対象システムの課題を **1 課題 1 ファイル**で起票する。

## 出力先とファイル名

| 項目 | 内容 |
| --- | --- |
| 出力先 | `docs/management/issues/`（`docs/process/registry.md` の成果物キー `issue-record`） |
| ファイル名 | 発番で得た ID に `.md` を付けたもの |

## 起票の手順

1. `docs/process/registry.md` から成果物キー `issue-record` の行を引き、出力先を確認する（`Read`）
2. `docs/process/numbering.md` の手順で、接頭辞 `issue` の **ID を得る**（`Bash`）
3. 出力先に既存の `issue-*.md` があるかを確かめる。**無ければ出力先ごと作る**（`Glob`）
4. ID に `.md` を付けた名前で、下のテンプレートに従って 1 ファイル書く（`Write`）
5. リポジトリルートから repo の `.venv` の Python で `reports/tools/wiki_support.py maps` を回す（`Bash`）。全部の課題の frontmatter を検証し、`docs/management/issues/INDEX.md` と wiki の地図の「課題」の区画を作り直す。検証で止まったら、どの出力も変わらない。今回書いた課題で止まったら、書式を直して回し直す。ほかの課題で止まったら直さずに、その課題と止まった理由を呼び出し元へ返す。複数を書くときは、書き終えてから 1 回回す
6. 起票したファイル名を呼び出し元へ返す

## テンプレート

```markdown
---
id: issue-YYYYMMDD-xxxxxx
title: <一行で言い切る。ファイルを開かずに何の課題か分かること>
status: 未着手
raised: YYYY-MM-DD
phase: <PRD / 実装 / 監査 / ハーネス保守 / その他>
scope: <影響範囲。どの成果物・どの機能に及ぶか>
kind: <成果物 / ハーネス>
area: []
type: <機能追加 / 機能改善 / 性能改善 / リファクタリング / 不具合 / 不整合 / 調査>
domain: <アルゴリズム / 学習基盤 / UI / Env / 基盤 / 開発>
ai_judge: 未確認
ai_judged:
docs: []
prd:
priority: 中
depends: []
parent:
value: <1 / 2 / 3 / 5 / 8 / 13>
urgency: <1 / 2 / 3 / 5 / 8 / 13>
risk: <1 / 2 / 3 / 5 / 8 / 13>
size: <1 / 2 / 3 / 5 / 8 / 13>
wsjf: <（value ＋ urgency ＋ risk）÷ size>
resolved:
resolution:
memo:
tags: []
---

## 背景

<なぜこの課題が出てきたか。前提となる状況>

## 事象

<何が起きているか。観測できた事実だけを書く>

## 影響

<それによって何が困るか。放置した場合に何が起きるか>

## 対応方針

<どう対応するつもりか。未定なら「未定」と書く>

## 対応内容

<実際に行ったこと。起票時は空でよい>
```

frontmatter は、Obsidian のプロパティ欄で直したときと同じ書き方にそろえる。Obsidian で直しても書き方が変わらず、差分が値の変更だけになるようにするためである。

- 文字列は引用符で囲まない。YAML として読み違える値だけを二重引用符で囲む。「`: `」や「` #`」を含む値、`[` や `` ` `` などの記号で始まる値、数や `true`・`null` などに読める値（Obsidian と同じ YAML 1.2 の読み方で判断する）である。囲まずにおくと、YAML として読めず、手順 5 の一覧の作り直しが止まる。値の中に `"` を入れない
- 日付は `2026-11-09` のように引用符を付けずに書く
- 空の値は `parent:` のように、コロンのあとに何も書かない（空白も置かない）
- リストは、空なら `[]`、1 件以上なら 1 行に 1 項目（`  - 値`。字下げは空白 2 つ）で書く
- 数は、整数になるときは小数点を付けない（`wsjf: 2`）
- 課題と PRD を指す欄（`parent`・`depends`・`prd`）は、Obsidian のリンクの形 `"[[ファイル名]]"`（拡張子なし）で書く。`[` で始まるので二重引用符で囲む。別名（`|`）とパスは付けない。課題の ID だけを書くと、手順 5 の一覧の作り直しが止まる

## 各項目の書き方

| 項目 | 指針 |
| --- | --- |
| `title` | 一覧で読んで判別できること。「エラーが出る」のような曖昧な表現を避ける |
| `status` | 下の状態の定義から選ぶ |
| `raised` | 起票日。取得した現在時刻の日付部分 |
| `phase` | どの工程で見つかったか |
| `scope` | 影響が及ぶ範囲。不明なら「調査中」 |
| `kind` | 何についての課題か。下の「監理の項目」の定義から選ぶ |
| `area` | `reports/tools/categories.json` の `categories` にある key の並び。先頭が主なカテゴリ。当たらなければ `[]`。アプリケーション自身の key も使える |
| `type` | 仕事の種類。機能追加＝新しい振る舞い、機能改善＝今ある振る舞いを使いやすく・見やすく・正確にする、性能改善＝速さ・メモリ、リファクタリング＝振る舞いを変えない作りの直し、不具合＝決めたとおりに動かない、不整合＝文書・規約と実物の食い違い（どちらを直すかは対応のときに決める）、調査＝測る・調べる |
| `domain` | 大まかな分類。アルゴリズム＝学習の手法（DQN・MuZero・NN・内的報酬など）、学習基盤＝Runner・replay・評価などの学習の共通の仕組み、UI＝Runner の画面・Viewer・GUI・可視化、Env、基盤＝設定・テンソル・ユーティリティ・プロファイリング、開発＝道具・テスト・ビルド・ハーネス。値は 1 つで、起票では `area` の先頭と本文から選ぶ。`kind` が `ハーネス` なら `開発` にする。起票のあとは、開発者が `area` と独立に直してよい |
| `ai_judge` | 未確認 / 残件有り / 残件無し / 判定不能。起票では `未確認` を書き、空にしない。PRD の実装済みは判定の値で表さず、その PRD を `prd` で指す課題の判定と状態から一覧の道具が導く |
| `ai_judged` | AI が判定した日付。`ai_judge` が `未確認` なら空、ほかの 3 つの値なら日付を書く。AI の自発的な更新は `anet-update-issue` の「判定」だけを使う |
| `docs` | 関係する指示・設計文書の repo 相対パスの並び。実在するファイルだけを書く。無ければ `[]`。この課題を直す PRD は `prd` に書き、`docs` に重ねない。PRD に関係するだけの課題は、その PRD を `docs` に書く |
| `prd` | この課題を直す PRD のリンク（`"[[NNN_slug_10prd]]"`）。`docs/memo/` 直下の PRD を 1 本だけ指す（課題と PRD は N:1）。PRD を起こすときに `anet-create-prd` が書く。無ければ空 |
| `priority` | 開発者が直接書き換える、直近の手の付け方のメモ（下の「管理外のメモ」）。起票では `中` を置く |
| `depends` | 先に解決しないと直せない、または直し方が決まらない課題のリンクの並び（書き方は上の「テンプレート」の決まりによる）。無ければ `[]` |
| `parent` | 親の課題のリンク（下の「分け方」）。無ければ空 |
| `value` `urgency` `risk` `size` | 下の「監理の項目」の目安から選ぶ。起票時の見立てでよく、棚卸し（`anet-list-issues`）で見直す |
| `wsjf` | `value` `urgency` `risk` `size` から計算した値を書く。目分量で書かない |
| `resolved` | 解決したときだけ日付を書く。起票時は空 |
| `resolution` | 完了の理由。解決にするときだけ、対応済み / 対応しない / 重複 / 再現しない / 不要になった から書く。解決でなければ空 |
| `memo` | 開発者が直接書き換える自由なメモ（下の「管理外のメモ」）。起票時は空 |
| `tags` | 開発者が直接書き換える横断のテーマ（下の「管理外のメモ」）。起票時は `[]` |
| 背景 | 前提となる状況。読み手が経緯を知らなくても事象を理解できること。工程の中で見つかった事項は、開発者に質問したかを事実どおりに書く（候補の根拠から引き継ぐ。質問していないのに「質疑で決まらず」と書かない） |
| 事象 / 影響 | **必ず分けて書く。** 原因が未特定でも起票してよい |
| 対応方針 | これからどうするか。未定なら「未定」 |
| 対応内容 | 実際に行ったこと。**起票時は空**。対応した工程が、このファイルへ直接追記する（いつ書くかは各工程の手順による）。前の工程が書いた行は書き換えない。今回の工程が書いた行は、完了を報告するまで直してよく、直しを戻したら消す。形は `- YYYY-MM-DD <PRD の番号か工程>: <この課題について行ったこと>。確かめ: <結果>。[PRD](…)・[実装記録](…)` とし、当たらない要素は省く。コミットのハッシュは書かない（書く時点でまだ無い） |

## 状態の定義

| 状態 | 意味 |
| --- | --- |
| `未着手` | 起票のみ |
| `調査中` | 原因や影響を調べている |
| `対応中` | 解決方法が決まり作業している |
| `中断中` | 着手して一部を済ませたが、手を止めている。外部要因を待っているのではない（外部要因なら `保留`）。**再開すれば本版で対応する** |
| `保留` | 外部要因待ち（実働環境・他部門の判断など）。**条件が整えば本版で対応する** |
| `次版` | **当面は扱わないと決めた。** 外部要因待ちではなく、開発者が意図して先送りした状態 |
| `解決` | 対応完了。`resolved` に日付を、`resolution` に完了の理由を記入する |

`解決` と `次版` は開発者が決める（`解決` は `anet-prepare-commit` が持ちかける）。ほかの状態は、開発者の指示のほか、工程の出来事に合わせて AI が書く。どちらも `anet-update-issue` が書く（同 skill の「工程の出来事」「解決を持ちかける」）。

## 監理の項目

どの課題から手を付けるかを考えるための項目である。**`wsjf` は効果・時間・リスク・手間から計算した目安であり、作業の順を決めるものではない。** どれから手を付けるかは、開発者がそのときの事情（担当、時期、ほかの作業）で決める。一覧での並べ方は `anet-list-issues` が定める。 値を変えるのは `anet-update-issue` で、開発者の指示（棚卸しの提案を採ることを含む）があるときだけである。

| 項目 | 値 | 意味 |
| --- | --- | --- |
| `kind` | `成果物` | フレームワーク・アプリ・設定・設計文書についての課題 |
| | `ハーネス` | AGENTS.md・skill・品質確認観点・プロセス・エージェント定義についての課題 |
| `depends` | 課題のリンクの並び | 先に片づける課題。これらの状態が `解決` でない間、この課題は一覧で「待ち」として示す。**依存は循環させない** |
| `parent` | 課題のリンク | この課題を束ねる親。親は子を束ねるだけで、直すのは子である。**親子の対応は子の `parent` だけで持ち、親の本文には書かない**（子の一覧は `anet-list-issues` に親の ID を渡して引く） |
| `value` `urgency` `risk` `size` `wsjf` | 下の「WSJF」 | 効果・時間・リスク・手間と、そこから計算した値 |

anet の「本版」は今の開発で扱うこと、「次版」は当面は扱わないことを表す。版で区切って開発しているという意味ではない。`area`・`type`・`docs`・`prd`・`domain` も監理の項目で、起票後は開発者の指示により `anet-update-issue` が変える。`domain` は、開発者が Obsidian などで直接書き換えてもよい。

### WSJF

`wsjf` は WSJF（Weighted Shortest Job First）の値である。遅らせたときに失うもの（`value` ＋ `urgency` ＋ `risk`）を、直す手間（`size`）で割る。**大きいほど、先に片づける値打ちがある。** 元になる 4 つの値は 1・2・3・5・8・13 から選ぶ。間の値は使わない。見立ての細かさに見合わないためである。

| 項目 | 何を見るか | 目安 |
| --- | --- | --- |
| `value` | 効果。直したときに得られるもの（成果物の品質、開発の時間と費用、作業の効率。種別が `ハーネス` ならハーネス自体の開発の効率も） | 13 配布・リリースや稼働ができない ／ 8 毎回の実行で品質か時間に大きく効く ／ 5 目に見えて効く ／ 3 少し効く ／ 2 わずか ／ 1 体裁 |
| `urgency` | 時間。遅らせるほど高くつくか | 13 決まった期日（配布・リリース・引き渡し・試行など）の前に要る ／ 8 次の実行で毎回当たる、または遅らせるほど直す量が増える ／ 5 使い始めると当たる（ハーネスならそれを使う開発者、開発対象システムなら利用者） ／ 3 いずれ当たる ／ 2 当たる場面が限られる ／ 1 急がない |
| `risk` | リスク・機会。危険・取り返しがつかないか、ほかの課題の前提になるか | 13 権利・情報の漏れ ／ 8 誤った成果物が気づかれずに残る ／ 5 ほかの課題の `depends` に挙がっている、または監査や保護に効く ／ 3 ほかの課題の前提になる（`depends` にはまだ挙がっていない） ／ 2 少しある ／ 1 無い |
| `size` | 手間。直す材料（実測・工程を動かした結果など）が揃っていなければ重くする | 1 文書の数行 ／ 2 小さな変更 ／ 3 1 か所の変更とレビュー（成果物 1 つ、または SKILL・Agent 1 本） ／ 5 複数の成果物・資材の変更と判断 ／ 8 設計を含む大きな変更 ／ 13 外部の判断や大量の作業 |
| `wsjf` | （`value` ＋ `urgency` ＋ `risk`）÷ `size` | 小数第 2 位を四捨五入し、小数 1 桁で書く。整数になるときは小数点を付けない（`2.0` ではなく `2`） |

- **`urgency` は予定で変わる。** 期日が決まったり動いたりしたら、棚卸しで見直す
- 手間が 1 の課題は値が大きくなりやすい。文書の数行の直しなどは、まとめて片づけるとよい
- 状態が `次版` と `解決` の課題は、5 つとも空でよい

### anet での当てはめ

上の目安を、anet では次のように読む。課題どうしを同じ基準で横に並べて比べられるよう、起票でも棚卸しでもこの読みを使う。

| 項目 | 読み方 |
| --- | --- |
| `value` | 8 は、主な実験（そのとき回している Atari・RND・DropMerge などの題材）の Run の結果か実時間に直接効くもの、またはよく使う操作で Run を落とす不具合を消すもの。5 は、実験や開発の作業で目に見えて効くもの。3 は、限られた場面で効くもの、保守の手間が減るもの。2 は、文書・コメント・エラー文の整合 |
| `urgency` | 期日の決まったリリースが無い間は 13 を使わない。8 は、今の Run や作業で毎回当たるもの、遅らせるほど直す量が増えるもの。5 は、予定している作業（次にグリルする PRD など）を始めると当たるもの。2 は、既定でない構成やまれな操作でだけ当たるもの。1 は、PRD が「着手しない」と書くもの、条件待ちのもの |
| `risk` | 8 は、設定や条件の誤りが黙って通り、違う条件の Run の結果が残るもののうち、使っている構成か、よくある誤り（綴りの誤りなど）で起きるもの。使っていない設定でだけ起きるなら 2 にする。5 は、`depends` の先になっているもの（待たれている側）、Run を落とす経路を塞ぐもの、既定で有効な処理を守るもの。8 と 5 の両方に当たるときは 8 にする |
| `size` | 下の表による |

`depends` に課題を足すと、待たれている側が 5 の条件に当たる。そのため、`anet-update-issue` で既存の課題の `depends` に課題を足す開発者の指示は、待たれている側の `risk` が 5 未満なら 5 に上げて `wsjf` を計算し直す指示を含む。待たれている側の `risk` が 5 以上なら変えない。起票（`anet-audit` の起票を含む）で新しい課題の `depends` に既存の課題を書いたときは、起票の手順のとおり新しい課題のファイルだけを書き、待たれている側は変えない。その `risk` は棚卸しで見直す。

`size` は、次の行を上から当て、最初に当たった値にする。

| 条件 | `size` |
| --- | --- |
| 大量の移動か、外部の判断を含む | 13 |
| 直すのが文書・コメント・設定の数行だけである（PRD の課題も含む） | 上の目安の 1〜3 から選ぶ |
| グリル前の暫定 PRD の仕事を表す PRD の課題 | 8 |
| 設計が確定済みの PRD の仕事を表す PRD の課題 | 5 |
| 上のどれにも当たらない | 上の目安から選ぶ |

`anet-audit` のホットスポット補正は、この読みで決めた `urgency` を 1 段（1・2・3・5・8・13 の隣の値へ）上げ下げする。隣の値が無いとき（1 から下げる）と、上げた先が 13 で期日の決まったリリースが無いときは変えない。補正したときは、そのことと理由を背景に書き、`wsjf` を計算し直す。棚卸しで見直すときは、背景に補正の記録がある課題に、同じ補正をかけて比べる。

### 管理外のメモ

`priority`・`memo`・`tags` は、開発者が Obsidian などで課題のファイルを直接書き換えるメモである。監理の項目ではなく、`anet-update-issue` を通さない。

| 項目 | 書き方 |
| --- | --- |
| `priority` | 直近の手の付け方のメモ。起票では `中`（メモ無し）を置く。開発者は、直近で手を付けたいものを `高`、当面は後回しにするものを `低` などと書く |
| `memo` | 自由なメモ。文字列でもリストでもよい。起票では空にする |
| `tags` | 横断のテーマ（NGU・RND など、分類や `area` と別の切り口）。Obsidian 標準のタグの欄で、タグの一覧や検索で絞れる。起票では `[]` にする |

- AI は、起票の値を置くほかは自分の判断で書き換えず、見直しも提案しない。開発者に書き換えを頼まれたときは、`anet-update-issue` を通さずに、頼まれた欄の値だけをファイルで書き換える（対応内容と備考は書かない）。課題の中身（効果・時間・リスク・手間）の評価は `wsjf` の 4 つの値で表し、`priority` には持たせない
- 一覧を作る道具（`reports/tools/wiki_support.py`）は値を検査せず、一覧（`INDEX.md`）と地図の「課題」の区画に出さず、並びにも使わない。書き換えても一覧と地図は変わらないので、一覧の作り直しやコミットを合わせなくてよい
- 統計（`reports/tools/stats.py`）は、本版の課題の `priority` の件数だけを数える（欄が無いか空なら「（無し）」）。統計は取ったときの作業ツリーの写しなので、書き換えと統計の取り直しを合わせなくてよい。`memo` と `tags` は数えない
- 扱わないと決めた課題は、`priority` ではなく状態を `次版` にする
- 欄が無くてもよい（開発者が消してもよい）。一覧（`anet-list-issues`）も、欄が無いことを欠けとして報告しない

## 分け方

**1 課題は、1 つの判断で閉じられる問題とする。** 直し方の方針が 1 つに決まる単位であり、症状の数では分けない。

| 場合 | 扱い |
| --- | --- |
| 同じ原因で、直す場所も同じ | **新しく起票せず、既存の課題へ追記する。** 工程を動かして見つかった事例・実測・新しい根拠もここに当たる |
| 直す時期が違う（本版／次版）、判断の前提が違う、別々に直せる | 分ける |
| 決めることが 3 つ以上あり、それぞれ別々に決めて直せる | 親と子に分ける。子の `parent` に親のリンクを書く |
| 1 件の課題から PRD を 2 本以上起こす | 元の課題を親にし、PRD ごとに子の課題を作って、子の `prd` にその PRD を書く（1 件の課題が指せる PRD は 1 本まで） |
| 片方を直さないと、もう片方を直せない、または直し方が決まらない | 分けたうえで、後のほうの `depends` に前のほうを書く |

工程末の候補で「新規」か「既存へ追記」かを決めるときも、この表による（`docs/process/protocol.md` 7 節）。

## いつ起票するか

**起票する時機は `docs/process/protocol.md` 7 節による。**

要点だけ再掲する。**本 SKILL が呼ばれるのは、開発者が採用を決めたあとである。**

| 呼ばれ方 | |
| --- | --- |
| 工程末 | 候補を提示し、**開発者が選んだものについて**本 SKILL が呼ばれる |
| 工程の途中で止まるとき | 上流の成果物の食い違いや誤りで止まるときは、候補を提示し、開発者が選んだものについて呼ばれる（`docs/process/protocol.md` 5 節） |
| 開発者の指示 | 候補の提示を省いて直接呼ばれる |

**自分の判断で書き始めないこと。** 候補の挙げ方と判定は `docs/process/protocol.md` 7 節が定める。`anet-audit` の起動（housekeeping の了承を含む）は新しい指摘を記録する指示とみなす。PRD 起票の指示には、PRD の課題（題材の課題が無いときの、その PRD の仕事の課題と、題材の課題で覆えない仕事の課題）の作成が含まれる。

## 起票の指針

- 原因が分からなくても書いてよい。`status` を `調査中` にする
- 課題から PRD を起こすときは `anet-create-prd` に ID を渡す。統合・分割は、開発者の指示で本 skill と `anet-update-issue` が記録する
- **1 ファイルに 1 課題だけ書く。** 関連する課題でもファイルを分け、本文で相互に参照する（親子の対応は除く。子の `parent` だけで持つ）。単位は「分け方」による
