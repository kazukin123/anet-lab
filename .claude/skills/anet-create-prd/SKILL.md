# PRD の作成・改訂

[プロセス契約](../../../docs/process/protocol.md) の Step 1〜6 に従う入口。anet での対応は [レジストリ](../../../docs/process/registry.md)、自己点検は [PRD 品質確認観点](../../../docs/quality/prd.md) による。プロセス契約とレジストリを先に読み、工程固有の手順だけを本書で補う。PRD のテンプレートは作らない。

引数は題材、issue の ID（カンマ区切り）、または既存 PRD のファイル名。既存 PRD は改訂として扱う。成果物は PRD、PRD の課題（`prd` でその PRD を指す課題）の結び付け、必要な用語集・ADR と wiki の更新。レジストリの「この場で直す」（ビルドもテストも要らない直し）を除き、実装へは進まない。

開発者への応答で既存の課題と PRD を名指すときは、その応答で最初に出る箇所を、ファイルへのリンク（リンクにできない環境や質問欄ではパス）にする。課題には題名（長ければ要点だけ）を添え、PRD はファイル名をリンクの文字にする。`docs/memo/done/` などへ移った PRD も、今ある置き場へリンクする。対象を決めたとき（改訂する PRD と複数一致の候補、その PRD の課題、題材の課題、止まる理由に挙げる課題とその結び付き先の PRD）に限らず、グリルで取り込む課題、起票の候補の「既存へ追記」の先、関係する別の PRD への言及も同じにする。ファイルが無い ID や名前はリンクにしない。開発者が、どの課題・PRD かを応答の中で分かり、前の応答を探さずに開いて確かめられるようにするためである。

## 1. 対象を決める

新規か改訂かを決める。既存 PRD は `docs/memo/` のサブフォルダも含めて完全一致で探し、本文と引用する ADR を読む。複数一致または未発見なら対象を尋ねる。issue の ID が渡されたときは、下の「issue を題材にする」を先に通す。

最初の応答の前に、`docs/wiki/index.md` を題材の語（別名を含む）で引き、関係する知見のページと、触る部分のアプリケーション・機能カテゴリのページ（トピック別まとめ）を読む。読んだページ名を1行で示す（関係するページが無ければ「なし」）。既存 PRD なら要点提示、新規なら goal anchor を示す応答に置く。出典と食い違う箇所は起草で直すために控える。

読んだトピック別まとめの「選ばなかった形」「変えるときの条件」のうち今回に関係するものを、「触る既存部品の働き」に添える。既存PRDなら要点提示、新規ならgoal anchorの応答に置く。「不採用」の形を選択肢にする場合は出典と、下記の「再グリルで開き直す条件」のどれに当たるかを示す。別の題材・ゴールでの採用は前提の変化に含める。「先送り」「範囲外」は再開条件が揃ったかを添えて出してよい。

同じく最初の応答の前に、[PRD 品質確認観点](../../../docs/quality/prd.md)を読む。読んだ節の名前を応答に 1 行で示す。

### 既存 PRD の要点提示

既存 PRD や題材に対応する設計メモがある場合、最初に1画面程度で次を平易に示す。章ごとの転記ではなく、共有する前提の説明にする。

- 問題、ゴール、非ゴール。
- 設計の形を決める主要な決定と、その根拠の ADR。触る既存部品の働きも1行ずつ示す。
- 未決、暫定値、要確認事項。
- 過去のグリルと改訂時期。主要な決定の前提だけを現行コード・用語集・後続の判断と照合し、ずれが無ければそう示す。前提の表（段3の「前提の表」）がある PRD では、表の行で照合する。
- 今回検討する論点の見込み。

会話の途中で新しい事実（実機の報告、調査の結果、レビューの指摘）から再グリルに入るときも、問いの前に、新しい事実、影響を受ける決定、候補の案を 1 画面で整理して示す。新しい事実は、前提の表の行に足すか直し、共通の前提として示す（段2の「共通の前提と確かめ」）。

主要な決定の前提の照合には wiki の知見を使い、触る既存部品の働きにはトピック別まとめを使う。wiki はまとめなので、PRD が依存する事実は元の出典を確認して PRD 本文に出典つきで書く。

同じ応答に goal anchor と共通の前提の一覧（段2の「共通の前提と確かめ」）を示し、既存内容への質問に答えてから質疑へ入る。説明と決め直しを混ぜない。

### 再グリルで開き直す条件

確定事項を再び問うのは、前提が変わった、コードや新しい証拠と矛盾した、あとの決定で不要になった、ユーザーが求めた、別モデルが結論に反対した、のいずれかだけである。理由や前提を問うだけの論点は開き直さず、本文を補って示す。暫定の印（下の「暫定と Plan Mode」）がある PRD は、確定した決定を持たないので、この条件によらず、未決表の各行を決まっていない論点として段2の「論点の仕分け」に通す（仕分けたあとの振り分けは「暫定と Plan Mode」の 3 段落目）。暫定の印があり、未決表のほかに、確定事項や「提案の骨子（暫定の既定）」などの節にも暫定の既定を置いた PRD（この決まりより前の暫定の起票）は、その節の各行も同じく通す。

## 2. 質疑

共通理解に達するまで、設計の決定木を枝ごとにたどり、決定どうしの依存を1つずつ解く。ほかの決定が依存する決定から先に扱う。たどった論点は下の「論点の仕分け」で分け、①②④⑤⑥はその区分に従って調査・確かめ方の整理・実装計画や未決表への記録を行う。ユーザーに問う論点は③だけにする。

問いを出す前に、推奨の理由か選択肢の挙動が、まだ聞いていない問いの答えで変わるかを確かめる。変わるなら、そちらを先に聞く（依存の順の自己点検）。

「読む時機で値が違う」型の問題では、方式を選ぶ前に、その値がイベント時点の事実か（イベントのデータで運ぶ）、今の状態か（問い合わせる）を決める。

### goal anchor

goal anchor の応答を出す前に、`anet-update-issue` の「工程の出来事」で、題材の課題（改訂と再グリルでは、その PRD の課題も）を調査中にする。暫定の起票では質疑が無いので変えない。Plan Mode の間は書かず、Plan Mode を抜けて起草に入るときに書く。

解く問題、ゴール、明示された非ゴールを短く示し、合意を得る。以後の判断はこのゴールに照らす。途中で方向がずれた場合は、ゴール自体が変わったかを確認する。同じ応答に、共通の前提の一覧と確かめの文言を置く（次の「共通の前提と確かめ」）。

### 共通の前提と確かめ

問いに答えるには、その判断に要る前提を開発者が理解している必要がある。前提は、事実（コード・文書・測定）、用語、既存部品の働き、過去の判断（ADR・選ばなかった形）、守る線（規約・非ゴール）である。示す前提の数や細かさは規則で縛らず、AI が判断する。開発者が指定すれば、理解が不完全でも、前提が欠けていても、問いへ進む。

- **共通の前提の一覧**: 2 つ以上の論点が使う前提と、全体の流れの前提を、goal anchor の応答（既存 PRD では要点提示と goal anchor を示す応答）に番号つきで並べる。どれを共通にするかは AI が判断する。各行は番号（P1 から）・内容・出典（開けるリンク。文書は節の行、コードは行番号まで）にし、開発者にとって新しい前提（その会話でも、その PRD の前のグリルでも扱っていないもの。今回の測定、初めて触る部品など）に「新」と付ける。前提の表（段3）がある PRD では、表を読んで示し、確かめの列が「飛ばした」の行と、暫定の印がある PRD の行には「新」を付けて示し直す。共通の前提が無ければ「共通の前提はありません」の 1 行を置く。
- **確かめ**: 応答の末尾に「ゴールと非ゴールはこれでよいですか。あわせて、説明が要る前提・違うと思う前提があれば、番号を挙げてください」と置き、本文で聞く（質問欄は使わない。番号を自由に返す形で、前提が 5 つ以上だと選択肢に収まらないため）。番号が挙がったら説明する。返事が前提に触れなければ、説明が要る番号は無いものとして進め、下の食い違いの指摘で補う。開発者が確かめを飛ばすと言えば飛ばす。結果は前提の表の確かめの列に書く（段3）。理解を深める往復（説明や具体例を求める返答と、その答え）は、減らす対象にしない。
- **追加の共通の前提**: scope screen で共通の前提が増えたら、最初の個別の問いの応答に「追加の共通の前提」として添える。
- **この問いの前提**: 1 つの論点だけの前提は、その問いに添える（「選択肢の示し方」）。
- **食い違いの指摘**: 問いの答えが示した前提と食い違うときは、記録する前に、食い違う前提の番号と中身を示して確かめる。
- **欠けた前提の印**: 一覧の前提が欠けていると分かったら、その応答では「欠け」の印を付けて示すだけにし、扱いは下の「欠けた前提」で、ゴールの合意のあと scope screen より前に聞く。1 つの返事に、ゴールの合意・前提の番号・欠けた前提の扱いを混ぜないためである。

改訂と再グリルでも行う。前提の表が無い既存の PRD では、本文から前提を拾って示し、起草で表を足す。暫定の起票は質疑を省くので、確かめは行わない（「暫定と Plan Mode」）。

### 欠けた前提

欠けた前提は、コードや文書を読んでも分からず、測定・試作・調べものの結果が要る前提である。読めば分かるものは、その場で調べて示す（「論点の仕分け」の①）。

欠けた前提が分かったら（goal anchor の応答でも問いの途中でも）、欠けた前提ごとに 1 問ずつ、「先にそろえる」「結果ごとの分かれ方で決める」「前提なしで決める」を推奨つきで聞く。同じ測定や調べものでそろう前提は、1 つの論点としてまとめて 1 問にしてよい。推奨の目安は、結果しだいで、ほかの決定がよりどころにする決定の推奨が変わるなら「先にそろえる」、変わらないなら「分かれ方で決める」である。

- **結果ごとの分かれ方で決める**: 「論点の仕分け」の④と同じく、確かめ方と結果ごとの分かれ方を未決表に書く。前提の表の出典は「欠け」とし、「分かれ方で決めた」と未決表の番号を添える。
- **前提なしで決める**: 前提の表の出典を「欠け」とし、「前提なしで決めた」と添える。
- **先にそろえる（すぐ済むもの）**: 調べものや短い試作は、その場でそろえて続ける。結果は PRD の現状の節に書き（PRD がまだ無ければ起草で書く）、前提の表の出典はその節を指す。
- **先にそろえる（時間がかかるもの）**: 測定・build・Run が要るものは、グリルを止めて PRD を書く。build と Run の起動は [AGENTS.md](../../../AGENTS.md) の決まりに従う。止めるときは次のとおりにする。
  - PRD には、それまでの決定、前提の表、グリルの材料、そろえる段（問い・測り方・結果ごとの分かれ方の表）、まだ聞いていない論点（未決表）を書く。会話を持たない別のセッションが続けても、何を問うかを拾い直さずに済むようにするためである。
  - 冒頭の行（新規なら起票の行、改訂なら改訂の行）に「前提をそろえるためにグリルを止めた」と書く。改訂のときは、そのグリルで決めた・決め直した決定の番号も書き、レビュー済みの確定事項と見分けられるようにする。
  - 段5の自己点検は、書いた節に当たる項目だけを通し、書いていない節（受入・実装契約・移行対象など）は、未決表に「グリルを続けて書く」と記す。PRD 品質確認観点の項番 43 の「グリルを終えた PRD」の確かめは当てない。段6のレビューは受けず、グリルを続けて終えたときに受ける。wiki への書き戻し（段3・段7）は行う。段5の3行（改訂のときは4行）は止めるときの報告に置き、その「レビュー結果」には、受けていないことと、受ける時機（グリルを続けて終えたとき）を書く。
  - 段5の末尾の「残る未決をまとめて1問で聞く」は行わず、段7の起票の候補も示さない。未決表の行（まだ聞いていない論点、「グリルを続けて書く」の行、範囲外の候補）は、グリルを続けて終えたときに扱う。止めるのは同じ工程の途中で、残る論点はグリルを続けて問うためであり、欠けた前提がそろわないうちに推奨の既定で埋めないためである。
  - 題材の課題の状態は調査中のまま変えず、新しい課題も起こさない（プロセス契約の停止条件 8 に当たらない）。題材の課題の対応内容に、止めたこと・そろえる前提・続ける条件を 1 行足す。状態から待ちが見えないので、待っているものを課題に残すためである。
  - Plan Mode のときは PRD を書かず、決まったこと・前提・そろえる段・残る論点を計画として示し、承認を受けて Plan Mode を抜けてから書く。
- **止めたグリルを続ける**: そろったら、同じ PRD を渡して続ける。結果を現状の節に書き、前提の表の出典を直す。止める前の決定は開き直さない。開き直すのは、そろえた結果がその決定の前提を変えたか、決定と矛盾したときだけである（「再グリルで開き直す条件」）。終えたら、冒頭の改訂行に、グリルを続けて終えた旨を書く。

### scope screen

新しい機構・概念ごとに、ゴールへの寄与を確認する。仮説を確かめる PRD では、仮説・比べ方・終わり方を確認する。「今は要らない」を理由に削らない。実装の負荷は AI が持つため、後で要るものは同時に作る。器や抽象は、確定した要求から導ける最小の形で提案する。

非ゴールや「変えない」で案を消すときは、消える案を名指しし、それが本当の制約か（クリーンブレークで移せないか）を 1 行で書く。

先送りできるのは、実験結果が無いと決められない場合と、別の関心なので別 PRD にする場合だけ。先送りの理由と、何が揃ったら作るかを PRD 本文に記録する。

後で要るので同時に作るものは、次の境界で詰める。

| 区分 | 対象 | 決め方 |
|---|---|---|
| 契約 | 外から見える振る舞い・設定キー・公開 API・メトリクス名、既存部品との受け渡し・持ち主・失敗時の挙動など、PRD が設計として決めるもの全部 | 1問ずつ |
| 細部 | 契約の枠の中の値や方式で、推奨の既定が契約や他の決定から出るもの。既定値、閾値、表示・ログ書式など | 契約を詰めたあと、推奨の既定と理由の一覧の扱いを1問で聞く |
| 実装の詳細（⑤） | PRD の契約に効かない関数分割やファイル配置など | 実装計画へ送る |

細部の一覧は `<番号>. <事項>: <推奨の既定>（理由: 1 行）` とする。プロセス契約1.2節の切り上げと同じ形で「推奨で埋める／後で決める／1件ずつ聞く」を問う。切り上げ以外にもこの形を使う読み替えはレジストリにある。答えは PRD に書き、「後で決める」は未決表へ残す。追加の会話なしで実装へ入れる状態にするため、細部を実装計画へ送らない。細部の一覧の1問は「一覧の扱い」という1つの論点を問うもので、別々の判断を並べて各々への回答を要求しない。

メトリクスを足す PRD では、tag を定義する設定ファイルとプロファイル（`metrics_scalar.txt` の `metrics.scalar.@munchausen` など）と、そのプロファイルを Run プロファイルの既定の連鎖に入れるかを、細部の一覧の行に入れる。既定の連鎖に入れて基準の比較が変わるなら、細部ではなく契約として聞く。決めずに起草すると、足す設定、移行対象、受入の節で書き方が食い違うためである。

クラス構成と名前は細部にも⑤にも入れず、起草のクラス一覧に書く。

### 論点の仕分け

| 区分 | 扱い |
|---|---|
| ① コードや文書で分かる事実 | 調べ、根拠のリンクを添えて示す。聞かない |
| ② 規約・ADR・CONTEXT.md・現行コード、または質疑で決めた決定の組み合わせから一意に導ける事項 | 聞かずに一覧で示す。導いた根拠の所在を少なくとも1つ示せるものに限る（決定の組み合わせから導いた帰結は、導いた決定の名指しが根拠） |
| ③ ゴール・優先度・許容する不利益の選択 | 推奨案を添えて1問ずつ聞き、回答を待つ |
| ④ 実験・試作でしか分からない事項 | 確かめ方と、結果ごとの分かれ方を決める。先にそろえるかは「欠けた前提」で開発者が選ぶ。分かれ方で決めたら、前提の表の出典に「欠け」と扱いを書く |
| ⑤ PRD の契約に効かない実装の詳細 | 実装計画へ送る。クラス構成と名前は除く |
| ⑥ 範囲外 | issue の候補にする。工程中は未決表に貯める。起票はプロセス契約7節とレジストリに従い、ユーザーが選んだものだけ行う |

①と②の根拠は、人がすぐ開けるリンクで示す。文書は該当節の行、ADR はファイル、コードは行番号付きにする。質疑で決めた決定の組み合わせから導いた帰結の行だけは、導いた決定の名指し（D1・D2 など）を根拠とし、リンクは要らない。

① でコードの振る舞いを事実にするとき、または ② の根拠にするときは、その値や結果を使う側の入口から当該の処理までを辿り、入口の位置も挙げる。外部ライブラリでは利用者の操作の入口（イベントの受け口）、このリポジトリのコードでは値を読む側の呼び出し（Evaluation Trace が列の値を読む箇所、Replay が次の観測を返す箇所など）が入口である。作る側の関数や、途中の 1 つの関数だけで判定しない。入口を辿れないか、条件分岐が多いなら ④ にして試作で確かめる。

① で「〜だけ」「〜しかない」「n 件」と書く事実は、出力を切らずに（`head` や件数の上限を付けずに）引いた検索の結果から書き、根拠に検索語・検索した範囲・件数を添える。切った結果からは「少なくとも」までしか書かない。出典の数値を写すときは、出典の表の区間（窓）と値をそのまま書き、区間を変えたり丸めたりしない。切った検索や言い換えた値の誤りは、出典と照らすレビューまで見えないためである。

決定の組み合わせで、利用者の操作でできること・できないことが変わる帰結は、理由欄の 1 行で済ませず、独立に示す。対になるもの（Train View と Evaluation View など）の片方だけが不可になる、ある操作が常に不可になる、など、許容する不利益の選択に当たる帰結は ③ として聞く（② には出さない）。それ以外の、決定から一意に導ける帰結（最後の 1 つは動かせない、など）は ② の一覧に「帰結」の行として出し、根拠には導いた決定の名指し（D1・D2 など）を書く。質疑の途中で分かった帰結は、その応答の問いに添える ② の追加の行か ③ の問いにし、最初の一覧へ戻さない。

②の一覧は、scope screen 後の最初の個別の問いと同じ応答で示す。質疑の途中で分かった ② の事項（決定の組み合わせの帰結など）は、その応答の問いに添えて追加の行で示す。goal anchor の合意と scope screen の確認はこの問いに数えない。当たる事項が無ければ一覧は出さない。各行は `<番号>. <事項>: <導いた内容>（根拠: <リンク>）` とし（帰結の行は `（根拠: D1・D2）` のように導いた決定の名指し）、ユーザーが番号を挙げれば③へ戻す。根拠の所在（帰結の行なら導いた決定）を示せないものは③として聞く。推奨案があることは、一意に導けることではない。実質の選択を「既定値」の名目で②へ入れない。

性能の受入を持つ PRD で、ホットパス（step のループ、学習との重なり、thread pool）の順番や回数を変える案を選ぶ前に、頻度×単価を step 単位で見積もって本文に書く。受入の閾値の半分を超える見込みなら、決める前に試作で測る（④）。

### 選択肢の示し方

各案を正常・境界・失敗時の具体的な挙動で比較する。該当する API の呼び出し例や設定例（コロン記法）を添え、性能と保守性のどちらで有利かを書く。速さが変わらない案どうしは、正しさと保守性で比べる。テストと設計文書の書き換えは、テスト・文書として成り立つ限り欠点に数えない。未共有の概念を名前だけで出さない。PRD の節番号や決定の番号（§2.5、D3 など）で中身を指して済ませず、何がどう困るかをその場で 1 文で書く。用語、具体例、コードとの照合は後述の Domain awareness と During the session に従う。

1 つの論点だけの前提は、その問いに「この問いの前提」として添え、番号を振って前提の表（段3）に入れる。推奨の理由には、よりどころにした前提を、番号と 1 句の中身で書く（例: 「推奨: X（P3 の、プロセス契約は anet の外でも使うことによる）」）。推奨をそのまま選ぶ答えは前提と食い違いようがないので、前提を取り違えていれば理由を読んで気づけるようにするためである。

弱点が案の一部の作りだけにあるなら、弱点の無い作りも比べる表に入れる。却下の根拠はコードで確かめる。ユーザーの発言を推奨の根拠に引くとき、読みが 2 つあれば両方を示して確かめる。部品の持ち主を決める論点では、使う部品が自分で作って持つ案を、比べる表に入れる。既存の文書の一般則（所有の慣習など）を推奨の根拠に引くときは、それが正しさの理由か、慣習かを分けて書く。

アルゴリズム（学習則、優先度、正規化など）と指標の式を選ぶ問いでは、問いを出す前に、文献と公開実装でどうしているかを確かめ、比べる表に「事例」の行を入れる。ソースとフォルダの構成、名前の付け方、ビルドと配置の分け方、テストの置き場と参照できる範囲のように、ほかのプロジェクトも同じことを決めていて、広く使われる型がある事柄を選ぶ問いでも、同じにする。この種の問いで確かめる先は、広く使われている公開のプロジェクトと、道具（ビルドの道具、テストの枠組みなど）の公式の文書である。確かめられなかったものは「未確認」、記憶だけによるものは「記憶による」と書く。アルゴリズムと指標の式を選ぶ問いで事例の無い案（その PRD で考えた指標の式など）は、境界の挙動（分母が 0 に近い局面、符号の向き、値が平らな局面）を具体の数で示す。広く使われる型がある事柄を選ぶ問いで事例の無い案は、「事例」の行に事例が無いと書けば足り、境界の挙動を数で示すことは求めない。

新しい設定キー、メトリクスの鍵、仕組みを案にするときは、同じ役の既存のもの（勾配の扱いを切り替える skip の `feature_gradient` など）をリポジトリで検索する。流用できるかを比べる表に入れ、名前と値の語、値の意味（掛ける係数・単位）をそろえるかを決定の理由に書く。そろえないときは、その理由を書く。

案が既存の部品の形（口の引数、列の数、保存の形、設定キーなど）を変えるときは、問いを出す前に、その部品名と用語で `docs/adr` のファイル名を引き、当たった ADR を読む（[AGENTS.md](../../../AGENTS.md) の「設計判断の記録(ADR)を読む条件」の 1 つ目）。案が ADR の判断と食い違うなら、その ADR と判断を選択肢の挙動に書く。

質問は1問ずつとし、明示的な回答を待つ。無回答や時間の経過を同意と扱わない。質問欄が返す自動の値（`[No preference]`、`did not answer` など）も無回答で、そのときは質問欄が届いていない（Remote Control 越しなど）とみなし、本文に選択肢を書いて聞き直す。コードや文書で解ける疑問は探索して解く。

### 問いを出し直すとき

説明を求められて答えたあと、回答が問いに合っていなかったとき、ほかの論点を挟んで戻るとき、別モデルの検討の論点として聞くときなど、前に出した問いをもう一度出すときも、その応答だけで答えられるように書く。

- 論点、決めると何が変わるか、選択肢ごとの具体的な挙動、性能と保守性の比較、推奨とその理由を、前の応答と同じだけ省かずに示す。
- 「上の表」「前と同じ」「先ほどの A」のように、前の応答を参照させて省かない。チャットが長くなると、ユーザーは前の応答を探すことになる。
- あいだの説明や回答で変わった点（選択肢の増減、推奨の変更、前提の訂正）は反映し、何が変わったかを1行で添える。
- 選択式の問い（質問欄）を使う場合も、各選択肢の説明を、ほかの応答を見なくても意味が分かる文にする。

### 暫定と Plan Mode

「暫定」と指示された起票では質疑を省き、決めきれない点を未決表へ書く。暫定でも起票時に正式番号を取り、PRD の課題を結び付ける（段3）。番号は memo README の「採番」に従って取る。仮の共有番号は作らない。

暫定の起票の PRD には、確定した決定を置かず、確定事項の節を作らない。起点の会話で方向が出ている点も、決めきれない点も、未決表の行にする。AI が置いた既定は、その行の「暫定の既定」の列に、理由と依存とともに書く。実装契約・受入・移行対象などの節は、暫定の既定を前提に書いてよく、前提にした未決表の番号を名指す。冒頭の起票の行には「暫定」と書く。起票の行に「暫定」があり、冒頭の改訂行に、その PRD 自身のグリル（再グリル）を終えた記録が無い PRD を、以下「暫定の印がある PRD」と呼ぶ。ほかの PRD のグリルへの言及や、これからグリルする予定は、終えた記録に当たらない。グリルを終えた PRD は、起票の行に「暫定」が残っていても印が無い（以前の決まりで再グリルした PRD も同じ）。起点の会話の方向は冒頭の起点の行に書き、理由に引いてよいが、決定として扱う書き方（「ユーザーの選択」「合意した」など）にしない。暫定の起票は、あとのグリルですべてを見直す前提で置くためであり、確定事項の章に未確定の既定を置くと、見直す予定と添えても確定と紛れるためである。

暫定の起票でも、前提の表（段3）を書く。欠けた前提は出典に「欠け」と書き、確かめの列は「対象外」にする。前提をそろえる段は PRD に書かない。暫定の印がある PRD を再グリルするときは、goal anchor の応答で表の欠けた前提を示し、「欠けた前提」のとおり扱う。

作業を終えた時点で暫定の印が残る PRD（暫定の起票など）は、段6のレビューを受けない。段5の自己点検と、wiki への書き戻し（段3・段7）は行う。PRD のレビューは、その PRD を使うときに受ける。再グリルで印を外すときは段6で、印があるまま実装に入るときは [anet-impl-prd](../anet-impl-prd/PRD-IMPLEMENTATION.md#暫定の印がある-prd) の「暫定の印がある PRD」で受ける。段5の3行（改訂のときは4行）は完了報告に置き、完了報告の「レビュー結果」には、受けていないことと、受ける時機（再グリルか実装の入口）を書く。暫定の起票で欠けた前提があれば、完了報告に、その番号と何が欠けているかを 1 行で置く（例: 「欠けた前提: P3・P7（測定の結果が要る）。再グリルの前にそろえるかは、再グリルの最初に聞きます」）。質問はしない。暫定の PRD は再グリルで未決表のどの行も開き直すので、起票の時点のレビューの指摘の多くは書き直す箇所に付き、再グリルのレビューと二重になるためである。

暫定の印がある PRD を再グリルするときは、未決表の各行を決まっていない論点として段2の「論点の仕分け」に通す。③は問い、②は一覧で示す（ほかの論点と同じ扱いで、③だけを問う）。そのあと、未決表のどの行も、次のどれか 1 つへ振り分ける。

- 確定事項の節（再グリルで新しく作る）へ移す: ③で答えを得た行と、②の行。
- 未決表に残す: ③で「後で決める」と答えた行と、④の行（④は確かめ方も書く）。「暫定の既定」の列は消す。
- 未決表から外して、本文の事実を書く節（現状など）へ移す: ①の行。根拠のリンクを付ける。
- 未決表から外して実装契約のクラス一覧へ移す: クラス構成と名前の行（起草の「クラス一覧」の決まりによる）。
- 未決表から外す: ⑤の行。
- 仕分けの⑥のとおり送る: ⑥の行。

振り分けを終えたら、冒頭の改訂行に、グリルを行って暫定の印を外した旨を書く（起票の行は当時の記録として書き換えない）。暫定の既定を前提に書いた節の「未決表の番号」の名指しは、移した先（確定事項の D 番号など）へ書き換える。印を外したあとの再グリルは「再グリルで開き直す条件」による。暫定の印があり、未決表のほかに、確定事項や「提案の骨子（暫定の既定）」などの節にも暫定の既定を置いた PRD（この決まりより前の暫定の起票）は、その節の各行も未決表の行と同じく振り分ける。

Plan Mode は前提にしない。Plan Mode で起動された場合は、質疑が終わった時点で決まったことを計画として示し、承認を受けて Plan Mode を抜けてから起草へ進む。モード中は PRD・用語集・ADR・wiki を編集しない。どちらのモードで始めても、最後に実装へ進まない。

## issue を題材にする

ID は `issue-`、8 桁の日付、`-`、6 桁の 16 進である。件数に上限は無い。各 ID へ次の条件を上から順に当て、最初に当たった理由を示す。1 件でも該当したら、PRD を書かず、issue も変えずに止まる。

1. 形が違う、またはファイルが無い。
2. 状態が次版か解決である。
3. prd が空でない（結び付き先の PRD を示す。改訂するなら、その PRD のファイル名を渡す）。

docs に文書（PRD を含む）を持つ issue も受け付け、docs は変えない。ただし、docs にその PRD 自身を持つ issue（その PRD に関係するだけとしていた issue）を題材にするか範囲へ取り込むときは、その PRD を docs から消して prd に書く（prd に書いた PRD を docs に重ねない）。parent を持つ issue も受け付け、parent は変えない（1 件の課題から PRD を 2 本以上起こすときは、元の課題を親にした子を題材にする）。グリルで取り込む issue にも同じ条件を当て、該当すればその件を取り込めない理由を示す。ID を渡した起票の指示と、範囲へ取り込む選択は、prd を書く指示を含む。

題材ごとに題・事象・影響・対応方針と現在のコードの根拠を示し、goal anchor に「題材の issue がすべて片付く」を含める。area が複数なら当たる全カテゴリのトピック別まとめを読み、ページが無い件は読まない。

## 3. 起草

PRD と課題は、課題の `prd` 欄で結び付ける（課題と PRD は N:1）。どの PRD にも、`prd` でその PRD を指す課題が 1 件以上あり、PRD の範囲は、それを指す課題の全部で覆う。PRD 専用の窓口の課題は作らない。段7で、次のとおり結び付ける。

- 題材の issue があれば、その `prd` に PRD のリンクを書く。
- 題材の issue で覆えない仕事（PRD のゴールのうち、どの題材にも当たらない部分）があれば、その分の課題を `anet-create-issue` で 1 件作り、`prd` に PRD のリンクを書く。覆えるなら作らない。
- 題材の issue が無い PRD は、その PRD の仕事の課題を 1 件作る。`type` は PRD の中身（機能追加・リファクタリングなど）で決める。

`prd` の書き込みは `anet-update-issue` の開発者の指示のモードで行い、題材のほかの監理の項目は変えない。題材の status は段2の goal anchor で調査中にしたもの（暫定の起票では元のまま）を変えない。既存 PRD の改訂では、その PRD の課題を使う。改訂で仕事を PRD の範囲から外したときは、その課題の `prd` を `docs` へ移す（範囲から外した仕事が残る PRD は、一覧の道具が実装済みにしないため）。

issue を題材にしたか範囲へ取り込んだ PRD には、ID・題・area・現在のコードで確認した根拠の位置・直す確定事項の D 番号・確かめる受入の項番の対応表を置く。未決なら D 番号に代えて未決表の番号を書く。対応表の規約と検査は PRD 品質確認観点の「issue の対応表」に従う。

PRD 本文、必要な `CONTEXT.md` と ADR、および関係する wiki のページを書く。PRD は [memo README](../../../docs/memo/README.md) の工程・採番・リンク規約に従い、会話を知らなくても読めるものにする。作業記録は PRD 本文の確定事項、未決表、冒頭の改訂行が兼ねる。未決の扱いはプロセス契約1節・7節による。

用語を置き換えるときは、一括置換を使わず、置き換え前の語を引用する文（改訂の記録の「〜を〜に改めた」、受入の検索文字列、退けた案の表）を除いて直す。置換のあとに旧い語で検索し、残りが引用だけであることを確かめる。

部品を消す・まとめる提案（設定のプロファイルの整理、クラスの統合など）では、書く前に、消す部品の中身を 1 つずつ（設定の行、選択、メソッドなど）行き先へ割り振る。行き先は、新しい置き場、消す、未決表の行のどれかにする。たとえば Run プロファイルを本流へまとめるなら、まとめる側のプロファイルの行ごとに、新しい置き場（本流、設定ファイル本体、bat の引数など）へ移すか、もう要らないので消すか、決めきれないので未決表の行にするかを決める。割り振らずに「部品を消す」とだけ書くと、中身の一部が行き先を失い、レビューで指摘されるまで気づかないためである。

触るファイルとクラスの名前で `docs/memo/` を検索し、同じ箇所を触るまだ実装していない PRD が見つかれば、実装の順序の扱いを書く。どちらが先かの 2 通りに加え、段階を持つ PRD では、ほかの PRD が段階の切れ目で入る場合と途中で入る場合の扱い（入れてよい時機、取り直す基準）も書く。並んで起票された PRD は、片方の段階の途中で入りうるためである。

### wiki への書き戻し

グリルで分かった知見を、まず PRD 本文に出典つきで書き、その節を出典として wiki の関係するページへまとめる。wiki だけにある知見を作らず、読んで気づいた食い違いもこの段で直す。暫定の起票（質疑を省く場合）でも行う。[wiki の規約](../../../docs/wiki/README.md)に従い、目録を更新し、書いた側が機械的な確かめと公開できない値の走査を行う。最終 blob の記録は段7で行う。

### 前提の表

PRD に「前提」の節を置き（ゴールの節のあと、確定事項の前）、グリルで示した前提（共通の前提と、問いに添えた前提）を表に書く。列は番号・種類・内容（1 行）・出典・確かめである。前提が 1 つも無ければ、節に「なし」と書く。会話を持たない別のセッションが再グリルするとき、表を読めば共通の前提を示し直せるようにし、レビューで書き漏れを見つけられるようにするためである。

- **番号**: P1 から振る。改訂で足すときは続きの番号にし、消しても詰めず、同じ番号を使い直さない。
- **種類**: 事実（コード・文書・測定）、用語、既存部品の働き、過去の判断（ADR・選ばなかった形）、守る線（規約・非ゴール）。
- **出典**: 開けるリンクにし、文書は節の行、コードは行番号まで示す。同じ PRD の中の節は「§3.2」のように節の番号で書く（測定の結果のような長い事実は現状の節に書き、表から指す）。開発者の発言は「開発者の発言（日付）」と書き、グリルの材料の節を指す。リンクにできない出典（セッションの中で確かめた道具の入力の定義など）は、確かめた手段と日付を書く（例: 「Claude Code の道具の入力の定義（2026-11-19 に確認）」）。欠けたまま決めた前提は「欠け」と書き、扱い（「分かれ方で決めた」と未決表の番号、または「前提なしで決めた」）を添える。そろえた前提は、そろえた結果を書いた節を出典にする。
- **確かめ**: 次の 4 つのどれかにし、空欄にしない。「済み」（共通の前提を示し、説明が要る番号が挙がらなかった。追加の共通の前提も同じ）、「説明した」（番号を挙げられて説明した）、「飛ばした」（開発者の指定で確かめそのものを飛ばした）、「対象外」（暫定の起票の前提、1 つの論点だけの前提、起草（別モデルの検討を含む）で足した前提）。

再グリルで表を足すときは、そのグリルで示した前提を書く。既存の決定の理由を、表の番号へ書き換えなくてよい。

グリルの前後の材料（開発者の発言と AI の案）は、「グリルの材料」の節に分けて書き、決定として扱わない。

### 決定の理由と前提

確定事項の各決定（暫定の起票では、未決表の各行の暫定の既定）に理由を書く。その理由が他の決定や事実に依存するときは、何に依存しているかを名指す。依存する前提は、前提の表の番号で名指す。再グリルでの前提の変化と、自己点検での決定の残滓を本文から判定できるようにする。

### 成功の測り方

効果が出たことを確かめる指標を書く。scope screen で先送りしたものには、理由と作る条件を書く。理由は、scope screen が先送りを認める 2 つ（実験の結果が要る、別の関心）のどちらかを名指して書く。

### クラス一覧

足す・変える・消すクラスがあれば、実装契約の節に、名前・区分（新規／変更／削除）・責務（1行）・置き場（機能グループ）の列を持つ一覧を AI が書く。消すだけの PRD でも書く。グリルでは問わない。ユーザーは起草後の問いや実装前に修正でき、実装レビューでも指摘できる。

一覧の直前に必ず次の1行を添える。

> 従えない事情があれば、実装する側が理由を実装計画に書いて変えてよい（質問しない）。

実装は一覧に従うが、上の許可も PRD 自身の契約である。この扱いを実装スキルや読み替え表へ追加しない。

## 5. 自己点検

PRD 品質確認観点の全項目を、各項目の適用範囲に従って通す。加えて次を確認する。

- **行ごとに当てる項目**：項番 14・25・29・34 と、確認内容に「各」「それぞれ」「すべて」のどれかがある項目は、読みながら当てず、対象の行を先に全部挙げて数えてから、1 行ずつ当てる。この定めに当たらない項目は、確認内容が行ごとの中身を問うものでも、この箇条の対象にしない（観点の全項目を通すことは変わらない）。挙げ方は次のとおりにする。項番 29 は、確定事項の番号の全部。項番 14 は、受入の番号の全部。項番 34 は、非ゴールの全行と、確定事項と実装契約を「変えない」「のまま」「残す」「触らない」「範囲外」「対象外」のそれぞれで検索して当たった行。項番 25 は、`CONTEXT.md` の差分で足した語と、PRD が付ける新しい名前。この定めに当たるほかの項目は、確認内容がいう行（導入する機構と概念、題材にした issue、判定を当てた結果の一覧の行など）を同じように挙げる。項番 34 と 25 で挙げた行の数は、下の自己点検の結果の「観点」の行に書く（当たる行が無ければ 0 と書く）。読みながら当てると、言い回しの弱い行（理由が「範囲外」の 1 語だけの非ゴール、名前を「今のまま」にする決定など）を、項目に当たる行と気づかないまま通すためである。
- **目的のずれ**：goal anchor 後に足した機構・要求がゴールに寄与しない、またはゴール自体が動いた場合は、「ゴールを変える／ずれた部分を戻す」を別の1問で聞く。未決をまとめた問いの前に聞き、主要な流れを止める事項の選択肢へ読み替えない。
- **決定の残滓**：後の決定で前提が変わった決定を直し、何を直したかを示す。「〜しない」「触らない」のような否定の形の決定は、同じ対象（ファイル・状態・設定）への操作を書くほかの決定と突き合わせ、食い違えば範囲を限って書き直す。
- **変える経路の検索**（新規の起票でも、今ある規則・手順・経路を変えるとき）：変える規則や経路を書いている箇所（skill、プロセスの文書、設計文書、設定、テスト）をリポジトリで検索し、移行対象を列挙する節（PRD 品質確認観点の項番 15 が見る節）に挙げる。検索語には、変える規則の言い回しに加えて、変える振る舞いの識別子（ログの文言、関数名、設定キー、メトリクス名）を入れ、大文字小文字を区別せずに引く。同じ振る舞いを、文書が「一度 WARN する」「`log.warn` を出す」のように別の言い回しで書くためである。口（関数の引数・戻り値、仮想関数）を変えるときは、変える関数の名前そのもの（`Push(` など）を検索語に入れる。呼び出しに加え、継承して上書きする宣言（テスト用の差し替えを含む）にも当たる。識別子の「関数名」を新しく足す名前だけと読むと、変える口の名前が検索語から漏れるためである。消す・名前を変えるものが一覧になるとき（設定のプロファイル、テストのタグなど）は、一覧の名前の全部を検索語にし、追跡しているファイルの全体を `git grep` で引く。代表の名前だけや、覚えている場所だけで列挙しない。漏れた場所は、移行対象にも直さないものにも入らないまま、レビューまで見つからないためである。検索語と見つかった箇所の数は、新規でも改訂でも、下の自己点検の結果の「観点」の行に書く。改訂のときは、言い回しと識別子の検索を下の (d)・(e) と同じ検索で済ませてよく、そのときもその検索語と件数を「観点」の行に書く。ただし、消す・名前を変えるものの一覧の検索は、改訂でも (d)・(e) で済ませず、追跡しているファイルの全体を引く。(d)・(e) は移行対象に挙げ済みの文書しか見ないので、挙げ漏れた場所が見つからないためである。
- **検索の受入と線引きを実物に当てる**（検索して 0 行や決まった件数を期待する受入を書いたときと、直すもの・残すものの線引き（現用の範囲、過去の記録、除くものなど）を書いたとき。新規でも改訂でも）：受入に書いた検索（線引きだけを書いたときは、線引きが分ける対象を引く検索）を、いまの追跡しているファイルの全体にそのままかけ、当たったファイルを 1 つ残らず、線引きの「直すもの」か「残すもの」のどれかの行へ割り振る。どの行にも入らないファイルが 0 件になるまで、線引きか受入を直す。割り振りは、当たったファイルの総数と、行ごとの件数の合計が一致することで確かめる。1 つのファイルが 2 つの行に入るなら、線引きを直す。代表の種類や、思いついた置き場だけで数えない。線引きを書くときに思い浮かべなかった種類のファイル（課題記録、検証資材、道具が作る生成物、Git の設定など）が、直すものにも残すものにも入らないまま、レビューまで見つからないためである。0 行を期待する検索は、あわせて、変更のあとに正しく残る新しい名前（新しいパス、新しいターゲット名など）の一覧に同じ検索をかけ、当たらないことを確かめる。当たるなら、検索の文字列を変えるか、数える前に除く文字列を受入に書く。旧い名前が新しい名前の一部になる（旧い `aaa/bbb/` を `src/aaa/bbb/` へ移すなど）と、移行が済んでも 0 行にならないためである。当たったファイルの総数と行ごとの件数、新しい名前に当てた結果は、下の自己点検の結果の「観点」の行に書く。
- **改訂の突き合わせ**（改訂のとき）：観点の点検と「目的のずれ」「決定の残滓」の直しを終えたあとに、レビュー依頼の「変更箇所」の一覧を書き、(a) 冒頭の改訂行と、細部・未決の節の前文などの改訂の記録（この一覧から書き起こし、編集の前に書いた記録を残さない）、(b) 同じ事項を列挙する複製（文書の更新先、「変えないもの」「守ること」の例外など。1 か所を正本と宣言し、ほかは「§x の例外を除き」のように参照にする）、(c) 訂正した事実の行の位置列（行番号）、(d) 移行対象の文書（jp・en・検証資材）を旧い文言で検索した結果と、断定が変わる既存テスト（受入が指すテストのタグで検索し、新しい規則で成り立たなくなる断定を、移行対象を列挙する節（PRD 品質確認観点の項番 15 が見る節）に挙げる）、(e) 足した列挙や規則が覆うべき箇所（同じ操作を使う受入、同じ規則の写し、件数を書く箇所）を検索した結果、をその一覧と突き合わせる。突き合わせで直したものは、一覧と (a) の記録に足してから結果を示す。

自己点検の結果は、次の3行（改訂のときは、改訂の突き合わせの行を足した4行）で示す。該当が無い場合も含めて必ずこの順で書き、機械的な検査の結果だけで済ませない。必ず置く応答は段6で定める（レビューを受けない暫定の PRD は「暫定と Plan Mode」、前提をそろえるためにグリルを止めた PRD は「欠けた前提」）。

```text
観点: 全項目を通した（直したもの: …／なし。行ごとの項目: 項番 34 に n 行・項番 25 に n 語。経路の検索: <検索語> n 件（今ある規則・手順・経路を変えるときだけ。新規・改訂とも）。割り振り: 当たり n 件＝直す a 件＋残す b 件、新しい名前への当たり 0 件（検索の受入か線引きを書いたときだけ。新規・改訂とも））
```

## 6. レビューと差し戻し対応

作業を終えた時点で暫定の印が残る PRD と、前提をそろえるためにグリルを止めた PRD は、この段を行わずに段7へ進む（「暫定と Plan Mode」「欠けた前提」）。それ以外の PRD は、レビューを必ず独立したコンテキストの `anet-review-agent` で受ける。依頼の組み立てと起動・続けての依頼は [anet-review](../anet-review/SKILL.md) の「2. 依頼を組み立てる」「3. 呼ぶ」を参照する。同じ手順を書き写さない。応答原文の保存は同スキルの「原文を保存する」に従う。

`anet-review-agent` へ最初の依頼を出す応答には、段5の3行（改訂のときは4行）を必ず置く。それより前の応答で自己点検の結果を示した場合や、別モデルの検討を待つ間に点検した場合も、この応答にもう一度置く。自己点検に専用の応答が無いと、見立てが隣の報告に紛れて抜けるためである。続けての依頼（2往復目以降）の応答には置かない。

レビュー専用入口の「成果物を直さず停止する」は、この工程の差し戻し対応へ適用しない。プロセス契約 Step 4・5、1.3節に従い、指摘を仕分け、自分で直せるものをまとめて直してから同じレビューエージェントへ出し直す。往復のたびにユーザーへ返さない。判断待ち・停止、レビュー後に残る未決への質問はプロセス契約による。

出し直す前に、プロセス契約 1.3 節の「直した箇所の帰結を自分で洗う」の表の行ごとに、直した節・用語・値・規則を検索語にして PRD とその移行対象を検索し、見つかった帰結を同じ往復で直す。検索の先には、PRD とその移行対象に加えて、直しで中身が変わる部品の `CONTEXT.md` の項目と、その部品の判断を記録する ADR を必ず入れる。ADR は、いつ書いたかによらず、部品名で `docs/adr` のファイル名を引いて見つける。部品の中身を変える直しは、その部品を定義する用語集の項目と、判断を記録する ADR にも帰結が出るが、移行対象に挙げ済みの文書だけを引いても見つからないためである。その往復で起こした・直した ADR は、あわせて、題と 1〜3 文に収まり PRD を写していないか（PRD 品質確認観点の項番 22）も確かめる。とくに、判定の規則や範囲（残す・消す・直すを決める規則、在庫・除外など）を足したり変えたりしたときは、その規則を実物（設定の名前、テスト、資材などの一覧）に当て、何が残り、何が消え、何を直すかの結果を手元で表にする。その結果を、同じ範囲を書くほかの節（受入、移行対象、例外の注記）と 1 行ずつ突き合わせる。規則が、検索に当たるファイルを直すもの・残すものに分ける線引きなら、段5の「検索の受入と線引きを実物に当てる」をもう一度行い、当たったファイルの全部を割り振って、どの行にも入らないファイルが 0 件であることを確かめる。指摘された種類のファイルだけを足して出し直さない。文字列の検索だけでは、規則を変えたことで結果が変わる実物（規則から外れたテストが参照する名前など）を拾えない。検索語と見つかった箇所の数は、出し直す依頼の「起草時の論点」に書く。1 か所の直しの帰結が次の往復の指摘になると、往復が伸び続けるためである。

一覧（例外・除外・対象など）に項目を足すか除くときは、その一覧に既にある項目の語を検索語にして、同じ一覧を書いている箇所をすべて見つけ、全部に同じ直しを当てる。一覧の写しは節ごとに言い回しが違う（「〜だけは」「〜のほかに」「〜を除き」）ので、足す項目の語では見つからないためである。

観点の適用範囲（確定事項と実装契約など）に合わせて一部の節だけを直したときも、旧い語と新しく書いた言い回しの検索は、文書の全体（冒頭の改訂の行、表、退けた案を含む）にかける。新しく書いた言い回しが、別の行で別の意味に使われていないかも見る。直した節の外に旧い言い方が残るか、同じ言い回しが 2 つの意味で並ぶと、次の往復の指摘になるためである。

## 7. 未決を示して停止する

起票候補はレジストリに従う4区分（新規・既存へ追記・この場で直す・見送り推奨）で示す。候補の表は、その応答の最終メッセージに置き、聞く手段は [anet-prepare-commit](../anet-prepare-commit/SKILL.md) の「ステージ」の節と同じにする（質問欄だけで示さない。質問欄の画面が先に出て表が残らず、ユーザーが別のメッセージを送ると候補が見えなくなるため）。候補を出し直すときは、前の応答を参照させずに表を省かずに再掲する。新規はissueへ記録する。PRDの課題の結び付け（段3）もこの段で行う。Plan Modeではどちらも書かない。

完了条件は、対象の PRD と関連文書の起草・自己点検が済み、レビューが OK になり（暫定の印が残る PRD と、前提をそろえるためにグリルを止めた PRD では要らない）、残る未決とその扱いが記録されていること。前提をそろえるためにグリルを止めた PRD では、下の起票の候補を示さない（「欠けた前提」）。

プロセス契約 Step 6・6節・7節に従い、未決の起票候補を示して停止し、ユーザーが選んだものだけ記録する。候補が無ければ「なし」と示して完了報告へ進む。完了報告は同3.2節・3.3節に従い平易に書く。次の入口はレジストリから示すが、実装は始めない。完了報告では、[AGENTS.md](../../../AGENTS.md) の「コミットの準備を提案する」に従って、コミットの準備をするかを聞く。この会話でレビューの差し戻しかユーザーの訂正があったときだけ、完了報告の「次にできること」の番号付きの候補に「この会話の手戻りから、ハーネスの改善策を出す（`anet-improve`）」を足す。ほかの候補があるときは、その後ろに置く。選ばれたら [anet-improve](../anet-improve/SKILL.md) の手順で進める。

起票の候補を記録したあと（未決表と「未解決」の ID への置き換えを含む）、完了報告の直前に、書き戻した内容とその時点の PRD 本文を照合し、食い違えば wiki を直す。候補が無ければ「なし」を示したあとに行う。その時点の PRD を `git hash-object` で計算し、`docs/wiki/log.md` に `writeback` の行を、是正があれば `fix` の行も足す（直したページが無ければ `→ なし`）。暫定でも行う。途中停止で記録が残らなかったものは、`anet-lint-wiki` が入ったら取り込み漏れとして拾う。Plan Mode の間は記録も編集しない。

## Domain awareness

During codebase exploration, also look for existing documentation:

### File structure

Most repos have a single context:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

If a `CONTEXT-MAP.md` exists at the root, the repo has multiple contexts. The map points to where each one lives:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

Create files lazily — only when you have something to write. If no `CONTEXT.md` exists, create one when the first term is resolved. If no `docs/adr/` exists, create it when the first ADR is needed.

## During the session

### Challenge against the glossary

When the user uses a term that conflicts with the existing language in `CONTEXT.md`, call it out immediately. "Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"

### Sharpen fuzzy language

When the user uses vague or overloaded terms, propose a precise canonical term. "You're saying 'account' — do you mean the Customer or the User? Those are different things."

### Discuss concrete scenarios

When domain relationships are being discussed, stress-test them with specific scenarios. Invent scenarios that probe edge cases and force the user to be precise about the boundaries between concepts.

### Cross-reference with code

When the user states how something works, check whether the code agrees. If you find a contradiction, surface it: "Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"

### Update CONTEXT.md inline

When a term is resolved, update `CONTEXT.md` right there. Don't batch these up — capture them as they happen. Use the format in [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md).

`CONTEXT.md` should be totally devoid of implementation details. Do not treat `CONTEXT.md` as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else.

Keep each definition to one or two sentences. If a term needs a paragraph to pin down, it is a spec and not a term — put the detail in the design doc and leave the glossary entry short enough to remember.

### Offer ADRs sparingly

Only offer to create an ADR when all three are true:

1. **Hard to reverse** — the cost of changing your mind later is meaningful
2. **Surprising without context** — a future reader will wonder "why did they do it this way?"
3. **The result of a real trade-off** — there were genuine alternatives and you picked one for specific reasons

If any of the three is missing, skip the ADR. Use the format in [ADR-FORMAT.md](./ADR-FORMAT.md).

**Keep it short.** An ADR is a title plus 1-3 sentences. `Status`, `Considered Options` and `Consequences` are optional — most ADRs do not need them. Do not mirror the PRD: the PRD says what to build, the ADR says why this shape was chosen and what was rejected. An ADR long enough to be skimmed instead of read has failed at its only job.

**Never rewrite an existing ADR.** An ADR records the judgement made at that time; rewriting it destroys the reason the decision looked right then. When a later decision changes one, append a short note at the top of the old ADR — which ADR revised it, what was replaced, what still stands — and then write the new one. Partial revision is the normal case, so always say which parts survive. When a document an ADR links to is renamed or moved, updating only the path inside that link's parentheses so it still points to the same document is not a rewrite (`docs/memo/README.md`, "リンクの注意"); retargeting the link to another document is.
