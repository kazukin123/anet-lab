# PRD 実装ワークフロー

## 入力契約

最短の対応呼び出しは次の形:

```text
/implement-prd-with-docs 013_sample_prefetch_10prd.md
```

PRD ファイル名だけが渡された場合は、「この PRD を実装し、実装計画を保存し、その計画から開始する」という意味として扱う。次のような明示形も受け付ける:

- `/implement-prd-with-docs docs/memo/013_sample_prefetch_10prd.md`
- `/implement-prd-with-docs 013_sample_prefetch_10prd.md を実装してください`
- `/implement-prd-with-docs 013_sample_prefetch_10prd.md プラン内容は20impl.mdにも保存`

## PRD 解決

ユーザーへ質問する前に PRD を解決する:

1. 引数が存在するパスなら、そのまま使う。
2. ファイル名だけなら、まず `docs/memo/` をサブフォルダ(`done/` `frozen/` `dropped/`)
   込みで再帰的に探し、完全一致を取る。
3. `docs/memo/` に一致がなければ、リポジトリ全体で完全一致を探す。
4. 複数一致した場合は、候補を示して使う正確なパスを確認する。
5. 一致がない場合は、検索済みの場所を報告してファイルパスを確認する。

実行対象の PRD 名を曖昧一致で決めない。曖昧一致は、完全一致に失敗した後の候補提示にだけ使う。

## 実装計画ファイル解決

`NNN_slug_10prd.md` という PRD に対する実装計画は、同じディレクトリに置き、`NNN_slug_2ximpl.md` 形式にする。

`2x` は連番枠であり、固定の `20` ではない:

- 最初の実装計画: `NNN_slug_20impl.md`
- 次の実装計画: `NNN_slug_21impl.md`
- 以後: `NNN_slug_22impl.md` のように続ける

規則:

1. ユーザーが `20impl.md` や `NNN_slug_20impl.md` のように計画ファイルを明示した場合は、その番号を使う。
2. 計画番号が明示されていない場合は、同じ PRD 接頭辞かつ `2[0-9]impl.md` に一致する同階層ファイルを調べる。
3. 対応する実装計画が存在しなければ、`20impl.md` を選ぶ。
4. 対応する実装計画が存在すれば、既存の最大 `2x` の次番号を選ぶ。
5. 既存ファイルを更新する場合は、更新前に必ず読む。
6. 実質的に異なる計画を上書きする場合、または見えているユーザー変更と衝突する場合は、書き込み前に確認する。

例:

- `013_sample_prefetch_10prd.md` に既存計画がない -> `013_sample_prefetch_20impl.md`
- `013_sample_prefetch_10prd.md` に既存 `20impl` があり、番号指定がない -> `013_sample_prefetch_21impl.md`
- `013_sample_prefetch_10prd.md プラン内容は20impl.mdにも保存` -> `013_sample_prefetch_20impl.md`

## ドキュメント前提のグリリング

`grill-with-docs` と同じ規律を使う。ただし、実装開始に向けて最適化する:

- プロダクトや設計の質問をする前に、PRD、関連コードパス、近いテスト、設定、`CONTEXT.md`、関連 ADR を読む。
- リポジトリから答えられる疑問は、探索で答える。
- スコープ、挙動、API 形状、データフロー、互換性、失敗時挙動、テスト、展開方針を実質的に変える質問だけをする。
- 質問は一つずつ行い、推奨回答も添える。
- PRD とコードの矛盾は、具体的なファイル参照とともに示す。
- `CONTEXT.md` は解決済みのドメイン用語に対してのみ更新し、実装詳細は書かない。
- ADR は、決定が戻しにくく、背景なしでは意外で、実際のトレードオフがある場合だけ提案する。

## 未決事項監査ゲート

`*_2ximpl.md` を保存する前に必ずこのゲートを通す。目的は質問を増やすことではなく、実装中に設計判断をやり直さない状態へ PRD を固めること。

### 決定点の分解

PRD を読み、実装判断へ影響する決定点へ分解する。最低限、次の観点を確認する:

- スコープ境界: やること、やらないこと、既存挙動を維持する範囲。
- 挙動と API: 新しい public API、設定キー、既定値、出力、エラー文言。
- データフローと所有権: State、Resource、依存方向、更新責務。
- 互換性と失敗時挙動: 旧設定、未知値、不正値、フォールバック、WARN/ERROR。
- テストと検証: 追加すべきテスト、既存テストの更新、実行コマンド。
- ドキュメント: `CONTEXT.md`、ADR、設定例、既存 memo の更新要否。

各決定点を次のいずれかに分類する:

- `repo evidenceで解決済み`: コード、設定、テスト、docs から答えが出ている。ファイルパスや確認した事実を残す。
- `ユーザー判断が必要`: 回答によって実装挙動、API、設定契約、テスト方針、展開方針が変わる。
- `2ximplへ固定`: 実装者が妥当に固定でき、ユーザー質問にするほどの設計分岐ではない前提。
- `PRD範囲外`: 今回の実装を止めない関連事項。必要なら後続メモや TODO に回す。

### grill-with-docs の確認観点

- `CONTEXT.md` の用語と PRD の用語が衝突する場合は、計画保存前に明示する。
- 曖昧または過負荷な語がある場合は、実装上の意味を一つに絞り、必要なら canonical term を提案する。
- PRD の主張がコード、設定、テスト、ADR と食い違う場合は、具体的なファイル参照を添えて矛盾として扱う。
- 境界条件は具体的なシナリオで確認する。例外系、旧設定、空データ、複数 env、device 差、runner 設定の継承など、変更対象に合うものを選ぶ。
- ADR は、戻しにくく、背景なしでは意外で、実際のトレードオフがある場合だけ提案する。既存 ADR が合うなら再利用する。

### 質問ルール

リポジトリ探索で解ける疑問は質問しない。`ユーザー判断が必要` に分類した決定点だけ、一問ずつ質問して回答を待つ。質問には必ず次を含める:

```md
未決事項: {何が決まっていないか}
repo evidence: {確認したファイルや現在の挙動}
推奨回答: {推奨する選択と理由}
別回答の影響: {別選択だと実装、テスト、docs がどう変わるか}
```

複数の未決事項を一度に並べない。最初の回答で次の質問の前提が変わることがあるため、依存順に一つずつ進める。

### ゲート通過サマリ

ユーザー判断が必要なブロッカーが 0 になったら、`*_2ximpl.md` 保存前に短いサマリを出す。質問が不要だった場合も省略しない:

```md
未決事項監査:
- ユーザー判断が必要なブロッカー: 0
- repo evidenceで解決した点:
  - {根拠つきで解決した重要点}
- 2ximplに固定する前提:
  - {保存する計画に書く前提}
- PRD範囲外:
  - {今回止めない関連事項。なければ「なし」}
```

ブロッカーが残っている状態で `*_2ximpl.md` を保存しない。ユーザー回答によって計画が実質的に変わった場合は、保存後に「この合意内容で実装へ進みますか? YES/NO」と確認し、YES の場合だけ実装へ進む。

## TDD 実装フェーズ

コード変更を伴う実装では、利用可能なら `tdd` skill も読む。`tdd` skill が利用できない環境でも、この節の最低限の契約は必ず守る。

- docs/config-only の変更は TDD 必須対象外にする。ただし、設定契約、既定値、失敗時挙動、runner-facing behavior が変わる config 変更は behavior-changing として TDD 対象にする。
- `*_2ximpl.md` には、テスト対象の public interface または config/runner-facing surface と、優先して確認する observable behavior を書く。
- テストは private method や内部構造ではなく、public API、設定読み込み、runner-facing behavior など、外から観測できる挙動を検証する。
- horizontal slicing を禁止する。全テストを先に書いてから全実装を行わず、1つの behavior ごとに RED -> GREEN を完了する。
- 最初の behavior は tracer bullet として、1つのテストで end-to-end の経路を確認する。
- 各サイクルでは、次の1テストを書き、失敗を確認し、最小実装で通し、次の behavior へ進む。
- refactor は GREEN 後だけ行う。各 refactor 後に関連テストを再実行する。
- 実装中に計画外の public interface 変更や追加 behavior が必要になった場合は、実装を止めて `*_2ximpl.md` またはユーザー判断へ戻す。

## 保存する計画の形

実装計画は日本語で書く。簡潔にしつつ、実装者が追加判断なしで進められる粒度にする。

PRD がより具体的な形式を求めていない限り、次の構造を使う:

````md
# {機能名} 実装メモ
## 概要
{実装する内容と、選択した既定値を書く。}
## 主な変更
- {挙動またはサブシステムごとにまとめた変更を書く。}
## テスト
- Public interface / surface: {テスト対象にする public API、設定、runner-facing behavior を書く。}
- 優先 behavior: {TDD の縦スライス順に、観測可能な挙動を書く。}
- TDD 順序: {tracer bullet から始め、1テスト -> 最小実装 -> 次テストの順序を書く。コード変更がない場合はその理由を書く。}
## 検証
```powershell
{リポジトリに適したコマンド}
```
## 前提
- {固定した前提または既定値を書く。}
````

## 実行ルール

- 無関係な未コミット変更のあるファイルを保持する。
- 編集範囲は PRD と保存済み実装計画に必要な範囲へ絞る。
- 言語、ログ、ビルド、改行コードなど、リポジトリ固有のエージェント指示に従う。
- 実装時は保存済みの `*_2ximpl.md` を正本として扱う。
- コード変更を伴う実装では TDD 実装フェーズに従い、RED 中に refactor しない。
- 編集後は、変更ファイルと実行した検証コマンドを報告する。
