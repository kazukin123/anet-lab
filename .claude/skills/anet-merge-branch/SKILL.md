# ブランチを取り込むときの衝突を解く

`$anet-merge-branch <ブランチ>`。ローカル main を指定されたブランチへマージし、そのブランチの PR をマージのコミットの形で main に取り込む。取り込みの結果は PR でも両親の履歴を保つ。仕様は [RFD0204](../../../docs/memo/0204_branch_merge_conflict_assist_10rfd.md) を参照する。

## 1. 状態を確かめる

- `git branch --list` と `git worktree list --porcelain` でローカルのブランチ名と作業場所を特定する。名前が無いか一致しなければローカルの一覧を示し、ブランチはあるがワークツリーが無ければ開発者に作成を頼む。明示回答まで止まる。
- 選んだワークツリーで `git status --porcelain=v1 --untracked-files=all`、`git diff --cached --name-status`、`git rev-parse HEAD main` を調べる。マージや rebase がすでに進行中なら、その状態と作業の記録を確かめてから続きに入る。これから始める別のマージを重ねない。実際の編集とマージは指定ブランチのワークツリーで行う。
- `git rev-list --left-right --count origin/main...main` でローカル main の先行コミットを調べる。比較できなければ、その理由を計画に記す。PR の前には開発者に現在の参照をそろえてもらう。

## 2. 衝突の一覧を作る

- `git merge-base <ブランチ> main` で分かれた点を引く。`git merge-tree --write-tree --name-only <ブランチ> main` で試しのマージをする。終了コード 0 は自動マージ可、1 はテキストの衝突あり。ほかのエラーでは診断を確認して止める。出力の先頭のツリーを使ってブランチとの差を確認する。衝突したパスと診断はツリーの行と分けて読む。
- `git diff --name-status -M <分かれた点> main` と `git diff --name-status -M <分かれた点> <ブランチ>` を読み、両側が変えたパスを拾う。また、両側で追加された RFD・ADR を番号で照合し、両側が変えた生成区画を拾う。削除と追加は改名の表示に限らず突き合わせ、移した側のフォルダ規約と本文から対応を調べる。片側が新しく足した旧フォルダのページも調べる。生成区画、記録、本文が同居するファイルでは節を区別する。
- 両側の意図は、分かれた点からの差分を出発点に、`git log <分かれた点>..<各側> -- <パス>` の件名と `git show` の差分、件名が指す RFD と実装計画・課題、wiki の出典から読む。セッションの履歴は読まない。両側が変えた正本が自動マージできても、意図が食い違うかを確かめる。

### 一覧の形

1 項目を 1 ファイルとし、一部だけなら区画の名前を添える。番号の重なりは、関係するパスをまとめて旧い番号 1 つを 1 件と数える。各項目に次を書く。

- 対象のパス（該当する節・区画）と衝突の種類
- 自動マージの可否。「不可（理由）」か「可」。決まりの衝突は「可（決まりに反する理由）」
- main の変更と、ブランチの変更
- 解き方
- あなたに聞くこと。決まりで解けるときは、聞かずに決まる理由

## 3. 計画の承認を得る

一覧、解き方、振り直しで変えるファイル、ビルドの要否、ローカル main の origin/main に対する先行状況、マージに入れない未コミットの変更を示す。開始前のステージ済み変更や、未コミットの変更とマージ・解消・再生成で触るパスの重なりは明示する。当たるファイルの扱いは開発者に聞く（コミット、一時的に退ける、捨てる）。開発者が扱いを決め、ワークツリーの状態を確認できるまで、該当ファイルに触らずマージを始めない。重ならない変更は作業ツリーに残す。

明示の承認が届くまで、振り直しやマージの開始を待つ。見せた時点の両側の先端と分かれた点をコミットのハッシュで記録する。先端が変わったら一覧と計画を見直し、扱いや変更対象が変わったら改めて承認を得る。

## 4. 番号の重なりを先に解く

- いつもブランチの側を振り直す。`git for-each-ref` で `refs/heads` と `refs/remotes` を列挙し、各参照の `git ls-tree -r --name-only <参照> -- docs/memo docs/adr` を見る。さらに `git worktree list` が示したすべてのワークツリーにある同じディレクトリのファイル名を、未追跡のものも含めて調べる。種別ごとに最大番号の次を取る。参照やワークツリーを確認できなければ、番号が空いていると判断しない。
- RFD の本体と計画のファイル名、参照のリンクと表記、テストのタグ、関係する `.scratch/` の置き場をそろえる。古い履歴、実験記録や Run artifact を保持する。改名と表記の直しを同じコミットに載せ、Git が改名と見ることを確かめる。テストのタグを直したときはビルドと関連テストを回す。
- 旧い番号を使い続ける RFD と区別するため、[採番の規約](../../../docs/memo/README.md#採番)どおり、RFD の題の下の振り直しの行に、分かれた点以後のブランチの履歴で旧い番号を件名に持つコミットをすべて 8 桁のハッシュで名指す。件名の scope と末尾を読み、変更パスにかかわらず拾う。main にまだ入っていない振り直しの行を同じ日に直し直すときは、元の番号と名指しを保ってその行に新しい番号を反映する。
- ブランチにしか無い ADR も、ファイル名の番号と参照先を直す。本文は保つ。
- 振り直しのコミットは開発者が行う。済んだら Git が改名と認識したことを確かめ、試しのマージと一覧を作り直して変わった項目を示す。

## 5. マージを始める

承認済みの先端、マージで変わるパス、解消・再生成で触るパス、ステージ済み変更、未コミットの変更を再確認する。マージで変わるパスは、試しのマージのツリーとブランチの先端の差に、衝突したパスを加えて決める。ステージ済み変更があるか、未コミットのパスが重なれば「計画の承認を得る」の扱いに戻る。

指定ブランチのワークツリーで AI が `git merge --no-commit --no-ff main` を実行する。衝突で止まったときは `git ls-files --unmerged` と `git status` を見て一覧と突き合わせる。この向きでは ours はブランチ、theirs は main。すでに最新なら `MERGE_HEAD` は無いので、マージ中のステージの例外を使う場面ではない。Git が別の理由で止まった場合は原因を報告する。

マージ中は、承認済みのブランチと main の先端が `HEAD` と `MERGE_HEAD` に一致することを確かめ、そのハッシュを比較に使う。開始直後に不一致が判明したときは解き始めず、差分と中止・再計画の手順を示す。

## 6. 区画ごとに解く

表を上から当て、該当した行で扱う。置き場が移った場合は移した先の区画で当て直す。決まりで解ける区画を先に扱い、正本の判断が済んでから wiki の書く部分を合わせる。

| 種類 | 当てる条件 | 解き方と確認 |
|---|---|---|
| 番号の重なり | 両側が同じ番号で別の RFD・ADR を追加 | マージ前にブランチの側を振り直す。決まりで決まる |
| 置き場の移動 | 一方が移した旧い置き場のファイルを、他方が変更または追加 | 移した側の置き場を使い、もう片側の変更をそこへ当てる。移した先で表を当て直す。行き先を決められないときは聞く |
| 道具の生成物 | 課題の `INDEX.md`、トピック別まとめの「ファイル」「RFD の一覧」「課題」、wiki のサマリ・概念ページの YAML ヘッダのうち規約が道具で作るキー | 対象の区画だけ片側から採る。マージ中に行う再生成は「入力をそろえて再生成する」に従う |
| 作業の記録 | `docs/wiki/log.md` | main の行を保持し、分かれた点以降にブランチが足した行を、元の順で末尾へ足す |
| AI の派生物 | `docs/wiki/` の手で書く本文・サマリ・目録・トピック別まとめの節 | 下の「wiki の書く部分」に従う。出典の食い違いは聞く |
| 正本 | 上の条件に当たらない区画。RFD、コード、規約、課題の本文、CHANGELOG、実験記録、wiki の利用者が足した YAML のキーなど | コミット・RFD・課題をたどり、両側の意図、案、推奨理由、どちらの受入に効くかを示して選んでもらう。ほかの記録は両側の記述を残す案にする。自動マージ可で意図も食い違わなければそのまま採る |

判断が要る正本の衝突は 1 件ずつ聞く。同じ形の衝突は根拠と選択肢をまとめて 1 問にする。決まっていない挙動を新しく足す形で解消しない。

### wiki の書く部分

`git diff <分かれた点> <取り込む main の先端> -- docs/wiki/README.md` を確認する。

- 差が空なら、分かれた点からのブランチの差分を、移した先の書く区画へ当て直す。ページの導線と相対リンクを現在の置き場に直し、道具が作る YAML のキーは `headers` に任せる。
- 差があれば、再生成できるブランチ側の記述を採らず、ブランチの `log.md` の行が名指す材料を取り込む。行が旧パスを指す場合は、材料の現在のパスを突き合わせる。`scan` が既済とみなしても対象の材料を明示し、現在の [wiki の規約](../../../docs/wiki/README.md) と [取り込みの手順](../anet-ingest-wiki/SKILL.md) に従ってサマリ、該当ページ、目録を更新する。やり直した材料の記録は、元のブランチの行より後ろに追記する。main 側の派生物を土台に使う。
- どちらの場合も wiki だけが持つ横断的知見、見立て、疑問は両側から残す。成立の経緯は日付順にそろえ、同じ出典の同じ事実は 1 行にして出典を添える。出典が食い違うときは両側の文と出典を示して聞く。

### 入力をそろえて再生成する

課題の単票、RFD、wiki の本文・目録・作業の記録を解き終えてから、マージ中に `wiki_support.py maps` で課題一覧とトピック別まとめの生成区画を再生成する。次に `wiki_support.py headers` で wiki の YAML ヘッダのうち道具が作るキーを再生成する。材料を取り込み直す手順に含まれる再生成も、この順で行う。

### ステージと中止

承認後のマージ中は、区画を解くたびに AI が `git add -- <対象パス>` する。削除で解いたパスも含む。再生成の前後を比較し、生成したパスだけを 1 件ずつ対象として確かめてステージする。残りの区画があるファイルは、後の編集のたびにステージし、マージ前の検証では印と未マージのパスが無いことを両方確かめる。マージに入れないと報告したパスに再生成が及ぶことが分かったら、実行前にその扱いを開発者に確かめる。作業ツリー全体の一括ステージは行わない。

開発者が中止を選んだときは AI が `git merge --abort` を実行する。実行後に `MERGE_HEAD` が消え、マージに含めなかった変更が残ることを確認する。失敗したらその状態を報告し、他の Git 操作で状態を上書きしない。マージ開始前に中止した場合は、すでに行った振り直しがあれば、その変更を残す。

## 7. 確かめて報告する

- `git ls-files --unmerged` が空で、`git grep -n -E '^(<<<<<<<|>>>>>>>) '` で衝突の印が 0 件。ステージと作業ツリーを比較し、解消・再生成分の取りこぼしと、マージに入れないパスが index に無いことを確かめる。
- リポジトリの Python 環境で実行した `maps` と、再生成後に実行する `scan` の終了コードが両方 0、RFD と ADR の番号がそれぞれ一意、wiki で「（RFD を一意に決められない）」が 0 件であることを確認する。再生成で変わったファイルをステージした状態で確かめを終える。
- `log.md` は main に続いてブランチの追記が元の順で並ぶことを確認する。取り込みをやり直した材料は `scan` の取り込み待ちに無く、やり直した行はブランチから来た行より後ろにあることを確認する。`src/`・`apps/` が変わったら [AGENTS.md のビルドと検証](../../../AGENTS.md#ビルドと検証)に従う。
- 最後に作り直した一覧の全項目と、マージに入れない未コミットの変更を報告する。種類ごとの件数、開発者に聞いた数、実行した git の操作の数を添える。題材の課題があれば、数と検出の手作業での誤り・手間の有無を「対応内容」に 1 行で記録する。この課題記録をマージに含める場合は、再生成した一覧も含めて確かめる。
- AGENTS.md の決まりに従い、マージのコミットの件名の案を 1 行示す。開発者がコミットする。マージ中のステージと件名には `anet-prepare-commit` を使わない。検証で失敗した項目があるときは、結果と原因を示してコミット待ちとは区別する。コミット後は生成結果が変わらないことと、マージに含めなかった変更がマージの両親と結果の差分に混ざっていないことを確認する。

## 8. PR を取り込む直前にもう一度確かめる

ローカル main が origin/main より先なら、開発者が main を push してから PR を入れる。開発者がブランチを push したあと、PR を入れる直前に、その時点の main に試しのマージを当て直し、決まりの衝突も見直す。新しい衝突が出たら一覧の作成からやり直し、再承認を受ける。PR は開発者がマージのコミットの形で取り込む。squash と rebase での取り込みは行わない。
