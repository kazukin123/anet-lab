# ANET Review

成果物を、レビューエージェント（`an-review`）のレビューに出す。対象を決め、依頼を組み立て、呼び、応答を示して止まる。
観点は `docs/quality/`、依頼と応答の形は `docs/process/protocol.md` の 2 節と 3.1 節、成果物ごとの観点と入力元は `docs/process/registry.md` が持つ。本書は、それらを書き写さない。

## 禁止事項

- 成果物を直さない。指摘への対応は、応答を見たユーザーの指示を受けてから、通常の作業として行う。
- git の書き込み操作をしない。
- `docs/process/protocol.md` は 2 節だけを読む。全体は読まない。大きいためである。
- レビューエージェントを呼ぶときに、モデルを指定しない。

## 1. 対象を決める

引数は任意で、空白区切りで並べる。

| 引数 | 対象 | 成果物キー |
| --- | --- | --- |
| PRD（名前が `_10prd.md` で終わるファイル） | その PRD | `prd` |
| 実装計画（名前が `_2[0-9]impl.md` で終わるファイル） | その実装計画 | `impl-plan` |
| そのほかのファイルのパス | そのファイル | `impl` |
| ディレクトリのパス | その配下で、基準コミットから変わったファイルと、Git が追跡していない新しいファイル | `impl` |

- 基準コミットは `HEAD` にする。ユーザーが別のコミットを示したときは、それを使う。
- PRD と実装計画がファイル名だけで渡されたときは、`docs/memo/` を、`done/` `frozen/` `dropped/` を含めて再帰的に探し、完全一致で解決する。一致が無いときと、複数あるときは、呼ばずに、探した場所と候補を示して尋ねる。
- ディレクトリの配下のファイルは、`git diff --name-only --no-renames <基準コミット> -- <ディレクトリ>` と `git ls-files --others --exclude-standard -- <ディレクトリ>` で挙げる。

### 引数にパスが無いとき

- その会話で変更したファイルを対象にする。成果物キーは、上の表と同じに決める。
- 「その会話で変更したファイル」は、この会話の中で、ファイルを書く道具かコマンドで、作った・変えた・消したファイルである。リポジトリの外のファイルと、Git が無視するファイル（`git check-ignore` が当たるもの。`.scratch/` など）は除く。
- 対象に PRD があるときは、同じ会話で変えた `docs/adr/` のファイルと `CONTEXT.md` を `impl` に入れず、その PRD の依頼の変更箇所に書く（2 の「あわせて書くもの」）。
- その会話で変更したファイルも無いときは、**レビューエージェントを呼ばない。** `git status --short` の結果を示して、対象を尋ねる。**未コミットの変更すべてを、黙って対象にしない。** 作業ツリーには、ほかの会話の変更が同時にあるためである。

### 実装計画を渡されたとき

実装計画を渡され、ほかにパスが無いときは、実装（`impl`）もあわせて対象にする。変更ファイルは、次の順に決める。

1. その会話で変更したファイルのうち、上の表で `impl` に当たるもの。
2. 1 が無ければ、実装計画の「主な変更」に挙がったファイルのうち、基準コミットから変わったもの。
3. 2 も無ければ、実装計画だけを対象にする。

### 呼ばずに尋ねるとき

`impl` か `impl-plan` の対象に、Git が追跡していて基準コミットから変わっていないファイルがあるときは、呼ばずに、そのファイルを示して基準コミットを尋ねる。そのまま渡すと、`docs/quality/impl.md` の、変更箇所を特定する機械検査が成り立たない。

### 依頼の分け方

- 観点ファイルは、成果物キーで、`docs/process/registry.md` の成果物レジストリから引く。
- 観点ファイルが同じ成果物（`impl-plan` と `impl`、複数の PRD）は、1 回の依頼にまとめる。
- 観点ファイルが違う成果物（`prd` と `impl`）は、別々のレビューエージェントへの依頼に分ける。

## 2. 依頼を組み立てる

先に次を読む。

- `docs/process/protocol.md` の 2 節（見出し `## 2. レビュー依頼の形式` から、次の `## 3.` の見出しの前まで）。依頼の項目と書き方は、ここによる。
- `docs/process/registry.md`。
- `impl-plan` か `impl` を出すときは、`docs/quality/impl.md` の「位置づけ」の節。

項目ごとの決め方:

| 項目 | 決め方 |
| --- | --- |
| 成果物キー、レビュー対象パス | 1 で決めたもの |
| テンプレートパス、品質確認観点パス | レジストリの行から引く |
| 入力元パス | `prd` は、レジストリの「入力資料」の定めで決める。PRD が本文で名指しした `reports/` と `docs/experiments/` のファイルで、無ければ「なし」と書く。`impl-plan` は、対の PRD（同じディレクトリで、名前の `_2[0-9]impl.md` を `_10prd.md` に置き換えたもの）。`impl` は、対象の実装計画と、その対の PRD。実装計画が無ければ、その会話の作業が従った PRD。どれも無ければ「なし」と書く |
| 変更箇所 | `prd` は、Git が追跡していないか、基準コミットから変わっていなければ「全体」。変わっていれば、`git diff <基準コミット> -- <PRD>` を見て、変えた節を挙げる。`impl-plan` と `impl` は、`docs/quality/impl.md` の位置づけの「変更箇所の渡し方」による |
| 既知の事項 | 同じ会話の前の往復で、レビューエージェントが報告したもの。ほかは、ユーザーが挙げたものだけを書く。無ければ「なし」 |
| 起草時の論点 | その会話で、判断に迷った箇所。無ければ「なし」 |

あわせて書くもの:

- PRD のレビューでは、あわせて起こした・変えた ADR と、`CONTEXT.md` の変更があれば、変更箇所に書く。`docs/quality/prd.md` の「ADR と用語」の適用範囲が、それで決まる。
- 実装のレビューでは、実行した検証（コマンドと結果）を書く。実装計画に記録があれば、その節を指す。
- PRD に沿わない変更（入力元が「なし」）では、変更の目的を 1〜2 文で書く。
- 会話から分からないものは「記述なし」と書く。推測で埋めない。

依頼文は「レビューを依頼します。依頼の形式は `docs/process/protocol.md` 2 節によります。」で始め、項目を箇条書きで並べる。まとめて依頼するときは、品質確認観点パスを 1 回だけ書き、ほかの項目を成果物ごとのブロックに分ける。

## 3. 呼ぶ

| | 新しく呼ぶ | 続けて依頼する |
| --- | --- | --- |
| Claude Code | サブエージェント `an-review` を起動する | 前のレビューエージェントに、起動したときに返った ID か名前を宛先にして、SendMessage で送る。SendMessage が読み込まれていなければ、先に読み込む |
| Codex | `collaboration.spawn_agent` で `an-review` を起動し、`collaboration.wait_agent` で待つ | `collaboration.followup_task` |

- 呼ぶ前に、対象、成果物キー、観点ファイル、新しく呼ぶのか続けて依頼するのかを、短く示す。確認は取らずに進める。
- **同じ会話で、前の起動と同じ対象を出し直すとき（指摘を直したあとなど）は、新しく呼ばずに、前のレビューエージェントに続けて依頼する。** 同じ対象とは、観点ファイルが同じで、今回の対象が前の起動の対象をすべて含むことである。
  - 変更箇所には、前の往復のあとで変えたファイルを書く。変えていないファイルを読み直させないためである。
  - 既知の事項には、前の往復の報告を加える。
  - 前の往復のあとで変えたファイルが無ければ、呼ばずに、その旨を示す。
- 続けて依頼できないときは、新しく呼び、その旨を示す。

## 4. 応答を示す

- レビューエージェントの応答を、全文でそのまま示す。要約や言い換えをしない。依頼を分けたときは、応答ごとに全文を示す。
- 応答を示したら止まる。指摘への対応は始めない。
- 保存を頼まれたときだけ、応答をそのまま保存する。置き場は、PRD に沿った作業なら `.scratch/prdNNN/`（`NNN` は、対象か入力元の PRD の番号）、PRD の無い変更なら `.scratch/review/` にする。名前は、ユーザーが示さなければ `review-<YYYYMMDD-HHMM>.md` にする。
- Codex で、親のスレッドが読み取り専用のときは、保存できない。その旨を示す。
