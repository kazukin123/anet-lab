# プロセスレジストリ

成果物ごとに、出力先・テンプレート・品質確認観点・担当を引く表。
[プロセス契約](protocol.md) とレビューエージェントの定義が、本書の節と列を名前で参照する。
レビューエージェントは、依頼で渡されなかった項目（テンプレート、品質確認観点、入力元）を、ここから補う。

## 成果物レジストリ

| 成果物キー | 成果物名 | 成果物種別 | 入力元 | 出力先 | テンプレート | 品質確認観点 | 担当 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `prd` | PRD | 文書 | `input` | `docs/memo/{NNN}_{slug}_10prd.md` | 未整備 | `docs/quality/prd.md` | `anet-create-prd` |
| `impl-plan` | 実装計画 | 文書 | `prd` | `docs/memo/{NNN}_{slug}_2{x}impl.md` | `.agents/skills/implement-prd-with-docs/PRD-IMPLEMENTATION.md` の「保存する計画の形」 | `docs/quality/impl.md` | `implement-prd-with-docs` |
| `impl` | 実装（コード、テスト、設定、設計文書・ADR・用語集の追随） | 変更 | `prd` `impl-plan` | 既存の構成に従う | — | `docs/quality/impl.md` | `implement-prd-with-docs` |
| `worklog` | 作業記録 | 文書 | — | 実装は `impl-plan`、PRD づくりは `prd` が兼ねる | — | — | 工程を実行する側 |
| `issue-record` | 未決の受け皿 | 文書 | — | `docs/management/issues/`（1 課題 1 ファイル） | — | — | 工程を実行する側（ユーザーが選んだものだけ書く） |

- **「入力元」の値は成果物キーである。** パスではない。`input` は、本書「入力資料」のキーを指す。
- **`—` は、そもそも持たないことを表す。`未整備` は、用意していないことを表す。** `prd` のテンプレートは用意していない。PRD の構造は、品質確認観点で見る。
- **`impl` は固定の出力先を持たない。** パスから行を逆引きできないので、レビューを依頼するときは成果物キーを渡す。レビュー対象は、依頼に書いた変更ファイルの一覧である。
- **`impl` は、PRD に沿わない変更にも使う。** そのときは、入力元を「なし」と書いて渡す。観点の扱いは、`docs/quality/impl.md` の位置づけによる。
- **`impl-plan` は作業記録を兼ねる。** テンプレートの節のあとに、経過と結果の節を足してよい。
- **`worklog` と `issue-record` は、品質確認観点を持たない。** レビューの対象にしない。
- **`docs/quality/refactor.md` は成果物の観点ではない。** `anet-audit` の refactor 観点が基準と分類タグに使う。レビューの依頼には渡さない。

## 成果物以外のレビュー対象

なし。

## サーフェスごとの所在

| 対象 | Claude Code | Codex |
| --- | --- | --- |
| レビューエージェントの定義 | `.claude/agents/anet-review-agent.md` | `.codex/agents/anet-review-agent.toml`（本文を持たない。左の定義を読んで従う） |

## 入力資料

| キー | 内容 | パス | 扱い |
| --- | --- | --- | --- |
| `input` | 会話での要求、サーベイ、実験記録 | `reports/` のサーベイと `docs/experiments/` の実験記録のうち、PRD が本文で名指ししたもの。会話での要求は、パスを持たない | 読み取り元である。工程の中で書き換えない |

レビューで入力元として読むのは、PRD が本文で名指ししたファイルだけにする。名指しが無ければ、入力元なしとして扱う。

## 工程 Agent の切り替え先

| 工程 | 入口 | 扱い |
| --- | --- | --- |
| 要件定義・PRD の作成／改訂 | [anet-create-prd](../../.agents/skills/anet-create-prd/SKILL.md) | PRD が設計契約も持つ。起草・自己点検・レビュー後に停止する（暫定の印が残る PRD はレビューを受けない。下の読み替え表） |
| 設計 | 独立した工程は置かない | PRD の実装契約に含める |
| 実装計画・実装・検証 | [implement-prd-with-docs](../../.agents/skills/implement-prd-with-docs/SKILL.md) | 保存済み計画から実装し、自己点検・レビュー後に停止する |
| コミット | [anet-prepare-commit](../../.agents/skills/anet-prepare-commit/SKILL.md)、人間 | 工程を終えた側が、完了報告で skill を実行するかを聞く（[AGENTS.md](../../AGENTS.md) の「コミットの準備を提案する」）。skill が文案を作り、選ばれたらステージする。commit と push は人間が行う |

起動は Codex が `$skill名`、Claude Code が `/skill名`。工程を終えた側が、次の工程を自動起動しない。課題に対応するときは、`anet-create-prd` に issue の ID を渡して PRD を起こすか、下の「この場で直す」を使う。上流を直す必要があるときは、PRD 作成／改訂の入口を示し、既存実装への波及もユーザーに知らせる。

## 成果物種別とアダプタの対応

独立したアダプタは作らず、担当の入口が既存規約に従って直接編集する。

| 成果物種別 | 生成手段 | 対象の単位と規約 |
| --- | --- | --- |
| 文書 | 担当の入口が Markdown を直接編集する | 今回選んだ成果物を単位とする。PRD は [memo README](../memo/README.md)、実装計画は [PRD-IMPLEMENTATION.md](../../.agents/skills/implement-prd-with-docs/PRD-IMPLEMENTATION.md) に従う |
| 変更 | 実装の入口が既存の構成を直接編集する | 保存済み計画の behavior ごとに進める。規約は [AGENTS.md](../../AGENTS.md)、ビルドと検証は同書の「検証」「AI エージェントでのビルド注意事項」に従う。コマンドは本表に書き写さない |

## この場で直す

範囲が小さく、設計の判断が要らず、意図が repo の事実から読める件を、工程末にも途中にも選択肢として出す。開発者が選んだ件だけを直す。

1. PRD の工程ではビルドもテストも要らない文書・skill・wiki・分類データなどだけを直せる。ビルドかテストが要る件は新規 issue の候補にする。実装の工程ではコードも直してよい。
2. 設計判断が必要と分かったら今回の直しだけを戻し（手順 3 で対応内容へ書いた行も消し、対応中にした状態は `anet-update-issue` の「工程の出来事」の取りやめの行で元に戻す）、新規に変えて示し直す。既存のユーザー変更を戻さない。
3. 同じ課題の既存 issue があれば、`anet-update-issue` の「工程の出来事」で対応中にし、その対応内容へ、直した内容と変更の場所を追記する（形は `anet-create-issue` の「各項目の書き方」）。直した分を成果物キー `impl`、入力元なしとして独立レビューへ出す。既存 issue があれば、依頼の変更の目的にその ID を書く。同じ観点のレビューエージェントを呼んでいれば続けて依頼し、違えば新しく呼ぶ。途中で直した分は、その工程のレビューへ含める。
4. 差し戻しは直して出し直し（中身が変わったら対応内容の行も直す）、OK のあとで完了報告する。同じ課題の既存 issue があれば、完了報告の前に `anet-update-issue` の判定で「残件無し」にする（直したあとも課題の事象が残っていれば「残件有り」）。status は対応中のままにし、解決は `anet-prepare-commit` が持ちかける。
5. 成果物の「未解決」を、直した旨と変更の場所に置き換える。
