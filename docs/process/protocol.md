# 工程 Agent 共通プロトコル

すべての工程 Agent（`an-requirements` / `an-design` / `an-implement` / `an-resolve-issue`）とレビュー Agent（`an-review`）が従う共通契約。

Agent ごとに応答形式や停止条件を再定義してはならない。何をどこに書くかは次のとおりとする。

| 何を | どこに |
| --- | --- |
| やり取りの形式と、すべての工程 Agent に共通する制約（9 節） | **本書に一本化する** |
| 工程固有の手順と制約 | 各 Agent 定義 |
| 成果物の節ごとの書き方と、後続の工程での扱い | **各テンプレート**。Agent 定義と本書がテンプレートに依存するのは、節や表を名指しした箇所だけである。それ以外の章立てと項目は、テンプレートの側で変えられる |

## 1. 実行の基本形

工程 Agent は次の Step を順に進める。停止条件に該当した場合、または開発者の判断待ちが発生した場合のみ返却する。

| Step | 内容 | 回数 |
| --- | --- | --- |
| 1 | **対象の決定** — 担当する成果物の候補を出し、開発者に選んでもらう（1.1） | 1 回 |
| 2 | **質疑** — テンプレートの必須項目と品質確認観点が求める情報の両方で不足を洗い出し、開発者の INPUT をまとめて受け取る。終わりに作業記録を書き出す（1.2） | 1 回 |
| 3 | **起草** — テンプレートに従って成果物を生成する。不明点は推測で埋めず、成果物に「未解決」と記して**作業記録へ貯める**（7 節）。**この時点では起票しない**（主要な流れを止める不明点はその場で聞き、上流の成果物の食い違いや誤りに当たったら止まる。下記）。課題 ID は起票が済んでから置き換える（Step 6）。テンプレートにあるが内容が無い章は「対象外」または「なし」と明記し、章ごと省略しない。テンプレートが任意とした節は、使わない場合の扱いをテンプレートの指示に従う。**書き終えたら自己点検をし、未決の事項をまとめて聞いてから Step 4 へ進む**（まとめてレビューに出すときは、そのまとまりで 1 回聞く。下記） | 成果物ごと |
| 4 | **レビュー依頼** — レビュー Agent へ依頼し、判定を受ける。**独立コンテキストで実行させる**こと。呼び出しの記法は surface ごとに異なるため本書では規定しない。**同じ品質確認観点ファイルを使う成果物は、まとめて 1 回で依頼してよい**（依頼の形式は 2 節。判定は成果物ごとに返る）。**2 往復目以降は、前の往復のレビュー Agent に続けて依頼できる環境では、続けて依頼する。** 変わっていないものの読み直しを無くすためである。続けられない環境では新しく呼ぶ | 成果物ごと（まとめて依頼した成果物は、そのまとまりごと） |
| 5 | **差し戻し対応** — 受け取った指摘を**自分で直せるもの**、**開発者の判断が要るもの**、**根拠が無く見送るもの**へ仕分ける（1.3）。直せるものを**すべて直してから** Step 4 へ戻る。判断が要るものが混じっていても途中で止めず、直しきってから残りを開発者へ返す。決まっていない振る舞いを求める指摘は「未解決」と記して作業記録へ貯め、それだけでは止まらない（1.3）。レビューが OK になってから、1 回だけまとめて聞く（下記）。OK なら次の成果物へ（まとめて依頼した場合は、そのまとまりのすべてが OK になるまで往復する）。**判定にかかわらず `範囲外の検出` を作業記録の「決まらなかったこと」へ積む**（2 節） | 成果物ごと（同上） |
| 6 | **起票と完了判定** — **起票の候補を提示して停止する**（7 節・停止条件 7）。開発者が選んだものを起票し、成果物の「未解決」を課題 ID へ置き換える。そのうえで完了条件を確認し、作業記録へ完了報告を追記して**停止する**。次の工程へは進まない（次の工程は、開発者がその工程の Agent を選んで始める。6 節） | **2 回（工程末）。停止しない場合は 7 節が定める** |

Step 4 と 5 の往復は Agent の内部で完結させる。往復のたびに開発者へ返さない。

**サブエージェントの呼び出しの説明に「最終」と書かない。** レビューや検証のためにサブエージェントを呼ぶとき、呼び出しごとに表示される短い説明を付ける環境では、その説明に対象と何回目かを書く（例: 「設計書 5 種のレビュー（2 往復目）」「画面の検証（3 回目）」）。最終になるかは結果が出るまで分からず、「最終」と書くと開発者が経過を読み違えるためである。

**Step 3 以降は作業記録を正本とする。** Step 1・2 で決まったことは作業記録に書き出されており、そのあとに決まったことと経過もそこへ積む（1.2 節「作業記録の書き出し」）。会話が長くなったら読み返す。

**会話が圧縮されたあとや、依頼の回数の上限などで止まって開発者が続けさせたあとも、同じ実行の続きである。** Step 3 以降なら、作業記録を発番し直さず、今の作業記録を読み直して、「経過」の続きから進める。読み直すのは、作業記録と、次にすることに要るものだけにする。今の作業記録が分からなくなったら、この工程の作業記録のうち完了報告の無いものを挙げ、どれが今の実行のものかを開発者に確かめる。1 件だけでも確かめる。前の実行の作業記録が、完了報告の無いまま残っていることがあるためである。1 件も無ければ、その旨を示して開発者の指示を待つ。Step 1・2 の途中なら、作業記録はまだ無い。前の実行の作業記録を引き継がずに質疑を続け、Step 2 の終わりに書き出す。**環境が作業領域の外に残す会話の履歴を読んで立て直さない。** 作業の正本ではなく、指示を取り違えるおそれがあるためである。

**止まった工程を再開するとき（5 節の停止条件 8・9）も、同じ作業記録の続きから進める。** 「経過」の最後の停止の行と、そのあとの行を読み、まず、すでに書いた部分を変わった上流に合わせ直してから続ける。課題解決 Agent で揃えたときは、そのあとに上流を直した記録（合わせ直す箇所）の行がある。1 つ上の工程に戻って直したときはその行が無いので、上流の成果物を読み直して、変わったところを確かめる。指摘への対応の途中で止まっていたときは、止まる前に直した分も含めてレビューに出す。再開するかどうかは、止まったときに記録した課題の状態に依らない。工程末の応答で、その課題を解決にしてよいかを開発者に尋ねる。

**起草のあとの自己点検（Step 3 の終わり）。** 書き終えたら、レジストリの「品質確認観点」列が指すファイルの全項目を自分で通す（観点ファイルが節ごとの適用範囲を定めていれば、それに従って項目ごとに対象外を決める）。満たしていないものは直す。直すのに開発者の判断が要るものは、起草中の不明点と同じく「未解決」と記して作業記録へ貯め、止まらずに進める（上の表の Step 3、9 節の制約 6）。自己点検は起草の一部であり、判断を要する事項は、自己点検を終えてからまとめて聞くためである（下記）。レビューの指摘への対応（Step 5）での仕分けと停止は、1.3 節による。判断に迷った項目は、レビュー依頼の「起草時の論点」に書く（2 節）。**自己点検はレビューの代わりではない。** 書いた Agent 自身が明らかな漏れを先に潰し、レビューは独立したコンテキストで「書いたつもり」を見つける。観点を知らずに書くと、外した分がすべて差し戻しになり、レビューの往復が増える。

**未決の事項は、レビューの前にまとめて聞く。** 自己点検を終えたら、起草中と自己点検で「未解決」と記して作業記録へ貯めた事項を、1.2 節「質疑の停止条件」の切り上げと同じ形で、推奨案とともに並べて 1 問で聞く（推奨案で埋める / 後で決める / 1 件ずつ聞く）。聞く事項から除くのは、プラットフォームの標準で決まる事項（1.2 節）と、主要な流れを止める事項ですでにその場で聞いたもの（下の「主要な流れを止める不明点」の段落、1.2 節「主要な流れを止める事項」）だけである。開発者が答えられるかを先回りして決めない。答えを成果物に反映し、反映した箇所に関わる観点で自己点検をもう一度通してから、レビューへ出す。まとめてレビューに出す成果物があるときは（上の表の Step 4）、そのまとまりのすべてを書き終えて自己点検を終えてから、1 回で聞く。「後で決める」を選んだものは「未解決」のまま残し、工程末に候補として挙げる。聞くときは 1.2 節「質問の出し方」の形で聞く（3.2 節の形式と 4 節は使わない）。委譲されて動いているときは聞かずに、未決の事項を委譲元へ返す（1.4 節）。

**レビューの指摘で見つかった未決の事項（1.3 節）は、レビューが OK になってから 1 回だけまとめて聞く。** 聞き方は上と同じである。答えを反映した箇所をレビューに出し、そのレビューで新しく見つかった未決の事項は聞かずに「未解決」のまま残す。聞くのを 1 回に限るのは、書き足した決まりの境目が次の指摘になり、往復が伸び続けるのを防ぐためである。そのあとで、完了を報告する前の手順（Agent 定義が定めるもの）と、起票の候補の提示へ進む。

**起草の途中や指摘への対応の途中で、主要な流れを止める不明点に当たったら、その事項についてだけ、その場で聞く。** 主要な流れを止めるかの判断、推奨案、選択肢は 1.2 節「主要な流れを止める事項」による。ただし、選択肢の「決まるまで止める」は `決まるまで実装を止める（この件を課題に記録して、ここで止まります。決まったら続きから再開します）` と書く（工程による読み替えは同じ）。聞くときは 1.2 節「質問の出し方」の形で聞く（3.2 節の形式と 4 節は使わない）。答えをもらったら、作業の続きに戻る。ほかの不明点は一緒に聞かない。委譲されて動いているときは開発者に聞けないため、聞かずに委譲元へ返す。上の表の Step 3、上の自己点検、1.3 節で「未解決」と記して止まらずに進めるとしているのは、主要な流れを止めない不明点である。

**上流の工程の成果物の食い違いや誤りのために、今の成果物を正しく作れないと分かったら、見つけた時点で止まる（5 節の停止条件 9）。** Step を問わない。今の成果物に効かない上流の不備は、これまでどおり作業記録へ貯め、工程末に候補として挙げる。要求資料の食い違いは当たらない（要件定義の質疑で扱う）。上流が決めていない事項は、上の「主要な流れを止める不明点」と 1.2 節の扱いによる。

### 1.1 Step 1: 対象の決定

1. レジストリから**担当 Agent が自分である行をすべて**引く
2. 各行の「入力元」列を逆引きし、入力元の成果物を読む
3. 各候補について次を判定し、**根拠とともに**提示する
4. 開発者が選んだものを今回の対象として固定する

| 示すもの | 値 |
| --- | --- |
| 作成状態 | **未作成** / **作成済み**（選べば更新になる） |
| 入力情報 | **充足** / **一部不足** / **不足** |
| 要否 | 推奨 / 任意 / 不要 と、そう判断した根拠 |
| 前の工程との関係 | 前の工程が完了しているか（前の工程の作業記録に、完了報告の無いものが残っていないか）。上流の成果物を直すために戻ってきたときは、直すと、依頼してきた工程の成果物のほかにも、すでに作った成果物に波及するか。前の工程を持たない Agent では示さない |

**前の工程との関係が合わなくても止めない。** 状況を示し、続けるか戻るかを開発者に選んでもらう（例: 前の工程が完了していない。直すと実装にも波及するので、課題解決 Agent で揃えることを勧める）。Agent の選択欄、切り替えのボタン、切替のコマンドのどれで始まっても、同じように確かめる。

**担当する成果物はすべて候補に出す。** 入力情報が足りなくても外さない。**足りない分は Step 2 の質疑で埋める**ため、判断材料を示して開発者に選ばせる。

**要否の条件表は作らない。** 入力元を読んで判断し、根拠を示す。条件は案件ごとに違うため先に書き切れず、書いても保守対象が増えるだけである。

**複数選べる。** 4 節の「1 候補 = 1 実行」は「次にできること」の候補の作り方に関する規則であり、本 Step の成果物選択には適用しない。

参照先（テンプレート・品質確認観点）が未整備であることも、この Step で分かる。**未整備を理由に停止しない**（5 節）。

**担当する成果物を持たない Agent もある。** その場合はレジストリを引かず、Agent 定義の「工程固有の判断材料」が定める候補を提示する。**開発者が選んで対象を固定する点は変わらない。**

**対象が決まってから変更範囲が決まる場合、この Step は 2 段になる。** 1 段目で対象を選び、2 段目で影響を調べて変更範囲を確定する。**調査の前に変更範囲を決めない。**

### 1.2 Step 2: 質疑

選んだ成果物**すべてについて**不足を洗い出し、**まとめて**聞く。工程の途中で小出しに聞かない。

**不足は、テンプレートの必須項目と、品質確認観点が求める情報の両方で洗い出す。** 観点は、レジストリの「品質確認観点」列が指すファイルである。観点が書き方を定めている項目（値と比較の向きで書く、など）は、その書き方で埋められるだけの情報を聞く。

| # | 原則 |
| --- | --- |
| 1 | **1 問ずつ聞く。** まとめて出さない。**1 問に入れる論点は 1 つにし、答えはその論点にだけ当てはめる** |
| 2 | **入力元やリポジトリから分かる事実は聞かない。** 自分で調べる。要件定義と設計では、**プラットフォームの標準で決まっている動きも聞かない**（下の「プラットフォームの標準の確認」） |
| 3 | **開発者が決めることだけ聞く。** 採否判断・優先度判断・責任者判断が対象 |
| 4 | 各質問には推奨案を添える。推奨案に、問うていない論点を混ぜない |

原則 1 と「まとめて聞く」は矛盾しない。**質問は 1 問ずつ出すが、Step としては 1 回にまとまっている**という意味である。

#### プラットフォームの標準の確認

**要件定義と設計の Agent は、質問を洗い出す前に、プラットフォームの標準の動きを `an-platform-spec` から受け取る。** 扱う領域（ワークフロー・画面・マスタ・権限など）を渡す。起草の途中や指摘への対応で、受け取った標準の動きに無いプラットフォームの事項に当たったときも、その事項を渡して確かめる。

| 受け取るもの | 扱い |
| --- | --- |
| 決まっている動き | 聞かない。成果物には、下の「従う内容」を振る舞いとして書く。「決めること」が添えてあれば、それだけを聞く |
| 選べること | 質問の選択肢に使う |
| できないこと | 選択肢にしない |

**質問を出すたびに、論点と選択肢を、受け取った標準の動きと照らす。** 論点が、従う内容の決まっている事項（「決まっている動き」に当たる事項か、標準から外れた決定がある事項。下記）に当たれば、その質問は出さない。選択肢が「できないこと」に当たれば、その選択肢を外す。迷ったかどうかに依らず、毎回照らす。入力元が「未解決」としている事項のように、聞くのが当然に見える論点ほど、照らさずに聞いてしまいやすい。

**論点がプラットフォームの動きに関わり、受け取った標準の動きに無いときは、質問する前に、その事項を渡して `an-platform-spec` で調べる。** 返ったものは上の表のとおり扱う。「分からない」と返ったときは、そのまま聞く。これも、迷ったかどうかに依らない。

**受け取った標準の動きは、開発者の判断で標準から外れた決定を除き、入力元の記述より優先する。** 標準の動きは、プラットフォームの仕様が変わったり `an-platform-spec` の要点が書き足されたりすると新しくなる。それより前に書かれた記述と食い違うのは、普通に起きることである。

**事項ごとに、従う内容を 1 つに決める。** 開発者の判断で標準から外れた決定（標準の動きと、それと異なる理由が書かれた記述。下の「聞かない事項の示し方」）がどこかにあれば、それに従う（9 節の制約 5）。無ければ、標準の動きに従う。入力元や既にある成果物が、その事項を「未解決」としていても、従う内容と異なることを書いていても、聞かない。ただし、標準から外れた決定どうしが食い違うときは、本節の扱いによらず、開発者の判断を求める。

従う内容と異なる記述（「未解決」を含む）は、場所によって次のように扱う。

| 異なる記述の場所 | 扱い |
| --- | --- |
| 今回の成果物（今回作るもの・更新するもの。ほかの今回の成果物の入力元を兼ねるものを含む） | 従う内容に書き改める |
| 入力元と既にある成果物のうち、今回の成果物でないもの | 直さない。今回の成果物のその箇所に、その記述と異なる理由（標準で決まっているため、または標準から外れた決定によるため）を添える。その記述は、不備として作業記録へ貯め、工程末に起票の候補として挙げる（7 節） |

今回の成果物のうち、標準から外れた決定に従う箇所には、標準の動きと、それと異なる理由を書く。

入力元が定めた扱いに、標準と食い違うために従えないことは、9 節の制約 5 の「従えない事情」に当たる。そのときの開発者の判断は、質問 1 の前に下の「聞かない事項の示し方」で示して求め、別に質問はしない。**それより後（質疑の途中、起草の途中、指摘への対応）で見つけたときは、開発者へ返さずに表のとおり進める。** 起票の候補は工程末に示す。

#### 質問の出し方

**質疑の途中は、3.2 節の応答形式を使わない。** 1 回の応答で示すのは、質問 1 つ、推奨案とその根拠、選択肢だけである。ただし要件定義と設計では、質問 1 の前に、聞かない事項を示す（下の「聞かない事項の示し方」）。

選択肢には**答えそのもの**を番号付きで書き、推奨を 1 番に置く。「〜と回答する」のような行動の形にしない。開発者は番号でも、選択肢に無い答えでも返せる。金額や名前を聞くなど、選択肢を作れない質問では選択肢を省く。

```
質問 1: 実装を複数のフェーズに分けますか？
推奨: 分けない。段階的なリリースの指示が無いため。

1. 分けない（推奨）
2. 分ける
```

#### 聞かない事項の示し方

**要件定義と設計では、質問 1 の前に、プラットフォームの標準で決まるため聞かない事項を示す。** 質問 1 と同じ応答に置く。受け取った標準の動きを自分の応答に書き出すことで、続く質問がそれに沿う。開発者も、取り違えに質疑の初めで気づける。

| 示すもの | 内容 |
| --- | --- |
| 対象 | 今回の成果物で扱う事項のうち、標準で決まっている動きに当たるもの。**標準から外れた決定がある事項は含めない**（開発者が既に決めたことであり、入力元から分かる事実として聞かずに従う。原則 2） |
| 必ず含めるもの | 対象のうち、入力元や既にある成果物が「未解決」としている事項と、標準の動きと異なることを書いている事項。そのことと、今回の成果物の記述であれば書き改めることを、今回の成果物でない記述であれば工程末に起票の候補として挙げることを添える |
| 当たるものが無いとき | 示さずに質問 1 から始める |
| 質問が 1 つも無いとき | 必ず含めるものがあれば、聞かない事項だけを示し、「違っていなければ、このまま進めてよいと返してください」と添えて、開発者の返事を待つ。この応答も質疑の一部であり、3.2 節の形式は使わない。必ず含めるものも無ければ、示さずに起草へ進む |

開発者が違うと答えた事項は、その答えを従う内容とする。答えが標準の動きと異なるときは、成果物のその箇所に、標準の動きと、それと異なる理由を書く（標準から外れた決定になる）。要点そのものの誤りと分かったときは、工程末に起票の候補として挙げる（7 節）。

```
次はプラットフォームの標準で決まるため、質問しません。違っていれば指摘してください。
- <事項>: <標準で決まっている動き>
- <事項>: <標準で決まっている動き>。<入力元の文書>は「未解決」としているため、作業の終わりに<入力元の文書>の直しを起票の候補として挙げます

質問 1: …
```

#### 主要な流れを止める事項

**入力元が「未解決」としている事項と、質問で埋める不足のそれぞれについて、決まらないと主要な流れが止まるかを判断する。** 主要な流れとは、要件定義書のユースケースの基本フローである（要件定義では、書こうとしているユースケースの基本フロー）。決まらないと、どれかの基本フローが最後まで通らなくなる事項を「主要な流れを止める事項」とする。代替フローだけに関わる事項は含めない。プラットフォームの標準で決まっている事項は、主要な流れを止めるものでも聞かない（上の「プラットフォームの標準の確認」）。

主要な流れを止める事項は、次のとおり聞く。

| 項目 | 決まり |
| --- | --- |
| 聞く順 | ほかの質問より先に聞く。答えによって、ほかの質問が変わることがあるためである |
| 聞き方 | 1 件ずつ聞く。下の「質疑の停止条件」の、残る項目をまとめて聞く 1 問に含めない |
| 推奨案 | 基本フローが通る最小の案。プラットフォームの標準で選べる手段があれば、それを優先する。大きい案を推奨にすると、入力元に無い振る舞いを足すことになるためである |
| 推奨案の根拠 | 決まらないと、どの流れの何ができなくなるか |
| 選択肢 | 推奨案とほかの案に加えて、下の 2 つを必ず置く |

| 選択肢 | 書き方 | 選ばれたら |
| --- | --- | --- |
| 決めずに進める | `決めずに進める（<作らない部分>は作らないので、<できなくなること>のまま完成します）` | その部分は作らず、「未解決」と記して進める。作業記録の「決まらなかったこと」に、先頭に `【通らない流れ】` を付けて積み、作らない部分を「決めたこと」にも積む（下の「作業記録の書き出し」）。工程末の応答に示し（3.2 節）、起票の候補に必ず挙げる（7 節） |
| 決まるまで止める | `決まるまで実装を止める（この件を課題に記録します。残りの質問に答えてもらったら止まり、決まったら続きから再開します）` | その場で課題に記録する（7 節）。残りの質問を続けて作業記録を書き出し、起草に入らずに止まる（5 節の停止条件 8） |

設計の工程では、選択肢の「実装」を「設計」に、「完成します」を「書き上げます」に読み替える。要件定義の工程では、「実装」を「要件定義」に、「完成します」を「書き上げます」に読み替える。

**4 つの選択肢のどれにも決まらないまま質疑を止めたとき（下の「質疑の停止条件」の 2・3）と、起草や指摘への対応の途中で聞いて（1 節）、開発者が選択肢のどれにも決めなかったとき（「まだ決められない」「後で決める」など）は、「決めずに進める」を選んだものとして扱う。** その部分を作らずに進め、上の表のとおり記録し、示し、候補に挙げる。決まらなかったことを、主要な流れを止めないふつうの未解決に紛れさせないためである。

**本小節は、要件定義・設計・実装の工程に当てる。** 課題解決 Agent は成果物を自分で作らないため、自分の質疑には当てない。委譲先が返した主要な流れを止める事項（1 節）は、課題解決 Agent が本小節のとおり開発者に聞く。選択肢は、その成果物を担当する工程の読み替えに従う。

```
質問 1: 予約画面で、会議室をどう選べるようにしますか？
推奨: 一覧から選べるようにする。設計書では決まっていませんが、
      これが無いと新規の予約ができないためです。

1. 一覧から選べるようにする（推奨）
2. 会議室のコードを直接入力させる
3. 決めずに進める（会議室を選ぶ部分は作らないので、新規の予約ができないまま完成します）
4. 決まるまで実装を止める（この件を課題に記録します。残りの質問に答えてもらったら止まり、決まったら続きから再開します）
```

#### 質疑の停止条件

次のいずれかを満たしたら質問を止める。**これ以外の理由で質問を切り上げない。**

| # | 条件 |
| --- | --- |
| 1 | 必要な項目がすべて埋まった |
| 2 | 残る項目について開発者が「決められない」「後で決める」と答えた |
| 3 | 同じ論点で 2 度聞いても確定しない |

**残る項目を 1 件ずつ聞かずに切り上げたいときは、残る項目を推奨案とともに並べ、扱いを 1 問で聞く。** 選択肢は「推奨案で埋める」「後で決める」「1 件ずつ聞く」とする。主要な流れを止める事項は、この 1 問に含めない（上の「主要な流れを止める事項」）。推奨案で埋めた項目は、開発者が決めたものとして扱う。

止めたあと、埋まらなかった項目は**作業記録へ貯め、工程末に起票の候補として挙げる**（7 節）。

#### 作業記録の書き出し

Step 2 の終わりに、レジストリの `worklog` が指す場所へ 1 ファイル書き出す。**これが Step 3 以降の正本になる。**

```markdown
# 作業記録 <発番で得た ID>

| 項目 | 内容 |
| --- | --- |
| 工程 | <この実行の工程。要件定義、設計、実装/テスト、課題解決のいずれか> |
| 実行日 | <ID の日付部分を YYYY-MM-DD の形で書く> |

## 対象
<Step 1 で選んだ成果物。選ばなかったものと、その根拠も書く>

## 前提
<Step 2 で開発者から得た INPUT>

## 決めたこと
<委譲先にも守らせる決定と、その理由（下記）。無ければ「なし」>

## 経過
<済んだこと（下記）>

## 決まらなかったこと
<未解決の事項と、レビューの「範囲外の検出」を貯める。
 事項ごとに、開発者に質問したかを添える（「質問した（後で決める）」／「質問していない（理由）」）。
 工程末にここから起票の候補を作る（7 節）。
 起票が済んだものは課題 ID を追記する。無ければ「なし」>

## 完了報告
<Step 6 で追記する>
```

**1 回の実行（Step 1 から工程末まで）が 1 ファイル**である。同じ工程を複数回に分けて動かせば、その回数だけできる。

ファイル名は接頭辞を `worklog` とし、**それ以降の規則と発番の手順は課題記録と同じ**とする。**同じ日に同じ工程を複数回動かしても衝突しない**ようにするためで、1 枚の表へ追記しないのと同じ理由による。

**発番は課題記録と同じ手段で行う。** 接頭辞に `worklog` を渡す点だけが違う。手順は `an-create-issue` SKILL の「発番」節が持っており、本書では書き写さない。**日付も乱数も推測で書かない。**

**作業記録を書く Agent は、その手段を実行できる必要がある。** 実行できなければ規則どおりの名前を出せない。**推測で名前を決めず、5 節の停止条件 6 として返す。**

**「決めたこと」は Step 2 の終わりから、「経過」は Step 3 から積む。** 会話が圧縮されても、作業記録だけで立て直せるようにするためである（1 節）。

| 節 | 積む時機 | 書くこと |
| --- | --- | --- |
| 決めたこと | Step 2 の終わり（書き出すとき）と、Step 3 以降で決まったとき | 委譲先にも守らせる決定と、その理由。作らない・使わないと決めたもの、変えてはいけないもの、複数の案から採ったもの、見送った指摘（1.3 節）、開発者が判断したこと。Step 2 で決まったものは、「前提」に書いたうえで、ここにも挙げる。委譲するときに渡す（8 節） |
| 経過 | 成果物の起草を終えたとき（実装では生成・検証・テスト・ビルドの段ごと）、レビューの判定を受けたとき、指摘を直し終えたとき、止まるとき（5 節の停止条件 8・9） | 済んだことと、その結果（例: 「画面の生成を終えた」「レビュー 2 往復目: 差し戻し、指摘 3 件」「2 往復目の指摘 3 件を直した」）。止まるときは `停止: <理由>（課題 <ID>。記録しなければ「記録なし」）。<どこまで済んだか>` と書く。上流を直した課題解決 Agent も、ここに再開したら合わせ直す箇所を書く |

**決めたことが変わったら、その行を今の決定に書き改め、改めた理由を添える。** 古い決定を別の行に残さない。委譲先は節を丸ごと受け取るため、食い違う行があると、古い決定に従って直し戻しうる。

**1 件 1 行で要点だけを書く。** 指摘の全文、道具の出力、コードは貼らない。読み直すたびにコンテキストを使うためである。

### 1.3 Step 5: 差し戻し対応

#### 指摘の仕分けは呼び出し元が行う

**レビュー Agent は「何が満たされていないか」を返すだけで、「直せるかどうか」は判断しない。** 自分のツール・権限・担当範囲・今回の変更内容を知っているのは呼び出し元だからである。

| 仕分け | 条件 | 行き先 |
| --- | --- | --- |
| **自分で直す** | リポジトリ内の情報と工程ルールで解決できる。**判断材料が揃っていれば決めてよい** | Step 5 で直す |
| **開発者の判断が要る** | **直し方**に複数の案がありどれを採るかで結果が変わる。方針・優先度・責任の所在が絡む。書く内容（振る舞い）が入力から決まらないだけの指摘はここに入れない（下記「指摘に応えて決まりを足すとき」） | `判断してほしいこと` へ回し、停止条件 3 で返す |
| **根拠が無く見送る** | 入力元・テンプレート・品質確認観点（レビュー Agent が自身の定義に持つ固定観点を含む）のいずれにも根拠が無い要求である | 直さない。理由を添えて作業記録の「決めたこと」に積み（1.2 節）、`既知の事項` に加えて次の往復へ渡す（2 節）。工程末の応答の `レビュー結果` にも書く（3.2 節） |

**レビューが返した `開発者への確認事項` は `判断してほしいこと` へ回す。** レビュー Agent が判定できなかったもの（業務知識・案件の事情・実機の確認が要るもの）であり、**呼び出し元も判定できない**。`再確認ポイント` は工程末の応答の `レビュー結果` に書き（3.2 節）、開発者が何を見ていないかを分かるようにする。

**ただし、この 2 つが付いただけでは停止しない。** どちらも修正を妨げないためである。**直せる指摘が残っている間は Step 4 へ戻って回し続ける。** 工程末の完了報告でまとめて開発者へ渡す。

**停止するのは、修正そのものに開発者の判断が要るときだけである**（停止条件 3）。「判定できなかったことの報告」と「修正が進められないこと」を混同しない。

**迷ったら「自分で直す」側へ寄せる。** 決められるものを開発者へ回すと、往復だけが増える。**見送るのは、指摘に根拠が無いときに限る。** 根拠はあるが直したくない、は見送りにならない。根拠の無い要求に応えて書き足すと、入力元に無い情報が根拠なく足され、その境界が次の指摘になる。

#### 直した箇所の帰結を自分で洗う

**直したらレビューへ戻る前に、その変更の帰結を自分で検索する。** 2 節が定める「宣言した変更の直接の帰結」は、**レビューに指摘される前に呼び出し元が潰せる**。

| 直したもの | 洗う先 |
| --- | --- |
| 節や項目を足した・消した | その節・項目を**参照している箇所**、**件数を書いている箇所** |
| 規則の本文を変えた | 同じ規則を**書き写している箇所** |
| 見出しを変えた | その見出し番号で**参照している箇所**、**見出しレベル**（小節のつもりが兄弟節になっていないか） |
| 用語や値を変えた | 同じ用語・値を使っている箇所 |
| **見出しを足した・動かした** | **その位置より後ろにあった既存の本文**。意図しない見出しの配下へ取り込まれ、射程が狭まっていないか |
| **指摘に応えて直した** | **同じ種類の記述をしている、文書のほかの箇所**（同じ観点に同じ形で当たる箇所）。レビューが示した箇所だけを直し、ほかを残さない |

**帰結は検索で見つかるものが多い。** 洗わずにレビューへ戻すと、1 箇所の修正が次の往復で 1〜3 件の差し戻しになる。

**直し終えたら、直した節に関わる観点で自己点検をもう一度通してから、レビューへ戻る。** 1 節「起草のあとの自己点検」と同じことを、直した節に絞って行う。同じ会話の中で済むため、レビューの 1 往復より安い。

#### 指摘に応えて決まりを足すとき

**指摘に応えるために成果物へ新しい決まり（条件・例外・対応表など）を足すときは、その決まりが当てはまる範囲の境界を先に洗う。** 境界の外や、ほかの決まりと重なるところで何が起きるかを決めきれないときは、足そうとした決まりの範囲を、決めきれる所までに狭める。残った部分は推測で埋めない（9 節の制約 6）。決まりの範囲をどこまでにするかの選択に開発者の判断が要るなら、上の仕分けの「開発者の判断が要る」として扱う。残った部分が決まっていない振る舞いなら、次の段落による。決まりを厳密にするほど、その境界が次の往復の指摘になり、往復が伸びるためである。

**決まっていない振る舞い（失敗したときの扱い、画面の戻り先、再試行など）を求める指摘には、推測で書き足さない。** その振る舞いが、入力元・受け取った標準の動き・開発者の答えのどれからも決まらないなら、「未解決」と記して作業記録へ貯める（9 節の制約 6）。**これは仕分けの「開発者の判断が要る」には当たらず、それだけでは停止しない。** 起草中の不明点（1 節 Step 3）と同じ扱いであり、レビューが OK になってから 1 回だけまとめて聞き（1 節）、「後で決める」となったものを工程末に起票の候補として挙げる（7 節）。「開発者の判断が要る」は直し方の選択に判断が要るときであり、書く内容が入力から決まらないこととは分ける。書き足した振る舞いは、その境界が次の指摘になる。ただし、主要な流れを止める振る舞いは、本段落の扱いによらず、その場で聞く（1 節、主要な流れを止める不明点）。

### 1.4 委譲されて動くとき

課題解決 Agent から工程の成果物を渡され、サブエージェントとして動くときの決まりである（9 節の制約 7 の例外）。サブエージェントは開発者と質疑できず、その中からレビュー Agent を呼べない環境もあるため、質疑とレビューは委譲元が受け持つ。

| Step | 委譲されて動くとき |
| --- | --- |
| 1 | 対象は委譲元が決めたものとする。候補を示さない |
| 2 | 質疑をしない。未決の事項をまとめて聞く手順（1 節）も行わず、未決の事項は委譲元へ返す。委譲元から受け取った直し方と「決めたこと」に従う。作業記録を作らない（委譲元の作業記録が正本である） |
| 3 | 受け取った直し方で直し、自己点検をする（1 節）。Agent 定義が起草の中に含める段（実装の工程の生成・検証・テスト・ビルドなど）も行う |
| 4・5 | レビューを呼ばない。委譲元がレビューを呼び、差し戻しの指摘を渡してくるので、それを直す。レビューが OK になったあと、完了を報告する前に行うと Agent 定義が定める手順（実装の工程の、完了を報告する前の必須の検証など）は、委譲元から依頼されて行う |
| 6 | 起票の候補を委譲元へ返す（7 節「委譲先が挙げた候補」）。直した箇所、自己点検の結果、作業記録に積むはずの事項（「決めたこと」と「経過」に当たるもの）を返して、停止する。委譲元がそれを自分の作業記録に積む |

**判断が要る事項に当たったら、そこで委譲元へ返す。** 直し方が決まっていない事項、上流の成果物の食い違いや誤り（5 節の停止条件 9 に当たるもの）、主要な流れを止める未決の事項（1 節）などである。返すときは、その事項と、どこまで直したかを書く。委譲元が開発者に聞いて、続きを渡す。

## 2. レビュー依頼の形式

工程 Agent が `an-review` を呼ぶときは、次をすべて渡す。**レビュー Agent は独立したコンテキストで動き、呼び出し元の会話を知らない**ため、省略すると正しく判定できない。

| 項目 | 内容 |
| --- | --- |
| 成果物キー | レジストリの行を特定するキー（例: `requirements`） |
| レビュー対象パス | 生成した成果物のパス |
| テンプレートパス | 準拠を確認する対象 |
| 品質確認観点パス | 全項目を走査する観点ファイル |
| 入力元パス | 整合性を確認する元資料。**レジストリの「入力元」列を引く** |
| **変更箇所** | **今回の実行で変更した箇所。** パスだけでなく、そのパス内のどこを変えたか（節・表・項番）まで書く。新規に作った場合は「全体」と書く |
| **既知の事項** | **既に起票済み・候補として提示済み・対応を見送ったもの。あわせて、同じ実行の前の往復でレビューが報告したもの。** `範囲外の検出` から除くために渡す。無ければ「なし」 |
| 起草時の論点 | 判断に迷った箇所、意図的に選択した設計 |

**同じ品質確認観点ファイルを使う成果物をまとめて依頼するときは、品質確認観点パス以外の項目を成果物ごとに書く**（1 節 Step 4）。判定は成果物ごとに返る（3.1 節）。まとめるのは、レビュー Agent が同じ観点・同じ入力元・互いの成果物を 1 回読めば済ませるためである。

**前の往復のレビュー Agent に続けて依頼するときも、渡すものは同じである**（1 節 Step 4）。変更箇所として渡したファイルをレビュー Agent が読み直す。

### 判定の範囲

**読むのは対象の全体、判定するのは変更箇所である。**

観点の多くは文書間の関係（参照整合・重複・層の分離）を見るため、**全体を読まなければ判定できない**。一方、差し戻しの根拠を全体へ広げると、1 箇所直すたびに既存のすべてが差し戻し対象になり、**変更が終わらなくなる**。

| 検出した場所 | 扱い |
| --- | --- |
| **変更箇所** | `不足点` と `修正要求` へ。**差し戻しの根拠になる** |
| **変更箇所以外** | `範囲外の検出` へ。**差し戻しの根拠にしない** |

**`範囲外の検出` は工程末の起票の候補になる**（7 節）。捨てるのではなく、判定と切り離して積む。

**`範囲外の検出` へ書くのは、今回はじめて見つけたものだけである。** 渡された「既知の事項」に当たるものは書かない。**既に判断が済んだものを毎回積み直すと、読む側が新しい発見を見分けられなくなる。**

**ただし件数や範囲が増えていれば、その増分は新規として書く。** 既知の事項として渡されたものでも、悪化していればそれは新しい事実である。

**同じ実行の中で往復するときは、前の往復で報告されたものも `既知の事項` へ加える。** 続けて依頼できない環境では、レビュー Agent は前回の報告を覚えておらず、渡さなければ毎回同じものを報告する。続けて依頼する環境でも同じく渡す（環境で振る舞いを分けない）。

### 既知の事項は変更箇所の内側でも除く

**既知の事項として渡されたものは、変更箇所の内側にあっても `不足点` へ書かない。** 除外が `範囲外の検出` にしか効かないと、既知の事項を含む節を触るたびに差し戻しが続き、判断が済んだものをもう一度判断することになる。

**機械検査の NG にも同じ規則が及ぶ。** 差し戻し条件「機械検査の結果が期待値と一致しない」は、**既知の事項を除いた結果**に対して適用する。

**ただし今回の変更によって件数や範囲が増えた分は書く。** 既知だからといって、悪化まで見逃さない。

**変更箇所が渡されなかった場合は全体を判定の対象とする。** 初回のレビューや、開発者が直接依頼した場合がこれに当たる。

**変更箇所は「今回の実行」を単位とする。** レビューの 1 往復ではなく、**Step 1 から工程末までの 1 実行**で変更したものすべてを指す（1.2 節の作業記録と同じ単位）。差し戻し対応で直した箇所も含む。

**宣言した変更の直接の帰結として壊れた箇所は、宣言の有無にかかわらず変更箇所に含める。** 正本を直して写しを放置する変更が通ってしまうためである。宣言された箇所を直したことで参照先・複製・件数・項番が合わなくなったものがこれに当たる。**これらは例示であり、列挙を閉じない** — 宣言した変更が原因で壊れたものは、形にかかわらず含める。

## 3. 応答形式

### 3.1 レビュー Agent から工程 Agent への応答

応答の 1 行目に総合判定を置き、続けて成果物ごとに次の 7 項目を返す。形を固定する。

```
総合判定: OK / 差し戻し（OK <件数> / 差し戻し <件数>）

判定: OK / 差し戻し
対象: <成果物キー>（<レビュー対象パス>）
不足点:
修正要求:
範囲外の検出:
再確認ポイント:
開発者への確認事項:
```

- `不足点` と `修正要求` には**変更箇所で見つけたものだけ**を書く（2 節「判定の範囲」）
- まとめて依頼された場合は、7 項目を成果物ごとに返す（2 節）
- **応答の 1 行目は `総合判定:` にする。** 成果物ごとの判定に 1 件でも差し戻しがあれば差し戻し、すべて OK なら OK とし、括弧に件数を添える。成果物が 1 つのときも書く。まとめて依頼したとき、最初の成果物の判定が全体の判定に見えないようにし、呼び出し元と開発者が 1 行目で全体を読み取れるようにするためである
- **成果物ごとの応答は `判定:` の行から始める。** どの成果物の判定かは `対象:` の行で示し、判定の前に見出しを置かない
- レビューに入る前に示す認識した内容は、応答の中にも、総合判定の行の次に置く。サブエージェントとして呼ばれたときは応答だけが呼び出し元に届き、それより前に示したものは届かないためである
- **総合判定・認識した内容・7 項目のほかに、項目や節を足さない。** とくに良かった点・所感・総評は書かない。判定にも直しにも使われず、書く量と読む量（費用と時間）だけが増えるためである
- `範囲外の検出` には**変更箇所の外で、今回はじめて見つけたもの**を書く。**既知の事項として渡されたものは書かない**（2 節）。**判定には影響させない。** 呼び出し元はこれを工程末の起票の候補へ回す（7 節）
- `開発者への確認事項` には、**レビュー Agent が判定できなかったもの**を書く。業務知識・案件の事情・実機の確認が要り、観点の充足を判定しきれなかった箇所である
- **修正に開発者の判断が要るかどうかは書かない。** それを決めるのは呼び出し元である（1 節 Step 5）。レビュー Agent は**何が満たされていないかを事実として返す**ところまでを担う
- `再確認ポイント` には、**判定に迷った点・適用しなかった観点・次回に重点を置くべき箇所**を書く。**適用しなかった観点は必ずここへ明記する。** 観点ファイルが節ごとの適用範囲を定めている節では、対象外にした項目を節ごとに件数で書き、項目ごとに列挙しない（適用した項目は項番で書く）
- リポジトリ内の情報と工程ルールで解決できる論点を開発者へ逃がさない
- 該当がない場合は `なし` と明記する

### 3.2 工程 Agent から開発者への応答

```
実施内容:
変更ファイル:
レビュー結果:
決まらなかったこと:
判断してほしいこと:
次にできること:
```

- `レビュー結果` には、最後の判定と往復の回数に加えて、レビューの `再確認ポイント` と、根拠が無く見送った指摘とその理由（1.3 節）を書く。**良かった点は書かない**（3.1 節と同じ理由）
- `決まらなかったこと` には、起票した課題の ID を列挙する（7 節）。**まだ候補の段階なら、候補である旨と件数を書く。** どちらも無ければ `なし` と明記する
- `判断してほしいこと` には、**開発者が採否を決める論点**と、**レビューが判定できず開発者の確認が要る事項**（1 節 Step 5）を書く。番号で選べる再実行候補はここに書かない
- 主要な流れを止める事項で、開発者が「決めずに進める」を選んだもの（1.2 節）があれば、`判断してほしいこと` の先頭に `【通らない流れ】` として書く。どの流れの何ができないかと、決めれば何を足せるかを示す。選んだ時点から時間が経っていることがあるため、改めて示す
- **質疑の途中の応答（質問と、聞かない事項の示し）には、この形式を使わない**（1.2 節「質問の出し方」「聞かない事項の示し方」）。起草や指摘への対応の途中で、主要な流れを止める事項を聞く応答と、未決の事項をまとめて聞く応答も同じである（1 節）
- 起票の候補を示すときは、7 節の候補の書式をそのまま `次にできること` に置く。ほかの判断の実行候補をどう出すかは 4 節による

### 3.3 開発者へ提示する文言

**開発者は、この工程の仕組み（本書・レジストリ・Agent 定義）を知らない前提で書く。** 事前に知っているのは起動の手順だけである。表示される文言だけで操作できるようにするためである。

| # | 規律 |
| --- | --- |
| 1 | **次に何をすればよいかが応答の中で完結する。** 仕様を読み返さないと分からない応答を返さない |
| 2 | **下の内部用語を使わない。** 使う必要があるときは、その場で意味が取れる言い換えに置き換える |
| 3 | 選択肢は**それ自体で何を意味するか分かる**ように書く。番号だけを並べない |

#### 内部用語

次の語は**この工程の仕組みの内部を知らないと意味が取れない**。3.2 節の応答、1.1 節の候補提示、停止時の返却など、**開発者が読むものには使わない**。

```
成果物キー / レジストリ / 成果物種別 / アダプタ / サーフェス
持ち越し案件 / 持ち越し課題 / 停止条件
L1 / L2 / L3
固定観点 / 可変観点 / 機械検査 / 読解観点
```

**「成果物」「品質確認観点」「レビュー」「課題」は内部用語ではない。** 字面で意味が取れるため使ってよい。

本節は**開発者へ向けた文言だけ**に適用する。3.1 節（レビュー Agent から工程 Agent への応答）は Agent 間のやり取りなので、正確さを優先して内部用語を使ってよい。

## 4. 次にできることの提示ルール

- 開発者の判断待ちが残らない範囲の継続（レビュー再実行、工程内の Step 移行）は、候補として提示する前に**実行する**
- **後続工程への引き継ぎは自動実行しない。** 次の工程は、自分が実行する候補として出さず、開発者がその工程の Agent に切り替えて始めるよう案内する。切り替え先と手段は 6 節による
- 開発者の判断が必要な場合は、判断ごとの実行候補を `次にできること` に必ず出す。**ただし起票の候補を示す応答では、起票の候補だけを選ばせる。** ほかの判断の実行候補は、起票のあとの応答で出す
- `次にできること` は番号付き候補リストにする。開発者が `1` `2` のように番号だけを返した場合、その候補を選択したものとして同じ文脈で次の実行へ進む
- **候補 1 は常に推奨アクション**とする
- **1 候補 = 1 実行**とする。追加指定が必要な候補は作らない。ただし**1 節 Step 1 の成果物選択には適用しない**（複数選べる）
- 差し戻し先が複数ある場合は、対象単位ごとに別番号へ分ける
- **質疑の応答（1.2 節の質問と、聞かない事項の示し）、起草や指摘への対応の途中で主要な流れを止める事項を聞く応答と、未決の事項をまとめて聞く応答（1 節）、起票の候補（7 節）には、本節を適用しない。** それぞれの節の書式で選ばせる

## 5. 停止条件

次のいずれかに該当したら、その場で返却する。

| # | 停止条件 |
| --- | --- |
| 1 | レジストリに担当成果物の行が無い、または行の参照先ファイルが存在しない（**成果物を生成する工程 Agent の場合**。レビュー Agent は停止せず、適用できる観点に絞って進める） |
| 2 | 入力資料が存在せず、質疑応答でも要件を確定できない |
| 3 | レビューが差し戻しで、修正に開発者の判断が必要 |
| 4 | 工程の完了報告（完了条件を満たしたあと） |
| 5 | 委譲先の Agent / SKILL が解決できない（別の Agent へ代替委譲せず、登録不整合として返す） |
| 6 | **本書が要求する手順を実行できない**（記録の発番など）。実行手段を持たない場合と、実行して失敗した場合の両方を含む。**委譲先が見つからない場合は 5 として返す**（本条は 5 を除いた残りである）。**レビュー Agent にも適用する** |
| 7 | **起票の候補を提示した**（7 節）。開発者が採用するものを選ぶまで書き込まない。**停止しない場合は 7 節が定める** |
| 8 | **開発者が、主要な流れを止める事項について「決まるまで止める」を選んだ**（1.2 節）。質疑の途中なら、残りの質問を終えて作業記録を書き出してから止まる。起草の途中なら、その場で止まる。指摘への対応の途中なら、その往復で直せる指摘を直してから止まる（レビューは呼び直さない）。完了報告は書かない。作業記録の「経過」に停止の行を書く（1.2 節）。止まるときは、記録した課題と、決まったら同じ作業記録の続きから再開できることを示す（1 節） |
| 9 | **上流の工程の成果物の食い違いや誤りのために、今の成果物を正しく作れない**（1 節）。見つけた時点で止まる。完了報告は書かない。作業記録の「経過」に停止の行を書き（1.2 節）、記録する課題の候補を示す（7 節）。開発者が候補を選んだあとの応答で、1 つ上の工程の Agent に戻って直す道と、課題解決 Agent で揃える道を示す（切り替え先は `docs/process/registry.md`「工程 Agent の切り替え先」）。下流にすでに作った成果物があれば、課題解決 Agent を推す。要求資料の食い違いは当たらない。委譲されて動いているときは、止まらずに委譲元へ返す（1.4 節） |

**テンプレートや品質確認観点が「未整備」の場合は停止しない。** できる範囲を進めたうえで、その旨を記す欄は次のとおりとする。

| Agent | 欄 | 理由 |
| --- | --- | --- |
| 工程 Agent | `判断してほしいこと` | **整備するかどうかは開発者の判断**である |
| レビュー Agent | `再確認ポイント` | **適用しなかった観点**の一種である（3.1 節）。判定できなかったのではなく、判定の材料が無い |

## 6. 工程の完了と停止

**AI は工程の完了を報告するが、成果物の妥当性を判断しない。**

- 完了条件を満たしたら、**完了を報告して停止する**
- レビュー Agent の OK 判定は、完了報告の前提であって妥当性の判断ではない
- **次の工程へは進まない。** 次の工程は、開発者がその工程の Agent に切り替えて始める。自分で次の工程を始めたり、その工程の Agent をサブエージェントとして呼んだりしない（9 節の制約 7）。工程を終えたときは、どの Agent に切り替えればよいかを、`docs/process/registry.md`「工程 Agent の切り替え先」から示す。切り替えの手段（Agent の選択欄、切り替えのボタン、切替のコマンド）は環境による。工程を終えたあとに次の工程へ進むよう指示されたとき（「設計に進んで」など）は、会話の中で Agent を切り替える環境では切り替えまで行ってよく、それ以外の環境では切り替え先と手段を示す。切り替えたあとは、切り替えたことを伝えて開発者の指示を待つ

**完了条件は各 Agent 定義が定める。** 本節は停止の規則だけを定め、工程固有の完了条件は持たない。

妥当性の判断と次工程への着手は開発者が決める。**本書の手順は、その判断を記録も確認もしない。**

## 7. 課題の記録

決まっていないことの置き場所は**課題記録に一本化する**。出力先はレジストリの成果物キー `issue-record` を引く。**1 課題 1 ファイル**とし、ブランチ間でのコンフリクトを避ける。

### 起票には開発者の選択が要る

**AI は課題記録を勝手に書かない。** 候補として挙げ、**開発者が選んだものだけを書く**。

| 段階 | 誰が | 何を |
| --- | --- | --- |
| 1 | AI | 工程末に**起票の候補**を提示して停止する（5 節 停止条件 7）。上流の食い違いや誤りで止まるときは、その時点で提示する（停止条件 9） |
| 2 | 開発者 | 採用するものを選ぶ |
| 3 | AI | 選ばれたものだけを `an-create-issue` SKILL で書き、成果物の参照を ID へ置き換える |
| 4 | AI | 完了を報告して停止する（6 節）。停止条件 9 で止まったときは、完了を報告せず、2 つの道（1 つ上の工程に戻って直す、課題解決 Agent で揃える）を示して止まる（5 節） |

**開発者が明示的に起票を指示した場合は、候補の提示を省いて直接書いてよい。** 主要な流れを止める事項で、開発者が「決まるまで止める」を選んだもの（1.2 節）もこれに当たり、その場で書く。

### 何を候補に挙げるか（持ち越し案件の判定）

**工程の完了判定（完了を報告して停止する時点）で未解決のものを候補に挙げる。**

| 状況 | 扱い |
| --- | --- |
| 工程の途中で開発者に聞いて決まった | **挙げない。** 会話で完結する |
| 完了判定の時点で未解決 | **挙げる** |
| 主要な流れを止める事項で、開発者が「決めずに進める」を選んだもの（1.2 節） | **必ず挙げる。** 区分は新規か既存への追記とし、見送りを推奨しない。動かない部分が記録に残らないまま埋もれるのを防ぐためである |
| 上流の成果物の食い違いや誤りで止まったもの（5 節の停止条件 9） | **止まる時点で挙げる。** 記録するかは開発者が選ぶ |
| 工程の途中で見つかった、その場で解決できない事項 | **その場で書かない。** 作業記録の「決まらなかったこと」へ貯め、工程末に候補として挙げる（開発者が「決まるまで止める」を選んだものと、停止条件 9 で止まるものを除く） |
| **レビューの `範囲外の検出` に挙がったもの** | **完了判定の時点で残っていれば挙げる。** 判定に使わなかったからといって捨てない（2 節「判定の範囲」）。**実行中に直したものは挙げない** — 未解決ではなくなるため、他の行と同じ扱いになる |

判定はタイミングで行う。「工程をまたぐかどうか」を主観で判断しない。

**特に、実働環境が無いことを理由に保留した項目は必ず候補に挙げる。** 挙げ漏らすと、実働環境が使えるようになった段階で何を検証すべきか追えなくなる。

### 候補の出し方

**開発者が読んで選べる形にする。** 既存の課題との重複は AI が先に判定し、区分を付けて示す。新規か既存への追記かは、`an-create-issue` SKILL の「分け方」による。

```
記録する課題の候補 3 件

| # | 区分 | 内容 | 根拠 |
| 1 | 新規 | <一行で言い切る> | <なぜ起票すべきか。開発者に質問したか> |
| 2 | 既存 <ID> へ追記 | <一行> | <同じ課題と判断した理由> |
| 3 | 見送り推奨 | <一行> | <既存 <ID> と重複 / 影響が小さい など> |

採用するものを番号で指定してください。すべて見送る場合はその旨を。
```

**根拠には、開発者に質問したかを書く**（作業記録の「決まらなかったこと」から引き継ぐ。例: 「質問した（後で決める）」「質問していない（最後のレビューで見つかった）」）。

**1 件も無ければ「記録する課題の候補はありません」と明記する。** 黙って省略しない。

### 停止しない場合

停止条件 7 は次の 2 つで発火しない。**これ以外に例外は無い。**

| 場合 | 扱い |
| --- | --- |
| 候補が 1 件も無い | 停止せず、その旨を示して完了報告へ進む |
| **委譲されて動いている** | 停止せず、候補を委譲元へ返す（下記「委譲先が挙げた候補」） |

### 見送られた候補の扱い

**見送りは記録しない。** 成果物には起草時の「未解決」がそのまま残る。同じ事象に再び当たれば、次の工程末に候補として再び挙がる。

### レビュー（Step 4）の時点では起票が未了である

**起票の多くは工程末（Step 6）に行うため、レビューを受ける時点では課題 ID が無いことが多い。** 途中で止まったときに記録した課題（5 節の停止条件 8・9）は、再開したあとのレビューの時点で ID がある。 レビュー Agent と品質確認観点は、**成果物に「未解決」と記されていること**をもって充足と判定する。起票済みであることを求めない。

**作業記録へ貯めることは工程 Agent 側の手順であり、レビューの判定基準ではない。** 作業記録は 2 節が定めるレビュー依頼の受け渡し項目に含まれない。義務は 1 節 Step 3 と 1.2 節が定める。

**完了条件の書き方は各 Agent 定義が定める**（6 節）。本節は起票の手順だけを定める。

**起票後の ID 置換に再レビューは要らない。** 「未解決」を課題 ID へ差し替えるだけであり、レビューが判定した内容は変わらない。

### 委譲先が挙げた候補

**委譲元がまとめて提示する。** 委譲先の Agent は候補を委譲元へ返し、自分では停止しない（上記「停止しない場合」）。**候補の提示を委譲元の実行にまとめる**ためである。

**委譲されて動いた Agent は、候補を委譲元へ返した時点で、起票に関する完了条件を満たしたものとする。** 開発者の選択とその後の起票は委譲元の実行の中で起きる。

起票済みの課題を見るときは `an-list-issues` SKILL を使う。

## 8. プラットフォーム依存の扱い

- 工程 Agent の本文に、プラットフォーム固有の手段の名前（SKILL 名・コマンド）を書いてはならない
- 成果物の生成手段は `an-platform-*` アダプタへ委譲する
- 要件定義と設計の Agent は、プラットフォームの標準の動きを `an-platform-spec` から受け取る（1.2 節）。要件定義書と設計書のレビューでは、レビュー Agent もその要点と照らす（照らし方は、その成果物の品質確認観点が定める）
- 出力先パスはレジストリから取得する

これらを守ることで、工程 Agent はプラットフォーム非依存を保つ。

### アダプタへ渡すもの

工程 Agent が手段を解決するアダプタを呼ぶときは、次をすべて渡す（`an-platform-spec` に渡すのは、扱う領域か個別の事項だけである。1.2 節）。**アダプタは手段を解決するだけで、何を作るかは判断しない。**

| 項目 | 内容 |
| --- | --- |
| 成果物種別 | レジストリの「成果物種別」列の値 |
| 機能名 | 対象を括る単位。要件定義書の主要機能で定めた値 |
| 対象 | その機能に属する個々の識別子。**設計書の一覧表から引く** |
| 出力先 | レジストリの出力先列。`{機能名}` を解決した実パス |
| 入力元 | 対象の仕様が書かれた設計書のパス |
| 決めたこと | 作業記録の「決めたこと」の節を、選ばずに丸ごと写したもの（1.2 節）。アダプタは手段へそのまま渡し、これに反する変更をしないこと、反しないと直せない指摘は直さずに返すことを求める。会話の圧縮や委譲で決めたことが失われ、委譲先が直し戻すのを防ぐためである |

**対象をまとめて渡すか 1 件ずつ渡すかは、アダプタの対応表が定める。** 生成の単位はプラットフォームによって異なるため、工程 Agent は決めない。

### 機能名の決まり方

| 工程 | 何をするか |
| --- | --- |
| 要件定義 | 主要機能の表で機能名を定める。**ここが唯一の源である** |
| 設計 | 各設計書の「機能」列で、個々の対象がどの機能に属するかを示す |
| 実装 | 出力先の `{機能名}` として使う。**新たに命名しない** |

機能名は**ディレクトリ名になる**。英数字とハイフンで書き、空白と記号を含めない。

## 9. 共通の制約

すべての工程 Agent が守る。**各 Agent 定義の「制約」には工程固有のものだけを書き、本節を書き写さない。** 同じ規則を複数の Agent 定義に置くと、1 本だけ直して食い違う。

| # | 制約 |
| --- | --- |
| 1 | **`docs/hidden/` を自分から参照しない。** 正解データと他題材の見本を置く場所であり、自分で探して読むと生成能力の検証にならない。開発者が明示的に指した場合のみ読む。書き換えは禁止 |
| 2 | **要求資料（`docs/input/`）は読み取り専用。** 書き換えない |
| 3 | 出力先・テンプレート・観点・入力元のパスを推測で書かない。`docs/process/registry.md` を引く |
| 4 | **工程の完了を報告するが、成果物の妥当性を判断しない。** 妥当性の判断と次工程への着手は開発者が決める（6 節） |
| 5 | **上流の工程の成果物が、後続の工程に向けて定めた扱いに従う**（入力元に限らない。作るものの要否、従うべき指定、実装の分け方など）。従えない事情があれば、推測で逸れずに開発者の判断を求める（要件定義と設計で、プラットフォームの標準と食い違うために従えないときは、1.2 節「プラットフォームの標準の確認」による） |
| 6 | **推測で埋めない。** 入力元やリポジトリから分からない事項は、質問するか、持ち越し案件として**作業記録へ貯め、工程末に候補として挙げる**（1 節 Step 3・1.2 節・7 節） |
| 7 | **ほかの工程 Agent をサブエージェントとして呼ばない。** 本書に従う Agent のうち、サブエージェントとして呼ぶのはレビュー Agent だけである。サブエージェントは開発者と質疑できず、その中からさらにレビュー Agent を呼べない環境もあるため、工程の手順が成り立たない。課題解決 Agent が、工程の成果物を担当の Agent へ渡す場合を除く（そのときの決まりは 1.4 節）。**アダプタが委ねるプラットフォームの規約がサブエージェントを使うこと（生成の分割や検証）は、この制約に当たらない**（その規約に従う） |

**レビュー Agent には適用しない。** 工程の完了を報告せず判定を返す役割であるため、同じ趣旨の制約を役割に合わせた形で自身の定義に持つ（OK 判定は妥当性の判断ではない、`docs/hidden/` にあるものをレビュー対象として指されても置き場所を理由に断らない、など）。
