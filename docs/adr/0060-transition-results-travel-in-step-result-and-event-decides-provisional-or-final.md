# 遷移の結果は Step の結果で運び、速報値か確定値かは読むイベントで分ける

通知の読み手が遷移の結果を env 本体へ問い合わせていたため終端の lane だけリセット後の値を読んでおり、ADR 0059 の、通知の間 env をリセットさせない直し方は、リセットが学習と重ならなくなって遅くなった。そこで **遷移の結果は Step の結果で運び（Step の結果の型が鍵の問い合わせに答える）、env への問い合わせは今の env の状態を返すものとし、BatchEnv は Reset と Step の 2 つに戻して自動リセットを Step の中で行う**ことを決定する。同じ鍵が速報値か確定値かは、読むイベント（`@train`・`@episode_end`）で決め、鍵の共有と NaN の条件は env の実装が決めて設計文書の鍵の表に書く。

## Considered Options

- **ADR 0059 の段（通知の間 env をリセットさせない）**: 通知の中の値は正しくなるが、Atari の非同期の学習 Runner で 5〜8% 遅くなった。却下。
- **段を残し、中身は Step の中で済ませたリセットの結果を返すだけにする**: 段が守るものが無くなり、使われない境目と呼ぶ順番の規則だけが残る。却下。
- **流れは前のまま、外から読む値だけを段まで終端の写しで出す**: 速さは戻るが、動き続ける env にイベントの時点の値を答えさせる埋め合わせのままで、env ごとに写しの作りが要る。却下。
- **予備の ALE で次のゲームを先に用意する**: Atari だけの対策で、ALE が増え（128 lane で約 85 MiB）、起動も延びる。却下。
- **鍵の名前で速報値と確定値を分ける**（例: 確定値に `game_end.` を付ける）: Step の結果に 2 組の値を持つ作りになり、設定の鍵の名前も書き換える。却下。

## Consequences

- `EpisodeEndEvent` は終わった Step の結果を持ち、評価セッションは採用 episode の値を Step の結果から溜める（ADR 0034 の継ぎ目は `continue_state` の使い回しに戻る）。trace の読み手も Step の結果から読む（ADR 0037 の読み口が変わる）。
- env の `GetScalar` から、完了したときだけ値を返していた鍵と、そのための持ち越しを外す。その鍵を読む `$env ... @train` の行は `$env_step ... @episode_end` へ移る。
- Atari は鍵を分けず、`episodic_life` で残機を失ったがゲームが続く step だけ、ゲーム単位の鍵を NaN にする。`ram_metric.[n]` も同じ規則に従う。ADR 0046 が「NaN の規則を変えるときは新しい ADR で行う」とした新しい ADR は本 ADR である。
- 詳細は [PRD 097](../memo/097_env_auto_reset_after_notification_10prd.md)。
