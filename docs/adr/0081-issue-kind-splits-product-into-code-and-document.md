# 課題の kind は成果物をコードと文書に分け、実装の課題か文書の課題かを kind で表す

同じ domain の課題でも、実装の課題か文書だけで閉じる課題かを一覧で見分けられるように、課題の `kind` の値「成果物」を「コード」と「文書」に分け、`ハーネス`・`文書`・`コード` の順に当てる（定義は [anet-create-issue](../../.agents/skills/anet-create-issue/SKILL.md) の「監理の項目」）。文書かどうかは起票の時点の中身からの見立てで決め、直す側が決まらない文書と実物の食い違いはコードに入れる。設計文書が仕様の正本なので、まず実物を疑うためである。

## Considered Options

- `type` に「文書整備」を足す: 欄は増えず、Conventional Commits の `docs` とも並ぶが、仕事の種類に「何を直すか」が混ざり、文書の誤り（不具合）や文書の追加（機能追加）と重なるので採らない。
- 「直す物」の欄を新しく足す: 関心は分かれるが、起票のたびに欄が増え、全部の課題に値を入れる移行が重いので採らない。

## Consequences

- 古い値「成果物」は受け付けない（互換の読みを置かない）。古い skill を読んだまま起票したセッションは、一覧の作り直しの検証で止まるので、その課題の値を直す。
