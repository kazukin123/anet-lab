# 設定の選択は参照先の最終値を読み、Run プロファイルの葉は CLI と同じ第 2 相で選択の後に勝つ

設定解決には、上書きが黙って効かなくなる経路が 2 つあった。(a) 選択 `X.$ = Y > Z` は宣言時点の Y / Z のスナップショットを写すため、後段の上書き層や CLI が Y へ加えた変更が X へ届かない。PRD 061 の `DefaultDQNAgent.actor.[eval_target].$ = …[eval] > …@target` がこの形で、差分を二重に書くしかなかった。(b) Run プロファイル(`run.@<name>`)の葉キーは直書きと同じ tier で実効側へ写るため、選択チェーンが同じキーを書くと負ける。2026-08-31 の `run.@head_relu` と 2026-09-12 の `run.@btrnet` で `net.@iqn` 所有の `[tau_embedding].structure` が握り潰され、いずれも fail-fast も警告も出なかった。CONTEXT.md の「Run プロファイルは上のラダーや上書き層より強い」という契約と実装が逆だった。

2026-09-12 の第 1 版は (a) の解決をカタログ項目(`[key]`)に限定したが、同じ右辺 `@policy_base` がコピー先に `[key]` があるかどうかで意味を変える非対称を生み、限定の根拠(identity)は消費側の性質で設定解決時には誰も知らないため原理にならなかった。全設定の静的走査で、最終値読みを全選択へ広げても実効設定が変わる箇所は 0 件(選択 98 本)だった。

**全ての選択が参照先の最終値(選択段・Run プロファイル第 2 相・CLI 第 2 相を全て適用した後の値とキー集合)を読み、結果は選択の宣言位置に書く**ことを決定する。読みは最終値、書きは「後から書いたものが勝つ」で、優先順位は 直書き < 選択チェーン・上書き層 < Run プロファイル < CLI の 4 段とし、Run プロファイルの葉キーには CLI と同じ第 2 相を与える。第 2 相の葉はそのキーへの最優先の書き込みとして最終値に含まれ、参照する選択へ届く。同じコピー先へ別の宣言位置から複数の `.$` が届く場合は最後に適用されるものだけを採用し、プロファイル自身の `.$` はその term の一部として実体化し、組み立て済み(実効側)の参照先の `.$` は子で再実行しない。`[key]` の有無で読み方を変えない。自己供給(選択の書き込み範囲が自分の source prefix と交わる形)と循環は経路付きで fail-fast、深さは依存グラフの最長経路長で 10 まで。`config_resolution.json` は適用したチェーンを適用順に載せ、第 2 相で値が変わったキーを `overrides` として記録する(`schema_version` は 1 のまま)。

## Considered Options

- **最終値読みを `[key]` カタログに限定する**: 同じ右辺の意味がコピー先で変わる非対称を生み、限定の根拠が原理でなく既存 config への影響回避だった。却下
- **選択を依存順へ並べ替える**: 後段 overlay が負けるなど書き込み優先順位を変える。却下
- **書きかけ map を同順で繰り返し読む / 全設定の Jacobi 反復と last-writer graph / 周回数の安全弁**: 契約は方式に依存させない。必須方式から除外
- **第 2 相の葉(Run プロファイル・CLI)は終端上書きで伝播しない**: 安いが、`run.@x : …[eval].policy.eps_start = 0` で `[eval]` だけが変わる stale copy を Run 層に作り直し、2026-09-08 の裁定「CLI 最終値まで継承」に反する。却下
- **owner と source が包含関係の選択を fail-fast にする**: `app.$ = app.online > P1` など実設定 9 件が落ちる。自己供給だけを止める。却下
- **握り潰しを WARN で可視化するだけ**: 検出に要る準備は第 2 相の実装と同じ。却下
- **継承専用の記号(`&` 等)や `+=` 相当の差分演算子**: 全選択で揃えれば見分ける必要がなく、差分は右辺の継承で表せる。追加しない

## Consequences

- 既存設定の実効値と解決記録は変わらない想定(静的走査 0 件、既知の握り潰し 2 件は設定側で回避済み)。実装完了は全 env × 代表 Run プロファイルの差分ゼロ gate で判定する(PRD 072 §7)
- Run プロファイルの直接キーが契約どおり選択チェーンに勝つ。「A3 に書けば回避できる」という経験則は不要になるが、上書き層へ書く用法はそのまま有効
- 寸法が連動するキー(`[tau_embedding].structure` と `[main_feature]`)は、個別キーの上書きより `DefaultDQNAgent.$` のチェーン差し替え(`@iqn2304`)で切り替えるほうが正しく、その用法も維持する
- リゾルバはスナップショットのコピーではなく依存を評価する実装になる。P4(第 2 相の再適用と `overrides`)単体は小さいが、伝播は P1 の評価器が担う
- `config_test.cpp:939`(同一 owner の nested)は両記録の `key = Env.$` を pin し、M01〜M15 の受入テストを追加する。`docs/design/100` の解決記録の記述は実装と同時に同期する
- `999_config_run_profile_override_precedence_10prd.md` は PRD 072 に吸収し廃止する
- 詳細契約・マニュアル草稿・受入条件は `docs/memo/072_config_selection_final_value_10prd.md`。Actor 設定カタログ側の決定は ADR 0038
