# Metrics表示は共通Step区間、保存LODはfactor4とする

PRD 089の調査では全タグの共有点予算とfactor16の段差により、2Runから表示が序数幅256→4096へ落ち、キャッシュの再利用で混在した。表示の比較単位をStep=0起点の共通区間とし、保存LODをfactor4へ変更する。区間に収まる完成bucketを再利用し、境界だけ下位へ降りることで、記録頻度の違うRunも同じ区間で正確に集約できる。

ADR 0015のfactor16のみを更新する。合成SQLite検証でfactor4は16に対してDB容量約1.7倍、境界L0参照約1/5だった。factor2の約3.5倍の容量増とfactor16の境界コストを比較して4を採用した。schema=2へ上げて全キャッシュを自動再構築する。マスタ地位、序数PK、短命接続、generation、migrationを持たない方針は維持する。グラフ単位の取得と通常モードの近傍描画によって、全タグ数が可視グラフの粒度を下げない。

2026-10-11、スクロール時の空白待ちを減らすため、近傍外の詳細windowを即時解放する方式から64MiBのLRU保持と近い順の先読みへ変更した。メモリ不足を実測していたわけではなく、保持範囲が保守的すぎた。概観は約64共通Step区間の軽量SVGで全選択タグへ先に表示し、詳細待ちも線を残す。Plotly描画を近傍へ限る方針は維持し、全グラフのPlotlyオブジェクトを常時保持するメモリ増を避ける。

2026-10-14、手書きSVGの軸・凡例・余白が詳細と一致せず、切替時に壊れて見えることを同一入力で再現した。SVG保持は維持し、共通のPlotly figureから直列生成する方式へ変更する。4Run×64graphの検証で生成約0.9秒、初回表示追加約36ms、保持メモリ増分約18MiBであり、二重の描画実装を維持するより見通しを優先した。外枠とheaderを保持し、遅着結果を排除する。保存LOD/schemaの判断は変更しない。
