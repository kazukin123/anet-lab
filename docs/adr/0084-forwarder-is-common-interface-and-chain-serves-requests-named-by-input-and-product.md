# 観測の加工は、共通の口 Forwarder の並びとし、並びへの依頼は「何を渡して何が欲しいか」で名付ける

観測の加工（重ねる・正規化）の定義が、行動選択・経験の受入れ・Sample・可視化の 4 つの経路と spec の生成に分かれて書かれていて、観測キーを 1 つ足すたびに全部をそろえることになっていた（[PRD161](../memo/161_observation_pipeline_10prd.md)）。**「TensorDict を受けて返す変換」だけを持つ口 Forwarder を基盤に置いて Network にも実装させ、観測の加工は、通したあとの spec も答える部品を設定で並べたものとし、並びへの依頼（統計を更新しつつ Frame を作る、重ねた束から Perception を作る、1 枚の Frame から Perception を作る）を選ぶと、その依頼用の Forwarder が返る**ことを決定する。lane の履歴を使う依頼だけは行動選択用の実行器が受け、Network と実行器（[ADR 0051](0051-nn-forward-prepares-concrete-calls-and-purpose-owned-execution.md)）と同じ二段にして、用途ごとの状態を定義から切り離す。

## Considered Options

- **定義を持つクラス 1 つから、各経路が部品を取り出して並べる**: 部品が増えるたびに、取り出す口と呼ぶ側の両方が変わる。却下。
- **部品が、使われる所ごとの関数と状態を自分で持つ**: Actor ごとに部品を複製することになり、履歴の持ち主が定義と混ざる。却下。
- **依頼を、呼ぶ側の状況（行動選択・push・Sample・可視化）で名付ける**: 呼ぶ側の都合の名前で、頼む中身を表さない。push するのは呼ぶ側で、並びに頼むのは「Frame を作る」である。却下。
- **依頼ごとに別の名前の口を作る、または Forward の引数に依頼を足す**: Network には依頼の区別が無く、共通の口が Network と違う形になる。依頼は、Forwarder を受け取るときに選ぶ。却下。
- **正規化の統計を、並びの外で Agent が持つ**: 1 つの正規化を、並びの位置と Agent の持つ統計の 2 か所で表すことになる。統計は部品が持ち、更新は「統計を更新しつつ Frame を作る」依頼だけで行う。却下。
- **共通の口に spec の変換も持たせ、Network が出力の spec を持つ**: 出力の spec を導くには Head まで仮の forward を通すことになり、乱数を引く module があると同 seed の等価性が崩れうる。使う側もまだ無い。出力の spec を使う部品が出たら足す。先送り。
- **逆方向（保存するとき用）の変換の口も持つ**: ReplayBuffer には加工前の Frame を入れ、読む側が同じ並びを順に当てるので、戻す処理が要らない。今の部品はどれも元に戻せない加工である。保存する形を加工する要求が出たら足す。先送り。
