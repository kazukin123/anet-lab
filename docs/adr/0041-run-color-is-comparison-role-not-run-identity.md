# Run 色は比較ごとの役割とし、分離は選択中 Run の集合に対してだけ保証する

Metrics Viewer の Run 色は、Run list 描画時に workspace 内の全 Run へ runId 昇順で先着順に配り、index を `runColorMap.size % 20` で決めている。
色が決まるのは「workspace 内での位置」であって「今の比較の構成」ではないため、比較したい 2 本が palette 上で隣り合えば似た色になり、20 離れれば同じ色になる。
Run が溜まった workspace で昔の Run と現在の Run を比べると、これが頻繁に起きる。
20 色 palette と現行規則で、選択集合に OKLab 距離 ΔE < 0.12 のペアが含まれる確率は、30 Run の workspace で 4 本比較のとき 62.5%（うち完全同色 13.6%）である。

**Run 色を「今の比較の中での役割」と定義し、Run の属性としない**ことを決定する。色は保存せず、reload と workspace 切替で配り直される。Run の同一性を担うのは runId（Run list と凡例が表示する）であって色ではない。
**分離を保証する範囲は選択中 Run の集合だけ**とし、未選択 Run は対象外とする。graph に描かれるのは選択中 Run だけなので、未選択 Run と chip の色が重複することは許す。

操作は 2 つに分ける。**`Recolor` ボタンは強制最適配色**で、現在の色を無視し、選択順に farthest-point で palette の最良組を配る（起点は palette 先頭 `#2F7DE1` に固定し、本数が同じなら常に同じ色の組になる）。
**`Auto` チェックボックスは維持優先パス**で、選択集合が変わるたびに走り、既存の色が `min(0.16, 今の palette で取れる最良)` を満たすなら維持し、満たさない Run だけを配り直す。既定は ON。
どちらも色は 20 色 palette から選び、新しい色を生成しない。選択が 20 本を超えたら次のラウンドを始め、ラウンド内では必ず相異なる色になる。

走査順を**選択順**（後から選んだ Run が末尾）にしたことで、追加安定が構造的に保証される。既存選択は常に前置され、判定は自分より前の色だけに依存するため、Run を足しても既存の色は動かない。
この性質があるため、維持しきい値を上げてもコストがほとんど無い。しきい値 0.16 は選択 5 本まで最小 ΔE 0.161 を保証し、7 本以上では palette の上限に律速されて 0.12 と同じ結果になる（N=7 で 0.115、N=10 で 0.103）。

## Considered Options

- **Run 色を Run の属性として永続する**（workspace 単位で localStorage へ保存）: 「この Run はこの色」という記憶が得られるが、消えた Run の掃除、workspace ごとの肥大、20 色を超えたときの枯渇処理が新たに要る。Run の同一性は runId が既に担っており、色に二重に持たせる理由が無い。却下。
- **選択順に palette 先頭から機械的に配る**: 実装は最小だが、選択を 1 本足すたびに後続の色がずれる。palette 先頭順の最小 ΔE も N=3 で 0.1162、N=7 で 0.0828 と低い。却下。
- **走査順を runId 降順（Run list の表示順）にする**: 同じ選択集合なら選んだ順に関係なく同じ色になり、スクリーンショットの再現性が得られる。一方、新しい Run を足すと既存の色が動きうる。実験を回しながら最新 Run を足す操作が頻繁なため、追加安定を優先して却下。
- **走査順を runId 昇順にする**: server 列挙順・`Select All` と一致するが、古い Run を後から足す（今回の主ユースケース）と、より新しい既存 Run の色が動く。却下。
- **ボタンと Auto を同じ維持優先パスにする**: 契約が 1 つで済むが、維持優先は冪等なので Auto が ON の間ボタンが実質無効になり、しきい値ギリギリの見づらい組（例 `#E23B4F` と `#B83280` の 0.1204）から逃げる手段が無くなる。却下。
- **ボタンを押すたびに別の配色へローテーションする**: 「この組み合わせが嫌」に唯一応えられるが、回転位置という推定しづらい状態を持ち、同じ操作が同じ結果にならない。却下。
- **最適配色の起点を「1 本目の現在色」にする**: 主役の色がボタンで動かない。ただし起点の色次第で結果が劣る（N=6 で最悪 0.144、palette 先頭固定なら 0.172）。ボタンは妥協なしの最良を担う役割なので却下。
- **未選択 Run の色も選択中と衝突しないよう配り直す**: Run list 全体で色が一意になるが、選択を変えるたびに未選択行の chip が動き、workspace の Run が 20 を超えるとそもそも一意にできない。却下。
- **未選択 Run を無彩色にする**: 「色＝比較の役割」と最も整合するが、基本色が消えるため選択のたびに必ず配り直しが要り、`Auto` を切れなくなる。却下。
- **選択が 20 本を超えたら分離しない**: 「上限は 20 本」という契約は明確だが、21 本目を選んだ瞬間に先頭 20 本の分離まで失われる。ラウンド継続を採用。
- **しきい値 0.12 / 0.20**: 0.12 は基本色をよく尊重するが 0.1204 の組を維持してしまう。0.20 は Auto の挙動がボタンへ寄りすぎて基本色がほぼ上書きされる。0.16 を採用。
- **色を使わず線種・marker で区別する**: 色の判別問題を解かず、Band 表示の塗りにも効かない。却下。
- **HSL などで N 色を動的生成する**: 20 本の上限は外れるが、暗背景 `#111` 向けに調整済みの palette の見た目と可読性を捨てる。却下。

## Consequences

- 既定 ON と しきい値 0.16 の組み合わせにより、**基本色（Run list の先着順の色）は選択した瞬間に上書きされるのが常態**になる。基本色が残るのは未選択行だけである。
- **同じ 4 本を選んでも、選んだ順が違えば色の割り当て先が変わる。** ボタンを押した場合は使われる色の組は同じで、どの Run に付くかだけが変わる。実験記録へ貼るスクリーンショットで色の一致が必要なら、選ぶ順を揃えるか、記録側で runId と色を併記する。
- **色は保存しない。** reload・workspace 切替の後は基本色から始まり、`Auto` が ON なら次の選択で分離し直される。OFF のときはボタンを押すまで基本色のままになる。
- **選択中と未選択で同じ色の chip が Run list に並ぶ。** 選択中かどうかは行の背景（`.run-row.active`）で判別する。
- **分離できる上限は palette の 20 色**である。21 本目以降は同じ色が再び現れ、`Select All` を大きな workspace で使うと重複する。上限を上げるには palette の拡張が必要で、それは別の決定とする。
- 選択が 1 本以下のときボタンは何もしない。分離すべき相手がいないためである。
- server、Metrics キャッシュ、HTTP API は変更しない。browser 側の表示規則だけが増える。
