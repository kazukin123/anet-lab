# 作業の種類でだけ要る規約の細則は品質確認観点を正本にし、AGENTS.md からは「作業ごとに読むもの」の表で導く

C++ のコーディング規約、コメント・TODO、ProfileRange、GetScalar、ログ、所有権、設定ファイルの細則は、`AGENTS.md` から `docs/quality/impl.md` の該当の節へ移して節の冒頭の「規約」を正本にし、書く前に読まれるように `AGENTS.md` には「作業ごとに読むもの」の表を、入口 skill には書く前に読む段を置く（PRD 087 の段階 3）。`AGENTS.md` は毎回全文を読む前提の文書なのに、その約 2 割がこれらの細則で、観点も同じ規約を言い換えて持っていたため、2 か所のずれと毎回の読み込みを無くす。PRD 087 の段階 1 の「観点は規約を書き写さず所在を指す」「`AGENTS.md` は変えない」と、ADR 0042 が正本を `AGENTS.md` と書いた代入演算子の運用規約の置き場を改めるもので、ADR 0049（共有コアの扱い）と、`AGENTS.md` に残る原則と how-to は変わらない。

## Considered Options

- **規約を別の新しい文書へ移し、観点は所在を指す形のままにする**: 段階 1 の観点の形を保てるが、置き場が 1 つ増え、書く側は規約の文書と観点の 2 つを読むことになる。
- **規約を既存の設計文書（140 や、設定ファイルならユーザーガイド 020 など）へ移し、観点は所在を指す形のままにする**: 置き場は増えないが、設計文書は PRD から作られる下流の文書で、更新の対象であり、積極的に読む前提ではないので、規約の正本にしない。書く側が 2 つ読むことにもなる。
- **観点の項目の文そのものを規約にする**: いちばん短いが、ProfileRange の名前の例や GetScalar の判断の基準のような理由と例が入らず、書く前の手引きとして弱い。
- **原則（クリーンブレーク、Fail-Fast、設定値の扱いの本文）まで移す**: `AGENTS.md` はさらに軽くなるが、PRD と実装の両方の観点が根拠にしていて正本の置き場が定まらず、観点を読まない会話（設計の相談、Codex への小さな依頼）で見落とされる。
