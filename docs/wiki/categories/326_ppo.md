# 326 Agent個別実装 PPO系列

[anet-lab](../../../README.md) › [wiki の目録](../index.md) › [機能カテゴリ](../index.md#機能カテゴリ)

## 概要・責務

- PPO系は、方策を直接学ぶAgentの系統で、最初のAgentのPPOAgentが離散行動のPPOを実装する。経験をReplayにためず、今の方策で集めたrolloutを1回の更新で使い切る（出典: [PPO系Agent](../../design/230_ppo_agents.jp.md)、§1.1）。
- PPO系は`src/algo/ppo`に置き、coreにだけ依存する。公開するのは初期化関数`InitPpo()`だけで、Runnerが起動時に呼んでfactoryを登録する（出典: [PPO系Agent](../../design/230_ppo_agents.jp.md)、§1.2）。
- 損失の式と更新の進め方はPPO系が持ち、行動の分布、advantageの推定、Headの合成はcoreの部品を使う（出典: [PPO系Agent](../../design/230_ppo_agents.jp.md)、§1.2）。
- NetworkはAgentが持ち、Learnerが更新する。学習のActorは同じNetworkを共有し、評価のActorは写しを持つ。rolloutの器とoptimizerはLearnerが持つ（出典: [PPO系Agent](../../design/230_ppo_agents.jp.md)、§2.1）。
- 方策と価値でBodyを共有するか分けるかは、Headが受け取る2つのキーを向けるbranchの設定だけで決まる（出典: [PPO系Agent](../../design/230_ppo_agents.jp.md)、§3.2）。

## 成立の経緯

- 2026-11-25: 方策ベースのAgentの系統としてPPO系を新設し、離散行動のPPOAgentと、設定・メトリクスのプロファイル・CartPoleの設定を足した。あわせて、coreに行動の分布・advantageの推定・Headの合成を足した（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§1・§6.1）。

## 選ばなかった形

RFD0202は暫定の起票で、次の項目は、再グリルで見直す前提の暫定の既定による。

- 方策と価値にNetworkを2つ持つ形 — 不採用: 写し・保存・同期・optimizerが2組になり、共有の形を別の仕組みで作ることになる（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U4）。
- Runnerにrolloutの境界を知らせる口や、評価をexp stepで駆動する口を足す形 — 不採用: 今の契約で書けるので足さない（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG2）。
- DQN系の部品をcoreへ移して、PPO系と共用する形 — 先送り: 開発者の了承が無いので移さず、候補と確かめ方を残した（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG1・§10）。
- 連続行動（Gaussianの分布と連続のHead）を同時に作る形 — 範囲外: 行動の受け渡しの横断の改修で、別の関心である。再開条件: 連続行動のRFD（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG3・§11）。
- Forwarderの並び（FrameStack・Normalize）をPPO系に結線する形 — 範囲外: 仕上げの部品がDQN系の中にあり、同じものを重ねて書くことになる。再開条件: Atariか連続行動をPPO系で回すとき（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG4・§11）。
- 報酬の正規化、観測の正規化、AMP、可塑性・勾配ノイズの診断、方策の確率のGUI表示を入れる形 — 範囲外: CartPoleの受入に要らず、どれも独立に足せる。再開条件は項目ごとにある（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG5・§11）。
- KLの判定をミニバッチごとに行う形（SB3の形） — 不採用: ミニバッチごとに、deviceからCPUへの転送が要る（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U23）。
- SACをこの系統に入れる形 — 範囲外: ReplayとQのNetworkを使い、rolloutとadvantageの推定を使わないので、別の系統にする。再開条件: 連続行動のあと（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U13・§11）。
- `ppo_assembler`・`ppo_heads`のファイルを立てる形 — 先送り: PPO系のAgentが1つで、専用のHeadが無い。再開条件: 2つ目のAgentか、専用のHeadを足すとき（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§7.8）。
- 更新結果の統計を`HostReadback`に載せる形 — 不採用: 読むのは更新の直後の同じスレッドで、あいだに進める処理が無く、載せても同期の転送と同じである（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U22）。

## 変えるときの条件

一般の条件は[リファクタリング観点](../../quality/refactor.md)の「ガードレール」、テストの充足は[定点統計](../../../reports/stats/trend.md)の「テスト充足」を見る。

- PPO系のライブラリは、coreにだけ依存し、兄弟の系統に依存しない。系統の一覧に`anet-algo-ppo`を足した依存の検査で確かめる（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§8）。
- Networkを共有するActorで集めたrolloutは、更新の前の最初のミニバッチで、新旧の方策の確率の比が1になる（`first_ratio_deviation`が1e-5以下）。収集時と更新時で、同じ入力から同じlog確率が作られていることを示す（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§9 A9）。
- テストの中の小さな課題で、seed 3つのすべてで、学習の終わりのreturnの平均が、最適な方策のreturnの9割以上になる（hiddenのテスト`[ppo_learn]`）（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§9 A12）。
- Runner・Observer・`rl.hpp`の今ある口と、DQN系のコードと動きを変えない（出典: [RFD0202](../../memo/0202_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG1・NG2）。
