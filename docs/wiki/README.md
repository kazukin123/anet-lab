# wiki の規約

wiki は、外にある正本を題材・機構、アプリケーション・機能カテゴリごとに束ねた、中身のあるまとめである。索引は目録だけに置く。[目録](index.md)・[作業の記録](log.md)。

## 原則と正本

- wiki だけにある知見を作らない。正本は実験記録、サーベイ、PRD、設計文書、ADRに残す。出典と食い違ったら出典を正とし、まとめを直す。
- 許す重複は「正本 → まとめ」の一方向の1段だけ。資料ごとの要約ページは作らない。memoryは出典にしない。PRDは元の出典を確認し、判断が依存する事実を本文に出典つきで書く。
- 新しい知見は先に正本へ書く。PRDの背景はPRD、PRDに繋がらないRun分析は実験記録を正本にする。実験記録READMEを要約と独自分析に仕分けるまでは、現在のREADMEの扱いを維持する（段階3）。
- srcは実装の地図からファイルへリンクするだけで、中身を要約しない。機能カテゴリ間の依存も書かない。機構ページは仕組みを説明せず、効いた条件・効かなかった条件・観測された現象を書く。仕組みは設計文書の章へリンクする。

実装契約と決定の理由は[PRD095](../memo/095_llm_wiki_10prd.md) §4・§7を参照する。

## 置き場と書式

```text
docs/wiki/
├─ README.md        規約（原則、書式、出典の書き方、更新のきっかけ、機械的な確かめ、公開できない値の走査）
├─ index.md         目録
├─ log.md           作業の記録（追記だけ）
├─ subjects/        題材（Env・ゲーム）。例 kung_fu_master.md
├─ mechanisms/      機構（アルゴリズムの部品・設定の軸・現象・評価の読み方）。例 lane_window.md
├─ apps/            実装の地図: アプリケーション（Topic の 1xx）。例 110_runner_app.md
└─ categories/      実装の地図: 機能カテゴリ（categories.json の 31x〜32x）。例 324_dqn.md
```

- 実装の地図の 2 段: 上の段は「アプリケーション」（RunnerApp、MetricsViewer）、下の段は「機能カテゴリ」である。「機能カテゴリ」は categories.json の定義（ファイルパスとの対応を持つもの）を指し、docs/design の README の章分けの「機能カテゴリ」とは別である（ページから設計文書の章へリンクして関係を示す）。「機能グループ」（`.hpp` / `.cpp` の組）はページにせず、機能カテゴリのページの中の行にする。ファイル名は categories.json の key。
- アプリケーションのページの範囲は、置き場（RunnerApp は `apps/runner/**`、MetricsViewer は `apps/metrics-viewer/**` と `viewers/metrics-viewer/**`）の下のファイルを、先に当たる機能カテゴリごとに並べたものである（置き場の下には、アプリケーション自身の key のほかに、別の機能カテゴリや、どの機能カテゴリにも当たらないファイルがあるため）。アプリケーションが含む機能カテゴリは、この並びから分かる。

- ファイル名は英小文字・数字・アンダースコア。
- 機構のページは仕組みを説明しない。書くのは、効いた条件・効かなかった条件・観測された現象である。仕組みは「関連」で設計文書の章を指す（設計文書の役割を変えないため）。
- ページの節は次の 5 つ。
  - 「今の結論」: 1〜5 行。「分かっていること」の項目の言い換えだけで書き、そこに無い新しい判断を書かない（wiki だけにある知見を作らないため）。
  - 「分かっていること」: 主張を 1 項目ずつ書き、それぞれに出典を付ける。
  - 「分かっていないこと」: 問いの形だけで書く。計画や候補は書かない（PRD の役割）。出典どうしが食い違うものもここに書き、食い違う出典を両方添える。
  - 「撤回・更新」: `- YYYY-MM-DD: <前の主張> → <今の主張>（出典: <リンク>）`。
  - 「関連」: 設計文書の章、CONTEXT.md の語、PRD。
- 実装の地図のページの節は、上の 5 つの代わりに次の 8 つにし、この順に並べる（取り込みで直す書く部分を前、機械的な部分（「ファイル」と「PRD の一覧」は点検が、「台帳の指摘」は台帳のツールが作り直す）を後ろに置く）。
  - 「概要・責務」: 設計文書の該当の章の言い換えだけで書き、出典を付ける。設計文書に書かれていなければ「設計文書に記述なし」と書き、src を要約しない（点検が報告に挙げる）。
  - 「成立の経緯」: どの PRD で生まれ・変わり、どの ADR が形を決めたかを、日付の順に 1 項目ずつ書き、それぞれに PRD か ADR の出典を付ける。
    - 載せる PRD は、ページの範囲のうち機能カテゴリに当たるファイル（アプリケーションのページなら、アプリケーション自身の key に当たるファイルと、ほかの機能カテゴリに当たるファイル）に触れたコミットの scope の PRD である。「機能カテゴリなし」のファイル（設定ファイル、`CMakeLists.txt`、workspace の設定など）だけに触れた PRD は載せない。そうした PRD は、機械的に作る「PRD の一覧」にだけ載る。
    - PRD の説明は題と目的から読んだ「何をしたか」の1行にする。ただし、題が対象のアプリケーション・機能カテゴリに関係しないときは、本文の、その対象に何をしたかが書かれた箇所から1行で書き、その節を出典に付ける。
    - 載せる ADR は、経緯に載せた PRD が本文で挙げる ADR と、「概要・責務」の出典にした設計文書の章が挙げる ADR のうち、対象のアプリケーション・機能カテゴリの形に関わるものに限る。
  - 「選ばなかった形」: 対象の形について選ばなかった形を、1 項目ずつ `- <選ばなかった形> — <不採用｜先送り｜範囲外>: <理由の 1 行>[。再開条件: <何が揃ったら作るか>]（出典: <PRD か ADR>、<節>）` で書く。
    - 裁定の語は出典の裁定をそのまま写す（「範囲外」は別の関心として別の PRD に回したもの）。再開条件は、先送りと範囲外で出典に書かれていれば写す。
    - 材料は、成立の経緯に載せた PRD の全文（節の名前によらない。「取り込み・点検」）と、経緯に載せた ADR の Considered Options である。
    - 載せるのは、対象のアプリケーション・機能カテゴリの形に関わるものだけにする（経緯の ADR の絞り方と同じ）。PRD が採った決定（何を作ったか）は写さない。
    - あとの PRD がその形を採ったら、項目を消さずに、末尾に `→ PRD0xx で採用（出典: <PRD>、<節>）` を添える。
    - 書くことが無ければ「記述なし」と書く。
  - 「変えるときの条件」: 対象を変えるときに守る不変条件と、挙動を変えていないことの確かめ方を、1 項目ずつ `- <条件か確かめ方>（出典: <リンク>、<節>）` で書く。
    - 写すのは、挙動を変えていないことの確かめ方（等価性・再現性・性能・回帰。metrics checksum の比較、同 seed の再現性、性能の比べ方など）と、出典が「変えない」「保つ」と書いた挙動である。新しい挙動の合否（機能の受入）は写さない。PRD が採った決定（何を作ったか）も写さない。
    - 材料は、「概要・責務」の出典にした設計文書の章、経緯に載せた ADR、経緯に載せた PRD の全文（節の名前によらない。「取り込み・点検」）である。
    - 節の冒頭に、「一般の条件はリファクタリング観点（`docs/quality/refactor.md`）の『ガードレール』、テストの充足は `reports/stats/trend.md` の『テスト充足』を見る」という 1 行を、ページからの相対リンクにして置く（同じ正本の要約を各ページへ写さないため）。
    - 書くことが無ければ「記述なし」と書く。
  - 「関係」: 設計文書の章、ユーザーガイドの節、アプリケーションのページなら含む機能カテゴリのページ、機能カテゴリのページなら含まれるアプリケーションのページ。機能カテゴリ間の依存は書かない。含むもの・含まれるものが無いときは、その項目を「含む機能カテゴリ: なし」「含まれるアプリケーション: なし」と書く（MetricsViewer の置き場の下のファイルは categories.json で 120 自身に当たるので、含む機能カテゴリは「なし」になる。`core` の下だけに当たる 315 ニューラルネットワークなどは、含まれるアプリケーションが「なし」になる）。
  - 「ファイル」（機械的に作る）: 対応するファイルを、機能グループ（同じ名前の `.hpp` / `.cpp` を 1 行）ごとに並べ、src のファイルへリンクする。ファイルの一覧は `git ls-files --cached --others --exclude-standard`（追跡中のファイルと、無視されていない未追跡のファイル）から作る（ほかの判定と同じく作業ツリーを含めるため）。
    - アプリケーションのページは、置き場の下のファイルを、先に当たる機能カテゴリごとの見出しの下に並べる。どの機能カテゴリにも当たらないファイル（`apps/runner/config/*.txt` など）は「機能カテゴリなし」の見出しの下に並べる。categories.json でアプリケーション自身の key に当たるファイル（RunnerApp の `apps/runner/src/`、MetricsViewer の置き場の全部）は、見出しを付けずに並べる。
    - テストのファイル（名前が `_test` で終わるもの）は、`_test` を除いた名前で対応する機能グループの行に寄せる（categories.json の正規表現はテストの名前に当たらないので、`stats.py` の `category_of`（`_test.cpp` を `.cpp` に置き換える）と同じ考え方で、拡張子によらず拡張子の直前の `_test` を除いた名前で当てる）。除いた名前でも当たらないテストのファイルは、機能カテゴリのページには載せない（アプリケーションの置き場の下なら、そのページの「機能カテゴリなし」に載る）。
  - 「PRD の一覧」（機械的に作る）: そのファイルに触れたコミットの scope にある PRD 番号（`PRD087` など）を番号の順に並べ、PRD へのリンクを付ける。番号に当たる PRD のファイルが 0 本か 2 本以上のとき（共有の番号 `999`、採番し直しで消えた番号など）は、リンクを付けずに `- PRD999 — （PRD を一意に決められない）` の形で載せ、点検の報告に挙げる（点検を止めない）。
  - 「台帳の指摘」（機械的に作る）: 監査の台帳のレコードのうち、状態が open か stale で、`file` がこのページの範囲に入るものを、優先度の順に `- F-0003 P1 defect — <題>` の形で並べ、末尾に台帳の一覧（`reports/registry/findings.md`）へのリンクを置く。無ければ「なし」と書く。
    - 作り直すのは点検ではなく、台帳のツール（`python reports/tools/registry.py build`）である。台帳の一覧（`findings.md`）と同じ派生ビューとして、ページの中の目印の行 `<!-- registry:begin -->` と `<!-- registry:end -->` の間だけを書き換える（「取り込み・点検」）。地図のページを新しく作った側（取り込み・点検・段階 3）は、目印の行を置いてから `registry.py build` を 1 回回し、区画を埋める。
    - 範囲に入るかは、「ファイル」の節と同じ決め方による。機能カテゴリのページは、`file` を categories.json に当てた先（テストのファイルは `_test` を除いた名前で当てる）、アプリケーションのページは、置き場の下のファイルである。
    - 載せるのは番号・優先度・観点・題だけで、指摘の本文や対処の方針は写さない（非ゴール）。
  - 機械的に作る 3 つの節は、冒頭に「点検が作り直す。手で直さない」（「台帳の指摘」は「台帳のツールが作り直す。手で直さない」）と書く。書く部分の 5 つの節の確かめ方は、下の「書いたあとの機械的な確かめ」に書く。
- 出典: 主張 1 つに出典 1 つ以上。正本への markdown の相対リンク（`[[ ]]` は使わない）に、節の名前を添える。Run が関わるものは Run 名を添える。
- 目録の行: 種類（題材・機構・アプリケーション・機能カテゴリ）ごとの見出しの下に `- [題名](相対パス) — 今の結論の 1 行（別名: …）`（実装の地図は「今の結論」の代わりに概要の 1 行）。別名には、略称・表記ゆれ・Run 名で使う略称を並べる（例 KFM の行に `別名: KFM, kfm, Kung-Fu Master`）。目録を題材の語で引いたときに外さないため。別名が無ければ括弧ごと省く。
- 作業の記録の行: `YYYY-MM-DD <種別> <材料のパス> blob:<sha1> → <直したページ>[, …]`。
  - 種別は `start`（先頭の 1 行。`rev:<sha>` で開始 revision）、`ingest`（取り込み）、`writeback`（PRD づくりの書き戻し）、`fix`（読んで気づいた是正）、`lint`（点検。`rev:<sha>` で点検した時点の revision）。
  - `blob` は、その時点の材料の `git hash-object`（作業ツリーの内容）。取り込み漏れの判定に使う。直したページが無ければ `→ なし`。
- 書いたあとの機械的な確かめ（書いた手順の最後に、書いた側が行う）。欠けていれば直してから終える。
  - 知見のページ: 「分かっていること」と「撤回・更新」の各項目、「分かっていないこと」の食い違いの項目に相対リンクがある（食い違いの項目は 2 つ以上）。
  - 実装の地図のページ: 「概要・責務」「成立の経緯」「選ばなかった形」「変えるときの条件」の各項目に相対リンクがある（「設計文書に記述なし」と「記述なし」の項目は出典を持たないので除く）。「関係」の各項目がリンクである（「なし」と書いた項目は除く）。機械的に作る 3 つの節は、点検か台帳のツールが作り直すので確かめない。
  - 共通: リンク先が実在する（PRD の品質確認観点の項番 4 と同じ検査。機械的に作る節と、点検が「（出典のリンク切れ）」と注記したリンクは除く）。ページが目録に載っている。
- 公開できない値の走査: 正本から写すとき、次が混ざっていないかを確かめる。絶対パス、ユーザー名、マシン名、認証情報、メールアドレス、IP アドレス、内部の URL（ローカルのサーバや私的な共有の URL。公開されている論文・リポジトリ・gist などへのリンクは除く）。AGENTS.md の実効 config の複製で走査する項目（絶対パス、ユーザー名、認証情報、メール、URL、IP）に、マシン名を足し、URL を公開資料へのリンク以外に絞ったものである。wiki のページは出典として公開資料へリンクするためである。


## 取り込み・点検

### anet-ingest-wiki


- 呼び方: `anet-ingest-wiki [<材料のパス>]`。
- 対象: パスがあればその材料。無ければ、この会話で書いた・直した材料を、会話と git の作業ツリーの変更（staged・unstaged・untracked）から決める（prepare-commit と同じ決め方）。材料（以下「材料の集合」）は、`docs/experiments/**/*.md`、`reports/` 直下の `*.md`（`reports/INDEX.md` を除く。サーベイ・論文解説・コード読解・調査の報告で、`_survey_tau_*.md` も含む。`reports/` の下のフォルダの台帳・統計・作業資材は含まない）、`docs/memo/**/*_10prd.md`、`docs/design/*.jp.md`（英訳の `.en.md` は派生物なので含まない）、`docs/adr/*.md` である。設計文書・ADR は実装の地図の正本として取り込む。PRD は、確定事項・決めること・未決・受入・実装契約・クラス一覧の節を除いた本文を材料にする（節の名前は PRD ごとに違うので、除く側で決める）。ただし、実装の地図の「選ばなかった形」と「変えるときの条件」に限り、成立の経緯に載せた PRD の全文（上で除く節を含め、節の名前によらない）を材料にし、写すものは 「置き場と書式」 の中身の決まりで決める。対象が無ければ「この会話の材料なし」と報告して終わる。
- 入力の検証: パスが存在しない、または材料の集合に入らないときは、何も直さずに、そのパスと材料の集合の定義を示して止まる。
- 動き: 材料を読み、目録とページのリンクから関係するページを決めて直す（新しいページも作る）。新しい知見を「分かっていること」へ、覆った主張を「撤回・更新」と「今の結論」へ、出典どうしの食い違いを「分かっていないこと」へ書く。前に取り込んだ材料が書き直されていれば、その材料を出典にしている主張と比べ、覆ったものを「撤回・更新」に書く（PRD のように `superseded` を追記する決まりを持たない材料でも、撤回を残すため）。実装の地図では、設計文書の章から「概要・責務」と「関係」を、PRD と ADR から「成立の経緯」を直す。成立の経緯に書くのは、PRD の題と目的から読んだ「何をしたか」の1行と、ADR の題である。PRD の題が対象のアプリケーション・機能カテゴリに関係しないときは、本文からその対象への変更を1行で書き、その節を出典に付ける。ADR は 「置き場と書式」 の参照元の条件を満たし、かつ対象の形に関わるものに限る。経緯に載せた PRD と ADR から「選ばなかった形」を（裁定の語と、あれば再開条件を添えて）、それらと設計文書の章から「変えるときの条件」を直す。あとの PRD が選ばなかった形を採っていれば、その項目に `→ PRD0xx で採用` を添える。PRD が採った決定の中身と、新しい挙動の合否は写さない（地図の 2 節に、選ばなかった形と、守った条件・確かめ方だけを 1 行で写す）。「台帳の指摘」の区画の中身には触れない（台帳のツールが作り直す）。実装の地図のページを新しく作ったときは、目印の行を置いてから `python reports/tools/registry.py build` を 1 回回す（「置き場と書式」）。目録を更新し、`log.md` に `ingest` の行を足す。最後に機械的な確かめと公開できない値の走査を行う。
- しないこと: 材料（正本）を書き換えない。git の書き込みをしない。質問して止まらない（決めきれないものは「分かっていないこと」へ）。PRD が採った決定は取り込まない（PRD の役割。地図の 2 節に写すものは上のとおり）。
- 報告: 直したページ、足した主張と撤回、「分かっていないこと」に書いたもの。

### anet-lint-wiki

- 呼び方: `anet-lint-wiki [max=<n>]`。housekeeping から呼ばれる。`max` は取り込み漏れを取り込む本数の上限で、1 以上の整数。それ以外の値は、何も直さずに値と期待値を示して止まる。
- 起点と「変わった」の判定: 起点は、`log.md` の最後の `lint` の行の revision、それが無ければ `start` の行の revision である。あるパスの集合の中で「変わったもの」は、`git diff --name-only <revision> -- <パス>`（その revision と作業ツリーの比較）に出るものと、`git status --porcelain --untracked-files=all -- <パス>` に出る未追跡のものを合わせたものとする（この repo は未コミットの材料が多く、コミットだけで比べると見落とすため）。
- 見るもの（7 つ）:
  1. 取り込み漏れ: 材料の集合の各材料の `git hash-object`（作業ツリーの内容）を、`log.md` の最後の `ingest`・`writeback` の blob と比べ、記録が無ければ「未取り込み」、違えば「更新あり」とする。`fix` の行は材料の全体を読んでいないので、取り込み済みの証拠にしない。パスが変わっただけの材料（記録にある blob と同じ blob が別のパスにある）は、取り込み漏れではなく 3 のリンク切れとして扱う。ただし `docs/memo/done/` へ移った PRD は、実装の地図の成立の経緯へ足すために未取り込みとして取り込む（実装の完了を拾うため）。段階 3 までは、開始 revision から変わった材料（上の判定）だけを対象にする。
  2. 撤回の反映漏れ: 起点から変わったページ（`docs/wiki/**/*.md` のうち上の判定で変わったもの）について、そのページが出典にしている節に `superseded`・`invalidated`・撤回・訂正の追記があるのに、ページの「撤回・更新」に無いものを見る。変わった材料の撤回は、取り込み（1 と `anet-ingest-wiki`）が材料ごとに書くので、ここでは見ない。点検の費用をページ数に比例させないため、全部のページを見るのは段階 3 の一括取り込みのときだけにする。
  3. 出典のリンク切れ。
  4. 目録に無いページ。
  5. 目録からも他のページからもリンクされないページ。
  6. 消えた名前: ページにコード書式で書いた設定キー（`.` で区切られた語）と公開クラス名が、今の `core`・`apps`（設定ファイルを含む）に無い。メトリクスの tag は `/` の前の群名だけを照合する（tag は実行時に組み立てられ、ソースに逐語では無いため）。`run_` で始まる語、パス、ファイル名は見ない。
  7. 実装の地図の機械的な部分: 全部のアプリケーション・機能カテゴリのページの「ファイル」と「PRD の一覧」を、categories.json と git（「置き場と書式」 の `git ls-files --cached --others --exclude-standard` と、コミットの scope）から作り直し、違えば書き換える。「台帳の指摘」の区画は台帳のツールが作り直すので、点検は触れない。あわせて、「概要・責務」が「設計文書に記述なし」のページを報告に挙げ、「選ばなかった形」「変えるときの条件」が「記述なし」のページは数だけを報告に挙げる。
- 直し方: その場で直す。取り込み漏れは「更新あり」を先に、`max` 本まで取り込む（`anet-ingest-wiki` と同じ動き。書き直された材料では覆った主張を「撤回・更新」に書く）。出典のリンク切れは、材料の集合の中で、まず同じファイル名を、見つからなければ先頭の番号を除いた名前（PRD なら `_intrinsic_reward_novelty_10prd.md` のような部分）を探し、1 つだけ見つかればリンクを直す。PRD の `done/`・`frozen/`・`dropped/` への移動と、`9xx` から正式番号への採番し直しがこれで直る。見つからないか 2 つ以上見つかったときは、リンクを残して主張の末尾に「（出典のリンク切れ）」と注記し、`lint` の行と報告に未解決として挙げる（人が直す）。注記したリンク切れは、前提条件の「出典のリンク切れ」に数えず、「置き場と書式」 の書いたあとの機械的な確かめからも除く（質問して止まらない約束のもとで、取り込みや点検が行き詰まらないため）。点検は回るたびに、注記の残っている数を報告に挙げる。`done/` へ移った PRD は、その PRD を scope に持つコミットが触れたファイル（そのコミットが無ければ PRD の本文の変更対象から読んだファイル）から、足す先を決めて成立の経緯へ足し、同じ先の「選ばなかった形」と「変えるときの条件」にもその PRD から足す（「置き場と書式」）。機能カテゴリのページへは、そのファイルを categories.json で写した先に足す。写すときは「ファイル」の節と同じく、テストのファイルは `_test` を除いた名前で写す。写した先がアプリケーション自身の key のとき（RunnerApp の `apps/runner/src/`、MetricsViewer の置き場のファイル）は、機能カテゴリのページへは足さない。足す先の機能カテゴリのページがまだ無いとき（段階 3 より前）は足さない。段階 3 で機能カテゴリのページを作るときに、その時点の `done/` の PRD から成立の経緯を作る。アプリケーションのページへは、そのファイルがアプリケーションの置き場の下にあり、かつ機能カテゴリに当たる（アプリケーション自身の key を含む）ときだけ足す（機能カテゴリを経由すると置き場に触れていない PRD まで入り、「機能カテゴリなし」の設定ファイルだけに触れた PRD まで入れると、アルゴリズムやメトリクスの PRD で経緯が埋まるため。「置き場と書式」 の「成立の経緯」）。消えた名前は、今の名前が出典か PRD から分かれば今の名前に直して当時の名前を括弧で残し、分からなければ「（当時の名前。今のコードに無い）」と注記する。直し方が決まらないもの（出典どうしの食い違い）は「分かっていないこと」へ書く。
- 記録: `log.md` に `lint` の行（`rev:<sha>` と直したページ）を足す。取り込んだ材料は `ingest` の行も足す。
- しないこと: `anet-ingest-wiki` と同じ。
- housekeeping の候補表の行: 名前 `wiki-lint`、スキル `anet-lint-wiki`、単位「1 回」、初期見積は 10% / 15（D21）。
  - 前提条件: 取り込み漏れ（見るもの 1）があるか、注記の無い出典のリンク切れ（見るもの 3）がある。どちらも材料の集合・ページのリンク・blob の記録だけで決まる。点検が取り込むか直すか注記するので、点検のあとには残らず、点検自身の `log.md` への追記や housekeeping 自身の `reports/` の下への書き込みでも真にならない。材料が変わって取り込まれていなければ 1 で、PRD が `done/` へ移るなどしてリンクが切れれば 3 で回る。`core`・`apps`・`docs/wiki` と監査の台帳の変化は条件に入れない（台帳の指摘は、台帳が変わるたびに台帳のツールが作り直すので、点検の仕事ではない。D36）。名前の点検（見るもの 6）は回るたびに行う。
  - 既定の優先順: stats の次（audit の前）に置く。anet-housekeeping の「既定の優先順」の行も改める。


### 機械処理の補助

[wiki_support.py](../../reports/tools/wiki_support.py)はskill内部の補助であり、知見の本文や裁定を自動で判断しない。repoの.venvでリポジトリルートから実行する。

- `scan`: 読み取り専用。未取り込み・更新あり・移動、起点以降のページ、未注記と注記済みのリンク切れ、目録漏れをJSONで返す。housekeepingは`eligible`で前提条件を確認する。
- `maps`: 全地図の「ファイル」「PRD の一覧」だけを再生成する。「台帳の指摘」は変更しない。
- 取り込みの選択、本文の照合と修正、注記、目録・ログの追記、公開できない値の走査はskillを実行する側が行う。正本を変えない。読み取り専用モードでは補助もscanだけを使う。

## 更新のきっかけ

- PRDづくりの最初の応答前に、目録を題材と別名で引く。触る部分の実装の地図も読む。
- PRDづくりの起草で、知見を先にPRD本文へ出典つきで書き、その節を出典としてページへ書き戻し、気づいた食い違いも直す。
- 未決の起票・IDへの置き換えのあと、完了報告の直前に最終本文と照合し、writeback（是正時はfixも）を記録する。暫定・999でも同じ。Plan Modeではwiki・ログを編集しない。
- その他の読み取りで食い違いに気づけば出典を正として直し、fixを記録する。Plan Modeでは是正事項を計画へ残す。
- 実験記録・サーベイの作成後は取り込み、PRDの実装完了（doneへの移動）や取りこぼしは点検で拾う。コミットhookで自動更新しない。
- Run分析の結論は、PRDの背景か実験記録のどちらへ書くかを1問で確かめる。書いたら同じ会話の終わりにanet-ingest-wikiで取り込む。


## 公開

コミット済みの `docs/` は既存のGitHub Pagesへ配信される。現状は整形されないMarkdownで、入口の図一覧にはwikiを追加しない。`reports/` とsrcはPages配信外なので、それらへの相対リンクはリポジトリで読むためのものとして扱う。Pagesの整形・入口変更は範囲外。
