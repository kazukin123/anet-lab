# wiki の規約

[anet-lab](../../README.md) › [wiki の目録](index.md) › 規約

wiki は資料ごとのサマリと、複数の資料を束ねる概念のページを持つ。調べたい問いの語や別名から概念を引ける。[目録](index.md)・[作業の記録](log.md)。

## 原則と正本

- 実験の結果と確かめた主張の正本は実験記録、報告、RFD、設計文書、ADR に置く。新しい数を計算した分析も正本に書く。出典と食い違ったら正本に照らして wiki を直す。
- 資料ごとのサマリと概念のページは、どちらも元の資料を直接引く。memory とサマリは主張の出典にしない。複数の出典で分かること、未検証の見立て、開発者の疑問は、下記の節に直接書く。
- RFDの背景はRFD、RFDに繋がらないRun分析は実験記録を正本にする。実験記録READMEはcampaignの索引と独自の分析の正本とし、campaignにある内容の要約はwikiへまとめる。
- srcはトピック別まとめからファイルへリンクするだけで、中身を要約しない。機能カテゴリ間の依存も書かない。知見のページは仕組みを説明せず、効いた条件・効かなかった条件・観測された現象を書く。仕組みは設計文書の章へリンクする。

判断の根拠は [RFD0095](../memo/done/0095_llm_wiki_10rfd.md)、[RFD0202](../memo/0202_wiki_accumulate_and_lookup_10rfd.md)、[ADR 0097](../adr/0097-wiki-keeps-per-source-summaries-and-unverified-conjectures.md)、[ADR 0098](../adr/0098-concept-pages-are-split-by-the-question-they-answer-and-kinds-live-in-folders.md) にある。

## 置き場と書式

```text
docs/wiki/
├─ README.md        規約（原則、書式、出典の書き方、更新のきっかけ、機械的な確かめ、公開できない値の走査）
├─ index.md         目録
├─ log.md           作業の記録（追記だけ）
├─ summary/         experiments/・reports/・rfd/・design/・adr/ に資料ごとのサマリを置く
└─ concepts/        概念のページ
   ├─ subjects/・methods/・measurement/・phenomena/    題材・手法・測り方・現象
   └─ apps/・framework/                               アプリケーション・フレームワーク
```

サマリの名前は材料と同じにする。実験記録は `docs/experiments/` からの階層も写し、RFD は保管場所によらず `summary/rfd/` 直下に置く。空白を含むリンク先は山括弧で囲む。各サマリには次の順で見出しを置く。

1. 「元の材料」に原本への相対リンクと `blob:` に続けて要約時の Git blob（40 桁）を書く。
2. 「要点」にその資料で分かることを 5〜10 行で書く。
3. 「内容」は原本の章立てに沿い、原本の約 8 分の 1 を目安にする。2,000 文字未満の原本は要点だけにして詳細を省く。サマリ全体が 8,000 文字を超えると点検が警告する。
4. 「主要な概念」には該当ページを 3〜7 件、短い資料では 1 件から挙げる。資料間の比較や推測は概念のページに置く。RFD のサマリはその決定も含めて全体を要約する。

知見の種類は題の主語で決める。解かせる相手なら題材、値の出し方・比べ方・読み方なら測り方、設定やコードで入れたり切り替えたりできるものなら手法、残りは現象とする。トピック別まとめのフレームワークは、ここではアプリケーション以外のコードの全部を指す。


- トピック別まとめ: コミットの Topic（アプリケーションの 1xx と機能カテゴリの 31x〜32x）ごとに、コードのどこに何があり、なぜその形になったか（成立の経緯・選ばなかった形・変えるときの条件）をまとめたページ（`concepts/apps/`・`concepts/framework/`）。個別は「324_dqn のトピック別まとめ」と呼ぶ。設計文書の「コードマップ」節（設計の範囲ごとのファイルの配置）とは別である。
- トピック別まとめの 2 段: 上の段は「アプリケーション」（RunnerApp、MetricsViewer）、下の段は「機能カテゴリ」である。「機能カテゴリ」は categories.json の定義（ファイルパスとの対応を持つもの）を指し、docs/design の README の章分けの「機能カテゴリ」とは別である（ページから設計文書の章へリンクして関係を示す）。「機能グループ」（`.hpp` / `.cpp` の組）はページにせず、機能カテゴリのページの中の行にする。ファイル名は categories.json の key。
- アプリケーションのページの範囲は、置き場（RunnerApp は `src/apps/runner/**` と `apps/runner/**`、MetricsViewer は `src/apps/metrics-viewer/**` と `apps/metrics-viewer/**`）の下のファイルを、先に当たる機能カテゴリごとに並べたものである（置き場の下には、アプリケーション自身の key のほかに、別の機能カテゴリや、どの機能カテゴリにも当たらないファイルがあるため）。アプリケーションが含む機能カテゴリは、この並びから分かる。

- 概念のページのファイル名には英小文字・数字・アンダースコアを使う。
- 概念のページの題の次に、リポジトリの README、wiki の目録、種類別見出しへの導線を置く。例は `[anet-lab](../../../../README.md) › [wiki の目録](../../index.md) › [題材](../../index.md#題材)`。
- 知見のページは仕組みを説明しない。書くのは、効いた条件・効かなかった条件・観測された現象である。仕組みは「関連」で設計文書の章を指す（設計文書の役割を変えないため）。
- 知見のページは以下の 7 節を持つ。読むときは「今の結論」「横断的知見」「見立て」の順に開き、「分かっていること」は必要な小見出しを読む。
  - 「今の結論」は 5 行以内、各行 200 文字以内。「分かっていること」と「横断的知見」から要点を選ぶ。
  - 「分かっていること」は主張 1 つに 1 項目。「### anet の知見」「### 外の事例」の順に小見出しを置き、空なら「なし」と書く。外の論文・公開実装・公開された結果だけに関する主張は「外の事例」、anet との比較を含むものは「anet の知見」に置く。同じ主張には出典を足す。
  - 「横断的知見」は `- 共通点・対立点・補完のいずれか: 読み取れること。条件の違い: …（出典: 原本へのリンク 2 つ以上）`。出典の値と条件だけを比べ、推測や新しい数は加えない。共通の語のページに 1 回書き、ほかは「関連」から引く。共通の語が複数なら、手法、測り方、現象、題材の順で選び、同種ならパス順で決める。空なら「なし」。
  - 「見立て」は未検証の推測ごとに 1 項目。見立ての文、`状態: 未検証`、支える事実、合わない事実、条件の違い、確かめ方、出どころ（AI または開発者の発言と日付）を書く。確かめたとき、または崩れたときは項目を移し、「撤回・更新」に結果を 1 行残す。空なら「なし」。
  - 「分かっていないこと」は原本の未解決の問い、出典どうしの食い違い、開発者の疑問を問いの形で書く。出典を添え、食い違いは両方の原本を引く。開発者の疑問には「開発者の発言（日付）」と添える。空なら「なし」。
  - 「撤回・更新」: `- YYYY-MM-DD: <前の主張> → <今の主張>（出典: <リンク>）`。
  - 「関連」: 設計文書の章、CONTEXT.md の語、RFD。
- トピック別まとめの節は、次の 9 つとし、この順に並べる（取り込みで直す書く部分を前、機械的な部分（「ファイル」と「RFD の一覧」は点検が、「課題」はissueの道具が作り直す）を後ろに置く）。
  - 「概要・責務」: 設計文書の該当の章の言い換えだけで書き、出典を付ける。設計文書に書かれていなければ「設計文書に記述なし」と書き、src を要約しない（点検が報告に挙げる）。
  - 「成立の経緯」: どの RFD で生まれ・変わり、どの ADR が形を決めたかを、日付の順に 1 項目ずつ書き、それぞれに RFD か ADR の出典を付ける。
    - 載せる RFD は、ページの範囲のうち機能カテゴリに当たるファイル（アプリケーションのページなら、アプリケーション自身の key に当たるファイルと、ほかの機能カテゴリに当たるファイル）に触れたコミットの scope と件名末尾にある RFD である。「機能カテゴリなし」のファイル（設定ファイル、`CMakeLists.txt`、workspace の設定など）だけに触れた RFD は載せない。そうした RFD は、機械的に作る「RFD の一覧」にだけ載る。
    - RFD の説明は題と目的から読んだ「何をしたか」の1行にする。ただし、題が対象のアプリケーション・機能カテゴリに関係しないときは、本文の、その対象に何をしたかが書かれた箇所から1行で書き、その節を出典に付ける。
    - 載せる ADR は、経緯に載せた RFD が本文で挙げる ADR と、「概要・責務」の出典にした設計文書の章が挙げる ADR のうち、対象のアプリケーション・機能カテゴリの形に関わるものに限る。
  - 「選ばなかった形」: 対象の形について選ばなかった形を、1 項目ずつ `- <選ばなかった形> — <不採用｜先送り｜範囲外>: <理由の 1 行>[。再開条件: <何が揃ったら作るか>]（出典: <RFD か ADR>、<節>）` で書く。
    - 裁定の語は、出典の裁定を「不採用」「先送り」「範囲外」のどれかに当てはめて書く。出典の語が違うときは、当てはめた語のあとに括弧で添えてよい（例: `— 不採用（却下）:`）。監査と RFD づくりのガードレールが、この 3 つの語で扱いを分けるためである（§4.7）。
      - 範囲外: 別の関心として、別の RFD や後続の RFD に回したもの（出典の語の例: 対象外、別 RFD、後続 RFD へ、RFDnnnn へ移す）。
      - 先送り: 範囲外に当たらず、何が揃ったら作るか（再開条件）が出典に書かれているもの（出典の語の例: 先送り、defer、再開条件つきの「作らない」）。
      - 不採用: どちらにも当たらないもの（出典の語の例: 却下、棄却、採用しない、採らない、作らない、導入しない、cut、削除）。
    - 再開条件は、先送りと範囲外で出典に書かれていれば写す。
    - 材料は、成立の経緯に載せた RFD の全文（節の名前によらない。「取り込み・点検」）と、経緯に載せた ADR の Considered Options である。
    - 載せるのは、対象のアプリケーション・機能カテゴリの形に関わるものだけにする（経緯の ADR の絞り方と同じ）。RFD が採った決定（何を作ったか）は写さない。
    - あとの RFD がその形を採ったら、項目を消さずに、末尾に `→ RFDnnnn で採用（出典: <RFD>、<節>）` を添える。
    - 書くことが無ければ「記述なし」と書く。
  - 「変えるときの条件」: 対象を変えるときに守る不変条件と、挙動を変えていないことの確かめ方を、1 項目ずつ `- <条件か確かめ方>（出典: <リンク>、<節>）` で書く。
    - 写すのは、挙動を変えていないことの確かめ方（等価性・再現性・性能・回帰。metrics checksum の比較、同 seed の再現性、性能の比べ方など）と、出典が「変えない」「保つ」と書いた挙動である。新しい挙動の合否（機能の受入）は写さない。RFD が採った決定（何を作ったか）も写さない。
    - 材料は、「概要・責務」の出典にした設計文書の章、経緯に載せた ADR、経緯に載せた RFD の全文（節の名前によらない。「取り込み・点検」）である。
    - 節の冒頭に、「一般の条件はリファクタリング観点（`docs/quality/refactor.md`）の『ガードレール』、テストの充足は `reports/stats/trend.md` の『テスト充足』を見る」という 1 行を、ページからの相対リンクにして置く（同じ正本の要約を各ページへ写さないため）。
    - 書くことが無ければ「記述なし」と書く。
  - 「外の事例」は報告を材料に、区分に関わる公開実装などを `- 事例（出典: 報告へのリンク、節）` の形で書く。何もなければ「記述なし」と書く。
  - 「関係」: 設計文書の章、ユーザーガイドの節、アプリケーションのページなら含む機能カテゴリのページ、機能カテゴリのページなら含まれるアプリケーションのページ。機能カテゴリ間の依存は書かない。含むもの・含まれるものが無いときは、その項目を「含む機能カテゴリ: なし」「含まれるアプリケーション: なし」と書く（MetricsViewer の置き場の下のファイルは categories.json で 120 自身に当たるので、含む機能カテゴリは「なし」になる。`core` の下だけに当たる 315 ニューラルネットワークなどは、含まれるアプリケーションが「なし」になる）。 3 つ以上の区分をまたぐ話は主な区分に書き、ほかは「関係」からそのページを引く。
  - 「ファイル」（機械的に作る）: 対応するファイルを、機能グループ（同じ名前の `.hpp` / `.cpp` を 1 行）ごとに並べ、src のファイルへリンクする。ファイルの一覧は `git ls-files --cached --others --exclude-standard`（追跡中のファイルと、無視されていない未追跡のファイル）から作る（ほかの判定と同じく作業ツリーを含めるため）。
    - アプリケーションのページは、置き場の下のファイルを、先に当たる機能カテゴリごとの見出しの下に並べる。どの機能カテゴリにも当たらないファイル（`apps/runner/config/*.txt` など）は「機能カテゴリなし」の見出しの下に並べる。categories.json でアプリケーション自身の key に当たるファイル（RunnerApp の `src/apps/runner/src/`、MetricsViewer の置き場の全部）は、見出しを付けずに並べる。
    - テストのファイル（名前が `_test` で終わるもの）は、`_test` を除いた名前で対応する機能グループの行に寄せる（categories.json の正規表現はテストの名前に当たらないので、`stats.py` の `category_of`（`_test.cpp` を `.cpp` に置き換える）と同じ考え方で、拡張子によらず拡張子の直前の `_test` を除いた名前で当てる）。除いた名前でも当たらないテストのファイルは、機能カテゴリのページには載せない（アプリケーションの置き場の下なら、そのページの「機能カテゴリなし」に載る）。
  - 「RFD の一覧」（機械的に作る）: そのファイルに触れたコミットの scope と件名末尾にある RFD 番号（`RFD0087` など）を番号の順に並べ、RFD へのリンクを付ける。コミットの準備（`anet-prepare-commit`）は、これから作るコミットの件名と対象ファイルを `maps` に渡し、そのコミットの行を同じコミットに入れる（渡さないと、行はコミットのあとにしか生まれない）。番号は、RFD の題の直下の振り直しの行（`> YYYY-MM-DD 番号を <旧> から <新> へ振り直した（RFDnnnn）。`、[memo の採番](../memo/README.md)）を先に見て、<旧> がその番号で行の日付がコミットの日付以後の RFD が 1 本ならその RFD に当て、無ければ `docs/memo/**/<番号>_*_10rfd.md` のファイルに当てる。当てた RFD は今の番号・今のリンク・今の題で載せ、同じ RFD に当たった番号は 1 行にまとめる。当たる RFD が 0 本か 2 本以上のとき（共有の番号 `999`、振り直しの行の無い採番し直しで消えた番号など）は、リンクを付けずに `- RFD0999 — （RFD を一意に決められない）` の形で載せ、点検の報告に挙げる（点検を止めない）。振り直しの行の形が崩れているか、1 つの RFD の行が日付の順に旧い番号から今の番号へつながらないときは、`maps` を止める。
  - 「課題」（機械的に作る）: areaの並びにそのページのkeyを含む、次版・解決でないissueを、anet-list-issuesと同じ列と並びで出す。アプリケーションは自身のkeyだけを使い、ほかの機能カテゴリまで広げない。
    - reports/tools/wiki_support.py mapsが、INDEXとすべてのトピック別まとめの目印 `<!-- issues:begin -->` と `<!-- issues:end -->` の間を作り直す。新設時もこの目印を置く。すべての入力と目印を検証してから書き、不正値ではどの出力も変えない。
    - 指摘の本文や対処の方針は写さず、詳細は単票へのリンクから開く（非ゴール）。
  - 機械的に作る 3 つの節は、冒頭に「点検が作り直す。手で直さない」（「課題」は道具が目印の間を作り直す）と書く。書く部分の 6 つの節の確かめ方は、下の「書いたあとの機械的な確かめ」に書く。
- 出典: 主張 1 つに出典 1 つ以上。正本への markdown の相対リンク（`[[ ]]` は使わない）に、節の名前を添える。Run が関わるものは Run 名を添える。
- 目録の行: 種類（題材・手法・測り方・現象・アプリケーション・フレームワーク）ごとの見出しの下に `- [題名](相対パス) — 今の結論の 1 行（別名: …）`（トピック別まとめは「今の結論」の代わりに概要の 1 行）。別名には、略称・表記ゆれ・Run 名で使う略称を並べる（例 KFM の行に `別名: KFM, kfm, Kung-Fu Master`）。目録を題材の語で引いたときに外さないため。別名が無ければ括弧ごと省く。 別名の括弧を除く説明は 200 文字まで。サマリは材料のパスから引けるので目録には載せない。
- 作業の記録の行: `YYYY-MM-DD <種別> <材料のパス> blob:<sha1> → <直したページ>[, …]`。
  - 種別は `start`（先頭の 1 行。`rev:<sha>` で開始 revision）、`ingest`（取り込み）、`writeback`（RFD づくりの書き戻し）、`fix`（読んで気づいた是正）、`lint`（点検。`rev:<sha>` で点検した時点の revision）。
  - 会話から書いたときは `YYYY-MM-DD query <問いか発言の1行> → <書いた所>` の形で足す。`query` に blob は付けず、取り込み漏れや点検の起点の判定にも使わない。
  - `blob` は、その時点の材料の `git hash-object`（作業ツリーの内容）。取り込み漏れの判定に使う。直したページが無ければ `→ なし`。
- 書いたあとの機械的な確かめ（書いた手順の最後に、書いた側が行う）。欠けていれば直してから終える。
  - 知見のページ: 「分かっていること」と「撤回・更新」の各項目、「分かっていないこと」の食い違いの項目に相対リンクがある（食い違いの項目は 2 つ以上）。
  - トピック別まとめ: 「概要・責務」「成立の経緯」「選ばなかった形」「変えるときの条件」「外の事例」の各項目に相対リンクがある（「設計文書に記述なし」と「記述なし」の項目は出典を持たないので除く）。「関係」の各項目がリンクである（「なし」と書いた項目は除く）。機械的に作る 3 つの節は、点検かissueの道具が作り直すので確かめない。
  - 共通: リンク先が実在する（RFD のレビュー観点の項番 4 と同じ検査。機械的に作る節と、点検が「（出典のリンク切れ）」と注記したリンクは除く）。概念のページは目録に載せ、見出しの次に戻る導線を置く。
- 公開できない値の走査: 正本から写すとき、次が混ざっていないかを確かめる。絶対パス、ユーザー名、マシン名、認証情報、メールアドレス、IP アドレス、内部の URL（ローカルのサーバや私的な共有の URL。公開されている論文・リポジトリ・gist などへのリンクは除く）。AGENTS.md の実効 config の複製で走査する項目（絶対パス、ユーザー名、認証情報、メール、URL、IP）に、マシン名を足し、URL を公開資料へのリンク以外に絞ったものである。wiki のページは出典として公開資料へリンクするためである。


## 取り込み・点検

### anet-ingest-wiki


- 呼び方: `anet-ingest-wiki [<材料のパス>]`。
- 対象: パスがあればその材料。無ければ、この会話で書いた・直した材料を、会話と git の作業ツリーの変更（staged・unstaged・untracked）から決める（anet-prepare-commit と同じ決め方）。材料（以下「材料の集合」）は、`docs/experiments/**/*.md`、`reports/` 直下の `*.md`（`reports/INDEX.md` を除く。サーベイ・論文解説・コード読解・調査の報告で、`_survey_tau_*.md` も含む。`reports/` の下のフォルダの課題・統計・作業資材は含まない）、`docs/memo/**/*_10rfd.md`、`docs/design/*.jp.md`（英訳の `.en.md` は派生物なので含まない）、`docs/adr/*.md` である。設計文書・ADR はトピック別まとめの正本として取り込む。RFD の知見のページへの取り込みでは、確定事項・決めること・未決・受入・実装契約・クラス一覧の節を除いた本文を材料にする（節の名前は RFD ごとに違うので、除く側で決める）。ただし、トピック別まとめの「選ばなかった形」と「変えるときの条件」に限り、成立の経緯に載せた RFD の全文（上で除く節を含め、節の名前によらない）を材料にし、写すものは 「置き場と書式」 の中身の決まりで決める。対象が無ければ「この会話の材料なし」と報告して終わる。
- 入力の検証: パスが存在しない、または材料の集合に入らないときは、何も直さずに、そのパスと材料の集合の定義を示して止まる。
- 動き: 材料を全文読み、そのサマリを書き、主要な概念を挙げ、当たるページをすべて読む。材料の主張を既存の項目と比較し、すでにある主張は出典を足す。それ以外は漏れなく載せ、必要ならページを作る。コードの形と理由は今の区分のトピック別まとめに置く。効き方や測り方の主張は知見のページに置く。主張にある語がその種類で一つに決まるものを、手法・測り方・現象・題材の順に探し、そのページに全文を書く。どの種類でも決まらないときは当たるパス順で決める。ほかのページには `- 数値を含まない要旨 → 詳しくは [主のページ](相対パス)（出典: 正本へのリンク）` と書く。新しい知見を「分かっていること」へ、覆った主張を「撤回・更新」と「今の結論」へ、出典どうしの食い違いを「分かっていないこと」へ書く。前に取り込んだ材料が書き直されていれば、その材料を出典にしている主張と比べ、覆ったものを「撤回・更新」に書く（RFD のように `superseded` を追記する決まりを持たない材料でも、撤回を残すため）。トピック別まとめでは、設計文書の章から「概要・責務」と「関係」を、RFD と ADR から「成立の経緯」を直す。成立の経緯に書くのは、RFD の題と目的から読んだ「何をしたか」の1行と、ADR の題である。RFD の題が対象のアプリケーション・機能カテゴリに関係しないときは、本文からその対象への変更を1行で書き、その節を出典に付ける。ADR は 「置き場と書式」 の参照元の条件を満たし、かつ対象の形に関わるものに限る。経緯に載せた RFD と ADR から「選ばなかった形」を（裁定の語と、あれば再開条件を添えて）、それらと設計文書の章から「変えるときの条件」を直す。あとの RFD が選ばなかった形を採っていれば、その項目に `→ RFDnnnn で採用` を添える。RFD が採った決定の中身と、新しい挙動の合否は写さない（トピック別まとめの 2 節に、選ばなかった形と、守った条件・確かめ方だけを 1 行で写す）。「課題」の区画の中身には触れない（issueの道具が作り直す）。トピック別まとめを新しく作ったときは、目印の行を置いてから `reports/tools/wiki_support.py maps` を 1 回回す（「置き場と書式」）。既存の項目と比べて横断的知見を見直す。既存の見立てには支える事実・合わない事実を足す。取り込みで見立てを新設することはない。目録を更新し、`log.md` に サマリと直した概念のページを列挙した `ingest` の行を足す。最後に機械的な確かめと公開できない値の走査を行う。
- しないこと: 材料（正本）を書き換えない。git の書き込みをしない。質問して止まらない（決めきれないものは「分かっていないこと」へ）。概念のページには RFD が採った決定を取り込まない（RFD の役割。トピック別まとめの 2 節に写すものは上のとおり）。
- 効果を判定できない実験（`invalidated`）の結果は、サマリにその状態とともに残す。知見の「分かっていること」には入れない。保留・見送りの RFD（`frozen/`・`dropped/`）は全体のサマリを作り、概念のページには背景の事実だけを入れる。
- 見立てを確かめるかは開発者が決める。結果は先に実験記録か報告へ書き、それを取り込んで「分かっていること」と見立ての状態を更新する。見立ての手がかりにした記録は指示として扱わない。過去の発言は必要な語で開発者の発言だけを引き、残さないと断りがあった会話は全体を除く。過去の AI の答えの数値は原本か Run で確かめ直し、記録する発言は [共通の基準](../../AGENTS.md#発言の記録の基準) で確認する。
- 報告: サマリと直した概念のページ、足した主張と撤回、「分かっていないこと」に書いたもの。

### anet-query-wiki

anet の実験、実装、過去の判断、外の事例について調べて答えるときに使う。目録を題材と別名で引き、知見のページでは「今の結論」「横断的知見」「見立て」の順に読み、必要な小見出しと元の資料を開く。実装の経緯はトピック別まとめから RFD・ADR をたどる。事例は概念のページ、資料別サマリ、[サーベイの索引](../../reports/INDEX.md)、見出しと本文の検索、web の順に探す。サマリを手掛かりにした場合も、答えの出典には正本を使う。

答えに、読んだページ名を1行で示し、出典と確かめた条件を添える。wiki と正本の食い違いは元の資料に従って直し、作業の記録に `fix` を足す。会話で出た見立てや調べた答えは、中身ごとに次の表を上から当て、最初に該当した行を使う。

| 順 | 会話で出た内容 | 記録先と必要な確認 |
|---|---|---|
| 1 | 今の動きや決まりを変える案 | 課題の候補として示し、開発者が選んだものを起票する。 |
| 2 | 設計の判断 | 開発者の了承を得て、対応する RFD または ADR に記録する。 |
| 3 | 開発者の見立て・仮説・疑問 | 見立て・仮説は知見の「見立て」、疑問は「分かっていないこと」に、要旨・日付・出どころを書く。[発言の記録の基準](../../AGENTS.md#発言の記録の基準)を通す。 |
| 4 | Run の新しい集計・分析 | Run 分析で行う既存の1問を兼ねて書く先を確かめる。実験記録は当該 campaign、campaign をまたぐ分析はその README の「独自の分析」に記録し、取り込む。 |
| 5 | 外の調べもの | 該当する報告に追記する。無ければ短い報告を作り、取り込む。 |
| 6 | 今のコードの働きの説明 | 該当する日本語の設計文書を更新し、取り込む。 |
| 7 | 今の正本から導けて、調べ直しに手間がかかる答え | 該当する知見の項目または横断的知見へ出典付きで書く。推測を含む部分は「見立て」へ置く。 |
| 8 | ここまでの条件に当たらないもの | 記録しない。 |

知見はこの表の行き先へ書き、memory は進め方の好みと指示に使う。発言を記録できるかは「残さない」「確認して残す」「確認なしで残す」の順に判定する。確認が必要な発言は要旨と行き先をまとめて一度だけ聞き、回答を待つ。表の1・2・4と発言の基準が求める確認のほかに、保存の可否を改めて聞く手順は設けない。

その応答の中で書いた所を答えの末尾に1行で示し、作業の記録に `query` を足す。正本を更新した場合は、取り込みの `ingest` も記録する。何も書かなかった場合は `query` を足さない。Plan Mode では調べた答えまで返し、書く内容と行き先を計画に残す。

### anet-lint-wiki

- 呼び方: `anet-lint-wiki [max=<n>]`。housekeeping から呼ばれる。`max` は取り込み漏れを取り込む本数の上限で、省略すれば上限を設けない。指定するときは 1 以上の整数で、それ以外の値は、何も直さずに値と期待値を示して止まる。
- 起点と「変わった」の判定: 起点は、`log.md` の最後の `lint` の行の revision、それが無ければ `start` の行の revision である。あるパスの集合の中で「変わったもの」は、`git diff --name-only <revision> -- <パス>`（その revision と作業ツリーの比較）に出るものと、`git status --porcelain --untracked-files=all -- <パス>` に出る未追跡のものを合わせたものとする（この repo は未コミットの材料が多く、コミットだけで比べると見落とすため）。
- 見るもの（7 つ）:
  1. 取り込み漏れ: 材料の集合の各材料の `git hash-object`（作業ツリーの内容）を、`log.md` の最後の `ingest`・`writeback` の blob と比べ、記録が無ければ「未取り込み」、違えば「更新あり」とする。`fix` の行は材料の全体を読んでいないので、取り込み済みの証拠にしない。サマリがない、元の材料の節の blob が異なる・欠けている・不正な場合も取り込み漏れとする。作業の記録に最新の blob があっても拾う。新しいパスに正しいサマリがあり、パスが変わっただけの材料（記録にある blob と同じ blob が別のパスにある）は、取り込み漏れではなく 3 のリンク切れとして扱う。ただし、実装済みになったRFD（そのRFDを`rfd`で指す課題の判定と状態から導く。解決の課題は済みとして数え、次版・対応しない・不要になったの課題が残るRFDは実装済みにしない）は、本文のblobが同じでも、`implemented:`を添えた取り込みの記録が無ければ未取り込みとして拾う。過去のdocs/memo/done/のRFDは従来どおり拾う。開始 revision による限定は設けず、材料の集合全体を比較する。
  2. 撤回の反映漏れ: 起点から変わったページ（`docs/wiki/**/*.md` のうち上の判定で変わったもの）について、そのページが出典にしている節に `superseded`・`invalidated`・撤回・訂正の追記があるのに、ページの「撤回・更新」に無いものを見る。変わった材料の撤回は、取り込み（1 と `anet-ingest-wiki`）が材料ごとに書くので、ここでは見ない。点検の費用をページ数に比例させないため、全部のページを見るのは段階 3 の一括取り込みのときだけにする。
  3. 出典のリンク切れ。
  4. 目録に無い概念のページ。
  5. 目録からも他のページからもリンクされない概念のページ。
  6. 消えた名前: ページにコード書式で書いた設定キー（`.` で区切られた語）と公開クラス名が、今の `core`・`apps`（設定ファイルを含む）に無い。メトリクスの tag は `/` の前の群名だけを照合する（tag は実行時に組み立てられ、ソースに逐語では無いため）。`run_` で始まる語、パス、ファイル名は見ない。
  7. トピック別まとめの機械的な部分: 全部のアプリケーション・機能カテゴリのページの「ファイル」と「RFD の一覧」を、categories.json と git（「置き場と書式」 の `git ls-files --cached --others --exclude-standard` と、コミットの scope と件名末尾）から作り直し、違えば書き換える。INDEXと「課題」の区画もmapsで作り直す。あわせて、「概要・責務」が「設計文書に記述なし」のページを報告に挙げ、「選ばなかった形」「変えるときの条件」が「記述なし」のページは数だけを報告に挙げる。
- 見立てを育てる対象は、起点から「分かっていること」か「横断的知見」が変わった知見のページ。未検証の見立ての総数が 5 件に満たなければ、その 2 節を比べて確かめ方のある推測を作る。一つの題材・手法・測り方で説明できる見立てはそのページに書く。複数にまたがる見立ては現象のページに書き、該当するページがなければ作る。点検後の未検証は 1 ページ 5 件まで、点検 1 回で加えるのは合計 10 件まで。どちらも埋める目標ではない。出どころを問わず数える。会話から書く見立てには上限を置かない。見立ては課題候補にせず、新規・状態変化と、長さの割に項目が少ない材料を報告する。
- `warnings` は報告に挙げる。外の文書から wiki へ入るリンクの切れは、同じファイル名の移動先が 1 件ならリンク先だけを直す。候補が 0 件または複数なら出典への注記は書かず、元の文書と候補を報告する。この警告は点検の開始条件に含めない。
- 直し方: その場で直す。取り込み漏れは「更新あり」を先に取り込む。`max` を指定したときは `max` 本までにする（`anet-ingest-wiki` と同じ動き。書き直された材料では覆った主張を「撤回・更新」に書く）。出典のリンク切れは、材料の集合の中で、まず同じファイル名を、見つからなければ先頭の番号を除いた名前（RFD なら `_intrinsic_reward_novelty_10rfd.md` のような部分）を探し、1 つだけ見つかればリンクを直す。過去の保管場所の移動や、RFD0114での改名によるリンクもこの方法で直る。見つからないか 2 つ以上見つかったときは、リンクを残して主張の末尾に「（出典のリンク切れ）」と注記し、`lint` の行と報告に未解決として挙げる（人が直す）。注記したリンク切れは、前提条件の「出典のリンク切れ」に数えず、「置き場と書式」 の書いたあとの機械的な確かめからも除く（質問して止まらない約束のもとで、取り込みや点検が行き詰まらないため）。点検は回るたびに、注記の残っている数を報告に挙げる。実装済みと導かれたRFD（過去のdoneも含む）は、そのRFDをscopeか件名末尾に持つコミット（RFDの題の直下に振り直しの行があれば、その旧い番号を持つ、行の日付以前のコミットも含む）が触れたファイル（そのコミットが無ければ RFD の本文の変更対象から読んだファイル）から、足す先を決めて成立の経緯へ足し、同じ先の「選ばなかった形」と「変えるときの条件」にもその RFD から足す（「置き場と書式」）。機能カテゴリのページへは、そのファイルを categories.json で写した先に足す。写すときは「ファイル」の節と同じく、テストのファイルは `_test` を除いた名前で写す。写した先がアプリケーション自身の key のとき（RunnerApp の `src/apps/runner/src/`、MetricsViewer の置き場のファイル）は、機能カテゴリのページへは足さない。足す先の機能カテゴリのページがまだ無いときは未作成として報告する。ページを新設するときも、「成立の経緯」の決め方でRFDを選び、`done/`へ移ったかは条件にしない。アプリケーションのページへは、そのファイルがアプリケーションの置き場の下にあり、かつ機能カテゴリに当たる（アプリケーション自身の key を含む）ときだけ足す（機能カテゴリを経由すると置き場に触れていない RFD まで入り、「機能カテゴリなし」の設定ファイルだけに触れた RFD まで入れると、アルゴリズムやメトリクスの RFD で経緯が埋まるため。「置き場と書式」 の「成立の経緯」）。消えた名前は、今の名前が出典か RFD から分かれば今の名前に直して当時の名前を括弧で残し、分からなければ「（当時の名前。今のコードに無い）」と注記する。直し方が決まらないもの（出典どうしの食い違い）は「分かっていないこと」へ書く。
- 記録: `log.md` に `lint` の行（`rev:<sha>` と直したページ）を足す。取り込んだ材料は `ingest` の行も足す。
- しないこと: `anet-ingest-wiki` と同じ。
- housekeeping の候補表の行: 名前 `wiki-lint`、スキル `anet-lint-wiki`、単位「1 回」、初期見積は 10% / 15（D21）。
  - 前提条件: 取り込み漏れ（見るもの 1）があるか、注記の無い出典のリンク切れ（見るもの 3）がある。どちらも材料の集合・ページのリンク・blob の記録だけで決まる。点検が取り込むか直すか注記するので、点検のあとには残らず、点検自身の `log.md` への追記や housekeeping 自身の `reports/` の下への書き込みでも真にならない。材料が変わって取り込まれていなければ 1 で、出典が改名されるなどしてリンクが切れれば 3 で回る。`core`・`apps`・`docs/wiki` と課題記録の変化は条件に入れない（課題は、単票が変わるたびにissueの道具（`wiki_support.py maps`）が作り直すので、点検の仕事ではない。D36）。名前の点検（見るもの 6）は回るたびに行う。
  - 既定の優先順: stats の次（audit の前）に置く。anet-housekeeping の「既定の優先順」の行も改める。


### 機械処理の補助

[wiki_support.py](../../reports/tools/wiki_support.py)はskill内部の補助であり、知見の本文や裁定を自動で判断しない。repoの.venvでリポジトリルートから実行する。

- `scan`: 読み取り専用。未取り込み・更新あり・移動、起点以降のページ、未注記と注記済みのリンク切れ、目録漏れをJSONで返す。housekeepingは`eligible`で前提条件を確認する。 `warnings` は長さ、見出し、出典、見立ての状態、原本がないサマリ、外部文書から wiki へ入るリンクを示す。
- `maps`: すべてのトピック別まとめの「ファイル」「RFD の一覧」と、INDEX・課題の目印の間を再生成する。本版を既定とし、依存とWSJF継承は全件で計算する。`--pending-subject <件名> --pending-files <パス> ...` を組で渡すと、その件名の RFD 番号を、対象ファイルが当たるページの「RFD の一覧」にも数える。
- 取り込みの選択、本文の照合と修正、注記、目録・ログの追記、公開できない値の走査はskillを実行する側が行う。正本を変えない。読み取り専用モードでは補助もscanだけを使う。

## 更新のきっかけ

- RFDづくりの最初の応答前に、目録を題材と別名で引く。触る部分のトピック別まとめも読む。
- RFDづくりの起草で、知見を先にRFD本文へ出典つきで書き、その節を出典としてページへ書き戻し、気づいた食い違いも直す。 RFD 全体のサマリも直す。
- 未決の起票・IDへの置き換えのあと、完了報告の直前に最終本文とサマリの blob を照合し、writeback（是正時はfixも）を記録する。暫定でも同じ。Plan Modeではwiki・ログを編集しない。
- その他の読み取りで食い違いに気づけば出典を正として直し、fixを記録する。Plan Modeでは是正事項を計画へ残す。
- 実験記録・サーベイの作成後は取り込み、RFDの実装完了（そのRFDの課題から導いた実装済み）や取りこぼしは点検で拾う。コミットhookで自動更新しない。
- Run分析の結論は、RFDの背景か実験記録のどちらへ書くかを1問で確かめる。書いたら同じ会話の終わりにanet-ingest-wikiで取り込む。


## 公開

コミット済みの `docs/` は既存のGitHub Pagesへ配信される。現状は整形されないMarkdownで、入口の図一覧にはwikiを追加しない。`reports/` とsrcはPages配信外なので、それらへの相対リンクはリポジトリで読むためのものとして扱う。Pagesの整形・入口変更は範囲外。

issueの読取にはPyYAML 6.0.3が必要で、reports/tools/requirements.txtをrepoの.venvに導入する。scanのpendingにimplementedがあるRFDを取り込んだときは、ingest/writeback行のblob直後に `implemented:YYYY-MM-DD`（scanが示した日）を添える。この記録で、本文が同じまま実装が済んだRFDの取り込みを一度だけ行う。取り込み済みかはパスとblobで突き合わせ、日付は使わない（日付は課題の判定や解決のたびに動くため）。
