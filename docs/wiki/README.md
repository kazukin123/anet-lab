# wiki の規約

wiki は、外にある正本を題材・機構、アプリケーション・機能カテゴリごとに束ねた、中身のあるまとめである。索引は目録だけに置く。[目録](index.md)・[作業の記録](log.md)。

## 原則と正本

- wiki だけにある知見を作らない。正本は実験記録、サーベイ、PRD、設計文書、ADRに残す。出典と食い違ったら出典を正とし、まとめを直す。
- 許す重複は「正本 → まとめ」の一方向の1段だけ。資料ごとの要約ページは作らない。memoryは出典にしない。PRDは元の出典を確認し、判断が依存する事実を本文に出典つきで書く。
- 新しい知見は先に正本へ書く。PRDの背景はPRD、PRDに繋がらないRun分析は実験記録を正本にする。実験記録READMEを要約と独自分析に仕分けるまでは、現在のREADMEの扱いを維持する。
- srcは実装の地図からファイルへリンクするだけで、中身を要約しない。機能カテゴリ間の依存も書かない。機構ページは仕組みを説明せず、効いた条件・効かなかった条件・観測された現象を書く。仕組みは設計文書の章へリンクする。

## 置き場とページの書式

ファイル名は英小文字・数字・アンダースコア。`subjects/` はEnv・ゲーム、`mechanisms/` は機構、`apps/` と `categories/` は実装の地図。機能カテゴリは `reports/tools/categories.json` の定義で、設計文書の章分けとは別。機能グループ（同名の .hpp / .cpp）はページではなく行にする。

知見のページは次の5節を持つ。

| 節 | 書くこと |
| --- | --- |
| 今の結論 | 1〜5行。「分かっていること」の言い換えだけで、新しい判断を足さない |
| 分かっていること | 主張を1項目ずつ書き、各項目に出典を付ける。観測・分析・仮説の確度を保持する |
| 分かっていないこと | 問いだけを書く。計画・候補は書かない。出典の食い違いには両方の出典を付ける |
| 撤回・更新 | `- YYYY-MM-DD: 前の主張 → 今の主張（出典: 相対リンク、節名）` |
| 関連 | 設計文書の章、CONTEXT.mdの語、PRD |

実装の地図は代わりに次の5節を持つ。

| 節 | 書くこと |
| --- | --- |
| 概要・責務 | 設計文書の章の言い換えと出典。無ければ「設計文書に記述なし」と書き、srcで補わない |
| 成立の経緯 | PRDの題と目的から読んだ何をしたかの1行（題が対象に関係しない場合は本文から対象への変更）、ADRの題を日付順で書く。各項目にPRDかADRの出典を付け、PRDの決定の中身は写さない |
| 関係 | 設計文書の章、ユーザーガイドの節、含む機能カテゴリ／含まれるアプリケーションへのリンク。該当しなければ「含む機能カテゴリ: なし」「含まれるアプリケーション: なし」 |
| ファイル | 機械的に作る。追跡・未追跡の全ファイルを機能グループごとに並べる |
| PRD の一覧 | 機械的に作る。対象ファイルに触れたコミットのscopeのPRD番号を番号順にリンクする |

経緯のPRDは、ページの範囲のうち機能カテゴリに当たるファイル（アプリケーション自身のkeyを含む）に触れたコミットのscopeから選ぶ。「機能カテゴリなし」の設定ファイルやworkspace設定などだけに触れたPRDは「PRD の一覧」にだけ載せる。PRDの題が対象のアプリケーション・機能カテゴリに関係しないときは、本文からその対象に何をしたかを1行で書き、その節を出典に付ける。経緯のADRは、経緯に載せたPRDの本文と「概要・責務」の出典にした設計文書の章が挙げるもののうち、対象のアプリケーション・機能カテゴリの形に関わるものに限る。

機械的な2節の先頭には「点検が作り直す。手で直さない」と書く。初回はカテゴリ定義とgitの履歴から生成する。取り込み・点検のskill（`anet-ingest-wiki`・`anet-lint-wiki`）が入ったら、点検が再生成する。

一覧は `git ls-files --cached --others --exclude-standard` から作る。アプリケーションの範囲はRunnerAppが `apps/runner/`、MetricsViewerが `apps/metrics-viewer/` と `viewers/metrics-viewer/`。カテゴリは定義順で先に当たるものを採る。アプリケーション自身のカテゴリに当たる行は見出し無し、他カテゴリはカテゴリ見出しの下、当たらないものは「機能カテゴリなし」の下へ置く。機能カテゴリのページはそのカテゴリに当たる全ファイルを載せる。

テストは拡張子直前の末尾 `_test` を除いた名前で分類し、その機能グループの行に寄せる。除いた名前でも当たらないものはカテゴリページへ載せず、アプリケーション内なら「機能カテゴリなし」へ載せる。同名の .hpp / .cpp は1行、異なるディレクトリで同名のファイルは混ぜない。

## 出典・目録・作業の記録

主張1つに出典1つ以上。正本へのMarkdown相対リンクと節名を添え、Runが関わるときはRun名も添える。`[[ ]]` は使わない。目録は題材・機構・アプリケーション・機能カテゴリの見出しの下に、`- [題名](相対パス) — 今の結論（地図なら概要）の1行（別名: …）` の行を置く。別名は略称・表記ゆれ・Run名で使う略称に限り、実際に対象を指して使われているものを載せる。ほかの概念と紛れる語は別名にしない。部品の名前は別名にせず、概要の1行に含める。別名が無ければ括弧ごと省く。

ログは追記だけとし、開始時の先頭行を `YYYY-MM-DD start rev:開始revision` にする。通常行は `YYYY-MM-DD 種別 材料のパス blob:sha1 → 直したページ[, …]`。blobは作業ツリーの材料の `git hash-object`。直したページが無ければ `→ なし`。

| 種別 | 意味 |
| --- | --- |
| ingest | 正本を1本読み、関係するページを更新した |
| writeback | PRDづくりの完了直前に、最終本文と照合した時点のblobを記録した |
| fix | 読んで気づいた食い違いを出典に合わせて是正した |
| lint | 点検。`YYYY-MM-DD lint rev:点検時revision` を記録する |

fix は材料全体を読んだ証拠ではないため、取り込み済み判定には使わない。

## 更新のきっかけ

- PRDづくりの最初の応答前に、目録を題材と別名で引く。触る部分の実装の地図も読む。
- PRDづくりの起草で、知見を先にPRD本文へ出典つきで書き、その節を出典としてページへ書き戻し、気づいた食い違いも直す。
- 未決の起票・IDへの置き換えのあと、完了報告の直前に最終本文と照合し、writeback（是正時はfixも）を記録する。暫定・999でも同じ。Plan Modeではwiki・ログを編集しない。
- その他の読み取りで食い違いに気づけば出典を正として直し、fixを記録する。Plan Modeでは是正事項を計画へ残す。
- 取り込み・点検のskill（`anet-ingest-wiki`・`anet-lint-wiki`）とRun分析の書き戻し手順が入るまでは、上記のPRDづくりと随時の是正で更新する。コミットhookで自動更新しない。

## 書いたあとの機械的な確かめ

書いた側が次を確認し、不足を直してから終える。知見の本文はレビューの対象にしない。

1. 知見ページの「分かっていること」「撤回・更新」の各項目に相対リンクがある。「分かっていないこと」で食い違いを示す項目には2つ以上ある。
2. 地図の「概要・責務」「成立の経緯」の各項目に相対リンクがある。「設計文書に記述なし」は除く。「関係」の各項目はリンクで、「なし」は除く。機械的な2節は点検が作り直すため、この項目では確かめない。
3. 相対リンクの `#` より前のパスをページから辿った先が実在する（PRD品質確認観点4と同じ）。コード中の記法、機械的な2節、点検で「（出典のリンク切れ）」と注記したものは除く。全ページが目録に載っている。
4. 正本から写す際、絶対パス、ユーザー名、マシン名、認証情報、メールアドレス、IPアドレス、内部URLを走査する。公開された論文・リポジトリ・gistへのURLは除外する。計画の「正本なし」の列挙も同じ走査を行う。

## 公開

コミット済みの `docs/` は既存のGitHub Pagesへ配信される。現状は整形されないMarkdownで、入口の図一覧にはwikiを追加しない。`reports/` とsrcはPages配信外なので、それらへの相対リンクはリポジトリで読むためのものとして扱う。Pagesの整形・入口変更は範囲外。
