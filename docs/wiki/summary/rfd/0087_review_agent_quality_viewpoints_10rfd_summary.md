# レビューエージェントとレビュー観点の導入（プロセス契約の共有コア）

## 元の材料

[レビューエージェントとレビュー観点の導入（プロセス契約の共有コア）](../../../memo/done/0087_review_agent_quality_viewpoints_10rfd.md) blob:776dc9c9f640ba9a1ffd730c45eb161567f97e0a

## 要点

- レビューの対象、観点、指摘の書き方がその場に依存していた問題を扱う。
- RFD 作成と実装の両方で、自己点検・独立レビュー・差し戻し対応・未決の提示を同じ流れにする。
- 工程の共通契約と、anet 固有の規則を載せるレジストリ・レビュー観点の責務を分ける。
- 作る側とレビューする側に、入力元と対象範囲と判定を共有する。
- 往復回数だけで効率を測らず、人間が判断に使った時間を成功指標にする。

## 内容

### レビューが必要になった理由

起票側から見えない規則が、レビューで初めて指摘されることがあった。対象別の観点と入力の所在を示し、起草時の自己点検と独立レビューが同じ契約を参照できるようにする。

### プロセス契約とプロジェクト固有の規約

汎用のプロセス契約はプロジェクトに依存しない文面で保ち、anet のファイル、読み替え、具体的な検査はレジストリと観点に置く。小さな変更のように RFD のない実装も、実装に適用できる観点で見る。

### 規約を共有する場所

RFD を書く側と実装する側では、成果物も根拠に使える資料も異なる。そこで、RFD の確認観点と実装の確認観点を別の文書に置き、それぞれが何を検査し、どの規約を根拠にするかを示す。汎用のレビューエージェントが anet のディレクトリや用語を直接知る代わりに、プロジェクトのレジストリが入力の種類や文書の場所を読み替える。共有コアは後から改訂できるが、語や契約を他プロジェクトにも通じる形に保つ。

### 工程と判定

RFD と実装の入口は自己点検、レビュー、差し戻し対応、未決を示す手順を共有する。レビュー担当は満たさない条件と出典を返し、修正や開発者の判断と区別する。

### 実装なしでレビューを依頼する入口

RFD を新設したときだけをレビューの入口にすると、日常の小さい変更が確認を通らない。一部をやり直した場合も、すでに満たした項目と、今回あらためて確認する箇所を区別する必要がある。そのため、起草や実装を最初から起動し直さず、対象と資料を渡してレビューだけを頼める手順を定める。判定には不足点、修正要求、再確認する条件を記し、人の判断が要る話を分ける。

### 質問の順と前提

RFD0097 の検討では、通知の前後どちらで読むかを先に選択肢にしたため、「遷移の結果をイベント自身が運ぶ」形が十分に比較されなかった。依存する選択を先に決めると、その答えを元の選択の根拠として使う循環も生じる。各案について実際に困っている事象、実装したときの動き、固定費を含む性能への影響を具体化し、前提を開いた上で比較する。別モデルの検討でも、同じ前提を与えれば同じ欠落が残り得る。

### 事例から確認観点を更新する

RFD0094 の作業では、共通層が特定の Agent の項目名を持つ、UI スレッドが学習更新のロックを待つ、対象外ファイルの BOM が変わるなどが、当時の観点から漏れた。案件固有の修正と、別案件でも役に立つ確認事項を分け、同じ問題を防ぐ箇所に規約を置く。実装と RFD の語の混在、既存呼び出しの境界条件、ガイド本文の手順と仕組みの区別も、この再発防止の対象に含む。

### 常時読む規約の量

全作業に共通する原則と、作業に応じて読む細則を分ける。コード・設定・skill などを直す前に該当する観点を参照し、書いた後は同じファイルの全項目で自己点検する。入口と観点に規則を二重に書くと、片方だけを更新したときに食い違うので、本文の正本を決めて相手側から参照する。

### 評価対象

説明に必要な往復まで短くしようとすると、利用者が判断の中身を理解する機会が減る。工程の改善は人が使った時間を基準に測り、応答回数だけを目標にしない。
