# 設計指示文書を RFD と呼び番号を4桁に統一する

## 元の材料

[RFD0195　設計指示文書を RFD と呼び番号を4桁に統一する](../../../memo/0195_document_term_rfd_and_4digit_numbers_10rfd.md) blob:7b130423176f7f456fdcd3ba78039cdb5b9a44f8

## 要点

- このリポジトリの設計指示は作り方と検証も含み、一般的な製品要求書の PRD とは役割が異なっていた。
- 現用の呼び名を RFD に改め、番号はゼロ埋めの4桁で表す。
- ファイル、スキル、課題の参照、テストや生成ツールなど機械が読む場所も対象とする。
- 過去のコミット件名など改変しない記録は旧表記から追跡できるようにする。
- リンクや参照先を一括照合し、移行後の採番・検索・一覧生成を確かめる。

## 内容

### 背景

AI の答え（2026-11-21）: 本来の PRD・`to-prd`・SDD の spec を比べ、anet の文書は 1 回の変更の仕様と判断の記録であり、spec の中でも OpenSpec の change（今の仕様と変更提案を分ける）や KEP・PEP に近いとした。呼び名を変える手間が大きいので、用語集に「PRD」の項目を足す案を示した。
開発者の発言（2026-11-22）: 呼び名の問いの前に「当然、影響が大きいので、ここは時間をかけたい。まず今のPRDの実態を整理したい。」と述べ、今の文書は「差分ベースの仕様書（要件定義、外部仕様から内部仕様まで、成果物に関する全行程）」と「AIが自律的に作業をする指示書」の 2 つの側面を持つと思うが、見方として足りているかを問うた。
開発者の発言（2026-11-22）: 「個人的には「指示書」と位置付けるのが、内容に依存しなくなり、かつ実運用に沿ってるので無難だと思い始めています。」「具体的な命名案として「ORDER」でどうかなと思っています。オーダー0066、みたいな。」「ただし仕様書や意思決定記録としての側面を表現しなくなるのはどうなんだろうとも思ってて」。候補をできるだけ多く挙げて比べるよう求めた。
AI の案（2026-11-22）: 23 案を挙げ、6 案に絞って比べた。指示を軸にするなら、ORDER を Change Order の略と定義して仕様と判断の側面を補う案も示した。

### 起草時点の現状

「PRD」は、`git grep -o -E 'PRD'`（追跡しているファイル全体、大文字小文字を区別）で 14,238 か所、`git grep -l -E 'PRD'` で 963 本である。
本 PRD と `third_party/` を除いて数えた。「語として」は大文字小文字を区別しない単語の一致、「語の一部として」は大文字小文字を区別しない部分一致である。
「spec」の意味は道具ごとに違う。Spec Kit と Kiro では 1 つの機能の要求（何を・なぜ）で、作り方は別の文書に分ける。OpenSpec では今の仕様そのものを指し、1 回の変更は change と呼ぶ。
持たないものは、状態・優先度・作業の順（課題）、今の仕様（設計文書・src）、内部の細部（実装計画）、使い方（ユーザーガイド）、利用者の話と PM の優先度（本来の PRD の中心）である。

### 確定事項

呼び名を RFDにする。文の中の名詞も番号の記号も大文字の `RFD`、機械が読む名前（ファイル名・skill 名・欄・タグ・フォルダ）は小文字の `rfd` にする。今の「PRD」と同じ使い分けである。
課題の前付けを、解決・次版も含めた全課題で改める。`prd` 欄を `rfd` 欄にし、値の Obsidian のリンクを新しいファイル名にする。`phase` の値 `PRD` を `RFD` にする。`docs` の値の文書のパスを新しいファイル名にする。
番号つきの呼び方は、どこでも 0 埋めの 4 桁で、記号と数字のあいだに空白を入れない（`RFD0195`、`[rfd0110_main_pane]`、`ANET_RFD0093_OUTPUT`、`MakeRfd0072ConfigData`）。本文の `PRD 072`（空白あり）も `RFD0072` にする。
issue-20261116-fe09dc を範囲へ取り込み、その `prd` 欄に本 PRD を書く。
