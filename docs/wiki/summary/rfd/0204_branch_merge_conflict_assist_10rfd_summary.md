# ブランチを main へ取り込むときの衝突を解く支援の案

## 元の材料

[RFD0204　ブランチを main へ取り込むときの衝突を、両側の内容と文脈を読んで解く支援の RFD](../../../memo/0204_branch_merge_conflict_assist_10rfd.md) blob:ad3d3daf23774efacc0b3c8e20209d25e1f584b1

## 要点

- 2026-11-27 にグリルと別モデルの検討を行い、暫定の印を外した。確定事項は D1〜D22、残る未決は検出を道具にするか（U17）だけである。
- 衝突を、git が自動マージできない「テキストの衝突」と、git は自動マージするが anet の決まりに反する「決まりの衝突」（同じ番号の RFD が 2 本入る、移した置き場の旧い場所にファイルが入る、など）に分ける。
- 入口は新しい skill `anet-merge-branch`。計画（衝突の一覧と解き方）を示して開発者の承認を受け、AI がマージの開始・中止と、解いたファイルのステージを行う。commit と push は開発者が行う。
- 種類と解き方の表を区画ごとに上から当てる。番号の重なりはマージの前にブランチの側を振り直し、置き場の移動は移した先で表を当て直し、道具の生成物は道具で作り直し、作業の記録は両側を残し、wiki の書く部分は規約が変わったときだけ取り込みをやり直す。
- 振り直しの行に旧い番号のコミットを名指す形を足し、道具はマージの途中でも両側の履歴を読む。
- 最初の適用は、この RFD を実装してから `feature/20261125-ppo` を取り込むことで、PR はそれまで待たせる。
- 公開の衝突解消の skill はどれも、番号の重なり・プロジェクト固有の生成物・追記だけのログの順を扱わない。anet の決まりの表が、この RFD の中心である。

## 内容

### 問題と現状

RFD0202 の番号が、main（wiki の積み上げと引き方）とブランチ `feature/20261125-ppo`（PPO 系）で重なった。ファイル名が違うので、git はこれを衝突として示さない。2026-11-27 の試しのマージでは、main が wiki のトピック別まとめを `docs/wiki/concepts/` の下へ移して中身も書き直したため、テキストの衝突が 8 ファイルになった（main で消したファイルをブランチで変えている 6、作業の記録と目録）。ブランチの wiki の変更は 93 行の足し算だけで、すべて PPO の RFD の書き戻しから来ている。暫定の起票は「同じ事実を両側が別の文で足した」と書いたが、分かれた点と比べると、その行はもとからあり main が書き直しただけだった。

### 事例

forge の skill は計画を先に示して承認を待ち、Matt Pocock の skill は文の塊ではなく両側の意図を選ぶ。生成物は手で合わせず作り直す型が共通である。多くの skill は AI が `git add` とコミットまで行う。LLM が実際の衝突を正しく解けるのは 6 割未満と報告されている（検索の要約による）。

### 確定事項

- 取り込む向き: ローカルの main をブランチへマージし、ブランチのワークツリーで解いて、PR をマージのコミットの形で入れる（squash と rebase はハッシュを消すので使わない）。main の作業ツリーは並行のセッションの変更とぶつかり、GitHub の画面は消したファイルを変えた衝突を解けない。
- git の操作: AI は計画の承認のあとに `git merge --no-commit --no-ff main` と `git merge --abort` を行い、区画を解くたびにステージする。直した分をステージしないままだと中止が失敗することを、使い捨てのリポジトリで確かめた。AGENTS.md の Git の例外を足す。
- ファイルの性質を、道具の生成物・AI の派生物・記録・正本の 4 つに分け、作り直せるかで解き方を決める。wiki の書く部分は、分かれた点のあと wiki の規約が変わっていなければ行を移した先へ当て直し、変わっていればブランチの側を捨てて取り込みをやり直す。
- 番号の重なりは、main の側が件名に引かれて変えられないので、いつもブランチの側をマージの前に振り直す。ADR は番号だけを直して本文を変えない。振り直しの行で旧い番号のコミットを名指し、道具はそのコミットだけを振り直した RFD に当てる（ADR 0077 の「日付以前のコミットに限る」をさらに絞る形）。
- 確かめは、衝突の印、`maps` と `scan`、番号の一意、作業の記録の順、ビルドとテストで、マージのコミットの前に行う。報告は 1 項目 1 ファイルで、自動マージの可否、両側の変更、解き方、開発者に聞くことを書く。
- 予防（採番がほかのワークツリーとブランチを見る）は範囲外で、別の課題の候補にした。

### 受入

skill の写しの一致、AGENTS.md の 2 か所、道具のテスト（名指し、8 つの誤りで止まること、マージの途中の履歴）、PPO のブランチの取り込みでの番号の一意・道具が止まらないこと・衝突の印 0 件・作業の記録の順・ビルドとテスト・PR のあとの main、報告の件数、課題への数の記録である。
