# 設定継承の差分適用と最終値参照

## 元の材料

[設定継承の差分適用と最終値参照](../../../memo/done/0072_config_selection_final_value_10rfd.md) blob:1a9f313cc523d2f56e7d87cf738b982969497feb

## 要点

- 設定の継承は選んだ素材の最終値を使い、後から選んだ側が持つキーの差分を重ねる。
- 後段の素材にない値は、前段で直接指定されたか継承されたかにかかわらず残す。
- Run プロファイルや CLI からの指定、設定キーの個別指定が効く順序をそろえる。
- 設定名にドットがあるかで宣言と上書きの意味を分ける仕組みを見直す。
- 以前の golden 比較を改訂後の検証に流用せず、設定の組み合わせごとに最終値を確かめる。

## 内容

### 背景とゴール

PRD 072の当初の課題は、選択元への後段変更が継承先へ届かないことと、Runプロファイルの指定が通常選択に負けることだった。2026-09-12版では最終値参照とRunの優先を実装したが、選択元を「宣言を運ぶ入れ物」と「組み立て済みノード」に分け、ドット無しの名前を上書き層として判定している。

### 確定契約

`X.$ = Y > Z`は、YとZがそれぞれのベース、部分指定、個別指定、Run・CLIを反映した最終値とキー集合を読み、YへZの差分を重ねる。Zが持つキーだけを上書きし、ZにないキーはYから残す。値の由来による削除はしない。
選択元が`@`プロファイル、`[key]`カタログ、通常prefix、その一部分のいずれでも同じである。参照先への後段変更・追加キーは、その参照先の優先順位を解決した最終値として継承先へ届く。継承先の変更は参照先へ逆流しない。
Runプロファイルは通常選択より前に展開し、葉についてはキーごとの最終指定を畳んで一度だけ適用する。Runの項は左から右の後勝ち。自身のリテラル葉を対象とし、別の`run.$`を供給するネストは禁止する。CLIの`run.$`指定はRun選択そのものを変更する。
第1相・第2相という先行版の実装表現を保つかは実装時に決める。契約は優先順位、伝播、適用対象、診断結果であり、選択の再実行を必須にしない。
選択の深さ上限は10。起点を1とし、最終値を求めて辿る選択の依存グラフの最長経路で数える。兄弟termの数・パスのセグメント数・反復回数ではない。キャッシュや宣言順で判定を変えない。Runの先行展開は深さに数えない。

### ユーザーマニュアル草稿

`?=`は既定キー。その設定のベースが同じキーを供給しなければ残り、供給すれば負ける。葉にだけ書け、`.$`・Runプロファイル・CLIでは書けない。
`:`のパーサ仕様は変更しないが、説明・新規記述では`@`プロファイルの区切り以外に使うことを推奨しない。通常キーは`Env.$ = @a`のように`.`で書く。左辺の`@`は原則1個を推奨し、外側の選択で内側の定義も切り替える必要がある場合だけ入れ子を使う。禁止・新しいWARNは追加しない。
各 M 番号は独立した入力であり、前の例の変更を持ち越さない。CLI の表は設定ファイルへの追記ではなく、別途 resolver に渡す override のキーと値を表す。
期待結果: `[eval]` と `[eval_target]` の eps_start はともに 0.01、両方に `policy.use_amp = true` が存在する。`@eval_base` 自体の eps_start は 0.05 のままで、use_amp は追加されない。
親からの最終値の伝播と子自身の優先を分けて検証する。2026-09-12版で実装したRun・CLIの伝播は本改訂でも維持する。

### 受入条件と既存テストの改訂

同じ実効葉を意図して個別指定した独立分岐では、その値が継承値に勝ち、競合WARNを出さない。個別指定と選択行を逆順にしても同じ結果になること。
同じキーに`?=`と`=`が混在する入力で、順序に関係なく`=`が勝つこと。プロファイル内の`?=`がそのプロファイルの`.$`に負け、外側へはベース値として届くこと。
file、Run、CLIの各チェーン置換経路で、選択先が持たないキーの既定キーが残ること。backendの`deterministic_warn_only`とappの`log_flush_interval_ms`を含め、プロファイルが全キーを持つという偶然に依存しないこと。

### 現用設定の移行と17件の比較

common.txtの共有既定値と、Atari / DropMerge / ImageCls / LunarLanderの通常選択が衝突する。
「旧golden」は`?=`で保持する値、「`=`のまま」は個別指定が勝った場合の値である。キーの種類数は入力をまたいで重複排除し、env別の件数は各envに属するmanifest入力の和集合とする。
文字列表記・コメント・定義位置・重複順を保ち、演算子だけを変更する。既存17入力の旧golden比較に加え、現用設定の通常入力・各Runプロファイル・Optuna追加設定・配線チェーンについて、変更前後の全キー・文字列値を比較する。既定値専用の名前や暗黙の継承は設けない。
既定キーは選択と独立に残るため、通常設定・Runプロファイル・batのCLI・設定生成ツール・補助テストのチェーン宣言は変更しない。固定17入力への適用も、同じ用途分類で葉の演算子を変えるだけで、manifest・CLI・注入値は保持する。これ以降に追加されたroot直書きの既定値も、同じ性質なら書き換え対象に含める。

### 検討経緯と簡素化の判断

旧選択の生成物を削除するための由来追跡。別々の選択元に由来する葉は、右側にない限り残す。
`=`を下書き、`:=`を上書きとする記法。プロファイル内の`=`が再びベースに負ける。上書き記号に既知の意味がない。
固定入力・旧golden・差分レポート。17件の実験条件を変えないことと、診断変更を機械的に確認する。
成功は「上書き層を識別するコードが不要」「個別・部分指定の行順で結果が変わらない」「書き換え後17件の値一致」「チェーンを足しても既定値が落ちない」で測る。過去の検証は20implへ参照を残し、本改訂の受入条件の証拠とは区別する。

### 今回扱わないこと

Actor APIや設定カタログへの移行(PRD 061)、NNブロックの未知キー検証など消費側の契約。
既定キーがチェーンに隠された、または個別指定がチェーンの値を隠したことの記録。必要になれば`overrides`と同じ絞りで別途検討する。
過去のRun artifactの書き換え、互換モード、staging・commit・push。
