# episode_start と stack・n-step の境界についての旧草案

## 元の材料

[RFD0149　episode_start と stack・n-step の境界についての旧草案](../../../memo/dropped/0149_episode_start_stack_contract_10rfd.md) blob:6fce910bcb8ccaf6a4666d5d9fe92b3a2cd7c569

## 要点

- この裁定案は中止になった。RFD0078 が、直前の done を伴わない episode_start を契約違反として ReplayBuffer の Push で止めると決め、設計とテストもそろったためである。
- 発端は Actor と ReplayBuffer で同じ入力の意味が違ったことだった。行動選択では episode_start を受けた lane のフレームを初期観測で埋め直した。
- 当時の ReplayBuffer は episode_start を保存せず、done または truncated だけで区切った。学習用に復元したスタックと n-step の収益は開始位置をまたげた。
- 失敗していた二つのテストは、開始フラグだけでも n-step の収益を打ち切り、スタックを初期フレームから作り直すことを要求していた。
- 草案では Replay 側も開始フラグで区切る案に傾いていたが、実行時に該当入力が起きるか、保存や速度にいくらかかるかは未確認だった。

## 内容

### 当時の二つの経路

同じエピソードの出来事を学ぶつもりでも、行動時の Actor と学習サンプルを作る ReplayBuffer に異なる状態列が見え得た。開始フラグ単独の入力に実害が生じる例は当時確認されていなかったが、既知失敗二件を新しい失敗と区別する負担は続いていた。

### 二つのテストが期待した境界

時刻3で再び episode_start を入れた例では、時刻1からの3ステップ収益は時刻2までの二つの報酬で終わる想定だった。時刻3の3フレームのスタックは時刻3の観測を3枚並べ、時刻2・1へ遡らない想定だった。これらは草案当時のテスト要求である。

### 検討した選択と中止の理由

Replay が開始フラグを保存する案、終端フラグだけを境界とする仕様にテストを合わせる案、既知失敗の扱いを続ける案を比べた。後続の RFD0078 が単独の開始フラグを受け付けないと決めたので、この三案から選ぶ必要がなくなった。
