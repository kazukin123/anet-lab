# CI のビルド・テストと定点ジョブの改善案

## 元の材料

[RFD0156　CI のビルド・テストと定点ジョブの改善案](../../../memo/0156_cicd_improvement_10rfd.md) blob:efef69bd6768bb025998714908996affae0f5d23

## 要点

- ビルド・テストの自動化や LLM 補助の使いどころを検討した暫定案である。実行条件と受入は候補として記録した。
- 調査時の CI は配布と文書公開が主で、ビルドが自動で動いた形跡とテスト実行の記録が乏しかった。
- PR と main の更新には構成を絞ったビルドと CPU テストを当て、JUnit 結果を成果物として保存する案を置く。
- 定点ジョブで統計や設定カタログを生成し、失敗テストを継続して追えるようにする。
- GPU のないホストと実験機の資源競合、依存の取得・ビルド時間を設計条件に含める。
- LLM による補助は決定的な検査とは別に扱い、入力と回数を抑える。

## 内容

### Context / Problem Statement

windows-ci.yml のトリガは `pull_request: branches: [ ]` と `workflow_dispatch` である。branches が空リストのため PR では起動せず、実質は手動起動のみになっている（空リストの厳密な挙動は要確認だが、自動で走った形跡はない）。main へ直接 push する運用が中心なので、PR トリガだけでは入口にならない点も併せて見直しが要る。

### 効く事実

実験機を self-hosted runner にすると実験と競合する。実験機は 1 時間で最大 8% の throughput ドリフトが実測されており、性能比較中の CI 実行は結果を汚す。

### 提案

L1 は既存 windows-ci.yml の改修で済む。L2 は決定的なスクリプトなのでローカルの空き時間スキルと実装を共有する。L3 だけが LLM 依存で、API 制約とコストの影響を受ける。

### 候補を採る場合の受入条件

失敗テストが台帳に first_seen 付きで残り、直った時点で last_seen が止まる。
Gemini レビューが Step Summary 以外の場所に残り、後から参照できる。

### スコープ外

ローカルの空き時間スキル群。CI とは台帳形式とスクリプトだけを共有する。
Pages 配信。既存の pages.yml のまま。
Doxygen 生成。時間だけかかり、品質ゲートにも定点情報にも寄与しないため対象外。
