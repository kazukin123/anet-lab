# MetricsViewer SQLite キャッシュ化(Phase 1: OOM 解消・LOD・viewport API)

## 元の材料

[MetricsViewer SQLite キャッシュ化(Phase 1: OOM 解消・LOD・viewport API)](../../../memo/done/0041_metrics_sqlite_cache_10rfd.md) blob:8555b0e57495ec4bcdafd06eb85e8e5954f57ab1

## 要点

- 大きい Run の全タグ・全点をヒープに保持していたことが Metrics Viewer のメモリ不足につながっていた。
- Run の指標を SQLite キャッシュへ取り込み、描画に必要な範囲を照会する。
- 複数の解像度を用意し、表示領域と幅に適した粒度で時系列を返す。
- フロントエンドは viewport に応じてデータを要求し、元ファイルを正本として扱う。
- 大きい Run でのメモリ使用と表示結果を確認し、キャッシュから再構築できるようにする。

## 内容

### 表示用データを取り出す単位

巨大な Run の全タグ・全点を Java のヒープに載せると、表示範囲を小さくしてもメモリ不足が起きる。各 Run の `metrics.jsonl` または不変な `metrics.jsonl.gz` を正本とし、SQLite の `metrics_cache.db` に追記位置、元の各点、描画用の粗い集計、タグの統計を保持する。ビューアは表示範囲と描画可能な点数に合わせて問い合わせる。

### 元の時系列を復元できる集約

元の各点に、タグ内の順序と実際の step を保存する。複数段の集約では16個ずつまとめ、最小値・最大値・末尾値にはそれぞれ実際の点の順序と step を持たせる。拡大すれば元の解像度まで戻れ、遠景でもスパイクや谷がブロックの先頭にずれない。タグ全体の統計は表示範囲や集約の粗さに左右されない。

### 取り込み、再開、再構築

1本の writer が最大100万件の完成行を1ブロックとして扱い、元の点・集約・統計・非 scalar の原文・読み込み済み位置を同じトランザクションで確定する。途中で停止しても次回は最後に確定した位置から再開する。読み取りは1要求・1 Run ごと、書き込みは1ブロックごとに接続を閉じ、変換中の gzip を除いて Run フォルダを移動できるようにする。

JSONL と gzip が両方あれば JSONL を使う。入力種別の変更、切り詰め、キャッシュ破損、スキーマ不一致などで入力の同一性を保証できなくなれば、DB と付随ファイルを破棄し、正本の先頭から作り直す。全再構築ではキャッシュの世代を更新し、同じ DB への通常の追記では世代を維持する。サーバーとブラウザはこの世代で古いデータの混入を防ぐ。

### API と画面

各 Run の準備状態は応答内に含めて、表示可能な系列だけでも取得できるようにする。要求全体が描画の最低点数を配れなければ HTTP 422、問い合わせの同時実行枠を得られなければ503を返す。ブラウザは手元のデータで表示範囲を覆えないときにだけ、150ミリ秒まとめて全対象を一度に要求する。各系列の表示点数はサーバーが制御するため、ブラウザは受信点を間引かない。

### 受け入れ条件

キャッシュを削除して再構築したときに確定済みの表示とタグ統計が再現し、変換中も確定部分を閲覧できることを確認する。巨大な実 Run では、表示点数を抑えながら、広い表示範囲の極値が元の時系列と同じ step に描かれることを照合する。
