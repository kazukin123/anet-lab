# RFD の判断に要る前提の共有

## 元の材料

[RFD0189　RFD の判断に要る前提の共有](../../../memo/0189_grill_premise_understanding_10rfd.md) blob:b2a5994ea0487411ea16c596dbaf4df269e79c9e

## 要点

- 設計を詰める質疑では、複数の論点に共通する前提をゴールと非ゴールの提示時に示す。一つの論点だけに必要な前提は、その問いに添える。
- 共通の前提を確かめるのが既定である。開発者が「このまま進める」と指定すれば、理解の確認も、欠けた前提を先にそろえる手順も飛ばして問いへ進める。
- 前提が欠けていれば「先にそろえる」「結果ごとの分かれ方で決める」「前提なしで決める」を推奨つきで示し、開発者が選ぶ。
- 前提の表には出典と確認結果を残す。暫定の起票は表だけを書き、欠けた前提の出典を「欠け」、確認を「対象外」とする。質疑や事前調査の段取りは行わない。
- 共通の前提を説明する機会は再グリルや質疑を伴う改訂にも置く。実装に合わせるだけの改訂には、前提の表を求める新しいレビュー観点を適用しない。

## 内容

### 問題と狙い

個別案への回答だけ先に受けると、回答のよりどころとなる事実や処理全体の理解が食い違ったまま設計が進む。過去には RND の統計処理を直す手順で先に測るべき前提が見つかった。新しい手順は、説明の必要な箇所だけに時間を使い、根拠を後から確かめられるようにする。

### 前提を示し、理解を確かめる時機

新規のグリルではゴールと非ゴールの提示時、既存 RFD の改訂では要点とゴールの提示時に共通の前提を並べる。開発者にとって新しいものに印を付け、説明が要る番号や異論を、ゴールへの返答に添えてもらう。後で回答と前提が食い違えば記録前に内容を確かめる。開発者が確認を飛ばす指定をした場合は表に「飛ばした」と記す。

### 前提が欠けた場合の三つの扱い

事実を先にそろえる、結果別の選択を先に定める、前提なしで決める、の三つから開発者が選ぶ。結果が他の重要な決定の推奨を左右するなら先に調べる案を勧める。短い調査や試作はその場で行い、長い測定や Run が要る場合は決定済みのこと・測り方・残る問いを RFD に残して質疑を止める。課題は調査中に保ち、測定後は同じ RFD で再開する。

### 表の記録と適用範囲

前提の番号・種類・内容・出典・確認結果を一つの表に置き、決定の理由から使った前提を引く。質疑を省く暫定の起票では表だけを作る。欠けた前提は「欠け」、確認結果は「対象外」とし、そろえる段取りは書かず、再グリルするときに扱う。受入では新規・質疑を伴う改訂に対するレビュー観点と手順を検査し、実際の質疑が円滑になったかは運用時に確かめる。
