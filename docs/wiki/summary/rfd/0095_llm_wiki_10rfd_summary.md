# 実験・設計の知見とトピック別まとめを引く wiki

## 元の材料

[LLM-Wiki 型のまとめの層（PRD の上流で、知見を題材と機構ごとに、実装の地図をアプリケーションと機能カテゴリごとにまとめる）PRD](../../../memo/done/0095_llm_wiki_10rfd.md) blob:0a19cbc1eba7fd8d043ff5dd067f0d51c9342613

## 要点

- 実験記録・調査・RFD の知見を題材や機構ごとに引けるようにし、後日撤回された結論を追いやすくする。
- 正本は wiki の外に保ち、主張に原本への出典を付けて派生ページをまとめる。
- アプリケーション・機能カテゴリには、設計の概要、成立の経緯、関係する資料とソースを結ぶ。
- 目録と追記型の記録を持ち、取り込み漏れ・出典の更新やリンクの切れを点検する。
- この RFD の設計時点では資料ごとのサマリは作らず、目的別に横断したページを中心としていた。

## 内容

### 背景と原則

実験記録は時系列、RFD やサーベイは資料の種類ごとに並ぶ。同じ題材を調べるたびに多くの資料を開き、後で撤回された結論を読み違えることがあった。wiki を正本から導くまとめとして置き、数値や判断の根拠を原本まで追えるようにする。

### 実験記録と知見

campaign 文書を要約した実験 README の記述は wiki へまとめる。一方、複数 campaign をまたいだ独自の分析や、ほかの材料にない集計は README に残し、wiki からその分析を引く。RFD に至らなかった Run 分析は実験記録を正本とする。

### 実装の経緯と制約

トピック別まとめはコードの構成だけでなく、アプリケーションや機能カテゴリの責務、成立の経緯、見送った案と変更時の条件を集める。次の改修で何に着手するかは RFD で決めるため、計画と一次の判断をここへ移さない。

### 取り込む主張を選ぶ

RFD の背景には、まだ実験記録になっていない Run の事実や調査結果が含まれる。RFD が採った設計の決定を知見のページで再定義せず、根拠となった観測を条件・出典とともに集める。後で条件違いや反例が分かったら、古い結論を打ち消す追記だけに依存せず、現在の項目と撤回の記録の両方を直す。元が memory しかない数字は出典にせず、正本を用意できるものだけを公開する。

### 人が書く説明と派生一覧

トピック別まとめには、アプリケーションの責務、関係する設計文書・ガイド、RFD と ADR から分かる成立の経緯を置く。ソースは所属するファイルへのリンクとして掲げ、実装の中身をコードから推測して説明しない。ファイルや変更に対応する RFD の一覧のように決定規則で求まる部分はツールで生成し、なぜ採用しなかったか、何を変えてはいけないかの説明は根拠を読んで書く。資料を置き換えた場合も、成立の経緯を消して過去の判断が見えなくなるのを避ける。

### 取り込みと点検

材料を読んで項目・目録・作業記録を更新する取り込みと、リンク・材料更新・撤回・派生一覧を点検する手順を分ける。作業記録の blob から取り込んだ版をたどり、原本と食い違う場合は原本を優先する。

### 読み始めと書き戻し

既存 RFD を改訂するときは要点の提示前に、題材から始めるときは最初の目的確認前に、該当する wiki ページと必要な原本を読む。グリル中に新しく分かった事実は起草時にまとめ、完了時に本文と wiki の内容が食い違っていないかを再確認する。したがって、RFD の決定根拠を wiki にだけ置かず、原本単体でも判断をたどれる。

### 材料が増えたときの点検

随時の修正は、資料をよく知っている会話の中で取り込むために使う。定常点検は複数の会話の取り残しを拾い、材料の blob、移動、リンク切れ、撤回の反映を確認する。保管フォルダを変えた RFD などは、単なる文字列置換ではなく実在する材料と突き合わせる。工程が対象とする本数を明示し、部分的な取り込みと全材料の確認を区別する。

### 段階導入と効果の見方

試作では Kung-Fu Master の題材ページを先に置き、RFD の検討を始めるときに読む経路を確かめる。資料を集めるために実際に開いた数や、背景の事実を訂正した回数を比較する。参照元が自分自身の RFD である試行は、読む資料の削減の測定には向かない。次の別の RFD の作成で、どのページが判断に使われたかを追う。
