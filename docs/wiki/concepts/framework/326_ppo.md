# 326 Agent個別実装 PPO系列

[anet-lab](../../../../README.md) › [wiki の目録](../../index.md) › [フレームワーク](../../index.md#フレームワーク)

## 概要・責務

- PPO系は、方策（状態から行動の確率への対応）を直接学ぶAgentの系統で、DQN系と並ぶ。最初のAgentの`PPOAgent`が離散行動のPPOを実装し、経験を共通ReplayBufferにためず、今の方策で集めたrollout（器は`LaneTimeTensorStore`）を1回の更新で使い切る（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§1.1；[ANETフレームワーク全体概要](../../../design/010_framework_overview.jp.md)、§5.2；[Agentと学習](../../../design/110_agents_and_learning.jp.md)、§2.4；[ReplayBuffer](../../../design/150_replay_buffer.jp.md)、§2.5・§3）。
- `src/algo/ppo`（ライブラリ`anet-algo-ppo`、名前空間`anet::rl::ppo`）に置き、coreにだけ依存して兄弟の系統に依存しない。公開するのは初期化関数`InitPpo()`だけで、Runnerが起動時に呼んで`PPOAgentFactory`を登録する。`PPOAgent`はRunnerの種類と評価の間隔を知らず、渡された経験を受け取って更新結果を返す（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§1.2；[ソース配置とライブラリの境界](../../../design/011_source_layout.jp.md)、「ライブラリとアプリ」）。
- 損失の式と更新の進め方はPPO系が持ち、行動の分布・advantageの推定・Headの合成はcoreの部品を使う（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§1.2）。
- NetworkはAgentが持つResourceで、Learnerが重みを更新する。学習のActorは同じNetworkを共有し、評価のActorは写しを持って`Sync()`で写し直す。rolloutの器とoptimizerはLearnerが持つ（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§2.1）。
- Networkは1つで、方策のHead（`policy_feature`を受け取り、logitsを出す）と価値のHead（`value_feature`を受け取り、valueを出す）をcoreの`CompositeHeadFactory`で並べる。Bodyを共有するか完全に分けるかは、2つのキーを向けるbranchの設定だけで決まり、コードは変わらない。PPOAgentのFactoryは、branch・body・outputを`PPOAgent.net.*`から読む（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§3.1・§3.2；[ニューラルネットワーク](../../../design/130_neural_networks.jp.md)、§2.3；[実行基盤と設定](../../../design/100_runtime_and_configuration.jp.md)、§2.1）。
- Actorは選んだ時点のlog確率・value・Networkの入力・方策の世代を行動の情報に載せる。Learnerはそれをためて、rolloutが埋まるまで空の結果を返し、埋まるとadvantageを推定してepoch×ミニバッチで更新し、optimizerのstep 1回につき1件の更新結果をまとめて返す（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§4・§5・§6.1・§7.5；[Agentと学習](../../../design/110_agents_and_learning.jp.md)、§6.2）。
- 方策の世代はrolloutの更新ごとに1進み、古さの最大が2以上のrolloutは学習に使わずに止める（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§6.3）。

## 選ばなかった形

- 方策と価値にNetworkを2つ持つ形 — 不採用: 写し・保存・同期・optimizerが2組になり、共有の形を別の仕組みで作ることになる（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U4）。
- Runnerにrolloutの境界や待ち合わせを知らせる口、評価をexp stepで駆動する口を足す形 — 不採用: 今のRunnerの契約で書けるので足さない（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG2・§12 U5・U8）。
- DQN系の中にあってほかの系統でも要る部品（rolloutの並べ替え、Actorの写しと同期、optimizerの組み立て、診断の間引き、2つのHeadの並べ方、Perceptionの仕上げ、設定の検証の補助、RNDの段取り）をcoreへ上げてPPO系と分け合う形 — 先送り: 開発者の了承が無いのでDQN系を変えない。再開条件: 部品ごとの「移す条件」（例: rolloutの並べ替えは3つ目の利用者が出たときか、RNDの補助学習をPPO系で使うとき）（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG1・§10・§12 U17）。
- PPOの損失、rolloutの並べ替え、optimizerの組み立ても、行動の分布やadvantageの推定と同じくcoreに置く形 — 先送り: 損失はPPO系の中身で、coreの`advantage`には推定だけを置く。再開条件: 2つ目の利用者が出たとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U2・§7.8）。
- `ppo_assembler`（2つのAgentが分け合う組み立て）と`ppo_heads`（専用のHead）のファイルを立てる形 — 先送り: PPO系のAgentが1つで、専用のHeadが無い（coreの`LinearHeadFactory`と`CompositeHeadFactory`で足りる）。再開条件: 2つ目のAgentか、専用のHead（連続行動の標準偏差など）を足すとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§7.8）。
- 連続行動（Gaussianの分布、tanhで縮める形とlog確率の補正、連続のHead）を同時に作る形 — 範囲外（非ゴール）: 行動の受け渡し（Env基底・経験・Viewer）の横断の改修で、別の関心である。再開条件: 連続行動のRFD（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG3・§11）。
- ActorとCriticに別の入力を渡すための、真値の観測キーの宣言と、`policy_feature`に向けたbranchに真値が入らないことの構築時の検査 — 範囲外（別の関心）: 観測キーの定義とEnvの側の関心である（2つのbranchの`bind`に別の観測キーを書く形は、今の設定で組める）。再開条件: 真値の観測を出すEnvのRFD（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§11）。
- Forwarderの並び（FrameStack・Normalize）をPPO系に結線する形（観測の正規化を含む） — 範囲外（非ゴール）: 仕上げの部品がDQN系の中にあり、同じものを重ねて書くことになる。再開条件: Atariか連続行動をPPO系で回すとき（DQN系のPerceptionの仕上げをcoreへ移すのと合わせる）（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG4・§11・§12 U11）。
- 報酬の正規化を入れる形 — 範囲外（非ゴール）: CartPoleの受入に要らず、独立に足せる（差し込み位置は蓄積の前のcoreの`RewardScaler`）。再開条件: 報酬の尺度が大きいEnvを回すとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG5・§11）。
- AMP（半精度のforward）を入れる形 — 範囲外（非ゴール）: CartPoleの受入に要らず、独立に足せる。再開条件: 画像のEnvをPPO系で回し、更新の時間がRunの長さを決めるようになったとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG5・§11）。
- 可塑性・勾配ノイズの診断を入れる形 — 範囲外（非ゴール）: CartPoleの受入に要らず、独立に足せる。再開条件: PPO系の学習の停滞を調べるとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG5・§11）。
- 方策の確率をGUIに表示する形（Actorが行動の情報に確率を載せ、Runnerのpanelが読む） — 範囲外（非ゴール）: CartPoleの受入に要らず、毎stepのdeviceからCPUへの転送が増える。再開条件: GUIで方策を見たいとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§3.2 NG5・§11）。
- RNN（Actorが再帰状態を持ち、Learnerのミニバッチをlane単位にする） — 範囲外（別の関心）: 再帰のmoduleがまだNNに無い。再開条件: RNNのmoduleがNNに入ったあと（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§11）。
- RND（外的と内的の2つの価値のHead、2つのadvantage） — 先送り: 実験の結果が要る（DQN系のRNDの評価が進行中）。再開条件: MontezumaをPPO系で回すとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§11）。
- A2C（clipなし・1 epoch・1ミニバッチの損失を選べる形） — 範囲外（別の関心）: 今回は離散のPPOだけを作る。再開条件: 比べたいとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§11）。
- PPG（補助の相と補助の価値のHead） — 先送り: 実験の結果が要る。再開条件: 共有のNetworkで方策と価値の釣り合いが問題になったとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§11）。
- SACをこの系統に入れる形 — 範囲外: ReplayとQのNetworkを使い、rolloutとadvantageの推定を使わないので、別の系統にする（分け合うのはcoreの分布だけ）。再開条件: 連続行動のあと（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U13・§11）。
- 写しを持つTrainのActorを、rolloutごとに方策の世代を見て写し直す形 — 範囲外（別の関心）: TrainのRunnerは`Sync()`を呼ばず、今は写しを持つActorをTrainに使わない。再開条件: Actorを別のdeviceで回すとき（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§11・§10 C2）。
- KLで止める判定をミニバッチごとに行う形（SB3の形。閾値の1.5倍で、optimizerのstepの前にやめる） — 不採用: ミニバッチごとにdeviceからCPUへの転送が要る（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U23）。
- 更新結果の統計の読み出しを`HostReadback`に載せる形 — 不採用: 読むのは更新の直後の同じスレッドで、あいだに進める処理が無く、載せても同期の転送と同じである（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U22）。
- 勾配のclipの上限の設定キーを、DQN系と同じ`learner.grad_clip_tau`と名付ける形 — 不採用: `tau`はsoft updateの係数・方策温度・τサンプルにも使う語で、何の値かが名前から読めない（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U30）。
- PPO系のメトリクスを`metrics.scalar.@baseline`に足す形 — 不採用: `@baseline`はDQN系の鍵を含み、PPO系で選ぶと見つからない鍵のWARNが並ぶ（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U16）。
- 1枚のときはstack軸を足さない形（観測をそのままNetworkの入力にする） — 不採用（却下）: 枚数で形の意味が変わり、次元の数から見分ける道具が残る（出典: [ADR 0086](../../../adr/0086-perception-stack-target-keys-always-carry-stack-axis.md)、Considered Options；[RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§12 U11）。

## 変えるときの条件

一般の条件は[リファクタリング観点](../../../quality/refactor.md)の「ガードレール」、テストの充足は[定点統計](../../../../reports/stats/trend.md)の「テスト充足」を見る。

- PPO系のライブラリはcoreにだけ依存し、DQN系など兄弟の系統に依存しない。ライブラリの依存の検査（`check_stage3_dependencies.py`）の系統の一覧に`anet-algo-ppo`を入れて確かめる（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§1.2；[RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§4 P11・§8の検証資材の行）。
- 共有するNetworkは通常evalにし、Learnerはミニバッチ1つのforwardからoptimizerのstepまでの区間ごとにだけ、Agentの排他のロックを持ってtrainにする（rolloutの更新の全体では持たない）。Actorは行動選択の中でevalとtrainを切り替えない（出典: [PPO系Agent](../../../design/230_ppo_agents.jp.md)、§12；[RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§4 P15・§7.10）。
- 毎stepと毎回の更新の経路にdevice間の同期の転送を足すときは、頻度と1回あたりの時間を見積もり、laneや行を回すループの中には置かない（出典: [RFD0209](../../../memo/0209_ppo_family_and_on_policy_core_parts_10rfd.md)、§4 P13・§7.6；[PPO系Agent](../../../design/230_ppo_agents.jp.md)、§11）。

## 外の事例

- Stable-Baselines3 の PPO・A2C の `ActorCriticPolicy` は `ortho_init=True` が既定で、特徴抽出と隠れ層を gain √2、行動の出力を 0.01、価値の出力を 1 の直交初期化にし、bias を 0 にする（出典: [weight_init_normalization_adam_survey_2026-11-27.md](../../../../reports/survey/weight_init_normalization_adam_survey_2026-11-27.md)、§7.4）。
- CleanRL の `ppo_atari.py` は全層を直交初期化（gain √2、方策の出力 0.01、価値の出力 1、bias 0）にし、`ppo_procgen.py` の IMPALA CNN は conv と 256 の線形層を PyTorch の既定のまま、方策と価値の出力だけを直交初期化にする（出典: [weight_init_normalization_adam_survey_2026-11-27.md](../../../../reports/survey/weight_init_normalization_adam_survey_2026-11-27.md)、§7.5）。
- OpenAI の phasic-policy-gradient（PPG）の IMPALA CNN は、conv と線形層の重みを、出力のユニットごとの L2 ノルムが指定の scale になるように縮め、bias を 0 にする（出典: [weight_init_normalization_adam_survey_2026-11-27.md](../../../../reports/survey/weight_init_normalization_adam_survey_2026-11-27.md)、§7.6）。
- TorchRL は損失を独立した部品（LossModule）にし、value estimator に TD0・TD1・TDLambda・GAE・VTrace・MultiAgentGAE を持つ。参照実装の `a2c/`・`ppo/` は ALE/Pong-v5 と HalfCheetah-v4 を既定の環境にし、継続検証のスクリプトがある（出典: [torchrl_survey_2026-11-20.md](../../../../reports/survey/torchrl_survey_2026-11-20.md)、§4.3・§5.1）。
- TorchRL の論文の Table 1（5 seed の平均±標準偏差）で、PPO は Atari の 40M フレームで Pong 20.52±0.58、Freeway 33.31±0.95、Boxing 98.31±0.93、Breakout 335.71±46.72、MuJoCo（v3）の 1M step で HalfCheetah 2770±821、Hopper 1703±742、Walker2D 3336±928、Ant 2469±606 だった。Atari の環境の版、sticky actions、評価の手順は確かめられていない（出典: [torchrl_survey_2026-11-20.md](../../../../reports/survey/torchrl_survey_2026-11-20.md)、§6.1）。
- GAE の計算時間は、1000 step の軌跡 1000 本で Tianshou 5.15 ms、SB3 14.1 ms、RLlib 9.38 ms、CleanRL 1.43 ms（JAX、GPU）、TorchRL compiled 2.67 ms、TorchRL vec 1.33 ms（GPU）で、CPU と GPU の間の移し替えは含まない（出典: [torchrl_survey_2026-11-20.md](../../../../reports/survey/torchrl_survey_2026-11-20.md)、§7.1）。
- CleanRL を fork して torch.compile と CudaGraphModule を足した LeanRL は、H100 で、PPO の Atari（Breakout-v5、EnvPool）を 1,022 から 6,809 fps（6.8 倍）に、連続行動の PPO を 652 から 1,774 fps（2.7 倍）にした（出典: [torchrl_survey_2026-11-20.md](../../../../reports/survey/torchrl_survey_2026-11-20.md)、§7.2）。
- CleanRL の `ppo_rnd_envpool.py` は、畳み込みと全結合を方策と外的・内的の 2 つの価値で共有し、2 つの価値が別に持つのは最後の 1 出力の全結合だけで、方策は別の 2 層を持つ。内的の GAE は次の非終端の印を常に 1 にし、外的は done で切る（出典: [value_decomposition_head_nstep_survey_2026-11-27.md](../../../../reports/survey/value_decomposition_head_nstep_survey_2026-11-27.md)、§2.4・§3.1）。
