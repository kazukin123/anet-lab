# Atari Breakout: BTR NN構成の移植検証 — 2026-09-12

対象 workspace: `atari-3rd`。ゲームは breakout 固定。すべて seed 1、`backend.@non-deterministic`。

基準は Munchausen 入りの RR4 構成で、`run.@v5_iqn_impala_x2 > run.@a5 > run.@a5_apex > run.@va_base` に
`run.@hard500 > run.@rr4 > run.@munch` を重ねる。各腕はそこから**NN構成だけ**を変えている。

起点は [2026-09-08](2026-09-08_replay-ratio-mechanism.md) 探索ブロック 10
（BTR 公開実装は同じ再利用 4 回で崩れず、本構成の RR4 素を大きく上回った）。
本記録は**その差が NN構成のどこから来るか**の分解を主題にする。

判定軸は `52_eval2/10_game_score_mean`（ε=0.01）と `42_env/41_game_score_ge432_ema`。
Breakout の満点は **864**（2 画面 × 432、216 ブロック）。

**eval2 のセッション構成が腕ごとに違う。** btrfull は interval 1009 learn step / 10 エピソード、

**E'**（`@AtariImpalaX2SN12Pool6Flat`）は BTR の SN 被覆に厳密一致させた版である。
BTR は `ImpalaCNNBlock.conv`（stem 3 本）が素の `nn.Conv2d` で、`norm_func` が掛かるのは
`ImpalaCNNResidual.conv_0 / conv_1` だけなので **12/15**。本記録の E は **15/15** で SN している。
`AtariImpalaConv32` と `AtariImpalaConv32SN` の設定差は `weight_norm.mode = spectral` の 1 行だけで、
学習パラメータ数は E と完全に同一である。

`AtariPool6` = `MaxPool2d(kernel 2 / stride 2 / padding 1)`。11×11×64 = 7744 を 6×6×64 = 2304 にする。
**`AtariLinear512` の入力が 7744 → 2304 になり、そこだけで 3,965,440 → 1,180,160 パラメータ減る**（A → B/C）。

**B と C の学習パラメータ数は完全に同一**である。SN は `u` バッファしか足さないので、
checkpoint の `model_size` が 17,211,990 対 17,286,434 と 74,444 バイトだけ違う（online + target の 2 本ぶん）。

B の配線は `run_20260913-071609_tmp_wiring_btrtrunknosn` で解決させてあり、
**C との設定差分は `main_feature.structure` の 1 行（SN 接尾辞）だけ**である。
A との差分は `AtariPool6` の挿入と `train.num_envs` 128 → 64 の 2 行。

## 探索ブロック 01: BTR 公開実装との突き合わせ

### 探索観点

[2026-09-08](2026-09-08_replay-ratio-mechanism.md) 探索ブロック 10 で、BTR 公開実装は同じ再利用 4 回で
本構成の RR4 素を大きく上回った。BTR の NN構成（Pool6 + 融合 2304 + SN、共有トランク無し）を移植して
差が埋まるかを見る。

### BTR の eval ε は途中で切り替わる

BTR の `main.py` は eval の ε を **index 125 まで 0.01、以降 0** にする。
eval は 250,000 遷移ごとに 200 回なので、**切り替え点は exp 31.25M** である。
コード側のコメントはこれを速度対策としている（"agents get stuck in some games, causing evals to last a very long time"）。

したがって **31.25M 未満の窓だけが ε を揃えた比較**になる。

## 探索ブロック 07: 実時間

| 腕 | NN構成 | 総params | eval2 設定 | throughput | 実時間 |
|---|---|---|---|---|---|
| A RR4 素（envs128） | trunk512 | 4,914,080 | 1009 / 10ep | 1,744 | 7h57m / 50M |
| C btrtrunk | trunk512 + Pool6 + SN | 2,128,800 | 3906 / 100ep | 1,328 | 4h11m / 20M |

出ていて、実験機のドリフト（1 時間で最大 8%）と同程度だったためである。

|---|---|---|---|---|
| **15/15** | btrfull r2 / aainit | 1,406 / 1,377 | 4h02m / 4h01m | |
| **12/15** | sn12 | **1,488** | **3h44m** | **+5.8%** |
| **0/15** | btrnosn | 1,492 | 3h43m | +0.3% |

**stem conv 3 本を外すと 5.8% 速くなり、res block 12 本を外しても 0.3% しか変わらない。**
SN の実時間コストは実質すべて stem にある。

同日比較でも裏が取れている。2026-09-15 の `aainit`（15/15）1,377 対 `sn12`（12/15）1,488 で +8.1%、
`actor_approx` の実測コスト −2%（探索ブロック 13）を引いて約 6%。

SN 無しが 50M へ届くまでの総実時間は **10h04m**（3h44m + 6h20m）、btrfull は 14h34m だが、
eval2 の設定が違うので**この 4.5h 差を NN構成の差として読んではいけない**。

btrfull の 952 は eval2 の interval が他の 4 倍あることによる。NN構成の重さだけの値ではない。

**上表の数値はすべて eval 込みである。** eval が経過時間に占める割合は設定で 21% から 99.7% まで
動くので（[2026-09-15](2026-09-15_replay-lane-window.md) 探索ブロック 05）、

## 探索ブロック 08: `AtariPool6` の用量反応

### 探索観点

Pool6 が最大の寄与（+55.1）と分かったので、縮小率だけを振って内点があるかを見る。
btrtrunk 骨格（トランク 512 + SN）で測る。この骨格なら **Pool は `AtariLinear512` の入力だけを変え、
τ 融合次元は 512 に固定されたまま**なので 1 変数になる。

```
AtariPool6 : k2 s2 p1 -> floor((11+2-2)/2)+1 = 6
AtariPool4 : k3 s3 p1 -> floor((11+2-3)/3)+1 = 4
```

### 探索結果

| Pool | 空間 | Linear 入力 | 融合前params | eval2 12-15M | 18-20M | `≥432` 18-20M |
|---|---|---|---|---|---|---|
| 無し | 11×11 | 7,744 | 4,355,488 | 399.9 | 406.4 | 5.72% |
| **6×6** | 6×6 | 2,304 | 1,570,208 | 455.0 | 461.4 | 8.83% |
| **4×4** | 4×4 | 1,024 | **914,848** | **466.1** | **487.2** | **9.67%** |

**3 窓すべてで 4×4 が最良。** 18-20M の +25.8 は複製幅 6.7 の 3.9 倍、12-15M の +11.1 も外側。
6-9M でも 430.7 対 418.1 で同順。

**6×6 は内点ではない。** BTR の `AdaptiveMaxPool2d(6)` は本構成の RR4 では最適点を当てていない。
BTR 自身は Pool を「性能は下がるが計算量が決定的に下がる」と評価しているが、本構成では逆である。

**伸びは後半ほど大きい。** 12-15M で +11.1、18-20M で +25.8。飽和ではなく、
**4×4 のほうが立ち上がりが遅く後から伸びる**形である。

### 機序

`38_agent_loss/02_loss_ema` が容量と逆順に並ぶ。

| Pool | 融合前params | loss 12-15M | loss 18-20M | eval2 18-20M |
|---|---|---|---|---|
| 無し | 4,355,488 | **0.418** | **0.397** | 406.4 |
| 6×6 | 1,570,208 | 0.544 | 0.531 | 461.4 |
| 4×4 | 914,848 | **0.547** | **0.559** | **487.2** |

**削るほど replay バッチへの当てはまりが悪くなり、成績が上がる。**
[2026-09-08](2026-09-08_replay-ratio-mechanism.md) まとめ 2 の逆順がそのまま成立する。

ただし **6×6 → 4×4 の loss 差は 12-15M でほぼゼロ**（0.544 → 0.547）なのに成績は上がる。
18-20M では 0.531 → 0.559 と開く。`22_grad_norm_ema` は 4×4 が一貫して高い（18-20M で 3.336 対 3.108）。
**容量削減だけでは説明しきれていない。**

### 切り分けていない点

Pool は**容量削減**と**空間の別名化**を同時にやる。`Linear(7744→1024)` を挟んでから `Linear512` に
すれば params はほぼ同じだけ減るが別名化は起きないので、その対で分離できる。未測である。

**本番構成（btrfull）へ持ち込めるかも未測である。** btrfull はトランクが無く
`Flatten` の出力がそのまま融合次元になるため、Pool を変えると**空間容量と融合次元が同時に動く**。
しかも 2 つは逆を向いている（空間は小さいほど良い、融合次元は 512 → 2304 で +39.9）。
