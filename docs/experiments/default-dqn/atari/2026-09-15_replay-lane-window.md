# Atari Breakout: replay の lane 窓と eval コスト — 2026-09-15

対象 workspace: `atari-3rd`。ゲームは breakout 固定。すべて seed 1、`backend.@non-deterministic`。

基準は [2026-09-12](2026-09-12_btr-network-port.md) の btrfull
（`run.@v5_iqn_impala_x2 > run.@a5 > run.@a5_apex > run.@va_base` に
`run.@hard500 > run.@rr4 > run.@munch > run.@btrnet > run.@btrsn`）。

判定軸は `52_eval2/10_game_score_mean`（ε=0.01）と `42_env/41_game_score_ge432_ema`。
本記録では **ε=0 断面**（`run.@evalonly > run.@eval2only > run.@greedy_eval`、
学習停止・4 セッション × 100 エピソード = 400 エピソード）を主判定に使う窓が多い。
Breakout の満点は **864**。

起点は `num_envs` を 64 → 128 に上げた 50M Run で、**学習中 eval では差が出ないのに
ε=0 断面で −69.4 が出た**こと。本記録はその原因特定を主題にする。

## 現時点のまとめ

1. **保つべき不変量は `replay_capacity / num_envs`（以下 lane 窓）である。**
   `replay_capacity` 単独でも `num_envs` 単独でもない。lane 窓 16,384 の 2 点は ε=0 で
   **685.12 対 685.30**（差 0.18 = ε=0 の学習 Run 複製幅 18.7 の 1/100）。この 2 点は `num_envs` が
   2 倍違い、遷移の総寿命も 2 倍違う。lane 窓 8,192 だけが **615.73** で **−69.4**（複製幅の 3.7 倍。
   探索ブロック 02）。

2. **効き方は閾値的で、貪欲エピソード長との比で決まる。** ε=0 のエピソード長は 7,750〜8,327。
   lane 窓 8,192 は約 1 本ぶん、16,384 は約 2 本ぶん。**1 本ぶんでは壊れ、2 本ぶんで直る。**

2b. **制御変数は lane step で測った窓であって、更新数で測った量ではない。** ラベルを追う量を残すと
   lane 窓・完全同居時間（lane step）・lane 窓 / エピソード長の 3 つで、これらは代数的に同じものである。
   **更新数で測った量はどれも追わない** — 遷移の総寿命（16,384 / 16,384 / 32,768）も
   完全同居時間（8,634 / 884 / **17,268**）も、ラベルと一致しない。
   したがって **`n_step` 由来の「価値を逆行させる機会が多いほど良い」という筋はそのままでは成立しない**
   （その筋なら機会が 2 倍ある G2 が G1 を上回るはずだが一致する）。
   言えるのは **「lane 窓 / エピソード長が同じなら、更新を何回かけても着地点は同じ」**までで、
   **その比が何を通じて成績を決めるかは未測**である（探索ブロック 02）。

3. **この差は学習中 eval（ε=0.01）にはほとんど出ない。** 45-50M の差 −4.8 は複製幅 6.7 の内側で、
   ε=0 の −69.4 は **14 倍**。5 窓平均でも −4.7 で、窓ごとに符号が入れ替わる（探索ブロック 01）。

4. **ε=0 のブレ幅は 2 種類ある。** eval プロトコル自体（同一スナップショットを 2 回）は今回 **2.12 点**、
   `≥600` は完全一致。ただし [2026-09-01](2026-09-01_btr-feedback-arms.md) 探索ブロック 30 の 4 対では
   **9.5〜16.2 点**で、水準が上がるほど広い。**学習 Run どうしの複製幅は ε=0 で 18.7 点**（同記録）。
   ε=0.01 の 6.7 点より広く、**ε=0 の 1 対 1 比較はこの 18.7 を物差しにする**（探索ブロック 03）。

5. **20M の ε=0 断面は腕の判定に使えない。** 50M で −98.7 だった SN 軸が、20M では **+5.0** と
   符号も逆になる。**貪欲変換**（ε=0.01 → ε=0 の得）は SN 無しで 20M **+48.4** → 50M **+10.0** と潰れ、
   SN 有りでは **+55.5 → +82.2** と育つ。同一系統（20M Run をそのまま resume）での観測なので
   Run 間ばらつきではない（探索ブロック 04）。

6. **`replay_capacity` を上げると ε=0.01 は上がるが ε=0 は上がらない。** cap2M は 45-50M で **632.0**
   （lane 窓の等しい envs64/cap1M の 602.9 に対し **+29.1**）だが、ε=0 は 685.30 で同点。
   **685 が 50M での天井に見える**（探索ブロック 02）。

7. **eval の実時間コストは設定で桁が変わる。** `btreval_r1` を載せた RR1 100M Run は
   eval デューティ **99.7%**（307 セッション、1 本中央 108.5s、合計 8.94h / 経過 8.97h）。
   eval / train の env step 比は **1.76**（探索ブロック 05）。

8. **RR1 では env stepping が律速で、eval の 1 step は train の 1 step を 1:1 で奪う。**
   総 env step スループットは eval 設定が大きく違う 2 本でほぼ一致した（**6,568 対 6,402**、2.6% 差）。
   eval を完全に切ると train は **6,783 exp/s** まで戻る。

9. **`interval` を learn step で書くと eval コストは訓練とともに勝手に膨らむ。** エピソード長が
   3,500 → 4,400 と伸びるぶん、同じ間隔でも eval の env step 比が 26% 増える（探索ブロック 05）。

10. **エピソード長はゲーム間で 8 倍違い、Breakout だけ裾が極端に長い。** train p50 は qbert 662 に対し
    name_this_game 5,440。最大は Breakout だけが打ち切り上限 26,995 に達する（探索ブロック 06）。

## 探索ブロック 01: `num_envs` 128 の断面

### 探索観点

`num_envs` は `replay_ratio` と独立なので、RR4 を保ったまま 64 → 128 にしても
1 遷移あたりの学習回数は変わらない。実際に成績が動くかを 50M で測る。

### 探索結果

学習中 eval（ε=0.01）を、既存の envs64 複製 2 本（r1 / r2）の両方と並べる。

| 窓 | r1(64) | r2(64) | envs128 | e−r1 | e−r2 |
|---|---|---|---|---|---|
| 6-9M | 449.8 | 452.6 | 437.1 | −12.8 | −15.6 |
| 9-12M | 481.5 | 478.4 | 471.7 | −9.8 | −6.7 |
| 12-15M | 494.9 | 488.2 | 502.8 | **+7.8** | **+14.6** |
| 15-18M | 517.3 | 522.4 | 521.3 | **+4.0** | −1.0 |
| 18-20M | 541.8 | 537.3 | 525.8 | −15.9 | −11.5 |
| 45-50M | 602.9 | — | 598.1 | −4.8 | — |
| **平均（5 窓）** | | | | **−5.3** | **−4.0** |

**5 窓平均は −4.7 で複製幅 6.7 の内側、5 窓中 2 窓はプラス。** 学習中 eval では差が立たない。

ところが ε=0 断面では分かれる。

|---|---|---|---|---|---|

|---|---|---|---|
| envs64 | 602.9 | 685.1 | **+82.2** |
| envs128 | 598.1 | 615.7 | **+17.6** |

envs128 は同じ ε=0.01 水準に到達しているのに、**貪欲化で伸びない**。

### 実時間には差が無い

窓を揃え、eval 設定も揃えた対（envs64 r2 対 envs128、いずれも `btreval_r4`）。

| | 5-10M | 10-15M | 15-20M | 平均 |
|---|---|---|---|---|
| envs64 r2 | 1,451 | 1,377 | 1,143 | **1,324** |

btrfull envs64 50M の 14h34m（eval1+eval2 各 10ep）と envs128 50M の 10h43m（eval2 100ep）の差は

## 探索ブロック 02: lane 窓の確定

### 探索観点

`num_envs` を変えると、同じ `replay_capacity` でも **1 つの env（lane）あたりの履歴窓**が変わる。

```
遷移の総寿命 = replay_capacity × replay_ratio / batch = capacity / 64 更新   ← capacity だけで決まる
lane 窓      = replay_capacity / num_envs                                    ← 比で決まる
```

`num_envs` 128 は lane 窓を 8,192 step へ縮める。ε=0 のエピソード長 7,750 に対し**約 1 本ぶん**しかない。
`num_envs` を 128 に保ったまま `replay_capacity` を 2M にすれば lane 窓は 16,384 に戻る。
**lane 窓が効いているなら envs64/cap1M と一致するはず**で、総寿命（16,384 対 32,768 更新）と
`num_envs`（64 対 128）はどちらも 2 倍違うので、一致すればその 2 つは無関係と分かる。

### 探索結果

| ε=0 @50M | `num_envs` | `capacity` | **lane 窓** | 総寿命 | **score** | SEM | `≥432` | `≥600` | 長さ |
|---|---|---|---|---|---|---|---|---|---|
| envs64 cap1M | 64 | 1,048,576 | **16,384** | 16,384 | **685.12** | 9.30 | 0.82 | 0.62 | 7,750 |
| envs128 cap1M | 128 | 1,048,576 | **8,192** | 16,384 | 615.73 | 3.25 | 0.75 | 0.45 | 6,004 |
| **envs128 cap2M** | **128** | **2,097,152** | **16,384** | **32,768** | **685.30** | 6.48 | **0.82** | **0.64** | 8,327 |

```
1,048,576 / 64  = 16,384
2,097,152 / 128 = 16,384      ← 完全一致
1,048,576 / 128 =  8,192      ← ここだけ −69.4
```

**685.12 対 685.30、差 0.18 点。** ε=0 の学習 Run 複製幅 **18.7**（探索ブロック 03）の **1/100** で、
区別がつかない。`≥432` は 0.82 で完全一致、`≥600` は 0.62 対 0.64 で複製幅の内側。
**−69.4 は同じ物差しの 3.7 倍**である。

**`num_envs` 単独は無関係**（64 と 128 で同一）、**`capacity` 単独も無関係**（1M と 2M で同一）、
**比だけが効く**。

閾値的である。

| lane 窓 | 貪欲エピソード何本ぶん | ε=0 |
|---|---|---|
| 8,192 | 約 1 本 | 615.7 |
| 16,384 | 約 2 本 | 685.1 / 685.3 |

### 機序: 効いているのは lane step で測った窓で、更新数で測った量ではない

3 点はいくつもの量で違うので、**ε=0 のラベル（good / bad / good）を追う量だけを残す**形で絞れる。
`replay_ratio` 4 / `batch` 256 なので、1 lane step あたりの learner 更新数は `num_envs × 4 / 256`。

| 量 | G1(685.1) | B(615.7) | G2(685.3) | ラベル追従 |
|---|---|---|---|---|
| `num_envs` | 64 | 128 | 128 | × |
| `replay_capacity` | 1M | 1M | 2M | × |
| 1 lane step あたりの更新数 | 1.0 | 2.0 | 2.0 | × |
| 遷移の総寿命（更新） | 16,384 | 16,384 | 32,768 | × |
| **完全同居時間（更新）** | **8,634** | **884** | **17,268** | **×** |
| **lane 窓（lane step）** | **16,384** | **8,192** | **16,384** | **○** |
| **完全同居時間（lane step）** | **8,634** | **442** | **8,634** | **○** |
| **lane 窓 / 貪欲エピソード長** | **2.11** | **1.06** | **2.11** | **○** |

完全同居時間 = 長さ `L` のエピソードが頭から尻尾までバッファに載っている時間で、
lane step では `lane 窓 − L`、更新数では `(lane 窓 − L) × num_envs × rr / batch`。

**追従する 3 量は代数的に同じもの**（`L` を固定すれば lane 窓の一次式）なので、
**制御変数は lane 窓ひとつ**である。

### この結果が否定するもの

**「完全なエピソードが同居している更新数が多いほど良い」は否定された。**
G1 と G2 は同居時間が更新数で **8,634 対 17,268 と 2 倍違うのに ε=0 は 685.12 対 685.30 で一致**する。

これは `n_step` 由来の筋（`n_step=3` なので長さ `L` のエピソードの尻尾から頭へ価値を伝えるには
`L/3` 回ぶんの逆行が要り、その間エピソードが同居していないと連鎖が切れる）を、
**そのままの形では支持しない**。その筋なら逆行の機会が 2 倍ある G2 が G1 を上回るはずである。

**遷移の総寿命も否定される。** G1 と B は総寿命が 16,384 更新で等しいのに −69.4 離れ、
G2 は G1 の 2 倍なのに一致する。

言えるのは **「`W/L` が同じなら、更新を何回かけても着地点は同じ」**までである。
G1 と G2 は `W/L` が 2.11 で等しく更新数が 2 倍違うのに ε=0 が一致し、
ε=0.01 の到達点が 602.9 と 632.0 で 29.1 違っても ε=0 は同じ 685 へ着く。

### 追従する量を式にする

`W` = lane 窓、`L` = その lane のエピソード長とすると、
**W の窓に頭から尻尾まで丸ごと載っているエピソードに属する遷移の割合**は、
位相一様・`L` 固定の近似で `1 − L/W` になる。**`W/L` だけの関数**である。

| `L` の取り方 | G1 | B | G2 | 良/悪 |
|---|---|---|---|---|
| train 全 lane 平均 2,100 | 87.2% | 74.4% | 87.2% | 1.17 倍 |
| ε=0.01 の lane 4,555 | 72.2% | 44.4% | 72.2% | 1.63 倍 |
| 貪欲 7,750 | 52.7% | **5.4%** | 52.7% | **9.77 倍** |

**バッファに入っているのは train 側（ε ラダー）のエピソードで、貪欲エピソードではない。**
ラダーの下端（ε ≤ 0.02 = 全 lane の 18.8%）だけが貪欲に近い長さになるので、
**閾値をまたぐのはその帯域だけ**である。高 ε の lane は `W/L` が 4〜8 あって無傷。
これは「ε=0 にだけ出る」ことと向きが合うが、帯域別の測定はしていない。

### 何が未測か

**「`W/L` が成績を決める」ことは 3 点で示せたが、「`W/L` が何を通じて成績を決めるか」は測れていない。**
上の `1 − L/W` は `W/L` の単調関数のひとつにすぎず、同じく追従する読みは他にもある
（lane 自身の履歴をどこまで遡れるか、lane 内の年齢の広がり、など）。**3 点ではこれらを区別できない。**

なお **「完全なエピソードが載っていること」自体が要件だとは言いにくい。**
`n_step=3` のブートストラップは 1 回の更新に完全なエピソードを要求しないし、
実際に更新数で測った同居時間は追従しなかった（前節）。

閾値がなぜ `W/L` ≈ 1〜2 に来るのか、なぜ ε=0 にだけ出て ε=0.01 には出ないのかも未測である。

### `capacity` を上げると ε=0.01 だけ上がる

lane 窓が同じ 2 点でも、学習中 eval は一致しない。

| eval2 (ε=0.01) | 6-9M | 9-12M | 12-15M | 15-18M | 18-20M | 25-30M | 35-40M | 25-48M | 45-50M |
|---|---|---|---|---|---|---|---|---|---|
| envs64 cap1M | 449.8 | 481.5 | 494.9 | 517.3 | 541.8 | 577.2 | 586.8 | 589.7 | 602.9 |

`≥432`（45-50M）は 17.31% / 16.29% / **17.68%**。

**同じ `num_envs` で `capacity` だけ動かした対（cap1M → cap2M）は 6 窓すべてプラスで平均 +19.2**、
6 窓中 5 窓が複製幅 6.7 の外。45-50M では envs64 cap1M に対しても **+29.1**。

にもかかわらず ε=0 は同点なので、**貪欲変換が縮んでいる**。

## 探索ブロック 03: ε=0 eval プロトコルの複製幅

### 探索観点

ε=0 断面の数字はすべて n=1 で、物差しが無かった。
**同一スナップショットを 2 回評価**すれば、eval プロトコル自体のばらつきが測れる。

この対は 2026-09-15 に bat の取り違えで偶然生じたもので、設定・スナップショットとも完全に同一である。

### 探索結果

| btrnosn 50M の同一 `agent_close.anet` | score | SEM | `≥432` | `≥600` | 長さ |
|---|---|---|---|---|---|
| `run_20260914-011415` | 586.45 | 7.10 | 0.70 | **0.41** | 6,792 |
| `run_20260915-100113` | 584.33 | 14.96 | 0.71 | **0.41** | 7,471 |

この対では **2.12 点**。`≥600` は完全一致、`≥432` は 0.01。

## 探索ブロック 04: ε=0 断面の予算依存性

### 探索観点

ε=0 断面は 50M でしか取っていなかった。20M のスナップショットが 4 本揃ったので、
**同じ軸を 20M で測ると何が見えるか**を確認する。SN 軸は 50M で −98.7 と分かっているので、
これが再現するかで 20M の感度が分かる。

### 探索結果

| 20M ε=0（400 エピソード） | score | SEM | `≥432` | `≥600` | 長さ |
|---|---|---|---|---|---|
| btrfull 15/15（基準） | **592.80** | 6.44 | 0.70 | 0.40 | 5,457 |
| SN 12/15 | 576.20 | 11.78 | 0.64 | 0.39 | 5,227 |
| `actor_approx` | 570.73 | 5.36 | 0.58 | 0.36 | 6,241 |
| **btrnosn 0/15** | **597.81** | 6.85 | 0.70 | 0.43 | 6,228 |

**SN を全部外した腕が基準をわずかに上回る（+5.0）。** 50M では同じ軸が **−98.7** である。
**20M の ε=0 断面は SN 軸に対して無感度**であり、この予算では腕の判定に使えない。

学習 Run 複製幅 **18.7**（探索ブロック 03）を当てると、基準に対する差は
SN 12/15 −16.6・`actor_approx` −22.1・0/15 +5.0 で、**内側 2 件・境界上 1 件**。
4 腕とも判定できていない。

### 貪欲変換が訓練とともに逆向きに動く

btrnosn は 20M Run をそのまま resume して 50M にしたので**同一系統**であり、Run 間ばらつきではない。

| | ε=0.01 | ε=0 | 貪欲変換 |
|---|---|---|---|
| btrfull @20M | 537.3 | 592.8 | **+55.5** |
| btrfull @50M | 602.9 | **685.1** | **+82.2** |
| btrnosn @20M | 549.4 | **597.8** | **+48.4** |
| btrnosn @50M | 576.4 | 586.4 | **+10.0** |

**btrnosn は ε=0.01 が伸び続けている（549.4 → 576.4）のに ε=0 が下がる（597.8 → 586.4）。**
貪欲変換が +48.4 から +10.0 へ潰れる。btrfull は逆に +55.5 → +82.2 と育つ。

SN の役割は「ε=0 を上げる」ではなく、**長い訓練で貪欲変換が潰れるのを防ぐ**ことである。
20M ではまだ潰れていないので差が出ない。

## 探索ブロック 05: eval の実時間コスト

### 探索観点

設定差は 2 点のみ。`run.@rfit`（`46_agent_replay_fit` 13 本、`interval:503` learn step、
probe batch 1024）の追加と、eval の変更（eval1 OFF、eval2 を 10 → **100 エピソード**）。

### 総 env step スループットは保存される

| | train | eval | **合計** | eval 比率 |
|---|---|---|---|---|
| mu1 50M（eval1+eval2 各 10ep） | 5,027 | 1,375 | **6,402 step/s** | 21% |
| rr1 100M（eval2 100ep） | 2,385 | 4,183 | **6,568 step/s** | **64%** |
| **tp_rr1（eval OFF）** | **6,783** | 0 | **6,783 step/s** | 0% |

**2.6% しか違わない。** RR1 では **env stepping が律速**で、eval の 1 step は train の 1 step を
**1:1 で奪う**。eval を完全に切ると 6,783 exp/s（10M を 23 分）。

### 間隔を learn step で書くとコストが訓練とともに膨らむ

```
eval env step / train env step
  mu1        :  20ep × 3,500 / 256,000 = 0.27
  btreval_r1 : 100ep × 4,400 / 250,112 = 1.76
```

`btreval_r1` / `btreval_r4` は **env step 換算で間隔が揃うように**作られている
（977 × 256 = 250,112、3906 × 64 = 249,984）。設計としては正しいが、
**eval コストはエピソード長に比例する**ので、訓練が進むほど比率が上がる。
本 Run ではエピソード長が 3,500 → 4,400 と 26% 伸びており、そのぶん比率も上がっている。

実時間に落とすと RR に強く依存する。

| | 間隔（env step） | 実効速度 | 間隔（実時間） | 1 セッション | デューティ |
|---|---|---|---|---|---|
| RR4 + btrfull | 250k | ~1,400 exp/s | 178s | ~108s | ~60% |
| **RR1 + 旧 net** | 250k | **~6,000 exp/s** | **42s** | **108s** | **飽和** |

### eval 単独でも lane が細いと遅い

`run.@evalonly` は `eval_batch_size = 16` / `num_envs = 1` で走る。
`run_20260915-113611_ev_btrfull_envs128_50m` は 4 セッション × 100 エピソード × 6,004 step =
240 万 env step を約 727s で処理しており **約 3,300 step/s**。学習が一切走っていないのに
上表の 6,783 に届かない。env のワーカースレッド数は work item 数（= lane 数）で頭打ちになる
（`EnvConfig::Resolve(worker_threads, work_items)`、`env.worker_threads = -1` は AUTO）。
