## 1. 目的と問題

LLM（画像を読めるもの）がゲームの常識で行動を選ぶ Actor を作り、KFM のボス討伐のように「何をすべきか」の知識が足りない場面に事前知識を持ち込む。形は 2 つある。

- **パターン A（単独 Agent）**: LLM だけで遊ぶ Agent。学習はしない。事前知識だけでどこまで行けるか（ボスを倒せるか、出口まで行けるか）を測り、そのプレイをデモとして残す。
- **パターン B（DQN ハイブリッド）**: 学習するのは DQN のまま。LLM の行動で得た経験（オフラインのデモ、または一部の lane のオンラインの行動）を、消えない別枠に入れて混ぜる。DQN は報酬で学ぶので、LLM の悪手は価値の低いデータになるだけで、先生を超えられる。LLM の知識を、速くて軽い専用のネットワークへ移すことにもなる。

### ゴール

- パターン A: KFM を LLM だけで遊び、評価と同じ指標（生スコア、面クリア・撃破の RAM メトリクス）と、呼び出しの回数・待ち時間・費用を記録できる。そのプレイを、パターン B が読めるデモとして保存できる。
- パターン B: デモ（段階 B1 はオフライン、段階 B2 はオンライン）を、FIFO で消えない別枠から固定の比率で学習バッチへ混ぜられる。既定は無効で、無効のときは今と同じ学習系列になる。

### 非ゴール

- LLM そのものの学習や fine-tuning。
- LLM の好みや提案を報酬にすること（Motif・ELLM 型）。サーベイでは Atari での効果が条件付きなので、必要なら別 PRD にする。
- 実機や実時間の制御ループに LLM を入れること（StampFly の路線では、LLM の知識は蒸留した軽いネットワークで持ち込む）。
- ゲームの仕様を変えること（§2.4）。
- 複数マシンへの分散（Ape-X 型）。段階 B2 で 1 台では足りないと分かったときに起こす。

## 2. 背景: KFM のボス討伐

### 2.1 ゲームの仕組み（2026-09-25 のエミュレータ調査）

- ボスは距離で出る。左へ歩くだけで約 3,000 フレーム（750 step）でボスの位置に着く。雑魚は動いているときに出てくる。
- ボス戦は約 340 フレーム（85 step）。11 発当てると倒せる。当てても点は入らず、点は撃破のときの 2,000 点だけ。
- 撃破後も雑魚は出続け、攻撃しながら約 1,000 フレーム（250 step）歩くと出口で残りの体力（最大 39）とタイマー（最大 31）が得点に換算される。報酬クリップでは換算の間の毎 step が +1（最大約 70 回）、生の得点では最大約 26,000 点。
- やられると面の最初に戻り、ボスの体力も元に戻る。
- 学習の構成は 84×84 の灰色・4 フレーム飛ばし・4 枚重ね、報酬クリップ、sticky action 0.25、γ = 0.997、n-step 3（実時間優先）。

### 2.2 学習の結果

| 構成 | 本数 | ボス行き（面クリア） | 要点 |
| --- | --- | --- | --- |
| 実時間優先（クリップあり） | 3 seed（100M） | seed 3 だけ | seed 3（`run_20260925-130017_atari_kfm_rr1_100m_seed3`）は評価で 5〜10M に面クリア 55%、15M 以降ほぼ 100%。seed 1・2 は一度も使わない |
| 同上（RTX 4060 機の複製） | seed 2 × 2 本（176M・100M） | なし | 学習中のボス命中 0〜1.6%、撃破 0 |
| 報酬クリップを外して 1/200 倍 | 2 seed（50M） | なし | 命中は 2〜3.5% に増えたが、撃破は命中の約 1 割で定着しない |
| ライフで区切る（`episodic_life`） | 1 seed（50M） | なし | ボス命中が最初から 0%。死なずに稼ぐ方へ早く固まる |
| sticky 0・低い ε・クリップ外し・PER α 0.6、＋n-step 10、＋γ 0.999 | 4 本（30M） | なし | 5M で 4 万点前後の稼ぎに固まり、ボス命中 0% |
| 同上 ＋ UQE | 1 本（30M） | なし | 5〜10M に学習中のゲームの 14.6% でボスに挑んだが、撃破は命中の 2%。10M 以降は挑まない |

### 2.3 分析の結論（2026-10-16〜17）

- **観測は足りる。** seed 3 は安定して倒していたので、勝つための情報は今の観測に入っている。
- **報酬では途中経過が見えない。** 当て 1 発は 0 点、撃破はクリップ後 +1 で雑魚と同じ。成功を区別できるのは出口の換算だけ。
- **2 つの戦略がほぼ同価値。** クリップ後の 1 step あたりの報酬は、ボス行きの seed 3 が 0.042、1 面の稼ぎが 0.048。どちらに落ちるかは序盤の経験で決まる。
- **珍しい成功が学習に残らない。** 1 遷移が寿命中に引かれる回数の期待値は約 1.0 で、4 件に 1 件は一度も引かれずに消える（PER の `per_alpha` 0.2）。
- **人間との差。** 人間がボスを倒せるのは、事前知識（「先へ進みボスを倒すのが目的」「バーが減る＝効いている」「攻撃を見てよけ、隙に打つ」）、内的な動機（好奇心・達成感・稼ぎへの飽き・上達の見込み）、成功の記憶があるから。本 PRD は事前知識を LLM から持ち込む。内的な動機は [999_intrinsic_reward_novelty_10prd.md](999_intrinsic_reward_novelty_10prd.md)、成功の記憶は本 PRD の別枠（§4 の B）が受け持つ。
- **LLM の役割の見立て。** DQN はボスに 11 発当てる腕を一度は身につけている（seed 3）。欠けているのは「出口まで行けば大きい」「ボスは倒すもの」という知識で、LLM は 1 秒に 15 回の細かい操作より、何をすべきかの判断で効くと見込む。

### 2.4 ユーザーの裁定（2026-10-16）

ボスの手前から始めること（状態の保存と復元）と、ボス体力の減りへの報酬は「ゲーム仕様を別にするのはやり過ぎ」で採らない。sticky action を切るのは本来のゲームに戻すので可。エージェント側の汎用の工夫は歓迎。LLM の事前知識はエージェント側の知識であり、ゲームの仕様の変更ではない。

## 3. 現状（2026-10-18 に確認したこと）

- anet の実行系（core・runner）に LLM や HTTP の呼び出しは無い（LLM を使うのは CI のレビューだけ）。
- Train の 1 step は `actor_->MakeAction(step_counts_, state_)` → `env_->Step` → `BatchExperience` → `learner_->UpdateFromBatch` の直線で、全 lane を一度に進める（[trainer.cpp](../../core/anet-core/src/trainer.cpp)）。1 つの lane だけ遅い Actor を待たせると、全 lane が止まる。
- Actor は Agent の Actor 設定カタログ（`<AgentPrefix>.actor.[key]`）から作られ、Runner は Actor キー（`run.train.actor` / `run.eval.[tag].actor`）で選ぶ。
- 強制行動の口は Eval 側にしか無い。Train 側の強制行動は [999_input_target_train_forced_action](999_input_target_train_forced_action_10prd.md) が「`MakeAction` の入力（lane mask と行動）」として計画している（決定点を 1 つにし、Actor の出力と実行した行動を常に一致させる）。人間の操作が最初の利用者で、LLM はその 2 番目の利用者になる。
- Atari の env は、表示用に元の RGB 画面（210×160）を保持できる（`AtariEnv.retain_rgb_frame`、既定 true。[AtariEnv.cpp](../../core/envs/atari1/src/AtariEnv.cpp) の `rgb_frame`）。LLM に渡す画面はここから取れる。行動の一覧は ALE の最小行動集合（`getMinimalActionSet`）。
- 実時間優先の学習は RTX 4060 機で毎秒約 1,900 遷移、128 lane なので 1 lane あたり毎秒約 15 step で、ゲームの実時間（60 fps ÷ 4 = 15 step/s）とほぼ同じ。LLM の 1 回の呼び出しは、1 step の間隔（約 67 ms）より桁で遅いと見込む（見込み。§8 で測る）。
- replay は 1 つの FIFO で、デモを消さずに残す別枠は無い。PER では、押し出された遷移は戻せない。
- Munchausen の log π 項は、方策が選ばない行動（デモの行動）を罰する向きに働く。ただし clip −1 で、1 step あたり −0.027（α 0.9 × τ 0.03）が下限。
- ε-greedy のランダムな行動は、全行動から一様に選ぶ（[dqn_based_agent.cpp](../../core/anet-core/src/dqn_based_agent.cpp) の `MakeEpsilonGreedyAction`）。spatial exploration では lane ごとに ε が決まっている。
- サーベイ（[LLM の事前知識で RL の探索と報酬を補助する手法](../../reports/llm_prior_knowledge_rl_survey_2026-10-18.md)、2026-10-18）の要点:
  - Atari での正の実証はあるが、ゲーム・報酬・観測の条件付きである。KFM のボス攻略や qbert の 8 面到達を直接改善した実証は見つからなかった（同 §9）。
  - step ごとに大きなモデルを呼ばないための実証済みの設計は、オフラインでの蒸留、応答のキャッシュ、エピソード単位の更新、生成したコードへの移行の 4 つ（同 §4・§9）。
  - LLM-Explorer は、次のエピソード群で試す行動の分布を LLM が作り、ε 探索の一様分布をそれに置き換える。呼び出しはエピソード単位で、Qbert 500k step を GPT-4o mini で約 1.3 ドル・約 10 時間と報告している（同 §1・§3.3・§4。金額は論文当時の値）。
  - 物体の認識や説明の正しさと、望む出来事の達成は別に確かめる必要がある。報酬モデルの値が高くても本来の成功と一致しない例がある（同 §8）。

## 4. 提案の骨子

### パターン A: 単独 Agent（LLM だけで遊ぶ）

1. `LLMAgent`（学習しない Agent）を作る。現在の画面（RGB）、直近の数枚、行動の一覧、短い指示文を LLM に渡し、行動を受け取る。
2. 呼び出しを減らすため、LLM は「行動と、それを続ける step 数」を返し、その間は呼ばない（既定: 最大 16 step）。
3. 学習しないので、env を LLM の応答まで待たせてよい。評価用の Runner（少数 lane）で回す。
4. 記録: 評価と同じ episode の trace（生スコア、面クリア・撃破・命中の RAM メトリクス）、呼び出しの回数・待ち時間・費用、LLM の応答の全文。
5. プレイ（観測・行動・報酬・終端）を、パターン B が読めるデモのファイルとして保存する。

パターン A だけで、事前知識だけで KFM のボスを倒せるか、出口まで行けるかが分かる。倒せないなら、パターン B の先生としての価値も低いと判断できる。

### パターン B: DQN ハイブリッド

段階 B0（LLM が ε 探索の行動分布を決める。LLM-Explorer 型）:

1. ε-greedy でランダムな行動を選ぶとき、全行動の一様分布の代わりに、LLM が決めた行動の分布から選ぶ。greedy の行動と ε の値（spatial のラダーを含む）は今のまま変えない。
2. LLM はエピソード単位（既定: 32 ゲームごと）に呼ぶ。直近のゲームの要約（生スコア、ゲームの長さ、画面の数枚）と行動の一覧を渡し、次に試す行動の分布を受け取る。学習スレッドは待たず、新しい分布が届くまでは前の分布（最初は一様）を使う。
3. 行動を決めるのは Actor のままなので、Actor の出力と実行した行動は一致し、強制行動の入力を必要としない。

段階 B0 は、ランダムな行動の中身を「ゲームの常識に沿った試し方」に替えるだけで、呼び出しの費用が最も小さい。KFM では、ランダムな行動が「左へ進み続ける」「攻撃を混ぜる」に寄れば、ボスに触れる回数が増えると見込む。

段階 B1（オフラインのデモ）:

1. パターン A で保存したデモ（または人間のプレイ）を、学習の開始時に「デモ用の別枠」へ読み込む。別枠は FIFO で消えない。
2. 学習バッチの一定の割合（既定 1/8）をデモの別枠から引き、残りを通常の replay から引く（R2D3 型）。
3. 任意で、デモの遷移に対して「デモの行動の Q が他の行動より一定以上大きい」ことを求める損失（DQfD の large margin loss）を足す。重みは学習とともに下げる。
4. Munchausen の項は、デモの遷移では外せるようにする（既定は外さない。−0.027 が下限で小さいため）。

段階 B2（オンラインの LLM lane）:

1. 一部の lane（既定 128 lane 中 4）を LLM lane とし、その lane の行動を LLM が決める。経路は Train 側の強制行動（`MakeAction` の入力の lane mask と行動）で、Actor の出力と実行した行動が一致する。
2. LLM は学習スレッドと別に非同期で動き、lane ごとの「最新の提案」の枠へ書き込む。提案が無い、または古い（有効 step 数を過ぎた）ときは、その lane も DQN の方策で動く。学習スレッドは LLM を待たない。
3. LLM lane の遷移は通常の replay に入り、あわせてデモの別枠にも入る。

段階 B0 は他の段階に依存しない。B1 は段階 A の成果物だけで回せる。B2 は強制行動の入力（観測パイプライン PRD → 999 の Train 側強制行動）ができてから着手する。どの段階で止めても、無効の既定では今と同じに動く。

## 5. User Stories

1. 研究者として、LLM の事前知識だけで KFM のボスを倒せるかを、評価と同じ指標で測りたい。
2. 研究者として、LLM のプレイをデモとして保存し、DQN の学習に消えない形で混ぜたい。
3. 研究者として、DQN が先生（LLM）の点数を超えるかを確かめたい。
4. 研究者として、LLM の待ち時間で学習のループを止めずに、一部の lane だけ LLM に任せたい。
5. 研究者として、LLM の呼び出しの回数と費用を Run ごとに把握し、上限で止めたい。

## 6. 作らないもの・先送り

| 項目 | 裁定 | 理由と再開条件 |
| --- | --- | --- |
| LLM の好みや提案を報酬にする（Motif・ELLM 型） | 先送り | サーベイでは、Motif は NetHack、ELLM は Crafter などでの評価で、Atari での効果量としては扱えない。良い文章上の判断でも最終目標の達成は保証されない（報酬ハックの例がある）。パターン A で LLM の判断が当てになると分かってから、別 PRD にする |
| RAM の値を文章にして LLM に渡す | 診断用に限る | RAM はメトリクスとして読むだけという方針（§2.4）。画面から読めない時に、LLM の判断の上限を測る比較としてだけ使う |
| 複数マシンへの分散（Ape-X 型） | 先送り | 段階 B2 で、1 台の LLM の呼び出しの速さが足りないと分かったときに起こす |
| デモの別枠の優先度付き抽選 | 先送り | まず固定比率の一様抽選で効くかを見る |
| LLM の fine-tuning、行動を直接出す専用モデルの学習 | 対象外 | 蒸留の先は DQN そのもの |

## 7. 背景の補足（デモの別枠は人間デモと共通）

デモの別枠と、別枠から混ぜて引く仕組みは、人間のプレイを学習に使う路線（[999_input_target_train_forced_action](999_input_target_train_forced_action_10prd.md)）とも共通の部品になる。データの出どころ（LLM か人間か）に依らない形で作る。

## 8. 決めること（詳細設計で詰める）

暫定の既定を置いた。グリルで確定する。

| # | 決めること | 暫定の既定 |
| --- | --- | --- |
| 1 | LLM の提供元とモデル | 画像入力に対応した API のモデル（Anthropic の Claude 系を第一候補）か、ローカルの VLM か。基準は 1 回の待ち時間、費用、画像の読み取りの正確さ。パターン A で 2〜3 個を比べる |
| 2 | API キー | 環境変数で渡し、設定ファイル・Run の config dump・ログに出さない。キーが無いのに LLM を有効にしたら、構築時に fail-fast |
| 3 | LLM に渡す状態 | RGB の画面（直近 2〜4 枚、縮小して送る）。RAM の文章化は §6 のとおり診断用だけ |
| 4 | 指示文に入れる事前知識の範囲 | ゲーム名、行動の一覧、「高い点を取る」という目的だけを既定にする。説明書の要約を足す腕は比較用に持つ（LLM が元から知っている知識と、渡した知識を分けて測る） |
| 5 | 応答の形 | 行動名と続ける step 数（1〜16）の JSON。形が崩れた応答は NOOP にせず、エラーとして数え、直前の行動を続ける回数の上限を設ける |
| 6 | 呼び出しの上限 | Run ごとの最大呼び出し回数と最大費用。超えたらパターン A は Run を終える、B2 は LLM lane を DQN に戻す |
| 7 | 再現性 | LLM の応答は同じ入力でも変わる。応答の全文を Run に保存し、保存した応答を使って同じプレイを再生できるようにする |
| 8 | デモのファイルの形 | 観測（84×84 の 4 枚重ねを作れる生の画面）・行動・報酬・終端を、エピソード単位で保存する。replay の直列化を流用するか、別形式にするか |
| 9 | デモの混合比 | 学習バッチの 1/8（R2D3 の既定に近い値）。設定キーは `DefaultDQNAgent.demo.batch_fraction`（0 以上 1 未満、範囲外は fail-fast） |
| 10 | large margin loss | 既定は無効。有効時の margin 0.8、重みは 10M かけて 0 へ（DQfD の値を出発点にする） |
| 11 | LLM lane の数と提案の有効期間 | 128 lane 中 4、提案は 32 step まで有効 |
| 12 | 指標の tag | 群番号 57（`57_agent_llm/...`）。例 `57_agent_llm/01_call_latency_ms`、`57_agent_llm/11_demo_sample_ratio`。40 文字以内 |

| 15 | 段階 B0 の分布の単位 | 全 lane で 1 つの分布（既定）か、lane の組ごとか。spatial のラダーで ε の高い lane だけに使う腕を比較用に持つ |

## 9. 成功の測り方と受入の目安

成功の測り方:

- パターン A: KFM の 100 エピソードで、面クリア率・撃破率・生スコアと、1 エピソードあたりの呼び出し回数・費用を記録する。ボスに挑む率と撃破 ÷ 命中が、DQN（命中 0〜14.6%、撃破 ÷ 命中 2〜10%）と比べてどうかを見る。
- 段階 B0: 実時間優先 30M（sticky 0、2 seed）で、学習中のボス命中が一様の ε より増え、10M 以降も続く。呼び出しの回数と費用が Run あたりで記録され、学習の速さが B0 なしと測定のぶれの範囲で同じ。
- 段階 B1: デモを混ぜた DQN（実時間優先 30M、sticky 0、2 seed）で、学習中のボス命中が 10M 以降も続き、撃破 ÷ 命中が上がる。基準では 6 本に 1 本しかボス行きに入らないので、命中と勝率の推移を主に見る。DQN の評価の点数が先生（パターン A）を超えるかも見る。
- 段階 B2: 学習のループの速さが、LLM lane なしの場合と測定のぶれの範囲で同じ（LLM を待っていない）。

受入の目安（詳細はグリルで確定する）:

1. LLM を無効にした既定で、本機能の前後の同 seed・決定的モードの短い Run の metrics checksum が一致する。
2. テストでは実際の LLM を呼ばない。決まった応答を返す偽物の LLM で、パターン A の Run が最後まで回り、デモのファイルができる。
3. デモの別枠の単体テスト: 通常の replay が何周しても別枠の遷移は消えず、学習バッチの中のデモの割合が設定どおり（許容幅つき）になる。
4. §8 の 2・5・9 の不正値や欠落で、構築時に設定キーと値を示して止まる。応答の形の崩れは数えられ、Run は止まらない。
5. 段階 B2: 偽物の LLM に大きな遅延を入れても、学習の step が止まらない。

## 10. 依存と順序

1. サーベイ（[LLM の事前知識で RL の探索と報酬を補助する手法のサーベイ](../../reports/llm_prior_knowledge_rl_survey_2026-10-18.md)）は実施済み。グリルの前に §3 の要点を読む。
2. パターン A と段階 B0 は独立に進められる。B0 は呼び出しが最も少なく、Agent の改修も ε のランダム行動の分布だけなので、最初の一歩の候補になる。その後に段階 B1 → 段階 B2。A・B0・B1 に実装上の依存は無い。B2 は Train 側の強制行動の入力（観測パイプライン PRD → [999_input_target_train_forced_action](999_input_target_train_forced_action_10prd.md)）に依存する。
3. デモの別枠は、人間のプレイを学習に使う路線と共有する。どちらが先に作っても、もう一方はそれを使う。
