# PRD115: 画像メモリの所有権とDropMergeのNOOP判定の修正

> 2026-11-04 起票。起点は画像メモリの所有権とDirectモードのNOOP判定についての2件のissue。ユーザーが両方を解消する1本のPRDのゴール・範囲と作成計画を承認した。

## 1. 問題とゴール

### 1.1 問題

画像生成では、メモリを確保する方法と、画像を破棄するときの解放方法が合っていない。DropMergeでは、行動モードごとのNOOPの意味と、NOOPへの罰の判定が合っていない。どちらも既存の責務の中で直せる不具合である。

題材は[画像メモリの課題](../management/issues/issue-20261103-dd8058.md)と[Directモードの課題](../management/issues/issue-20261103-be4cd5.md)。PRDの作成・レビュー完了と、不具合の実装・受入完了は区別する。今回は前者までを行う。

### 1.2 ゴール

- G1: 題材のissueがすべて片付く修正契約と受入条件を定める。
- G2: 既存の画像の寸法・全画素・画像種別を保ち、安全に画像を生成・破棄できるようにする。
- G3: DropMergeの4行動モードで、選択した命令の意味に一致するNOOPへの罰を、1回のEnv Stepにつき正しく適用する。
- G4: 不具合の再発を、画像の生成・破棄と、同条件のEnvの報酬差から検出できるようにする。

### 1.3 非ゴールと別の関心

| 今回扱わない案 | 理由と再開する条件 |
|---|---|
| HeatMap派生の描画処理を統合する構造整理 | 別の関心である。2件を直すための技術的な制約ではなく、描画の重複を整理する変更を別途選んだときに扱う |
| DropMergeの罰の値・報酬設計・行動集合の変更 | 別の関心である。NOOPの意味を既存の行動モードにそろえるのが本件の目的であり、学習上の報酬設計を見直す実験を選んだときに扱う |
| すべての画像処理の入力検証や確保方法を一括で変更する案 | 別の関心である。画像の4経路の修正と、そこで必要な確保失敗の検出に範囲を限る。ほかの具体的な不具合を修正対象に選んだときに広げる |
| 長期学習による成績比較 | 学習性能の仮説を検証するPRDではない。G2・G3は固定画像と固定seed・同行動列で判定できる。学習上の効果を研究するときは別の実験として扱う |

## 2. 現行コードで確認した事実

以下は2026-11-04のコード読みであり、実行による再現や修正後の合格を記録したものではない。

### 2.1 画像生成の責務と呼び出し経路

画像Observerが学習や訓練のイベントを受け、画像をMetricsLoggerへ渡す。例えば `TimeHistogramObserver::OnLearn` は [observers.cpp](../../core/anet-core/src/observers.cpp) の140〜170行、`SweepedHeatMapObserver::OnLearn` は392〜418行である。`MetricsLogger::Log` の [metrics_logger.cpp](../../core/anet-core/src/metrics_logger.cpp) の725〜732行から、`ImageSource::Render` の [image.cpp](../../core/anet-core/src/image.cpp) の18〜29行を通り、各 `RenderRaw()` に至る。保存経路以外の画像取得も同じ描画口を使う。

[heat_map.cpp](../../core/anet-core/src/heat_map.cpp) の416・502・561・819行は、それぞれTimeHeatMapの空画像・通常画像、Histgram、SweepedHeatMapで、`new[]`した画像領域を `wxImage::SetData` へ渡している。TimeHistogramも同ファイル756行でTimeHeatMapの描画を利用する。基底のHeatMapの195・318行の確保はすでに `malloc` であり、同じ不一致には当たらない。

利用中のwxWidgets 3.3.3の `src/common/image.cpp` の125〜130行では、画像が所有する領域を破棄時に `free` する。同ライブラリの `interface/wx/image.h` の1791〜1802行も、SetDataへ所有権を渡す領域に `malloc` を要求している。公開の一次資料は [wxWidgets 3.3.3の画像仕様](https://github.com/wxWidgets/wxWidgets/blob/v3.3.3/interface/wx/image.h) と [画像実装](https://github.com/wxWidgets/wxWidgets/blob/v3.3.3/src/common/image.cpp) にある。通常の描画が成功しても、解放方法の一致を証明したことにはならない。

### 2.2 DropMergeの行動と報酬

[DropMergeEnv.cpp](../../core/envs/dropmerge1/src/DropMergeEnv.cpp) の1004行からの `Step` は、1017〜1029行でモード別にDROPとNOOPを判定する。`direct`のすべての有効行動はDROPで、行動0は列0を選ぶ。対して1261〜1264行のNOOPへの罰は、生の行動番号が0かどうかだけで加算している。

同ファイル653〜690行の `processAction` は、直接指定モードと移動モードを分ける。移動モードで `noop_override=true` なら、選択されたNOOPを中央方向への移動へ変換するが、呼び出し元が受けた命令の意味は変えていない。また、DROPは落下中などに実行されないことがある。

[DropMergeEnv.hpp](../../core/envs/dropmerge1/src/DropMergeEnv.hpp) の102行の `noop_penalty` は既定が `-0.001`、[DropMerge.txt](../../apps/runner/config/DropMerge.txt) の1667行は `0.0`。したがってDirectモードの誤加算は、非ゼロの罰を使うときに報酬差として現れる。罰は最終的にStep報酬とエピソード累積報酬へ含まれるが、ゲームの生スコアを表す値とは区別される。

### 2.3 既存部品の境界

画像の生成・所有は可視化層、行動モードの意味と報酬はDropMergeEnvが担う。[可観測性](../design/140_observability.jp.md) §2・§3、[環境](../design/120_environments.jp.md) §2.2・§4.2に従う。両者をつなぐ新しい汎用部品は必要ない。

[可視化・メトリクスの地図](../wiki/categories/317_metrics.md) と [Env個別実装の地図](../wiki/categories/322_env_individual.md) にある不採用案を本件で採り直すものはない。画像の出力内容と、EnvからAgent・Runnerへ結果を渡す既存の境界を保つ。

## 3. 確定事項

### D1. 画像メモリの所有権

2.1の4経路では、画像が所有するメモリを、その画像の契約に適合する方法で確保・解放する。画像を返したあとも、返された画像自身の寿命に従って正しく解放される。公開APIと画像の寸法・RGB画素値・画像種別は維持する。空のTimeHeatMapのScale描画は従来どおり1×1の黒画像である。

理由: 2.1のwxWidgetsの所有権契約が解放方法を定めており、その契約への適合だけでG2を満たせる。画像の描画規則を変える必要はない。

### D2. 画像確保失敗

D1の4経路で要求された画像を確保できない場合、画素へアクセスする前に `ANET_SYSTEM_ERROR` で停止する。空画像・別の寸法・過去の画像への黙った代替はしない。エラーには描画対象と要求した幅・高さを含める。

理由: [AGENTS.md](../../AGENTS.md) の「Fail-Fast 原則」が、明示要求した資源の確保失敗を停止対象としているため。確保失敗を検出してから不正な領域へ書く経路を作らない。

### D3. NOOPへの罰の判定

有効な行動に対し、次の表はモードの行を1つだけ適用し、その行のNOOP条件を満たすときだけ `noop_penalty` をStep報酬へ1回加算する。物理シミュレーションの回数ではなく、EnvのStep呼び出し1回を単位にする。

| `action_mode` | NOOP条件 | それ以外の有効行動 |
|---|---|---|
| `direct` | 該当なし | 列0を含む全行動がDROP。NOOPへの罰を加算しない |
| `direct_noop` | 行動0 | 行動1以降はDROP。NOOPへの罰を加算しない |
| `move` | NOOP命令（行動0） | 移動・DROPにNOOPへの罰を加算しない |
| `move_fast` | NOOP命令（行動0） | 通常移動・高速移動・DROPにNOOPへの罰を加算しない |

理由: 2.2の既存のモード別の行動解釈に従えば、G3を満たし、Directの列0だけが不利になる誤加算を除けるため。

### D4. 選択した命令を基準にする

D3はEnvへ渡された命令の意味で判定する。`noop_override=true` の移動モードでNOOPが移動へ変換されても、NOOPへの罰を加算する。DROP命令が落下中などのため実行されなかった場合も、DROPをNOOPと読み替えない。Stepで加算した罰をエピソード累積報酬にも同じ1回分だけ含め、生スコア・観測・物理遷移・終了判定は変えない。

理由: 2.2の既存の命令解釈と、ユーザーが承認した「選択した命令を基準にする」に従うため。執行結果を基準にすると本件と別の報酬設計になる。

### D5. 現行契約の範囲と移行

公開API・設定キー・既定値・行動集合・画像種別を追加変更しない。`noop_penalty=0` は加算が0になる通常の値で、別のモードへ読み替えない。互換分岐・旧挙動へ戻す設定・警告は追加しない。入力の有効範囲は既存契約に従い、別の設定や不正行動の検証を本件へ広げない。現用の追随先は§6の一覧を正本とし、過去のRun・実験記録・ADRは保持する。

理由: D1〜D4は既存契約の局所的な修正であり、新しい選択や互換性の要求がないため。[AGENTS.md](../../AGENTS.md) のクリーンブレーク方針にも従う。

## 5. 受入条件と成功の測り方

以下は実装工程で満たす条件である。本PRDの起票時点では実装の検証を実行していない。性能や学習成績を合否条件にはしない。新たな同期・転送・背景処理を導入する要求はない。

### A1. 画像の寸法・全画素・画像種別

2.1の4経路のすべてについて、修正前の固定入力と期待画像を基準として、修正後の全RGB画素・寸法・画像種別が一致するテストを置く。期待画像は修正後の描画処理を呼んで作らず、修正前に保存した値か独立に計算した値とする。

- TimeHeatMapのScale: データなしは1×1の黒画像。データありは設定した寸法で、未観測セル・値のあるセルの両方を含める。
- Histgram: データなしの黒画像と、複数のbinにデータを入れた画像を含める。
- SweepedHeatMap: Reset直後の画像と、固定した値を評価した画像を含める。
- TimeHistogram: Scaleを明示した空・データありの描画で、TimeHeatMap経由の経路も同様に確認する。

各画像のコピーを残し、元の画像と生成元を破棄したあともコピーの全画素が期待値に一致し、最後にコピーも破棄できることを確認する。必要な画像の生成は既存の公開経路で行い、テスト専用の本体APIを追加しない。

### A2. 画像メモリの生成・破棄

A1の4経路を、それぞれ独立したプロセスで100回ずつ生成・破棄する。修正前は各経路の最初の不一致をメモリ検査が検出すること、修正後は100回完走して不一致が0件となることを要求する。全経路を1プロセスだけで実行して最初の異常終了で残りを未実施にしない。

WindowsではASanの `alloc_dealloc_mismatch=1` を明示する。既定では検出が無効であることと、コンパイル時のAddressSanitizerの有効化が必要であることは [Microsoftの一次資料](https://learn.microsoft.com/en-us/cpp/sanitizers/error-alloc-dealloc-mismatch?view=msvc-170) による。実際に使ったビルド条件・実行条件・修正前後の終了コード・対象経路ごとの結果を記録する。

ライブラリ境界を含む実際の確保・解放の経路で検出できることを修正前の結果で確かめる。検出できない環境、構築できない環境、未実施の経路は受入未達とし、通常Debugの完走で代替しない。公開用の検証手順は§6の検証資材に置き、実行ログの実体は実装計画からたどれるようにする。

### A3. 画像確保失敗

対象の4経路で確保失敗を検出し、画素アクセスより前にD2の識別情報を伴う `ANET_SYSTEM_ERROR` へ到達することを確認する。失敗の再現にはテスト用の外部の確保失敗注入を用い、本体にテスト専用APIや新しい設定を追加しない。再現条件、対象経路、停止位置とメッセージを記録する。注入できない場合は未達の経路を明記する。

### A4. 4行動モードの報酬差

CPU上の単一Envを2個用い、seedを123に固定し、各ケースで同じReset・同行動列を適用する。違いは `noop_penalty` だけとし、対照は0、比較側は `-0.25` とする。各stepの報酬差が、D3のNOOPなら `-0.25`、それ以外なら0となることを絶対誤差 `1e-5` 以下で確認する。

- `direct`: 有効な先頭・中間・最後の列のDROP。列0を必ず含める。
- `direct_noop`: NOOPと、先頭・中間・最後の列のDROP。
- `move`: NOOP、左右移動、DROP。
- `move_fast`: NOOP、左右移動、高速左右移動、DROP。

各ケースは空の盤面から始め、行動集合と直接指定の列数は両個体で同じにする。必要な条件は個体ごとに独立させ、途中の終端に後続ケースを依存させない。生スコアと、報酬以外の観測・物理状態・done・truncatedも両個体で一致することを確認する。差が0になることを、両個体の報酬が0になることと取り違えない。

### A5. 選択した命令と執行結果の境界

A4の比較方法で、移動モード2種の `noop_override=true` と `false` のそれぞれでNOOPの報酬差が `-0.25` であることを確認する。Direct系では `noop_override` の有無でD3の結果が変わらないことも確認する。

落下中にDROPを選んで実行されないケースを、公開のReset・Stepで準備する。命令を処理できない状況を実際に作れたことを観測で確かめ、そのDROPの報酬差が0となることを確認する。少なくとも `direct` の列0と `direct_noop` のDROPを含める。`use_instant_drop=false` など、準備に使った条件もテストに固定する。

### A6. 加算回数・累積・ゼロの罰

NOOPを複数回含む同行動列で、エピソード累積報酬差が `-0.25 × NOOP命令数` となることを絶対誤差 `1e-5` 以下で確認する。NOOP命令数は各モードのD3で数える。複数の物理シミュレーションを行う設定でも、EnvのStepあたりの加算は1回だけであることを、実際に複数回進んだケースで確認する。

加えて両個体の罰を0にした場合に、報酬を含む全結果が一致することを4モードすべてで確認する。累積報酬は返されたStep結果が持つ現在のエピソードの値を読み、View用の前エピソード履歴を代用しない。Step報酬と累積報酬の両方を検証し、スコアを報酬の代わりに比較しない。終了stepの結果も確認対象とする。

### A7. ビルド・関連テスト・検証記録

[AGENTS.md](../../AGENTS.md) のWindows/MSVC手順でDebugビルドを行い、追加した画像テスト、既存の画像テスト、DropMergeの対象テストを実行する。A1〜A6の結果と、実行したコマンド・終了コード・未実施の理由を実装計画に記録する。

A2のメモリ検査を含め、未実施・検出できない・環境不足の項目があれば、項目別に受入未達とする。後続の長期Runが来ることを完了条件にせず、この実装工程内で実行する。すべての受入の合格が実装完了の条件であり、PRDのレビューOKを実装の合格として扱わない。
