### PRD作成の契約

- 論点をPRD §5の6区分で仕分ける。①事実、②一意に導ける事項には開ける根拠リンクを添える。②はscope screen後の最初の個別質問と同じ応答で一覧を示し、番号で③へ戻せる。根拠を示せない選択は③として聞く。
- 選択肢は正常・境界・失敗時の具体的な挙動、API・設定例、性能と保守性で比較する。既存部品の働きを要点提示へ足す。
- scope screenはゴールへの寄与を確認する。仮説・比べ方・終わり方を明らかにする。先送りは実験結果待ちか別の関心に限定し、理由と作る条件を記録する。後で要るものも同時に作り、確定要求から最小の形を導く。
- 契約は1問ずつ、契約から導ける細部は推奨値と理由の一覧の扱いを1問で聞く。関数分割や配置は実装計画へ送る。クラス構成と名前はこれらに混ぜない。
- 起草で成功の測り方、決定の理由と依存する前提を書く。追加・変更・削除のクラス一覧（名前、区分、責務）を置き、直前に「従えない事情があれば、実装する側が理由を実装計画に書いて変えてよい（質問しない）」を添える。
- 最終簡素化パスと最後のYES/NOを削除。自己点検で目的のずれと決定の残滓を見る。目的のずれは未決のまとめ質問の前に別の1問で聞き、残滓は直して報告する。
- 再グリルで確定事項を開き直すのはPRD §5の条件だけ。暫定・999では質疑を省き、未決を記録する。Plan Modeでは質疑後に計画提示・承認を経てモードを抜けてから起草し、実装せず停止する。
- 両入口ともレビューの組み立て・起動・継続依頼は既存 `anet-review` の該当節を参照する。レビュー専用入口の「直さず停止」は借りず、差し戻し対応はプロセス契約に従って工程内で行う。
