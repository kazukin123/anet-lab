# PRD120: 課題の種類を仕事の種類にし、PRD との結び付けを課題の prd 欄（Obsidian のリンク）に替える

> 2026-11-10 実装の移しで直した。PRD119 の子の ee32bd・fb8a45 は、PRD119 の D12・D13 で「直さない」と決めて解決した課題で、完了の理由は「対応しない」になる。D11 の行 2 のとおり `prd` で PRD119 を指すと、§5.2 の行 2 で PRD119 が実装済みでなくなり、A4 と食い違う。PRD119 が直さないと決めた課題は、PRD119 が直す課題ではなく関係するだけの課題なので（D2）、D11 の行 1 に 227b05 と並べて足し、`docs` に PRD119 を置く形にした。あわせて、A3 の検索を frontmatter の行（行頭から）に限った。本文の説明の中の語まで数えないためである。
> 2026-11-10 起票。同じ日の会話でグリルを行い、§4 の確定事項を決めた。理由の列に「ユーザーの選択」とある形はユーザーが選び、細部（値の名前、列名、欄の既定など）は、ユーザーが推奨の既定で埋めることを選んだ。ほかは、規約・コード・ほかの決定から導いた。
> 起点: 開発者が、課題（`docs/management/issues/`）を Obsidian のプロパティ欄と Bases の表で、スマホからも手入れするようになった。そのときに、次の 4 点で困った。
> - 種類の欄（`type`）で、機能追加・不具合・リファクタリングといった仕事の種類を絞れない。
> - 値の名前「索引」「ずれ」が分からない。
> - `parent`・`depends` から課題へ、課題から PRD へ飛べない。
> - 大まかな分類と、横断のテーマの欄が無い。
>
> 関連: [issue-20261104-52ffba](../management/issues/issue-20261104-52ffba.md) の事象 1（段階に分けた PRD の「実装済み」の時機）は、D4 で解ける。[PRD925](925_issue_list_views_10prd.md)（一覧の見せ方。暫定）は、本 PRD を前提に再グリルする。

## 1. 問題

### 1.1 種類の欄で、仕事の種類が分からない

課題 133 件のうち 69 件の `type` が「索引」で、その課題が機能追加なのか、リファクタリングなのかが分からない。残りの値も、一般の課題管理の語とずれている。

- 「改善」は、振る舞いを変えない作りの直し（リファクタリング）の意味で使っている。
- 「案」は、新しい振る舞い（機能追加）の意味で使っている。
- 「ずれ」「索引」は、開発者に意味が伝わらなかった。

### 1.2 PRD 専用の課題が、仕事の課題と重なる

PRD114 の D10 は、PRD を起こすたびに「`type: 索引`」の課題を 1 件作り、その `docs` で PRD を指すと決めた。題材の課題は、`parent` でその課題を指す。ところが今の 69 件のうち 61 件は、子も、同じ PRD を指すほかの課題も無い。その PRD のただ 1 件の課題で、中身は普通の仕事の課題と変わらない（§2.3）。

### 1.3 段階に分けた PRD が、最初の段階で「実装済み」になる

PRD の実装が済んだかは、索引の課題の AI の判定「実装済み」で表す。段階に分けた PRD では、最初の段階を終えた時点でこの値が付く。wiki は、この値だけを見て PRD を実装済みとして取り込む（52ffba の事象 1）。

### 1.4 Obsidian で結び付きをたどれない

`parent`・`depends` は課題の ID だけを書き、PRD は `docs` にパスで書く。そのため Obsidian では、どちらもリンクとして開けない。

### 1.5 分類・テーマ・完了の理由の欄が無い

- `area` は機能カテゴリの細かい分け（16 種）で、「アルゴリズムの課題」「UI の課題」のような大まかな絞り込みができない。
- 開発者は横断のテーマ（NGU など）を `memo` に書いているが、`memo` は自由な文の欄なので、テーマで絞れない。
- 「解決」は、直したのか、やらないと決めたのか、重複だったのかを見分けられない。統計の「直した件数」も混ざる。

### 2.4 Obsidian の書き方と、名前の一意性

- Obsidian のプロパティでは、`"[[ファイル名]]"` の形で書いた値がリンクになる。プロパティ欄と Bases の表からタップで開け、バックリンクにも出る。
- 開発者が使う保管庫は、リポジトリ全体を開いている。Bases のフィルタが `docs/management/issues` と書かれていることから、そう判断した。
- 名前の重複は無い。課題 133 件のファイル名にも、PRD 173 本（`done/` などの過去の置き場を含む）のファイル名にも、同じ名前は無い。
- PRD の番号には、重複しているものと消えたものがある（[wiki_support.py:205](../../reports/tools/wiki_support.py) の「PRD を一意に決められない」の扱い）。

### 2.5 規約と過去の判断

- [ADR 0068](../adr/0068-work-state-and-order-live-in-issues-prd-stays-an-instruction-document.md) は、作業の状態と順序を課題が持ち、PRD は指示文書のままにすると決めた。「課題から起こした PRD だけ課題を残す」案は、ユーザーが起こした PRD が一覧から欠けるので退けた。
- PRD114 の D10 は、索引の課題を、題材が 1 件のときも分けて作ると決めた。理由は、AI の判定の欄が、PRD 側の「実装済み」と題材側の「残件有り・残件無し」の 2 つの意味を兼ね、監査の確かめ直しが「実装済み」を上書きするためである。
- PRD114 の D22 は、PRD の実装済みを、番号をスコープに持つコミットではなく、PRD の課題の AI の判定で拾うと決めた。コミットで拾うと、PRD の工程の中で直したコミットや起草のコミットも拾って誤るためである。本 PRD の D4 も判定から導く点は保ち、拾う元を窓口の課題 1 件から、PRD を指す課題の全部に変える。
- 課題の書き方は、2026-11-09 に Obsidian の書き方にそろえた（[anet-create-issue](../../.agents/skills/anet-create-issue/SKILL.md) の「テンプレート」）。`priority`・`memo` は、開発者が書く管理外の欄である。
- クリーンブレークの方針（[AGENTS.md](../../AGENTS.md)）により、旧い書き方の互換の読みを残さない。

## 3. ゴール・非ゴール・成功の測り方

### 3.1 ゴール

- **G1**：課題の種類の欄で、仕事の種類（機能追加・不具合・リファクタリングなど）を絞れる。
- **G2**：PRD との結び付けを各課題の `prd` 欄で持ち、PRD 専用の課題を作らない。すべての PRD が課題の一覧に載ることは保つ（ADR 0068）。
- **G3**：PRD の「実装済み」が、その PRD の仕事が全部済んだときだけ立つ。
- **G4**：Obsidian で、`parent`・`depends` から課題へ、`prd` から PRD へ開ける。
- **G5**：大まかな分類・横断のテーマ・完了の理由で、絞り込みと集計ができる。

## 4. 確定事項

| # | 決定 | 理由と依存 |
| --- | --- | --- |
| D1 | `type` は仕事の種類だけを表す。値は次の 7 つで、定義は次のとおり：<br>機能追加（新しい振る舞い）<br>機能改善（今ある振る舞いを使いやすく・見やすく・正確にする）<br>性能改善（速さ・メモリ）<br>リファクタリング（振る舞いを変えない作りの直し）<br>不具合（決めたとおりに動かない）<br>不整合（文書・規約と実物の食い違い。どちらを直すかは対応のときに決める）<br>調査（測る・調べる）<br>旧い値の索引・ずれ・改善・案はなくす | 仕事の種類で絞りたい（G1）。コミットの Topic（010 リファクタリング・020 性能改善・030 機能追加・040 不具合対応）の語に寄せ、新しい語を作らない。「改善」は今リファクタリングの意味で使っているので、同じ語に別の意味を持たせず、性能改善と機能改善に分けた（ユーザーの選択）。「ずれ」は「不整合」に改めた（ユーザーの選択） |
| D2 | 課題に `prd` 欄を足し、その課題を直す PRD を 1 本指す。課題と PRD は N:1 で、1 件の課題が指せる PRD は 1 本までにする。1 件の課題から PRD を 2 本以上起こすときは、元の課題を親にして、PRD ごとに子の課題を作り、子に `prd` を書く。PRD に関係するだけの課題は、`prd` を書かずに `docs` に PRD を書く。`prd` に書いた PRD を `docs` に重ねて書かない | 課題は仕事の単位、PRD は直し方の指示である（ADR 0068）。1 本までにすると、PRD ごとの実装済み（D4）が、ほかの PRD の進み具合を待たない。N:M にすると、A が済んでも B が済むまで A が実装済みにならない（ユーザーの選択） |
| D3 | 直下のどの PRD にも、`prd` で指す課題が 1 件以上ある。PRD の範囲は、それを指す課題の全部で覆う。PRD を書くとき、題材の課題があれば、その課題に `prd` を書く。題材で覆えない仕事があれば、その分の課題を 1 件作り、無ければ作らない。題材が無い PRD は、その仕事の課題を 1 件作る。PRD 専用の窓口の課題（索引）は作らない | すべての PRD を一覧に載せる（ADR 0068、ユーザーの選択）。覆えない分の課題が無いと、題材が済んだだけで PRD が実装済みになる（D4。ユーザーの選択）。61 件の索引が普通の仕事の課題と変わらなかった（§2.3） |
| D4 | PRD の実装が済んだかは、PRD 自身にも課題の欄にも持たせず、道具が課題から導く。判定の値「実装済み」はなくし、`ai_judge` は 未確認・残件有り・残件無し・判定不能 の 4 つにする。導き方は §5.2 による。やらないと決めた仕事（次版・対応しない・不要になった）が残る PRD は実装済みにしない | PRD114 の D10 が避けた 2 つの意味の兼用が起きない。段階の途中で実装済みにならない（52ffba の事象 1、G3）。D2・D3・D8 に依存する（ユーザーの選択）。やらない仕事の扱いは、別モデルの検討で、実装していない指示が wiki に実装済みとして入るおそれが挙がり、ユーザーが「やらない部分があれば止める」を選んだ |
| D5 | `parent`・`depends`・`prd` は、Obsidian のリンクの形 `"[[ファイル名]]"`（拡張子なし）で書く。課題の ID だけの書き方は受け付けず、検査で止める（互換の読みを残さない）。別名つき（`[[名前\|別名]]`）とパスつき（`[[docs/memo/名前]]`）も、末尾の名前で読む。起票では別名もパスも付けない | Obsidian でタップして開ける（G4）。名前は一意である（§2.4）。Obsidian の候補選びが書く形にそろえる。PRD の番号は一意でないので、番号では指さない |

## 5. 実装契約

### 5.1 課題の欄

| 欄 | 値 | 書く人 | 道具の検査 |
|---|---|---|---|
| `type` | D1 の 7 つ | 起票は AI、以後は開発者の指示（`anet-update-issue`） | 7 つのどれかでなければ止める |
| `ai_judge` | 未確認・残件有り・残件無し・判定不能 | AI（`anet-update-issue` の判定） | 4 つのどれかでなければ止める（「実装済み」も止める） |
| `prd` | `"[[<直下の PRD のファイル名>]]"` か空 | 起票と PRD の起草は AI、以後は開発者の指示 | 空か、`docs/memo/` 直下の `*_10prd.md` のリンクでなければ止める。過去の置き場の PRD は指せない |
| `parent` | `"[[<課題のファイル名>]]"` か空 | 同上 | 空か、課題の ID の名前のリンクでなければ止める |
| `depends` | `"[[<課題のファイル名>]]"` の並び | 同上 | 各値が課題の ID の名前のリンクでなければ止める。指す課題が無いときは、今と同じく一覧で「（無い）」と示す |
| `docs` | 関係する文書のパスの並び | 同上 | 今の検査（実在するパス）に、`prd` と同じ PRD を含まないことを足す |
| `domain` | D6 の 6 つのどれか 1 つ | 起票は AI、以後は開発者（直接書いてよい） | 6 つのどれかでなければ止める（空も止める） |
| `tags` | Obsidian のタグの並び | 開発者（管理外） | 検査しない |
| `resolution` | D8 の 5 つか空 | 解決にする操作（D8） | 状態が解決なら 5 つのどれか、解決でなければ空。外れたら止める |

- リンクは、`[[` と `]]` の間を `|` の前まで取り、`/` があれば最後の部分を名前として読む（D5）。
- 直下の PRD に、`prd` で指す課題が 1 件も無いとき（D3 に反するとき）、`stats.py` は今と同じく止まる。`wiki_support.py maps` は止めず、INDEX に「課題の無い PRD」の欄を作って並べる（§5.3）。`maps` は起票・判定・状態の書き換えのたびに回るので、PRD の下書きを置いてから課題を作るまでの間や、別の枠が下書き中のときに、無関係な課題の更新まで止めないためである（別モデルの検討の指摘を受けたユーザーの選択）。
- `ai_judged` の決まり（未確認なら空、ほかの値なら日付）は変えない。

### 5.2 PRD の実装済みの導き方

PRD を `prd` で指す課題の全部（状態を問わない）を集め、次の行を上から当て、最初に当たった行で決める。

| # | 条件 | 結果 |
|---|---|---|
| 1 | 課題が 1 件も無い | 検査で止まる（§5.1） |
| 2 | 状態が次版の課題か、状態が解決で完了の理由が「対応しない」「不要になった」の課題がある | 実装済みでない |
| 3 | 状態が解決で完了の理由が「重複」「再現しない」の課題を除くと、1 件も残らない | 実装済みでない |
| 4 | 除いたあとの課題がすべて、判定が「残件無し」か、状態が解決 | 実装済み。表示と記録に使う日は、それらの課題の `ai_judged` と `resolved` のうち最も新しい日 |
| 5 | 上のどれにも当たらない | 実装済みでない |

- 状態が解決でない課題の判定が「残件有り」「未確認」「判定不能」なら、行 5 で実装済みでない。
- やらないと決めた仕事（次版・対応しない・不要になった）が残る PRD は、実装済みにしない。PRD は指示文書で、実装していない指示が実装済みとして wiki に取り込まれないようにするためである。その仕事を PRD の範囲から外すときは PRD を改訂し、その課題の `prd` を `docs` へ移す。重複・再現しないは、直す仕事が元から無いので除く。
- 状態が解決の課題は、判定によらず済みとして数える。解決の課題にあとから「残件有り」が付いたときは、今と同じく一覧の「再開候補」に出し、状態を戻すかは開発者が決める。戻せば、行 5 で実装済みでなくなる。
- 人の `status` だけで実装済みにしないという今の決まりは、行 4 の「状態が解決」で変わる。解決は開発者が決めた事実なので、根拠に使う。

### 5.3 一覧と統計

- 一覧（INDEX と地図の「課題」の区画）の列は「# / ID / 状態 / WSJF / 待ち / 対象 / 工程 / 領域 / 分類 / 種類 / PRD / AIの判定 / 課題」にする。PRD の列は、PRD の番号に PRD へのリンクを付ける。
- 「解決待ち」の欄は、判定が「残件無し」で、解決でない課題を拾う。
- 「再開候補」の欄のあとに「課題の無い PRD」の欄を作り、直下の PRD のうち `prd` で指す課題が 1 件も無いものを、PRD へのリンクと題で並べる。無ければ「該当する PRD はありません。」と書く。
- wiki の点検（`scan`）は、§5.2 で実装済みになった PRD を、§5.2 の日とともに拾う。取り込み済みかは、PRD のパスと blob が同じで `implemented:` の付いた `ingest`・`writeback` の行が `log.md` にあるかで決め、日付は突き合わせに使わない。行の形（`implemented:YYYY-MM-DD`）は変えない。日付は課題の判定や解決のたびに動く導いた値で、突き合わせに使うと、監査の確かめ直しのたびに同じ PRD を取り込み直すためである。
- 統計は、`type` を「種類別」として数え、`domain` と `resolution` も数える。直下の PRD の状態は、D16 で、指す課題の状態から導く。
