## 1. 目的と問題

### 1.1 問題

anet はブランチを常用しないが、ワークツリーのセッションで main と並行に作業し、PR で main へ入れることがある（P1）。そのとき起きる衝突には、git が自動マージできずに止まるもの（テキストの衝突）と、git は自動マージするが anet の決まりに反するもの（決まりの衝突。番号の重なりなど）がある（§4、§5.2・§5.3）。

今は、マージの衝突の解き方の決まりが無い（P12）。解く人（開発者か AI）は、どれが道具の作る生成物か、どれが追記だけの記録か、番号が何から引かれるかを知っている必要がある（P3〜P6）。git の行の単位の解き方（片側を採る、両方を残す）では、wiki の作業の記録の行の順、移したページへの変更、同じ番号の RFD 2 本が、気づかれずに残りうる（§5.3・§5.4）。Claude Code には PR の衝突を扱う汎用の入口があるが、anet のこうした決まりを読まずに解く（P13）。公開の衝突解消の skill も、番号の重なり・プロジェクト固有の生成物・追記だけのログの順を扱わない（P24）。

### 1.2 ゴール

- ブランチを main へ入れる前に、起きる衝突を、テキストの衝突も決まりの衝突も、種類ごとに一覧にできる。
- 決まった解き方がある種類は、その解き方で解く。中身の判断が要る種類は、AI が両側の文脈（コミット、RFD、課題、wiki の出典）を読んで解き方の案を出し、開発者が選ぶ。
- 解いた結果が anet の決まり（番号を使い直さない、生成物は道具で作り直す、wiki は出典を正とする）に合っていることを、マージのコミットの前に確かめられる。
- 最初の適用として、`feature/20261125-ppo` を main へ入れる。
- 題材の課題 issue-20261126-56483f が片付く。

### 1.3 非ゴール（退けた案と、本当の制約か）

- 衝突を起こさない仕組み（採番がほかのワークツリーとブランチも見る、など）— 別の関心として、別の課題にした（[issue-20261127-692b3e](../management/issues/issue-20261127-692b3e.md)。2026-11-27 に起票）。作る条件は、開発者がその課題で RFD を起こすと選んだとき（D19）。本当の制約ではなく、範囲の線引きである。
- AI がマージのコミットと push をすること — commit と push は人間が行う決まりによる（P9）。決まりを変えれば移せるので本当の制約ではないが、コミットを開発者が結果を受け入れる点として残すと決めた（D2）。マージの開始と中止は、D2 で範囲に入れた。
- ブランチを常に使う運用へ切り替えること — 開発の進め方の話で、この RFD は今の使い方（ときどきワークツリーで並行する）の衝突を解く。本当の制約ではない。
- main に入った記録（コミットの件名、ADR の本文、実験記録、Run artifact、履歴資料）を書き換えて番号の重なりを消すこと — 過去の記録を書き換えない決まりによる（P10）。本当の制約である。

### 1.4 機構とゴールの対応

| 機構 | ゴールへの寄与 | 決定 |
|---|---|---|
| 試しのマージと、決まりの衝突の検出 | 起きる衝突を、作業ツリーを変えずに一覧にする | D6・D22 |
| 衝突の種類と解き方の表 | 決まった解き方がある種類を、解く人によらず同じに解く | D7・D9〜D12 |
| AI が両側の文脈を読んで出す案 | 中身の判断が要る衝突を、開発者が選べる形にする | D8・D12・D13 |
| 振り直しの行でコミットを名指す | 番号を振り直したあとも、両側の古いコミットの件名をそれぞれの RFD に当てる | D14・D15 |
| マージの途中に両側の履歴を読む道具 | コミットの前に、生成物を正しく作り直して確かめられる | D21 |
| 解いたあとの確かめ | 決まりに合っていることを、マージのコミットの前に確かめる | D16 |
| 入口と、git の操作の分け方 | 開発者が、どの場面で何を頼み、自分が何をするかが分かる | D1〜D5・D17・D22 |
| 最初の適用 | `feature/20261125-ppo` を main へ入れる | D18 |

### 1.5 成功の測り方

- `feature/20261125-ppo` を `anet-merge-branch` で取り込んだ結果で、受入 A4 の (a)〜(h) と A5・A6 がすべて満たされる。
- 衝突の種類ごとの件数と、開発者へ出した問いの数を、最初の適用で課題の対応内容に記録する（D17）。比べる基準が無い（P17 が欠け）ので、次の適用と比べる。
- 先送り: 衝突の検出を道具（スクリプト）にすること。理由は、実験の結果が要るため（P17 が欠け。U17）。作る条件は、最初の適用で検出の手作業に誤りか目立つ手間が出たこと（U17 の分かれ方）。

## 4. 用語

- **マージ**: この RFD では git のマージ（ブランチを取り込むこと）を指す。用語集が「マージ」を避ける語にしているのは設定の選択チェーンの話で、別のものである（P16）。用語集には足さない。
- **衝突**: マージで両側の変更が同じものに当たること。次の 2 つを含む。
  - **テキストの衝突**: git が自動マージできずに止まるもの。一覧では「自動マージ: 不可（理由）」と書く。
  - **決まりの衝突**: git は自動マージするが、合わせた結果が anet の決まりに反するもの（同じ番号の RFD が 2 本入る、移した置き場の旧い場所にファイルが入る、など）。一覧では「自動マージ: 可（ただし決まりに反する: 理由）」と書く。
- **衝突の印**: git がテキストの衝突の箇所に書く行（`<<<<<<<` で始まる行と `>>>>>>>` で始まる行など）。
- **試しのマージ**: 作業ツリーと index を変えずに、マージの結果を見る操作（P14）。
- **区画**: 衝突の解き方を当てる単位。ファイル全体か、ファイルの中の節（トピック別まとめの「ファイル」の節など）。1 つのファイルに性質の違う区画があれば、区画ごとに解き方を当てる（D7）。
- **ファイルの性質**: 区画を、作り直せるかで 4 つに分ける（D7）。
  - **道具の生成物**: 道具が材料から毎回同じに作るもの（課題の `INDEX.md`、トピック別まとめの機械的に作る 3 節、wiki のページの YAML ヘッダのうち `headers` が作り直すキー）。
  - **AI の派生物**: AI が材料から書くもの（wiki の書く部分）。同じ材料からでも毎回同じ文にはならない。
  - **記録**: 起きたことの記録で、作り直す材料が無いもの（`docs/wiki/log.md`、`CHANGELOG.md`、実験記録）。どちらの側の記述も消さない。`log.md` は表の 4 行目、ほかは 6 行目で扱う（D10）。
  - **正本**: 上のどれでもないもの（RFD、コード、ADR、設定、設計文書、skill、課題の本文と開発者のメモの欄）。

用語集を「衝突」「コンフリクト」「マージ」「ブランチ」「正本」「生成物」「派生」で引き、git の操作とこの 4 分けを指す語は無かった（2026-11-27。「派生」は DQN 派生手法の 1 件だけ）。既存の語で言い換えられないので、ここで名前を決めた。どれもこの RFD と `anet-merge-branch` の中だけで使う呼び名で、用語集には足さない。

## 8. 仕様

### 8.1 流れ

`anet-merge-branch <ブランチ>` は次の順に進める。

1. **状態を見る**: 取り込むブランチと、そのワークツリー、取り込む先（ローカルの main）を確かめる。引数のブランチがローカルに無いとき（名前の誤りなど）は、ローカルのブランチの一覧を示して止まる。ブランチにワークツリーが無ければ、作るよう開発者に頼んで止まる（D22）。ワークツリーの未コミットの変更とステージした変更を見ておく（D5）。
2. **一覧を作る**: 試しのマージと、決まりの衝突の検出で、衝突の一覧を作る（D6・D8・D17）。
3. **計画の承認を受ける**: 一覧、解き方、振り直しで変わるファイル、ビルドが要るか、ローカルの main が origin/main より先のコミットを持つかを示し、開発者の承認を待つ（D4・D22）。
4. **番号を振り直す**: 番号の重なりがあれば、ブランチのワークツリーで振り直す（D14・D15）。開発者がコミットしたら 2 からやり直し、一覧の変わり目を示す。
5. **マージを始める**: D5 の確かめをしてから、ブランチのワークツリーで `git merge --no-commit --no-ff main` を実行する（D2）。
6. **解く**: 一覧の項目ごとに §8.2 の表を当てる（D7）。決まりで解ける項目を先に解き、正本の衝突は 1 件ずつ聞く（同じ形はまとめて 1 問。D12）。AI の派生物は、ほかを解いたあとで扱う（D11）。区画を解くたびに、そのファイルをステージする（D2）。道具の生成物は、マージの途中に作り直す。課題の `INDEX.md` とトピック別まとめの 3 節は `maps`、YAML ヘッダの道具が作るキーは `headers` で作る（D9・D21、§8.2 の 3 行目）。
7. **確かめて報告する**: D16 の確かめを回し、D17 の形で報告する（マージのコミットの件名の案を含む）。commit は開発者が行う。
8. **PR を入れる**: 開発者が、要れば main を push し、ブランチを push する。PR を入れる直前に、試しのマージをその時点の main に当て直し、新しい衝突が出たら 2 からやり直す（D22）。PR はマージのコミットの形で入れる（D1）。

開発者が中止を選んだときは、AI が `git merge --abort` を実行する（D2）。解いた区画はそのたびにステージしてあるので、中止はどの時点でも通り、マージと重ならない未コミットの変更は残る（P41）。マージを始める前（1〜4）は、中止しても作業ツリーは変わらない（4 で直したファイルは、開発者がコミットするまで未コミットの変更として残る）。

- 別モデル（Fable）の案（2026-11-27。起草のあとの検討）: マージの途中の `maps` は main の側を読まないので、道具が両側の履歴を読むか、確かめをコミットのあとへ送る。`anet-prepare-commit` はマージの途中を扱わないので、skill が自分でステージするか、prepare-commit に節を足す。PR の取り込み方を決める（squash・rebase はハッシュを消す）。PR を入れる直前に main へ当て直す。wiki の書く部分の既定は、捨てて作り直すより、移した先へ行を当て直すほうがよい（ヘッダは道具が作る）。捨てた材料の記録の行が残ると、取り込みのやり直しの漏れに `scan` が気づかない。`git merge --abort` の振る舞いを前提に足す。記録の行の解き方は `log.md` に限る。件名の書き直しなら D15 が要らない（このうち最後のものは、振り直しの行が main の件名を当てるので採らなかった）。

## 13. 選ばなかった形

- `docs/wiki/log.md` に git の `merge=union` を指定する形 — 印なしで両側を残すが、順を決めない（P6、D10）。
- main の作業ツリーで直接マージする形 — 並行のセッションの未コミットの変更と重なり、git が断るか、ほかのセッションとぶつかる（P22・P30、D1）。
- ブランチを main の上へ rebase する形 — コミットごとに解き直しが要り、ours と theirs が入れ替わり、強制 push が要る（P29、D1）。
- PR の画面（GitHub）で解く形 — 消したファイルを変えた衝突を解けず、道具を回せない（P28、D1）。
- マージの開始もコミットも開発者が行う形 — 開発者が、マージの開始も AI に任せることを選んだ（D2）。
- AI がマージのコミットまで行う形（公開の skill の多くの形）— コミットを開発者が結果を受け入れる点として残す（P25、D2）。
- 決まりの文書だけを置き、手順は汎用の入口に任せる形 — 決まりの衝突を見つける手順と、D2 の例外を結びつける手順が無い（P13・P19、D3）。
- 既存の skill（`anet-prepare-commit`）にマージの段を足す形 — 検出と解消という別の関心が混ざる（D3）。
- wiki の書く部分を、いつもブランチの側を捨てて作り直し、捨てた行と結果を 1 行ずつ表で突き合わせる形（グリルで一度決めた D11 の前の形）— 規約が同じなら行の当て直しのほうが結果が決まり、表は当て直しと同じ手間になる（別モデルの検討、D11）。
- wiki の書く部分を、いつも移した先へ行で当て直す形（別モデルの案）— 規約が変わったときは、サマリなどのための取り込みがどのみち要り、当て直した行と取り込みが足す行が重なりうる（P44、D11）。
- wiki の書く部分を、いつも両側とも作り直す形 — main の側まで書き戻し直すことになり、wiki だけが持つ記述が消える（P20、D11）。
- マージの途中のステージを `anet-prepare-commit` で行う形 — マージの途中を扱わず、解いている途中に未ステージの変更があると中止が効かない（P40・P41、D2）。
- マージの途中の確かめを、マージのコミットのあとへ送る形 — ゴール 3 の「コミットの前に」を弱め、追いつきのコミットが毎回要る（D21）。
- 番号の重なりで、振り直す側を「変えられない記録に引かれていない側」の規則で選ぶ形 — main の側はいつも件名に引かれるので、結果はほぼブランチの側になり、記録の一覧を保つ手間だけが残る（P35、D14）。
- マージのあとに振り直す形 — 同じファイルに両側の番号が入り、1 か所ずつ中身で見分ける必要が出る（D14）。
- ブランチのコミットの件名を、履歴の書き直しで新しい番号にする形 — 件名だけを書き直しても、振り直しの行が main の旧い番号の件名を当てるので、道具の変更は要る（P3・P23）。振り直しの行も要らない形にするには、RFD のファイルが初めから新しい番号だったように、ブランチのコミットの中身まで作り直すことになり、強制 push も要る（D15）。
- 振り直した RFD のファイルに触れたコミットだけを当てる形 — RFD のファイルに触れずに件名に番号を書いたコミットを、気づかずに別の RFD に当てる（P37、D15）。
- 道具の変更（D15）だけ先に実装して PPO を手で取り込む形、今すぐ手で取り込む形 — 待っても手間が増えず、受入を本物の衝突で確かめられる（D18）。後者は RFD の一覧のずれ（P23）も残る。
- 似た衝突への答えを、次のマージへ持ち越す形（forge、git rerere）— 取り込みの数が少なく、ゴールに効かない。同じマージの中では、同じ形の衝突をまとめて 1 問にする（D12）。
- 汎用の衝突解消（アプリの操作、`steward` skill）だけに任せる形 — anet の決まりを読まない（P13）。
- ブランチで仮の番号を使い、マージのときに正式な番号を取る形 — 暫定の起票も正式な番号を使う決まり（[memo README](README.md) の「採番」）と、9xx を仮の番号に使うのをやめた判断（RFD0131）に反する。
