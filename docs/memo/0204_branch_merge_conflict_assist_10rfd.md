# RFD0204: ブランチを main へ取り込むときの衝突を、両側の内容と文脈を読んで解く支援の RFD

> 2026-11-26 起票（暫定）。質疑を省いた。確定した決定は持たず、AI が置いた既定と決めきれない点を §6 の未決表に置いた。§7〜§9 は §6 の暫定の既定を前提に書き、前提にした行の番号を名指す。
> 起点: 2026-11-26 の会話。RFD0202 の番号が main とワークツリーのブランチ `feature/20261125-ppo` で重なり、PR で main へ入れる前に解く必要が出た。開発者は、RFD の番号に限らず、内容と文脈を考えて解く AI の支援の仕組みを整えたいと述べた（§11）。
> 課題: [issue-20261126-56483f](../management/issues/issue-20261126-56483f.md)（題材）。

## 1. 目的と問題

### 1.1 問題

anet はブランチを常用しないが、ワークツリーのセッションで main と並行に作業し、PR で main へ入れることがある（P1）。そのとき起きる衝突には、git が印を付けて止めるもの（テキストの衝突）と、git が通してしまうが anet の決まりに反するもの（番号の重なりなど）がある（§5.2・§5.3）。

今は、マージの衝突の解き方の決まりが無い（P12）。解く人（開発者か AI）は、どれが道具の作る生成物か、どれが追記だけのファイルか、番号が何から引かれるかを知っている必要がある（P3〜P6）。git の行の単位の解き方（片側を採る、両方を残す）では、wiki の作業の記録の行の順、トピック別まとめの同じ事実の 2 行、同じ番号の RFD 2 本が、気づかれずに残りうる（§5.3・§5.4）。Claude Code には PR の衝突を扱う汎用の入口があるが、anet のこうした決まりを読まずに解く（P13）。

### 1.2 ゴール

- ブランチを main へ入れる前に、起きる衝突を、git が印を付けるものも付けないものも、種類ごとに一覧にできる。
- 決まった解き方がある種類は、その解き方で解く。中身の判断が要る種類は、AI が両側の文脈（コミット、RFD、課題、wiki の出典）を読んで解き方の案を出し、開発者が選ぶ。
- 解いた結果が anet の決まり（番号を使い直さない、生成物は道具で作り直す、wiki は出典を正とする）に合っていることを、マージのコミットの前に確かめられる。
- 最初の適用として、`feature/20261125-ppo` を main へ入れる。
- 題材の課題 issue-20261126-56483f が片付く。

### 1.3 非ゴール（退けた案と、本当の制約か）

- 衝突を起こさない仕組み（採番がほかのワークツリーとブランチも見る、など）— 別の関心として、別の課題の候補にする（U14）。本当の制約ではなく、範囲の線引きである。
- AI がマージのコミット・ステージ・push をすること — git の staging・commit・push は人間が行う決まりによる（P9）。決まりを変えれば移せるので、AGENTS.md の改訂として U3 で比べる。
- ブランチを常に使う運用へ切り替えること — 開発の進め方の話で、この RFD は今の使い方（ときどきワークツリーで並行する）の衝突を解く。本当の制約ではない。
- 過去の記録（main に入ったコミットの件名、ADR の本文、過去の RFD）を書き換えて番号の重なりを消すこと — 過去の記録を書き換えない決まりによる（P10）。本当の制約である。まだ main に入っていないブランチのコミットの件名を書き直す案は、U6 で比べる。

### 1.4 機構とゴールの対応

| 機構 | ゴールへの寄与 |
|---|---|
| 試しのマージと、印の出ない衝突の検出（U2） | 起きる衝突を、作業ツリーを変えずに一覧にする |
| 衝突の種類と解き方の表（§7。U5〜U11） | 決まった解き方がある種類を、解く人によらず同じに解く |
| AI が両側の文脈を読んで出す案（U11・U12） | 中身の判断が要る衝突を、開発者が選べる形にする |
| 振り直しの行でコミットを名指す（U6） | 番号を振り直したあとも、両側の古いコミットの件名をそれぞれの RFD に当てる |
| 解いたあとの確かめ（U13） | 決まりに合っていることを、マージのコミットの前に確かめる |
| 入口（U1）と手を動かす人の分け方（U3・U4） | 開発者が、どの場面で何を頼み、自分が何をするかが分かる |

### 1.5 成功の測り方

- `feature/20261125-ppo` を main へ入れた結果で、受入 A4 の (a)〜(f) がすべて満たされる（RFD・ADR の番号が一意、wiki の道具が止まらず、RFD の一覧に「RFD を一意に決められない」の行が出ない、衝突の印が 0 件、経緯の行が日付の順、ビルドとテストが通る）。
- 衝突を解くのに開発者へ出した問いの数。比べる基準が無い（P17 が欠け）ので、最初の適用の数を課題の対応内容に記録し、次の適用と比べる。

## 3. 背景

課題記録は、1 課題 1 ファイルと、日付と乱数の ID で、ブランチをまたいでも重ならないように作った（P7）。一方、RFD と ADR の番号は「最大の番号の次」を取る連番で（P2・P8）、採番のときにほかのワークツリーのファイルや、main にまだ入っていないブランチのコミットを見る決まりは無い。2026-11-25 にワークツリーのセッションで並行の作業を始め、2 日目に RFD0202 が重なった（§5.1）。同じ作業ツリーの中でも、並行のセッションが番号を取り合う。この RFD も、番号を引いたときは 0203 が空いていたが、書く直前に別のセッションが 0203 を取ったので 0204 にした（2026-11-26）。

## 4. 用語

- **マージ**: この RFD では git のマージ（ブランチを取り込むこと）を指す。用語集が「マージ」を避ける語にしているのは設定の選択チェーンの話で、別のものである（P16）。用語集には足さない。
- **衝突**: マージで両側の変更が同じものに当たること。git が印を付けて止めるもの（テキストの衝突）と、git が通すが anet の決まりに反するもの（この RFD では「印の出ない衝突」と呼ぶ）を含む。この RFD の中だけで使う呼び名で、用語集には足さない。
- **試しのマージ**: 作業ツリーと index を変えずに、マージの結果を見る操作（P14）。

用語集を「衝突」「コンフリクト」「マージ」「ブランチ」で引き、git の操作を指す語は無かった（2026-11-26）。git の語をそのまま使うので、新しい語は作らない。

### 5.3 印の出ない衝突

- **RFD の番号**: RFD0202 の 10rfd が 2 本、マージにそのまま入る。件名に `RFD0202` を持つコミットは、main に 2 件（`d7a20b11`・`e38d64b2`）、ブランチに 2 件（`66296d56`・`3ae08c1e`）ある。マージのあと、RFD の一覧は、この番号を持つコミットが触ったファイルを含むページで「（RFD を一意に決められない）」と出す（P4）。
- **番号を引く箇所の数**: `git grep -l -i -E` で数えた。main のコミット済みの側で `rfd0202` か `0202_wiki` を書くファイルは 9 件で、ADR 0097・0098 を含む（ADR の本文は書き換えられない。P10）。ブランチの側で `rfd0202` か `0202_ppo` を書くファイルは 22 件で、テストのソース 11 件（テストのタグ `[rfd0202]`、テストの名前、コメント）を含む。マージで両側の行が同じファイル（wiki のページ、`log.md`）に入ると、そのファイルの `RFD0202` がどちらの RFD かを、番号だけでは読み分けられなくなる。
- **振り直しの行の当て方**: 片側を今の決まりのまま振り直すと、振り直しの行は、行の日付以前の `RFD0202` の件名をすべて振り直した側へ当て、使い続けるもう片側の RFD のコミットまで当てる見込みがある（P3。コードを読んだ見立てで、動かしてはいない）。
- **置き場の移動**: main の作業ツリーでは RFD0202（wiki）の実装が進み、wiki のページを `docs/wiki/concepts/` の下へ移している（P18）。これが main に入ったあとでマージすると、ブランチが `docs/wiki/categories/` に新しく足した `326_ppo.md` は、移した先に入らず、旧い置き場に作られる。ブランチが今あるページに足した行は、git が改名を追えれば移した先に入る。

## 7. 仕様

暫定の既定（U1〜U13）を前提に書く。

`anet-merge-branch` は次の順に進める。

1. 取り込むブランチと、取り込む先（main）を確かめる。ブランチのワークツリーに、ステージしていない変更が無いことを確かめる（U3・U4）。
2. 試しのマージと、印の出ない衝突の検出を行い、衝突の一覧を示す（U2）。
3. 番号の重なりがあれば、振り直す側を決め（U5）、マージの前にその側のワークツリーで振り直す。開発者がコミットしたら、2 からやり直す。
4. 開発者に `git merge main` を始めてもらう（U3）。
5. 一覧の衝突ごとに、下の表で種類を決め、解く。聞く衝突は、決まった解き方の衝突を解き終えてから聞く。
6. 確かめ（U13）を回し、結果と、衝突ごとの種類と解き方の一覧を報告する。ステージとコミットは開発者に任せる（U3）。

衝突の種類と解き方。上から順に当て、最初に当たった行で扱う。最後の行は、ほかのどの行にも当たらない衝突をすべて受ける。

| 種類 | 当てる条件 | 解き方 | 開発者に聞くか |
|---|---|---|---|
| 生成物 | 道具が作り直すファイルか区画（P5） | どちらかの側を採り、`maps` で作り直す（U7） | 聞かない |
| 追記だけのファイル | `docs/wiki/log.md` | 日付の順に両側の行を残し、`scan` で確かめる（U8） | 聞かない |
| 番号の重なり | 両側が同じ番号で別の RFD か ADR を足した | U5 の規則で振り直す側を決め、手順 3 のとおりマージの前に次の空き番号へ振り直す。振り直しの行にコミットを名指す（U6）。リンク・表記・テストのタグ・`.scratch/` の置き場をそろえ、改名は git に改名と見られる形にする（P11） | 規則で決まらないときだけ聞く |
| 置き場の移動 | 片側が移した置き場へ、もう片側がファイルを足したか変えた | 移した先へ移す（U10） | 行き先が決まらないときだけ聞く |
| wiki の書く部分 | `docs/wiki/` の下の、概念のページ・サマリ・目録 | 両側を残し、経緯は日付の順、同じ事実はまとめる（U9） | 出典が食い違うときだけ聞く |
| 中身の衝突 | 上のどれにも当たらない | 両側の意図を読んで案を出す（U11） | 聞く |

- `docs/wiki/log.md` に git の `merge=union` を指定する形 — 行の順を守らず、道具の結果が変わる（P6、U8）。

- PR の画面で main の側の衝突を解く形 — 道具の作り直しと確かめを回せない（U4）。
- 汎用の衝突解消（アプリの操作、`steward` skill）だけに任せる形 — anet の決まりを読まない（P13）。
- ブランチで仮の番号を使い、マージのときに正式な番号を取る形 — 暫定の起票も正式な番号を使う決まり（[memo README](README.md) の「採番」）と、9xx を仮の番号に使うのをやめた判断（RFD0131）に反する。
