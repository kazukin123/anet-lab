# 多数の seed で打席を稼ぐ（条件付きの打ち切りで、火が付かなかった Run を早く止める）暫定 PRD

> 2026-10-18 起票。詳細設計は別途グリルで行う前提で、暫定の既定を置き、決めることを §7 に残した。
> 2026-10-23 改訂: §2 の KFM の見立てと 16 seed の結果を直し（挑むことは珍しくなく、壁は挑んでいる間に撃破 ÷ 命中が上がらないこと。[999_intrinsic_reward_novelty](999_intrinsic_reward_novelty_10prd.md) の §2.2・§2.3、[2026-10-15_kfm-boss-route.md](../experiments/default-dqn/atari/2026-10-15_kfm-boss-route.md) の探索ブロック 04）、§2 の Run 名を今のフォルダ名に直した。§1・§4 の「火が付く」の言い方と打ち切りの規則の例は変えていない。
> 起点: Atari kung_fu_master（以下 KFM）で、ボス行きに入るかが seed で決まり（既定の実時間優先で 5 本中 1 本）、入った Run は 4-5M に火が付いていたこと（§2）。独立の seed を多数回せば打席は稼げるが、全部を最後まで回すと時間が足りない。火が付かなかった Run だけを早く止め、付いた Run はそのまま最後まで続けたい。

## 1. 目的と問題

Run の途中の決めた時点で、指標の条件を確かめ、満たさなければ Run を正常に終える仕組み（条件付きの打ち切り）を足す。多数の seed に最後までの予算を与えて並べ、早い時点で火が付かなかった Run は止め、付いた Run はそのまま最後まで続ける。replay を含めて途切れずに続くので、チェックポイントからの再開の問題（replay が戻らない）を避けられる。

### ゴール

- Run の決めた exp step で、購読しているスカラー指標の条件（直近の窓の平均と閾値の比較）を評価し、満たさなければ Run を止められる。
- 打ち切ったことと、その理由（どの指標がいくつだったか）が Run のログとフォルダに残り、bat と分析が見分けられる。
- bat で多数の seed を並べ、打ち切りで全体の時間を縮められる。

### 非ゴール

- 個体の重みをコピーする PBT（§6 で先送り）。
- 打ち切った Run の後片付け（削除はユーザーが行う）。
- 学習の値を変えること。条件を満たした Run は、打ち切りが無い場合と同じ学習系列になる。

## 2. 背景

- KFM の実時間優先（既定）で、ボス行きに入ったのは 5 本中 1 本（seed 3、`run_20260925-130017_atari_kfm_rr1_100m_seed3`）。seed 2 との設定の差は `run.seed` だけだった。のちの既定の 10M × 16 seed を含めると、約 20 本に 1 本になる（[999_intrinsic_reward_novelty](999_intrinsic_reward_novelty_10prd.md) の §2.3）。
- seed 3 の学習中のゲームは、3-4M にボス命中 10%・撃破 ÷ 命中 0.03、4-5M に命中 51%・撃破 ÷ 命中 0.24、6-7M に 0.71、11-16M に 0.9。
- 挑むことは珍しくない。既定の 10M × 16 seed（s04〜s19）では、0.5M 窓の命中率のピークが 10% 以上の Run が 7 本あったが、挑んでいる間に撃破 ÷ 命中が上がった Run は無く、定着した Run も無かった。s08 は挑み始めの撃破 ÷ 命中が 0.22 と seed 3 とほぼ同じだったが、下がって 7.5M 以降は挑まなかった。壁は挑み始めることではなく、挑んでいる間に勝ち方を覚えることにある（[999_intrinsic_reward_novelty](999_intrinsic_reward_novelty_10prd.md) の §2.2・§2.3、[2026-10-15_kfm-boss-route.md](../experiments/default-dqn/atari/2026-10-15_kfm-boss-route.md) の探索ブロック 04）。当初は「火が付くのは稼ぎの戦略が固まる 5M ごろまでで、付けば数 M で勝率が上がる」と書いたが、この 16 seed で覆った。
- 報酬クリップを外す、ライフで区切る、ε を下げる、UQE にする、などの設定では、1 本ずつの Run でボス行きに入らなかった（2026-10-14〜18）。1 本ずつでは seed の当たり外れと区別できない。
- 公表値では、KFM で 20 万点を超えるのは R2D2・NGU・Agent57・MuZero など、Actor が数百・フレームが数十億〜数百億の分散学習ばかりで、200M フレーム級の DQN 系はどれも 8 万点未満（Atari-5 の公開データ）。打席の数が桁違いであることが共通している。
- 2026-10-18 に、13 bat で既定の実時間優先・10M・seed 4〜19 の 16 本を回した（1 本約 1.5 時間）。結果は上の項のとおり。挑み方が良い Run を続けるには、今は最初から回し直すしかない。

## 3. 現状（2026-10-18 に確認したこと）

- Run の終わりは、`app.*.train_exit_step` と `exp_exit_step` の 2 つだけで、RunnerApp の学習の 1 step 前の関数で判定し、`ControlSignal::STOP` と終了要求を出す（[RunnerApp.cpp](../../apps/runner/src/RunnerApp.cpp)）。指標の値で終える仕組みは無い。
- チェックポイントからの再開（`A3.auto_load_file`）は、重みと optimizer だけを戻し、replay・step の数え方・評価の予定は戻らない（[930](930_serialize_10prd.md)、`docs/design/020_user_guide_run.jp.md`）。火が付いた Run を「10M で止めて、あとで続ける」と、火を支えていた replay の中身を失う。
- KFM の RAM メトリクスは、学習側の 1 ゲームごとの平均として `42_env/54_ram_metric_3_mean`（ボス命中の回数）とその EMA（`55`）が出ている（[Atari.txt](../../apps/runner/config/Atari.txt) の `M1`）。「ボスに 1 回以上当てたゲームの割合」は指標に無く、Run ログの「Game over」行から数えている。閾値越え率の汎用化は [999_scalar_threshold_rate](999_scalar_threshold_rate_10prd.md) が扱う。
- bat は、前の Run の終了コードとフォルダを見て次へ進む（`:run_exe` と `:find_ckpt`）。打ち切りで終えた Run も、終了コード 0 なら成功として数えられる。
- RTX 4060 機（RAM 32GB）は、replay 2M の Run を 1 本ずつしか回せない（1 本で約 14GB）。

## 4. 提案の骨子

### 段階 1: 条件付きの打ち切り

1. 設定で、打ち切りの規則を 1 つ以上書く。規則は「どの exp step で」「どの指標（購読しているスカラーの tag）の」「直近何点の平均が」「閾値に対してどうなら続けるか」を持つ。
2. Run は、その exp step に達した時点で規則を評価する。続ける条件を満たさなければ、学習を正常に終える（`exp_exit_step` と同じ止め方。チェックポイントと評価の排水も同じ）。
3. 打ち切ったら、Run ログに規則の名前・指標の値・閾値を 1 行で出し、Run フォルダに同じ内容の小さなファイルを置く。終了コードは 0。
4. 規則の指標が購読されていない、または評価の時点で値が無い（窓に点が無い）ときは、構築時または評価時に fail-fast。黙って続けたり止めたりしない。

### 段階 2: bat での使い方

1. 多数の seed に最後までの予算（例: 50M）を与え、10M で「ボスへの挑み方」の規則を評価する。火が付かなかった Run は 10M で止まり、付いた Run は 50M まで続く。
2. 打席の費用の目安: 火が付く割合が 5 本に 1 本なら、16 本で「16 × 10M ＋ 約 3 本 × 40M」≈ 280M step。全部を 50M まで回す（800M step）の 3 分の 1 程度。
3. 結果の見方: 打ち切りのファイルの有無で、火が付いた Run を一覧できる。

段階 1 だけでも、Run を 1 本ずつ回すときの無駄（明らかに失敗した Run を最後まで回す）を減らせる。段階 2 は bat の書き方だけで、実装は要らない。

## 5. User Stories

1. 研究者として、多数の seed を並べ、早い時点で目的の振る舞いが出なかった Run を自動で止め、出た Run だけを最後まで回したい。
2. 研究者として、止まった Run と最後まで回った Run を、フォルダとログだけで見分けたい。
3. 研究者として、止める条件の指標や窓を、ゲームごとに設定で選びたい。

## 6. 作らないもの・先送り

| 項目 | 裁定 | 理由と再開条件 |
| --- | --- | --- |
| PBT（成績の良い個体の重みを悪い個体へコピーし、ハイパーパラメータをずらす） | 先送り | 個体を並行して回す計算機が要る（RTX 4060 機は 1 本ずつ）。点数で選ぶと、覚えている途中のボス行きを捨てる（seed 3 の eval2 は 10-15M 24.2k・15-20M 29.1k で、稼ぎの seed 1 の 30.1k・38.8k より低く、上回るのは 20M 以降）。並列の計算機と、点数以外の選ぶ基準が揃ってから起こす |
| 10M で止めた Run を後から続ける | 先送り | replay を含めた保存と再開（[930](930_serialize_10prd.md)）が要る。段階 1 では、続ける Run は止めずに走らせる |
| 規則で止める以外の動作（設定を変える、評価を増やす） | 対象外 | 設定を動かすのは [999_metric_targeted_hyperparam_control](999_metric_targeted_hyperparam_control_10prd.md) の側 |
| 打ち切った Run の削除 | 対象外 | Run の削除はユーザーが行う（AGENTS.md の Run 命名・後片付けルール） |

## 7. 決めること（詳細設計で詰める）

暫定の既定を置いた。グリルで確定する。

| # | 決めること | 暫定の既定 |
| --- | --- | --- |
| 1 | 設定キー | `app.batchrun.metric_exit.[<規則名>].tag`（スカラーの tag）、`.at_exp_step`（正の整数）、`.window`（直近の点数、正の整数）、`.op`（`ge` / `le`。続ける条件）、`.threshold`（実数）。online の実行でも同じキーを `app.online.*` に置けるようにするか |
| 2 | 不正値の扱い | 未知の `op`、正でない `at_exp_step` や `window`、非有限の `threshold`、購読されていない tag は構築時に fail-fast |
| 3 | 指標の値の取り方 | スカラーの観測の仕組みに「直近の値を読む口」を足すか、規則専用の observer を同じ定義から作るか |
| 4 | KFM の規則に使う指標 | 「学習側でボスに 1 回以上当てたゲームの割合」（閾値越え率。999_scalar_threshold_rate の仕組みか、RAM メトリクスの平均の EMA で代える）。既定の閾値 0.3（seed 3 は 4-5M で 0.51） |
| 5 | RAM の値を実験の選別に使ってよいか | RAM はメトリクスとして読むだけという方針（2026-10-16）に対し、学習ではなく「どの Run を続けるか」の選別に使うのは境界にある。グリルでユーザーが裁定する。使わない場合は、ゲームに依らない指標（学習中のエピソードの長さなど）で代える |
| 6 | 打ち切りの記録の形 | Run ログの 1 行と、Run フォルダの `metric_exit.json`（規則名・exp step・指標の値・閾値） |
| 7 | 評価の排水 | `exp_exit_step` と同じ扱い（実行中の評価セッションの排水は既存の規則のまま） |
| 8 | 用語 | 「条件付きの打ち切り」を CONTEXT に足すか |

## 8. 成功の測り方と受入の目安

成功の測り方:

- KFM で、既定の実時間優先・最後までの予算 50M・10M で規則を評価、を 16 seed 回し、火が付いた Run だけが 50M まで回る。全体の時間が、全部を最後まで回す場合のおおむね 3 分の 1 になる。
- 火が付いた Run の数（16 本中）から、点火の割合を見積もる。これを、内的報酬の方策の家族や Bootstrapped DQN の複数の Head を入れた構成と比べる物差しにする。

受入の目安（詳細はグリルで確定する）:

1. 単体テスト: 規則が、決めた exp step で、窓の平均と閾値を比べて続けるか止めるかを決める。点が無いときは止まって理由を出す。
2. 規則を書かない Run は、本機能の前後で metrics checksum が一致する。
3. smoke Run で、止まった Run に `metric_exit.json` とログの 1 行ができ、終了コードが 0 になる。止まらなかった Run には何もできない。
4. §7 の 2 の不正値で、構築時に設定キーと値を示して止まる。

## 9. 依存と順序

依存は無い。KFM の規則に閾値越え率を使う場合は、[999_scalar_threshold_rate](999_scalar_threshold_rate_10prd.md) との順序を決める（RAM メトリクスの平均の EMA で代えるなら依存しない）。
