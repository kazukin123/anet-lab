## 1. 目的と問題

### 1.1 問題

1. **名前が中身と食い違う。** 本来の PRD（Product Requirements Document）は、PM が製品について「何を・なぜ」を書く文書で、ユーザーストーリー・対象の利用者・優先度を中心に持ち、作り方は書かない。anet の PRD は、1 回の変更ごとに番号を取り、問題・ゴール・前提・確定事項とその理由・外から見える契約（公開 API の名前・設定キー・メトリクス名・失敗の扱い）・受入を書く（P8）。優先度と作業の順は課題が持つ（P7）。呼び名の由来の `to-prd` の雛形も、後半はすでに実装とテストの決定である（P9）。
2. **読み手が一般の PRD の像を持ち込みうる。** 初めて読む人や、新しく入る AI エージェントが「PRD」から製品の要求書の形（ユーザーストーリー、PM の文書）を推し、anet の文書の読み方・書き方を取り違えうる。
3. **用語集に注記しても、名前は残る。** 「PRD」は追跡しているファイル 924 本に 13,415 か所あり（P1）、skill 名・ファイル名・課題の欄・コミット件名・テストのタグのような、人が目にし機械が読む名前にも入っている（P2）。注記だけでは、名前を目にする場所ごとに取り違えの入口が残る。

### 1.2 ゴール

- **G1**: 中身に合う呼び名を 1 つ決め、今使っている場所（P2 のすべて）を新しい名前へ移しきる。
- **G2**: 過去の記録は書き換えない。そのうえで、旧い名前のままの記録から今の文書へたどれ、道具が切り替えの前後のコミットを数え漏らさない。

## 3. 背景

### 3.1 呼び名の来歴

anet の PRD づくりの skill は、グリルの規律を Matt Pocock 氏の `grill-with-docs` から派生し、文書の呼び名は同氏の `to-prd` に由来する（P9）。その後、anet の文書は、前提の表・実装契約・移行対象・受入の観測可能性のような、外から確かめられる契約を書く形へ育った（P8）。[PRD114](114_findings_intake_and_fix_prd_10prd.md)・[PRD120](120_issue_work_type_and_prd_link_10prd.md) で状態と順序を課題へ移し、文書は指示文書になった（P7）。実装したあとの今の仕様は、設計文書と src が持つ（P8・P11）。

### 3.2 グリルの材料

発言と案を分けて置く。どれも決定ではない。

- 開発者の発言（2026-11-21）: 「anetで言ってるPRDって言葉、MattPopock氏のフレームワーク由来だけど、本来のPRDとは違いますよね？ どっちかというとSPEC駆動開発のspecに近い？」
- AI の答え（2026-11-21）: 本来の PRD・`to-prd`・SDD の spec を比べ、anet の文書は 1 回の変更の仕様と判断の記録であり、spec の中でも OpenSpec の change（今の仕様と変更提案を分ける）や KEP・PEP に近いとした。呼び名を変える手間が大きいので、用語集に「PRD」の項目を足す案を示した。
- 開発者の発言（2026-11-21）: 「半端にしたくない。PRDという呼び名自体を改名したい。」
- AI の案（2026-11-21）: ゴール G1・G2、非ゴール 5 行、共通の前提 P1〜P9 を示し、この先の論点の見込み（新しい呼び名、保管場所の文書の改名、件名の書き方と道具の読み方、skill 名と課題の欄、テストのタグと識別子、ADR、リポジトリの外の memory）を挙げた。
- 開発者の発言（2026-11-21）: 「Ｏｋ。ただ、一旦、Issueと暫定PRDを作ってください。」
