## 1. 目的と問題

2026-07 のコアの詳細レビューが挙げた性能の改善候補 5 件を、repo の中に正本として置き、今も残っているかを確かめたうえで、直すかどうかを 1 件ずつ決められるようにする。

問題は 2 つある。

1. 候補が Claude Code の memory にだけあり、Codex からも、ほかの PRD づくりからも引けない。
2. 3 か月のあいだにコードが変わり、どれが今も残っているかが分からない（§2）。

### ゴール

- 5 件それぞれについて、今のコードで残っているか、残っていれば step あたりの費用がどれだけかを確かめる。
- 残っていて効果の見込めるものについて、直すかを決め、直すものは挙動を変えずに直す。

### 非ゴール

- 監査に性能の観点を足すこと。退ける案は「anet-audit に perf の観点を足して台帳に載せる」案で、台帳の観点の集合と巡回の順を変える別の関心になる。本当の制約ではないので、性能の候補が増え続けると分かったら別の PRD で扱う。
- 5 件以外の性能の改善（GPU の計算の予算、replay の Push の細かい最適化など）。

## 3. 提案の骨子（暫定）

1. 5 件それぞれについて、今のコードで残っているかを確かめる。残っていないもの（直っている、形が変わって当てはまらない）は、理由を本文に書いて閉じる。
2. 残っているものは、ProfileRange などで step あたりの費用を測る。比べ方は、同じ機械で交互に回し、複数の Run の終盤のブレ幅を超えて初めて差とみなす。
3. 効果が見込めるものだけを直す。直すときは、[リファクタリング観点](../quality/refactor.md)のガードレールに従う。hot path に触るなら性能をブレ幅基準で確かめ、RNG の呼び出し順・走査順・並列化に触るなら同 seed の再現性を確かめる。挙動を変えていないことは、同 seed の metrics checksum の一致で確かめる。

## 4. 作らないもの・先送り

| 項目 | 裁定 | 理由と再開条件 |
| --- | --- | --- |
| 監査に性能の観点を足す | 範囲外（別の関心） | §1 の非ゴール。性能の候補が増え続けると分かったら、anet-audit の観点の PRD として起こす |
| 5 件をまとめて 1 つの変更で直す | 不採用（暫定） | 件ごとに効き目と再現性への影響が違い、まとめると差を切り分けられない |

## 5. User Stories

1. 性能を詰める人として、過去のレビューが挙げた改善候補を、memory に頼らずに repo から引きたい。
2. 性能を詰める人として、どの候補が今も残っていて、step あたりいくら効くかを知ってから、直すかを決めたい。

## 6. 決めること（詳細設計で詰める）

| # | 決めること | 暫定の既定 |
| --- | --- | --- |
| 1 | 各件が今も残っているか（§2 の要確認） | 着手時に確かめる |
| 2 | 費用の測り方（どの構成・何 step・何 Run） | 実時間優先の Atari 構成と LunarLander の CPU 構成で、交互に回して比べる |
| 3 | 直すものの範囲と順 | 測った費用の大きい順 |
| 4 | 2 の「録画中だけ」の判定をどこで持つか | 録画の開始・終了を知っている側（決定点）で、capture の要求として渡す |
| 5 | 3 の StepResult の使い回しと、PRD 097 の Step の結果の受け渡しの関係 | PRD 097 の契約を変えない範囲でだけ使い回す |

## 7. 成功の測り方と受入の目安

- 5 件それぞれに「残っている／直っている／当てはまらない」の判定と根拠（ファイルと行）が、本文にある。
- 直したものは、step あたりの時間が、交互に回した複数の Run のブレ幅を超えて縮み、同 seed の metrics checksum が直す前と一致する。

## 8. 依存と順序

- 095 の段階 2 の 2026-07 の監査の指摘の登録と同じ時期に、§6 の 1 を確かめると手間が少ない（同じ memory の同じ節を読むため）。順序の依存は無い。
