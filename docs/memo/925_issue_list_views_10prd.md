## 1. 目的と問題

issue の一覧を、人が開いて眺め、次に何をするかを決めやすい形で見せる。

- PRD114 のあと、すべての仕事（PRD の索引の issue を含む）が issue になり、件数は 100 件を超える見込みである（台帳から 44 件、直下の PRD の索引の issue 64 件、以後の工程末の分）。
- 一覧の skill（`anet-list-issues`）は会話の中で表を出すが、開けばいつでも見られるファイルは、PRD114 の最小の一覧（`docs/management/issues/INDEX.md` と wiki の地図の「課題」の区画）だけである。
- 親子（`parent`）と依存（`depends`）の関係は、表では読み取りにくい。
- 表計算のソフトで並べ替え・絞り込み・書き込みをしながら見たい場面がある。

## 2. 現状（PRD114 の実装のあと）

1. issue は `docs/management/issues/issue-YYYYMMDD-xxxxxx.md` に 1 課題 1 ファイルで、frontmatter に状態・監理の項目（`priority`・`depends`・`parent`・WSJF）・`area`・`type`・`ai_judge`・`docs` を持つ（PRD114 §5.1）。
2. 一覧の skill は、依存と WSJF の順に並べ、`area`・`type` で絞り、「束ね」と「棚卸し」で提案する（PRD114 D12・§5.1）。
3. 最小の一覧は、`reports/tools/wiki_support.py` が `INDEX.md`（一覧の skill と同じ並び）と wiki の地図の区画を作り直す（PRD114 D21）。
4. 課題の skill と発番は、anet の skill と文書として持つ（PRD114 D2）。
5. `docs/` 配下は GitHub Pages に配信される（skills README の anet- スキル共通の約束）。

## 3. ゴール・非ゴール

- G1: 依存と親子を、木や図で見られる。
- G2: 一覧を、表計算のソフトで開いて並べ替え・絞り込みができる。
- G3: 一覧の表を、状態・優先度・WSJF・`area`・`type`・AI の判定で絞り込み、並べ替えられる見やすい形で見られる。
- 非ゴール: issue の記録を一覧の道具から書き換えること（一覧は派生物で、記録を変えるのは課題の skill だけ）。

本節で使う語を次のように置く。どれも仮の呼び方である。

| 語 | 意味 |
|---|---|
| Viewer | issue の一覧を人が見るための独自のアプリ |
| 選定 | 問いに答えて AI が選んだ issue の集合と、選んだ理由。保存した絞り込み条件と違い、AI の判断を含む |
| 鏡 | 正本は repo のファイルのまま、外部のチケット管理へ一方向に写し、そちらでは見るだけにする使い方 |

### 8.1 ユーザーの発言

| 話題 | 発言の要点 |
|---|---|
| 正本 | 正本は issue の単票 Markdown がよい。現状の制約である |
| 時差 | 編集のない Viewer でも、正本と見えるものの時差や整合性は気になる |
| 見る場所 | スマホからも見たい。Tailscale 経由で自宅のサーバーにつないでいるので、独自サーバーでもよい。VPS を借りて構築してもよい |
| 編集 | まずは見るだけが無難か。ただし、将来の AI 連携と編集の導入は検討しておきたい |
| 更新の経路 | UI がどうなるかは別として、更新は AI 経由に統一したい（せざるを得ない） |
| ハーネス | 主戦場は Claude Code と Codex のネイティブアプリのハーネスなので、親和性を優先するなら、プラグインなどでハーネスに組み込むのが一番よいのではないか |
| 既製か独自か | Obsidian は Viewer として欲しい機能の多くが素でできる。ただ、AI ネイティブならこの程度のアプリは割と簡単に作れるはずで、用途に特化するなら独自アプリに魅力を感じる |
| 画面 | Obsidian と Redmine はできることは同じでも、Redmine のほうが使いやすく感じる。ただの慣れかもしれない |
| 需要 | 一番の需要は、次にどの issue に対応するかを選ぶこと。次に、全体を俯瞰して状況を見ること。あとは健全性のチェック |
| AI 支援 | 自然言語で抽出条件を書くと良い感じの一覧になる支援が欲しい。ハーネス側の skill で指示し、結果の一覧だけ良い感じに出るとよい。画面に AI 向けの入力欄があってもよいが、入口はやはりハーネスである |
| 選定の時差 | AI 支援の検索は機械の条件として保存できず、検索した時点と最新で結果が食い違う。まずは割り切って、その場限りか短時間の結果にするか。ただし、出た一覧を自分の視点で分析することは要る |

### 8.2 ユースケース案

★ は 1 本目の候補である。各表の「選んだあと」は、更新を AI 経由にするため、AI への依頼として書く。

**A. 次に対応する issue を選ぶ**

| # | 場面 | 見たいもの | 選んだあと |
|---|---|---|---|
| ★A1 次の 1 件 | 手が空いて、次の仕事を決めるとき | 手を付けられる issue の上位。やりかけ（対応中・調査中）を先頭に。各行に WSJF、手間、「片付けると何件の待ちが解けるか」 | 本文を読み比べ、「PRD を起こす」「この場で直す」「別の枠へ渡す」のどれかを AI に頼む |
| ★A2 空き時間の小仕事 | Run を待つ間など、時間が短いとき | 手間が小さく、PRD の要らない直し（不具合・ずれ）だけ | 「この場で直して」と頼む |
| A3 束ねて PRD に | まとまった仕事を作りたいとき | 領域ごとのまとまりと、まとまりごとの WSJF | ID の列を `anet-create-prd` に渡す |
| A4 周辺の issue を拾う | PRD を書く前、実装の前 | その領域の未解決の issue。ついでに片付くもの、ぶつかるもの | PRD の題材に加える |
| A5 実装に回す PRD | 実装に渡す仕事を選ぶとき | PRD の索引 issue のうち、グリルが済んで実装に渡せるもの | 実装の依頼を作る |
| ★A6 文脈つきの選定 | 文脈を持ち込んで候補を絞りたいとき（§8.3 の例 1・2・4・7） | 問いに対して AI が選んだ候補と理由 | チェックを付け、依頼文を作って AI に渡す |
| A7 リリースの整理 | 次のリリースの内容を決めるとき（例 5） | 前回の tag から解決した issue と、入れる予定の issue | CHANGELOG の下書きを頼む |
| A8 外部の記録との突き合わせ | 実験記録などと照らして残りを整理するとき（例 3） | AI が実験記録・PRD・issue を読んで出した起票候補 | 選んだものの起票を頼む |

| # | 場面 | 見たいもの |
|---|---|---|
| ★B1 一目で状況 | 週の始め、出先からスマホで | 区分ごとの件数（手を付けられる・待ち・保留・次版・解決）、やりかけ、直近 1〜2 週に増えた件数と閉じた件数 |
| ★B2 PRD を軸に | PRD ごとの進み具合を知りたいとき | PRD の索引 issue の下に題材の issue を並べた木と、子の解決の割合 |
| B3 領域の偏り | 監査や束ねの対象を決めるとき | 領域 × 状態（または性質）の件数の表 |

**C. 健全性を確かめる**

| # | 何を見るか | 例 |

### 8.3 実際に起きている選び方の例

ユーザーが挙げた直近の例である。どれも「WSJF の順に次の 1 件」ではなく、文脈を持ち込んで候補を絞る選び方で、今の issue の項目だけで答えられるものはほとんど無い。

| # | 例 | 選ぶ軸 | 今の記録で答えられるか | 要るもの |
|---|---|---|---|---|
| 1 | TempoRL の評価が一旦落ち着いたので、メトリクス構成など既存の互換性に影響するが今ならできることを優先したい | 時機 × 互換への影響 | 答えられない。項目が無く、本文に「互換」とある issue は 1 件 | AI が本文から影響を判定する |
| 2 | NGU 対応の前にやっておくと効果的なことを片付けたい | 先の取り組みの前提か | 一部。NGU に触れる issue は 1 件あるが、`depends` は全件空 | NGU の索引 issue へ `depends` を張る。そうすれば依存の木で見える |
| 3 | 実験記録と照らし合わせて、TempoRL の評価の残りを整理したい（issue とは別かもしれない） | 実験記録との突き合わせ | 答えられない。題名に TempoRL を含む issue は 2 件、ファイル名に temporl を含む実験記録は 6 本。残りは PRD や実験記録に散らばっている | 下の「実験の残りの扱い（案）」 |
| 4 | 今週はユーザビリティ向上に関連した活動を重点にしたい | 領域をまたぐテーマ | 答えられない。言葉で拾える issue は 0 件で、RunnerApp・Metrics Viewer・GUI の領域でおおよそ拾えるだけ | AI がテーマを判定する。今週の重点を置く場所 |
| 5 | 次のリリースに含める内容を整理したい | 版 | 一部。状態に「次版」はあるが、どの版に入れるかは無い | 前回のリリースから解決したもの（git の範囲）と、入れる予定のもの |
| 6 | StampFly 関連の活動ができていないが、どうするか | 取り組みの進み具合 | 答えられない。issue は 0 件で、`docs/StampFly.md` だけがある | 取り組みごとの件数と最後に動いた日。「進め方を決める」issue |
| 7 | クレジットが余っているので、消化できて効果的な作業を振りたい（housekeeping 以外で） | AI に任せられるか × 規模 | 答えられない | 対応方針が決まっていて確かめ方もある、という AI の判定 |

**軸を 2 つの仕組みに分ける案**

- 記録に持つ軸（何度も使うもの）。テーマ（TempoRL・NGU・StampFly・使い勝手など）と版。`area` はコードの場所で、テーマは目的なので、関心が別である。「NGU の前提」は、二重に持たないよう、テーマにせず `depends` で表す。
- AI に問う選定（そのときだけの文脈）。例 1・4・7 のように問いがその場限りのもの。仕組みは §8.9。

**実験の残りの扱い（案）**

- issue にするもの: 次に回す Run、待っている比較の判断。状態と順序を持つ作業なので、「作業の状態と順序は issue で持つ」（[ADR 0068](../adr/0068-work-state-and-order-live-in-issues-prd-stays-an-instruction-document.md)）に沿う。性質は調査で、`docs` に実験記録と PRD を書く。
- 実験記録に置くもの: 結果、数値、解釈。issue には写さない。
- 「実験記録と照らして残りを整理する」こと自体は、AI の分析である（A8）。Viewer の側は、issue から実験記録を開ければ足りる。

**独自アプリと Obsidian の比較**

| 観点 | 案 1: Obsidian は PC と試作に使い、スマホ用は独自 Viewer を作る | 案 2: Obsidian を本命にし、木と依存の図は Bases の表示の形を自作する | 有利な案 |

| 性能（表示の軽さ） | 十分 | 十分 | 差なし |

| 保守性 | 自分の道具なので自由。そのぶん全部を保守する | Obsidian の版の変化に追従が要る（Bases はまだ開発中） | 差なし |
| スマホ | ブラウザで見られる。開発 PC で動かせば時差なし | アプリとファイルの同期が要る（同期のぶん時差あり） | 案 1 |
| AI の選定を見せる | 自由に作れる | 表示の形を自作すれば可能だが、絞り込みの画面は汎用のまま | 案 1 |
| ハーネスとの親和性 | 同じ（どちらも正本は同じファイルで、書くのは AI 経由） | 同じ | 差なし |

独自にする価値は次の点にある。

- 次の候補: 待ちのない未着手を、依存を踏まえて WSJF の順に並べる。
- 親子の木と依存の図。
- 画面での形の検査。AI が書いた記録の点検にもなる。
- repo 全体へのリンク。`docs` の欄から PRD・ADR・wiki を開ける（Obsidian は保管庫の外へたどれない）。
- git の情報。見ているブランチ・コミット・未コミットの件数と、各 issue がいつ変わったか。
- AI への橋渡し。選んだ issue から依頼文を作る。
- スマホ向けの見せ方を自分で決められる。
- 課題管理の言葉で話す画面（§8.10）。

作る前に決めておくことは次のとおりである。

| どこが | なぜ問題か | 手当ての案 |
|---|---|---|
| ファイルを読む処理が 2 つに分かれる | skill の書き方と Viewer の読み方がずれると、表が気づかないうちに崩れる | 読む処理と検査する処理を道具 1 本にまとめ、Viewer も skill もそれを使う |
| スマホの画面 | 13 列の表はスマホに収まらない | 狭い画面ではカードと絞り込みを中心にする |
| 機能が膨らむ | 見るだけのつもりが、編集まで広がりやすい | 書く機能は持たず、依頼文を作るところまでを境界として本書に書く |
| 保守 | 自作の道具は自分で直し続ける | 外部のライブラリを、YAML の読み込み・Markdown の表示・図の描画くらいに絞る |

規模の見立ては、1 本目（表・本文・木・時差なし・スマホ対応）がサーバーと画面を合わせて千数百行である。時間がかかるのは、組むことより見せ方を決める往復である。

### 8.7 正本と表示の時差、スマホから見る形

ずれの原因は 3 つある。

| 原因 | 何が起きるか | 対策の案 |
|---|---|---|
| 一覧ファイルを作り直す方式 | `INDEX.md` や HTML を作る方式だと、作り直すまで古いまま | 一覧ファイルを持たず、開くたびに issue のファイルを読む。ファイルの変更も監視する |
| どの時点のファイルを読むか | サーバーが GitHub から取ってくると、push（人の操作）まで古い | Viewer を、正本の作業フォルダがあるマシンで動かす |
| ブランチ・worktree | ほかのブランチで起票した issue は、main に merge するまで main の一覧に出ない | main の作業フォルダの一覧を正とし、ほかのブランチにまだ merge されていない issue があれば件数だけ出す（要検討） |

画面の頭に、どの作業フォルダ・ブランチ・コミットか、未コミットの issue が何件か、いつ読んだかを出す。ずれがあっても、見て分かるようにするためである。

| 置き場 | 時差 | 開発 PC が落ちているとき | 手間 |
|---|---|---|---|
| 開発 PC で動かし、`tailscale serve` で Tailscale の中だけに公開する | なし（作業フォルダをそのまま読む） | 見られない | 小 |
| 自宅のサーバー | 同期の方法による（git pull なら push まで遅れる。Syncthing なら数秒） | 見られる | 中 |
| VPS | push まで遅れる | 見られる | 中 |

開発 PC が常時起動しているなら、1 つ目がずれは最小である。小さな Node のサーバーは GPU を使わないので、Run の邪魔にもなりにくい。

### 8.8 ハーネスとの関係

- 親和性を生むのはプラグインという包みではなく、その中身の skill と MCP である。Claude Code のプラグインは skill・コマンド・エージェント・hooks・MCP サーバーを束ねて配る仕組みで、Codex のプラグインも skill・MCP・アプリ連携を束ねる（§8.12）。両方に共通する部品が skill と MCP である。
- anet は skill を `.claude` と `.agents` の両方に置いているので、この repo の中ではすでにハーネスに組み込まれた状態である。プラグインにして効くのは、ほかの repo へ配るときと版を付けるときである。
- ハーネスの中に表を出す手段もある。Claude のデスクトップアプリの mod（会話の横に常に出る枠。Claude だけ）と、MCP Apps（会話の中に操作できる画面を出す MCP の拡張）である。MCP Apps が Claude Code のローカル接続と Codex で動くかは確認できていない。どちらもスマホには届かないので、人が主に見る画面は Viewer を別に持つ案とする。

形の案は次のとおりである。

```text
正本  docs/management/issues/*.md
  ↑ 書くのはここからだけ
issue の道具（読む・形の検査・書く・WSJF・依存の検査）
  ↑ 呼ぶ                  ↑ 呼ぶ（必要になったら）  ↑ 読むだけ
skill（Claude・Codex）    MCP サーバー              Viewer（PC・スマホ）
```

- 今は、AI が skill の指示に従ってファイルを直接書く（道具を使うのは発番だけ）。書く処理を道具 1 本に寄せると、書き方の揺れが減り、Viewer も同じ読み方を使える。
- 将来 Viewer に編集ボタンを付けるときは、ボタンが記録を直接書くのではなく、「この issue を保留にして」のような AI への依頼文を作る。画面を増やしても、更新が AI 経由のままになる。

### 8.9 自然文の選定

**流れの案**

```text
ユーザー ─ 自然文の問い ─▶ ハーネス（Claude Code・Codex）
                            │ skill
                            ├─ 1. 索引で粗く絞る（frontmatter と題名だけ）
                            ├─ 2. 候補の本文だけ読んで判定し、理由を付ける
                            └─ 3. 選定ファイルを書く（道具が形を検査する）
                                      │
会話に出すのは件数・上位数件・URL       ▼ ファイルの変更を監視
                            Viewer（PC・スマホ）
                             理由、今の状態、選定のあとに変わった印を見せる
                             チェックを付ける → 依頼文をコピー → ハーネスへ
```

選定ファイルの形の例を次に示す。

```markdown
---
id: sel-YYYYMMDD-xxxxxx
question: 互換に響くが、TempoRL の評価が落ち着いた今ならできるもの
created: YYYY-MM-DDThh:mm
commit: （選定したときのコミット）
basis: 本文の「影響」「対応方針」で、設定のキー・tag・checkpoint・golden を変えるもの
items:
  - id: issue-…
    group: メトリクス
    reason: （選んだ理由）
---
（AI の所見: 1 本の PRD にまとめられる組、先に要る判断など）
```

**問いの結果の 4 種類**

| 種類 | 例 | 時差 | 扱いの案 |
|---|---|---|---|
| 機械の条件に訳せる問い | 「318_rl_core の不具合で手間が小さいもの」 | 無い | AI が問いを機械の条件に訳し、その条件を保存する。開くたびに最新で評価する |
| AI の判断・その場限り | 「今週の重点に合いそうなもの」 | 気にしなくてよい | 使い捨てか短い時間だけ。1 本目はここで割り切る |
| AI の判断・残すもの | 「互換に響くが今ならできるもの」 | ある | 判定した時点を明記し、今の状態を重ねて見せる |
| 何度も出る判断 | 互換への影響、AI に任せられるか | 項目の鮮度だけ | issue の項目に格上げする（`ai_judge` と同じ扱い）。そこからは機械の条件で引ける |

**残す選定の時差の手当て**

- 時点: 選定したときのコミットを記録する。その時点の issue の内容は git から戻せるので、中身の写しを別に持たない。
- 選ばれた issue が変わったとき: 今の状態を正本から読んで重ね、「選定のあとに解決した」などの印を付ける。
- 選定のあとに増えた・変わった issue: 「この選定のあと、起票 3 件・変更 2 件はまだ判定していない」と示す。選定がどこまでを見て判断したものかを分かるようにする。
- 問い直し: 全件をもう一度判定せず、判定していない差分だけを問い直す。
- AI のぶれ: 同じ問いでも AI は毎回少し違う集合を返す。判断の基準を選定ファイルに残して問い直しにも使い、結果は「新しく入った issue・外れた issue」として理由付きで出す。

1 本目は、その場限り（短時間）の選定に今の状態を重ねる形とする案である。判定していない差分の表示と差分だけの問い直しは、そのあとに足せる。

**出た一覧を自分の視点で分析する**

選定を Viewer の中で、ほかの絞り込みと組み合わせられる集合として扱う。「この選定」かつ「状態: 本版」かつ「領域: 318」のように重ねて絞り込め、AI が付けた理由・まとまり・点数は列として並べ替えやまとめの軸に使える。AI は候補の集合を選び、どう切り分けて見るかは人が画面で決める、という分担である。

**画面の AI 入力欄**

足すとしても、Viewer が自分で AI を呼ぶ作りにせず、依頼文を作ってコピーするだけにする案である。Viewer が AI を直接呼ぶと、入口がハーネスと Viewer の 2 つになり、権限と API キーの管理も Viewer に持ち込まれる。

**入口の skill**

| 観点 | `anet-list-issues` に自然文の引数を足す | 別の skill にする（仮名 `anet-select-issues`） | 有利な案 |
|---|---|---|---|
| 使い勝手 | 入口が 1 つで済む | 入口が 2 つになる | 引数を足す |
| skill の分かりやすさ | 「記録を変えない、決まった並び」の skill に、AI の判断とファイルの書き込みが混ざる | 関心が分かれる | 別の skill |
| 保守性 | 引数が既知の語か自然文かを見分ける必要がある。今は未知の値で止まる作りである | 重なる部分（読み込み）は道具に寄せれば小さい | 別の skill |
| 性能 | 変わらない | 変わらない | 差なし |

### 8.10 画面（Obsidian Bases の試用と Redmine との比較）

試用は `docs/management` を保管庫にし、状態・工程ごとのまとめと WSJF の並べ替えを持つ `.base` で行った（`.base` と保管庫の設定は repo に残していない）。docs 全体を保管庫にしないのは、Doxygen の出力（`docs/html` だけで 17,190 ファイル・143 MB）まで読み込むためである。

Bases の仕掛けは次のとおりである。Viewer でも同じ考え方を使える。

- frontmatter を YAML として読んで内部の索引に入れ、ファイルの変更を監視して、変わったファイルだけ読み直す。
- 型は値の形から推定する（数値は数値順、リストは札で表示）。
- `.base` は問い合わせの定義で、データを持たない。画面の操作はこのファイルに保存される。

標準でできないことは、左の列の固定、親子を入れ子にした木、`depends` の ID から依存の図を描くこと、Web サーバーとして配信することである。かんばんでカードを動かすと frontmatter が書き換わるので、見るだけなら眺めるだけにする。

スクリーンショットで比べた差を、次にまとめる。慣れのほかに、画面に次の理由がある。

| 観点 | Redmine | Obsidian Bases | Viewer の案 |
|---|---|---|---|
| 言葉 | 未完了、トラッカー、対象バージョン | 生のキー名に、is not、links、ファイル | 列名は状態・WSJF・優先度・領域。「未解決」「本版」を 1 回で選べる値にする |
| 絞り込みの選び方 | 「ステータス: 未完了」を 1 回選ぶ | 「is not 解決」かつ「is not 次版」と除外を積む | 肯定で選ぶ |
| 絞り込みの見え方 | ページの上に常に出ていて、条件は URL に残る | 浮いた窓で、開くと表を隠す。閉じると条件が見えない | 上に札で並べ、条件を URL に入れてスマホとも共有できるようにする |
| 情報の密度 | 行が低く、番号が短く、題名に幅を使える | 行が高く、`issue-20261103-…` が幅を取る（移し替えた issue は日付が同じで、見分けは末尾 6 文字だけ） | 行を低くし、ID は末尾 6 文字だけ見せる。題名に一番幅を使う |
| まとまりの見出し | 「要件 7」「バグ 33」と件数付き | 「area 110_runner_app」とキー名が前に付く。値が空のまとまりは「area」だけ | 値と件数を見せ、折り畳める |
| よく使う問いへの導線 | 右の欄に、保存した問い・版・サマリー | 左上の切り替え欄 | 横の欄に、保存した問い・選定・版・集計表 |
| 行から次の操作へ | 行のチェックでまとめて操作。設定で行の下に説明を出せる | 無し | 選んだ issue から依頼文を作る。切り替えで「事象」の 1 行目を行の下に出す |

### 8.11 §4・§6 の既定と合わなくなる点

§8 の案を採るなら、次の既定は再グリルで見直す。

- D1: 1 枚の HTML と Mermaid と CSV に分ける形。Viewer の中の画面になる。CSV は書き出しとして残すかを決める。
- D2: 道具の役目が「出力を作る」から「読む・検査する・書く」に広がる。
- D3: 引数「書き出し」は、一覧ファイルを持たないなら要らない。
- D4: `index.html`・`tree.md`・`issues.csv` を派生物として置く形。一覧ファイルを持たない案と合わない。
- §1 の「書き込みをしながら見たい」と §3 の非ゴールの関係。R14・R15 で決める。
- §6 の 1・4・5: Viewer の見た目、更新のきっかけ、GitHub Pages の扱いは、Viewer を動かすなら前提が変わる。
