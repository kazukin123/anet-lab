## 1. 目的と問題

課題の置き場を、台帳から issue（`docs/management/issues/` に 1 課題 1 ファイル）に替える。issue の仕組み（課題の skill 3 本・発番・置き場の決まり）は anet の skill と文書として持ち、anet のプロセス契約の節と anet の値で書く。すべての PRD に issue を 1 件伴わせ、作業の状態・優先度・依存・順序は issue で持ち、PRD は指示文書のままにする。

解く問題は次の 5 つ（事実は §2）。

1. 工程の最後の起票候補で「新規」を選ぶと、置き場は 999 の暫定 PRD しかない。小さな修正も 1 件 1 本の PRD になり、「小さな修正では PRD を起票しない」運用と合わない。
2. 台帳は回っていない。37 件を 1 ファイル（1 行 1 課題の JSON）で持ち、人が開いて読みにくい。工程の最後の起票候補からは使われず、片付ける入口も無い。
3. 同じ種類の課題が、見つけた工程によって 999 PRD と台帳に分かれる。
4. PRD は指示文書なので、優先度・依存・作業順を持てない。直下で片付いていない PRD は 64 本あり、順序は番号（9xx の下 1 桁）でしか表せない。
5. 999 の PRD は 39 本が同じ番号で、番号では区別できない。

### 1.1 用語

本書の語はハーネス（エージェントの作業環境）の語で、フレームワークの語ではないので、[CONTEXT.md](../../CONTEXT.md) には足さない。既存の語で言い換えられないものだけを次のとおり使う。

| 語 | 意味 |
|---|---|
| issue | 課題記録（レジストリの成果物キー `issue-record`）。`docs/management/issues/` に 1 課題 1 ファイルで置く。不具合・ずれ・改善・案・調査・索引のどれでもよい。`.scratch/` に置く実装の単位（[issue-tracker](../agents/issue-tracker.md) の「Implementation issue」）とは別のもの |
| 共有コア | プロジェクトに依存しない文面で持つファイル。anet 固有のことはレジストリの読み替えと観点に置く（ADR 0049）。対象はプロセス契約とレビューエージェントの定義で、課題の仕組みのファイルは含めない（D2）。名前（skill・エージェント・アダプタの名前）は `anet-` で始まる名前にする（D3） |
| 台帳 | `reports/registry/findings.jsonl`。本書で退役させる |
| 仕事は issue・指示は PRD | 作業の状態・優先度・依存・順序の正本は issue とし、PRD はその issue を解く指示文書とする分け方（D9） |
| PRD の issue | PRD 1 本に対応する、`type: 索引` の issue。対応する文書の欄（`docs`）でその PRD を指す。題材の issue は、その子（`parent`）になる（D10）。今ある PRD に作るものを、とくに索引の issue と呼ぶ（D15） |
| AI の判定の欄 | issue の frontmatter のうち、AI が `anet-update-issue` の「判定」で自動で書き換えてよい欄（`ai_judge`・`ai_judged`）。人の判定（`status` と監理の項目）とは分ける（D8） |
| この場で直す | 工程の中で見つけた小さな課題を、PRD を起こさずにその工程の中で直すこと（D7） |
| issue の対応表 | issue を題材にしたか範囲に取り込んだ PRD が持つ表。issue ごとに、直す確定事項と確かめる受入を指す（D20） |
| 工程の最後の起票候補 | [プロセス契約](../process/protocol.md) §7 の、工程の完了判定で未解決のものを候補に挙げて開発者が選ぶ手順。anet では anet-create-prd の段 7 と implement-prd-with-docs の工程末で行う |

## 3. ゴール・非ゴール・成功の測り方

### 3.1 ゴール

- G1（入口）: 工程の最後の起票候補から、課題を issue（1 課題 1 ファイル）として記録できる。小さな直しはこの場で直せる。
- G2（出口）: issue をまとめて 1 本の PRD にでき、そのあとは通常の PRD と同じ流れで片付く。
- G3（一本化）: 課題の置き場を issue に一本化する。台帳は退役し、監査と anet-improve も issue に書く。すべての PRD に issue を伴わせ、作業の状態・優先度・順序は issue で持つ。

### 3.2 非ゴール

- プロセス契約を anet 向けに書き換えること。退ける案は「プロセス契約に issue の区分や anet の値を書き足す」案である。ADR 0049 の判断（共有コアはプロジェクトに依存しない文面に保つ）による本当の制約で、anet 固有のことはレジストリの読み替えに置く（D4）。課題の仕組みのファイルは共有コアに含めないので、この制約を受けない（D2）。
- 一覧の見せ方を作り込むこと（依存のツリー、スプレッドシート、見やすい HTML、`anet-list-issues` への機能の足し方）。退ける案は「本書で一覧の道具まで作る」案である。本当の制約ではなく、別の関心として別の PRD にする（§8）。
- anet-housekeeping の候補にすること。退ける案は「定常整備で PRD を自動で起票する」案である。本当の制約である。housekeeping は了承のあと判断を既定値で進めて質問しない（[anet-housekeeping](../../.agents/skills/anet-housekeeping/SKILL.md) 78 行目）が、PRD の起票はグリルの質疑を挟む。
- GitHub Issue を課題の置き場にすること。本当の制約である。エージェントが repo の中を検索して読む流れの外にあり、投稿のたびに外部への書き込みになる。

### 3.4 成功の測り方

- 本書の実装のあと、最初の 5 回の工程の最後の起票候補（anet-create-prd と implement-prd-with-docs を合わせて数える）で、次を数える。
  - 候補のうち、issue にした件数、この場で直した件数、999 の暫定 PRD にした件数。999 にした件数が 0 であれば G1 を満たす。
  - この場で直した件のうち、直した分のレビューが OK になってから完了報告したもの。全件であれば D7 の流れが守られている。
- issue を題材にした PRD を 1 本起こした時点で、次を満たせば G2 を満たす。
  - レビュー（項番 38 を含む）が OK になる。
  - 題材の issue がすべて、`parent` で PRD の issue を指し、PRD の issue の `docs` が PRD を指す。
- 移し替えのあと、次を満たせば G3 を満たす。
  - `docs/memo/` 直下の PRD のすべてに、対応する文書の欄でその PRD を指す issue が 1 件ある。
  - 台帳のファイルと CLI が無い。

- 分類を `scope` の先頭に機能カテゴリの key を書く決まりで持つ — 不採用: 自由記述の欄に機械が読む決まりを重ねるので壊れやすく、性質で絞れない（D5）。
- 出口の別 skill（`anet-create-fix-prd` など）を作る、束ねる提案を持たない — 不採用: 別 skill は一覧の並べ方と束ね方の写しになる。提案を持たないと、再グリルで決めた既定 5 件の提案が無くなる（D11・D12）。
- レビューエージェントとプロセス契約の名指しを今の名前のまま持つ、またはファイル名だけ改めて本文の名指しを読み替える — 不採用: 共有コアの名前の接頭辞が 2 つになる。後者は本文と名前が食い違う（D3）。
- 名前の新旧の対応を本書の表に持ち、本書の実装で名前を改める — 不採用: 名前の新旧の対応をリポジトリに置かない（D3）。
- `area` を 1 つの値にする — 不採用: 2 つの機能カテゴリにまたがる課題が、主でない側の地図と絞り込みから漏れる（§6 の 3）。
- 入口の手順を新しい skill（`anet-record-finding`）に持たせる — 不採用: `anet-create-issue` が持つ（D2）。
- `registry.py validate` の F 番号の重複検査 — 不採用: issue の番号は日付と乱数で、ブランチをまたいでも重ならない（§2 の 12）。
- 9xx の PRD を、すべて 900 からの連番、または使われていない帯へ振り直す — 不採用: 900 からの連番は使われた番号を再び使い、過去の記録の番号が別の PRD を指す。使われていない帯へ全部を移すと、今の 910〜941 の 10 本の名前まで変わる（D13）。
- 今ある `done/`・`frozen/`・`dropped/` の PRD を直下へ戻す、`999` 以外の PRD の名前を揃える — 不採用: 123 ファイル・1,049 個のリンクを直すことになる（D14）。
- PRD の実装済みを、番号をスコープに持つコミットで拾う — 不採用: PRD の工程の「この場で直す」のコミットや起草のコミットも拾い、誤る（D22）。
- 一覧の作り込み（依存のツリー、スプレッドシートへの書き出し、見やすい HTML、`anet-list-issues` への機能の足し方） — 先送り: 別の関心（見せ方）で、試作で見比べないと決めにくい。再開条件: 本書の §5.11 の最小の一覧が動いたとき。工程末の起票候補として示し、別の PRD で決める。
- anet-housekeeping の候補にする — 不採用（§3.2）。
- GitHub Issue を課題の置き場にする — 不採用（§3.2）。

## 10. 依存と順序

- 前提: §5.1 の表のファイルの初めの版が作業ツリーの両方の置き場に置いてあり、名前が D3 のとおり揃っていること。どちらも本書の範囲外で、実装する側は行わない。課題の skill 3 本か `anet-review-agent` の定義が無ければ、§5.1 に入らずに止まる。名前が揃ってから §5.1 で検査 4 のパターンを改めるまでのあいだ、検査 4 は共有コアの名前に当たって 0 件にならない。
- 実装の順は次のとおりとする。
  1. 置かれた課題のファイル（§5.1 の表）の確かめ（§7 の 3）、課題の skill 3 本の `agents/openai.yaml`、検査 4 のパターン（§5.1 の「名前」）。
  2. 課題の仕組みの直しと足し（§5.1）とレジストリ（§5.2）と、§7 の 2 の確かめ。
  3. anet の skill（§5.3〜§5.6）と、skills README・AGENTS.md・issue-tracker・refactor.md。
  4. 台帳の 37 件の移し替えと退役（§5.7）。
  5. `999` の振り直し（§5.9）と、索引の issue（§5.8）。
  6. memo README・PRD 品質確認観点（§5.10）。
  7. 最小の一覧・wiki・定点統計（§5.11）。
  8. 試走 A・B・D・E と、§7 の残りの確かめ。
  9. 動線マップの作り直し。
- 試走 C・C2 は次の工程の最後で行う。
- 索引の issue と移した issue の監理の項目（AI の見立て）は、`area` ごとに分けて棚卸しする（棚卸しは本文まで読むので、100 件を超えると 1 回では回らない）。
