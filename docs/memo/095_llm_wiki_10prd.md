## 1. 目的と問題

実験記録・サーベイ・PRD に散らばった知見を、題材（Env・ゲーム）と機構（アルゴリズムの部品・設定の軸・現象）ごとに「今分かっていること」のページにまとめる層を、`docs/wiki/` に足す。あわせて、アプリケーションと機能カテゴリごとに、関係する PRD・ADR・設計文書・ユーザーガイド・src のファイルと、成立の経緯・概要・責務を 1 ページにまとめる「実装の地図」を置く。正本は wiki の外に残し、ページの主張にはすべて出典を付ける。PRD づくり（グリル）が、PRD を起こす前に材料と触る部分を 1 枚で読めるようにし、PRD づくりや Run 分析で分かった知見をページへ戻す。

解く問題は次の 5 つ（詳細は §3）。

1. 知見が時間順（campaign）と種類（実験記録・サーベイ・PRD）でしか並んでいない。ある題材について今どう考えているかを知るには、関係する文書を全部読み直すことになる。
2. 後から覆った結論が、元の記述のまま残っている。撤回は後ろの追記にしか無く、読む側が取り違える。
3. 同じ背景を PRD ごとに書き写している。実験記録に入っていない分析が PRD の背景に散らばっていて、題材から引けない。
4. 事実上の知見の置き場が Claude の memory になっていて、Codex からは読めない。PRD づくりの読む道にも、実験記録とサーベイが入っていない。
5. 実装のある部分について、関係する PRD・ADR・設計文書の章・ユーザーガイドの節・src のファイルと、なぜ今の形かを 1 か所で引けない。設計文書は概要・責務を持つが成立の経緯をほとんど持たず、PRD と ADR は変更・判断ごとに分かれ、atlas（`docs/archify`）はコードから作る構造図で根拠を持たない。PRD づくりの要点提示が求める「触る既存部品の働き」も、毎回あちこちから集め直している。

### ゴール

1. 題材・機構ごとのページを、出典つきで `docs/wiki/` に置ける。目録（`index.md`）と作業の記録（`log.md`）がある。
2. PRD づくりの前に関係するページを読み、PRD づくりや Run 分析で分かった知見をページへ書き戻す。
3. 材料（実験記録・サーベイ・PRD・設計文書・ADR）を 1 本ずつ取り込んで、関係するページを直せる。
4. 撤回の取り残しを、点検で見つけて直せる。
5. Claude と Codex が同じページを読める。
6. アプリケーション・機能カテゴリごとに、関係する PRD・ADR・設計文書の章・ユーザーガイドの節・src のファイルと、成立の経緯・概要・責務を、1 ページで引ける（実装の地図）。

### 非ゴール

- src の中身の要約。PRD づくりは src を直接読む。コードを今の形にまとめるのは docs/design（PRD の下流）の役割で、二重になる。src は、実装の地図のファイルの一覧からリンクする先として扱う。機能カテゴリ間の依存（どれがどれを使うか）も、コードを読まないと分からないので書かない。
- PRD の根拠を wiki に預けること。PRD は self-contained のまま（[README.md](README.md) §工程と担当）で、判断が依存する事実は出典つきで PRD 本文に書く。
- docs/design・ADR・CONTEXT.md・サーベイ・atlas の役割を変えること。実験記録の README の扱いだけは決める（§4.5）。
- `reports/tools/categories.json` の対応を変えること（実装の地図はこの対応を使うだけ。§3 の 110 の直しは、本 PRD とは別に行った）。
- 過去の記録の書き換え。campaign 文書・ADR・done の PRD は当時の記録のまま残す。撤回は wiki のページの側に書く。実験記録の README は campaign 文書の索引と知見の置き場で、段階 3 で仕分ける（§4.5）。
- 検索の基盤（ベクトル検索、全文検索のサーバ）。目録で回る規模である（§2）。
- repo の外の個人の知識管理。

## 2. 背景

LLM-Wiki は、RAG のように質問のたびに元の資料を読み直すのではなく、資料を取り込む時点で LLM がまとめ直し、相互リンクした markdown の wiki に積み上げておく型である（[Karpathy の gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)、2026-04-04）。

- 3 つの層: 元の資料（正本。LLM は読むだけで書き換えない）、wiki（LLM が書いて保つ、中身のあるまとめ。資料ごとの要約、対象・概念ごとのページ、比較、全体像）、規約（wiki の書式と作業の手順）。
- 3 つの作業: 取り込み（資料を 1 本読み、関係するページを直し、目録と記録を更新する）、問い合わせ（目録からページをたどり、出典つきで答える。良い答えはページとして戻す）、点検（矛盾、古くなった主張、どこからもリンクされないページ、抜けたリンク）。
- 目録（1 行 1 ページ）と、追記だけの作業の記録を持つ。資料 100 本・ページ数百までは目録だけで回り、それを超えたら検索を足す、とされている。
- 人が資料を集めて質問し、LLM がまとめと保守を受け持つ。

本 PRD の型は、一般の型と同じく「正本は外、wiki は中身のあるまとめ、索引は目録だけ」である。違いは 2 つある。

- 資料ごとの要約ページは作らない。実験記録（campaign 文書）とサーベイが、すでにその役を担っている。wiki に置くのは、複数の正本を題材・機構ごと、アプリケーション・機能カテゴリごとに束ねたページだけである。
- 「wiki だけにある知見を作らない」を原則にする（§4.1）。一般の型は問い合わせの答えをそのままページにできるが、本 PRD では、知見はまず正本（実験記録・PRD）に書き、wiki はそれをまとめる。

実装の地図も、一般の型の「対象ごとのページ」に当たる。正本は設計文書・ADR・PRD・ユーザーガイドで、src はファイルの一覧からリンクするだけにする（中身は要約しない）。

下流には同じ形の層がすでにある。docs/design は PRD の積み重ねを今の形にまとめた層で、取り込み（PRD の実装と同じ変更で設計文書を直す）と点検（anet-audit の drift）を持つ。欠けているのは上流の、材料を今の形にまとめる層である。

| LLM-Wiki | anet で近いもの | 足りないところ |
| --- | --- | --- |
| 元の資料 | Run フォルダ、`papers/` の PDF、外部の実装、実験記録、サーベイ、PRD | なし |
| 資料ごとの要約 | 実験記録（campaign 文書）、サーベイ・論文解説（`reports/`） | なし |
| 対象・概念ごとのページ | 実験記録の README の判断表と知見の節が一部を担う。実装については、設計文書が概要・責務を、atlas が構造図を持つ | 題材・機構ごとの「今分かっていること」が無い。README の中で要約と独自の分析が混ざっている。実装の部分ごとに、PRD・ADR・設計文書・ガイド・src と成立の経緯を結ぶページが無い（§3） |
| 目録 | `reports/INDEX.md`、`docs/experiments/*/README.md` | 種類ごとに分かれ、題材から引けない |
| 規約 | AGENTS.md、各 skill | 知見の層の規約が無い |
| 取り込み | anet-survey-queue（サーベイを足すところまで）、「採用した知見は README の表へ」の運用（Claude の memory のフィードバックにだけ書かれている） | 題材・機構のページを直す手順が無い |
| 問い合わせと書き戻し | PRD づくり、Run 分析 | 分かった知見の戻し先が無い |
| 点検 | anet-audit の drift（コードと設計文書） | 知見どうし・出典との食い違いを見ない |

## 4. 提案の骨子

### 4.1 位置づけと原則

```text
Run フォルダ・論文・外部の実装
   ↓ 記録・要約
docs/experiments・reports・docs/memo（正本。実装の地図は docs/design・docs/adr も）
   ↓ 取り込み（正本 → まとめの一方向）
docs/wiki（今分かっていること）         ← 足す層（PRD の上流）
   ↓ 読む
PRD づくり ── src も直接読む。CONTEXT.md・ADR・wiki は起草で書く
   ↓            知見はまず PRD の本文に出典つきで書き、wiki はその節をまとめる
PRD（起点）
   ↓ 実装
src ＋ docs/design（PRD の結果の今の形）  ← PRD の下流
```

| 置き場 | 答える問い | 性質 |
| --- | --- | --- |
| docs/experiments（campaign 文書） | 何を測って、何が出たか（当時） | 正本 |
| docs/experiments の README の独自の分析の節 | campaign 文書に無い分析（§4.5 で残すもの） | 正本 |
| reports（サーベイ） | 外で何が知られているか | 正本 |
| PRD | 何をどう作るか。背景に、直す理由・日ごろの検討・Run の結果を持つことがある | 正本 |
| **docs/wiki** | ある題材・機構について、今何が分かっているか。あるアプリケーション・機能カテゴリが何で、なぜ今の形か（実装の地図） | **まとめ（派生）** |
| ADR / CONTEXT.md | なぜその形にしたか／語の意味 | 正本 |
| docs/design / src | 今どう作られ、どう動くか | PRD の下流。設計文書は実装の地図の「概要・責務」の正本でもある（src はファイルの一覧からリンクするだけ） |

- **wiki だけにある知見を作らない。** 主張はすべて wiki の外に出典を持つ。出典と食い違ったら出典を正とし、ページを直す。
- 許す重複は「正本 → まとめ」の 1 段だけである。正本だけを真実として直し、まとめはそれに追随する（docs/design が PRD から作られるのと同じ一方向）。同じ正本の要約を 2 か所に置く「まとめ ↔ まとめ」は作らない。
- memory は出典にしない。今後の知見は、memory ではなく正本（実験記録・PRD）に書いてから wiki に入れる。memory に残すのは、進み具合・作業上の指示・好み・ページへのポインタだけにする。
- 読み手は AI（PRD づくり、Claude と Codex）と人（起票する人、研究者）の両方である。
- wiki から実験記録・サーベイ・PRD・設計文書へリンクを張る。設計文書から wiki へは張らない（設計文書は PRD から作り、根拠は PRD が持つ）。PRD は判断が依存する事実を元の出典つきで本文に書き、wiki のページは「その後分かったこと」の入口として関連の行に添えるだけにする。

コミットのたびの自動更新（hook）はしない。git の操作は人が行う。

### 4.5 段階 3: 既存の材料の取り込み、README の仕分け、memory の移し替え

1. 既存の材料を取り込む。`anet-lint-wiki` の開始 revision による限定を外し、`max` を決めて回す。複数エージェントで数時間かかる規模なので、着手前に見積もってユーザーに確かめる。
2. 実験記録の README 4 本（default-dqn・atari・dropmerge・lunarlander）の知見を仕分ける（ADR 0056）。対象は、知見の節（「現時点の判断」「DQN 系列共通の知見」「評価観点」など）と、campaign 表のセルの要約・日付つきの追記の両方である。
   - 判定: 記述ごとに campaign 文書と突き合わせ、同じ内容が見つかれば要約として扱い、wiki のページに畳んで README から消す（wiki のページは campaign 文書を出典にする）。見つからなければ、campaign 文書に無い独自の分析として README に正本として残し、wiki はその節を出典に引く。
   - campaign 表は索引に縮める。残す列は期間・文書（リンク）・主題と、状態の語（`docs/experiments/README.md` の「状態と確度」の `active`・`completed` など）である。セルの要約と日付つきの追記は、上の判定で仕分ける。判定で campaign 文書に無いと分かった追記は消さず、README の独自の分析の節へ移して残す。
   - 過去の記録との関係: セルの日付つきの追記は、campaign 文書の探索ブロックを README で要約したもので、いつ判断が変わったかの当時の記録は campaign 文書が持つ（campaign 文書は書き換えない）。そのため、要約と確かめた追記を README から消すことは、過去の記録の書き換えに当たらない。
   - 運用: 今の「採用した知見は README の表へ」の運用は、Claude の memory のフィードバックにだけ書かれていて、repo の文書には無い。新しい運用「採用した知見（要約）は wiki へ、新しい独自の分析は正本の側（実験記録、または README の独自の分析の節）へ」を `docs/experiments/README.md` に書き足し、memory のフィードバックを改める。
   - README は campaign の索引と、残した独自の分析の節になる。移した部分は GitHub Pages の docs/experiments からは消え、docs/wiki 側で公開される。
3. Claude の memory の project 型の知見を移す。正本がある知見は、wiki がその正本を引き、memory の側はページへのポインタに置き換える。正本の無い知見は、実験記録に起こすかを 1 件ずつユーザーに確かめる。
4. 実装の地図の残りのページを作る。アプリケーションは 120 MetricsViewer、機能カテゴリは、段階1で作った311を除く categories.json の 31x〜32x の残り13個である（完成時は14個）。

段階 3 は範囲を広げるだけで、途中で止めても取り込んだ分だけ前より良い。

### 4.6 置き場と書式

```text
docs/wiki/
├─ README.md        規約（原則、書式、出典の書き方、更新のきっかけ、機械的な確かめ、公開できない値の走査）
├─ index.md         目録
├─ log.md           作業の記録（追記だけ）
├─ subjects/        題材（Env・ゲーム）。例 kung_fu_master.md
├─ mechanisms/      機構（アルゴリズムの部品・設定の軸・現象・評価の読み方）。例 lane_window.md
├─ apps/            実装の地図: アプリケーション（Topic の 1xx）。例 110_runner_app.md
└─ categories/      実装の地図: 機能カテゴリ（categories.json の 31x〜32x）。例 324_dqn.md
```

- 実装の地図の 2 段: 上の段は「アプリケーション」（RunnerApp、MetricsViewer）、下の段は「機能カテゴリ」である。「機能カテゴリ」は categories.json の定義（ファイルパスとの対応を持つもの）を指し、docs/design の README の章分けの「機能カテゴリ」とは別である（ページから設計文書の章へリンクして関係を示す）。「機能グループ」（`.hpp` / `.cpp` の組）はページにせず、機能カテゴリのページの中の行にする。ファイル名は categories.json の key。
- アプリケーションのページの範囲は、置き場（RunnerApp は `apps/runner/**`、MetricsViewer は `apps/metrics-viewer/**` と `viewers/metrics-viewer/**`）の下のファイルを、先に当たる機能カテゴリごとに並べたものである（置き場の下には、アプリケーション自身の key のほかに、別の機能カテゴリや、どの機能カテゴリにも当たらないファイルがあるため）。アプリケーションが含む機能カテゴリは、この並びから分かる。

- ファイル名は英小文字・数字・アンダースコア。
- 機構のページは仕組みを説明しない。書くのは、効いた条件・効かなかった条件・観測された現象である。仕組みは「関連」で設計文書の章を指す（設計文書の役割を変えないため）。
- ページの節は次の 5 つ。
  - 「今の結論」: 1〜5 行。「分かっていること」の項目の言い換えだけで書き、そこに無い新しい判断を書かない（wiki だけにある知見を作らないため）。
  - 「分かっていること」: 主張を 1 項目ずつ書き、それぞれに出典を付ける。
  - 「分かっていないこと」: 問いの形だけで書く。計画や候補は書かない（PRD の役割）。出典どうしが食い違うものもここに書き、食い違う出典を両方添える。
  - 「撤回・更新」: `- YYYY-MM-DD: <前の主張> → <今の主張>（出典: <リンク>）`。
  - 「関連」: 設計文書の章、CONTEXT.md の語、PRD。
- 実装の地図のページの節は、上の 5 つの代わりに次の 5 つにする。
  - 「概要・責務」: 設計文書の該当の章の言い換えだけで書き、出典を付ける。設計文書に書かれていなければ「設計文書に記述なし」と書き、src を要約しない（点検が報告に挙げる）。
  - 「成立の経緯」: どの PRD で生まれ・変わり、どの ADR が形を決めたかを、日付の順に 1 項目ずつ書き、それぞれに PRD か ADR の出典を付ける。
    - 載せる PRD は、ページの範囲のうち機能カテゴリに当たるファイル（アプリケーションのページなら、アプリケーション自身の key に当たるファイルと、ほかの機能カテゴリに当たるファイル）に触れたコミットの scope の PRD である。「機能カテゴリなし」のファイル（設定ファイル、`CMakeLists.txt`、workspace の設定など）だけに触れた PRD は載せない。そうした PRD は、機械的に作る「PRD の一覧」にだけ載る。
    - PRD の説明は題と目的から読んだ「何をしたか」の1行にする。ただし、題が対象のアプリケーション・機能カテゴリに関係しないときは、本文の、その対象に何をしたかが書かれた箇所から1行で書き、その節を出典に付ける。
    - 載せる ADR は、経緯に載せた PRD が本文で挙げる ADR と、「概要・責務」の出典にした設計文書の章が挙げる ADR のうち、対象のアプリケーション・機能カテゴリの形に関わるものに限る。
  - 「関係」: 設計文書の章、ユーザーガイドの節、アプリケーションのページなら含む機能カテゴリのページ、機能カテゴリのページなら含まれるアプリケーションのページ。機能カテゴリ間の依存は書かない。含むもの・含まれるものが無いときは、その項目を「含む機能カテゴリ: なし」「含まれるアプリケーション: なし」と書く（MetricsViewer の置き場の下のファイルは categories.json で 120 自身に当たるので、含む機能カテゴリは「なし」になる。`core` の下だけに当たる 315 ニューラルネットワークなどは、含まれるアプリケーションが「なし」になる）。
  - 「ファイル」（機械的に作る）: 対応するファイルを、機能グループ（同じ名前の `.hpp` / `.cpp` を 1 行）ごとに並べ、src のファイルへリンクする。ファイルの一覧は `git ls-files --cached --others --exclude-standard`（追跡中のファイルと、無視されていない未追跡のファイル）から作る（ほかの判定と同じく作業ツリーを含めるため）。
    - アプリケーションのページは、置き場の下のファイルを、先に当たる機能カテゴリごとの見出しの下に並べる。どの機能カテゴリにも当たらないファイル（`apps/runner/config/*.txt` など）は「機能カテゴリなし」の見出しの下に並べる。categories.json でアプリケーション自身の key に当たるファイル（RunnerApp の `apps/runner/src/`、MetricsViewer の置き場の全部）は、見出しを付けずに並べる。
    - テストのファイル（名前が `_test` で終わるもの）は、`_test` を除いた名前で対応する機能グループの行に寄せる（categories.json の正規表現はテストの名前に当たらないので、`stats.py` の `category_of` と同じく、除いた名前で当てる）。除いた名前でも当たらないテストのファイルは、機能カテゴリのページには載せない（アプリケーションの置き場の下なら、そのページの「機能カテゴリなし」に載る）。
  - 「PRD の一覧」（機械的に作る）: そのファイルに触れたコミットの scope にある PRD 番号（`PRD087` など）を番号の順に並べ、PRD へのリンクを付ける。
  - 機械的に作る 2 つの節は、冒頭に「点検が作り直す。手で直さない」と書く。書く部分の 3 つの節の確かめ方は、下の「書いたあとの機械的な確かめ」に書く。
- 出典: 主張 1 つに出典 1 つ以上。正本への markdown の相対リンク（`[[ ]]` は使わない）に、節の名前を添える。Run が関わるものは Run 名を添える。
- 目録の行: 種類（題材・機構・アプリケーション・機能カテゴリ）ごとの見出しの下に `- [題名](相対パス) — 今の結論の 1 行（別名: …）`（実装の地図は「今の結論」の代わりに概要の 1 行）。別名には、略称・表記ゆれ・Run 名で使う略称を並べる（例 KFM の行に `別名: KFM, kfm, Kung-Fu Master`）。目録を題材の語で引いたときに外さないため。別名が無ければ括弧ごと省く。
- 作業の記録の行: `YYYY-MM-DD <種別> <材料のパス> blob:<sha1> → <直したページ>[, …]`。
  - 種別は `start`（先頭の 1 行。`rev:<sha>` で開始 revision）、`ingest`（取り込み）、`writeback`（PRD づくりの書き戻し）、`fix`（読んで気づいた是正）、`lint`（点検。`rev:<sha>` で点検した時点の revision）。
  - `blob` は、その時点の材料の `git hash-object`（作業ツリーの内容）。取り込み漏れの判定に使う。直したページが無ければ `→ なし`。
- 書いたあとの機械的な確かめ（書いた手順の最後に、書いた側が行う）。欠けていれば直してから終える。
  - 知見のページ: 「分かっていること」と「撤回・更新」の各項目、「分かっていないこと」の食い違いの項目に相対リンクがある（食い違いの項目は 2 つ以上）。
  - 実装の地図のページ: 「概要・責務」と「成立の経緯」の各項目に相対リンクがある（「設計文書に記述なし」の項目は出典を持たないので除く）。「関係」の各項目がリンクである（「なし」と書いた項目は除く）。機械的に作る 2 つの節は、点検が作り直すので確かめない。
  - 共通: リンク先が実在する（PRD の品質確認観点の項番 4 と同じ検査。機械的に作る節と、点検が「（出典のリンク切れ）」と注記したリンクは除く）。ページが目録に載っている。
- 公開できない値の走査: 正本から写すとき、次が混ざっていないかを確かめる。絶対パス、ユーザー名、マシン名、認証情報、メールアドレス、IP アドレス、内部の URL（ローカルのサーバや私的な共有の URL。公開されている論文・リポジトリ・gist などへのリンクは除く）。AGENTS.md の実効 config の複製で走査する項目（絶対パス、ユーザー名、認証情報、メール、URL、IP）に、マシン名を足し、URL を公開資料へのリンク以外に絞ったものである。wiki のページは出典として公開資料へリンクするためである。

### 4.7 手順と skill の契約

**AGENTS.md「wiki(docs/wiki)を引く条件」（段階 1）**

- 次のときに、`docs/wiki/index.md` を題材の語で引き、関係するページを読む: PRD を起こす・グリルする前、ある機構の知見を別の Env へ持ち込む前、Run 分析の結論を出す前。
- 既存の契約・構造を変える提案をする前に、触る部分のアプリケーション・機能カテゴリのページ（実装の地図）を引き、成立の経緯から該当の PRD と ADR をたどる。
- 読んで、ページと出典（または新しい結果）の食い違いに気づいたら、出典を正としてその場で直し、`log.md` に `fix` の行を足す。PRD づくりの中では、起草でまとめて直す。
- wiki だけにある知見を作らない。新しい知見は先に正本へ書く。書式と確かめ方は `docs/wiki/README.md`。

**anet-create-prd（段階 1、`.agents` と `.claude` の両方）**

- 段 1: 最初の応答の前に、`docs/wiki/index.md` を題材の語（別名を含む）で引き、関係するページを読む。既存の PRD なら、要点提示の「主要な決定の前提を後続の判断と照合する」項目で、ページの知見を照合先に使う。要点提示の「触る既存部品の働きを 1 行ずつ示す」項目には、触る部分の実装の地図のページを使う。読んだページの名前を 1 行で示す。置き場は、既存の PRD なら要点提示、新規の題材なら goal anchor を示す応答である。関係するページが無ければ「なし」と示す。
- 段 3: PRD・CONTEXT.md・ADR に加えて wiki を書く。グリルで分かった知見は、PRD の本文に出典つきで書いたうえで、その節を出典にしてページへ書き戻す。読んで気づいた食い違いもここで直す。書いたら機械的な確かめと公開できない値の走査を行う。
- 段 7: 起票の候補を示し、ユーザーが選んだものを記録したあと（PRD の未決表への記録と、「未解決」を ID へ置き換えることを含む）、完了を報告する直前に行う。候補が無ければ、「なし」を示したあと、完了を報告する直前に行う。書き戻した内容とその時点の PRD の本文が食い違っていないかを確かめ、食い違えばページを直す。そのうえで、その時点の PRD の blob で `writeback` の行を（是正があれば `fix` の行も）`log.md` に足す。途中で止まって行が残らなかった場合は、`anet-lint-wiki` の取り込み漏れとして拾われる。
- Plan Mode の間は wiki も編集しない（PRD・用語集・ADR と同じ）。
- 暫定・999 の起票（質疑を省く）でも、段 3 の書き戻しと段 7 の記録は行う。

**anet-ingest-wiki（段階 2）**

- 呼び方: `anet-ingest-wiki [<材料のパス>]`。
- 対象: パスがあればその材料。無ければ、この会話で書いた・直した材料を、会話と git の作業ツリーの変更（staged・unstaged・untracked）から決める（prepare-commit と同じ決め方）。材料（以下「材料の集合」）は、`docs/experiments/**/*.md`、`reports/` 直下の `*.md`（`reports/INDEX.md` を除く。サーベイ・論文解説・コード読解・調査の報告で、`_survey_tau_*.md` も含む。`reports/` の下のフォルダの台帳・統計・作業資材は含まない）、`docs/memo/**/*_10prd.md`、`docs/design/*.jp.md`（英訳の `.en.md` は派生物なので含まない）、`docs/adr/*.md` である。設計文書・ADR は実装の地図の正本として取り込む。PRD は、確定事項・決めること・未決・受入・実装契約・クラス一覧の節を除いた本文を材料にする（節の名前は PRD ごとに違うので、除く側で決める）。対象が無ければ「この会話の材料なし」と報告して終わる。
- 入力の検証: パスが存在しない、または材料の集合に入らないときは、何も直さずに、そのパスと材料の集合の定義を示して止まる。
- 動き: 材料を読み、目録とページのリンクから関係するページを決めて直す（新しいページも作る）。新しい知見を「分かっていること」へ、覆った主張を「撤回・更新」と「今の結論」へ、出典どうしの食い違いを「分かっていないこと」へ書く。前に取り込んだ材料が書き直されていれば、その材料を出典にしている主張と比べ、覆ったものを「撤回・更新」に書く（PRD のように `superseded` を追記する決まりを持たない材料でも、撤回を残すため）。実装の地図では、設計文書の章から「概要・責務」と「関係」を、PRD と ADR から「成立の経緯」を直す。成立の経緯に書くのは、PRD の題と目的から読んだ「何をしたか」の1行と、ADR の題である。PRD の題が対象のアプリケーション・機能カテゴリに関係しないときは、本文からその対象への変更を1行で書き、その節を出典に付ける。ADR は §4.6 の参照元の条件を満たし、かつ対象の形に関わるものに限る。PRD の決定の中身は写さない。目録を更新し、`log.md` に `ingest` の行を足す。最後に機械的な確かめと公開できない値の走査を行う。
- しないこと: 材料（正本）を書き換えない。git の書き込みをしない。質問して止まらない（決めきれないものは「分かっていないこと」へ）。PRD の決定は取り込まない（PRD の役割）。
- 報告: 直したページ、足した主張と撤回、「分かっていないこと」に書いたもの。

**anet-lint-wiki（段階 2）**

- 呼び方: `anet-lint-wiki [max=<n>]`。housekeeping から呼ばれる。`max` は取り込み漏れを取り込む本数の上限で、1 以上の整数。それ以外の値は、何も直さずに値と期待値を示して止まる。
- 起点と「変わった」の判定: 起点は、`log.md` の最後の `lint` の行の revision、それが無ければ `start` の行の revision である。あるパスの集合の中で「変わったもの」は、`git diff --name-only <revision> -- <パス>`（その revision と作業ツリーの比較）に出るものと、`git status --porcelain --untracked-files=all -- <パス>` に出る未追跡のものを合わせたものとする（この repo は未コミットの材料が多く、コミットだけで比べると見落とすため）。
- 見るもの（7 つ）:
  1. 取り込み漏れ: 材料の集合の各材料の `git hash-object`（作業ツリーの内容）を、`log.md` の最後の `ingest`・`writeback` の blob と比べ、記録が無ければ「未取り込み」、違えば「更新あり」とする。`fix` の行は材料の全体を読んでいないので、取り込み済みの証拠にしない。パスが変わっただけの材料（記録にある blob と同じ blob が別のパスにある）は、取り込み漏れではなく 3 のリンク切れとして扱う。ただし `docs/memo/done/` へ移った PRD は、実装の地図の成立の経緯へ足すために未取り込みとして取り込む（実装の完了を拾うため）。段階 3 までは、開始 revision から変わった材料（上の判定）だけを対象にする。
  2. 撤回の反映漏れ: 起点から変わったページ（`docs/wiki/**/*.md` のうち上の判定で変わったもの）について、そのページが出典にしている節に `superseded`・`invalidated`・撤回・訂正の追記があるのに、ページの「撤回・更新」に無いものを見る。変わった材料の撤回は、取り込み（1 と `anet-ingest-wiki`）が材料ごとに書くので、ここでは見ない。点検の費用をページ数に比例させないため、全部のページを見るのは段階 3 の一括取り込みのときだけにする。
  3. 出典のリンク切れ。
  4. 目録に無いページ。
  5. 目録からも他のページからもリンクされないページ。
  6. 消えた名前: ページにコード書式で書いた設定キー（`.` で区切られた語）と公開クラス名が、今の `core`・`apps`（設定ファイルを含む）に無い。メトリクスの tag は `/` の前の群名だけを照合する（tag は実行時に組み立てられ、ソースに逐語では無いため）。`run_` で始まる語、パス、ファイル名は見ない。
  7. 実装の地図の機械的な部分: 全部のアプリケーション・機能カテゴリのページの「ファイル」と「PRD の一覧」を、categories.json と git（§4.6 の `git ls-files --cached --others --exclude-standard` と、コミットの scope）から作り直し、違えば書き換える。あわせて、「概要・責務」が「設計文書に記述なし」のページを報告に挙げる。
- 直し方: その場で直す。取り込み漏れは「更新あり」を先に、`max` 本まで取り込む（`anet-ingest-wiki` と同じ動き。書き直された材料では覆った主張を「撤回・更新」に書く）。出典のリンク切れは、材料の集合の中で、まず同じファイル名を、見つからなければ先頭の番号を除いた名前（PRD なら `_intrinsic_reward_novelty_10prd.md` のような部分）を探し、1 つだけ見つかればリンクを直す。PRD の `done/`・`frozen/`・`dropped/` への移動と、`9xx` から正式番号への採番し直しがこれで直る。見つからないか 2 つ以上見つかったときは、リンクを残して主張の末尾に「（出典のリンク切れ）」と注記し、`lint` の行と報告に未解決として挙げる（人が直す）。注記したリンク切れは、前提条件の「出典のリンク切れ」に数えず、§4.6 の書いたあとの機械的な確かめからも除く（質問して止まらない約束のもとで、取り込みや点検が行き詰まらないため）。点検は回るたびに、注記の残っている数を報告に挙げる。`done/` へ移った PRD は、その PRD を scope に持つコミットが触れたファイル（そのコミットが無ければ PRD の本文の変更対象から読んだファイル）から、足す先を決めて成立の経緯へ足す。機能カテゴリのページへは、そのファイルを categories.json で写した先に足す。写すときは「ファイル」の節と同じく、テストのファイルは `_test` を除いた名前で写す。写した先がアプリケーション自身の key のとき（RunnerApp の `apps/runner/src/`、MetricsViewer の置き場のファイル）は、機能カテゴリのページへは足さない。足す先の機能カテゴリのページがまだ無いとき（段階 3 より前）は足さない。段階 3 で機能カテゴリのページを作るときに、その時点の `done/` の PRD から成立の経緯を作る。アプリケーションのページへは、そのファイルがアプリケーションの置き場の下にあり、かつ機能カテゴリに当たる（アプリケーション自身の key を含む）ときだけ足す（機能カテゴリを経由すると置き場に触れていない PRD まで入り、「機能カテゴリなし」の設定ファイルだけに触れた PRD まで入れると、アルゴリズムやメトリクスの PRD で経緯が埋まるため。§4.6 の「成立の経緯」）。消えた名前は、今の名前が出典か PRD から分かれば今の名前に直して当時の名前を括弧で残し、分からなければ「（当時の名前。今のコードに無い）」と注記する。直し方が決まらないもの（出典どうしの食い違い）は「分かっていないこと」へ書く。
- 記録: `log.md` に `lint` の行（`rev:<sha>` と直したページ）を足す。取り込んだ材料は `ingest` の行も足す。
- しないこと: `anet-ingest-wiki` と同じ。
- housekeeping の候補表の行: 名前 `wiki-lint`、スキル `anet-lint-wiki`、単位「1 回」、初期見積は 10% / 15（D21）。
  - 前提条件: 取り込み漏れ（見るもの 1）があるか、注記の無い出典のリンク切れ（見るもの 3）がある。どちらも材料の集合・ページのリンク・blob の記録だけで決まる。点検が取り込むか直すか注記するので、点検のあとには残らず、点検自身の `log.md` への追記や housekeeping 自身の `reports/` の下への書き込みでも真にならない。材料が変わって取り込まれていなければ 1 で、PRD が `done/` へ移るなどしてリンクが切れれば 3 で回る。`core`・`apps`・`docs/wiki` の変化は条件に入れない。名前の点検（見るもの 6）は回るたびに行う。
  - 既定の優先順: stats の次（audit の前）に置く。anet-housekeeping の「既定の優先順」の行も改める。

## 5. User Stories

1. 起票する人として、PRD づくりの前に、題材について今分かっていることを 1 ページで読みたい。実験記録を全部読み直したくない。
2. 起票する人として、撤回された結論を、撤回されたと分かる形で見たい。
3. Codex として、Claude の memory に頼らずに、同じ知見を読みたい。
4. 研究者として、ある機構の知見を別の Env へ持ち込むとき、効いた条件と効かなかった条件を 1 ページで見たい。
5. 研究者として、実験を記録したら、その会話の終わりに関係するページがまとめて直ってほしい。
6. 研究者として、Run 分析で分かったことが memory に埋もれず、正本と wiki に残ってほしい。

## 8. 成功の測り方と受入
