# RFD0208: 作業の中で分かったことを残す（reports を作った流れで分けた置き場、wiki の種類「ハーネス」、サマリの名前）RFD

> 2026-11-28 起票（グリル）。
> 起点: 課題 2 件。開発者が、2 件を題材に 1 本の RFD を起こすよう指示した（`/anet-create-rfd issue-20261127-f42cd7 issue-20261127-01b29b`）。グリルで、2 件を 1 本の RFD の 2 つの部（作業の中で分かったことの置き場と、rfd 欄のリンクが 1 つに当たること）として扱うと決めた（§1.2）。
> 課題: [issue-20261127-f42cd7](../management/issues/issue-20261127-f42cd7.md)・[issue-20261127-01b29b](../management/issues/issue-20261127-01b29b.md)（この RFD の仕事）。

## 1. 目的と問題

### 1.1 問題

1. **作業の中で分かったことを書く正本が無い。** Run でもコードでも外の調べものでもない、anet で作業して分かったこと（道具の振る舞いの実測、費用、作業の進め方で効いたこと・効かなかったこと）は、会話で出た内容の書く先の表で「記録しない」に落ちるか（P2）、Claude Code の memory に残る（P9）。memory は Claude Code だけが読み、wiki の出典にならない。
2. **作業の中で調べた事例を書く決まりがはっきりしない。** skill や工程を作る作業の中で調べた一般の事例が、「会話で調べた答え」に当たるかが書かれていない（P8）。RFD づくりで比べる表の「事例」の行のために調べたものを、報告に書く決まりも無い（P7）。
3. **ハーネスの知見の載せ先が無い。** 知見のページの種類の決まりに、ハーネスの置き場の定めが無い（P3）。RFD0202 の §5.7 に書いた skill の起動の実測と公開の比較実験の記事は、wiki のどのページにも無い。
4. **報告の置き場で、流れの違う記録が混ざる。** `reports/` 直下に、survey スキルの出力、論文解説、公開実装のコード読解、anet の道具の調査が並ぶ（§5.1）。作業の中で分かったことを同じ所に足すと、何の記録か分からなくなる（P23）。
5. **課題の rfd 欄のリンクが 2 つのファイルに当たる。** rfd 欄の名前だけのリンクは、保管庫の中で RFD とそのサマリの 2 つに当たる（P11）。今は Obsidian が RFD を開く（P16）が、その選び方は文書に書かれていない（P12）。

### 1.2 ゴール

- G1（見聞きを残す）: Run・コード・外の調べもののどれでもない、anet で作業して分かったことが、Claude Code と Codex のどちらからも読める正本に残り、wiki から引ける。
- G2（調べた事例を残す）: skill や工程を作る作業の中で調べた一般の事例が正本に残り、次に同じことを調べるとき、索引と wiki から先に見つかる。
- G3（wiki の載せ先）: G1・G2 で残したハーネスの知見が、wiki のどのページに載るかが決まっていて、取り込みで載る。
- G4（rfd のリンク）: 課題の rfd 欄のリンクが、保管庫の中で RFD の 1 つだけを指す。
- 題材の課題 [issue-20261127-f42cd7](../management/issues/issue-20261127-f42cd7.md) と [issue-20261127-01b29b](../management/issues/issue-20261127-01b29b.md) がすべて片付く。

2 つの課題は関心が別なので、1 本の RFD の中の 2 つの部として扱う。G1〜G3 が前の部（作業の中で分かったことの置き場）、G4 が後の部（rfd のリンク）に当たる。

### 1.3 非ゴール（退けた案と、本当の制約か）

- memory に今ある知見を正本へ移す作業 — [RFD0112](0112_claude_memory_tidy_10rfd.md)（memory の定期整備）の関心である。この RFD は行き先を決めるところまで行う（D16）。範囲の線引きで、本当の制約ではない。
- RFD0202 の、これからの質問の指標の判定の決まりを変えること — 測っている最中なので（P5）、判定の表には触れない。範囲の線引きで、本当の制約ではない。書く先の表に行を足すことと、新しい種類のページを足すことは、判定の決まりを変えることに当たらない（S17）。
- wiki の本文の出典の書き方と、RFD0203 が決めた YAML ヘッダのキーの組と書き方 — 今回の問題に関係しない。本当の制約ではない。キーの値（`material` のパス、`material_kind` の値、`page_kind` の値）は、置き場と種類が変わるので変わる（D11・S8・S9）。
- Obsidian の手元の設定（保管庫の根、リンクの作り方、手元の `*.base`） — 追跡しないファイルなので、RFD で決めない。本当の制約ではない。
- survey と paper-details の skill そのものの出力先の決まり — このリポジトリの外にある。範囲の線引きで、本当の制約ではない。anet の側の決まりで出力先を指定する（D5）。
- 課題の rfd 欄の書き方 — 名前だけの形のまま変えない（D19）。サマリの名前を変えて重なりを無くすので、変える理由が無い（D8）。本当の制約ではない。

### 1.4 機構とゴールの対応

| 機構 | ゴールへの寄与 |

### 1.5 成功の測り方

効果は、次の 4 つで見る。期間は、実装を終えた日の翌日から 4 週間とする。

- **作業ノートの育ち方**: `reports/notes/` の作業ノートの本数と、作業ノートを出典に持つ知見のページの項目の数（ハーネスのページとほかの種類に分けて数える）。0 本のままなら、書く先の表の行が会話で使われていないとみて、課題に記録する。
- **置き場の線引きが保たれているか**: `scan` の「`reports/` の置き場に当たらない Markdown」の警告が 0 件であること（`reports/` 直下の Markdown が `INDEX.md` だけで、`reports/survey/`・`reports/paper/`・`reports/notes/` の下のフォルダに Markdown が無い）。
- **名前の重なり**: 保管庫の Markdown のうち、RFD（`docs/memo/**/*_10rfd.md`）と同じファイル名のものが、その RFD のほかに 0 件であること。
- **事例の見つかり方**: 期間中の RFD づくりで、比べる表の「事例」の行の出典に、作業ノートかサーベイ・論文解説を引いた行の数。

## 3. 背景

wiki は、正本を外に置き、資料ごとのサマリと、複数の資料を束ねる概念のページを持つ（RFD0095、RFD0202）。正本は実験記録・報告・RFD・設計文書・ADR の 5 種で（P1）、会話で出た内容は、書く先の表で正本か wiki の節へ送る（P2）。RFD0202 は「分かっていること」を「anet の知見」と「外の事例」に分け（D13）、トピック別まとめに節「外の事例」を足して、その材料を報告にした（D14）。

課題の rfd 欄は、RFD0120 で Obsidian のリンクの形にし、名前の重複が無いことを前提に、パスを付けない名前だけの形にした（P14）。RFD0202 で、材料と同じ名前のサマリを置くことにしたので、この前提が崩れた（RFD0203 の P7・U1）。RFD0203 は、wiki のページの YAML ヘッダのリンクに、根からのパスと拡張子と表示名を付けた。

## 4. 用語

- **作業ノート**: 作業の中で分かったことを書く正本。`reports/notes/` に、題（道具や作業の場面）ごとに 1 本置く（D2・S4）。作業の中で survey スキルを使わずに調べた外の事例も、ここに書く（D3）。wiki の規約で定める（D20）。wiki の作業の記録（`docs/wiki/log.md`）と、プロセス契約の作業記録（worklog）とは別のものである。
- **サーベイ**（置き場の名前としての）: survey スキルで作った報告。`reports/survey/` に置く（D1）。2026-11-28 より前に作った報告のうち、論文解説と anet の道具の調査を除くものも、作った道具をファイルから決められない（P30）ので、過去の記録として `reports/survey/` にまとめる（S1）。これから survey スキルを使わずに調べたもの（公開実装の読解を含む）は、作業ノートに書く（D3）。
- **論文解説**: paper-details スキルで作った報告。`reports/paper/` に置く（D4）。
- **流れ**: 記録がどの道具・作業で作られたか。`reports/` の下のフォルダを分ける基準（D1）。外から得たか中で分かったか（出どころ）では分けない。
- **ハーネス**（知見の種類としての）: 主語に、AI のエージェント（Claude Code・Codex とそのアプリ）、ハーネスのファイル（S13 の 9 個の正規表現に当たるファイル）、ほかのソフトウェア（このリポジトリの `src/` と `apps/` が組み込むか起動するもののほかの、すべてのソフトウェア。`reports/tools/` と `.github/` の道具と、git・Obsidian・CMake・Nsight などを含む）のどれかが入る知見のページの種類（S10）。分野で分ける種類で、答える問いで分ける 4 種（題材・手法・測り方・現象）とは軸が違う（D6）。主語がハーネスの側でないもの（題材の Env、Agent と手法、学習、評価、Run とその結果、`src/` と `apps/` が組み込むか起動するもの、それらの値の測り方と読み方）だけの知見は入れない。wiki の規約で定める（D20）。課題の `kind` の値「ハーネス」（AGENTS.md・skill・レビュー観点・プロセス・エージェント定義についての課題。[anet-create-issue](../../.agents/skills/anet-create-issue/SKILL.md) の 156 行）より広く、ほかのソフトウェアと、エージェントの振る舞いと費用も含む。課題の `kind` は、何を直すかで分ける監理の項目で、知見の種類とは目的が違うので、合わせない（課題の `kind` の定めは変えない）。用語集の「optunaハーネス」（探索を回す道具。`CONTEXT.md` の workspace の項）や、311 のトピック別まとめの「探索harness」とは別のもので、知見の種類の名前には「ハーネス」だけを使う。
- **サマリの印**: サマリのファイル名の、拡張子の前に足す `_summary`（D8・S7）。summary は wiki のサマリのページのことで、用語集が範囲統計の避ける語に挙げる range summary とは別である。

用語集（`CONTEXT.md`）には足さない（D20）。

### 8.2 作業ノート

- 単位は題（道具や作業の場面）ごとに 1 本、名前は `<題>.md`（英小文字・数字・アンダースコア、日付なし）（S4）。例: `codex_app_subagent.md`、`claude_code_skill_invocation.md`。
- 1 行目は `# 作業ノート: <題>`、続けて範囲を 1〜2 行書く。項目ごとに、確かめた日、確かめた手段、分かったこと、出典を書く。直すときは訂正の項目を足す（S5）。
- YAML ヘッダは付けない（S6）。
- 書いたら、`reports/notes/INDEX.md` の表（日付・ファイル・題・関連）に行を足すか、日付を直す（S3）。
- 書いたら取り込む（書く先の表のとおり）。公開できない値の走査と、発言の記録の基準を当てる（D15）。

### 8.3 書く先の表（変えたあと）

上から順に当て、最初に条件を満たした行で扱う（今の決まりのまま）。変えるのは、行 5 の送り先と、行 7 の追加だけである（D10）。

| 順 | 会話で出た内容 | 記録先と必要な確認 |
|---|---|---|
| 1 | 今の動きや決まりを変える案 | 課題の候補として示し、開発者が選んだものを起票する（今のまま） |
| 2 | 設計の判断 | 開発者の了承を得て、RFD か ADR に記録する（今のまま） |
| 3 | 開発者の見立て・仮説・疑問 | 知見の「見立て」か「分かっていないこと」（今のまま） |
| 4 | Run の新しい集計・分析 | 実験記録（今のまま） |
| 5 | 外の調べもの（survey スキルで作るものを除く） | 当たる作業ノートに追記する。無ければ作業ノートを作り、取り込む |
| 6 | 今のコードの働きの説明 | 設計文書を更新し、取り込む（今のまま） |
| 7 | 作業の中で分かったこと（道具の振る舞いや費用の実測、作業の進め方で効いたこと・効かなかったこと） | 当たる作業ノートに追記する。無ければ作業ノートを作り、取り込む |
| 8 | 今の正本から導けて、調べ直しに手間がかかる答え | 知見の項目か横断的知見（今の行 7） |
| 9 | ここまでの条件に当たらないもの | 記録しない（今の行 8） |

### 8.4 材料の集合とサマリ

- 材料の集合は D11 のとおり。各フォルダの `INDEX.md` は材料に入れない。
- サマリの名前は、材料のファイル名の拡張子の前に `_summary` を足したもの（S7）。置き場は、実験記録は `summary/experiments/` の下に階層をなぞり、報告は `summary/reports/survey/`・`summary/reports/paper/`・`summary/reports/notes/`（S8）、RFD は保管場所によらず `summary/rfd/` の直下、設計文書は `summary/design/`、ADR は `summary/adr/` に置く。
- YAML ヘッダの `material_kind` は、実験記録・サーベイ・論文解説・作業ノート・RFD・設計文書・ADR のどれか（S8）。キーの組と書き方は RFD0203 のまま。
- 例: `reports/notes/claude_code_skill_invocation.md` のサマリは `docs/wiki/summary/reports/notes/claude_code_skill_invocation_summary.md`、`material_kind: 作業ノート`。

### 8.5 種類「ハーネス」

- フォルダは `docs/wiki/concepts/harness/`、`page_kind` は「ハーネス」、目録の見出しは「ハーネス」（「現象」の次）（S9）。
- 知見のページの 7 節（今の結論・分かっていること（anet の知見・外の事例）・横断的知見・見立て・分かっていないこと・撤回・更新・関連）を持つ。「関連」には、触れる skill・規約・プロセスの文書、RFD、ADR を置く（今の「設計文書の章、CONTEXT.md の語、RFD」に当たる）。
- 主のページを決める順（S10）: 主張の主語で見て、上から当てる。(1) 主語に、AI のエージェント（Claude Code・Codex とそのアプリ）、ハーネスのファイル（S13 の 9 個の正規表現に当たるファイル）、ほかのソフトウェア（このリポジトリの `src/` と `apps/` が組み込むか起動するもののほかの、すべてのソフトウェア。`reports/tools/` と `.github/` の道具と、git・Obsidian・CMake・Nsight などを含む）のどれかが入るなら、答える問いの種類を問わずハーネスを主にし、主語にハーネスの側でないものも入るなら、その側に要旨の行を置く。組み込むとは、`src/` のコードがリンクするか読み込むこと（LibTorch・CUDA・ALE などのライブラリと Env）と、それらがさらに読み込むもの（GPU のドライバなど）である。Run が動く OS の核（カーネル）と計算機（CPU・GPU・メモリ）も、組み込むものと同じ側に置く。OS に付いてくるシェルや端末などの道具は、組み込むものに入らない。起動するとは `apps/` の実行体・bat・設定・`apps/tools/` が起動すること（Runner・Metrics Viewer、`apps/` の bat、`apps/tools/` の道具と、それらが起動する TensorBoard・MLflow・optuna-dashboard）である。CMake（`src/` をビルドする）と Nsight（Runner を外から測る）と、PowerShell などのシェルは、組み込みも起動もされないので、ほかのソフトウェアに入る。(2) 1 に当たらなければ、手法・測り方・現象・題材の順で決める。
  - 例: 「skill は説明文だけではほとんど選ばれず、AGENTS.md の決まりから呼ぶと使われる」（RFD0202 の §5.7）は、ハーネスのページ（例 `concepts/harness/skill_invocation.md`）に全文を書く。
  - 例: 「Claude のアプリの表示が重いと、Run の実時間が遅くなる」は、ハーネスのページを主にし、Atari の実時間を扱う知見のページには要旨の行を置く。
- 見立ての置き場（S11）は、「S10 の 1 に当たる見立て（主語に、AI のエージェント、ハーネスのファイル、ほかのソフトウェアのどれかが入るもの）はハーネスのページ」を先頭の行にして、RFD0202 の S46 の (1)〜(4) を続ける。点検の 4 つの型（S12）は、ハーネスのページにも当てる。

- AI の案（選ばれなかったもの）: 作業の中で分かったことを `docs/` の下の新しい正本の置き場にする。フォルダ名を `field_notes` にする。ハーネスの知見を今の 4 種で分けて目録に小見出しを置く。311 の範囲を広げない。リンクの丸括弧の中だけを直した材料を、新しい記録の種別で取り込み済みにする。どれも §13 に理由を書いた。
- AI の読み違いと訂正: 「外から、は一緒」を、外から得たもの（論文解説や作業の途中の外の調べものを含む）を全部 `survey/` に置く、と読んで聞かずに決まる事項を示した。開発者の「`survey/` は survey スキルで生成したものの置き場」で、置き場は作った流れで分けると読み直し、その事項を取り下げた（D3・D4 で決め直した）。

## 13. 選ばなかった形

- 作業の中で分かったことの正本を `docs/` の下の新しい置き場にする形 — 不採用: `docs/` の下は GitHub Pages で配信する公開文書である（D1、開発者の選択）。
- `reports/` 直下に混ぜ、ファイル名か索引の見出しで分ける形 — 不採用: 流れの違う記録が混ざり、何の記録か分からなくなる（D1）。
- 実験記録の下（`docs/experiments/harness/` など）に置く形 — 不採用: 実験記録は Run の campaign の置き場で、Run の無い記録が混ざる（P17、D1）。
- 正本を持たず wiki に直接書く形 — 不採用: 確かめた主張は先に正本に書く（P1）。
- 置き場を出どころ（外から得たか、中で分かったか）で分け、外から得たものを全部 `survey/` に置く形 — 不採用: `survey/` は survey スキルの出力の置き場にする（P29、D1・D3・D4）。
- フォルダ名を `field_notes`・`lessons`・`observations`・`findings` にする形 — 不採用: 前の 2 つは開発者が選ばず、後の 2 つは既にある語と紛れる（P26、D2）。
- 作業の中で調べた外の事例を、RFD づくりでは RFD の本文だけに書く形 — 不採用: 書く先が RFD づくりの中と外で分かれ、トピック別まとめの「外の事例」に入らない（D3）。
- 論文解説を `reports/survey/` に入れる形 — 不採用: これから作る論文解説が、survey スキルの出力の置き場に混ざる（D4）。今ある報告で作った道具を決められないもの（P30）は、過去の記録として `survey/` にまとめる（S1）。
- survey と paper-details の出力を直下に書かせ、取り込みの前に AI が移す形 — 不採用: 移す判断が取り込みに混ざり、作った skill をファイルから決められないものがある（P30、D5）。
- 汎用の skill の出力先の決まりを、skill の側で直す形 — 範囲外: このリポジトリの外にある（§1.3、D5）。
- ハーネスの知見を今の 4 種で分け、目録に「ハーネス」の小見出しを置く形 — 不採用: 開発者の選択（D6）。道具を変えずに済み、RFD0202 の D21 と ADR 0098 に触れない利点があった。
- ハーネスの知見を 311 のトピック別まとめだけに載せる形 — 不採用: 効き目と実測を書く節が無い（P34、D6）。
- 311 の範囲を広げない形 — 不採用: 開発者の選択（D7）。今の範囲でもハーネスの RFD のほとんどが経緯に載っていた（P37）。
- 311 の範囲に `.claude/skills/` も入れる形 — 不採用: すべて `.agents/skills/` の写しで、ページが長くなるだけ（P36、S13）。
- 課題の rfd 欄を、保管庫の根からのパス（`"[[docs/memo/…]]"`）にする形 — 不採用: Obsidian で選び直すと名前だけが書かれる見込みで、決まりと違う形が混ざる（P38、D8）。
- 課題の rfd 欄を、RFD0203 と同じパス＋拡張子＋表示名にする形 — 不採用: 上と同じ理由に加え、道具が `.md` を外すよう直すことになる（P13、D8）。
- rfd 欄を今のままにし、前提だけを書き直す形 — 不採用: 文書に無い選び方に頼り続け、G4 を改めることになる（P12・P16、D8）。
- 移動でリンクのパスだけが変わった材料を、新しい記録の種別（「リンクだけを直した」）で取り込み済みにする形 — 不採用: 開発者の選択（D9）。取り込み直しの使用量が要らず、あとの移動にも使える利点があった。
- 今の直下の 54 本を直下に残し、これから作るものだけをフォルダに分ける形 — 不採用: 「直下に報告を置かない」と食い違う（D1・D9）。
