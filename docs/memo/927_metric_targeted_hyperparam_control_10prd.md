# メトリクス目標値によるハイパラ自律調整 暫定 PRD

> 2026-11-03 番号を 999 から 927 へ振り直した（PRD114）。

> 状態: 暫定メモ。案と未決 Q1〜Q10 は未確定。詳細は別途グリルで詰める。本 PRD は実装着手を意味しない。
> 起点: 2026-09-01 の Atari 探索。`per_initial_priority` を `max` から `fixed 0.3` に変えた腕で壁突破率が半減し、動いた観測量が `07_evicted_unsampled_ratio` ただ 1 つだった。同じキーが DropMerge では逆の符号を持つ。
> 関連: [docs/experiments/default-dqn/atari/2026-09-01_btr-feedback-arms.md](../experiments/default-dqn/atari/2026-09-01_btr-feedback-arms.md) 探索ブロック 04（実測）、[035_approx_actor_priority_per_10prd.md](done/035_approx_actor_priority_per_10prd.md)（`actor_approx` = 推定による初期優先度）、[952_run_queue_snapshot_10prd.md](952_run_queue_snapshot_10prd.md)（計画の凍結。本 PRD は逆に実行中の変更を扱う）。

## Context / Problem Statement

ハイパラはすべて**開ループの定数**である。値は人間が別環境・別予算で得た経験から選び、Run 中は動かない。以下 4 点はすべて実測事象である。

### 1. 同じキーが環境で符号を変える

`per_initial_priority_mode` は Atari で `max` が勝ち、DropMerge では `fixed` が勝つ。DropMerge では `max` が明確に悪く、推定を使う `actor_approx` も `fixed` に負けた（当時の Run は保持されていないため実測は残っていない）。DropMerge の値も長らく `1.0` で、`07_evicted_unsampled_ratio` を見ながら `0.3` へ下げた経緯がある。

**「正しい値」は環境の関数であり、人間が観測量を見て手で追い込んでいる。**

### 2. 定数は 1 本の Run の中でもズレていく

優先度の分布は学習とともに育つ（同 Run で `11_q_max_mean` 0.4 → 9.4、`04_td_std` 0.06 → 0.60）。固定値はこれに追従しないので、相対的にどんどん低くなる。

| ~exp | `fixed 0.3` | `max` |
|---|---|---|
| 4M | 0.269 | 0.237 |
| 9M | 0.321 | 0.256 |
| 24M | 0.347 | 0.244 |
| 39M | 0.352 | 0.248 |
| 49M | **0.354** | **0.249** |

`07_evicted_unsampled_ratio`（一度もサンプルされずに追い出されたデータの割合）。**規則は観測量を一定に保ち、定数は漂わせる。** 成績は壁突破率 0.75% 対 1.35%（同設定複製対の平均）で半減した。

### 3. 既存の「適応」は controller ではなくラチェット

`mode = max` は分布に追従するが、`max_prio_` は `1.0` 初期・`std::max` でしか更新されない**単調高水位**である（[replay_buffer_impl.cpp:961,1062](../../core/anet-core/src/replay_buffer_impl.cpp)）。上にしか動かないので、一度でも極端な TD 誤差が出ると挿入水準がそこに張り付く。DropMerge の長年の `fixed 1.0` は、**`max` を t=0 の値で凍結したもの**にあたる。

### 4. 観測量には内部最適がある

| 状態 | `07_evicted_unsampled_ratio` | 結果 |
|---|---|---|
| 高すぎ（`fixed 0.3`, RR1） | 0.354 | 収集データの 1/3 が学習器に届かず、壁突破率が半減 |
| 適正付近（`max`, RR1） | 0.249 | 基準 |
| 低すぎ（RR4） | 0.0001 | 全データが最高優先度で入り、優先度付けが機能停止 |

**「最小化すればよい」ではない。** 内部最適があるということは、上限や下限へ張り付ければ済む問題ではなく、制御が意味を持つということでもある。

**したがって欲しいのは**: 観測量に目標値を与え、設定値を遅い制御で追わせる汎用機構。個別キーの特別扱いではなく、`(観測量, 設定キー, 目標値)` の対応を宣言する形。

## 効く事実（既存機構の調査結果 2026-09-02）

**この 3 点により、新規に要るのは「制御則」と「実行中に設定を書き換える口」の 2 つに縮む。**

1. **観測量は既に出ている。** `39_agent_per` / `37_agent_qtd` / `34_agent_plasticity` / `35_agent_churn` 群は Observer 経由で毎 update 取得できる。新規計測は不要。
2. **制御対象は既に config キーである。** `per_initial_priority` は `ReplayBufferConfig` の値で、実行時に差し替える先が明確。
3. **EMA と interval のインフラがある。** メトリクス側に `$ema` と `interval` が既にあり（[metrics_scalar.txt](../../apps/runner/config/metrics_scalar.txt)）、制御に必要な平滑化と発火間隔はそこに乗る。

**逆に無いもの**: 実行中に設定値を書き換える経路。現状 config は起動時に解決して以後不変であり、これは意図した設計でもある（[952_run_queue_snapshot_10prd.md](952_run_queue_snapshot_10prd.md) は逆方向に「凍結」を強化している）。

## 前提として先に要る作業

**目標値が分かっていない。** 0.249 が 0.354 より良いことは測れたが、0.15 や 0.05 がどうかは未測定で、RR やバッファ容量とも交絡している。

制御を書く前に、**設定値を横に振って `(観測量, 成績)` の対応を取る較正キャンペーン**が要る。これは既存の腕振り運用（`apps/1x_batch_run*.bat`）でそのまま実施できる。**この較正が済むまで制御則は書けない。**

## 提案

### 形 A: 実行中の閉ループ制御

`(観測量タグ, 設定キー, 目標値, ゲイン, 発火間隔)` を config で宣言し、Learner が遅い積分制御で設定値を更新する。

```
control.[per_init].observe   = 39_agent_per/07_evicted_unsampled_ratio
control.[per_init].actuate   = DefaultDQNAgent.learner.per_initial_priority
control.[per_init].target    = 0.25
control.[per_init].interval  = 10,000        # learn step
control.[per_init].gain      = 0.05          # log 空間の比例ゲイン
control.[per_init].clamp     = 0.05, 5.0
```

制御は **log 空間**で行う（優先度は正の量でスケールが数桁動くため）。発火間隔は観測量自身の時定数より十分遅くする。

### 形 B: オートチューナ（実行中は開ループのまま）

同じ機構を**較正専用 Run** でだけ動かし、収束した値を報告する。本番 Run はその値を定数として pin する。

**形 B は形 A の部分集合であり、実装は共通。違うのは使い方だけ。**

### なぜ形 B を併記するか — 比較可能性との衝突

閉ループは**設定値を Run の履歴の関数にする**。これは A/B の帰属を壊す。ちょうど `per_beta_step = ${@vars.half_exp_step}` が「予算依存の唯一の学習ハイパラ」となって予算違いの Run の比較を壊していたのと同じ構造で、2026-09-01 にそれを消したばかりである。

**制御は運用（良い Run を得る）の道具であって、帰属（差の原因を特定する）の道具ではない。** アブレーションでは形 B で得た定数を pin して開ループで回すのが筋になる。

### 候補となる (観測量, 設定キー) の対

| 観測量 | 設定キー | 目標値の根拠 |
|---|---|---|
| `39_agent_per/07_evicted_unsampled_ratio` | `per_initial_priority` | **両方向の失敗を実測済み**（本 PRD 冒頭）。最有力 |
| **`13_target_q_delta_abs / 17_q_gap`** | **`soft_update_tau`** | **2026-09-03 追加。3 点（τ 0.001 / τ 0.008 / hard C=125）で成績と単調に対応。無次元。第 5 節** |
| `37_agent_qtd/24_grad_clip_ratio` | `grad_clip_tau` | クリップは安全弁であって正規化器ではない、という既存判断がある（`tau=5` は毎 update 発動して劣化）。現状 0.0005 で不発 |
| `34_agent_plasticity/42_probe_dead_ratio` | 学習率 / `weight_norm` | **不適。** 第 6 節 |
| `35_agent_churn/11_target_disagreement` | `soft_update_tau` | **不適。** 成績と逆行する（第 5 節）|

**制御対象になる条件は、観測量が存在することではなく、観測量と成績の対応が測れていること**である。下 2 行はその反例として残す。

## 制御観測量の選定基準（2026-09-03 追加）

実測を通して、良い観測量に共通する性質が 4 つに整理できた。

| 条件 | `tgtΔ/q_gap` | `evicted_unsampled` | `probe_dormant` / `probe_srank` |
|---|---|---|---|
| ① 成績と単調（または単峰） | ○ 3 点で単調 | ○ 両方向の失敗を実測 | **× 6 例で非対応** |
| ② つまみの直下にある | ○ τ の直接効果 | ○ 初期優先度の直接効果 | × 遠い下流 |
| ③ 無次元 | ○ 比 | ○ 割合 | ○ 割合 |
| ④ 他要素で乱れない | ○ | ○ | × 構造・活性・RR で全部動く |

**良い 2 つに共通するのは「つまみが直接動かすものを、そのまま測っている」ことである。** τ → target の遅れ、初期優先度 → 学習器に届くデータの割合。いずれもつまみの 1 段だけ下流にある。

`probe_*` 群が落ちるのは ④ より ① による。決定打は活性関数の最小差での対照で、**LeakyReLU 腕と ReLU 腕は churn・系統差率・target 不一致が区別できないのに壁突破率が 1.4 倍違った**（2026-09-03、[実験記録](../experiments/default-dqn/atari/2026-09-01_btr-feedback-arms.md)）。差が出ることと成績を予測することは別である。

## 5. `soft_update_tau` を制御対象に加える根拠（2026-09-03）

### 5.1 実測

RR1 / V/A ReLU 基準で 3 点を測った。

| | 壁突破率 | `13_tgtΔ` | `17_q_gap` | **tgtΔ/q_gap** | `11_q_max` | `01_churn` | `11_target_disagreement` |
|---|---|---|---|---|---|---|---|
| soft τ=0.001 | 3.48% | 0.1068 | 0.0529 | **2.02** | 8.99 | 0.0104 | 0.2097 |
| **soft τ=0.008** | **6.16%** | **0.0860** | 0.0510 | **1.69** | **11.45** | 0.0192 | 0.2262 |
| hard C=125 | 6.13% | 0.0915 | 0.0473 | **1.93** | 10.89 | 0.0167 | 0.3030 |

**成績順（0.008 > hard > 0.001）と単調に対応するのは `13_tgtΔ`（逆順）・`11_q_max`（順）・`tgtΔ/q_gap`（逆順）の 3 つだけ**で、`01_churn`・`11_target_disagreement`・`41_probe_dormant_ratio`・`17_q_gap` 単独は対応しない。

`13_tgtΔ` は Q のスケールに比例する（同 Run で `q_max` が 0.4 → 11 と育つ）ため、絶対値では固定目標を置けない。**`17_q_gap` で割って無次元化した比が制御観測量の候補**になる。意味は「target の遅れが行動ギャップの何倍か」で、1 を下回れば target の argmax はおおむね正しく、1 を大きく超えれば target はノイズで行動を選んでいる、と読める。

実測は 2.02 → 1.69 で**まだ 1 を超えている**。**τ をさらに上げる余地がある、という検証可能な予測が立つ。**

### 5.2 `11_target_disagreement` が使えない理由

0.2097（最低スコア）→ 0.2262（最高）→ 0.3030（同着最高）で**成績と逆行する**。target が新しくなるほど online 自身の churn（0.0104 → 0.0192）を受け継ぐためと考えられる。診断には使えるが制御目標にならない。

### 5.3 文献調査からの制約（[survey](../../reports/target_network_update_rate_survey_2026-09-03.md) 参照）

**(a) 単位を明示する必要がある。** 文献では frames / agent steps / parameter updates / gradient steps が混在し、原典 DQN では論文の表と公式実装が 4 倍食い違う。**制御値のメトリクス出力（Q5）には単位を併記すること。**

**(b) 業界慣行は「gradient step 軸で固定」である。** data-efficient Rainbow は replay period を 4 → 1 に変えても target 周期を 2,000 updates に据え置き、単位を脚注で明示している。Scaled-QL もバッチ 16 倍で gradient step 単位の周期を据え置く。**したがって RR を変えたときの再設定則は、文献に依拠できない。**

**(c) 定数スケジュールは理論的に準最適だと証明されている。** ただし表形式 Q 学習が対象で、深層 RL での検証はない。同論文は精度トリガ型（平均 TD 誤差が閾値を下回ったら同期）も Appendix で提案しており、**本 PRD の形 A とは別系統のイベント駆動案として存在する。**

**(d) 感度はアルゴリズム依存である。** Rainbow では K に対して性能が平坦（K=1 でも劣化なし）で、既定の 8,000 は「先行論文からの惰性」と評価されている。一方 DQN では大きい K が重要とされる。**「τ を制御する価値があるか」自体が構成依存**なので、較正キャンペーンは構成ごとに要る。

**(e) 自動調整の先行手法は存在するが主流に入っていない。** 調整信号は t-soft update（main/target パラメータ差の二乗平均）ほか 7 系統あり、合意はない。Atari 規模で優位を示した例は本調査では見つかっていない。**`tgtΔ/q_gap` を使う先行例も見つかっていないので、採用するなら独自の選択になる。**

## 6. `probe_*` 群を制御対象から外す根拠（2026-09-03）

可塑性指標が成績を予測しないことは、本キャンペーンで 6 例が確定している（SN 腕 / VA+pool6 / fuse2304 / hard125 / btrstruct / LeakyReLU）。文献側も同方向で、可塑性喪失は単一の測定量に帰着できないとされ、dormant neuron が駆動因か症状かは未決とされている（[survey](../../reports/target_network_update_rate_survey_2026-09-03.md) §5）。**条件 ① を満たさないので目標値を置けない。**

## 受入条件（暫定）

1. **較正が先**: `per_initial_priority` を 3 点以上振り、`07_evicted_unsampled_ratio` と壁突破率の対応が単峰であることを実測する。**これが取れないと目標値を置けない**ので最初に確認する。
2. **開ループ等価**: 制御を無効化した場合、既存 Run とメトリクス checksum が一致する。
3. **追従**: `fixed` 初期値から始めて、制御が `07_evicted_unsampled_ratio` を目標値の帯へ引き込み、50M を通して保つ。`max` 相当（0.24〜0.26 で平坦）と同等以上の平坦性を示す。
4. **記録**: 制御値の時系列がメトリクスとして残り、Run 終了後に有効値の履歴を復元できる。
5. **成績**: 制御 Run の壁突破率が、同設定の `max` 複製対の幅を下回らない。
6. **オートチューナ**: 較正 Run が収束値を報告し、その値を pin した開ループ Run が制御 Run と同等の成績を出す。

## スコープ外

- **Run 間のハイパラ探索**。既存の optuna ハーネスの領域。本機構は 1 本の Run の中を扱う。
- **`per_initial_priority` 以外の対の実装**。候補表は挙げるが、較正が済んでいるのは 1 対もない。
- **`actor_approx`**（推定による初期優先度）。あちらは「1 件ごとに正しい値を推定する」方向で、本 PRD は「分布の統計量を目標に保つ」方向。[035_approx_actor_priority_per_10prd.md](done/035_approx_actor_priority_per_10prd.md) が扱う。
- **`mode = max` のラチェット修正**。単調高水位を真のトラッカーへ変える改修は本機構と独立に可能で、別件。
- **計画の凍結・キュー**。[952_run_queue_snapshot_10prd.md](952_run_queue_snapshot_10prd.md) が扱う。
