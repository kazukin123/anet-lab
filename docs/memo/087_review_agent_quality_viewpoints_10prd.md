# PRD 087: レビューエージェントと品質確認観点の導入（プロセス契約の共有コア）

> 起点: 2026-10-03。PRD と実装のレビューは、起票側とは別の枠と人間が行っている。しかし、何に照らして見るかを定めた文書が無く、
> 指摘を受け渡す形も決まっていない。規約の一部は片方のエージェントにしか見えない場所にあり、もう一方が起草したものは、レビューで初めてそれに当たる。

## 1. Context（背景・目的）

### 1.1 レビューの基準と形が、どの文書にも無い

工程の正本である [docs/memo/README.md](README.md) §工程と担当 は、レビューを「起票側の枠、およびコミット前に人間」「指摘と修正」と定めるだけである。
[動線マップ](../agents/README.md) の表 2 も、コミット前のレビューで読むものを「変更差分、PRD の受入基準、`git diff <base>`」と挙げるだけである。

このため、次のことが起きている。

- 何を見るかは、レビューする側のその場の判断で決まる。
- 指摘の形が毎回違う。受け取った側が「自分で直す」「裁定を仰ぐ」「見送る」を分ける基準も無い。
- 直した箇所の周りが次の指摘になり、往復が続く。[084](084_noisynet_10prd.md) は、2026-10-03 の 1 日で担当レビューの反映が 3 回あった（冒頭の改訂行）。

### 1.2 規約の一部が、片方のエージェントにしか見えない

動線マップ §5 のとおり、global の指示と memory 層を持つのは Claude Code だけで、Codex の user-level の入口は空である。
そこにある規約は、もう一方が起草するときには見えない。起草物はレビューで初めてその規約に当たり、指摘と手直しの往復になる。

規約を、どちらのエージェントからも読める観点の表にすれば、起草した側がレビューに出す前に自分で通せる。

### 1.3 PRD づくりの入口 skill が shadow されている

project と user-level に同名の `grill-with-docs` があり、中身が違う（動線マップ 発見事項 1）。Claude Code で `/grill-with-docs` を打つと user-level 版が起動することは、[080](080_harness_map_10prd.md) の起票時に実際に起きた。project 版に手順を足しても、その起動では読まれない。

project 版は、元の skill から手順が増えている（goal anchor、scope screen、最終簡素化パス、最後の YES/NO）。同じ名前で持ち続ける理由が薄れている。

### 1.4 同じプロセス契約を、anet の外でも使っている

工程の手順とレビューエージェントの定義は、anet の外のプロジェクトでも同じものを使っている。
anet 用に書き換えて持つと、どこかで見つけた直しを持ち寄れなくなる。
プロジェクトに依存しない文面のまま持てば、直しをそのまま持ち寄れる。

## 3. ゴール / 非ゴール

- **G1**: PRD と実装（PRD が作るもの全部）に対して、観点に照らした判定を受けられる。Claude Code と Codex のどちらの枠からも、同じ観点・同じ依頼の形・同じ応答の形で受けられる。
- **G2**: 起草した側が、レビューに出す前に同じ観点を自分で通せる。観点は、どちらのエージェントからも読める場所にある。
- **G3**: 共有コアが、プロジェクトに依存しない文面のままである。
- **G4**: PRD づくりと実装の入口 skill が、自己点検 → レビュー → 差し戻し対応 → 未決の提示 → 停止、の同じ手順で動く（段階 2）。
- **NG1**: 別枠の再グリルと、コミット前の人間のレビューを置き換えない。レビューエージェントが見るのは観点の充足であり、設計の妥当性は判断しない。
- **NG2**: 入口を太らせない。`AGENTS.md` へプロセス契約の内容を書き写さない。
- **NG3**: 課題管理の仕組み、ハーネス自体をレビューする観点、エージェント間で定義を変換する仕組みは作らない。
- **NG4**: 設計の工程を作らない。PRD が設計契約を含む現行の形のままにする。
- **NG5**: PRD のテンプレートを作らない。
- **NG6**: 観点の初期項目に、リポジトリの文書に書かれていない規約を入れない。足すのは使ってみてから、ユーザーの判断で行う。
- **NG7**: 共有コアを、anet 向けの文面に書き換えない。汎用の文面のまま良くなる直しは、してよい。

## 4. 用語

`CONTEXT.md` は RL ドメインの用語集なので、プロセスの語彙は載せない（[080](080_harness_map_10prd.md) と同じ扱い）。本 PRD と、`docs/process/` `docs/quality/` の文書で使う。

| 語 | 定義 | 避け語 |
|---|---|---|
| **プロセス契約** | 工程の手順、停止条件、応答の形、レビュー依頼の形を定めた 1 つの文書（`docs/process/protocol.md`） | プロトコル、ルール |
| **共有コア** | プロジェクトに依存しない文面で持つファイル。プロセス契約と、レビューエージェントの定義の 2 つ。ほかのプロジェクトでも同じものを使う | フォーク、コピー |
| **レジストリ** | 成果物ごとに、出力先・観点・担当を引く表（`docs/process/registry.md`）。anet 用に書く | 台帳 |
| **品質確認観点** | レビューと自己点検で走査する項目の表。項番で引用する | チェックリスト、レビュー基準 |
| **レビューエージェント** | 観点に照らして OK か差し戻しかを判定するサブエージェント（`an-review`）。成果物は直さない | レビュー skill、reviewer |
| **自己点検** | 起草した側が、レビューに出す前に、観点の全項目を自分で通すこと | セルフレビュー |
| **読み替え表** | 共有コアの記述のうち anet に実体が無いものを、anet の実体へ対応づける表（レジストリの中に置く） | 対応表、マッピング |

共有コアは、AI エージェントの役割を「工程 Agent」「レビュー Agent」と書く。anet のドメイン用語の Agent（強化学習の Agent）とは別物である。
anet で書く文書では「エージェント」と書き、共有コアの表記はそのままにする。

## 6. 実装契約

### 6.1 段階 1: レビューと観点

#### 共有コアの配置

2 ファイルは、ユーザーが用意して置く。実装する枠は、この 2 ファイルを起草しない。

置くファイルは、次を満たす。

- anet に無い文書を参照していない。プロセス契約が参照する `.md` は、`docs/process/registry.md` だけである。
- 特定の製品やプラットフォームに固有の語を含まない。

共有コアは、レジストリの節を見出しで参照する。レジストリは同じ見出しを持つ（次項）。

#### `docs/process/registry.md`

次の節を持つ。共有コアが見出しで参照する節は、中身が無くても「なし」と書いて置く。

| 節 | 段階 1 の中身 |
|---|---|
| 成果物レジストリ | 下の表 |
| 成果物以外のレビュー対象 | なし |
| サーフェスごとの所在 | レビューエージェントの定義: Claude Code は `.claude/agents/an-review.md`、Codex は `.codex/agents/an-review.toml` |
| 入力資料 | 会話での要求、`reports/` のサーベイ、`docs/experiments/` の実験記録。いずれも読み取り元で、工程の中で書き換えない |
| 工程 Agent の切り替え先、成果物種別とアダプタの対応、読み替え表 | 段階 2 で書く |

成果物レジストリの行:

#### 品質確認観点 2 本

`docs/quality/prd.md`（PRD 用）と `docs/quality/impl.md`（実装用）を書く。

形式:

- 冒頭に位置づけの表を置く（対象の成果物、参照するエージェント、対象外）。
- 項番は表の中で一意にする。項目を消しても番号を詰めない。指摘の引用が壊れるためである。
- 検索で判定できる項目は「機械検査」の節に分け、検索対象・パターン・期待値を書く。読まないと判定できない項目だけを読解観点に残す。
- 確認内容は、満たすか満たさないかを判定できる文にする。「適切に」「十分に」で終わらせない。
- **規約を書き写さない。** 各項目は規約の所在（文書と節）を指し、成果物がそれを満たすかを問う。規約の本文は、元の文書だけが持つ。

#### Codex 用の定義 `.codex/agents/an-review.toml`

- `name = "an-review"`、`sandbox_mode = "read-only"`。
- 本文は次の 2 点だけにする。本文を 2 か所に持たないためである。
  - 最初に `.claude/agents/an-review.md` を読み、その定義に従う。
  - ほかのエージェントを起動しない（Codex では道具で禁じられないので、文面で禁じる）。
- `model` は書かない。親と同じモデルで動く。

#### 使い方（段階 1 の時点）

- 起草した枠でも別枠でも、レビューエージェントを名指しで呼び、対象のパスを渡す。依頼の形と応答の形は、共有コアの定めによる。
- 実装のレビューでは、変更箇所として、基準コミットと変更ファイルの一覧を依頼に書く。一覧は、呼び出し元が `git diff --stat <基準>` で作る。
- 別枠へ結果を渡すときは、応答をそのまま `.scratch/prdNNN/` に保存する。

## 7. テスト / 検証

- **共有コア**: 共有コアが参照する `.md` のファイルが、anet に実在する。anet 固有の語（`anet`、`PRD`）を含まない。
- **観点**: 項番に重複が無い。各項目に規約の所在がある。
- **レビューエージェント（PRD）**: Claude Code と Codex のそれぞれで、既存の PRD 1 本に全体のレビューを当てる。応答が共有コアの定める形で返り、指摘が観点の項番を引用している。対象ファイルに差分が出ない（`git status` で確かめる）。
- **レビューエージェント（実装）**: 直近の実装 1 件に、基準コミットを渡して当てる。確かめることは、PRD のレビューと同じである（応答の形、項番の引用、対象ファイルに差分が出ないこと）。
- **続けて依頼**: 2 往復目を同じレビューエージェントに依頼でき、変えていないファイルを読み直さない。
- **費用**: Claude Code と Codex のそれぞれで、1 往復目と 2 往復目の消費を、実装計画（`*_2ximpl.md`）に記録する。合否には使わない。レビューエージェントを通す範囲とモデルの指定（§5）を見直す材料にする。
- **段階 2**: `anet-create-prd` で小さい PRD を 1 本、`implement-prd-with-docs` で実装を 1 本通す。自己点検、レビュー、未決の提示、停止が起きたことを確かめる。差し戻し対応は、レビューが差し戻しを返したときに起きたことを確かめる。OK が返ったときは、起きなくてよい。追加・変更した skill について `diff -rq .agents/skills .claude/skills` に差が無い。

## 10. 影響・移行

- **既存の運用への影響**: 段階 1 では、既存の skill と工程を変えない。レビューエージェントを呼ぶかどうかは、その都度の判断である。段階 2 で、PRD づくりの入口が `anet-create-prd` に変わる。
