## 1. Context（背景・目的）

### 1.1 レビューの基準と形が、どの文書にも無い

工程の正本である [docs/memo/README.md](README.md) §工程と担当 は、レビューを「起票側の枠、およびコミット前に人間」「指摘と修正」と定めるだけである。
[動線マップ](../agents/README.md) の表 2 も、コミット前のレビューで読むものを「変更差分、PRD の受入基準、`git diff <base>`」と挙げるだけである。

このため、次のことが起きている。

- 何を見るかは、レビューする側のその場の判断で決まる。
- 指摘の形が毎回違う。受け取った側が「自分で直す」「裁定を仰ぐ」「見送る」を分ける基準も無い。
- 直した箇所の周りが次の指摘になり、往復が続く。[084](084_noisynet_10prd.md) は、2026-10-03 の 1 日で担当レビューの反映が 3 回あった（冒頭の改訂行）。

### 1.2 規約の一部が、片方のエージェントにしか見えない

動線マップ §5 のとおり、global の指示と memory 層を持つのは Claude Code だけで、Codex の user-level の入口は空である。
そこにある規約は、もう一方が起草するときには見えない。起草物はレビューで初めてその規約に当たり、指摘と手直しの往復になる。

規約を、どちらのエージェントからも読める観点の表にすれば、起草した側がレビューに出す前に自分で通せる。

### 1.3 PRD づくりの入口 skill が shadow されている

project と user-level に同名の `grill-with-docs` があり、中身が違う（動線マップ 発見事項 1）。Claude Code で `/grill-with-docs` を打つと user-level 版が起動することは、[080](080_harness_map_10prd.md) の起票時に実際に起きた。project 版に手順を足しても、その起動では読まれない。

project 版は、元の skill から手順が増えている（goal anchor、scope screen、最終簡素化パス、最後の YES/NO）。同じ名前で持ち続ける理由が薄れている。

### 1.4 同じプロセス契約を、anet の外でも使っている

工程の手順とレビューエージェントの定義は、anet の外のプロジェクトでも同じものを使っている。
anet 用に書き換えて持つと、どこかで見つけた直しを持ち寄れなくなる。
プロジェクトに依存しない文面のまま持てば、直しをそのまま持ち寄れる。

### 1.5 レビューだけを頼む入口が無い

段階 1 では、レビューエージェントを名指しで呼ぶ（§6.1 の「使い方」）。使ってみて、次のことが分かった。

- 依頼の項目（プロセス契約の 2 節）は、呼ぶ側が毎回組み立てる。実装のレビューでは、基準コミットと変更ファイルの一覧も要る。段階 1 の受入では、Codex に渡す依頼文を、別のファイルに用意した。
- 新しく呼ぶ 1 回の消費が大きい（§2.4）。2 往復目を同じレビューエージェントに続けて依頼するかどうかは、呼ぶ側が覚えているかに任されている。
- 小さい変更は、PRD を起こさずに実装する。段階 1 の時点では、PRD の無い変更をレビューの対象外にしていたので、その変更には観点が効かない。

### 1.6 グリルの往復が、開発のネックになっている

PRD づくりのグリルが、開発全体の速さを決めている。2026-10-18 に、過去のグリルの記録を数えた（§2.5）。分かったことは次のとおりである。

- 選択肢の問いの 3 分の 2 は、推奨のまま通っている。規約やコードから答えが決まる問いも、1 問ずつ往復している。
- 説明を求める返答（具体的な姿、既存部品の働き）が 8% ある。その前に、ユーザーは 6 分ほど止まっている。選択肢が抽象的なまま出ると、理解のための往復が増える。ただし、理解を深める往復は品質の源なので、減らす対象にしない（ユーザー判断）。
- 最終簡素化パスの問いは、9 割が推奨のまま（ほぼ keep）通る。「今は要らない」を理由にした削減の提案が多いが、ユーザーは、後で要るものは同時に作るほうを選ぶ。実装の負荷は AI が持つので、整理を終えた仕様を削る判断にはならない。振り返りとして要るのは、目的を見失っていないかの確認だけである（ユーザー判断）。
- 別モデルでの再グリルは効く。092 と 093 は 3 回グリルし、2 回目以降にも仕組みの形が変わる指摘が出た。しかし、別枠との往復は、ユーザーが仲介する手間がかかる。
- `anet-review` は明示起動なので、グリルのあとに呼ばれないことがある。
- Plan Mode に入れ忘れることがある。現行の手順は、最後の問い（計画の承認か、実装の開始か）を Plan Mode かどうかで分けている。

## 3. ゴール / 非ゴール

- **G1**: PRD と実装（PRD が作るもの全部）に対して、観点に照らした判定を受けられる。Claude Code と Codex のどちらの枠からも、同じ観点・同じ依頼の形・同じ応答の形で受けられる。
- **G2**: 起草した側が、レビューに出す前に同じ観点を自分で通せる。観点は、どちらのエージェントからも読める場所にある。
- **G3**: 共有コアが、プロジェクトに依存しない文面のままである。
- **G4**: PRD づくりと実装の入口 skill が、自己点検 → レビュー → 差し戻し対応 → 未決の提示 → 停止、の同じ手順で動く（段階 2）。
- **G5**: PRD の無い変更も、同じ観点で判定を受けられる。レビューだけを、1 つの入口から頼める（段階 1.5）。
- **G6**: PRD づくりの入口 skill で、ユーザーに問うのは、ユーザーの裁定が要る論点だけにする。規約やコードから導けることと、調べれば分かることは、問わずに示す（段階 2）。
- **G7**: 別のモデルの論点を、別枠と往復せずに、同じ枠の中で受けられる。入れるかは、その都度ユーザーが決める（段階 2）。
- **NG1**: 別枠の再グリルと、コミット前の人間のレビューを置き換えない。レビューエージェントが見るのは観点の充足であり、設計の妥当性は判断しない。別モデルの検討（G7）も、別枠の再グリルを置き換えない。
- **NG2**: 入口を太らせない。`AGENTS.md` へプロセス契約の内容を書き写さない。
- **NG3**: 課題管理の仕組み、ハーネス自体をレビューする観点、エージェント間で定義を変換する仕組みは作らない。
- **NG4**: 設計の工程を作らない。PRD が設計契約を含む現行の形のままにする。
- **NG5**: PRD のテンプレートを作らない。
- **NG6**: 観点の初期項目に、リポジトリの文書に書かれていない規約を入れない。足すのは使ってみてから、ユーザーの判断で行う。
- **NG7**: 共有コアを、anet 向けの文面に書き換えない。汎用の文面のまま良くなる直しは、してよい。
- **NG8**: レビューだけの入口（`anet-review`）は、成果物を直さない。指摘への対応は、応答を見たユーザーの指示を受けてから、通常の作業として行う。
- **NG9**: 理解を深めるための往復（説明や具体例を求める返答と、その答え）を、減らす対象にしない。問いの数そのものを、品質や効率の指標にしない。

## 4. 用語

`CONTEXT.md` は RL ドメインの用語集なので、プロセスの語彙は載せない（[080](080_harness_map_10prd.md) と同じ扱い）。本 PRD と、`docs/process/` `docs/quality/` の文書で使う。

#### 品質確認観点 2 本

`docs/quality/prd.md`（PRD 用）と `docs/quality/impl.md`（実装用）を書く。

- 冒頭に位置づけの表を置く（対象の成果物、参照するエージェント、対象外）。

- 確認内容は、満たすか満たさないかを判定できる文にする。「適切に」「十分に」で終わらせない。
- **規約を書き写さない。** 各項目は規約の所在（文書と節）を指し、成果物がそれを満たすかを問う。規約の本文は、元の文書だけが持つ。

### 6.5 段階 1.5: レビューだけを頼む入口

段階 1 の「使い方」（§6.1）を、skill の手順にする。あわせて、PRD の無い変更をレビューに出せるようにする。節の番号は足した順で、段階の順ではない。

#### skill `anet-review`

- 新規。`.agents/skills` と `.claude/skills` の実体コピーに、`SKILL.md` と `agents/openai.yaml` を置く。
- 起動は `/anet-review` と `$anet-review`。明示起動だけにする。書き方は、既存の明示起動の skill に合わせる（`description` に起動条件を書き、`agents/openai.yaml` に `policy.allow_implicit_invocation: false` を置く）。
- やることは 4 つである。対象を決める。依頼を組み立てる。レビューエージェント（`an-review`）を呼ぶ。応答を示す。
- 成果物を直さない（NG8）。git の書き込み操作をしない。

**対象の決め方**

引数は任意で、空白区切りで並べる。

| 引数 | 対象 | 成果物キー |
|---|---|---|
| PRD のファイル名（`*_10prd.md`） | その PRD | `prd` |
| 実装計画のファイル名（`*_2ximpl.md`） | その実装計画 | `impl-plan` |
| そのほかのファイルやディレクトリのパス | そのファイル。ディレクトリは、その配下で基準コミットから変わったファイルと、Git が追跡していない新しいファイル | `impl` |

- 基準コミットは `HEAD` にする。ユーザーが別のコミットを示したときは、それを使う。
- 引数にパスが 1 つも無いときは、その会話で変更したファイルを対象にする。成果物キーは、上の表と同じに決める。
- その会話で変更したファイルも無いときは、レビューエージェントを呼ばずに、`git status --short` の結果を示して、対象を尋ねる。**未コミットの変更すべてを、黙って対象にしない。** 作業ツリーには、ほかの枠の変更が同時にあるためである。
- 実装計画を渡され、ほかにパスが無いときは、実装（`impl`）もあわせて対象にする。変更ファイルは、その会話で変更したファイルにする。無ければ、実装計画の「主な変更」に挙がったファイルのうち、基準コミットから変わったものにする。それも無ければ、実装計画だけを対象にする。
- 観点ファイルは、成果物キーでレジストリから引く。観点ファイルが同じ成果物（`impl-plan` と `impl`）は、1 回の依頼にまとめる。観点ファイルが違う成果物（`prd` と `impl`）を同時に渡されたときは、別々のレビューエージェントへの依頼に分ける。

**依頼の組み立て**

依頼の項目と書き方は、プロセス契約の 2 節による。skill が読むのは 2 節と 3.3 節（応答を示すときに使う）だけで、プロセス契約の全体は読まない（§2.3）。項目ごとの決め方は、次のとおりである。

| 項目 | 決め方 |
|---|---|
| 成果物キー、レビュー対象パス | 上の「対象の決め方」 |
| テンプレートパス、品質確認観点パス | レジストリの行から引く |
| 入力元パス | `prd` は、レジストリの「入力資料」の定めで決める。`impl-plan` は、対の PRD（同じディレクトリの、名前の `_2ximpl.md` を `_10prd.md` に置き換えたもの）。`impl` は、対象の実装計画と、その対の PRD。実装計画が無ければ、その会話の作業が従った PRD。どれも無ければ「なし」と書く |
| 変更箇所 | `prd` は、Git が追跡していないか、基準コミットから変わっていなければ「全体」。変わっていれば、基準コミットからの差分を見て、変えた節を挙げる。`impl-plan` と `impl` は、`docs/quality/impl.md` の「変更箇所の渡し方」による |
| 既知の事項 | 同じ会話の前の往復で、レビューエージェントが報告したもの。ほかは、ユーザーが挙げたものだけを書く。無ければ「なし」 |
| 起草時の論点 | その会話で、判断に迷った箇所。無ければ「なし」 |

- PRD のレビューでは、あわせて起こした・変えた ADR と、`CONTEXT.md` の変更があれば、変更箇所に書く。`docs/quality/prd.md` の「ADR と用語」の適用範囲が、それで決まるためである。
- 実装のレビューでは、実行した検証（コマンドと結果）を依頼に書く。実装計画に記録があれば、その節を指す。`docs/quality/impl.md` の「検証と報告」が、依頼の記述を見るためである。
- PRD に沿わない変更では、変更の目的（1〜2 文）も依頼に書く。
- 会話から分からないものは「記述なし」と書く。推測で埋めない。

**呼び方**

| | 新しく呼ぶ | 続けて依頼する |
|---|---|---|
| Claude Code | サブエージェント `an-review` を起動する | 前のレビューエージェントにメッセージを送る（SendMessage） |
| Codex | `collaboration.spawn_agent` で `an-review` を起動し、`collaboration.wait_agent` で待つ | `collaboration.followup_task` |

- 呼ぶ前に、対象、成果物キー、観点ファイル、新しく呼ぶのか続けて依頼するのかを、短く示す。確認は取らずに進める。
- **同じ会話で、前の起動と同じ対象を出し直すとき（指摘を直したあとなど）は、新しく呼ばずに、前のレビューエージェントに続けて依頼する。** 変更箇所には、前の往復のあとで変えたファイルを書く。変えていないファイルを読み直させないためである。既知の事項には、前の往復の報告を加える。
- 続けて依頼できないときは、新しく呼び、その旨を示す。
- Codex の手順に「閉じる」を書かない（§2.1）。
- モデルは指定しない（§5）。

**応答と保存**

- レビューエージェントの応答の原文を、毎回そのまま保存する（置き場は §5）。
- 画面には、原文を平易に言い直した説明を示し、末尾に原文の置き場を添える。原文は画面に出さない。
  - 書き方は、プロセス契約の 3.3 節（開発者へ提示する文言）による。内部用語と、観点の項番・番号を使わない。日本語で書く。
  - 原文の指摘を、1 件ずつ説明に対応させる。足さない、落とさない、判定を変えない。原文に無い直し方を足さない。
  - 適用した観点・適用しなかった観点の件数や一覧は、説明に書かない。原文に残る。
- 応答を示したら止まる。指摘への対応は始めない（NG8）。
- Codex で、親のスレッドが読み取り専用のときは保存できない（§2.1）。そのときは、説明のあとに原文を全文で示し、保存できなかった旨を示す。

## 7. テスト / 検証

- **共有コア**: 共有コアが参照する `.md` のファイルが、anet に実在する。anet 固有の語（`anet`、`PRD`）を含まない。
- **観点**: 項番に重複が無い。各項目に規約の所在がある。
- **レビューエージェント（PRD）**: Claude Code と Codex のそれぞれで、既存の PRD 1 本に全体のレビューを当てる。応答が共有コアの定める形で返り、指摘が観点の項番を引用している。対象ファイルに差分が出ない（`git status` で確かめる）。
- **レビューエージェント（実装）**: 直近の実装 1 件に、基準コミットを渡して当てる。確かめることは、PRD のレビューと同じである（応答の形、項番の引用、対象ファイルに差分が出ないこと）。
- **続けて依頼**: 2 往復目を同じレビューエージェントに依頼でき、変えていないファイルを読み直さない。
- **費用**: Claude Code と Codex のそれぞれで、1 往復目と 2 往復目の消費を、実装計画（`*_2ximpl.md`）に記録する。合否には使わない。レビューエージェントを通す範囲とモデルの指定（§5）を見直す材料にする。
- **段階 2**: `anet-create-prd` で小さい PRD を 1 本、`implement-prd-with-docs` で実装を 1 本通す。自己点検、レビュー、未決の提示、停止が起きたことを確かめる。差し戻し対応は、レビューが差し戻しを返したときに起きたことを確かめる。OK が返ったときは、起きなくてよい。追加・変更した skill について `diff -rq .agents/skills .claude/skills` に差が無い。
- **段階 2（グリルの手順）**: 上の PRD の 1 本を、Plan Mode で起動する。scope screen が済んだあとの最初の個別の問いと同じ応答で、②の一覧が示される（当たるものが無ければ示されない）。②の一覧の各行と、①の事実に、開けるリンクで根拠の所在が添えてある。足す・変える・消すクラスがあれば、起草した PRD の実装契約の節にクラス一覧（名前、区分、責務）がある。最終簡素化パスの問いが出ない。自己点検の結果に、目的のずれと決定の残滓の見立てがある。質疑の終わりに計画が示され、承認のあと Plan Mode を抜けて、起草から停止まで進む。
- **段階 2（別モデルの検討）**: Claude Code で 1 回通す。入れるかの 1 問が、推奨と費用の目安を添えて出る。入れると答えたとき、`anet-other-model` が、§5 の決め方で選んだモデル（セッションのモデルとは違うもの）で起動する。返った論点のうち、③に当たるものだけが聞かれる。消費と時間を、実装計画に記録する。合否には使わない。問いに添える費用の目安を、この記録で置き換える。
- **段階 2（効果）**: 段階 2 の受入のあと、PRD 3 本を通したところで、§2.5 と同じ数え方で、PRD 1 本あたりの人の時間を数える。品質の見張りとして、実装までのグリルの回数と、グリルのあとのレビューの指摘の数も数え、§2.5 と並べて実装計画に記録する。往復の数は指標にしない（NG9）。合否には使わず、受入基準にも入れない。段階 2 の完了を、この記録で待たせないためである。
- **段階 1.5（PRD の無い変更）**: Claude Code と Codex のそれぞれで、ファイルを変更した会話から、`anet-review` を引数なしで起動する。その会話で変更したファイルだけが対象になり、依頼の入力元が「なし」になる。画面に平易な説明と原文の置き場が示され、原文がその置き場に保存される。説明は、内部用語と観点の項番を含まず、原文の指摘と 1 件ずつ対応する。原文の 1 行目は `総合判定:` で、`再確認ポイント` の適用した項目に、項番 14・15 が入っていない。起動の前後で、対象ファイルの `git hash-object` が変わらない。
- **段階 1.5（続けて依頼）**: 同じ会話で、対象のファイルを 1 つ変えてから、もう一度引数なしで起動する。新しく呼ばずに、前のレビューエージェントに続けて依頼する。
- **段階 1.5（PRD と、対象が無いとき）**: Claude Code と Codex のどちらか片方で確かめる。PRD のファイル名を渡して起動すると、成果物キー `prd` のレビューが返る。何も変更していない会話から引数なしで起動すると、レビューエージェントを呼ばずに、`git status --short` の結果を示して対象を尋ねる。
- **段階 1.5（モデル）**: Claude Code で、「PRD の無い変更」と同じ対象を、親より軽いモデルを指定して、新しく呼ぶ。この測定は、skill を通さずに、レビューエージェントを直接呼んでよい。指定したモデルの名前と、消費・時間・指摘の項番を、指定しない 1 往復目と並べて、実装計画（`*_2ximpl.md`）に記録する。合否には使わない。
- **段階 1.5（文書と改行）**: `git -c core.safecrlf=false diff --no-index --no-renames --name-status` で、`anet-review` の 2 つのコピーと、skills README の 2 つのコピーに差が無い。`git ls-files --eol -- .agents .claude .codex` の全行が、`w/lf` と `attr/text eol=lf` を持つ。

## 10. 影響・移行

- **既存の運用への影響**: 段階 1 では、既存の skill と工程を変えない。レビューエージェントを呼ぶかどうかは、その都度の判断である。段階 1.5 で、レビューだけの入口 `anet-review` が増える。既存の skill の手順は変えない。段階 2 で、PRD づくりの入口が `anet-create-prd` に変わる。
- **既存の PRD**: 書き直さない。観点は、これから起票・改訂する PRD に当てる。
- **グリルの手順（段階 2）**: 最終簡素化パスが無くなるので、これから起票する PRD は Complexity audit の節を持たなくてよい。先送りしたものは、理由と、何が揃ったら作るかを本文に残す（観点 9）。既存 PRD の Complexity audit は書き直さない。別モデルの検討は、入れたときだけ、サブエージェント 1 回分の消費が増える。
- **動線マップ**: `docs/process/` `docs/quality/` `.claude/agents/` `.codex/agents/` が増える。次回の `anet-harness-map` の再生成で反映する。調査対象にこれらを足す必要があれば、その契約の改訂は別件にする。
- **費用**: レビュー 1 往復は、プロセス契約と観点と対象を読むぶんの固定の消費がある。Codex では起動のたびに `AGENTS.md` も渡る（§2.1）。§7 の記録を見て、レビューエージェントを通す範囲とモデルの指定を見直す。段階 1 の実測は、§2.4 にある。
- **陳腐化**: 観点は規約を書き写さず所在を指すので、規約の本文が変わっても観点は直さなくてよい。規約の節が消えたり改名されたりしたときは、観点の所在が切れる。観点ファイルにもリンク検査を当てる。
