## 1. 目的と問題

### 1.1 問題

会話で案・選択肢・論点に記号（A〜G、1〜5、P3、U1 など）を振ると、そのあとの会話は記号で進む。ユーザーは、記号が何を指すか、どの案を試してどうなったか、何が決まったかを確かめるために、元の応答までスクロールして戻る必要がある。スマホでは、長い会話の中から元の応答を探すのがとくにしんどい（P1）。

記号を出すたびに短い名前を添える決まり（P3）で、1 つの記号の中身はその場で分かるようになった。しかし、案の全体（いくつあり、どれを試し、どうなったか）、決まったこと、進み具合、残件は、会話を読み返さないと一覧できない。寝たあとなど間が空くと、何をどこまでやったかを聞き直すことになる。

### 1.2 ゴール

- その会話の手助けになる情報を、会話を遡らず、聞き直さずに、1 か所で見返せる。中身は、議論や整理の助けになる情報（案・選択肢とその状態、決まったこと、未決など）に、進捗と残件を加える。寝たあとなど間が空いても、それを見れば思い出せる。
- その場所を、スマホからも開ける。Claude Code と Codex のどちらの会話でも開ける。
- AI は、言われなくても、手助けが要る会話では作り、会話の進みに合わせて更新する。簡単な題材では作らない。RFD のグリル（`anet-create-rfd`）では最初に作る。ユーザーが頼んで作らせることもできる。
- 題材の課題 issue-20261122-717309 が片付く。

### 1.3 非ゴール（退けた案と、本当の制約か）

- まとめページを正本にすること — 決定の正本は RFD・実験記録・課題に置く（P10）。ページは見返し用の写しで、決定を書く先を増やさない。本当の制約（正本を 1 つにする方針）。
- 会話の本文での記号の扱いを変えること — 記号に名前を添える決まり（P3）はそのまま続け、問いと決定は会話で行う。本当の制約ではなく、役割を分けるための線引きである。
- handoff の skill を変えること — チャット枠を移るときの引き継ぎは、handoff の skill を変えずに、引継ぎ文の中身で合わせる（D14）。本当の制約ではなく、開発者の指示（§12）。handoff の skill はもともと、ほかの成果物をパスか URL で参照し、次の会話で使う skill を挙げる（[handoff の SKILL.md](../../.agents/skills/handoff/SKILL.md)）ので、変えずに足りる。
- 実装の会話の場面の指針を今回作ること — 最初に用意する場面はグリル・実験・一般の 3 つにした（D8）。本当の制約ではなく、開発者の選択。実装の会話でも、記号を引き始めたら一般の場面で作る（D9）。場面は、あとで `docs/process/summary-page/` にファイルを足し、場面の一覧と AGENTS.md の行を直せば増やせる（D21）。

### 1.4 機構とゴールの対応

| 機構 | ゴールへの寄与 |
|---|---|
| 作る場面の決まり（D9・D10・D22） | 要る会話では言われなくても作り、簡単な題材では作らない。グリルでは最初に作る。頼めば作る |
| 中身の共通の型（D7）と場面ごとの指針（D6・D8・D20） | どの会話でも、冒頭・いまの位置・記号の一覧が同じ場所にある。場面ごとに要る情報（進捗・残件など）を落とさない。指針だけを直せる |
| ページの単位（D25） | 1 つの会話の枠に 1 ページなので、開くページが 1 つで済み、主題を行き来しても作り直さない |
| ひな形（D26） | 直してきた見た目（日本語の字形、畳み方、先頭へ戻るボタンなど）を、どのページにも持ち越す |
| 更新の時機（D11） | 会話の進みとページが食い違わず、どの応答で離れてもそのときの状態が載っている |
| 置き場（D1・D2・D18） | Claude Code と Codex のどちらの会話でも、スマホから同じ URL で開ける |
| 引き継ぎ（D14・D16・D17） | 新しい会話へ移っても、同じページで見返せる |
| 決まりの置き場（D5・D21・D22） | どの会話でも条件に当たれば効き、頼めば起動できる |

### 1.5 成功の測り方

- 場面に入った会話（グリル・実験）と、記号を引き始めた会話で、AI が言われずにページを作り、中身が変わった応答で更新している。会話の記録で数える。
- ページのある会話で、ユーザーが案の中身を確かめるために会話を遡る、または「C は何だっけ」「どこまでやったっけ」と聞き返すことが起きない。ユーザーの報告と会話の記録で確かめる。
- 簡単な会話（Run を 1 本見るだけ、番号で選んで終わるなど）では作られていない。会話の記録で確かめる。
- 費用の側は、1 つの会話でページに使う文脈の合計と、会話が要約された回数を控える（U2）。
- 確かめる会話と、その会話が来ないときの扱いは、受入の A9〜A19 による（D23）。

## 3. 背景

RFD0161 のグリルは論点と方針が多く、AI がまとめのページを作ってユーザーが見返した（P2）。この形は、その会話の中での工夫で、決まりには書かれていない。Atari の枠の会話では作られず、ユーザーは記号の中身を探して会話を遡った（P1）。

## 4. 用語

- **まとめページ**: 会話の手助けになる情報（いまの位置、振った記号とその状態、場面ごとの節）を並べ、会話の進みに合わせて更新する HTML のページ。本 RFD での呼び名で、用語集には足さない（D13）。既存の語のうち、RFD の前提の表・未決表は RFD の中の記録、wiki のトピック別まとめは機能ごとの知見の置き場で、どちらも会話の進みに合わせて更新する見返し用のページを指さないので、言い換えられない。
- **会話の枠**: 1 つの会話と、同じ面で同じ仕事を続けた会話（handoff の引継ぎ文でページを受け取った会話と、同じ枠のページを目印のファイルか題で見つけて続けた会話（みなし方は D27）。D9 の行 3・D14）をひとまとめにしたもの。面をまたいで続けた会話は、別の枠になる（D14）。まとめページは枠ごとに 1 枚（D25）。[memo README](README.md) の「工程と担当」がいう「枠」（起票側の枠、実装する枠など、作業をする会話）は 1 つの会話を指し、handoff で続けた会話を含まないので、言い換えられない。
- **場面**: まとめページの中身の指針を分ける会話の種類。最初に用意するのは、グリル・実験・一般の 3 つ（D8）。既存の「工程」（RFD づくり・実装など。[registry.md](../process/registry.md)）は工程の区切りで、実験や一般の会話を含まないので、言い換えられない。
- **場面の指針**: 場面ごとに、共通の型に足す節を書いた文書（`docs/process/summary-page/<場面>.md`。D6）。既存の「レビュー観点」は成果物の検査、registry の「テンプレート」は成果物の書式（未整備）で、会話のページの中身を指さないので、言い換えられない。
- **ページの名前**: まとめページのファイル名（`.html` と `.md` の共通の部分）に使う短い名前（例: `grill-rfd0197`。D16）。グリルの会話では「題材」と呼んでいたもの。「ファイル名」だけでは `.html` と `.md` のどちらかを指すので、両方の共通の部分を指す語として置く。
- **目印のファイル**: ページの隣に置き、題・面・出した先・状態を書いた数行のファイル（`.scratch/summary/<ページの名前>.md`。D17）。既存の「索引」（課題の `INDEX.md` など）は全件の一覧で、1 ページの所在だけを書くファイルを指さないので、言い換えられない。
- **面**: 会話を動かしている道具の別（Claude Code か Codex）。同じ区別を、プロセスの文書は「サーフェス」と呼ぶ（[registry.md](../process/registry.md) の「サーフェスごとの所在」）。ただし「サーフェス」は、開発者へ見せる文言に使わない内部用語とされている（[プロセス契約](../process/protocol.md) 3.3 節）。まとめページと skill の文言は開発者が読むので、本 RFD では「面」と呼ぶ。
- **ひな形**: 共通の見た目と共通の 3 節の骨組みだけを持つ HTML（`docs/process/summary-page/template.html`。D26）。「テンプレート」は、用語集では設定プロファイルの避ける語に、registry では成果物の書式に使われていて紛れるので、「ひな形」と呼ぶ（下の用語集との関係）。

用語集（`CONTEXT.md`）との関係（2026-11-22 に `CONTEXT.md` を検索して確認）:

- 用語集の「場面」（ForwardScene）は、Forwarder の並びを使う局面（行動選択・Sample・可視化）を指すフレームワークの語である。本 RFD の「場面」は会話の種類を指し、別の語である。AGENTS.md も「〜の場面」を普通の語として使っているので、名前は変えない。
- ページの名前の印 `exp-` と場面の指針の `exp.md` の `exp` は experiment（実験）の略で、用語集の「exp step」（経験の step）とは別である。印は開発者の指定による（D16）。
- skill の名前 `anet-summary-page` の `summary` は、用語集では Metrics Viewer の範囲の統計の避ける語（range summary）に出るだけで、見出しの語ではない。ここでは会話のまとめを指す。`page`・`grill`・`general` は、用語集に無い。
- ひな形のファイル名 `template.html` の `template`（テンプレート）は、用語集では「プロファイル（設定プロファイル）」の避ける語に出る（`CONTEXT.md` の 250 行。設定プロファイルをテンプレートと呼ばない）。本 RFD のひな形は設定ではなく HTML の骨組みで、設定プロファイルとは別である。本文では「ひな形」と呼ぶ。
- 「面」「目印」「会話の枠」「ひな形」は、用語集の見出しの語に無い。

- **D15 終わり方**: 枠の中の主題が済んだら（実験の結論を記録に書いた、など）、その主題の塊に「終わった」と書いて畳む。ページ全体は、次のどちらかのときだけ、いまの位置に「終わった」と書いて最後に 1 回出し、目印のファイルの状態も「終わった」にする（この 2 つは条件の全部で、例ではない）: グリルの枠で、グリルを終えた（完了報告をした）とき／どの枠でも、ユーザーが終えると言ったとき。実験と一般の枠は、ユーザーが終えると言うまで続行中のままにする。ページとファイルは消さない。理由: `.scratch/` は Git が追わないので、残しても害が無く、あとで見返せる（P10）。ページは枠ごとに 1 枚なので（D25）、主題が済むたびにページを終えない。

### 6.4 名前・目印・出し方・見た目・場面の節

- **D16 ページの名前と題**: ページの名前（ファイル名）は英小文字・数字・ハイフンにし、枠の主な主題で付け、最初に作ったときの場面の印を前に付ける（グリルは `grill-`、実験は `exp-`）。一般は印を付けない。例: `grill-rfd0197`、`exp-atari`。同じ面で handoff で続ける会話では、同じ名前を使う。別の枠のページ（面をまたいだ先のページ、終わったページと同じ主題で後から始めたページ）に同じ名前が付くときは、ファイルを上書きせず、終わったページも消さない（D15）。そのときの名前の付け方は D28。ページの題（表示名）は、ファイル名とは別に付ける短い呼び名で、後ろにコロンなどで説明を付けない（例: 「RFD0197 グリルまとめ」「Atari 実験まとめ」）。理由: 印を前に付けると、ファイルの一覧で場面ごとに並ぶ（開発者の指定。推奨は後ろに付ける形だった）。ページは枠ごとに 1 枚なので（D25）、名前も枠の主題で付ける。題は P24。
- **D17 目印のファイル**: `.scratch/summary/<ページの名前>.md` に、題、面（Claude Code か Codex）、出した先（URL。Codex は Site の ID も）、状態（続行中か終わった）、元の会話（日付と主題）、前後のページ（面をまたいだ先のページ、同じ主題で後から始めたページ。D14・D28）を書く。最終更新の時刻は持たない。フォルダは切らず、ページの HTML と並べる。理由: 状態が変わるときだけ書き換えれば済み、毎回の更新の手間を増やさない。並行する会話どうしで同じファイルを書かない（P25）。一覧ファイルを 1 つ置く形は、並行する会話の書き込みがぶつかり、終わった行を消す決まりも要る。HTML の先頭のコメントに書く形は、出したページのソースにも入る。フォルダを切る形は、見づらいので開発者が退けた。
- **D18 出し方と、出せなかったとき**: Claude Code は D1 の道具で出す。Codex は、HTML に外枠（`<!doctype html>`、`<html lang="ja">`、viewport）を付け、ホスティングの設定とともに Sites 専用の Git へ送り、所有者だけの版として出す。外枠と設定は出すときだけ組み立て、`.scratch/summary/` には置かない。出せなかったとき（道具が使えない、Codex のネットワークの許可が下りない）は、手元のファイルを残してパスを知らせ、次に中身が変わった応答でもう一度出す。会話は止めない。理由: P21 で動いた手順そのまま。許可が要る場面があった（P21）。
- **D19 共通の見た目と文言**: 見た目はひな形（D26）が持つ。スマホの幅で読め、明暗の表示に合わせる。文言は平易にし、内部の用語を使わない。ページの言語を日本語と明示し、Web フォントは使わず、端末の日本語フォントにする。先頭へ戻るボタンを常に出す。いまの位置は DOING（進行中）・TODO（次にすること）・WAITING（あなたの返事待ち）・DONE（直前に済んだこと）を同じ形で並べる。全部片付いた塊は既定で畳む。ページの大きさの目安は今は置かず、終わった塊を畳むだけにする（目安は U2 の結果で決める）。記号の状態の語は「未試行」「試行中」「結果あり」「決まった」「退けた」。理由: ゴール（スマホ）、P11、P4 の見た目の決まり、このグリルのページへの開発者の要望（§5.5、§12）。
- **D20 場面の節**: 共通の 3 節（D7）に、場面ごとに次の節を足す。
  - グリル（`grill.md`）: ゴールと非ゴール、前提（欠けた前提は、全部そろったら畳む）、未決表の行とその状態、決まったこと（推奨と違う選択はそう書く）、聞かずに決まった事項、進み具合（グリルの手順のどこまで来たか）、語。
  - 実験（`exp.md`）: Run の一覧（名前、設定の差、状態（段取り中・走行中・完走・止めた）、結果の要点）、比べ方（何を見て判定するか）、決まったこと、未決と残件、進み具合（段取り → 起動 → 途中の確かめ → 分析 → 記録）。
  - 一般（`general.md`）: 共通の 3 節のほかの見出しは、会話に合わせて自由に決めてよい。この旨を指針に明記する。
  同じ枠で別の場面に入ったときは、その場面の節を塊として同じページに足す（D25）。枠の中で主題が並ぶときは、場面の節を主題ごとの塊に分けて持つ（例: 実験の Run の一覧を、Montezuma と Breakout の塊に分ける）。
  理由: グリルの節は、このグリルのページで試して要望を受けて直した形（§5.5）。実験の節は、P1 の会話で要った情報と、Run の運用の流れ。一般で見出しを自由にするのは開発者の指定。
- **D21 AGENTS.md の行**: 「AI エージェントの概念説明ルール」の、記号に名前を添える箇条（416 行）の次に 1〜2 行を足す。書くのは、この箇条を、節の冒頭の文の設計や仕様の議論に限らず、どの会話にも当てること、始める条件のうち AGENTS.md で気づく必要があるもの（実験の場面に入ったとき、前の応答で振った記号をあとの往復で引いたとき、頼まれたとき）、skill `anet-summary-page` を使うこと、チャット枠を移るときは引継ぎ文にページを入れること、場面の一覧が `docs/process/summary-page/README.md` にあること。グリルは `anet-create-rfd` の段で作るので、ここには書かない。場面を足すときは、README とこの行を直す。理由: README を開かなくても、どの会話でも条件に気づける（P9）。節の冒頭の文は「設計や仕様の議論で」と絞っているので、どの会話にも当てると行の中に書く（416 行の箇条と同じ書き方。P3）。手順は書かない（P14）。Run 分析の決まりの側には合図を置かない。AGENTS.md は毎回全文を読むので（P26）、1 か所で足りる。
- **D22 `anet-create-rfd` の段**: 「goal anchor」の節に、goal anchor の応答を出す前に `anet-summary-page` でグリルのまとめページを作る（すでにあれば更新する）旨を足す。両方のコピーをそろえる（P27）。暫定の起票（質疑をしない）では作らない。Plan Mode の間は作らず、作らないことを会話で 1 度だけ知らせ、Plan Mode を抜けた最初の応答で作る。理由: グリルの最初の応答から見返せる。質疑の無い起票には見返す会話が無い。Plan Mode の間はファイルを書けない（P38）。

### 6.5 確かめ方

- **D23 効果の確かめ方**: 実装のあとの最初のグリル 1 本と、最初の実験の会話 1 本で確かめる。見るのは、ページが作られて更新されたかと、ユーザーが遡らずに済んだか（ユーザーの報告と会話の記録）。Codex の会話と、handoff で続けた会話も、最初の 1 本ずつで確かめる。作らない側、変わらない応答で出さないこと、終わり方、面をまたぐとき、出せなかったときも、同じ期間の会話で確かめる。handoff を使わずに続けるときと、同じ名前が付くときも同じ。その会話が実装の完了までに来なければ、課題の対応内容に残し、次の該当の会話で確かめる（受入 A9〜A19）。理由: 合否が、たまたま来た会話に左右されないようにする。
- **D24 見た目と文言の土台**: D19 のうち「スマホの幅・明暗・平易な文言」は、ゴールと P4・P11 から決まる（聞かずに決まる事項として示し、異論が無かった）。

### 6.6 別モデルの検討を受けて決めたもの

- **D25 ページの単位**: まとめページは会話の枠ごとに 1 枚にする。枠の中で主題が並ぶ・移るときは、ページの中に主題ごとの塊を持ち、済んだ塊は畳む（D15）。同じ枠で別の場面に入ったときも、新しいページは作らず、その場面の節を塊として足す（D20）。理由: 開発者の発言「そのチャット枠の会話の手助けになる情報全般」（§12）と単位がそろう。1 つの会話で開くページが 1 つなので「1 か所で見返せる」に合う。困りごとが起きた長い会話（P1）は、1 つの枠で Montezuma と Breakout のように主題を並べて進めるので、主題ごとに 1 枚だと、行き来のたびにページを終えて作り直すことになる（作るたびに約 2.7 万トークン。P7）。主題ごとに 1 枚で同時にいくつも続ける形は、1 つの会話に URL が複数でき、どれが今のページかを探すことになる。
- **D26 ひな形**: `docs/process/summary-page/template.html` を 1 枚置く。持つのは、共通の見た目（D19。ページの言語の指定、端末の日本語フォント、明暗、スマホの幅、先頭へ戻るボタン、畳み方、DOING・TODO・WAITING・DONE の並び）の CSS と、共通の 3 節（D7）の骨組みだけで、スクリプトも場面の節も持たない。ページを作るときは、ひな形を写して中身と場面の節を埋める。理由: 開発者の発言「内容の指針やテンプレ的なのを作っておきたい」（§12）。このグリルで直してきた見た目（§5.5）を固めて持ち越し、ページごとの戻り（漢字が中国語の字形になる、など）を防ぐ。見た目を 1 枚に集めるので、場面ごとに 3 枚持つ形のように食い違わない。置き場は D6 のとおり 1 か所。Claude Code で見た目の決まりの skill を読む分は残る（P36）ので、作る費用がどれだけ減るかは U2 で測る。

### 6.7 レビューで出た未決を埋めたもの

レビュー（2 往復目）の指摘から出た 2 件で、決まりから一意に導けなかったので、レビューが OK になったあとに開発者に聞き、推奨で埋めた。

- **D27 handoff を使わずに続けるときの、同じ枠のページのみなし方**: ユーザーが続けると言った仕事の主題（RFD の番号、実験の対象の名前など）を、同じ面で状態が続行中の目印のファイルの名前と「元の会話」の主題（D17）で照らす。1 つに決まれば、そのページを同じ枠のページとみなして続ける（D9 の行 3）。目印のファイルで 1 つも当たらなければ（目印のファイルが 1 枚も無いときを含む）、面の道具のページの一覧から、同じ主題で題を照らす（D14 の予備の手）。題で照らす候補は、目印のファイルが `.scratch/summary/` に無いページ（目印のファイルが消えたページ）に限る。一覧のページと目印のファイルは、目印のファイルの「出した先」（D17）の URL で結び付ける。目印のファイルがあるページは、題で照らす候補にしない（続行中のものは前の段で照らし終えている。終わったものは続けない。D15）。題で 1 つに決まれば、そのページを同じ枠のページとみなして続け、消えた目印のファイルを作り直す（D9 の行 3）。題でも 1 つも当たらなければ、同じ枠のページは無いとして D9 の行 4 以降で扱う。目印のファイルか題で 2 つ以上当たれば、候補の名前を示してユーザーに選んでもらい、選ばれたページを続ける。選ばれなければ D9 の行 4 以降で扱う。D27 そのものはページを作らない。作るかどうかは D9 の行 4〜7 で決まり、作るページの名前が、終わったページなど別の枠のページと同じになるときは D28 で付ける。理由: ページの名前（D16）は枠の主題の付け方に幅があり、名前だけでは 1 つに決まらないので、ユーザーが示した主題と目印のファイルの両方で照らす。目印のファイルが消えたページを見つける予備に題で探すのは、引き継ぎ（D14）で開発者が選んだ形による。題で探す候補から、目印のファイルがあるページを除くのは、終わったページを続けたり、その目印のファイルを上書きしたりしないため（D15・D28）。迷うときに推測で別の枠のページを続けると、ほかの仕事のページを上書きしうる。
- **D28 別の枠のページに同じ名前が付くときの付け方**: 面をまたいだ先のページ（D14）や、終わったページと同じ主題で後から始めたページのように、別の枠のページに D16 で同じ名前が付き、同じ名前の `.html` か `.md` がすでにあるときは、名前の後ろに `-2`、`-3` と、まだ使われていない番号を足す（例: `grill-rfd0197-2`）。冒頭と目印のファイルの「前後のページ」（D17）には、前のページの URL を載せる。前のページは上書きも削除もしない。理由: 前のページを上書きせず消さない（D15）ためで、番号を足すだけなら、名前の印と主題（D16）を保ったまま、ファイルの一覧で前のページと並ぶ。

## 8. 仕様

- AI は、ユーザーと話す会話で、D9 の表の作る行（行 4〜7）に当たったら、聞かずにまとめページを作り、「まとめページを生成しました: <URL>」を 1 行で知らせる（D9・D10）。
- ページは会話の枠ごとに 1 枚で、主題が並ぶときは主題ごとの塊を中に持つ（D25）。
- ページの中身は、共通の 3 節（冒頭・いまの位置・記号の一覧）に、場面の指針の節を足したもの（D7・D20）。ひな形を写して作り、見た目は D19・D26。
- 中身が変わった応答の最後の前に、1 回だけ出し直す（D11）。Claude Code は同じファイルで出し直して同じ URL を保ち（D1）、Codex は新しい版を出して同じ URL を保つ（D2・D18）。
- ページの HTML は `.scratch/summary/<ページの名前>.html`、目印のファイルは `.scratch/summary/<ページの名前>.md`（D16・D17）。別の枠のページに同じ名前が付くときは、名前の後ろに `-2`、`-3` と番号を足し、前のページを上書きしない（D28）。
- 会話の本文では、記号に名前を添える決まりを続け、問いと決定は会話で行う（D12）。
- チャット枠を移るときは、handoff の引継ぎ文に URL とファイルのパスと skill を入れる。新しい会話は、同じ面なら同じ URL で続け、面をまたぐなら新しいページを作って前のページの URL を載せる（D9 の行 4）。handoff を使わずに続けるときは、同じ面の続行中の目印のファイルか、ページの一覧の題から、同じ枠のページを見つける（D14・D9 の行 3。みなし方は D27）。
- 枠の中の主題が済んだら、その塊を「終わった」にして畳む。グリルを終えたときか、ユーザーが終えると言ったときに、いまの位置に「終わった」と書いて最後に 1 回出し、目印のファイルを「終わった」にする（D15）。
- `anet-create-rfd` のグリルでは goal anchor の応答の前に作る（D22）。
- ユーザーは `/anet-summary-page`（Codex は `$anet-summary-page`）か言葉で、作らせることができる（D5・D9 の行 5）。
- Plan Mode の間は、作らず、更新もしない。作る・更新する行に当たれば 1 度だけ知らせ、抜けた最初の応答で、当たった行の扱いを行う（D9 の行 2・D22）。

## 13. 選ばなかった形

| 形 | 選ばなかった理由 |
|---|---|
| Claude Code で、手元の HTML をファイルを送る道具で毎回送る | 札が更新の回数だけ増え、最新を探すことになる（P5）。Codex にファイルを送る道具が無い |
| Claude Code で、文書を作る道具（Claude Docs）に置く | その道具は頼まれたときだけ作る（P22）。Codex に同じものが無い |
| Codex で、スレッドの中で Markdown のファイルを見せる・ChatGPT Space の Page に置く | 中身が Markdown になり、Claude Code の HTML と型を 2 つ持つ（P18・P19） |
| 決まりを skill だけに置く | 自動で作るのが、skill の説明文に AI が気づくかどうかに頼る（P9） |
| 決まりを AGENTS.md だけに置く | 手順で AGENTS.md が数千バイト増え、細則を外に置く方針（P14）と逆向き。頼む入口が無い |
| 場面の指針を skill のフォルダに置く | skill の本体ではないものを 2 か所にコピーすることになる（開発者の判断） |
| 場面の指針を `registry.md` に置く | 成果物の対応表に別の関心が混ざり、レビュー役にも毎回読ませる（P29） |
| 目印を一覧ファイル 1 つにする | 並行する会話の書き込みがぶつかり、終わった行を消す決まりが要る（P25） |
| 目印を HTML の先頭のコメントにする | 出したページのソースに入り、全体を読むと約 1 万トークンかかる |
| ページごとにフォルダを切る | 見づらい（開発者の判断） |
| 目印・URL を課題や RFD に書く | 公開リポジトリに非公開ページの URL を残す（P23） |
| 会話ごとに新しいページを作り、引き継がない | 主題ごとにページが増え、ユーザーが前のページを探すことになる |
| 記号付きの案が 3 つ以上になったら作る（暫定の既定） | 案を 1 回出しただけの簡単な会話でも、作る費用（P7）を使う |
| 毎回の応答で更新する／大きな区切りだけ更新する | 前者は変わらない応答で費用を使う。後者は離れる直前の状態が載らないことがある |
| ページを主題ごとに 1 枚にし、主題が変わったら前を終える | 1 つの枠で主題を行き来する長い会話で、行き来のたびにページを作り直す（D25） |
| ページを主題ごとに 1 枚にし、同時にいくつも続ける | 1 つの会話に URL が複数でき、どれが今のページかを探すことになる（D25） |
| 記号を引いたら作る条件に除外を置かない／工程の番号付きの選択肢だけを除く | 前者は番号で選んで終わるだけの会話でも作る。後者は会話の途中の 2 択で選ぶ会話を拾い、除く一覧の保守も要る（D9） |
| 実験の場面を、Run の段取りか分析を始めたら作る／実験を場面から外す | 前者は Run を 1 本見るだけの会話でも作る（P35）。後者は実験の節（Run の一覧・比べ方）を使えない（D9） |
| ひな形を置かない／場面ごとに 3 枚置く | 前者はページごとに見た目が戻りうる。後者は見た目を直すとき 3 枚がずれうる（D26） |
| Run 分析の決まりの側にも、まとめページの合図を置く | AGENTS.md は毎回全文を読むので、1 か所で足りる（D21） |
