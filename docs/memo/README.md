# docs/memo — PRD と実装計画の置き場

PRD (`NNN_<slug>_10prd.md`) と実装計画 (`NNN_<slug>_2ximpl.md`) を置く。

**状態と作業順はissueで表す。** 新しいPRDは直下に置き続け、本文に状態の行を持たない。issueはprd欄でPRDを指す（issueとPRDはN:1）。どのPRDにも、prdでそのPRDを指すissueが1件以上ある。PRDの範囲は、それを指すissueの全部で覆う。

| 場所 | 意味 |
|---|---|
| 直下 | 現在のPRD。状態・優先度・依存・順序は対応するissueが正本 |
| done/・frozen/・dropped/ | 過去の保管場所。既存のファイルは動かさず、新しく移さない |

## 採番

起票時に900未満の最大番号の次を取る。暫定の起票も同じ正式番号を使う。一度使った番号はファイルが無くなっても再利用しない。ファイル名とgit履歴（コミットの件名・本文、過去のファイル名）を確認する。欠番を埋めない。

9xxは過去のPRDのIDであり、新しい番号にも作業順の表現にも使わない。旧999はPRD114で未使用の9xxへ振り直した。実装開始時に再採番しない。

## 運用

完了・保留・中止は対応するissueの状態と対応内容で表す。凍結は保留として再開条件を書き、中止は解決か次版として理由を書く。PRDの実装済みは、そのPRDを指すissueの判定と状態から道具が導く（PRDにも判定の欄にも持たせない）。PRDと実装計画は同じディレクトリで保持する。

## 工程と担当

PRD は起票して終わりではない。次の工程を通す。**担当は固定しない**(どの枠が何を持つかはトークン予算で入れ替わる)が、
**工程の非対称は固定する**。

| 工程 | 誰が | 成果物 |
|---|---|---|
| グリルして起票 | 起票側の枠で `anet-create-prd`（題材はissueのIDでもよい）。PRDとissueはissueのprd欄で結び付ける。起草後に自己点検とレビューを行い、未決を示して停止する。暫定の起票はレビューを受けず、再グリルか実装の入口で受ける | `NNN_*_10prd.md` |
| 再グリル(精査) | **起票側とは別の枠**で `anet-create-prd`。モデルが違うほど別の指摘が出る。同じ枠でも任意の「別モデルの検討」で別モデルの論点を受けられる（Claude Code だけ）が、別枠の再グリルを置き換えない | PRD の改訂(改訂履歴を冒頭の引用行に残す) |
| 調整 | 人間。必要なら人間が仲介してエージェント間を往復させる | 裁定の反映 |
| 実装計画 | **実装する枠**が作る | `NNN_*_2ximpl.md`。skill の実行そのものを計画の代わりにする PRD もある |
| 実装・検証 | 実装する枠で `implement-prd-with-docs`。暫定の印がある PRD は、実装の前に PRD のレビューを受ける。実装・検証後に自己点検、レビューと差し戻し対応を行い、未決を示して停止する | コードと検証結果 |
| レビュー | 起票側の枠、および**コミット前に人間**。観点([docs/quality/](../quality/))に照らした判定は、レビューエージェントでも受けられる | 指摘と修正 |
| コミット | `commit` と `push` は人間のみ。文案と、選ばれたときのステージは `anet-prepare-commit` | `git add` / `commit` / `push` |

- **重い PRD ほど枠を分ける。** 起票・精査・実装を別の枠に置くと、単一の枠で通すより品質が上がる。
  この 3 つが同じ枠になることもあるが、少なくとも起票と精査は分ける。
- 軽い変更で枠をまとめる判断は起票時に行い、PRD の確定事項へ「担当」として書く。既定の担当は定めない。暫定の起票（確定事項の節を持たない PRD）では、担当も未決表の行にし、「暫定の既定」の列に書く。
- 枠をまたぐときは **PRD を self-contained に保つ**。受け手は会話履歴を持たないので、決定は PRD 本文に書く。
- 工程ごとの読む条件(何を読んでから着手するか)は [動線マップの表 2](../agents/README.md) が持つ。
- **観点に照らした判定は、skill `anet-review` から頼める**(`/anet-review`、`$anet-review`)。依頼を組み立てて、
  レビューエージェント(`anet-review-agent`)を呼び、応答を平易に言い直して示す(原文は `.scratch/` に保存する)。引数が無ければ、その会話で変更したファイルが対象になる。
  PRD や実装計画のファイル名、パスを渡してもよい。PRD の無い変更も出せる。レビューエージェントを名指しで呼んでもよい。
  観点は、PRD が [docs/quality/prd.md](../quality/prd.md)、実装計画と実装が [docs/quality/impl.md](../quality/impl.md)。
  依頼と応答の形は [プロセス契約](../process/protocol.md) の 2 節と 3.1 節、成果物ごとの観点と入力元は
  [レジストリ](../process/registry.md) が持つ。起草した側も、レビューに出す前に同じ観点を自分で通せる。
  レビューエージェントが見るのは観点の充足で、設計の妥当性は再グリルと人間のレビューが見る。

## リンクの注意

サブフォルダへ移すと相対リンクの深さが 1 段変わる。

- 移動するファイル内の `](../` は `](../../` になる。
- 直下に残るファイルを指すリンクには `](../` を足す。
- 他ディレクトリ(`docs/design` 等)から移動先を指すリンクにはフォルダ名を挿入する。
- 同じ行き先へ一緒に移る組(PRD と対応する実装計画など)のリンクは無修正で生き残る。

移動後は必ずリンク切れ検査を実行する。

```bash
find docs -name '*.md' | while read f; do
  grep -ohE '\]\([^)#][^)]*\)' "$f" | sed 's/^](//; s/)$//' | grep -v '^http' | while read l; do
    [ -e "$(dirname $f)/${l%%#*}" ] || echo "BROKEN: $f -> $l"
  done
done
```
