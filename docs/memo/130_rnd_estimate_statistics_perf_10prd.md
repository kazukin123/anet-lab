## 1. 目的と問題

### 1.1 問題

既定の RND（`statistics_mode = whiten`）を有効にした Atari の Run は、RND なしの 1.661 倍の実時間がかかる。RND の時間の 62.66% は、採点（`Estimate`）の中の統計の区間が占める（§2.1）。この区間は CPU の 1 スレッドで動く。放っておくと、RND を使う実験（Montezuma の β の比較、価値の分解、[PRD924](924_intrinsic_reward_novelty_10prd.md) の NGU）の 1 本ごとの実時間が、この分だけ長いままになる。

同じクラスに 2 つの統計方式（whiten と variance_feedback）が同居し、どちらの組が有効かを表す分岐が、採点・補助学習・読むだけの採点・写し・保存・読み込みに散っている（§2.5）。統計の区間を組み替えると、この分岐の全部に触ることになる。

統計の区間のどの処理に時間がかかっているかは、起票の時点では測っていなかった。ステージ 0 で測り、時間の大半は、観測の統計の更新の中の、batch 方向の平均と分散の集計だった（§2.8）。

### 1.2 ゴール

- **G1**: 既定の RND を有効にした Run の実時間が、RND なしに近づく（測り方は §1.5）。
- **G2**: 2 つの統計方式が型で分かれ、方式を 1 つ足すときに触る場所が 1 か所になる。採点と補助学習の共通の前半が 1 つになる。
- **G3**: 統計の区間の内訳を、あとからいつでも Tracy で測れる。
- **G4**: §9 の課題 2 件が片付く。

### 1.3 非ゴール（退けた案と、本当の制約か）

| 退けた案 | 理由 | 本当の制約か |
|---|---|---|
| Evaluation Trace を開いている間の、推定器の写し（`Clone`）を軽くすること | 題材の外（[issue-20261114-9468cb](../management/issues/issue-20261114-9468cb.md)）。採点の統計とは別の経路で、開発者は今の遅れを許容とみている | 制約ではない（別の課題で扱える） |
| Taiga 設定（`variance_feedback`、補助学習を 1 件ずつ）の補助学習の費用を下げること | 費用の主因は設定そのもの（1 件ずつの backward と optimizer step で 64.63%）で、統計の区間は 0.34% である（§2.1） | 制約ではない |
| target と predictor の forward と、補助学習の backward を軽くすること | 既定の RND では合わせて 20.70% で、統計と正規化（74.58%）より小さい。Network の形と AMP の話になり、別の関心である | 制約ではない |
| 観測の正規化の部品を使う、RND 以外の呼び出し（DQN の観測の正規化）を変えること | Q の学習の値と診断値に関わる。既定が素通しで、費用も無い（§5.1 の D4） | 制約ではない |

| 可塑性メトリクスの計算による停止を直すこと | RND とは別の関心である（§10。課題に起票済み） | 制約ではない |
| RND の設定キー、メトリクスの名前、checkpoint の書式を変えること | 今ある Run の設定と checkpoint を、そのまま使い続ける（§4） | 制約ではない（クリーンブレークで移せるが、移す理由が無い） |

### 1.4 機構とゴールの対応

新しい機構は足さない。足す部品は次のとおりで、名前は §6.2 に置いた。

| 足すもの | ゴールへの寄与 |
|---|---|
| 統計の区間の中の計測の区間（実装済み） | G3 |
| 正規化と batch の集計を計算 device で行う並び（D1〜D3） | G1、G4（f9790d） |
| 観測の正規化の部品の、統計だけを更新する口（D4）と、平均と標準偏差の写し（D5） | G1、G4（f9790d） |
| batch 方向の集計の式の差し替え（D7）と、統計を更新しない正規化で clip の割合を数えない直し（D6） | G1、G4（f9790d） |
| 方式ごとの統計をまとめる型と、3 つの処理の単位（D12） | G2、G4（0ddffa） |

### 1.5 成功の測り方

- 既定の RND の実時間 ÷ RND なしの実時間（同じ回・同じ実行体・同じ経験数で、3 巡の群ごとの中央値）が、主の構成（§5.6）で 1.15 以下、副の条件で 1.25 以下になる（D16）。
- Tracy で、採点の統計の区間に、捨てている正規化の区間が出ない。
- 整理のあと、`RndNoveltyEstimator` の中で、統計方式によって分かれる箇所が、構築時に型を選ぶ 1 か所だけになる。

### 2.2 採点の処理の流れと、計算する場所

`RndNoveltyEstimator::Estimate`（[intrinsic_rnd.cpp:504](../../core/anet-core/src/intrinsic_rnd.cpp) から）は、1 intake の N 件の観測をまとめて、次の順に処理する。

1. 観測を CPU へ移す（515 行）。
2. CPU で、整数の画素を浮動小数点にし（518〜519 行）、正規化する（522〜528 行）。
3. 正規化した観測を計算 device へ送る（530 行）。
4. target と predictor の forward を行い、誤差を作る（532〜536 行）。
5. 誤差 N 件と、target の出力（N×出力次元）を CPU へ戻し、誤差が有限かを確かめる（538〜546 行）。
6. 統計の区間（547〜580 行。中身は §2.3）。
7. 倍率 α を、入力と同じ device へ返す（582 行）。

設計文書も、観測を CPU へ移して正規化し、誤差の検査と統計を CPU で扱うと書いている（[212](../design/212_rnd_lifelong_novelty.jp.md) の §5.1）。入力は、学習の入口に届く生の観測の最新 1 フレームである（[PRD116](116_rnd_lifelong_novelty_10prd.md) の D5）。

§2.1 の測定では、観測の転送と結果の転送が 1 intake あたり合わせて 0.003 ms だった。この値から、測った構成では観測と α が CPU にあったと読める。コードでは確かめていない（§5.2 の Q3）。

### 2.3 統計の区間の中身

既定（whiten）では、統計の区間で次を CPU で行う。課題 f9790d が起票時に挙げた中身と、今のコードは同じである。

- **α の計算と誤差の統計の更新**（556〜561 行）。誤差の統計の平均と標準偏差で α を作り、N 個の誤差で統計を更新する。
- **観測の正規化統計の更新**（563 行）。`NormalizeAndUpdateStats` を呼び、戻り値は使わない（562 行の `@todo`）。この関数は、統計を更新したあと（[scaler_impl.cpp:553](../../core/anet-core/src/scaler_impl.cpp)）、渡された観測の全体を正規化し直して、clip した割合を数える（同 556〜557 行、425〜434 行）。
- **target の出力の統計の更新**（575 行）。N×出力次元の値で、次元ごとの累積の統計を更新する。
- **診断値の読み出し**（576〜580 行）。target の出力の分散の平均と最大、誤差の平均、α が上限に当たった割合。

統計の更新（`RunningMeanStd::Update`、[scaler_impl.cpp:149](../../core/anet-core/src/scaler_impl.cpp) から）は、batch の平均と分散を、渡された入力の device と精度で計算し（171 行）、結果を CPU の倍精度へ移して（179〜180 行）、累積へ合流する（197〜221 行）。正規化（同 374〜388 行）は、呼ぶたびに、累積の標準偏差と平均を、入力の device の単精度に作り直す（377・383 行）。

variance_feedback では、観測の統計も誤差の統計も、lane の順に 1 件ずつ更新する（[intrinsic_rnd.cpp:177-225](../../core/anet-core/src/intrinsic_rnd.cpp)）。この順は方式の定義である（[PRD116](116_rnd_lifelong_novelty_10prd.md) の D5）。

### 2.4 採点を呼ぶ側（PRD128・PRD121 のあと）

- 採点を呼ぶのは `DefaultDQNAgent::IntrinsicRewardCoordinator::ScoreBonus`（[default_dqn_agent.cpp:110](../../core/anet-core/src/default_dqn_agent.cpp) から）である。α からボーナスを作り、内的報酬用の報酬スケーラを通し（117 行）、価値の分解のために、β を掛ける前の成分も返す（119 行）。
- 同じ関数が、ボーナスの診断値を 6 回の `.item<float>()` で読み出す（122〜127 行）。ボーナスが CUDA にあれば、1 回ごとに同期の転送になる。PRD128 は、これを 1 回の転送にまとめる案を範囲の外に置き、RND の時間の内訳と合わせて測るときに決め直すとした（[PRD128](128_dqn_agent_refactor_bundle_10prd.md) の §1.3、[324 DQN のトピック別まとめ](../wiki/categories/324_dqn.md) の「選ばなかった形」）。
- §2.1 の数値は、PRD121 より前の実行体のものである。価値の分解を入れたあとの基準は取り直す（§5.2 の Q6）。

### 2.5 2 つの統計方式の同居と、前半の重複

- whiten は `normalizer_` と `error_stats_` を使い、variance_feedback は `feedback_stats_` を使う。どちらが有効かは、`feedback_stats_` が値を持つかだけで表される（[intrinsic_rnd.hpp:116-119](../../core/anet-core/src/intrinsic_rnd.hpp)）。
- この分岐は、コンストラクタ（[intrinsic_rnd.cpp](../../core/anet-core/src/intrinsic_rnd.cpp) の 456 行）、写し（478・487・492 行）、`Estimate`（522・549 行）、`EstimateWithoutUpdate`（594・604 行）、`Learn`（633・642 行）、`Save`（691 行）、`Load`（729・739・743 行）にある。課題の起票のあと、PRD127 の読むだけの採点と写しにも同じ分岐が入った。
- `RndErrorStatistics` も、累積と直近重みの 2 組のメンバを持ち、メンバ関数が `use_ema_` で分かれる（同 72・91・96・101・107・116 行）。
- `VarianceFeedbackStatistics::UpdateErrors` は、直前に `NormalizeAndUpdate` が同じ件数で件数を進めていることを前提に、件数を逆算する（同 218 行）。この呼ぶ順の前提は、型にも名前にも出ていない。
- `Estimate`（514〜546 行）と `Learn`（637〜661 行）の前半は、CPU への転送、浮動小数点への変換、正規化、device への転送、2 つの forward、誤差の計算、有限性の検査が同じ並びである。違いは、`Learn` が predictor の forward の前に勾配を有効にする 1 行である。`EstimateWithoutUpdate`（590〜600 行）も同じ並びを持つ。

### 2.9 1 intake の処理の流れ（2026-11-15 にコードで確認）

この節と §2.10 の行番号は、計測の区間を足したあとの作業ツリーの位置である。

既定（whiten）の RND の処理は、読むものと書くものから、3 つの単位に分けられる。時間は §2.8 の主の値である。

| 単位 | コードの位置 | 読むもの | 書くもの | 時間（1 intake） |

| 関係 | 種類 | 根拠 |

| 採点 → push | データの依存 | ボーナス（価値の分解では内的報酬の成分）を報酬に載せてから、内側の Learner へ渡す（[default_dqn_agent.cpp:956-959](../../core/anet-core/src/default_dqn_agent.cpp)、977 行） |

| 採点 → 観測の統計の更新 | 方式の定義 | 採点は更新前の統計で行い、採点のあとに更新する（[PRD116](116_rnd_lifelong_novelty_10prd.md) の D5） |
| 採点 → 同じ intake の補助学習 | 方式の定義 | 設計文書の処理順（[212](../design/212_rnd_lifelong_novelty.jp.md) の §3.6 の図と、その説明） |

| 統計更新・補助学習と、push・Q の学習 | 依存なし | Q の学習は、RND の重みと統計を読まない。RND の補助学習と DQN の更新は、別々の重みと optimizer を使う（[212](../design/212_rnd_lifelong_novelty.jp.md) の §3.6） |

- variance_feedback は、lane ごとに正規化と統計の更新を交互に行い、誤差の z を更新後の統計で作る（[PRD116](116_rnd_lifelong_novelty_10prd.md) の D5、522〜525 行、549〜554 行）。採点と統計更新を分けられない。

NGU に関わる記録は次のとおり。

- [PRD924](924_intrinsic_reward_novelty_10prd.md) の §4.6 の基準案（未決）は、内的報酬を収集時の事実として保存し、学習時に再計算しない。新規性は、観測をエピソード内の記憶へ加える前に算出し、そのあとに記録を更新する。
- PRD924 の §4.5 の基準案（未決）は、Q への条件付けに、直前の外的報酬と内的報酬を入れる。
- NGU 原典は、actor が内的報酬を算出して Replay へ入れ、learner が、抽出した系列の末尾 5 時点で、行動予測網と RND の predictor を学習する（[PRD116](116_rnd_lifelong_novelty_10prd.md) の §8.1 の 3、PRD924 の §4.6 が引く原典の付録 A）。

- NGU 原典が、RND の誤差の統計をどこで更新するかは、確かめていない。

### 2.11 計算 device へ寄せる試作の測定の結果（2026-11-15）

### 2.12 型の変換と正規化の所在、集計の部品を使うもの（2026-11-16 にコードで確認）

グリルの質疑で確かめた。

- **前処理は 2 段ある。** NN の外（Agent と推定器）の正規化と、NN の中の前処理である。NN の中の前処理（`NetworkBoundaryPreprocessor::Format`、[nn_impl.cpp:1174](../../core/anet-core/src/nn_impl.cpp) から）は、離散の観測を one-hot にし（1203〜1237 行）、連続の byte の観測を浮動小数点にして 255 で割る（1240〜1241 行）。受け取った tensor の device の上で動く。Q の Network も、RND の target と predictor も、これを通る。
- **Q の主の経路は、device へ送ってから正規化する。** Actor は、frame stack、device への転送、観測の正規化の順に行う（[dqn_based_agent.cpp:2701-2708](../../core/anet-core/src/dqn_based_agent.cpp)）。学習は、計算 device のサンプルを正規化する（同 3799〜3800 行）。正規化は NN の外にある。
- **RND の正規化は、共通の観測の正規化の部品である。** 推定器は、自分用の設定と統計で、部品を 1 つ持つ（[intrinsic_rnd.cpp](../../core/anet-core/src/intrinsic_rnd.cpp) のコンストラクタ）。RND 独自なのは、その手前で、連続の byte の観測を浮動小数点へ変える処理だけである。Network を組むときに、その観測の型を浮動小数点に書き換えるので、NN の中で 255 で割られない。
- **観測の種類ごとの通り道。** 正規化の部品は、浮動小数点で離散でない観測にだけ統計を付ける（[scaler_impl.cpp:721-724](../../core/anet-core/src/scaler_impl.cpp)）。連続の byte（Atari の画素）と連続の浮動小数点（LunarLander の観測など）は白色化され、離散の観測（GridMaze のマスなど）は素通しで、NN の中で one-hot になる。観測が画像であることは、RND の制約ではない。どの観測を RND の Network に入れるかは、RND の Network の設定の、枝の `bind` で決まる。
- **`RunningMeanStd` を持つもの。** 統計つきの観測の正規化（[scaler_impl.hpp:149](../../core/anet-core/src/scaler_impl.hpp)）、報酬スケーラ（同 213 行）、RND の誤差の統計と target の出力の統計（[intrinsic_rnd.hpp:80](../../core/anet-core/src/intrinsic_rnd.hpp)、118 行）である。batch 方向の集計の行（[scaler_impl.cpp:173](../../core/anet-core/src/scaler_impl.cpp)）を通るのは、観測の正規化と target の出力の統計で、全要素の集計の行（同 166 行）を通るのは、報酬スケーラと誤差の統計である。
- **Q 入力用の観測の正規化は、既定が素通しである**（[agent.txt:304](../../apps/runner/config/agent.txt)）。`apps/runner/config/` の設定ファイルを `obs_norm` で検索したところ、素通しを切る指定は無かった。batch 方向の集計の行を通るのは、出荷の設定では RND だけである。
- **統計つきの正規化を呼ぶコード**（テストを除く）は、Q 入力用の 2 か所（[default_dqn_agent.cpp:964-965](../../core/anet-core/src/default_dqn_agent.cpp)）と、RND の採点の 1 か所である。
- **計算 device が CPU の構成での統計の費用。** GridMaze（CPU、256 lane）の測定では、統計は RND の時間の 4.72% だった（[PRD116 の実装記録](116_rnd_lifelong_novelty_23impl.md)）。

## 4. 規約と過去の判断

- 毎回の学習の更新に通る経路に、device 間の同期の転送を足さない。足すときは、頻度×1 回あたりの時間の見積もりを書く。計測済みの処理を分けたら、分けたあとの区間にも計測を置く（[実装 品質確認観点](../quality/impl.md) の「計測」）。
- RND の統計の取り方を変えるときは、`warmup_mode = collect_errors` の組、`variance_feedback`、RND 無効の 3 構成で、同 seed・決定的モードの短い Run の metrics checksum を、着手前に保存した実行体と一致させる（[PRD123](123_rnd_intrinsic_reward_scale_10prd.md) の §4 D5・§7.2 の 1）。本 PRD のステージ 1 は、値の前提（§5.1）により、whiten の構成ではこの一致を求めず、値の近さで確かめる。RND 無効と variance_feedback の構成では、一致を求める（§7 の 4）。ステージ 2 は、すべての構成で一致を求める（§7 の 11）。
- RND の累積と `variance_feedback` の checkpoint は、書式の識別子と中身を変えず、着手前に保存した実行体の checkpoint を同じ設定で読める（[PRD123](123_rnd_intrinsic_reward_scale_10prd.md) の §4 D11）。
- 読むだけの採点を挟んでも、学習へ渡る報酬の列と診断値が変わらない（[PRD127](127_eval_trace_intrinsic_reward_columns_10prd.md) の §7 の 10）。読むだけの採点の倍率は、直後に同じ観測 1 件を採点へ渡したときの倍率と一致する（同 §5.1）。
- 挙動を変えない直しでは、hot path の速さが変わらないことを Run のブレ幅で確かめる。「挙動を変えない」には、ログの文言と WARN の回数を含める（[リファクタリング観点](../quality/refactor.md) の「ガードレール」「運用ルール」）。
- 汎用の部品の局所的な情報だけで結果が決まる処理は、個別の実装の中に書かず、その部品の共通処理として足して利用側から呼ぶ（[AGENTS.md](../../AGENTS.md) の「汎用機構と利用側の責任境界」）。

### 5.3 ステージ 2: 統計方式の整理（値を変えない）

D12 の中身である。

- 方式ごとの統計（観測の正規化、誤差からの倍率、診断の平均と標準偏差、保存と復元）を 1 つの型にまとめ、whiten 用と variance_feedback 用の実装を、構築時に 1 つ選ぶ。
- 誤差の統計も、累積用と直近重み用に分ける。
- 型の口は、採点のための正規化、誤差から倍率を出して統計を進めること、補助学習を休むかどうか、を中心にする。正規化をどの device で行うか（whiten は計算 device、variance_feedback は CPU）と、正規化のときに統計を更新するか（variance_feedback は更新する）は、実装が持つ。
- 採点・補助学習・読むだけの採点に共通する、正規化のあとの部分（2 つの forward、誤差の計算、有限性の検査）を、1 つにする。ステージ 1 で 3 か所に書いた置き場の変更は、whiten の実装の 1 か所になる。
- whiten の処理を、採点（読むだけ）、統計更新、補助学習の 3 つの単位に切る（§2.10）。variance_feedback は、採点と統計更新を分けない。採点と補助学習の間で、中間の結果（正規化した入力、target の出力）を使い回さない。whiten の採点から統計更新へは、誤差、target の出力、観測を渡す。
- warm-up の扱い（採点で倍率を 1 にする条件、誤差を統計に入れるか、補助学習を休むか）は、方式の実装が持つ。判定の単位と、補助学習を休む条件が、方式で違うためである（§2.10）。
- `UpdateErrors` が件数を逆算する前提は、観測の統計の更新と誤差の統計の更新を、variance_feedback の実装の中の 1 つの流れにして無くす。
- 公開の口、checkpoint の並びと書式の識別子、設定キー、診断の鍵、ログの文言、既存の計測の区間名は変えない（D12、D13）。

### 5.5 頻度と単価の見積もり

- 頻度: 採点と統計更新は、intake ごとに 1 回で、N 件をまとめて処理する。補助学習は、`learn_ratio` と `learn_batch_size` で決まる回数で、主の構成では intake ごとに 1 回である。
- 単価（主、Tracy をつないだ状態）: 今は、RND 全体が 1 intake あたり 23.347 ms（1 exp step あたり 0.182 ms）である。試作は 6.482 ms（0.051 ms）だった（§2.11）。C1・C3・C9 を足すと、さらに約 1 ms 減る見積もりである（§5.7 の AI の整理 7）。区間の足し引きによる見積もりで、確かではない。
- 足す同期の転送: 採点 1 回あたり、CPU への読み戻しが、誤差に加えて、集計の結果（観測と target の出力）と、target の出力の最大値の分だけ増える。試作の測定で、増える分は合わせて約 0.2 ms だった。計算 device へ送る量は、浮動小数点 3.6 MB から、整数の画素 0.9 MB になる。

- 起票時の見積もり（副の条件で 1.267）は、試作の測定（参考の比 1.117）で置き換えた。

**AI の整理 1: CPU と GPU の分担**

採点の各段を、開発者の 3 つの原則に当てた。大きさは主の構成（128 観測）の値である。

| 段 | 大きさ | 今 | 原則に当てた置き場 |
|---|---|---|---|
| 観測が届く | 画素 0.9 MB（整数） | CPU | CPU（Env の出力） |
| 浮動小数点への変換、正規化、clip | 約 90 万要素 | CPU（2.679 ms） | 計算 device |
| 計算 device への転送 | — | 浮動小数点 3.6 MB | 整数の画素 0.9 MB |
| forward 2 本 | — | 計算 device | 計算 device |
| 観測の統計の batch の集計 | 約 90 万要素 | CPU（11.857 ms） | 計算 device |
| CPU への読み戻し | — | target の出力 256 KB と誤差 128 件 | 集計の結果（約 60 KB）と誤差 128 件 |

- 線引きは要素数である。約 90 万要素の一括の演算は計算 device、数千要素以下の状態の更新は CPU に置く。
- 今 CPU に置いているのは、既存の CPU の正規化と統計の部品を使うためだった（[PRD116 の実装計画](116_rnd_lifelong_novelty_21impl.md) の「入力 device と計算 device を分け」の行）。正しさの理由ではない。
- 部品は、入力の device を問わない。正規化は入力の device で計算し（[scaler_impl.cpp:378](../../core/anet-core/src/scaler_impl.cpp)）、統計の更新は、入力の device で batch を集計してから、結果を CPU の倍精度へ移す（同 173 行、182〜183 行）。観測を先に計算 device へ送れば、CPU の `var_mean` を通らない。
- GPU には空きがある（§2.8 の Q4）。RND の CPU の計算の間に GPU が止まるのは、GPU への処理を出すのが同じスレッドだからである（§2.9）。CPU の計算を短くすると、その分だけ GPU の空きも減る。

**AI の整理 2: 2 つの進め方の比較（CPU のまま無駄を除く形の時間は見積もり。計算 device へ寄せた形は、あとから試作で測った）**

| | 今 | CPU のまま無駄を除く（C1・C8・C9） | 一括の演算を計算 device へ（C2 と C1・C9） |
|---|---|---|---|
| RND（主、1 intake） | 23.2 ms | 7〜8 ms | 起票時の見積もりは 5〜6 ms。試作（C1・C9 なし）の測定は 6.482 ms（§2.11） |
| RND 無効の構成の値 | — | C8 が共通の集計の式を変えるので、丸めの範囲で変わりうる | 変わらない |
| RND 有効の値 | — | 丸めの範囲で変わる | 丸めの範囲で変わる |
| 転送 | — | 今のまま | 計算 device へ送る量が 4 分の 1、読み戻しが小さくなる |
| 設計文書（212 の §5.1） | — | 今のまま | 「CPU で扱う」を書き換える |
| CPU で計算する構成（GridMaze など） | — | 効く | 効かない |

- 見積もりの内訳（主、1 intake）: C8 が約 −12 ms（batch の集計 11.857 ms と 0.745 ms が、参考測定の比で約 0.6 ms になるとした）、C1 が −1.5 ms、C9 が約 −2.5 ms（採点と補助学習の clip の区間 1.716 ms と 1.011 ms のうち、clip そのもの以外。内訳は測っておらず、推定である）。

**AI の整理 3: 並列処理化**

- 演算の中の並列（CPU のスレッド数）は、実時間が延びた（§2.8 の Q7）。
- 採点を別のスレッドへ出す形は、得が小さい。メインスレッドは、1 intake に約 100 ms、学習の完了を待っている（§2.9 の値からの計算）。そこで採点すれば 1 intake から外せるが、無駄を除いたあとの RND は 5〜8 ms の見積もりで、得は 1 intake の 5% ほどである。採点と補助学習は predictor と統計を共有するので、順が変わると値が変わる。push がボーナスを待つ形も作り直しになる。
- GPU の側の並行は要らない。時間がかかっているのは kernel の発行で、10 秒のうち 2.617 秒である（§2.8）。
- 順の案: 無駄を除く、一括の演算を計算 device へ寄せる、それでも RND が 1 intake の 1 割以上残れば並列処理化を検討する。

**AI の整理 4: 前後関係を崩したときの帰結（§2.10 の表への補い。推定を含む）**

- 観測の統計の更新を採点の前に移すと、採点する観測自身が、正規化の統計に入る。
- 補助学習を採点の前に移すと、学習したあとの観測を採点するので、誤差が小さく出る。
- 補助学習が次の採点より遅れると、その分だけ古い predictor で採点し、誤差が大きめに出る。NGU 原典の形（actor が算出し、learner が学習する）では、actor の重みは learner より古くなる（構成からの推定で、原典の記述は確かめていない）。
- 統計更新と補助学習は、データの依存では、次の採点までに終わればよい。今の 23.2 ms のうち、push の前に要るのは、採点の約 4.2 ms である。

**AI の整理 5: NGU で変わること・変わらないことと、本 PRD への含み**

- 採点は、NGU でも収集時（push の前）のままである（PRD924 の §4.6 の基準案）。エピソード内の新しさは、その lane のエピソードの記憶に照らして出すので、あとから Replay のサンプルだけで再計算できない。
- PRD924 の §4.5 の基準案（Q の入力に直前の内的報酬）を採ると、採点は次の行動の決定より前に要る。今は、行動を決めたあとに学習用のスレッドで採点している（§2.9）ので、採点の置き場が動く。
- 補助学習は、母集団が intake の観測から Replay へ変わりうる（§2.10）。
- 本 PRD への含みは 4 つある。(1) 整理（ステージ 2）で、採点（読むだけ）、統計更新、補助学習の 3 つの単位に分ける。置き場が変わっても、部品は変わらない。(2) 採点と補助学習の間で、中間の結果（正規化した入力、target の出力）を使い回さない。補助学習が Replay の側へ移ると、使い回せない。(3) 採点から統計更新へは、同じ観測の誤差、target の出力、観測の集計を渡してよい。計算 device で集計すれば、統計更新は CPU での小さな合流だけになる。(4) 入力の device で正規化する形が合う。Replay のサンプルは計算 device にあり、今のコードは必ず CPU へ移す（[intrinsic_rnd.cpp:515](../../core/anet-core/src/intrinsic_rnd.cpp)、643 行）ので、往復の転送になる。
- 3 つの単位に分けるのは構造のためで、速さのためではない。無駄を除いたあとは、どの単位も数 ms の見積もりである。

**AI の整理 6: 律速と、同期の待ちを遅らせる形（推定を含む）**

- 今は、3 つの単位とも学習用のスレッドに乗っている（23.2 ms）。データの依存で push の前に要るのは、採点（約 4.2 ms）だけである（§2.10）。
- 学習用のスレッドが RND に使う時間は、CPU での計算、kernel を出す時間、GPU の完了を待つ時間（CPU への読み戻し）の 3 つに分かれる。待つ時間は小さい。採点の誤差の転送が 0.174 ms、補助学習の誤差の転送が 0.128 ms で、`cudaStreamSynchronize` は 10 秒のうち 0.016 秒だった（§2.8）。GPU の実行は、今も、出した側を待たせていない。
- そのため、「GPU に載せて、完了を待たない」形の得は、CPU での計算（統計 13.587 ms、採点と補助学習の正規化 2.679 ms と 1.535 ms）を GPU へ移す分であり、C2 と同じである。待ちを次の採点まで遅らせること自体の得は、0.1〜0.2 ms の見積もりである。
- 統計更新は、遅らせなくてよい。batch の集計の kernel を forward と同じ流れで出し、集計の結果を誤差と一緒に 1 回で読めば、採点に要る 1 回の読み戻しに相乗りできる。
- GPU へ寄せたあとに残るのは、補助学習の kernel を出す時間である（forward 2 本 0.871 ms、backward 0.852 ms、optimizer 0.754 ms。合わせて約 2.5 ms）。これは学習用のスレッドの CPU の時間で、ストリームを分けても残る。無くすには、CPU の別のスレッドから出す形（§5.1 の D9）が要り、得は 1 intake の 2〜3% の見積もりである（試作の前の見積もりである。試作の測定では、補助学習は 3.612 ms で、1 intake の約 100 ms の 3〜4% に当たる。§2.11）。
- ストリームは 1 本のままが扱いやすい。同じストリームの処理は、出した順に実行される。前回の補助学習の更新が、次の採点の forward より先に終わることは、待ち合わせを書かなくても成り立つ。ストリームを分けると、その順を明示の待ち合わせで作ることになる。ストリームを分ける効果が出るのは GPU が詰まっているときで、今は kernel が動く時間が最大 37.1% である。libtorch でストリームを分ける口の扱いは、確かめていない。
- 補助学習の途中の読み戻し（誤差の有限性の検査と、loss の診断値。[intrinsic_rnd.cpp:658-667](../../core/anet-core/src/intrinsic_rnd.cpp)）を無くすと、検査が optimizer の更新のあとになる。今は、異常な誤差で重みを汚さないように、更新の前に検査している。得が 0.128 ms なので、変えない案とする。
- 段階の案: (1) 無駄を除く（C1・C8・C9）。(2) 一括の演算を GPU へ寄せ、読み戻しを採点の 1 回にまとめる（C2）。(3) 補助学習を別のスレッドから出す（入れない。§5.1 の D9）。(2) の時間は、あとから試作で測った（§2.11）。

**AI の整理 7: 試作の結果の読み（2026-11-15。見積もりを含む）**

- 計算 device へ寄せる形は、C1・C3・C9 を入れない素朴な形でも、RND を 1 intake あたり 23.347 ms から 6.482 ms にした（§2.11）。起票時の見積もり（5〜6 ms）に近い。
- 試作の内訳から、さらに約 1 ms を削れる見積もりである。捨てている正規化（C1）が 0.336 ms、平均と標準偏差の作り直し（C3）が 3 回で 0.378 ms、統計を更新しない正規化の clip の区間（C9 の対象）が採点と補助学習で 0.157 ms と 0.121 ms である。clip の区間のうち、割合を数える処理の分は測っていない。
- C3 の当否が変わった。CPU では 1 回 0.067 ms だったが、計算 device では、作り直しのたびに転送が入り、1 回 0.10〜0.17 ms になる。
- 試作で新しく出た費用は、採点の観測の転送（主で 0.558 ms）である。
- 削ったあとに残るのは、補助学習（3.612 ms）と採点の forward（0.695 ms）で、kernel を出す時間が中心である（AI の整理 6）。
- GPU の完了を待つ時間は、試作でも小さい。`cudaStreamSynchronize` は 10 秒のうち 0.034 秒だった。kernel が動く時間は最大 44.8% で、GPU は埋まっていない。
- 区間ごとの足し引きによる見積もり（さらに約 1 ms）は、確かではない。計算 device への転送は、先に積まれた GPU の処理の完了を待つことがあり、試作で増えた区間（採点の観測の転送、補助学習の backward と optimizer の更新）は、待つ時間が別の区間へ移っただけの可能性がある（推定で、確かめていない）。受入は、実時間で判定する（§7 の 1）。
- 「CPU のまま無駄を除く」形（C1・C8・C9）の時間は、測っていない。C8 は、計算 device が CPU の構成のために要る（開発者の発言）。計算 device が CUDA の構成では、C2 を入れると batch の集計は CPU の `var_mean` を通らないので、C8 の効果は出ない。

### 6.1 変えないもの

設定キー、メトリクスの名前、診断の鍵、checkpoint の書式の識別子と中身の並び、ログと WARN と ERROR の文言・順・回数、seed の作り方、乱数の消費の順、forward の回数と順、一生の新しさの口（採点、読むだけの採点、補助学習、診断、保存と読み込み、写し）、既存の計測の区間名、Q 入力用の観測の正規化の呼び出し、NN の中の前処理（D3、D4、D13）。

意図して変える点は次のとおり。

- ステージ 0（実装済み）: 計測の区間が増えた。既存の `statistics` の区間は、α の計算、誤差の統計の更新、観測の統計の更新（内側の区間 `observation_statistics`）を指し、target の出力の統計と診断値の読み出しは、続く別の区間になる。2026-11-12 の記録の「統計」と比べるときは、`statistics`・`target_feature_statistics`・`diagnostics` の 3 つを足す。
- ステージ 1: 計算 device が CUDA の、既定 RND を有効にした Run で、観測の統計、α、内的報酬が、丸めの範囲で変わる（D1）。計算 device が CPU の、既定 RND を有効にした Run も、観測の統計と target の出力の統計が、丸めの範囲で変わる（D7）。variance_feedback は、診断値 `target_feature_var` だけが、丸めの範囲で変わる（D10）。
- ステージ 1: RND 無効の Run は、出荷の設定では変わらない。Q 入力用の観測の正規化を、設定で素通しから統計つきに変えた Run だけ、観測の統計が丸めの範囲で変わる（D7、§2.12）。
- ステージ 1: 計測の区間は、名前を変えない。採点と補助学習の `observation_transfer` は計算 device への転送を測るようになり、`input_transfer` は転送を含まなくなる。採点の統計の区間に、正規化のやり直しは入らなくなる（D4）。
- ステージ 1: 統計を更新しない正規化は、clip した割合を数えない（D6）。統計つきの正規化の診断値（clip の割合）は、今と同じく、統計を更新する正規化が数えた値である。
- ステージ 1: 統計だけを更新する口は、統計の更新（外れ値を除く更新と、外れ値の割合を含む）だけを行い、clip の割合は更新しない（D4）。RND の観測の正規化の clip の割合は、どこでも数えなくなる。この値は、今も診断値として外へ出していない。外れ値を除く更新を有効にした構成では、統計だけを更新する口の中に、同期の読み出しが残る（RND の既定は無効である）。
