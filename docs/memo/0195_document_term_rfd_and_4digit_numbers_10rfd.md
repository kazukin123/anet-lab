## 1. 目的と問題

### 1.1 問題

1. **名前が中身と食い違う。** 本来の PRD（Product Requirements Document）は、PM が製品について「何を・なぜ」を書く文書で、ユーザーストーリー・対象の利用者・優先度を中心に持ち、作り方は書かない。anet の文書は、1 回の変更ごとに番号を取り、問題・ゴール・前提・確定事項とその理由・外から見える契約（公開 API の名前・設定キー・メトリクス名・失敗の扱い）・受入を書く（P8、§5.6）。優先度と作業の順は課題が持つ（P7）。呼び名の由来の `to-prd` の雛形も、後半はすでに実装とテストの決定である（P9）。
2. **読み手が一般の PRD の像を持ち込みうる。** 初めて読む人や、新しく入る AI エージェントが「PRD」から製品の要求書の形（ユーザーストーリー、PM の文書）を推し、anet の文書の読み方・書き方を取り違えうる。
3. **用語集に注記しても、名前は残る。** 「PRD」は追跡しているファイル 963 本に 14,238 か所あり（P1）、skill 名・ファイル名・課題の欄・コミット件名・テストのタグのような、人が目にし機械が読む名前にも入っている（P2）。注記だけでは、名前を目にする場所ごとに取り違えの入口が残る。
4. **番号の形が 3 桁を前提にしている。** ファイル名の検査（[PRD 品質確認観点](../quality/rfd.md) の項番 2）、課題の `prd` 欄の検査、道具が件名から番号を読む形が、どれも 3 桁を前提にしていて、番号が 1000 に届くと止まる（[issue-20261116-fe09dc](../management/issues/issue-20261116-fe09dc.md)）。

### 1.2 ゴール

- **G1**: 中身に合う呼び名を 1 つ決め、今使っている場所（P2 のすべて）を新しい名前へ移しきる。
- **G2**: 過去の記録は書き換えない。そのうえで、旧い名前のままの記録から今の文書へたどれ、道具が切り替えの前後のコミットを数え漏らさず、定点統計の起票の月も変わらない。
- **G3**: 番号を 0 埋めの 4 桁にし、1000 を超えても、ファイル名・件名・道具の読み方を変えずに済むようにする。

### 1.3 非ゴール（退けた案と、本当の制約か）

| 非ゴール | 理由 | 本当の制約か |
|---|---|---|
| 文書の中身・工程（グリル、起草、実装計画、実装）・品質観点の項目の中身を変えること | 名前と番号の形だけを変える。中身を変える話は別の関心である | 制約ではない。別の PRD にできる |
| 過去の記録（コミット済みの ADR の本文、実験記録、Run のフォルダ、git の履歴、保管場所の文書の本文）を書き換えること | P4・P5。D19 の「残す」の行。改名したファイルを指すリンクの、丸括弧の中のパスだけを直す | 本当の制約である。git の履歴は書き換えられず、旧い名前は履歴に残り続ける。G1 の「移しきる」は、今使っている場所についていう |
| 番号の値を変えること（振り直し） | 値を変えると、コミット件名 270 件（§5.2）と ADR に書いた番号が、別の文書を指す。4 桁にするのは 0 を足すだけで、値は変えない（D8） | 本当の制約である（P4 による） |
| 文書の中に状態を持たせること（一般の RFD の形。§5.4） | 状態と順序は課題が持つ（P7、ADR 0069）。呼び名を RFD にしても、この形は変えない | 制約ではない。ADR 0069 を改める別の PRD にできる |
| リポジトリの外にある Matt Pocock 氏の skill（`to-prd`・`grill-with-docs` など）を変えること | 外の配布物で、anet の語ではない | 本当の制約である |

## 4. 用語

- **「PRD」**: 改める前の呼び名。本 PRD の中では、実装までは文書そのものも改める前の名前で呼ぶ。
- **RFD**: 改めたあとの呼び名（D1）。用語集の項目は実装で足す（D14）。
- **直下の文書・保管場所**: `docs/memo` の直下の文書と、`done/`・`frozen/`・`dropped/` の下の文書（P13）。
- **実装が済んだ文書**: 直下の文書のうち、その文書を `prd` 欄で指す課題がすべて解決か次版のもの（P7・P23）。
- **経緯の行**: 改めた経緯として旧い名前「PRD」を挙げる行で、同じ行に `RFD0195` を書いたもの（D22）。
- **改名と見分ける**: git がファイルを「消して足した」ではなく「名前を変えた」と見ること（P20）。
- **1 回目のコミット・2 回目のコミット**: D4 の分け方による 2 つのコミット（§9.6）。
- **これから書き出す先・今ある材料を指すパス**: `.scratch/` の下を指すパスのうち、新しく出力を書く先と、手元に今ある出力や実行体を読む先（D5）。
- **側面 A〜F**: 今の文書の実態の 6 つの見方（§5.6）。
- 道具の出力の鍵 `rfd_count` と関数 `rfd_state` の count・state は、文書の本数と文書の状態を指す。用語集の「学習側 counts」や Env の状態とは別のもので、今の `prd_count`・`prd_state` の名前を写しただけである。

- 「spec」の意味は道具ごとに違う。Spec Kit と Kiro では 1 つの機能の要求（何を・なぜ）で、作り方は別の文書に分ける。OpenSpec では今の仕様そのものを指し、1 回の変更は change と呼ぶ。
- 1 回の変更ごとに番号を取り、決めてから実装する文書の呼び名は、Rust・Python・Kubernetes・Go・Swift のどれも「提案（proposal）」の系統（RFC、Enhancement Proposal、proposal、design doc）である。ゴール・非ゴール・設計の詳細・テスト計画・代わりの案を 1 本に持つ点で、anet の文書（P8）に最も近いのは KEP である。
- Python は、決着した提案を過去の記録とし、今の仕様を別の文書に置く。anet の、実装のあとの今の仕様を設計文書と src が持つ形（P11・P13）と同じ分け方である。
- 一般の RFD と anet の文書を、§5.6 の側面ごとに比べると、変更の識別子（D）・時期（E）は近く（話題ごとの連番、番号の取り合いの扱い、下書きから議論して決める段の並び）、扱う範囲（F）も近い（Oxide は手順や統治にも使い、Joyent は機能の要望を別の文書に分ける）。判断の記録（C）と差分の仕様（A）は向きが同じで、anet のほうが形式が厳しい。遠いのは、AI がそのまま実装する指示（B。受入・作業の順序・移行の一覧）、状態の置き場（一般の RFD は文書の中、anet は課題）、実装したあとの今の仕様の置き場（Oxide は実装済みの RFD、anet は設計文書と src）である。

### 9.1 設定と失敗の扱い

道具と検査が受け付ける入力の形は次のとおりである（D10〜D13・D17）。

件名からは、次の 2 か所にある番号の記号をすべて読み、読んだ番号を合わせて 1 つの集まりにする（今の `subject_prd_numbers` と同じく、両方から読む。D17）。「番号の記号」は、`RFD` に続く 4 桁の数字か、`PRD` に続く 3 桁の数字で、どちらもその数字のすぐ後ろに数字が続かないものをいう。

- 件名の末尾の参照の並び（今の形）
- 過去の形の scope

- 読んだ番号は値で扱い、4 桁の番号として文書に当てる（`PRD195` も `RFD0195` も 195）。2 か所のどちらにも番号の記号が無い件名からは番号を読まない（今と同じ）。例として、`fix(PRD918): … RFD0195` からは 918 と 195 の両方を読む。
- `RFD195`（3 桁）や `PRD0195`（旧い記号で 4 桁）は番号の記号に当たらないので読まない。旧い記号を見張らないので（D9）、知らせもしない。
- 読んだ番号を文書に当てる手順は今と同じである。番号ごとに振り直しの行を先に見て、コミットの日がその行の日付以前（その日を含む）なら、その行を持つ今の文書に当てる（ADR 0077 のまま）。何度も振り直した文書（例 `999 → 901 → 132`）でも、行の途中の番号（901）の文書ではなく、行を持つ今の文書（132）に当てる。当たらなければ、ファイル名の番号（`NNNN_*_10rfd.md`）で探す。振り直しの行の旧い番号と新しい番号は、形（3 桁か 4 桁か）によらず値で比べ、同じ文書の行どうしのつなぎも値で確かめる。振り直しの行で当たる文書があれば、それだけを候補にし（ファイル名の番号では探さない）、無ければファイル名の番号で探す。こうして得た候補が 2 本以上か 0 本なら、どれにも当てず、解決できない番号にする（今と同じ順と扱い。旧い番号 999 を 2 本以上の文書が振り直しの行に持つ場合など）。

### 9.6 コミットの分け方（D4）

コミットは人間が行い、`anet-prepare-commit` が 2 回に分けて提案する。

| コミット | 入れるもの |
|---|---|
| 1 回目 | (1) すべての改名（文書・実装計画・検証記録・`docs/memo` のほかの番号つきのファイル・skill のディレクトリとファイル・品質観点・検証資材のフォルダとファイル・`prd101_muzero_test.cpp`・`config_resolver_prd072.json`）。(2) 改名したファイルを指す、どのファイルの中のリンクの丸括弧の中のパスと Obsidian のリンクの名前の直し（改名したファイルの中のものも含む）。(3) 改名しないファイルの変更（道具、src・apps のコード・テスト・タグ・識別子・環境変数・bat、AGENTS.md・CONTEXT.md・README.md・registry・memo README・課題の README・wiki の手で書く節・設計文書・CHANGELOG、課題の前付け・題・scope）。ただし、改名したファイルの見出しを指す `#` の直しは、D26 のとおり 2 回目に入れる。(4) 改名したファイルのうち、動作に効く中身の直し。道具のテスト（`wiki_test.py`・`issues_test.py`）の断定、検証資材のスクリプトと README の環境変数の名前とパスの文字列、改名したテストのファイルのタグとテスト名、skill の前付けの名前と、skill の本文が名指すほかの skill・品質観点のパス、品質観点（`docs/quality/rfd.md`）の項番 2・3 の形。(5) コミットの準備が `maps` で作り直した生成物（D20） |
| 2 回目 | (1) 改名したファイルの残りの本文の語の置き換え（直下の文書、skill、品質観点、検証資材の README とスクリプトの説明）。(2) コミットの準備が `maps` で作り直した生成物（課題の一覧、wiki の生成の節。D20）。(3) wiki の取り込みの記録（D23）。(4) 改名したファイルの見出しを指す `#` の直し（改名しないファイルの中のものも含む。D26） |

- 1 回目をステージしたら、`git diff --cached -M --name-status` で、改名したファイルがすべて `R` であること（同じファイルが `D` と `A` に分かれていないこと）を確かめる（受入 A11）。(4) の直しで `R` にならないファイルが出たら、そのファイルの (4) の直しを、動作に要る最小の行まで減らしてから確かめ直す。それでも `R` にならないときは、実装を止めて開発者に扱いを聞く。
