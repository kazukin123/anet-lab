# リファクタリング観点

リファクタリングの候補を選ぶときに走査する観点。

## 位置づけ

| 項目 | 内容 |
| --- | --- |
| 対象 | コードのリファクタリング候補。挙動を変えない変更に限る |
| 参照するエージェント | `anet-audit` の refactor 観点。本書を基準に読み、観点名を issue の分類に使う。人がリファクタリングの計画を立てるときも読む |
| 対象外 | 挙動が変わる修正。既知の不具合は defect として別に扱う。機械の検査へ回す書き方と、ソースの配置も候補にしない（「候補にしないもの」） |

- 観点は排他の分類ではなくタグである。扱い方は「運用ルール」による。
- 本書は成果物のレビューには使わない。レビューの観点は [impl.md](impl.md) と [prd.md](prd.md) が持つ。
- 「観点」の表の「重み」は、観点どうしの重みの区分である。`anet-audit` が起票する課題の `priority`（開発者のメモ）には写さず、`value`・`risk` の見立ての材料にする（[anet-create-issue](../../.agents/skills/anet-create-issue/SKILL.md) の「監理の項目」）。

## 価値と層

候補は、次の 3 つの価値のどれかを良くするものである。3 つは同列に扱う。

| 価値 | 意味 |
| --- | --- |
| スマートさ | 同じことを、より少ない概念・より少ない特例・より短い経路で実現している |
| 可読性 | 読んだ印象と実際の挙動が一致し、上から順に読んで追える |
| 過不足の少なさ | 目的に要らないものが無く、要るものが欠けていない |

実行時の性能に効く箇所では、3 つの価値より性能を優先する（「ガードレール」）。

観点は 2 つの層に分ける。

- 構造: 機構・クラス・関数の切り方と関係。
- 記述: 1 つの関数の中の書き方のうち、読んで判断するもの。機械で判定できる書き方は「候補にしないもの」による。

## 観点

### 構造

| 観点 | 価値 | 重み | 内容 |
| --- | --- | --- | --- |
| 重複の生成源（抽象の欠落） | スマートさ | 高 | 種別（イベント・型・モードなど）を 1 つ足すと、同じ形のクラス・メソッド・分岐を複数の場所へ足すことになる構造。放置すると増え続けるため、既存の重複より優先する（例: MetricsLogObserver 系の On* アダプタ増殖） |
| 既存の重複 | スマートさ | 高 | 種別の軸を持たない写し。既定値・処理の骨格・検証・状態が別々の場所にあり、片方を直すともう片方も直す。既に食い違っていれば、その食い違いも書く |
| 特例で支える汎用機構 | スマートさ | 高 | 汎用の層にある、特定の名前・型・モードで分ける分岐、動作を切り替える bool の引数、型の判定 |
| 仕事をしていない層 | スマートさ | 中 | 引数を渡すだけのラッパ、Set/Clear の対、決定のあとから知らせる通知や hook |
| 可読性（直観との不一致） | 可読性 | 高 | 読んだ印象と実際の挙動・役割が一致しない（名前が役割を偽っている、抽象度の違うものに似た名前が付いている等） |
| 1 関心 1 機構違反 | 可読性 | 高 | 1 つのクラス・関数に複数の関心が同居している。全体の進行を書く関数に、細部の計算・解析・文字列の組み立てが並ぶ |
| 肥大化 | 可読性 | 高 | 1 クラス／1 関数が大きすぎて、全体を把握しないと安全に変更できない（行数だけでなく分岐・状態の多さも見る） |
| 暗黙の前提（所有・寿命・スレッド境界・順序） | 可読性 | 高 | 生ポインタ保持、singleton の寿命、無ロック共有、呼ぶ順番の決まり、複数の bool やメンバの組で表した状態が、型や名前から読めない。同型のバグを生み続ける構造（例: VideoLogger UAF、Notifier Attach 競合） |
| 変更の波及と依存 | 可読性 | 中 | 1 つの仕様変更のために複数のファイル／クラスを同時に触る必要がある（shotgun surgery）。モジュール間の循環参照、レイヤ違反 |
| 不要コード | 過不足の少なさ | 高 | 呼ばれない関数・クラス、読まれないメンバ・設定、到達しない分岐 |
| 互換・移行の名残 | 過不足の少なさ | 中 | 旧い名前・旧い形式のための分岐、別名、読み替え、旧い設定キーのための警告。同じ意味の語を 2 つ受け付ける箇所は、新旧が分からなくても事実として拾う |
| 先回りの抽象 | 過不足の少なさ | 中 | 実装が 1 つしか無い interface、いつも同じ値が渡る引数・設定、使われていない拡張点 |
| 重ねて持つ状態・検証 | 過不足の少なさ | 中 | ほかの値から導ける値を別に持つ。同じ検証を 2 つの層で行う |
| 型に無い制約 | 過不足の少なさ | 中 | 種別や状態を、文字列・bool・-1 などの特別な値で表している |
| 共通処理の置き場違い | 過不足の少なさ | 中 | ある型・仕組みの検証や変換を、それを使う側が個別に書いている |
| 設定に出すべき値の埋め込み | 過不足の少なさ | 中 | 実験ごとに変える値が、コードに埋まっている |
| テスト容易性 | 過不足の少なさ | 中 | singleton／GUI／CUDA 直結で seam がなく、単体テストが書けない |

### 記述

| 観点 | 価値 | 重み | 内容 |
| --- | --- | --- | --- |
| 分岐で書いた対応表 | スマートさ | 中 | 文字列や enum の比較が縦に並ぶ if 連鎖・switch で、表やデータ 1 つで書けるもの |
| 局所の繰り返し | スマートさ | 中 | 同じ式・同じ数行が、関数の中や隣り合う関数に繰り返し現れる |
| 遠回りな値の受け渡し | スマートさ | 中 | 多くの引数にばらして持ち回る、宣言してから離れた所で代入する、出力引数で返す、使い捨ての一時変数が連なる |
| 込み入った制御 | 可読性 | 中 | 意味を読み解かないと分からない長い条件、状態を追わないと読めないループや分岐の組み立て |
| 命名 | 可読性 | 中 | クラス／メソッド／変数の名前が役割・抽象度を表していない（tag／name の使い分け等、既存規約とのズレを含む）。意味の取れない略語や汎用名、1 つの変数を別の意味で使い回す |
| コメントの過不足 | 過不足の少なさ | 低 | コードをなぞるだけのコメント、今のコードと合わない古いコメント。コードで表現できない制約（契約・単位・不変条件、順序や性能の理由）の説明が無い。「読めないからコメントが欲しい」は命名・構造の問題として上位の観点で扱う |

## 候補にしないもの

| 種類 | 内容 | 扱い |
| --- | --- | --- |
| 機械の検査へ回す書き方 | 体裁（インデント、行の長さ、折り方）、未使用の include・変数・引数、不要な `this->`・cast・`else`、コメントアウトされたコード、`const`・`override`・`explicit`・`[[nodiscard]]`・指示付き初期化の欠落、添字のループや `.first`／`.second` などの定型の書き換え、bool の式の簡約、入れ子の三項演算子、冗長な cast、長い型名、数値・文字列の直書き、機械で判る実装規約とのズレ | 個別には挙げない。検査の仕組みは [issue-20261110-9d4e5a](../management/issues/issue-20261110-9d4e5a.md) が扱う。検査で覆えないと分かった分は、観点へ戻す |
| ソースの配置 | ファイルの分け方、どのファイルに置くか、公開ヘッダと内部ヘッダの境界 | 新しい候補にせず、配置を扱う課題へ追記する |
| 挙動が変わる直し | 不具合の疑い。1 つの関数の中で不正な入力の扱い（WARN して続行、ERROR を出して飛ばす、例外）が混ざる箇所 | 候補にせず、気づいた事実を別に記録する。既知の不具合はバグトラックで別に管理する |
| 性能のための形 | 「ガードレール」の性能の区分が「性能のための形」のもの | 候補にしない。理由がコードから読めなければ「コメントの過不足」として拾う |

## 運用ルール

- 観点は排他の分類ではなくタグ。複数に当たった候補は、最も根本の観点で対処方針を決め、他は付随する症状として自動解消を狙う。
- 種別の軸で増えるものは「重複の生成源」、軸を持たない写しは「既存の重複」とする。呼ばれない・読まれないものは「不要コード」、書かれない・いつも同じ値のものは「先回りの抽象」とする。
- 「挙動を変えない」には、ログの文言と WARN の出る回数を含める。文言や回数が変わる直しは、候補から外すか、変わることを候補に書く。
- 「呼ばれない」「実装が 1 つしか無い」「ここでしか使っていない」は、構築する箇所と呼び出す箇所を検索して確かめ、検索語と件数を書く。
- 候補ごとに、その箇所を名指しで構築・呼び出すテストがあるかを書く。
- ホットスポット補正: 変更頻度の高いファイル内の指摘は、起票する課題の `urgency` を 1 段上げ、今後触る予定のない場所は 1 段下げる。幅と端の扱いは [anet-create-issue](../../.agents/skills/anet-create-issue/SKILL.md) の「anet での当てはめ」による。

## ガードレール（実施時の条件）

- 候補ごとに、次の性能の区分を付ける。呼ばれる頻度は、呼び出し元のコードで確かめる（間隔で間引かれているか、毎 step か、起動時だけか）。

  | 性能の区分 | 意味 | 扱い |
  | --- | --- | --- |
  | 関わらない | 起動時・設定の読み込み・構築、低頻度の処理 | 3 つの価値で判断する |
  | 中立 | hot path（Sample／Push／Learn、per-step 経路）だが、直しても速さは変わらない見込み | 候補にする。perf-neutral であることをブレ幅基準で確認する |
  | 軽くなる | hot path で、直すと処理が減る見込み | 候補にする。確認は「中立」と同じ |
  | 性能のための形 | バッファの使い回し、導ける値のキャッシュ、確保や仮想呼び出しを避けた手書きなど | 候補にしない（「候補にしないもの」） |
  | 判定できない | 性能のためかどうかがコードから読めない | 候補に残し、何が分かれば判定できるかを書く |

- RNG の呼び出し順・コンテナの走査順・並列化に触る場合は、同 seed の再現性チェックを必須にする。
- テストが無い箇所は、特性テストの追加を先行ステップとして計上する。
