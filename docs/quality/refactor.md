# リファクタリング観点

リファクタリングの候補を選ぶときに走査する観点。

## 位置づけ

| 項目 | 内容 |
| --- | --- |
| 対象 | コードのリファクタリング候補。挙動を変えない変更に限る |
| 参照するエージェント | `anet-audit` の refactor 観点。本書を基準に読み、観点名を台帳の分類タグに使う。人がリファクタリングの計画を立てるときも読む |
| 対象外 | 挙動が変わる修正。既知の不具合は defect として別に扱う |

- 観点は排他の分類ではなくタグである。扱い方は「運用ルール」による。
- 本書は成果物のレビューには使わない。レビューの観点は [impl.md](impl.md) と [prd.md](prd.md) が持つ。

## 観点

### 優先度: 高

| 観点 | 内容 |
| --- | --- |
| 可読性（直観との不一致） | 読んだ印象と実際の挙動・役割が一致しない（抽象度の違うものが並列に並ぶ、名前が役割を偽っている等） |
| 1 関心 1 機構違反 | 1 つのクラス／機構に複数の関心が同居している、または 1 つの関心が複数の機構に分散している |
| 重複の生成源（抽象の欠落） | 型・イベント種別ごとに同型のボイラープレート／アダプタ／分岐を書かされる構造。放置すると増え続けるため、既存の重複より優先する（例: MetricsLogObserver 系の On* アダプタ増殖） |
| 既存の重複・不要コード | コピペ重複、死にコード、死に設定。共通化（基底クラス／ユーティリティ化）または削除 |
| 肥大化 | 1 クラス／1 メソッドが大きすぎて、全体を把握しないと安全に変更できない（行数だけでなく分岐・状態の多さも見る） |
| 所有権・寿命・スレッド境界の暗黙さ | 生ポインタ保持、singleton の寿命、無ロック共有など、同型のバグを生み続ける構造（例: VideoLogger UAF、Notifier Attach 競合） |

### 優先度: 中

| 観点 | 内容 |
| --- | --- |
| 命名 | クラス／メソッド／変数／名前空間の名前が役割・抽象度を表していない（tag／name の使い分け等、既存規約とのズレを含む） |
| 変更の波及（shotgun surgery） | 1 つの仕様変更のために複数のファイル／クラスを同時に触る必要がある |
| 依存関係の複雑さ | モジュール間の循環参照、レイヤ違反、不要な include |
| 規約違反・不統一 | 実装規約（`LOG::warn`、無名 namespace 回避、配置規約など）とのズレ |
| 過度なハードコーディング | マジックナンバー／文字列、設定に出すべき値の埋め込み |
| テスト容易性 | singleton／GUI／CUDA 直結で seam がなく、単体テストが書けない |

### 優先度: 低

| 観点 | 内容 |
| --- | --- |
| コメント不足 | コードで表現できない制約（契約・単位・不変条件）の説明に限る。「読めないからコメントが欲しい」は命名・構造の問題として上位の観点で扱う |

## 運用ルール

- 観点は排他の分類ではなくタグ。複数に当たった候補は、最も根本の観点で対処方針を決め、他は付随する症状として自動解消を狙う。
- ホットスポット補正: 変更頻度の高いファイル内の指摘は優先度を 1 段上げ、今後触る予定のない場所は 1 段下げる。
- 挙動が変わる修正はリファクタリング候補に入れない（既知の不具合はバグトラックで別に管理する）。

## ガードレール（実施時の条件）

- hot path（Sample／Push／Learn、per-step 経路）に触る場合は、perf-neutral であることをブレ幅基準で確認する。
- RNG の呼び出し順・コンテナの走査順・並列化に触る場合は、同 seed の再現性チェックを必須にする。
- テストが無い箇所は、特性テストの追加を先行ステップとして計上する。
