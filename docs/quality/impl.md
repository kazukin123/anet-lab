### 名前

**規約**

**名前の付け方**

設定キー、メトリクスの tag、クラス・関数・メンバ・引数、層（block）、プロファイルの名前は、次に従って付ける。PRD で付ける名前も同じである。

1. 設定の階層は、その値を読む持ち主（Agent・Learner・Head・Actor・Env などの概念）に合わせて入れ子にする（`head.init.*`、`spatial.epsilon.*`）。同じ部品の役割の違いは、葉の名前ではなく役割の階層で表す（`learner.current.nn_forward_key` と `learner.target.nn_forward_key`）。
2. 1 つの名前に 2 つの意味を持たせない（時間の両端は `start`／`end`、ラダーの両端は `first`／`last`）。ほかの意味で使っている語は避け、既存の表記に揃える（Munchausen の α・`per_alpha` と紛れる `alpha` ではなく `learning_rate`）。
3. 同じものは既存の語と形に揃える（`q`／`q_dist` に対して `skip_q`／`skip_q_dist`。参照キーは `<thing>_key`）。論文の語は、比べる軸が合うときだけ使い、合わなければ軸の合う一般の語にする（`action_out`／`action_in`）。
4. モードや選択のキーは、何のモードかが分かる名にし、上の階層の名・値の語・ほかのキーとぶつけない（`skip.network_mode`。`skip.mode` は何のモードかを言わず、`net_mode` は root の `net` と紛れる）。
5. 形が 1 つしか無いものに、列挙の値を持つキーを作らない。2 つ目が要るときに足す（`head.use_dueling` は bool）。
6. 層の名は、幅ではなく層の順で付ける（`SkipFC1`。幅は `linear.out_features` で上書きする）。
7. 構造体のメンバと引数は、型と役割が名前から読めるようにし、ある時点でしか成り立たない名を避ける（`network` ではなく `network_config`。返す時点でしか実行済みでない `executed` ではなく `actions`）。
8. 説明に使う記号（`z`）は記号であることを書き、設定キーや公開名（`skip_context`）と取り違えないようにする。
9. 名前を変えるときは、変える理由（多義の解消、既存の表記への揃えなど）を、PRD・実装計画・依頼のどれかに書く。

用語集との照合は [AGENTS.md](../../AGENTS.md) §用語(CONTEXT.md)を引く条件、クラス名の接尾辞と動詞、名前つきの定数、汎用層の名前は本書「C++ コード」の規約による。

### 設定ファイル

**規約**

**設定ファイルの代入演算子**

運用は、**共通ファイルのベース定義は`?=`、環境別ファイルはデフォルト設定だけ`?=`、それ以外は原則`=`**とする。選択宣言`.$`・Runプロファイル・CLIは常に`=`。既存の実効値を保つために`?=`が必要な葉だけ、理由を添えてデフォルト設定へまとめる。

この運用は設定編集・監査の規約であり、resolverの名前・位置による特別扱いではない。人向けの説明、ファイル別の一覧、DropMerge・Atariの例は[Run実行ユーザーガイド](../design/020_user_guide_run.jp.md)の§3.6・§3.7を参照する。設定変更時は`check_default_leaves.py`と全キー・文字列値の比較で意図しない変化がないことを確認し（手順は[core/anet-core/testdata/prd072/README.md](../../core/anet-core/testdata/prd072/README.md)）、あわせて `core\anet-core\bin\Debug\anet-core-test.exe "[shipped_config]"` で出荷設定の検査を通す（規約は本書「テスト」）。

**設定ファイルのプロファイル境界**

設定ファイルで左辺にプロファイル（`@name`）を含む行は、**プロファイルの境界を`:`で区切り、`.`で続けない**。`:`は`.`と同じ意味で、どこまでがプロファイルかを読み取りやすくするために使う。

- NG: `DefaultDQNAgent.@baseline.head.projection.noisy.enabled ?= false`
- OK: `DefaultDQNAgent.@baseline : head.projection.noisy.enabled ?= false`

**metrics の tag の文字数**

`metrics.scalar.[tag]` の tag は、**群名と `/` を含めて 40 文字以内**にする。Metrics Viewer の Tags 一覧で見切れるため。超えそうなら群名ではなく名前側を縮める。

**並び順を番号で決める設定**

並び順を番号で決める設定（Evaluation Trace の列 `app.eval_trace_panel.columns.[N]` など）は、**分類ごとに桁を分け、差し込む空きを残して振る**。十の位で分類の中の順を決め、一の位は 0 にして空けておく。添字で並ぶ列だけ一の位を使う。Trace の列の分類と番号は、[Run実行ユーザーガイド](../design/020_user_guide_run.jp.md)の§6.5の表に従う。詰めて振ると、あとから差し込むたびに全ファイルの番号を振り直すことになるため。

**新しい機能の設定の足し方**

新しい機能の設定は、Agent の設定ファイル（`agent.txt`）の `@baseline` に、無効の既定と、おすすめの配線・値を `?=` で書く。有効化は `skip.enabled = true` のような葉 1 つで済むようにし、env 固有の値（スキップ長の上限 J など）は env の既定（`?=`）に置く。変種は env・CLI・bat の葉で指定する。`@` プロファイルは、分布表現の切り替え（`@iqn`）のような本当に別の束にだけ作り、機能ごとの変種のために作らない。metrics の群は、env の `run.@<機能>` がカタログのプロファイルを連鎖に足す。プロファイルが増えるほど、Run で何が効いているかを追えなくなるため。

**Run プロファイルの metrics の連鎖**

Run プロファイル（`run.@name`）で `metrics.scalar.$` を書くと、先に重ねたプロファイルの連鎖は消え、後ろのプロファイルの連鎖だけが残る。**丸ごと書くときは、そのプロファイルと重ねて使うプロファイルの群を落とさない**（例: `run.@munch > run.@skip` と重ねる `run.@skip` は `metrics.scalar.@munchausen` を含める）。重ねて使うプロファイルは、リポジトリに書かれた組み合わせ（既定の `run.$` とコメントにした `run.$` の例、番号付きの bat、文書の例）から決める。

### C++ コード

**規約**

C++ コードは Google C++ スタイルガイドを前提とします。
ただし、既存コードに明確なローカル規約がある場合は、無理に一括変更せず、周辺コードとの一貫性を優先してください。

個別の指示・合意が無い限りにおいて、以下を意識してください。

- C++20 を前提とする。
- ANET では、原則として 1 クラス 1 ファイルではなく、機能グループ単位で `.hpp` / `.cpp` を作る。
  例: `dqn_based_agent.*` は DQN 系の Policy、Actor、Learner をまとめ、`nn_modules.*` は NN module 群をまとめ、`observers.*` は Observer 群をまとめる。
- 新しいクラスを追加する場合も、まず既存の機能グループに属するかを確認し、独立したサブシステムとして分ける理由がある場合だけ新規ファイルを作る。
- ヘッダオンリーで実装が完結する `.hpp` を新設する場合も、同じ機能グループ名の `.cpp` を作り、その `.cpp` では当該ヘッダの include だけを行う。
  例: `foo.hpp` を追加する場合は `foo.cpp` も追加し、公開ヘッダなら `#include "anet/foo.hpp"`、内部ヘッダなら周辺コードと同じ include 形式で当該ヘッダだけを include する。
- C++20 の指示付き初期化（Designated Initializers）は原則使用し、可読性が極端に低下する場合のみ通常のコンストラクタ呼び出しや段階的な代入を優先する。
- include は必要最小限にする。
- include は、その `.cpp` 自身のヘッダ → 標準ライブラリ → ミドルウェア（libtorch・wxWidgets・ALE など外部依存）→ anet 系の順に書く。anet 系（`anet/…` の公開ヘッダと、`nn_heads.hpp` のような内部ヘッダ）の中は、依存の少ない基礎のヘッダ（`anet/profile.hpp`・`anet/log.hpp` など）を先に、それに依存する上位のヘッダを後に書く。テスト（`*_test.cpp`）は、自身のヘッダの位置に `anet/catch_test.hpp` を置く。既存ファイルの include を、この規約だけを理由に一括で並べ替えない。
  例:
  ```cpp
  #include "dqn_based_heads.hpp"
  #include <array>
  #include <cmath>
  #include <string>
  #include <utility>
  #include "anet/profile.hpp"
  #include "nn_heads.hpp"
  ```
- C++ の `.hpp` 側では `using namespace` を使用しない。
- C++ の `.cpp` 側では、`namespace ... {}` で全体を囲むのではなく `using namespace ...;` を使用。
- 同じ名前空間で省略可能な名前空間修飾は省略する。
- `const` を適切かつ積極的に使う。
- 生ポインタ `T*` は所有しない借用を表す。所有は `std::unique_ptr` / `std::shared_ptr` で表す（フレームワークが所有を規定する場合は下記）。
- 引数は、必須なら `T&`、省略可なら `T* = nullptr`。値が小さく複製が安い省略可の入力は `std::optional<T>` で受ける。借用に `std::optional<std::reference_wrapper<T>>` は使わない。
- 借用をメンバに保持してよいのは、所有者が借り手も所有している場合（Agent 所有の Resource をモジュールが借りる等）と、同期呼び出しの間だけ生きる値型が運ぶ場合に限る。どちらも「誰の所有を借りるか」をメンバの行末コメントに書く。参照メンバも同じ。
- 生涯固定の依存はコンストラクタで受けて保持し、呼び出しごとに変わる入力は引数で渡す。途中で差し替える Set/Clear の対は作らない。Resource が特定モジュールの State を指すことは禁止する。
- wxWidgets の親子所有、`wxLog::SetActiveTarget` の target 移譲、`wxProcess` の終了通知と delete の規約、C API のハンドル（`FILE*`）は、その API の所有規約に従う。コメントは不要。
- `dynamic_cast` はテストコード内に限定し、production code では使用しない。型ごとの分岐が必要な場合は、仮想関数、明示的な interface、既存 API の拡張、または型情報を持つデータ構造で表現する。`dynamic_cast` を避けるために取り出し口（`GetXxxSource`・`AsXxx` など）を足す前に、基底の型がその interface を持つべきかを見る。
- UI スレッド（GUI のイベントとタイマー）から、学習スレッドが更新の間ずっと持つロックを取らない。学習側の可変状態は、学習スレッドで作った写しか、atomic に公開した値を通して読む。
- クラス名は、作る側・結果・読み口などの役割を、接尾辞（Provider・Builder・Reader・Result など）で示す。既存のコードで使われている動詞（Create・Capture・On など）は、既存と同じ意味で使う。
- 外で使わない補助のクラスは、持ち主のクラスの内側（private な入れ子）か、.cpp の無名名前空間に置き、公開ヘッダの名前空間で宣言しない。
- 設定の固定キーは `ANET_READ_CONFIG(config_data, head.init.trunc_b)` の形で読み、設定 DTO のメンバのパスを設定キーと一致させる。`ReadConfig(config_data, "head.init.trunc_b", head_init.trunc_b)` のように、文字列のキーと名前の違うメンバを対応付けない。一致させるために、必要なら DTO に入れ子の struct を設ける。`ReadConfig` を直接使ってよいのは、キーが実行時に決まる場合（`actor.[<key>]` のような添字付きのキー）と、読んだ値を別の型へ変換して持つ場合（文字列を enum へ変換する `skip.network_mode` など）に限る。
- 次のリテラルは、名前つきの定数（`kXxx`）にして使う。
  - 同じ値を 2 か所以上で使うもの（書き込みと読み込み、比較と診断のメッセージなど）。
  - 外と取り決める識別子。使うのが 1 か所でも定数にする。保存データ・ファイル形式の識別子と版、TensorDict キー、メトリクスと GetScalar の鍵、ファイル名、環境変数、コマンドライン引数が当たる。

  設定キー（`ANET_READ_CONFIG` のメンバのパスで表す）とログ・エラーメッセージの文言は定数にしない。設定の列挙値（`"online"` などの文字列の選択肢）とテストの期待値は、1 か所でしか使わないなら直書きでよい。診断のメッセージに識別子を出すときは、その定数から組み立てる。定数は、使う範囲が収まる一番狭い場所に置く（ファイルの中だけなら `.cpp`、外からも使うなら持ち主のクラスのメンバ）。

  値の名前は、保存形式の版なら、機能名と機能内の版を混ぜず、その型全体の版で表すのが望ましい（例: `DefaultDQNAgent/skip-v1` ではなく `DefaultDQNAgent-2`）。

### 計測

**規約**

性能測定が必要な処理には `ANET_PROFILE_SCOPE` 系のマクロを入れ、後から実測できる状態を保ってください。

特に以下の処理を追加・変更する場合は、計測範囲を入れることを優先してください。

- 学習・評価・実行ループから頻繁に呼ばれる処理。
- `Step`、`Reset`、`MakeAction`、`UpdateFromBatch`、`Forward`、`Sample`、`Push` など、実行時間の主要因になりやすい境界。
- batch size、env 数、action 数、node 数、画像サイズ、ログ量などに応じて処理量が増える処理。
- Tensor 変換、device 転送、同期、queue 処理、ReplayBuffer、NN forward、loss 計算、可視化、画像・動画・GraphViz 出力など、CPU/GPU/I/O の負荷が読みにくい処理。
- 既存の計測済み処理を分割・共通化する場合の、分割後の主要フェーズ。

計測名は既存コードに合わせて `ClassName::FunctionName` または `ClassName::FunctionName.phase` のように安定した名前にしてください。
細かすぎる getter、単純な分岐、軽量な per-element 内側ループには原則として入れず、測定のノイズにならない意味のある処理境界を選んでください。
計測用のブロックを作ってスコープを不自然に狭めないでください。
フェーズ全体を測る場合は、原則として `ANET_PROFILE_SCOPE(phase)` を対象フェーズの先頭に置き、そのフェーズで使うローカル変数の構築・初期化も測定対象に含めてください。
測定対象から意図的に外したい重い初期化がある場合だけ、別スコープへ分けてください。
連続フェーズを測る場合は、同じ可視 lifetime 内で `ANET_PROFILE_SCOPE_NEXT(phase)` または `ANET_PROFILE_SCOPE_NEXT_FROM(phase, prev_phase)` を使ってください。

`ANET_PROFILE_SCOPE_FULL(var_name, full_name_literal)` は例外用途です。
lambda / callback / timer / async worker / prefetch など、自動生成される `ClassName::FunctionName.phase` が profiler 上の論理処理名として不適切な場合、または既存の計測名を維持して before/after 比較を可能にしたい場合だけ使ってください。
`full_name_literal` は `ClassName::FunctionName.phase` またはそれに準じる stable な完全名にしてください。
通常のメンバ関数・自由関数内のフェーズ計測では `ANET_PROFILE_SCOPE(phase)` を優先し、単に任意の名前を付けたいという理由では `ANET_PROFILE_SCOPE_FULL` を使わないでください。

推奨:

```cpp
ANET_PROFILE_SCOPE(sample);
ExperienceSamples cpu_samples;
inner_->Sample(cpu_samples, minibatch_size, beta);
```

避ける例:

```cpp
ExperienceSamples cpu_samples;
{
    ANET_PROFILE_SCOPE(sample);
    inner_->Sample(cpu_samples, minibatch_size, beta);
}
```

毎 step・毎 tick・毎回の学習の更新に通る経路に、別のスレッドのロック待ち、レイアウトや表示全体の組み直し、device 間の同期の転送を足さない。同期の転送には、次の書き方が当たる。

- GPU のテンソルを CPU へ読み戻す `.item()`・`.cpu()`・`.to(torch::kCPU)` と、要素ごとの読み出し（lane ごとの `x[b].item()` など）。`.to(torch::kCPU)` は `non_blocking=true` を付けても当たる。CPU で値を使う前に転送の完了を待つ必要があるためで、同期を避けて読み戻せるのは、既存の非同期の読み戻し（`anet::transfer::HostReadback`）に載せ、載せてから `Wait()` までのあいだに後続の処理を進めるときだけである。載せた直後に、あいだに何も挟まずに `Wait()` して値を使うのは、`.cpu()` と同じく同期の転送に当たる。
- CPU のテンソルを CUDA へ送る `.to()`。ただし、pinned のテンソルを `non_blocking=true` で送るものは非同期なので当たらない。pinned でないテンソルからは、`non_blocking=true` でも同期の転送になる。

lane や行などの要素を回すループの中には、見積もりがあっても同期の転送を置かない。要るときは、ループの前で 1 回にまとめる。まとめたあとも経路に同期の転送が 1 回残るなら、それも「足す」に当たる。同期の転送を避けるには、pinned のテンソルを `non_blocking=true` で送るか、`HostReadback` に載せて後続の処理を進めてから `Wait()` する。要素のループの外に同期の転送を足すときは、頻度×1 回あたりの時間の見積もりを実装計画に書く。

適用: 所在の節が挙げる種類の処理を足した、変えた、または分割した実装。

### GetScalar

**規約**

`GetScalar()` の `std::optional<float>` は、key の認識可否と値の成立可否を分けて扱ってください。

- 指定された key が未知、または委譲先でも処理できない場合だけ `std::nullopt` を返す。
- 指定された key が既知だが、現在の状態、タイミング、設定、入力不足により値を出力できない場合は `std::numeric_limits<float>::quiet_NaN()` を返す。
- 未初期化 EMA、episode 未確定、PER 無効、batch 不足、非対応条件などは、既知 key なら `NaN` とし、0、前回値、既定値に偽装しない。
- wrapper / aggregator は `std::nullopt` を未知 key、`NaN` を値未成立として扱う。

適用: `GetScalar()` を足した、または変えた実装。

| 項番 | 確認観点 | 確認内容 | 規約の所在 |

### 所有権

**規約**

Agent 関連の変数・オブジェクト追加時は、必ず以下の資料に従ってください。

- [docs/ownership_guideline.md](../ownership_guideline.md)

要点:

- State は、それを更新するモジュールが所有する。
- Resource は Agent が所有する。

- policy net、target net、optimizer、ReplayBuffer、RNG、Config などは Agent 所有の Resource。

### ログ

**規約**

実装内のログ出力は、ユーザーから個別に指定がない限り基本英語で書いてください。

### テスト

**規約**

**本番の設定ファイルを読むテスト**

設定の仕組み（resolver、Config のコンストラクタ、metrics の解析）は、testdata か合成の設定で確かめる。`apps/runner/config` 配下のファイルを読むテストは仕組みのテストではなく、出荷している設定の検査であり、固定してよいのは次の 2 つだけにする。

- 共通層（`_main.txt` が include するファイル）の、PRD が既定と宣言した葉の解決値。
- 実行時に黙って通る規則（群ごとの指標の揃い、休眠 tag の Actor 参照、プロファイル連鎖で群を落とさない、など）。

env 別ファイル（`Atari.txt` など）の値・本数・群やキーの列挙は等値比較しない。固定したいなら PRD072 の golden か hidden の採取テストにする。Run の構築時に止まる検査（未知の eval 名・未宣言の Actor）を前倒しするだけのテストは作らない。これらのテストはタグ `[shipped_config]` を持ち、設定を変えたあとに `anet-core-test.exe "[shipped_config]"` で走らせる。設定を変えてこの種のテストが落ちたら、テストを新しい値に書き換える前に、写しを規則に置き換えられないかを見る。env 別ファイルは実験のたびに変わる（Atari.txt の変更の半分は設定だけの変更）ので、写しを固定すると正当な設定変更のたびにテストが落ちるため。
