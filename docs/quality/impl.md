# 実装 品質確認観点

実装計画と実装のレビューと、実装した側の自己点検で走査する観点。

## 位置づけ

| 項目 | 内容 |
| --- | --- |
| 対象の成果物 | [レジストリ](../process/registry.md) の成果物キー `impl-plan`（実装計画）と `impl`（実装）。同じ依頼で、まとめて渡してよい |
| 参照するエージェント | レビューエージェント。依頼で、観点ファイルのパスとして渡される。実装する側も、レビューに出す前の自己点検で読む |
| 対象外 | 設計の妥当性。PRD があれば PRD の側で決め、無ければコミット前の人間のレビューが見る |
| 変更箇所の渡し方 | 依頼の「変更箇所」に、基準コミットと、変更ファイルの一覧を書く。まだ Git が追跡していない新しいファイルは「新規（全体）」と書く。文書は、変えた節も書く |
| 読む範囲 | 実装計画と設計文書は、全体を読む。コード・テスト・設定ファイルは、差分と、差分が属する関数・クラス、項目の判定に要る箇所を、検索して読む。全文は読まない。1 ファイルで数百 KB のものがあるためである。プロセス契約の 2 節は対象の全体を読むと定めるが、コード・テスト・設定ファイルでは、この範囲に読み替える |

- 各項目は規約の所在を指し、成果物がそれを満たすかを問う。規約の本文は、所在の文書だけが持つ。
- 項番は本書の中で一意である。指摘は項番で引用する。項目を消しても、番号は詰めない。
- 判定の範囲と応答の形は、[プロセス契約](../process/protocol.md) の 2 節と 3.1 節による。
- 節の適用範囲に当たらない項目は、対象外として扱う。
- 「変更ファイル」は、依頼に書かれた変更ファイルの一覧である。`impl-plan` をあわせて渡されたときは、実装計画のファイルも含める。

### 入力元が「なし」のとき

PRD に沿わない変更は、`impl` として、入力元を「なし」と書いて渡される。次の項目は、扱いを変える。表に無い項目は、そのまま適用する。

| 項番 | 入力元が「なし」のときの扱い |
| --- | --- |
| 14・15（受入基準の充足、確定事項への適合） | 対象外 |
| 16・17（過剰の不在、変更の範囲） | 依頼に書かれた変更の目的に照らして見る。目的が書かれていなければ、対象外 |
| 30・34（新しいファイルの理由、公開ヘッダの変更） | 理由や変更の記述は、依頼にあればよい |
| 47（計画との対応） | 実装計画が無ければ、対象外 |

| --- | --- | --- | --- |
