## 背景

2026-11-12 に、PRD116 の受入の §6.3（性能）のうち未実施だった Atari 分を測った。Montezuma・64 lane・CUDA・Release で、RND なし・既定 RND・Taiga 設定を ABC→CBA で 3 巡回し、別の Run で Tracy の内訳を採った（[実験記録](../../experiments/default-dqn/atari/2026-11-12_rnd_performance.md)）。結果を見た開発者が、既定 RND の統計の区間の重さを課題として起票するよう選んだ。開発者への質問はしていない。

PRD116 の実装では、採点の統計の区間で観測を正規化し直して結果を捨てる二重計算について、「費用を測ってから、統計の更新だけを行う口を足すかを決める」としていた（[intrinsic_rnd.cpp](../../../core/anet-core/src/intrinsic_rnd.cpp) の `Estimate` の `@todo`）。今回の測定は区間を細かく分けていないので、この二重計算の費用だけは取り出せていない。

## 事象

- 89,984 経験の中央値は、RND なし 19.019 秒、既定 RND 31.584 秒（1.661 倍）、Taiga 設定 280.616 秒（14.754 倍）だった。
- 既定 RND の Tracy（8 秒、388 intake、1 intake は 64 観測）で、RND 全体は 1 intake あたり 13.097 ms だった。そのうち統計の区間が 8.206 ms（62.66%）を占めた。ほかは、正規化 1.561 ms（11.92%）、target forward 0.799 ms、predictor forward 0.770 ms、backward 0.603 ms、optimizer step 0.538 ms などだった。
- 既定（`statistics_mode=whiten`）の統計の区間（`intrinsic_rnd.cpp` の `Estimate`、`ANET_PROFILE_SCOPE_NEXT(statistics)` から `result_transfer` の前まで）は、次をすべて CPU で行う。
  - 誤差の統計の更新：64 個のスカラー。
  - `normalizer_->NormalizeAndUpdateStats(float_observations)`：観測を正規化し直したうえで、画素ごとの `RunningMeanStd` を double で更新する。正規化の結果は捨てる。
  - target 出力の統計の更新：64×512、double。
  - 診断のための値の読み出し：分散の平均、最大、誤差の平均、clip の割合。
- 測った Run は `backend.torch_num_threads = 1`（`common.txt` の既定）で、CPU の torch の演算は 1 スレッドだった。
- Taiga 設定（`variance_feedback`）では、統計の区間は RND 全体の 0.34% だった。Taiga 設定の主な費用は、1 件ずつの optimizer step（35.90%）と backward（28.73%）である。
- 統計の区間の中の各処理（観測の正規化統計、二重計算の正規化、target 出力の統計、診断の読み出し）がそれぞれどれだけかかっているかは、測っていない。

## 影響

- 既定 RND を使う Atari の Run は、この構成で RND なしの 1.66 倍の時間がかかる。そのうちで最も大きいのが統計の区間である。
- 観測の正規化統計と target 出力の統計の処理量は、lane の数と観測の大きさに比例する。そのため、128 lane で回している Montezuma の Run では、1 intake あたりの費用はさらに大きくなる見込みである（未測定）。
- 放っておくと、RND を使う実験（Montezuma の β の比較、PRD121 の価値の分解、924 の NGU）の 1 本ごとの実時間が、この分だけ長いままになる。

## 対応方針

未定。考えられる手は次のとおりで、どれを採るかは費用の内訳を測ってから決める。

- 統計の区間をさらに細かく区切って測る。
- 二重計算をやめ、統計の更新だけを行う口を足す（`@todo` の件）。
- 統計を device の上で、または float でまとめて計算する。
- 統計の CPU の演算のスレッド数を見直す。

正規化統計の計算の精度と順序を変えると、RND を有効にした Run の学習の系列が変わりうる。そのため、無効時の同一性と、有効時の値の扱い（どこまでの差を許すか）を決めてから直す。速さの確かめは、`core/anet-core/testdata/prd116/run_performance_atari.py` で同じ条件の 3 巡を回して比べる。

## 対応内容

- 2026-11-13 PRD128 の再グリル: 学習の入口のボーナスの診断が、`.item<float>()` を 6 回呼んで値を 1 つずつ CPU へ写している（[default_dqn_agent.cpp](../../../core/anet-core/src/default_dqn_agent.cpp) の `DefaultDQNAgent::UpdateFromBatch` の内的報酬の区間。PRD128 の実装のあとは内的報酬のクラスへ移る）。これを 1 回の転送にまとめる案は、性能の変更なので PRD128 の範囲から外し、RND の時間の内訳と合わせて測ってから決めることにした。この課題に取り組むときの材料にする。[PRD](../../memo/128_dqn_agent_refactor_bundle_10prd.md)（§1.3）
