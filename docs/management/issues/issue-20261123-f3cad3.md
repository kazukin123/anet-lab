## 背景

2026-11-23 の監査（観点 drift、範囲 `docs/design/160_applications_and_tools.jp.md`）で、160 の記述をコードと突き合わせて見つけた。分類は文書 stale である。開発者には質問していない。3 つとも 160 の図と一覧の数行の直しで、まとめて直せるので 1 件にした。

ホットスポット補正: 160 は 90 日の変更回数が 43 回で、設計文書（jp）の中で 200 に次いで多い（`reports/stats/stats.json` の `flow.churn90`）。urgency を 2 から 3 へ 1 段上げた。

## 事象

- §4 の mermaid の flowchart は、Metrics Viewer の subgraph の `DB[(Run-local SQLite cache)]`（`160_applications_and_tools.jp.md:198`）と、Optuna の subgraph の `DB[(optuna.db)]`（219 行）に同じ node の ID `DB` を使う。mermaid の node の ID は図の全体で 1 つなので、2 つは 1 つの node にまとまり、ラベルは後の `optuna.db` になる。そのため描いた図では、`MetricsIngestor` が optuna.db へ書き、`MetricsRepository` が optuna.db から読み、Optuna の harness と Dashboard が同じ node を使う。英訳（`160_applications_and_tools.en.md` の 200 行・221 行）も同じである。本文（234 行）は「Run directory、Optuna DB、artifact store が process 間の contract」と書く。
- §3.1 の Runner のコードマップは、`src/apps/runner/src/` の画面のファイルのうち、`EvalTracePanel`（§3.4 で詳しく書く）、`HeatMapPanel`、`Conv2dPanel`（§3.4 で Trace に追従する pane として書く）、`ErrorDialog`（§7.1 の共通の error reporter の表示）へリンクしない。リンクがあるのは RunnerApp・WorkspaceDialog・RunnerFrame・TrainPanel・EvalPanel・QValuePanel・LogPanel だけである。§3.4 が書く `gui::TracePlayer`・`TraceRowSorter`・`gui::EnableColumnDragMove` の置き場の `src/core/base/include/anet/gui.hpp`・`src/core/base/src/gui.cpp` もコードマップに無い。
- §7.1 は FPS の menu の選択肢を「Train が 0 (Off)・0.1・…・60、Eval が 0.1・…・120」と書く。実装の menu はどちらも先頭に設定の値を選ぶ `Config` の項目を持つ（`src/apps/runner/src/RunnerFrame.cpp:847` の `ID_TrainFpsConfig`、860 行の `ID_EvalFpsConfig`）。step 数の menu については、160 も `Config` を書いている（§7.1 の `app.eval_panel.step_per_frame` の項）。

## 影響

- §4 の図を見た人が、Viewer が Optuna の DB を読み書きする、または Optuna と Viewer が 1 つの DB を共有すると読み違える。process 間の contract を説明する図なので、境界の理解を誤らせる。
- Evaluation Trace など §3.4 の本文の大きな部分について、コードマップからファイルへたどれない。

## 対応方針

- §4 の Optuna 側の node の ID を別の名前（`ODB` など）にする。英訳も同じに直す。
- §3.1 のコードマップに、Evaluation Trace（EvalTracePanel と gui.hpp/cpp）、HeatMap・Conv2d、エラーの表示（ErrorDialog）の行を足す。
- §7.1 の FPS の選択肢に `Config`（設定の値）を足す。
- 文書だけの直しで、コードは変えない。
