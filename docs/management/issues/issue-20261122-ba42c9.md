## 背景

PRD161（観測パイプラインと強制行動の `MakeAction` 入力化）のグリル（2026-11-20〜22）で、Q の Network へ渡す観測の加工を、設定で並べる「Forwarder の並び」にまとめる形を決めた（[PRD161](../../memo/161_observation_pipeline_10prd.md)）。RND の Network へ渡す観測の加工は、この仕組みに載せず、今のまま RND が持つ（同 NG3・D33）。

範囲に入れないことは、グリルでゴールと非ゴールを確かめたときに合意した。課題にするかは、グリルの中では質問していない。工程末に起票の候補として示し、開発者が記録すると選んだ。

## 事象

- RND は、byte の画像を float に直して、自前の統計で正規化している（[intrinsic_rnd.cpp](../../../src/core/base/src/intrinsic_rnd.cpp)）。
- PRD161 は、`TensorSpec` に値の尺度の属性を足し、Q の側の正規化の対象を、属性が「尺度が決まっていない」のキーにする（PRD161 の D17）。Atari の byte の画像は「決まっている」と宣言するので、Q の側では正規化の対象にならない（同 D18）。
- RND の正規化の対象の判定は、PRD161 では変えない。属性に合わせると、Atari で RND の観測の正規化が外れて、動きが変わるためである（同 D33）。
- PRD161 を実装したあとは、観測の加工の定義が、Q の側（Forwarder の並び）と、RND の側（RND の中）の 2 か所に残る。

## 影響

- RND の入力に、Q の側と同じ加工（重ねる、キーを落とす）を当てたいとき、RND の側に同じ処理を書き足すことになる。
- 正規化の対象の決め方が、Q の側（属性）と RND の側（RND の中の判定）で違い、同じキーの扱いを 2 か所で読むことになる。

## 対応方針

未定。

着手の条件は、RND の入力に、Q の側の並びと同じ部品（重ねる、キーを落とす、正規化）を当てる構成が要るようになったときである（PRD161 の NG3）。RND の正規化の対象を属性に合わせるかは、Atari の動きが変わるので、Run で比べて決める。
