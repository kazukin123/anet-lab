## 背景

PRD117（WARN の意味の線引きと読まれない設定の検出）の再グリルで、WARN を出す箇所を 1 つずつ扱いを決めた。PER の抽選の代替は、WARN を Run ごとに 1 回にするだけにし、代替そのものをやめるかどうかは範囲外にした（[PRD117](../../memo/117_warn_policy_and_unread_config_10prd.md) の D9、§9 の 20）。

開発者に質問したか: 質問した。扱いを聞き、開発者が「代替は残して WARN を 1 回にする。代替の是非は課題の候補にする」を選んだ（2026-11-10）。工程末に候補として示し、開発者が起票を選んだ（2026-11-11）。

## 事象

優先度つきの抽選（PER）は、有効な位置を引き当てられずに batch が埋まらなかったとき、残りを一様の抽選で埋めて WARN を出す。

- core/anet-core/src/replay_buffer_impl.cpp の `PER Rejection Sampling failed to fill batch. Falling back to uniform.`（PRD117 の起票時点で 1213 行）。試行の上限は batch の大きさの 10 倍。コードのコメントは「滅多に起きないが、ツリーが空に近い極初期など」の保険としている。
- AGENTS.md の Fail-Fast 原則は、明示した要求を果たせないときは fail-fast とし、黙って代替しないとしている。PER を明示した設定の一部を、別の方法に代えていることになる。
- 過去の Run のログ 616 本に、この WARN は 1 件も無い（PRD117 §2.1・§2.6）。起きる条件は分かっていない。

## 影響

起きた Run では、一部の batch の抽選の分布が PER と一様の混ざったものになる。PRD117 を実装したあとは、WARN が Run ごとに 1 回になるので、2 回目以降は黙って続く。起きる状況が続く不具合があった場合、最初の 1 回の WARN でしか気づけない。

## 対応方針

未定。候補は、代替をやめて止める、代替を残す（今のまま）、起きた回数を診断値として出す、の 3 つ。起きる条件が分かっていないので、起きた事例を見てから決める。止める形は、正当な極初期の状況で Run を落とす恐れがある。
