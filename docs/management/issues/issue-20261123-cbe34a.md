## 背景

2026-11-23 の定常整備（anet-audit、観点 architecture・範囲 318_rl_core）で見つけた。観点は依存（Runner の frame loop が MetricsLogger の確定の時機を決めている）。flush の時機を変えると異常終了のときに残る行が変わるので、リファクタリングではなく、設計文書と実物の食い違い（不整合）として起こした。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `trainer.cpp`（churn90 が 17）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 3 から 5 へ 1 段上げた。

## 事象

- [trainer.cpp](../../../src/core/base/src/trainer.cpp) 171 行の `RunnerBase::DoUpdateFrame` は、最後に `anet::MetricsLogger::Instance()->Flush()` を呼ぶ（43d36841、2025-12-21 から）。
- 学習スレッドでは `RunnerThread::ProcessStep`（trainer.cpp 1330〜1340 行）が `DoUpdateFrame(1, ...)` を呼び、`ThreadBase` のループ（thread.cpp 56 行）がそれを繰り返すので、train step ごとに flush する。EvalPanel は UI のタイマーから `DoUpdateFrame`（`src/apps/runner/src/EvalPanel.cpp` 317 行）を呼ぶので、タイマーごとに flush する。
- flush の中身は `JsonlBackend::Flush`（metrics_logger.cpp 225〜238 行）で、mutex を取って `ofstream::flush()` を呼ぶ。
- アプリの `RunnerApp::FlushRunOutputs`（RunnerApp.cpp 649〜657 行、f0c00339）のコメントは、標準出力とメトリクスを pause・save などの明示的な境界でだけ flush すると書く。[140](../../design/140_observability.jp.md) も、§5.2 で FlushRunOutputs の境界でだけ flush する、§8 で metrics まで同じタイマーで flush して I/O の頻度を増やさない、§2 でどこへ保存するかは MetricsLogger と backend の責務、と書く。
- `DoUpdateFrame` の flush を確かめるテストは無い。metrics.jsonl を読む core のテスト（trainer_test.cpp 1683 行、episode_end_test.cpp 1170 行）は、自分で `Flush()` を呼んでから読む。
- 毎 step の flush が Run の速さにどれだけ効くかは測っていない。

## 影響

出力をいつ確定するかが、core の Runner（毎フレーム）とアプリ（境界だけ）の 2 か所で決まり、140 と FlushRunOutputs を読んで直しても、学習中の I/O の頻度は変わらない。学習スレッドが step ごとに JSONL の mutex を取り、背景評価や UI スレッドの書き込みと取り合う。一方で、Run が異常終了したときに metrics.jsonl が直前の step まで残るのはこの flush による可能性があり、そう意図したという記録は無い。flush をただ消すと、落ちた Run の最後の行が欠ける。

## 対応方針

未定。metrics.jsonl をいつ確定するか（アプリの境界、時間ごと、MetricsLogger 自身の決まり）と、異常終了で失ってよい量を開発者が決め、決めた側だけに持たせる。Runner の frame loop から MetricsLogger への依存は外す方向。140 §5.2・§7・§8 を決めた形に合わせる。確かめは、トピック別まとめの「変えるときの条件」の RFD0094 §4.1 D3・§8 の 1（metrics の出力・定義レコード・WARN の時機を変えない。同 seed の短い Run で比べる）と RFD0122 §4 D8・§6 A7（全 scalar の点の一致）による。実時間は交互 3 巡以上で比べる（性能の区分は「軽くなる」の向きで、量は測っていない）。
