## 背景

2026-11-23 の監査（観点 refactor、範囲 324_dqn）で見つけた。観点は `docs/quality/refactor.md` の「先回りの抽象」（いつも同じ値が渡る引数）と「局所の繰り返し」である。開発者には質問していない。どちらも ImageCls の Agent の構築の数行で、まとめて片づけられるので 1 件にした。

## 事象

- `ImageClsAgentConfig` のコンストラクタは 2 つ目の引数 `config_prefix` を override の接頭辞として受け取り（`src/algo/imagecls/src/image_cls_agent.hpp:58`）、空でなければ override の接頭辞の下の Actor カタログも読む（80〜84 行）。この引数を渡す呼び手は無い。本番の `ImageClsAgentFactory::CreateAgent`（`image_cls_agent.cpp:775`）も、テスト（`image_cls_agent_test.cpp` の 881・1241・1269・1300・1325 行、`imagecls_config_baseline_test.cpp` の 101・158・160 行）も、1 引数で作る（検索語 `ImageClsAgentConfig(`）。
- `ImageClsAgent` のコンストラクタは、設定を 2 回ずつ書く。
  - INFO: 冒頭の `LOG::info() << "ImageClsAgent config=" << config_.ToString()`（`image_cls_agent.cpp:585`）と、末尾の `LOG::info() << "ImageClsAgent initialized. config=" << config_.ToString()`（638 行）。
  - メトリクス: 冒頭の `MetricsLogger::Instance()->Log(config_)`（586 行）と、末尾の `MetricsLogger::Instance()->Log(config)`（637 行）。`MetricsLogger::Log(const std::string&, const anet::Config&)`（`src/core/base/src/metrics_logger.cpp:676`）は、`json/ImageClsAgent.json` と `config/` の下のファイルを書き直し、Run のメトリクスのマスタへ json の行を 1 行足す（657〜673 行の `LogJsonInternal` の `backend_->WriteJsonl`）。そのため、ImageCls の Run のマスタには `ImageClsAgent` の json の行が 2 行入る。DefaultDQN と Rainbow のコンストラクタは 1 回ずつである（`default_dqn_agent.cpp:479〜480`、`rainbow_agent.cpp:39〜40`）。
- 2 回目の書き込みの間に設定は変わらない（`config_` は const）。

## 影響

- 読む人は、override の接頭辞で ImageCls を作る使い方があるのかを確かめることになる。
- Run のマスタと Viewer のキャッシュの json の行（`json_lines`）に、同じ設定の行が 2 つ入る。設定の行を数えたり並べたりする道具は、ImageCls の Run でだけ重複を扱うことになる。

## 対応方針

- `ImageClsAgentConfig` のコンストラクタを 1 引数にし、override の接頭辞の分岐を消す。
- 構築時の設定の書き込みを、INFO 1 回とメトリクス 1 回にする。消す側は末尾の 2 行とする（DefaultDQN と同じく、冒頭で書く）。INFO の文言 `ImageClsAgent initialized.` を残すかは対応のときに決める。
- INFO の行の数と、マスタの json の行の数が変わる（それぞれ 1 つ減る）。ほかの挙動は変えない。ImageCls のテスト（`image_cls_agent_test.cpp`）が期待値を変えずに通ることを確かめる。構築時だけの処理なので、性能の区分は「関わらない」。
