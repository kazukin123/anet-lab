## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

PRD923（Train 側の強制行動）と PRD922（操作入力の設定化）は、強制行動の経路を触る。[issue-20261103-93f8a6](issue-20261103-93f8a6.md)（手動の行動と GPU 推論の device 不一致）も同じ経路にある。

## 事象

- `EvalRunner` の 1 step は、`DoStep()` → `DoStep(-1)` → `DoStep(action, step_counts_)` → `DoStepInternal(action, event_counts, true)` と 4 段で渡す（core/anet-core/src/trainer.cpp:349-352、339-342、257-261。宣言は core/anet-core/include/anet/trainer.hpp:137-144）。評価 session の `RunSession` は `DoStepInternal(-1, event_counts, false)` を直接呼ぶ（trainer.cpp:375）。
- 「強制行動なし」を `action = -1` で表し、`action >= 0` を 3 か所で見る（trainer.cpp:268、293、314）。
- `notify_episode_end` が false のときは、エピソード終了の集計と通知を飛ばして `last_step_had_episode_end_ = false` だけを書く（trainer.cpp:328-332）。
- `DoStep(int64_t action)` はメンバ `step_counts_` を const 参照のまま `event_counts` として渡す（trainer.cpp:341）。`DoStepInternal` は途中で `step_counts_` を進める（318-320）ので、329 行で読む `event_counts` は進めた後の値になる。引数の型（`const StepCounts&`）からは、呼び出した時点の値に見える。
- コンストラクタ 2 つは、`session_env_` の初期化 1 行のほかは同じ文である（trainer.cpp:213-223 と 225-236）。
- `last_forced_` は lane の数だけの `vector<bool>` だが、いつも全要素へ同じ値を入れる（trainer.cpp:314）。

## 影響

- 呼び出しの行（375 行の `(-1, event_counts, false)`）を読んでも、何を選んでいるかが分からない。強制行動の経路を触る PRD923・PRD922 は、この切り替えの上に足すことになる。
- `event_counts` が別名で途中から値が変わる点は、関数を分けたり値渡しに直したりすると、EpisodeEndEvent に載る counts が変わる落とし穴になっている。

## 対応方針

強制行動を `std::optional<int64_t>` にし、「1 step 進める」と「エピソード終了を集計して配る」を別の private 関数に分け、呼ぶ側（DoStep と RunSession）が要るほうだけを呼ぶ。`event_counts` は「進めた後の自分のカウンタ」と分かる形で渡す。コンストラクタは片方へ委譲する。公開の `DoStep` の 3 つの形は残し、EpisodeEndEvent の counts の値は今のまま保つ。
