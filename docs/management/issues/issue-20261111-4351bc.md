## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

PRD958（TempoRL の後続）は skip の継続状態を触る。

## 事象

- `dqn::Actor` の mutable のメンバは 11 個ある（core/anet-core/src/dqn_based_agent.hpp:772、777-779、784-790）。時計・snapshot・skip の継続状態である。
- const の関数が状態を進める。`Actor::MakeAction`（core/anet-core/src/dqn_based_agent.cpp:2391 から）、`UpdateSnapshot`（2369 から）、`ApplySkip`（2484 から）、`ResetSkipSession`（2571 から）、ネットワークの重みを書き換える `CopySourceNetwork`。`MakeAction` が const なのは基底（core/anet-core/include/anet/rl.hpp）の宣言による。
- 排他は source のネットワークの読み取りだけに掛かり、Actor 自身のメンバには掛かっていない。1 つの Actor を 1 つのスレッドだけが使う前提かどうかは、型からもコメントからも読めない。
- 行動選択の出力のうち `forward_output` と `risk_num_taus` は、`DQNActionInfo` の public メンバ（dqn_based_agent.hpp:498-499）として一時的に運ばれ、`ApplySkip` で読まれ、`MakeAction` の中で空に戻される。skip が無いときも毎回入れて消している。
- 排他の有無だけが違う 2 行が 2 回書かれている。
- 「skip 用の方策が共有か」を、`skip_->shared_policy` と `skip_->policy != policy_` の 2 つの書き方で判定している。本番ではこの 2 つは同じ値になる。

## 影響

- const と書いてある関数が状態を進めるので、呼ぶ側は「同じ引数で 2 回呼んでも同じ」と読めてしまう。
- 一時的な値が結果のオブジェクトの public メンバに載るので、どこまで有効かを追わないと分からない。PRD958 で skip の継続状態を足すと、mutable のメンバがさらに増える。

## 対応方針

先に、Actor がスレッドをまたいで共有されるかを Runner の側で確かめる。そのうえで、(1) 時計・snapshot・skip の継続状態を 1 つの struct にまとめて mutable を 1 つにする、(2) `forward_output`・`risk_num_taus` は行動選択の戻り値を「DQNActionInfo と一時出力の組」にして結果から外す、(3) 排他は条件付きで lock する形にして 2 行の写しを消す、(4) `shared_policy` は方策が同じかどうかから導く。const を外すには基底とほかの Actor の実装への波及があるので、別に決める。
