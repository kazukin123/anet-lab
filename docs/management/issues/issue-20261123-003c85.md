## 背景

2026-11-23 の定常整備（anet-audit、観点 defect・範囲 318_rl_core）で見つけた。分類は境界。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `replay_buffer_impl.cpp`（churn90 が 16）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- `NStepQueueController::ExtractSequences`（[replay_experience.cpp](../../../src/core/base/src/replay_experience.cpp) 55〜87 行）は、n_step が 0 のとき `Peek(0)` が空を返し、`peeked.size() == static_cast<size_t>(n_step_)` が真になって空の系列を出し、記録を 1 件捨てる。ProcessQueue は空の系列を飛ばし（[replay_buffer_impl.cpp](../../../src/core/base/src/replay_buffer_impl.cpp) 1668〜1669 行）、Update も MarkValid も呼ばないので、Size() は 0 のままである。
- n_step が負のときは、size_t へ変えた値が巨大になり、終端が来たときだけ系列を出す。収益は実質エピソードの終わりまでの和になる。
- `CreateReplayBuffer`（replay_buffer_impl.cpp 2516〜2537 行）は容量・per_initial_priority・mode を検査するが、n_step は検査しない。必要な容量は `max(1, n_step)` で計算するので通る（2519〜2520 行）。
- DQN では `rep_config.n_step = use_n_step ? n_step : 1`（`dqn_learner.cpp` 917 行）で、設定の読み取り（`default_dqn_agent.hpp` 490 行）に範囲の検査は無い。n_step > 0 を確かめるのは step 診断の部品（`dqn_assembler.cpp` 92〜94 行）だけで、Evaluation Trace を使うときにしか作られない。`Learner::CanUpdate` は Size() が batch に届くまで待つ（`dqn_learner.cpp` 1614〜1616 行）。
- 同梱の設定の n_step は 1・3・5 だけで、0 以下を名指しするテストは無い（検索語 `n_step\s*=\s*(0|-)`）。

## 影響

n-step を切るつもりで `learner.n_step = 0` と書くと、Run は動き続けるが学習が 1 回も起きない。LearnEvent が出ないので評価も発火しない（`dqn_learner.cpp` 1679〜1681 行のコメントのとおり、評価を動かすのは LearnEvent だけ）。エラーも WARN も出ず、Run を流し終えるまで気づけない。負の値では、違う収益で黙って学習する。

## 対応方針

`CreateReplayBuffer` で `n_step >= 1` を fail-fast にし、完全キーを示す（`full_keys` の "n_step" は `dqn_learner.cpp` 909 行で既に写されている）。確かめは、トピック別まとめの「変えるときの条件」の RFD0078 6.2（公開 API と抽選の分布を変えない。ERROR を足すだけ）、RFD0094 §4.1 D3（既存の fail-fast の文言と時機を変えない）、RFD0121 §8.2（1 成分のときの記録と収益を保つ）による。性能には関わらない（構築時だけ）。
