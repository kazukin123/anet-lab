## 背景

2026-11-10 に、リファクタリングの候補を広く拾うための観点を整理した。観点のうち、文・式・宣言・体裁の書き方に関するものの多くは、読まなくても機械で判定できる。

開発者から「単純な表現の問題は lint などの静的解析の仕組みで扱いたい」との指示があり、候補の提示を省いて起票した。あわせて、この課題で覆える見込みの範囲は、リファクタリング候補の抽出の対象から外すと決まった。

## 事象

- `.clang-format` と `.clang-tidy` が無い。`.editorconfig` が定めるのは、末尾の改行、行末の空白、改行コードだけである。
- `CMakeLists.txt` は `CMAKE_EXPORT_COMPILE_COMMANDS` をコメントアウトしている（22 行）。MSVC の警告の指定は `/wd4267`（無効化）と `/w14996`（有効化）だけである（109〜110 行）。
- CI（`.github/workflows/windows-ci.yml`）は 3 構成のビルドだけで、静的解析の手順が無い。
- [実装 品質確認観点](../../quality/impl.md) の機械検査は、検索 7 項目とスクリプト 5 項目で、変更ファイルだけを見る。書き方の水準の観点は読解に頼っている。
- `apps/metrics-viewer` には `checkstyle.xml` と整形の設定ファイルがあるが、`pom.xml` に checkstyle・formatter の記述は無い。

本体の C++（テストを除く約 175 ファイル、約 69,000 行）を正規表現で粗く数えた件数は次のとおり。誤検出を含む目安で、指摘の数ではない。

| 手がかり | 件数 |
| --- | --- |
| 添字の `for`（範囲 `for` は 518） | 273 |
| `.first`／`.second`（構造化束縛は 176） | 215 |
| コメントアウトされたコードらしい行 | 234 |
| `this->` | 105 |
| `static_cast` | 726 |
| タブ始まりの行 | 1,759 |
| 140 字を超える行 | 188 |

## 影響

- 単純な書き方の問題が、レビューと監査の読解でしか見つからない。見落としが出て、指摘がレビューごとにぶれる。
- 新しいコードにも同じ書き方が入り続け、あとで直す量が増える。
- リファクタリング候補の抽出では、機械で判る指摘が件数を占め、構造の候補が埋もれる。

## 対応方針

未定。決めることは次のとおり。

1. 道具。候補は clang-tidy、clang-format、MSVC の警告レベルと `/analyze`、自作の検索。MSVC・libtorch・wxWidgets・CUDA の構成で動くかを先に確かめる。
2. 有効にする検査の組。下の「覆う見込みの範囲」を出発点にする。
3. 今ある指摘の扱い（一括で直す、触った所から直す、今ある分を基準として記録して増やさない）。[AGENTS.md](../../../AGENTS.md) は大規模な整形を避けると定め、impl.md は include の並べ替えと既存ログの英語化を一括で行わないと定めるので、あわせて決める。
4. 走らせる場所（手元、CI、レビューの機械検査）。
5. 性能のためにその形にしている箇所を、検査から外す書き方。
6. Java（`apps/metrics-viewer`）と Python の道具を範囲に入れるか。

### 覆う見込みの範囲

リファクタリング候補の抽出から外す範囲である。覆えるかは 1 で確かめ、覆えなかった分は抽出の観点へ戻す。

| 観点 | 当たるもの |
| --- | --- |
| 体裁の不統一 | タブと空白の混在、行の長さ、宣言の折り方 |
| 書かなくてよい記述 | 未使用の include・変数・引数、不要な `this->`・cast・`else`、コメントアウトされたコード |
| 宣言の欠落 | `const`・`override`・`explicit`・`[[nodiscard]]`、指示付き初期化 |
| 標準の語彙で書ける手書き | 添字のループ、`.first`／`.second`、検索・集計の定型 |
| 条件と制御の定型 | return のあとの `else`、bool の式の簡約、入れ子の三項演算子 |
| 型と変換 | 冗長な cast、長い型名の直書き |
| 意味の読めないリテラル | 数値の直書き |

読んで判断する観点（分岐で書いた対応表、同じ式の繰り返し、値の受け渡しの遠回り、名前、コメントの中身）は、この課題の範囲に入れない。

## 対応内容

- 2026-11-11 リファクタリング候補の抽出: 機械の検査で拾える例を 1 つ足す。`anet::ThrowError`（core/anet-core/include/anet/diag.hpp:72）は必ず例外を投げるが、宣言に `[[noreturn]]` が無い。そのため `ANET_SYSTEM_ERROR` の直後に到達しない文が残っている（random.cpp:124 の `throw std::invalid_argument(...)`、schedule.hpp の `return T{};` 2 か所、util.cpp の `return std::nullopt;`。数えたのは util・profile・random の範囲だけ）。`[[noreturn]]` を付けると、到達しない文をコンパイラの警告や clang-tidy で見つけられるようになる。付けたときに警告の出方が変わる箇所があるかは確かめていない。確かめ: 宣言を今のコードで確かめた。
