## 背景

2026-11-23、RFD0161（観測加工の定義の一元化）の実装のあとに、開発者が公開ヘッダ `anet/forwarder.hpp` を見て、依頼の型の名前が中身と合っていないこと、型の関係が込み入っていること、RL に依らない層に RL の概念が入っていることを挙げた。2026-11-23〜24 に、開発者と hpp の草案を直しながら形を決め、[RFD0200](../../memo/0200_forwarder_public_interface_rework_10rfd.md) として起こした。

## 事象

- 公開の型が 6 つあり、実行するものが 2 種類（`Forwarder`・`ForwardExecutor`）、部品の口が 2 種類（`SpecForwarder`・`ForwarderProvider`）ある。並び（`ForwarderChain`）は、Forwarder と、Forwarder を作る側を兼ねる。`ForwardRequest` は、依頼ではなく種類の列挙である（RFD0200 §1.1）。
- `anet` 名前空間（RL に依らない層）に、`episode_start` の引数、依頼の種類の列挙、並びの決まり、重ねる枚数とキーを答える口、図の名前が入っている。部品の種類は 3 つに固定で、外から足せない（同 §1.2・§1.3）。
- spec は、構築のときの 1 つ（Env の観測 1 枚ぶん）しか渡せない。依頼ごとに実際に渡すものは違う（同 §1.4）。
- 重ねる枚数とキーは、並びの中の部品の設定が持ち、並び → Agent → Learner → ReplayBuffer と、データと逆の向きに渡る（同 §1.5）。

## 影響

- 使う側が、使い道によって口を使い分けることになり、どの依頼の spec かが口から読めない。
- RL に依らない層を、依頼の種類を足すたびに変えることになる。部品を基盤の外から足せないので、ほかの観測加工（RND の観測加工、直前 action を観測へ足す部品）を同じ仕組みに載せにくい。
- 行動選択と ReplayBuffer の両方が使う設定の正本が、並びの中の 1 つの部品にある。

## 対応方針

[RFD0200](../../memo/0200_forwarder_public_interface_rework_10rfd.md) のとおりに実装する。

- 2026-11-24 RFD0200: 起票のあとに、直近の系列（観測・行動・報酬・開始の印）を並びの外のバッファに置く案が出た。採ると、RFD の決定の一部（開始の印を入力の鍵にすること、`FrameStack` を並びの部品のままにすること、など）が変わる。開発者は、今の RFD のまま先に実装すると述べた。材料は RFD の §10.4 にあり、実装のあとの再グリルで使う。[RFD](../../memo/0200_forwarder_public_interface_rework_10rfd.md)

## 対応内容

- 2026-11-24 RFD0200: グリルを行い、RFD を起こした（確定事項 30 件、受入 18 件、未決なし）。あわせて、用語集の 5 項目、ADR 0094〜0096 と ADR 0084・0086 への注記、wiki の 4 ページを書いた。確かめ: RFD のレビューが OK（2 往復）。[RFD](../../memo/0200_forwarder_public_interface_rework_10rfd.md)
