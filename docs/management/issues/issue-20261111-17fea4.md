## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

どちらも「設定の境界で 1 回だけ enum にする」で片づく同じ形の問題なので、1 件にした。

## 事象

- policy_type。
  - 同じ意味の語を 2 つ受け付ける。`"EpsilonGreedy"`／`"0"`、`"UQE"`／`"1"`、`"ThompsonSampling"`／`"2"`、`"Greedy"`／`"3"`。
  - 受け付ける範囲が関数ごとに違う。`ValidateActionPolicy`（core/anet-core/include/anet/default_dqn_agent.hpp）は `"3"` を通さないが、`DefaultDQNAgent::CreateActionPolicy`（core/anet-core/src/default_dqn_agent.cpp:293 から）は `"3"` を Greedy として受ける（315）。target の ε の検査は `"EpsilonGreedy"` だけを見て `"0"` を見ない（default_dqn_agent.cpp:238）。`"3"` は設定の検証を通らないので、設定からは届かない分岐である。
  - int の定数 `kActionPolicyType_EpsilonGreedy` ほか 3 つ（core/anet-core/include/anet/agent.hpp）は参照が 0 件である。文字列の定数 `kActionPolicyTypeStr_*` があるのに、同じ文字列の直書きも残る（default_dqn_agent.hpp:237、239、default_dqn_agent.cpp:238、296、299 ほか）。
  - UQE と Thompson の「quantile_mode が none なら不可」の検証が、設定の構築時と `CreateActionPolicy` の中（同じ文が 2 回）の 2 つの層にある。
  - 数字の値を設定するテストは見当たらない。
- quantile_mode。
  - `"none"`／`"qr"`／`"iqn"` を `std::string` で持ち、比べる行が default_dqn_agent.hpp に 5 行、default_dqn_agent.cpp に 10 行（100、141、149、198、256、266、301、309、822、828）、dqn_based_agent.cpp に 19 行ある。
  - 同じ値を Actor ごとの方策、skip の方策、target の方策、learner へ写している。`CreateActionPolicy` は、渡された方策の値ではなく Agent の `config_.quantile_mode` を見る。
  - 値の検証は、値を使う行より後ろにある。同じクラスの `skip.network_mode` は、境界で enum へ変えている。

## 影響

- 方策を 1 つ足すと、検証・既定値の導出・生成の 3 か所の文字列の比較を直す。分布の表し方を 1 つ足すと、Head の分岐・Learner の分岐・設定の検証・テンソルの契約の検証を直す。打ち間違いがコンパイルで見つからない。
- 写しを 4 か所に持つので、Agent の値と方策の値が食い違う状態を型が許す（テストで設定を作ったあとに書き換えると起きる）。

## 対応方針

設定を読む境界で、policy_type と quantile_mode を 1 回だけ enum に変える関数（名前と別名の対応表を 1 つ）を置き、検証・既定値の導出・生成・Head と Learner の選択は enum を見る。config dump の記録は文字列のまま残す。使われない int の定数は消す。数字の別名を残すか外すかは受け付ける設定が変わるので別に決める。外すならクリーンブレークとして設定ファイルを一括で直す。`"3"` と `"0"` の扱いの差は、写すか直すかを決める。`ActionPolicyConfig`・`LearnerConfig` の欄まで enum にするかは、範囲を分けてもよい。
