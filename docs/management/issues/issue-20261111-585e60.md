## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

どれも名前・コメントを実際の動きに合わせる小さな直しで、確かめ方も同じ（呼び出しとログが変わらないこと）なので、1 件にした。

## 事象

- `BatchState` の `IsDone`・`IsTruncated`・`IsEpisodeStart`（core/anet-core/include/anet/rl.hpp:474-491）は、名前に反して lane 0 だけを見る（`done[0]` などを返す）。呼び出しは observers.cpp の 4 か所（714、761、1193、1230）だけで、テストは無い。同じ struct の `GetSingle(index)` は lane を引数で取る。
- `DefaultAgentFactory`（core/anet-core/include/anet/agent.hpp:406）は、名前が `AgentFactory` の実装に並ぶが `AgentFactory` を継承していない。していることは、device の解決、設定の記録、登録済みの `AgentFactory` を class_id で引いて渡すことである（core/anet-core/src/agent.cpp:69-99）。構築は trainer.cpp:1054 の 1 か所で、作った直後に 1 回使うだけである。`AgentRepository` に `/// @todo AgentFactory → AgentCreator` が残っている（agent.hpp:368）。
- `NetworkGraphVizConfig`（core/anet-core/include/anet/nn.hpp）の 2 項目。
  - `show_param_shapes`（86 行、コメント「parameterのshapeを表示するか」）が真のとき、`Network::MakeGraphViz` は module の設定値のキーと値を出す（core/anet-core/src/nn_impl.cpp:2412）。parameter の shape は読まない。
  - `cluster_branches`（92 行、コメント「branchごとに囲みを作るか」）は、branch のノードの style 名を "branch" か "default" に切り替えるだけである（nn_impl.cpp:2376）。囲みを作る処理は GraphViz の層にも無い。
- Runner の 4 関数。
  - `RunnerFrame::OnUpdateTrainStatus`（apps/runner/src/RunnerFrame.cpp:1663）は Frame の UPDATE_UI に付き、学習状態の表示は 1 行で、残りは最前面の切り替え、最大化が解けたことの検出、主 pane の占有規則と置き場の見張りである。
  - `RunnerApp::InitTrainer`（apps/runner/src/RunnerApp.cpp:907）は Trainer を作らない。profile の区間だけの TrainObserver と、100 learn step ごとにログを出す LearnObserver を付けるだけである。
  - `RunnerFrame::CreateStatusBar`（RunnerFrame.cpp:365）は引数なしの private 関数で、中で基底の同名関数を `wxFrame::CreateStatusBar(3)` と修飾して呼ぶ。並びの関数は SetupMenuBar・SetupToolBars・SetupPanes・SetupEvents である。
  - `ReportError`（apps/runner/src/ErrorDialog.cpp:11）は、ログへの出力のあと約 65 行で画面を組み立てて modal で出す。関数名からは画面が出ることが読めない。

## 影響

- `next_state.IsDone()` は「batch 全体が終わったか」に読めるが、lane が複数あっても先頭だけを見る。
- 「学習状態の更新」を探す人は Frame の周期処理を見落とし、「Trainer の初期化」を探す人はログ用の observer に行き着く。`CreateStatusBar` は基底の関数を上書きしたように見える。
- 設定を書く人は、`show_param_shapes`・`cluster_branches` が名前どおりに効かないことに、図を出して初めて気づく。

## 対応方針

- `BatchState` の 3 つは、名前を実際の動きに合わせるか、lane を引数に取る形にして呼ぶ側の 4 か所で 0 を渡す。公開ヘッダの関数名が変わる。
- `DefaultAgentFactory` は、役割（設定から device を決めて Agent を作る入口）に合う名前にするか、device と Agent を返す 1 つの関数にする。agent.json の出力と INFO のログの文言は変えない。
- `NetworkGraphVizConfig` の 2 項目は、メンバ名を変えると設定キーが変わる（キーはメンバ名から作られる）ので、コメントを実際の動きに合わせるだけにする。
- Runner の 4 関数は、名前を中身に合わせる。`OnUpdateTrainStatus` は「状態の表示・最前面・レイアウトの見張り」の 3 つの呼び出しに分け、`ReportError` は画面の組み立てを別の関数に分ける。ログの文言は変えない。
