## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

PRD920（NN のブロック別の勾配メトリクス）は、ブロックごとの値を集めるために同じ走査を足す。

## 事象

- 次の 6 か所が、`for (branch : body_->GetBranches())` → `branch->GetNetworkStruct()` → `GetBlocks()` → `block->GetModule()` の入れ子を手で書いている（core/anet-core/src/nn_impl.cpp）。
  - `Network::ValidateForwardReuse`（241 から）
  - `NetworkForwardExecutor::Impl` のコンストラクタ（2011 付近）
  - `Network::GetNoisyParameterEntries`（2072 から）
  - `Network::ComputeParameterNormSplit`（2163 から）
  - `Network::GetSpectralNormEntries`（2296 から）
  - `Network::MakeGraphViz`（2354 から）
- null の検査の有無がそろっていない。5 か所は struct と module の両方を検査し、実行器の準備の 1 か所は branch と struct だけを検査して module は検査せずに呼ぶ。
- 同じ対象を、Forward の側は検査せずに使う（`NetworkBlock` の Forward、`NetworkStruct` の Forward、`NetworkBranch::Execute`、`NetworkBody` の branch の呼び出し）。構築する側は null を渡していない（`NetworkStructBuilder::Build` は空の構造でも `make_shared<NetworkStruct>()` を返す。テストの構築にも null は見当たらない）。

## 影響

- module に聞く問い合わせを 1 つ足すたびに、入れ子の走査をもう 1 つ書くことになる。PRD920 もその 1 つになる。
- 「struct や module が null でありうるのか」が場所ごとに違って読める。Forward の側は null なら落ちる書き方なので、走査の側の検査が何を守っているのかがコードから分からない。

## 対応方針

`NetworkBody` に「全 module を branch・block つきで順に渡す」関数を 1 つ置き、6 か所をその呼び出しにする。null の検査は走査の中の 1 か所に寄せるか、構築する側が null を渡さない前提をコメントで書いて消す。消してよいかはテストで確かめる。`GetSpectralNormEntries` は SN のある構成で `SoftCopyTo` から毎回呼ばれるので、速さが変わらないことを確かめる。
