## 背景

2026-11-17 の会話で、Montezuma の本線（`mz_tg` の列。価値の分解の merge・split）と、Taiga ら寄せの基準の Run（`run.@rainbow_like`＋`run.@rnd_taiga`）、サブ機の易しいゲームの比較 Run（Breakout・Qbert）を並べて見たときに、開発者から「Run ごとに tag の構成が少しずつ違い、比べられなくて困る。tag の種類はむやみに増やしたくない」と指摘があった。下の事象は、そのときに調べた結果である。

開発者はその場で「`@min` は保守していないので使わない方向。消すか整理するかは課題に」と決めた。

関連する課題: [issue-20261103-0ef7b8](issue-20261103-0ef7b8.md)（PRD108、tag の番号の全体整理。名前の付け直しが範囲で、どの Run がどの組を使うかは扱っていない）、[issue-20261103-52bda0](issue-20261103-52bda0.md)（PRD096、横軸の単位と間隔を数える単位を分ける）、[issue-20261108-06a3f0](issue-20261108-06a3f0.md)（PRD118、Atari.txt の Run プロファイルを平らにする。§1.4 の「learn step で数える値が replay ratio ごとの別プロファイルを要する」は、下の間引きと根が同じ）。

## 事象

2026-11-17 に、5 本の Run の `metrics.jsonl` の先頭にある tag の宣言を比べた。

| Run | tag の数 |
|---|---|
| メイン機 `run_20261116-005336_mz_tg_g99ne_split_s1`・`run_20261117-142732_mz_tg_r121_g99ne_s2`（本線） | 237 |
| メイン機 `run_20261117-043636_mz_rbw_rndtg_s1`・サブ機 `run_20261116-224834_mz_rbw_rndtg_s2`（Taiga 寄せ、RND あり） | 110 |
| サブ機 `run_20261117-223826_bo_dqiqn_s1`（Taiga 寄せの Q 側、RND なし） | 81 |

5 本に共通の tag は 77 で、内訳は `42_env` 26・`52_eval2` 26・`53_evalg` 16・`34_agent_plasticity` 5・`37_agent_qtd` 2・`38_agent_loss` 1・`90_perf` 1。ずれの出どころは 3 つある。

1. 基本の組が 2 系統ある。本線は `metrics.scalar.$ = metrics.scalar.@baseline > @munchausen > @replay_fit > M1 > M2 > @value_decomposition`（12 bat の `VDMET`）。`run.@rainbow_like` は `apps/runner/config/Atari.txt` の 82 行で `metrics.scalar.@min > M1 > M2` に差し替えている（79〜80 行のコメント「更新が約 27 倍なので、更新ごとのメトリクスは間引き」）。`@min`（`metrics_scalar.txt` の 182〜188 行、2026-08-27 の fd8d755b から）は、同じ量に `@baseline` と違う名前を付けている。

   | 量 | `@baseline` | `@min` |
   |---|---|---|
   | エピソード数 | `10_train/11_eps_count` | `00_train/11_eps_count` |
   | 学習側の報酬 | `20_eps/10_train_reward` | `10_eps/10_eps_reward` |
   | 速さ | `90_perf/12_exp_step_per_sec`（exp step） | `90_perf/11_train_step_per_sec`（train step） |

   `@min` を連鎖に使う設定は `run.@rainbow_like` だけで、ほかの設定ファイル（CartPole・DropMerge・ImageCls・LunarLander）ではコメントの行にしか出てこない。
2. `run.@rainbow_like` は、プロファイルの中で tag を 8 本個別に宣言している（`Atari.txt` の 83〜90 行）。名前は本線と同じでも、横軸と間隔が違う。`37_agent_qtd/11_q_max_mean`・`37_agent_qtd/17_q_gap`・`38_agent_loss/01_loss` は、本線が exp step の軸で interval 1、`run.@rainbow_like` が learn step の軸で interval 2000。`34_agent_plasticity/01〜03・05・61` は、本線が interval 500、`run.@rainbow_like` が 5000（どちらも learn step）。
3. bat の引数で tag を 9 本足している。`34_agent_plasticity/41〜45`（probe で測る可塑性、interval 5000）と `77_agent_value/41〜44`（Greedy の session の診断）で、11・12 bat の Montezuma の価値の分解の列（変数 `PL1`〜`PL5`・`VDG1`〜`VDG4`）と 13 bat の段 54 にだけある。可塑性は、学習の batch で測る `01〜05` と、probe で測る `41〜45` の 2 種類が並んでいる。

このほか、機能が有効のときだけ出る tag がある（`56_agent_in` は RND、`77_agent_value` は価値の分解、`54_evalgs` は greedy_single、`36_agent_munchausen`、`39_agent_per` など）。これらは機能の有無で名前が変わらない。

## 影響

- 本線と Taiga 寄せ・易しいゲームの Run を Metrics Viewer で重ねても、エピソード数・学習側の報酬・速さが別の tag なので重ならない。
- 同じ名前の tag でも横軸の単位が違うと、横の位置がずれたまま重なり、気づかずに読み違えるおそれがある。
- bat で足した tag は、その列の Run にしか無く、比べる相手の Run に無い。
- 列ごとに組を差し替えたり tag を足したりする形が続くと、tag の種類が増え、保守と比べる手間が増える。

## 対応方針

- 決めたこと（2026-11-17、開発者）: `@min` は使わない。
- 案: Atari の Run はすべて同じ組を使い、Run プロファイルと bat では `metrics.scalar.$` を差し替えず、tag も足さない。同じ量には名前を 1 つ、横軸を 1 つ（exp step）にする。間引くときは組を替えずに記録の間隔で行い、間隔は exp step で数える（PRD096 の、横軸と間隔を数える単位を分ける仕組みが前提）。機能の tag は機能の組に置き、その機能を有効にするプロファイルが連鎖へ足す。過去の Run の tag 名は変えない。
- 未決:
  1. `@min` を消すか、`@baseline` の名前に合わせて整理するか。
  2. 可塑性を `01〜05`（学習の batch）と `41〜45`（probe）のどちらに一本化するか。probe の計算の止まりは [issue-20261115-e5a0eb](issue-20261115-e5a0eb.md)。
  3. bat で足した 9 本の置き場（共通の組か、機能の組か）。`[greedy]` は Atari だけにあり、共通の組に書くと Atari 以外で ERROR になる。
  4. `run.@rainbow_like` の間引きの方法と時期（PRD096 のあとにするか）。
  5. PRD108 の再グリルにまとめるか、別に先に片づけるか。
