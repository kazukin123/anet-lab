## 背景

2026-11-23 の定常整備（anet-audit、観点 refactor・範囲 318_rl_core）で見つけた。観点は「既存の重複」で、「共通処理の置き場違い」が付随する。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `replay_buffer_impl.cpp`（churn90 が 16）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- 同じ記法を 4 つの関数が別々に解く。[rl.cpp](../../../src/core/base/src/rl.cpp) 43〜67 行の `GetObservationTensor`（`BatchExperience::GetTensor` から）、[replay_buffer_impl.cpp](../../../src/core/base/src/replay_buffer_impl.cpp) 797〜810 行の `ParseObservationSubKey` と 859〜877 行の `GatherObservationRows`、`probe.cpp` 13〜27 行の `GetObservationSpecKeyForBase`、`image.cpp` 99〜101 行（`MakeExperienceProbe`）と 139〜141 行（`MakeAgentProbe`）。
- subkey が空（`base.`）のとき、rl.cpp と Replay は ERROR を出すが文言が違う。probe.cpp は空の文字列を返し、image.cpp は state の spec を付ける。
- 接尾の無い base のとき、rl.cpp と Replay は `ToUnifiedObservation` を使い、probe.cpp は "vector" の spec を使う。
- subkey を付けた経路で、Replay は float32 へ変換し（869 行）、rl.cpp は元の dtype のまま返す（60〜66 行）。
- 名指しのテストは `probe_test.cpp` 136〜151 行と `replay_buffer_test.cpp` 1785〜1881 行にある。subkey が空の場合のテストは無い。

## 影響

記法を 1 つ変える（subkey の区切りや既定の解釈を変える）と 4 つのファイルを直すことになり、既にある食い違いがさらに増える。同じキーを書いても、可視化の経路と Replay の経路で、止まるかどうかと値の dtype が違う。

## 対応方針

解き方を 1 つの関数にし、「未指定・subkey あり・空」の 3 つの状態を返す。エラーの文言と dtype の違いは挙動に関わるので、この直しでは各所に残して変えない。公開の定数（`STATE_OBS` など）は変えない。確かめは、トピック別まとめの「変えるときの条件」の RFD0094 §4.1 D3（fail-fast の文言と時機を変えない）と RFD0122 §4 D8・§6 A7 による。性能には関わらない（`BatchExperience::GetTensor` は HeatMapVectorObserver の log_interval で間引いたあと、Replay の `GetTensorVector` は可視化の経路から呼ばれる）。
