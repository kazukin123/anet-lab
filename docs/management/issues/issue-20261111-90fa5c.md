## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

`ComputeQValueHeatMap` は PRD122 でパネルから切り出した関数である。平滑化の指定の重ね持ちは [issue-20261110-3f4e63](issue-20261110-3f4e63.md) に追記した。

## 事象

- `ComputeQValueHeatMap`（apps/runner/src/QValuePanel.cpp:420 から、218 行）の中に、Advantage の引き算、ヒストグラム化（累積範囲の更新、0 の位置、投票）、表示の範囲決め、正規化の 4 つの段が並ぶ。
  - `is_hist` の分岐が 2 回に分かれている。
  - 使い捨ての変数と重ねた代入がある。`disp_min`・`disp_max` を宣言で入れて直後に同じ値を入れ直す、`zero_point` はいつも 0、`guide_line_ratio` が局所変数と `data.guide_line_ratio` の 2 つある。
  - 累積範囲の更新は Max 側と Min 側で同じ形を 2 回書く。呼び出しをまたぐ状態 `range` を書き換えるのは、この部分だけである。
- データの受け渡し。
  - `ApplyData` は同じ `shared_ptr` を `latest_data_`（406）と `data_store_` の両方へ入れる。`Update` は `data_store_.Get()`（642）から読み、`latest_data_` を読むのは `CreateTraceSnapshot` だけである。
  - `data_store_` は mutex を持つ `UIDataStore` で、`update_pending_` は `std::atomic<bool>` である。一方、同じコールバックの中で `latest_step_` と `latest_data_` を保護なしで書く。
  - 評価の Runner を進める箇所で読めたのは、UI のイベントの中だけである。

## 影響

- 範囲の更新（状態を持つ）とそれ以外（入力だけで決まる）が 1 つの関数に混ざり、どこが状態に触るかを全部読まないと分からない。
- 型からは「別スレッドから届く」と読めるが、保護の無いメンバの書き方からは「UI スレッドだけ」と読める。どちらの前提で直せばよいかがコードから決まらない。

## 対応方針

- `ComputeQValueHeatMap` をファイル内の関数（範囲の更新、ヒストグラムの投票、表示範囲の正規化）に分け、本体は 3 つを順に呼ぶ 20 行ほどにする。テストがこの関数を直接呼んでいるので、分けたあとも同じテストで確かめる。
- 先に、評価の通知が UI スレッド以外から来る経路があるかを `EvalRunner` の側で確かめる。UI スレッドだけなら `latest_data_` 1 つと普通の bool にして `data_store_` を外す。別スレッドから来ることがあるなら、`latest_step_`・`latest_data_` も同じ保護の中へ入れ、その旨を宣言のコメントに書く。
