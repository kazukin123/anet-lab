## 背景

2026-11-11 の会話で、開発者が「実装にかかる時間の多くがテストなので、修正に関係するテストだけを回すなど、決まりを整えて効率化できないか」と尋ねた。AI が過去の実行記録とビルドの記録を調べ、決まりの文面を起草して開発者と詰めた。途中で開発者から次の指摘と質問があり、文面を直した。

- 実装前の控えを作業ごとのフォルダへ写す案では、`.scratch` がさらに膨らむ。今でもどれを消してよいか分からず困っている。
- 控えとログの置き場を 1 か所に共有して大丈夫か。
- なぜ実行体を直接回さずにコピーするのか。

最後の問い「実装前の控えをやめる形に文面を直すか」には答えが出ていない。開発者がこの日の作業を止め、この課題の起票を指示した。`.scratch` 全体の棚卸しと置き方の決まりは、別の作業で進めている。

## 事象

測った事実:

- core の全件（`anet-core-test.exe` を引数なしで回すこと）は 1 回 374〜708 秒かかる（`.scratch` に残る PRD109・110・119 の JUnit）。走っている Run と CPU・GPU を取り合うと延びる。
- テスト実行体の起動だけで約 12 秒かかる（テスト 1 件でも同じ）。
- Debug のリンクは、`anet-core-test.exe` が中央値約 69 秒、`AnetRLRunner.exe` が約 101 秒、`AnetRLRunner-gui-test.exe` が約 50 秒かかる（`out/build/x64-Debug/.ninja_log`）。
- 計測できた時間の約半分は、prefetch の決定性テスト 2 本（`DQN learner prefetch path is deterministic under fixed jitter` の 48 組と、`PipelineTrainRunner prefetch path is deterministic under fixed jitter` の 12 組）が占める。ただし JUnit は `GENERATE` を使うテストの時間を少なく数える（各テストの合計 273 秒に対して全件は 530 秒）ので、順位は下限である。

テストの回し方:

- 実装前と変更後の両方で全件を回すのが通例になっている。AGENTS.md の検証の節と impl.md の項番 48 には「関連するテスト」とあるだけで、範囲も回数も決まっていない。
- PRD の受入基準の書き方によっては、前後の比較が要る。「直す前に通っていたテストが落ちない」（PRD122）や「既知の失敗は前後で変わらない」（PRD918）と書くと要る。「既知の失敗以外の失敗が無い」（PRD117）と書けば要らない。テンプレートと品質確認観点にこの言い回しの決まりは無い。
- PRD110 の実装では、小さな直しのたびに前後で全件を回し、全件だけで 12 回、合計約 6,900 秒かかった。
- 実装前の全件を回している間にリンクして、実行体のロックで失敗した例がある（PRD122 の LNK1168）。
- 知られている失敗のうち 2 件は起票済み: [issue-20261109-fa2f69](issue-20261109-fa2f69.md)（`[shipped_config]` を単独で回すと oneDNN の assert で止まる）と [issue-20261111-61ad60](issue-20261111-61ad60.md)（GUI の Logs の折り返しテスト）。

置き場:

- `.scratch` は 483 GB、81,897 ファイル、最上位のフォルダが 86 個ある。そのうち 361.5 GB は exe・dll・pdb の写しで、157 のフォルダに 3〜5 GB ずつある（`baseline-bin`、`before`、`bin\Debug` の写しなど）。実装前の控えとして、実行体を libtorch・CUDA の DLL ごと写したものが主である。控えのためのワークツリー `.scratch/prd067-baseline` も `git worktree list` に残っている。
- 同じチェックアウトで、別の作業が同時にビルドとテストを行う。2026-11-11 の調査中にも `anet-core-test.exe` が 3 回作り直された。テスト実行体は全作業で 1 個なので、別の作業のコミット前の変更も自分の実行体に入る。

確かめた手段:

- Catch2 の `-#` で、テストファイル名がタグになる。`anet-core-test.exe -# "[#replay_buffer_test]"` で 114 件、`[prd122]` と合わせると 123 件が選ばれた。GUI テストの実行体でも使える。
- 実行体だけをコピーし、`PATH` の先頭に元の `core\anet-core\bin\Debug` を足すと、DLL をコピーせずに回せた。

## 影響

- 実装の時間の多くが全件の待ちに使われる。全件を何度も回すほど、走っている Run とも CPU・GPU を取り合う。
- `.scratch` が膨らみ続け、どれを消してよいか分からない。ディスクも圧迫する。
- 控えとログの置き場を決めずに共有すると、同時に走る別の作業とログや控えが上書きし合い、別の作業の結果を自分の結果として読むおそれがある。

## 対応方針

AGENTS.md の検証の節に、テストを回す範囲と回数の小節を足す。あわせて impl.md の項番 48 を直す。会話で起草した文面は次のとおりである（未合意の案）。

```markdown
### テストを回す範囲と回数

全件は、変更が届くテスト実行体を引数なしで回すこと（core を変えたら `anet-core-test.exe`、Runner の GUI を変えたら `AnetRLRunner-gui-test.exe` も）を指す。全件は 1 回に 10 分前後かかるので、回すのはコードを変えた作業の最後だけにする。途中を絞るのは時間のためであり、最後の全件は省かない（「長時間のビルド・テスト・バッチ検証」）。

テストの控えとログは `.scratch/test-tmp/<作業名>/` だけに置き、同じ作業の中では上書きする。作業名は PRD 番号（`prd122`）、PRD が無ければ課題の ID の 6 桁にする。同じチェックアウトで別の作業が同時に走るので、ほかの作業のフォルダを使わない。作業ごとのフォルダへ、実行体・DLL・pdb・テストのログをコピーしない。結果は、件数と落ちたテストの名前を実装記録に書く。`test-tmp` の下のフォルダは、その作業をコミットしたら消してよい。

- 着手前は全件を回さない。Debug ビルドのあと、テスト実行体だけを `.scratch/test-tmp/<作業名>/baseline/` へコピーしておく。
- 変更後に落ちたテストは、まず `docs/management/issues/` に同じ失敗が起票されていないかを見る。無ければ、控えた実行体でそのテストだけを回し、着手前から落ちていたかを確かめる。DLL は、元の実行体のフォルダを `PATH` の先頭に足して読ませ、リポジトリルートから回す。
  `$env:PATH = "$PWD\core\anet-core\bin\Debug;$env:PATH"; & .scratch\test-tmp\prd122\baseline\anet-core-test.exe "落ちたテストの名前"`
- TDD の途中は、テスト実行体のターゲットだけをビルドし（`--target anet-core-test`、GUI は `--target AnetRLRunner-gui-test`）、近いテストだけを回す。近いテストは、変えたテストファイルと、変えた本体に対応するテストファイルのファイル名タグ、計画で決めたタグ、設定を変えたときの `[shipped_config]` である。実行体の起動だけで十数秒かかるので、1 回の起動にまとめる。
  `core\anet-core\bin\Debug\anet-core-test.exe -# "[#replay_buffer_test],[prd122]"`
- 全体ビルドと全件は、レビューに出す前に 1 回にする。全件は出力を `.scratch/test-tmp/<作業名>/` へ実行体の名前で保存して背景で走らせ、待つ間に文書の追随と自己点検を進める。走っている間は同じ実行体をリンクしない（実行体のロックで失敗する）。
- レビュー指摘の直しのあとは、直した箇所の近いテストを回す。直しが本体のコードに及んだときだけ、全体ビルドと全件をもう 1 回回す。
```

impl.md の項番 48 の確認内容には、「本体のコードを最後に変えたあとに回した全件の記録がある」を足す。今より厳しくなるが、途中の全件を減らす代わりに最後の 1 回をレビューで確かめるためである。

決めることが残っている:

1. 実装前の控えを取るか、やめるか。控えの役目は、変更前の版を残し、起票されていない失敗が着手前からあったかを数秒で確かめることだけで、同時実行とは関係ない。AI はやめる形を勧めた。知られている失敗は課題として起票されつつあり、同じチェックアウトでは控えにも別の作業の変更が混ざるためである。やめる場合は、上の文面の最初の 2 つの箇条を次の 1 つにまとめ、2 段落目の「テストの控えとログ」を「テストのログ」にし、`PATH` の例を消す。
   `- 着手前は全件を回さず、控えも取らない。変更後に落ちたテストは、docs/management/issues/ に同じ失敗が起票されていれば照合で済ませる。起票されていなければ、自分の変更との関係を調べる。関係が無いと分かったら、工程末の起票の候補にする。`
2. PRD の受入基準を「既知の失敗以外の失敗が無い」の形で書く決まりを、`docs/quality/prd.md` に足すか。
3. `.scratch` 全体の置き方の決まり（別の作業で棚卸し中）と、`test-tmp` の名前と消してよい時期をそろえる。

重い prefetch のテスト 2 本を、既定では最小再現にして今の回数を hidden（`[.]`）へ移す案は、テストのコード変更で別に直せるので、この課題に含めない。手を付けるなら、Run が止まっているときに `--durations yes` で全件を測り直してからにする。
