## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

どれも DropMergeEnv の中の作りで、同じ seed で前後が一致することを確かめれば済むので、1 件にした。エピソード統計の 5 か所の写しは [issue-20261111-c68178](issue-20261111-c68178.md) に分けた。PRD086（DropMerge のマクロ行動）は行動の解釈を触る。

## 事象

- `DropMergeEnv::Step`（core/envs/dropmerge1/src/DropMergeEnv.cpp:1005 から、267 行）の 1 つの関数に、行動の分類、DROP 列の連続の統計、NoLegal 候補の記録、物理の反復、安定待ちの継続の判定、blocked run と settle の統計、NoLegal の裁定、最大 step と無 DROP の時間切れ、エピソード終了時の記録が順に並ぶ。
  - 報酬の加算が 6 か所に散る。`calcReward`（1472 から）は、合体スコアが正ならそれを reward と raw_reward の両方へ入れて返すだけで、残りはコメントアウトされた罰の行である。名前は「報酬を計算する」だが、罰は 1 つも足さない。
  - 継続の判定は 6 つの値を見る。関数の中で読み書きするメンバは 20 個を超える。
- 行動の解釈を 4 か所で別々に行う。Step は action を DROP か NOOP かに分けたあと `decodeDirectDropColumn`（646 から）で列を求め、`processAction`（660 から）は同じ action をもう一度列へ直し、`makeState`（1319 から）は NOOP かどうかを判定し直す。`action_mode_` が direct 系かの判定は 6 か所にある。Direct では DROP の判定がいつも真になるが、`decodeDirectDropColumn` は範囲の外で -1 を返すので、2 つの見方は範囲の外の action で食い違う。
- DROP の位置の計算を、実行する側（`processAction`）と「置ける列があるか」を調べる側（`hasAnyLegalDropForCurrentFruit`、578 から）が別々に持つ。列の中心の式が 3 か所、壁へのクランプの式（余白 0.01f の直書き）が 2 か所、出現の高さが 3 か所にあり、ノイズの範囲も別の式で表す。今は食い違いは見当たらない。
- 「全部の果物を回る」ループが 8 か所にある（488、552、858、887、970、1240、1381、1507）。どれも dynamic の body の読み飛ばしで始まり、うち 5 か所は Fruit の検査も行う。半径は `config_.fruit_radii[rank - 1]` の形で 12 か所から引く。
- 盤面を、const の `makeState` が mutable の `grid_cache_` へ float に直して入れ（1454）、結果の構築がもう一度写す（1517）。`grid_cache_` を読むのはこの 1 か所だけで、同じ盤面は観測にも int8 の Tensor として入っている。毎 step 900 要素の写しが 2 回起きる。結果の構築の前に `makeState` が呼ばれている必要があるという順序は、型から読めない。
- LunarLander の ResetResult と StepResult は `std::shared_ptr<const LunarLanderEnv>` を値で受け、参照外しして渡すだけである。`shared_from_this` を使うのは LunarLander の 2 か所だけで、DropMerge は `const DropMergeEnv&` を受ける。2 つの Env とも `std::enable_shared_from_this` を継承する。

## 影響

- 終了理由や罰を 1 つ足すとき、267 行のどこに置くかを順序ごと読み解く必要がある。報酬がどこで決まるかは、`calcReward` を読んでも分からない。
- 行動の種類を 1 つ足す（PRD086 のマクロ行動など）と、4 か所の解釈を同じに直すことになる。
- NoLegal の判定は「実行する側と同じ位置に置けるか」を調べるので、`processAction` の式を変えて `hasAnyLegalDropForCurrentFruit` を直し忘れると、判定が黙ってずれる。
- body の種類を 1 つ足すと、8 つのループの条件を見直すことになる。

## 対応方針

- Step を「行動の解釈」「物理の反復（sim_steps と合体スコアを返す）」「終了の裁定（done・truncated・理由を返す）」「エピソード終了時の記録」の private 関数へ分け、Step は進行と報酬の合算だけを書く。`calcReward` は消し、合体スコアを直接足す。
- 行動は Step の先頭で 1 回だけ「種類と列」に解釈し、`processAction` と統計へ渡す。範囲の外の action の今の扱いは保つ。
- 列の中心・クランプの上限・出現の高さ・果物の半径を小さな private 関数にし、果物の走査は「果物ごとに関数を呼ぶ」private 関数にする。走査の順は変えない。
- 結果は観測の grid の Tensor を持ち、aux を求められたときに float へ直す。`grid_cache_` を消す。
- LunarLander の 2 つの構築子は `const LunarLanderEnv&` を受け、2 つの Env から `enable_shared_from_this` を外す。
- RNG の呼び出し順を保ち、同じ seed で前後の結果が一致することを確かめる。物理 frame ごとの経路なので、速さはブレ幅の基準で確かめる。
