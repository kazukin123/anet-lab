## 背景

anet は個人開発で、ブランチは常用していない。ただ、Claude Code アプリのワークツリーセッションや Codex のワークツリーで、main と並行して作業することがある。RFD の採番（[docs/memo/README.md](../../memo/README.md) の「採番」）は、起票の時点で最大番号の次を取る決まりで、ほかのワークツリーのファイルと、main にまだ入っていないブランチのコミットは見ない。

2026-11-25、PPO 系の作業をワークツリー `feature/20261125-ppo` で進め、その RFD に 0202 を振った。同じ頃、main の別のセッションが、wiki の積み上げと引き方の RFD に 0202 を振った。開発者はこのブランチを PR で main へマージする予定で、その前に衝突を解く必要がある。

2026-11-26、開発者の要望（要旨）: 個人開発でブランチの需要は少ないが、コンフリクト解消の AI 支援はいつか作りたかった。これを機に、RFD の番号に限らず、内容と文脈を考えて解く仕組みを整えたい。この課題は、開発者の指示で、候補の提示を省いて起票した。

## 事象

2026-11-26 に確かめた。

- main と `feature/20261125-ppo` の分岐点は `9310b087`。ブランチ側は 4 コミットで、origin にも push してある。
- 両方に RFD0202 がコミットされている。main は `0202_wiki_accumulate_and_lookup_10rfd.md`（20impl・21impl も）、ブランチは `0202_ppo_family_and_on_policy_core_parts_10rfd.md`（20impl も）。コミットの件名も、両方が `RFD0202` を持つ（main の `d7a20b11`・`e38d64b2`、ブランチの `66296d56`・`3ae08c1e`）。
- 作業ツリーを変えない試しのマージ（`git merge-tree --write-tree main feature/20261125-ppo`）では、テキストの衝突は 4 ファイルで、すべて wiki だった。`docs/wiki/log.md`、`docs/wiki/categories/315_nn.md`・`318_rl_core.md`・`321_agent_core.md`。RFD はファイル名が違うので、番号の重なりは衝突として出ず、2 本ともそのままマージに入る。
- 衝突の中身は、両方が同じ箇所の末尾に行を足した形だった（log.md の行、トピック別まとめの「成立の経緯」の日付順の行と、要点の行）。`318_rl_core.md` では、ReplayBuffer の `GetSampleObsSpecs` という同じ事実を、両方が別の文で足している。
- 課題の `INDEX.md`（`reports/tools/wiki_support.py maps` の生成物）と `docs/wiki/index.md` は、行単位の自動マージで衝突なしに通った。その結果が、マージ後に作り直した結果と一致するかは確かめていない。
- `wiki_support.py` の `rfd_rows` は、コミットの件名の番号を、振り直しの行があればその RFD へ、無ければファイル名の番号で引く。ファイル名の番号で 2 本当たると「RFD を一意に決められない」と出して点検へ回す。振り直しの行があると、行の日付以前の件名の番号をすべてその RFD へ当て、その番号を使い続ける別の RFD があるかは見ない（コードを読んだ見立てで、動かしてはいない）。
- 今のハーネスには、マージの衝突の解き方を決めた skill・手順は無い。
- 2026-11-27 RFD0204 のグリル: 上の「`318_rl_core.md` では、ReplayBuffer の `GetSampleObsSpecs` という同じ事実を、両方が別の文で足している」は読み違いだった。その行は分かれた点にもともとあり、main が書き直しただけで、ブランチが足したのは `ComputeGae` と `CategoricalDistribution` の行である。また、main が wiki のページを `docs/wiki/concepts/` の下へ移したため、2026-11-27 の試しのマージではテキストの衝突が 8 ファイルに増えた（すべて wiki）。[RFD0204 §5.2・§5.4](../../memo/0204_branch_merge_conflict_assist_10rfd.md)

## 影響

- 番号の重なりはテキストの衝突にならないので、git に任せると同じ番号の RFD が 2 本 main に残る。コミットの件名の `RFDnnnn` と wiki の RFD の一覧が番号で RFD を引くので、どちらの RFD を指すか分からなくなる。
- 片方を今の決まりのまま振り直すと、振り直しの行が、使い続けるもう片方の RFD のコミットまで振り直した側へ当てる見込みがある（事象の最後から 2 つめの見立て）。
- wiki の追記の衝突を機械的に両方残すと、日付の順が崩れたり、同じ事実が 2 行になったりする。片方だけ残すと、もう片方の記録が消える。生成物は手で解かずに作り直すのが正しいが、解く人がどれが生成物かを知っている必要がある。
- ブランチが長く分かれるほど、番号・wiki・課題の一覧の衝突が増え、解くときに両側の文脈（RFD の中身、どのセッションが何をしたか）を読み直す手間が増える。並行のワークツリーセッションを使うほど起きる。

## 対応方針

暫定 RFD を起こし、グリルで決める。起票の時点の見立て（案）は次のとおり。

- 衝突を種類に分ける。番号・ID の重なり（テキストの衝突にならない意味の衝突）、追記の形のファイル（log.md、成立の経緯）、生成物（INDEX.md、トピック別まとめの生成区画）、中身の衝突（コード・文書の同じ箇所）。
- 決まった手順で解けるもの（生成物は作り直す、番号は振り直す）は道具か手順に任せ、判断が要るものは AI が両側の文脈を読んで解き方の案を出し、開発者が選ぶ。
- 最初の適用は `feature/20261125-ppo` の PR とする。
