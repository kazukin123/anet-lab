## 背景

開発者から、`anet-prepare-commit` が提案するコミットメッセージは文言を調整しないと使えないことが多く、まずコミットメッセージのルールを改善したいとの依頼があった。本課題では、その改善を起票する。

現行のルールは [AGENTS.md](../../../AGENTS.md) の「Git 操作・コミットメッセージルール」にあり、Conventional Commits の形式、変更全体の主目的を表すこと、付随する修正を summary に含めないこと、Topic Issue 番号の選び方を定めている。[anet-prepare-commit](../../../.agents/skills/anet-prepare-commit/SKILL.md) はそのルールを参照し、スキル内へ複製しない構成である。

## 事象

開発者の申告では、提案されたコミットメッセージをそのまま使えず、人手で文言を調整することが多い。調整が必要だった提案と修正後の具体例、調整の共通点、現行ルールの不足箇所は、この起票時点では確認していない。

## 影響

コミットのたびに提案文言を見直して書き換える手間がかかり、コミット準備を支援するスキルの効果が下がる。望む表現の基準が共有されなければ、同じ文言調整が繰り返される。

## 対応方針

まずコミットメッセージの文言を決めるルールを改善する。開発者が求める内容は、下の「開発者が示した基準」に記録した。規約としての具体的な文面は未定。

- 調整が必要だった提案と、開発者が使いたい文言を比較し、共通する判断基準を整理する。
- その基準を `AGENTS.md` のコミットメッセージルールへ反映し、必要な例を添える。`anet-prepare-commit` は引き続き同じルールを参照する。
- 具体例に改訂後のルールを当て、追加の文言調整なしに使える提案になったかを開発者が判断する。

今回の起票ではルールやスキルの変更は行わない。

## 開発者が示した基準（2026-11-05）

コミットメッセージには、**達成した結果や、扱った事象の本題を簡潔に書く**。

次のものは入れたくない、という意図が明示された。

- どう修正したかという方法・実装手段。
- 付随する作業や、作業の途中経過。
- 差分を見れば分かる詳細。

短い文字数へ機械的に収めることではなく、本題を選んで残すことを重視する。件名から外した詳細を本文へ移せばよい、という意図ではない。

この基準は、以下の過去ログから推測した傾向や、Codexの分析レポートに書いた改善候補より優先する。特に、レポートの「操作を具体化する」は、操作や修正方法を列挙する規則として引き継がない。過去の実コミットに含まれる「レビュー対応」などの経緯も、望ましい文言の規範として採用しない。

## グリルの決定（2026-11-05）

上の「対応方針」の文面は未定という記述、各調査の時点の「ルール改訂はまだ行っていない」という記述、「確かめたい点」「用途から見た材料」の案は、次の決定と規約の改訂で置き換わる。文面の正本は [AGENTS.md](../../../AGENTS.md) の「Git 操作・コミットメッセージルール」である。

| 論点 | 決定 |
| --- | --- |
| 件名の形 | `type(対象名): 本題。 PRD番号 課題ハッシュ #Topic`。Topic番号は人に読めないので、scopeは対象名にし、PRD番号は末尾へ移す |
| 対象名 | 規約の一覧から主な1つを選ぶ。当てはまらなければ一覧へ足す |
| 課題との紐づけ | 課題をすべて、IDのハッシュの部分（6桁）で並べる。PRDがあっても付ける |
| 本文 | 既定で付けない。頼まれたときだけ |
| Co-Authored-By | 案に付けない |
| 本題が2つのとき | 「。」で2文に分ける。「〜し、〜」で連結しない。付随作業を2文目へ回さない |
| 短い件名・経緯の件名 | AIの案では出さない。人が手で書く件名は縛らない |
| fix | 症状と起きる条件。条件が内部の原因と一致するなら内部の言葉でもよい |
| feat | 機能の名前で伝わるなら名前、伝わらなければできるようになったこと |
| refactor | 変えた対象と変化の大枠。手順は書かない |
| PRDの文書 | 何についてのPRDか。起票・グリルの語は書いてよい（推奨案の「工程の語を書かない」は採らなかった） |
| 実験記録 | 題材。数値や結論は書かない。題材が多ければ主な1〜2個 |
| 語尾 | 名詞止め。文末の「。」は必ず付ける |
| 列挙 | 2つまで。3つ以上は総称で言い換える |
| 「の」 | 続けない。複合語にできるなら複合語にする（最初の案の試走で開発者が指摘） |
| 語 | 開発者がふだん使う技術語を選ぶ。和語に言い換えた語や、文書の中だけで使う語にしない。画面やコードに名前があればその名前を書く。適用はコミットメッセージ案だけ（開発者の指摘を受けログで確かめ、内容変更のうちClaude 84組中15組、Codex 32組中8組が語の言い換えだった） |
