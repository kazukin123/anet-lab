## 背景

[設計文書160（アプリケーションとツール）](../../design/160_applications_and_tools.jp.md)は、Runner や Metrics Viewer などのアプリケーションの文書として置かれた。開発環境（ハーネスの道具、hook、wiki と課題の保守など）を書く設計文書を用意していなかったため、その種の記述が「ツール」の枠として 160 に足されてきた。開発者の指摘で起票した（質問はしていない）。

開発環境の文書には、[040 開発環境構築ガイド](../../design/040_development_environment.jp.md)がある。初期環境構築から IDE 上のビルド完了までの手順のガイドである。

## 事象

- 160 の 1.3「記載範囲」は、`apps/runner`、`apps/metrics-viewer`、`apps/runner/tools` と起動 launcher を扱うと書く。一方、7.4「wikiと課題の保守」は、記載範囲の外の開発環境の道具を 8 項目で書く。jp・en の両方である。挙がっている道具:
  - `reports/tools/wiki_support.py`
  - `reports/tools/stage_issue_memos.py`
  - `.agents/hooks/commit_cue.py`
  - `.agents/hooks/search_guard.py`
  - `reports/tools/requirements.txt` による PyYAML の導入
- 160 の 8 章「テストと変更時の確認事項」では、ハーネスの道具の検証資材が、アプリケーションの検証資材と並ぶ。
  - PRD114: 課題から INDEX・トピック別まとめ・統計を作る。
  - PRD095: トピック別まとめ・blob・リンクを扱う。
- [設計文書の README](../../design/README.jp.md) の 160 の行は、範囲を「Runner GUI、Metrics Viewer、補助ツール」、読者を「アプリケーション開発者」とする。
- wiki の [311_dev_tools のトピック別まとめ](../../wiki/categories/311_dev_tools.md)は、設計の参照先を 160 の §2.3・§3.3・§7.3・§8 にしている。311（開発プロセス／開発ツール／テスト基盤）だけを書く設計文書は無い。
- 040 は手順のガイドで、7 章「Python 補助ツール」に仮想環境、workspace metrics 圧縮、MLflow bridge を持つ。

## 影響

- アプリケーションを変える開発者が 160 を読むと、ハーネスの道具の記述が混ざっていて、アプリケーションの責務と process の境界が読み取りにくい。
- ハーネスの道具や hook を足すたびに、書き先が 160 の 7.4 になり、混ざりが増え続ける（commit_cue・search_guard も 7.4 に足された）。
- 開発環境の道具の仕組みを探す人やエージェントは、アプリケーションの文書を開かないと見つけられない。

## 対応方針

160 から開発環境の記述を分け、開発環境の文書へ移して整える。対象は 7.4 と、8 章のハーネスの道具の検証資材などである。決めることは次のとおり。

- 置き場をどうするか。手順のガイドの 040 を広げるか、仕組みを書く 1xx の設計文書を新設するか。
- どこまでを開発環境とするか。Optuna harness と `apps/runner/tools` を、アプリケーション側に残すかどうかなど。
- 分けたあとの参照をどう直すか。
  - 160 の 1.3「記載範囲」
  - README の役割の行
  - 311 のトピック別まとめの設計の参照
  - en 版
