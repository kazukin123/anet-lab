## 背景

Atari のプロファイルは `run.@eval2ch_r1 : run.eval_schedule.[eval_target].interval = 0` で `eval_target` の評価を意図して止めている（`apps/runner/config/Atari.txt` 468 行）。一方、`M1.[51_eval1/…]` などの scalar は `$eval.[eval_target]` を参照したまま残る。

この場合に WARN を出して skip する動きは PRD052 §2.5 の決定で（[PRD052](../../memo/done/052_eval_schedule_separation_10prd.md)）、[設計文書 100](../../design/100_runtime_and_configuration.jp.md) にも「dormant tag の一度だけの WARN」と書かれている。つまり現行の契約どおりで、不具合ではない。

設定の読まれない葉を検出する [issue-20261107-0c34dd](issue-20261107-0c34dd.md) の対応で、WARN が増える見込みがある。開発者が、その対応と一緒に扱いたいとして起票を指示した（2026-11-07）。別々に直せるので課題は分けた。

同じ日に、学習済みの checkpoint を読み込んで評価だけを流す Run で WARN が 4 件出た。開発者が「WARN の適正化の観点で分析し、設定で直すものはその場で直し、実装で直すものはこの課題を更新する」よう指示した（2026-11-07）。実装が要る RND の 2 件は、直す場所は違うが、開発者の指示でこの課題にまとめた。

## 事象

- 確かめた Atari の Run の全部で、次の WARN が 1 回ずつ出ている。`mz_nm_rnd_b0p1_s1`、`mz_nomunch_s1`、`mz_rbw_imp_s1`、`mz_rt_base_s1`、サブ機の `a5_ntg_aln_btreps_s1`。

  ```text
  [W] Skipping metrics for unscheduled eval tag. tag='eval_target'. The tag is defined in run.eval but has no active run.eval_schedule entry.
  ```

- これらの Run のログにある WARN はこの 1 種類だけである。
- 同じ Run のログには、Run 構築時の INFO として `eval.[eval_target]: definition-only` がすでに出ている。
- WARN は `core/anet-core/src/trainer.cpp` 866 行で出し、`core/anet-core/src/trainer_test.cpp` 1056 行が WARN のレベルで検査している。
- [PRD081](../../memo/081_evalpanel_episode_trace_10prd.md) は、この WARN を scalar が dormant tag を参照したときだけ出す形を定めている（同 PRD 92 行）。
- `$eval.[eval_target]` の参照は `Atari.txt` 31 行のほか、`DropMerge.txt`、`DropMerge_optuna.txt`、`GridMaze.txt`、`metrics_scalar.txt` にもある。これらの Env で WARN が出ているかは確かめていない。

### 評価だけの Run の WARN（2026-11-07）

`mz_nm_rnd_ev_taurnd` は、RND ありの Run（`mz_nm_rnd_b0p1_s1`）の `agent_close.anet` を `learner.enabled=false`・`run.train.num_envs=1` で読み込み、評価だけを流した。出た WARN は次の 4 件である。

| WARN | 出る理由 | 直し方の判断 |
|---|---|---|
| `DefaultDQNAgent.intrinsic.learn_batch_size=32 exceeds num_envs=1; using num_envs observations per intrinsic learning step.` | Train の lane が 1 なので、RND の補助学習の batch が足りない（`default_dqn_agent.cpp` 109〜112 行）。ただし `learner.enabled=false` では補助学習そのものを休止するので、この検査は意味を持たない | 実装。休止するときは検査しない |
| `DefaultDQNAgent.intrinsic.enabled=true with learner.enabled=false: intrinsic scoring and training are suspended.` | 評価だけの Run で RND を有効にしている（同 118〜119 行） | 実装。RND の checkpoint を読むには `intrinsic.enabled=true` が要る（同 406〜408 行で不一致はエラー）ので、設定では消せない |
| `ActionPolicy spatial exploration is enabled with num_envs < 32. num_envs=1` | Train の lane を 1 にしたのに ε ラダーが有効なまま（`dqn_based_agent.cpp` 1524〜1525 行） | 設定。評価だけの Run の共通プロファイル `run.@evalonly` でラダーを切った（対応内容） |
| `Skipping metrics for unscheduled eval tag. tag='eval_target'. …` | 上と同じ | 本課題の上の事象と同じ |

今回の Run は `run.@evalonly` を使わず、bat の引数で評価だけの設定を組んだ。`run.@evalonly` は `eval_target` の評価も動かすので、それを使えば 4 件目は出ない。

## 影響

- 意図した設定の Run で毎回 WARN が出るので、ログの WARN を読み飛ばす習慣がつく。
- 設定の読まれない葉のような、本当に見るべき WARN を足しても、この行に紛れやすい。2026-11-06〜07 の RND の Run は、意図と別の Network で動いていても WARN が出ず、気づくのが遅れた。今後の検出の効果を保つには、正常な Run の WARN を 0 件にしておくほうがよい。

## 対応方針

未定。候補は次のとおり。

- dormant tag の skip を INFO に下げる。`definition-only` の INFO と内容が重なるので、片方にまとめてもよい。未定義の tag の参照はエラーのままなので、綴りの誤りは今までどおり止まる。変えるのはログのレベルと、テスト 1 件、PRD052 の決定を引き継ぐ設計文書 100 の記述である。
- `interval = 0` で明示的に止めた tag は INFO、schedule の記述が無い tag は WARN に分ける。意図して止めたかどうかを区別できるが、判定が 1 つ増える。
- 設定の側で、`eval_target` を止めるプロファイルでは `51_eval1` の購読行を外す。WARN の意味は保てるが、プロファイルごとに購読の連鎖を書き分けることになり、保守が重い。

評価だけの Run の RND の 2 件の候補は次のとおり。

- `learn_batch_size` と `num_envs` の検査は、補助学習を休止しないときだけ行う。休止するときは 2 件目の WARN だけが残る。
- 2 件目は、checkpoint を読むための設定として正しい組み合わせなので、INFO に下げる。読み込みの検査（406〜408 行）は変えない。
- または、`intrinsic.enabled=false` でも RND の区画を読み飛ばして checkpoint を読めるようにし、評価だけの Run では RND を切れるようにする。checkpoint の読み込みの契約が変わるので、PRD116 の checkpoint の決定（§5.6）と合わせて決める。
