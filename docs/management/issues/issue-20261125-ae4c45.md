## 背景

2026-11-25 の監査（観点 drift、範囲 `docs/design/140_observability.jp.md`）で見つけた。分類は文書 stale である。開発者には質問していない。どれも 140 の図と並びの直しで、まとめて直せるので 1 件にした。

ホットスポット補正: 140 は 90 日の変更回数が 38 回で、設計文書（jp）の中で 200・160 に次いで多い。urgency を 2 から 3 へ 1 段上げた。

## 事象

- 節番号: `### 6.x step座標系`（264 行）と `### 6.x trace チャネル`（311 行）が、仮の番号のまま残る。そのあとに `### 6.1 Evaluation Traceの列と読み取り`（335 行）が続く。
- 置き場: `### 遷移値のtarget env_step`（469〜475 行）は、記法の説明なのに `## 10. 関連文書` の下にある。`### TempoRL の scalar と Trace`（428〜442 行）は `## 9. テストと拡張時の確認事項` の途中にあり、「Observerまたは出力形式を変更する場合は次を確認する」の一覧（444 行から）を前の段落から切り離している。
- §4 の静的構造の図: Observer は 3 種類だけで、`SessionEndObserver`・`MetricsLogSessionEndObserver`・`MetricsLogTraceObserver` が無い。§2 の表は、Notifier が 4 種類の Observer を登録すると書く。図の `ImageObserver` というクラスは無い。実物は `HeatMapVectorObserver`・`MultiPairHeatMapObserver`・`Conv2dVisualizationObserver`（TrainObserver）と `TimeHistogramObserver`・`SweepedHeatMapObserver`（LearnObserver）で（`src/core/base/include/anet/observers.hpp:73-287`）、作って Notifier に付けるのは `ObserverFactory` ではなく `ImageProviderFactory`・`ImageProviderManager`（`src/core/base/include/anet/image.hpp:320-354`。RunnerApp が `CreateAndRegister` を呼ぶ）である。§2 の「Image/Graph Observer」の行にも作り手が無い。
- §5.1 の記録の流れの図: 通知が Train・Learn・EpisodeEnd の 3 つだけで、SessionEnd が無い。
- §3 のコードマップ: 本文が説明する `metrics.hpp`・`metrics.cpp`（`MetricValueReader`・`StepTraceBuilder`。§6.1）、`image.hpp`・`image.cpp`（画像の Observer の作り手と状態スイープ）、`heat_map.hpp`・`heat_map.cpp`（§7.3）、`gui.hpp` の `TracePlayer`（§6.1・§5.3）が無い。

## 影響

- 節の番号で引けないので、ほかの文書やコードから 140 §6 の節を指せない（指しているのは「§6」だけである）。
- 図だけを見た人が、評価セッションの集約の通知と trace の行を知らず、画像の Observer を `ObserverFactory` が作ると読み違える。
- 画像・trace を変える人が、コードマップからファイルへたどれない。

## 対応方針

- §6 の節に番号を振り直し、`env_step` の節を §6 へ、TempoRL の節を §6 か §7 の指標の説明へ移し、§9 の一覧をつなげる。
- §4 と §5.1 の図に SessionEnd と trace を足し、`ImageObserver` を実物の 2 種類（Train・Learn）と作り手（`ImageProviderFactory`）に直す。画像の Observer の置き場の見直しは [issue-20261123-eac719](issue-20261123-eac719.md) が扱うので、直す順を合わせる。
- §3 に metrics・image・heat_map・gui の行を足す。
- 英訳も同じに直す。コードは変えない。
