## 背景

2026-11-25 の監査（観点 test-gap、範囲 120_metrics_viewer）で見つけた。定点統計（`reports/stats/trend.md`）の「テスト負債」の表は C++ だけで、Java と JavaScript は行数の合計（Java の本体 7,100 行、テスト 13,072 行）しか出していない。そこで、Java の本体のクラスをテストの側から検索し、ロジックを持つクラスはどれも名指しか HTTP API の結合テストで通っていることを確かめたうえで、Playwright のテストだけが通す JavaScript（4,302 行）を関数の単位で見て、本番の呼び手があるのにテストが通さない経路を探した。開発者には質問していない。

ホットスポット補正: `metrics-viewer.js` は 90 日の変更回数が配置の移動の前後で 18 回＋2 回で（`reports/stats/stats.json` の `flow.churn90`）、コードのファイルの上位 1% に入る。urgency を 2 から 3 へ 1 段上げた。

## 事象

- 容量を超えたときの解放: 設計 210（§2.3 の表と §2.8、`docs/design/210_metrics_viewer.jp.md` の 113・216 行）は、詳細 window を「選択中、64 MiB の LRU」で保持し、「容量内で画面に近い順に先読みする」と書く。実装は `DETAIL_CACHE_BYTES`（`metrics-viewer.js:8`）を使い、`DataCache.retainWindows`（556〜573 行）が古い順に捨て、`requestVisibleData` が先読みの前に見積もりを足して超えるなら打ち切る（3706〜3709 行）。
- テストで容量に触れるのは `ComparisonResolutionPlaywrightTest` の 2 か所（80・169 行の `app.cache.detailBytes() <= 64 MiB`）だけである。その素材（`createFixture`）は、4 Run のうち 1 tag だけが 8,192 点で、残り 63 tag は 16 点しか無い。LOD の window は 1 区間 72 byte（summary の 6 列で 36 byte、minMax の 3 点で 36 byte）なので、全部の window を合わせても 1 MB 程度にしかならない。捨てる分岐（`size > DETAIL_CACHE_BYTES`）と先読みを打ち切る `break` は、どのテストでも通らない。検索語 `DETAIL_CACHE`・`retainWindows`・`detailBytes` でテストを引いて確かめた。
- 実際の使い方では容量を超える。2026-11-25 に走っている Montezuma の Run（`run_20261125-154821_mz_n10_sema_s2`）は scalar の tag を 223 個持つ。画面幅から決まる 1,200 区間で 1 系列はおよそ 87 KB なので、4 Run の全 tag（892 系列）で約 77 MB になり、64 MiB（約 67 MB）を超える。
- 先読みを打ち切ったあとの扱い（「容量で遠い graph の先読みを止めた分は、次の Reload まで取り直さない」。210 の 598 行）も、打ち切りが起きないので通らない。
- Copy Name の代替: `NameClipboard.copy`（1974〜1985 行）は、Clipboard API が使えない（`window.isSecureContext` が偽）か拒まれたとき、`copyTextBySelection`（274 行、`document.execCommand("copy")`）へ切り替え、拒まれたあとは API を呼ばない。テスト（`RunListPlaywrightTest` の 806〜842 行、`RunComparisonPlaywrightTest` の 114 行から）は、API が成功する場合だけを通す。`createQueryChannel` の代替（`randomUUID` が無い場合）には専用のテストがある。
- 分割した数列の復号: server の `MetricTraceEncoder` は 250,000 要素ごとに Base64 の文字列を分け、client の `decodeBase64Bytes`（83〜102 行）がつなぐ。テストの復号はどれも先頭の 1 本（`get(0)`）だけを読み、Playwright の素材も 1 本だけを作る。既定の点数上限（`metricsviewer.max-points-per-request` は 500,000）では分割が起きうるが、画面の幅から決まる要求は 1 系列 2 万点に届かず、画面からの要求では起きない。

## 影響

- 容量を超えたときの解放や先読みの停止を壊しても、どのテストも落ちない。壊れ方は「画面に近い window を捨てて取り直しを繰り返す」「捨てずにタブのメモリが増え続ける」のどちらかになり、tag の多い Run を 4 本以上重ねる使い方でだけ現れる。
- LAN の別の端末から http で開くと（localhost でない http はセキュアでない扱いになる）、Copy Name は代替の経路だけを通る。代替が壊れても、開発の端末では気づけない。

## 対応方針

- `DETAIL_CACHE_BYTES` を超える状況を、定数を変えずに作る。`DataCache` に大きな window を直接入れてから `retainWindows` を呼ぶ（近傍の tag を残し、古い順に捨てることを確かめる）か、`page.evaluate` で `windowBytes` の値を大きく見せて、先読みの打ち切りと打ち切ったあとの Reload の扱いを確かめる。本体に試験用の口は足さない。
- Copy Name は、`isSecureContext` が偽の場合と `writeText` が拒む場合の 2 通りを、`addInitScript` で作って確かめる。
- 分割した数列は、`base64ToFloat64Array`・`base64ToFloat32Array` へ 2 本以上の文字列を渡す確認を 1 つ足す。server の側は、`MetricTraceEncoder` に 250,001 要素を渡して 2 本に分かれることを確かめる。
- 描画や取得の速さには触れない。
