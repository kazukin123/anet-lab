## 背景

2026-11-10 の会話で NGU（[PRD924](../../memo/924_intrinsic_reward_novelty_10prd.md)）の公開実装を調べた。公式のコードは見つからず、第三者実装の DI-engine が NGU の設定を MiniGrid（`MiniGrid-DoorKey-16x16-v0`）向けに持っていることを確かめた。開発者から「GridMaze が MiniGrid のようなスパースな報酬の評価に対応していないのはもったいない」「DI-engine との比較評価をやるなら MiniGrid との互換モードも欲しい」との発言があり、起票の指示を受けた。方式や範囲について開発者に質問はしていない。

GridMaze では、[PRD116](../../memo/116_rnd_lifelong_novelty_10prd.md) の Run で RND の bonus が最初の数千 step で 0 になった。観測が位置の 2 値だけで、盤面が固定のためである（PRD116 §6.4・§7）。PRD924 は GridMaze の盤面を観測に入れることを非ゴールにしている（PRD924 §1、2026-10-24 の開発者の方針）。今の GridMaze は、観測を変えずに Agent の側で対策する題材（PRD924 §2.7）でもある。

## 事象

今の GridMaze（[GridMazeEnv.cpp](../../../core/envs/gridmaze1/src/GridMazeEnv.cpp)、[GridMaze.txt](../../../apps/runner/config/GridMaze.txt)）は次のとおり。

- 観測は位置 (x, y) を 0〜1 に正規化した 2 値だけ。
- 行動は上・下・左・右の 4 つで、向きは無い。
- 盤面は既定で 5×5、壁と穴を密度で置く。鍵や扉のような物は無い。既定の `seed_mode = process` では、盤面はプロセスの間ずっと同じ。
- 報酬は既定で goal 1.0・hole −1.0・wall −0.1・step −0.01。どれも設定で変えられる。goal 以外を 0 にすればゴールだけの報酬になるが、goal の報酬は一定で、かかった step 数では変わらない。打ち切りは `max_steps`（既定 100）。

MiniGrid（Farama）の DoorKey は次のとおり（[DoorKey の文書](https://minigrid.farama.org/environments/minigrid/DoorKeyEnv/)、[doorkey.py](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/envs/doorkey.py)、[minigrid_env.py](https://github.com/Farama-Foundation/Minigrid/blob/master/minigrid/minigrid_env.py)、2026-11-10 に確認）。

- 行動は 7 つ。左に向く・右に向く・前進・拾う・置く・扉などを操作する・完了。
- 観測は、向いている方を基準にした 7×7 の部分視野。各マスは（物の種類、色、状態）の 3 値で表す。ほかに、向きとミッションの文がある。
- 報酬は成功で `1 − 0.9 × (step_count / max_steps)`、失敗で 0。
- `max_steps` の既定は 10 × size²（16×16 なら 2,560）。
- 課題は族として並ぶ（Empty・FourRooms・DoorKey・MultiRoom・KeyCorridor など）。盤面は Reset ごとに乱数で作る。

DI-engine の MiniGrid 向け NGU の設定は次のとおり（[minigrid_ngu_config.py](https://github.com/opendilab/DI-engine/blob/main/dizoo/minigrid/config/minigrid_ngu_config.py)、2026-11-10 に取得）。

- `env_id='MiniGrid-DoorKey-16x16-v0'`、収集の env は 8、`max_step=300`、`stop_value=0.96`。
- 観測は平らなベクトルにしている（`obs_shape=2739`）。
- 最後の 0 でない外的報酬を 100 倍する（`last_nonzero_reward_rescale=True`、`last_nonzero_reward_weight=100`）。設定のコメントは、内的報酬に埋もれさせないためと書いている。
- 同じディレクトリに、R2D2・RND（PPO）・ICM（PPO）・PPO・Dreamer の MiniGrid 向けの設定もある。

## 影響

- 探索の手法（RND、PRD924 の NGU）を、難しい探索の題材で安く回せない。GridMaze では新しさがすぐ尽きる。Atari の Montezuma では 1 本が 30M step の規模になる。
- DI-engine などの外部実装が MiniGrid で出した結果と比べられない。MiniGrid の成績は、課題・観測・行動・報酬の式・`max_steps` で決まる。今の GridMaze は、そのどれも MiniGrid と同じではない。
- DI-engine の設定は MiniGrid の既定と違う（`max_step`、最後の外的報酬の倍率、観測の形）。比べるには、MiniGrid の既定と DI-engine の設定のどちらに揃えるかも決める必要がある。

## 対応方針

未定。決めることは次のとおり。

- **置き場所。** GridMaze の別のモードにするか、別の Env にするか。どちらでも GridMaze の既定（位置 2 値の観測、PRD924 §2.7 の題材）は変えない。
- **作り方。** C++ で MiniGrid の課題の一部を作り直すか、Python の MiniGrid を呼ぶ橋渡しを作るか。
  - 作り直す場合、盤面の乱数までは同じにならない。比べられるのは、同じ課題の族での成績の分布になる。
- **範囲。** どの課題の族から始めるか。DI-engine の NGU の設定に合わせるなら DoorKey になる。
- **揃える程度。** 観測・行動・報酬・打ち切りを、どこまで MiniGrid に揃えるか。比べる相手を MiniGrid の既定にするか、DI-engine の設定にするか。
- **成績の指標。** 成功率と MiniGrid の式の return を、Run より先に用意する。
