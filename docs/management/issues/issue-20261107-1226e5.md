## 背景

2026-11-07 の Montezuma の RND の Run で、Train では鍵を取るようになったのに、評価（EvalPanel）では止まる場面があった。どの画面で新しさのボーナスが大きいかを、EvalPanel の Evaluation Trace で 1 step ずつ確かめたいという話が出た。開発者が修正の形を確かめたうえで、起票を指示した（2026-11-07）。

同じ日に、Montezuma の Run 7 本を整理して次の仮説を立てた（2026-11-07）。データを集める Train の方策には ε と τ の揺れが入り、成績を測る Greedy には揺れが入らない。そのため Greedy がたどる状態のうち Train でめったに通らないもの（止まり場）は、Q が関数近似の外挿のまま直らず、そこで止まる。開発者は、DropMerge を含めほかの場面にも同じ影響があるとみている。新しさの値は「Train のデータでどれだけ見たか」の目安になるので、この仮説の検証にも本課題を使うよう、開発者が追記を指示した（2026-11-07）。

PRD116 は、評価での採点と診断を範囲外にしている。eval の runner は学習の入口を呼ばないので、採点の場所が構造上届かないことを理由に挙げ、「評価で内的報酬を見たくなったら 924 の採点の場所の問いで決める」としている（[PRD116](../../memo/116_rnd_lifelong_novelty_10prd.md) の 37 行）。

## 事象

- 内的報酬は、Agent が Train の遷移を受け取って Replay へ渡す入口（`DefaultDQNAgent::UpdateFromBatch`、`core/anet-core/src/default_dqn_agent.cpp` 713〜721 行付近）で、書き込みのロックを取って計算している。eval と EvalPanel はこの入口を呼ばないので、評価の step では内的報酬を計算していない。
- RND の採点（`RndNoveltyEstimator::Estimate`）は、呼ぶたびに誤差の統計を更新する。Taiga 式の統計（`variance_feedback`）では観測の統計も更新する。そのため、評価の観測でそのまま呼ぶと学習用の統計が汚れる。
- Evaluation Trace は、Trace を開いているときに step ごとに Agent の診断の口（`AgentStepDiagnosticsProvider::Observe`）を 1 回呼び、列ごとに `GetScalar(key, lane)` で値を読む（`core/anet-core/src/metrics.cpp` の `StepTraceBuilder::OnTrain`）。DQN はこの口で `approx_priority` を出していて、報酬の換算には学習用の統計を変えない `ScaleWithoutUpdate` を使っている（`default_dqn_agent.cpp` の `CreateStepDiagnosticsProvider`）。内的報酬の鍵は、この口に無い。

## 影響

- 評価で止まる場面や鍵の周りで、新しさのボーナスがどれだけ出ているかを確かめられない。学習側の値は 56_agent_in の群の集計だけで、step ごとには見えない。
- 探索がうまくいかないときに、ボーナスが小さいのか、方策が使えていないのかを切り分けにくい。
- 上の仮説を確かめられない。Greedy が止まった画面が Train のデータに少ない場所かどうかを、step ごとに測る手段が無い。

## 対応方針

Actor 側へ計算を移さず、既存の step 診断の口に、学習用の統計を変えない採点を足す形を基本の案とする。

- RND の推定器に、今の統計で誤差・z・ボーナスを計算するだけの口を足す（`ScaleWithoutUpdate` と同じ考え方）。誤差の統計・観測の統計・predictor の学習は変えない。
- DQN の step 診断の口に、`intrinsic.error`・`intrinsic.z`・`intrinsic.bonus` のような鍵を足す。`GetScalar` で求められたときに初めて計算し、同じ行の中では結果を使い回す。列に入れていなければ計算しない。
- 採点する観測は、学習と同じく `intrinsic.observation` に従う（既定は次の画面、`state` なら行動した画面）。
- 学習側は書き込みのロックで RND を更新するので、Trace 側は読み取りのロックで読む。1 lane の順伝播 2 回で済む見込み（費用は未測定）。
- Evaluation Trace の列の設定（Atari ほか RND を使う env）に列を足す。
- 出す値は「その時点の predictor と統計で計算した、この画面の新しさ」で、学習中に実際に足したボーナスとは時点がずれる。設計文書 212 にこの違いを書く。

仮説の検証での使い方は次のとおり。

- Greedy が止まった画面の誤差（または z）が、Train でよく通る画面より高ければ、止まり場が Train のデータに少ない場所だと言える。Montezuma の止まり場（開始位置付近、ロープの上など）で確かめる。
- RND を使わない Run（DropMerge など）でも、β を 0 にして RND を付ければ、報酬を変えずに「見慣れ度」の物差しとして使える（β を 0 にしても採点と補助学習は止まらない。設計文書 212 の設定表）。DropMerge の NOOP 停滞が同じ形かを、これで確かめる。
- あわせて、Greedy の軌跡で Q の値と実際のその後の割引収益を比べる（Evaluation Trace のダンプと集計で、実装は要らない）。止まり場で Q が大きく上回っていれば、過大評価が直っていない裏付けになる。
- 仮説が当たっていた場合の改善策（Train の一部の lane を評価と同じ方策にする、[PRD924](../../memo/924_intrinsic_reward_novelty_10prd.md) の方策の家族など）は、本課題の範囲に入れない。

学習用の内的報酬を、遷移を集めるとき（Actor 側）に計算して外的報酬と分けて保存する形は、統計の更新順・補助学習の刻み・終端の扱い・Replay の保存形式まで変わるので、本課題の範囲に入れない。[PRD924](../../memo/924_intrinsic_reward_novelty_10prd.md) の §8 の 7「ボーナスの合成と尺度」と 11「保存する報酬」で扱う。
