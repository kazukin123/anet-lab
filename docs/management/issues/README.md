# 課題記録

開発対象システムの課題を **1 課題 1 ファイル**で記録する。工程をまたぐ課題、および「今は解決できない」と判断した事項をここへ積む。

**AI は課題を勝手に書かない。** 工程末と、工程を途中で止めるときに起票の候補を挙げ、開発者が選んだものだけを `anet-create-issue` SKILL が書く（`docs/process/protocol.md` 7 節）。監査の起動と PRD 起票の指示には、その工程で定めた課題記録の作成が含まれる。開発者が直接ファイルを置いてもよい。

**1 枚の表へ追記しないのは、ブランチを分けて作業したときにコンフリクトするため。** ファイルを分ければ、別々のブランチで起票しても衝突しない。

## 書き方

**ID の形は `docs/process/numbering.md`、ファイル名の規則・frontmatter の項目・本文の構成・状態の定義は `anet-create-issue` SKILL が正本である。本書では書き写さない。**

開発者が直接ファイルを置く場合も、同じ形に揃える。既存のファイルを 1 つ開けば形は分かる。

## 一覧を見る

`anet-list-issues` SKILL を使う。状態や工程で絞り込める。

```
/anet-list-issues            本版（次版・解決を除く）
/anet-list-issues 本版       次版と解決を除く
/anet-list-issues PRD        その工程だけ
/anet-list-issues 棚卸し     監理の項目の値と、統合・分割の候補を提案する
/anet-list-issues <課題 ID>  その課題を親に持つ課題（子）だけ
```

依存（`depends`）と WSJF（`wsjf`。効果・時間・リスクを手間で割った値）を目安に並ぶ。前提の課題を待っているもの、外部要因待ち、決着済みは下に並ぶ。WSJF も並びも目安であり、どれから手を付けるかは開発者がそのときの事情で決める。

`INDEX.md` の表のあとの「解決待ち」と「再開候補」は、状態を開発者が決める課題である。解決待ちは AI が済んだと判定した課題で、解決にするかを決める。再開候補は解決したあとに AI が残りを見つけた課題（解決の日付が無い解決の課題も含む）で、戻すかを決める。そのあとの「課題の無い PRD」は、`docs/memo/` 直下の PRD のうち、どの課題の `prd` からも指されないもので、その PRD の仕事の課題を作るか、題材の課題の `prd` に書く。

## 状態を変える

`解決` と `次版` は開発者が決め、`anet-update-issue` SKILL が書く。`解決` は、コミットの準備（`anet-prepare-commit`）が、AI が済んだと判定した課題を候補として持ちかける。解決にするときは、完了の理由（`resolution`）も書く。解決・次版以外への変更は、グリルの開始や実装計画の保存などの工程の出来事に合わせて、AI が承認なしで書く（同 SKILL の「工程の出来事」）。

## 監理の項目を変える

`anet-update-issue` SKILL を使う。WSJF の元になる値（効果・時間・リスク・手間）・依存・親・対象・種類・PRD・分類を変えるときと、棚卸しの提案を採るときである。値の目安は `anet-create-issue` SKILL の「監理の項目」にある。

## 管理外のメモを書く

`priority`（直近の手の付け方のメモ）と `memo`（自由なメモ）と `tags`（横断のテーマ）は、開発者が Obsidian などで課題のファイルを直接書き換える。道具は値を検査せず、一覧と地図にも出さないので、書き換えたあとに一覧を作り直さなくてよい。分類（`domain`）も、開発者が直接書き換えてよい（こちらは一覧に出るので、書き換えたら一覧を作り直す）。統計は `priority` の件数だけを、取ったときの写しとして数える。AI に頼むと、AI はその欄の値だけをファイルで書き換える（`anet-create-issue` SKILL の「管理外のメモ」）。
