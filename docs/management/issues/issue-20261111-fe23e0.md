## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

## 事象

- `BatchEnvSpec`（core/anet-core/include/anet/rl.hpp:305 から）は `num_envs`・`num_threads`・`episode_scope` と `ToJson`・`ToString` だけを持つ。
- `episode_scope == EpisodeScope::PER_LANE ? … : …`（と SHARED の向き）の比較が、テストを除いて 19 か所にある。core/anet-core/src/env.cpp に 12 か所（175、181、203、211、215、237、254、274、285、290、315、397）、trainer.cpp に 4 か所、observers.cpp に 3 か所。
  - 式は 3 種類である。group の数（`PER_LANE ? num_envs : 1`）、group から lane または env_index（`PER_LANE ? group : …`）、lane から group（`SHARED ? 0 : index`）。trainer.cpp の 2 か所（評価の結果の通知、103 付近と 377）は同じ文である。
- 終端の mask を CPU へ移して読む処理が、`ReadBoolMask`（env.cpp:132 から）のほかに、`EpisodeStatsAccumulator::Add`、`EvalSessionEnv::HasAllFreshGroups`、`ThreadPoolDiscreteEnv::Step` に別々にある。`done | truncated` を CPU へ移した結果は `BatchStepResult::GetEpisodeEndMask` が結果ごとに 1 回だけ作って持つが、`Add` と `ThreadPoolDiscreteEnv::Step` はそれを使わずに同じ計算をする。
- `EpisodeStatsAccumulator::Add` は、報酬を足すループを PER_LANE と SHARED で 2 つ書いている。

## 影響

- `BatchEnvSpec` の意味（group が何個あり、どの lane に当たるか）を、使う側が毎回書いている。scope の種類を 1 つ足すと 19 か所を直す。
- 毎 step の経路で、同じ mask の `logical_or` と CPU への移動が 1〜2 回重なっている。

## 対応方針

`BatchEnvSpec` に `GroupCount()`・`LaneOfGroup(group)`（env_index を返すものを含む）・`GroupOfLane(lane)` を置き、使う側はそれを呼ぶ。`Add` と `ThreadPoolDiscreteEnv::Step` は `GetEpisodeEndMask()` を使い、`HasAllFreshGroups` は `ReadBoolMask` を使う。公開ヘッダに関数が増える。`Add` が受ける done・truncated が Bool でない場合に `GetEpisodeEndMask` と同じ結果になるかを先に確かめる。エラーの文言は変えない。
