## 背景

2026-11-23 の定常整備（anet-audit、観点 refactor・範囲 318_rl_core）で見つけた。観点は「特例で支える汎用機構」で、「変更の波及と依存（レイヤ違反）」が付随する。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `trainer.cpp`（churn90 が 17）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- [trainer.cpp](../../../src/core/base/src/trainer.cpp) 971 行の `validate_planned_name("EvalPanel", "EvalPanel")` が、共通基盤の `RunManager` のコンストラクタで名前 "EvalPanel" を予約する。
- その名前で Runner を作るのはアプリで、`RunnerFrame.cpp:553` の `CreateEvalRunner("EvalPanel", ...)` と `EvalPanel.cpp:147` である。同じ名前が、文字列で core とアプリの 2 つの層に書かれている。
- `RunManager` を構築する本番の箇所は `RunnerApp.cpp:445` の 1 か所だけである。
- 予約名で止まることは `trainer_test.cpp` の 1112〜1121 行と 1142〜1143 行が確かめる。

## 影響

アプリ側で評価パネルの Runner の名前を変えても、core の予約は古い名前のまま残る。そのあと設定に同じ名前の評価 tag を書くと、起動時の検査を通り抜け、パネルを初期化するとき（`CreateEvalRunner`）に重複のエラーで落ちる。core の汎用の構築に、特定のアプリの部品の名前が入っている。

## 対応方針

予約する名前を、`RunManager` の構築の入力としてアプリから渡す。構築する箇所は 1 か所なので、今と同じ名前を渡せば挙動は変わらない。issue-20261111-4a6b6f（RunManager のコンストラクタの肥大化と名前の予約の検査が 2 つあること）と一緒に直すと手間が減る。確かめは、トピック別まとめの「変えるときの条件」の RFD0094 §4.1 D3（"Duplicate Env name" などの fail-fast の文言と時機を保つ）による。性能には関わらない（構築時だけ）。
