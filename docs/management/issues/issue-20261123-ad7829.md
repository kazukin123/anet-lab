## 背景

2026-11-23 の定常整備（anet-audit、観点 refactor・範囲 318_rl_core）で見つけた。観点は「先回りの抽象」（sim_step）と「互換・移行の名残」（別名）。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `rl.hpp`（churn90 が 20）と `trainer.cpp`（17）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- `StepCounts::sim_step`（[rl.hpp](../../../src/core/base/include/anet/rl.hpp) 111 行）へ書き込む本番の箇所は無い。`sim_step\s*(\+\+|\+=|=[^=])` で `src` を引くと、当たるのは宣言、`gui.cpp:746` のログの文字列、`gui_test.cpp:216` の指示付き初期化だけである。
- それでも sim_step を読む箇所が並ぶ。`StepAxis::SIM`（rl.hpp 102・121・134・148 行）、`Runner::SIM_STEP`（1337 行）、`RunnerBase::GetScalar`（[trainer.cpp](../../../src/core/base/src/trainer.cpp) 182 行）、字句 `$sim_step`（metrics.cpp 49・85 行）、observers.cpp 1279 行。
- [140](../../design/140_observability.jp.md) §6 は `$sim_step` を JSONL の step へ使う counter として説明する。
- `TrainRunner::GetScalar` の `train_reward`・`train_reward_ema`（trainer.cpp 466・467 行、定数は rl.hpp 1331・1332 行）は、`RunnerBase::GetScalar` の `reward`・`reward_ema`（194・195 行）と同じメンバ `last_reward_`・`reward_ema_` を返す。
- 同梱の設定（`apps/runner/config`）で、鍵として `$sim_step`・`train_reward`・`train_reward_ema` を書く行は無い（`GridMaze_muzero.txt` などの `10_train_reward` は tag の名前で、読む鍵は `episode_return`）。
- 名指しで sim_step を構築するテストは `gui_test.cpp:216` だけで、値が進むことを確かめるテストは無い。

## 影響

`$sim_step` を軸に書いた scalar は、全点が step 0 に並び、エラーも WARN も出ない。別名はどちらが正の名前か読めず、Train では両方が値を返し、Eval では `reward` だけが返すので、同じ設定を Train と Eval で使うと片方だけ値が欠ける。

## 対応方針

SIM の軸と `sim_step` を消すか、進める実装を入れるかを決める。別名はどちらか 1 つにし、140 §6 を合わせる。受け付ける語が減るので、`$sim_step` は構築時の ERROR に、消した別名は値が取れない通知に変わる。これは外から見える変化として明記する。確かめは、トピック別まとめの「変えるときの条件」の RFD0094 §4.1 D3（metrics 出力・定義レコード・WARN・fail-fast の文言と時機。ここでは変わる点を明記する）と RFD0122 §4 D8・§6 A7（RFD0098 の検証資材の短い Run で全 scalar の点を一致させる）による。性能には関わらない（GetScalar は scalar の発火のときだけ呼ばれる）。
