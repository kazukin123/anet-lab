## 背景

現行の checkpoint は Agent、より正確には `DefaultDQNAgent` 固有の archive であり、Run 全体を継続する仕組みではない。

## 事象

対応するPRD: [143_serialize_10prd.md](../../memo/0143_serialize_10rfd.md)
- 2026-11-23 監査（backlog）: checkpoint の形式の定数は、878230ef（RFD0121）の V3 の 2 つを足して 6 つになった（`src/algo/dqn/src/default_dqn_agent.cpp:36-41`）。
- 2026-11-23 監査（backlog）: `docs/memo/done/0000_v2.txt`（「V2対応残件」）に「auto_load_file を agent から trainer に移動」が未完のまま残る。`auto_load_file` は今も `DefaultDQNAgent` と `ImageClsAgent` の設定である（`default_dqn_agent.hpp:87`、`image_cls_agent.cpp:630-632`）。
- 2026-11-23 監査（architecture、範囲 324_dqn）: Agent の口の保存と読み込みが非対称である。`anet::rl::Agent` は `Serializable` を継承し、`Save(OutputArchive&)` と `Load(InputArchive&)` を既定で 0 を返す仮想関数として持つ（`src/core/base/include/anet/rl.hpp:856`〜857 行）。`Save` は DefaultDQN と ImageCls が override し、Runner が呼ぶ（`src/apps/runner/src/RunnerApp.cpp:731`）。`Load` は、DefaultDQN・Rainbow・ImageCls のどれも override せず、本番で Agent の `Load` を呼ぶ箇所も無い（検索語 `agent->Load`・`agent_->Load`。テストを除く）。読み込みは、各 Agent が自分の設定 `auto_load_file` をコンストラクタで見て、private な `LoadNetwork(filename)` で行う（`default_dqn_agent.cpp:573`〜576 行、`image_cls_agent.cpp:631`〜634 行）。

## 影響

このPRDの作業の状態・優先度・順序をissueで管理する。

## 対応方針

対応するPRDと保存済み実装計画に従う。

- 2026-11-11 リファクタリング候補の抽出: Run 全体の保存で触る今の checkpoint の作りに、次の写しがある。(1) DefaultDQNAgent の形式を 4 つの文字列の定数で表している（default_dqn_agent.cpp:30-33。skip の有無と内的報酬の有無の組）。書く側は代入を 2 回重ねて選び（337-339）、読む側は 4 つとの比較から 2 つの bool を作り直し（399-401）、エラー文に 4 つを並べる。任意で保存する部分が 1 つ増えると、定数が 8 つになる。`LoadNetwork` の前半（ファイルを開く→ヘッダを読む→設定の文字列を読む→ログ）は ImageClsAgent::LoadNetwork と同じ手順の写しで、`InputArchive` の作り方とヘッダの読み方が既に違う。読んだ設定の文字列は、どちらもログに出すだけで今の設定と比べない。(2) serialize.hpp の「長さ＋本体」の読み書きが、文字列用（Write 70、Read 165）と torch 用（WriteTorchObject 98、ReadTorchObject 199）の 2 組ある。文字列だけ 1GB の上限があり（173）、書く側は長さの 8 バイトを含めた数を、読む側は本体の長さだけを返すので、同じ中身でも Save と Load の合計が一致しない。空の本体の扱いも違う。Run 全体の形式を決めるときに、形式の表し方（有無の組とヘッダの文字列の変換）と、長さ付きのバイト列の読み書きを 1 組にすることを一緒に決めるとよい。戻り値をそろえると、ログに出る読み込みのバイト数が変わる。確かめ: 定数と関数の位置を今のコードで確かめた。
