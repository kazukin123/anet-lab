## 背景

2026-11-23 の定常整備（anet-audit、観点 refactor・範囲 318_rl_core）で見つけた。観点は「可読性（直観との不一致）」で、「不要コード（届かない return）」が付随する。工程の中で開発者に質問はしていない。

## 事象

- [rl.cpp](../../../src/core/base/src/rl.cpp) 98〜165 行の `StateSpec::ValidateObservation` は bool を返す。失敗の経路 6 つは、どれも `ANET_SYSTEM_ERROR` のあとに `return false` を置く（103・114・124・133・142・160 行）。`ANET_SYSTEM_ERROR` が呼ぶ `ThrowError` は `[[noreturn]]`（`diag.hpp:72`、1660b759）なので、この 6 つの return には届かない。
- 呼び出しは [trainer.cpp](../../../src/core/base/src/trainer.cpp) 551・692 行で、どちらも `ANET_ASSERT(...)` の中である。Env のテスト 23 か所（AtariEnv_test 7、DropMergeEnv_test 14、LunarLanderEnv_test 2）は `CHECK(...)` で受ける。
- 隣の `AssertSanity` は void を返す。

## 影響

名前と戻り値の型から「検査の結果を返す」と読めるが、実際は「失敗すると例外を投げ、成功すると true」である。呼ぶ側が false を見て扱いを分けても、その分岐は動かない。テストの `CHECK` も false の場合を確かめていない。

## 対応方針

void の Assert 系の名前にし、Runner 側は今の `ANET_ASSERT` と同じく Release で実行しない形を保つ。テストは例外を投げないことを確かめる形に替える。確かめは、トピック別まとめの「変えるときの条件」の RFD0122 §4 D8・§6 A7（RFD0098 の検証資材の短い Run で全 scalar の点を一致させる）による。性能には関わらない（Runner の初期化で 1 回）。
