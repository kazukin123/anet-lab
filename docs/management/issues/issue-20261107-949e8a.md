## 背景

2026-11-07 に、RND の探索を Montezuma で比べるため、RAM メトリクスを足した（`apps/runner/config/Atari.txt` の `ram_metric.[montezuma_revenge]`。1 は `room_max`、4 は `x_min`）。足すときに、部屋の広がりと持ち物を数えたかったが、今の畳み方では表せなかった。開発者が、実装の制約で入れられなかった指標を課題として残すよう指示した（2026-11-07）。

番号の枠（今の tag は 1〜4）が足りない件は [PRD108](../../memo/108_metrics_tag_numbering_10prd.md) の D4 で 1〜9 に広がる予定なので、本課題では扱わない。番号を付けない定義を記録しないのは、220 §4.9 の設計どおりである。

## 事象

- 畳み方は `max_seen`・`min_seen`・`inc_count`・`dec_count`・`reach_count:N` の 5 種だけである（`core/envs/atari1/src/AtariEnv.cpp` 306〜325 行、[220 §4.9](../../design/220_atari_env.jp.md)）。1 ゲームで観測した値の種類数を数えるものと、特定のビットの変化を数えるものが無い。
- Montezuma の部屋番号（0x83、開始は 1）について、今使えるのは次の 2 つで、どちらも訪れた部屋の数にならない。
  - `inc_count`（`room_up`）は部屋番号が増えた回数で、行き来でも増える。`mz_nm_rnd_b0p1_s1` では、得点が 400 のまま 1 ゲームで 41 回になったゲームがあり、何部屋を回ったかは分からない。
  - `max_seen`（`room_max`）は最大の番号だけで、開始の左の部屋 0 へ行っても増えない。
- 持ち物（0xC1）はビットごとに意味がある。鍵 2 と剣 32 は確かめ済みで、ほかのビットは OC_Atari の注釈による（鍵 2・4・8・16、剣 32・64、たいまつ 128、アミュレット 1。2026-11-06 の ALE での調査）。今の畳み方では、鍵を取った回数と剣を取った回数を分けられない。
- Burda ら（arXiv 1810.12894、§3.1・Figure 3・4）は、訓練中に見つけた部屋の数を探索の指標にしている。anet の RAM メトリクスはゲームごとの集計なので、Run 全体で見つけた部屋の数（ゲームをまたいだ和集合）も出せない。

## 影響

- RND の腕どうしを、鍵の先へどれだけ広がったかで比べられない。行き来が多いだけの方策と、新しい部屋へ進んだ方策の区別がつかない。
- 公開の結果（見つけた部屋の数）と同じ物差しで比べられない。
- 鍵・剣・たいまつなど、持ち物ごとの取得を数えられず、得点（鍵 100、扉 300 など）から推し量るしかない。

## 対応方針

未定。候補は次のとおり。

- 値の種類数の畳み方（例 `distinct_count`）。1 ゲームで観測した値を 256 ビットの集合に入れ、種類数を返す。Montezuma なら訪れた部屋の数（開始の部屋を含む）になる。レベルをまたぐと部屋番号が重なる点（0xB9 のレベルは未確認）を、定義か文書で扱う。
- ビットを見る畳み方（例 `bit_rise_count:<mask>`）。指定したビットが 0 から 1 になった回数を数え、持ち物を種類ごとに数えられるようにする。
- Run 全体の和集合（訓練中に見つけた部屋の数）は、ゲームごとの集計の外の話になる。metrics 側の集計か trace の後処理のどちらで持つかを、同じ PRD で決めるか別に分ける。
