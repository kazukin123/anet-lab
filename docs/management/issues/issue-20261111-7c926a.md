## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

PRD940（target network の更新の step 軸）は target の更新を触る。

## 事象

- `Network::CopyTo`（core/anet-core/src/nn_impl.cpp:2510-2530）と `Network::SoftCopyTo`（2532-2595）が、どちらも `named_parameters(true)` と `named_buffers(true)` を src と dst で作り、src のキーで dst を引く。個数の検査 `ANET_ASSERT(src.size() == dst.size())` も合わせて 4 か所にある。
- `SoftCopyTo` は、hard update を使わない設定では learn step ごとに呼ばれる（core/anet-core/src/dqn_based_agent.cpp の target の更新）。呼ばれるたびに、名前の文字列つきの一覧を 4 つ作り、名前で引き、Tensor の列を 4 本作る。
- `SoftCopyTo` の中に SN の単位化と `kEps` の定義（2588）もある（SN の式の写しは [issue-20261111-c5c9a7](issue-20261111-c5c9a7.md)）。

## 影響

- 対にする規則（名前で引く、個数を確かめる、浮動小数でない buffer は写す）を変えると、2 つの関数を直す。PRD940 は target の更新を触るので、この上に足すことになる。
- learn step ごとに名前の文字列を作り直している。費用は測っていない。

## 対応方針

「src と dst の parameter・buffer を名前で対にした列を返す」内部の関数 1 つを両方が使う。対の列を持っておいて毎回作り直さない案は、新しく性能のための形を足すことになるので、測ってから決める。parameter をあとから登録する lazy な層（初回の forward で登録する）があると、対の列を持っておく案は成り立たないので、その点も合わせて確かめる。
