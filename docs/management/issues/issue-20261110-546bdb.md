## 背景

PRD918 の実装確認で、追加した設定検査と既存の hidden 検査 `[prd103-config]` を同時に実行した際に見つかった。PRD918 の工程末で、新規課題として記録することを開発者が選んだ。指標名をどちらへ合わせるかという修正方針の判断は、まだ質問していない。

検査の起点となった契約は [PRD103](../../memo/done/103_temporl_reference_alignment_10prd.md)。発見時の実行条件と結果は [PRD918 の実装記録](../../memo/918_eval_schedule_first_fire_20impl.md) の「旧 hidden 検査との同時実行」に残した。本件は PRD918 の初回発火の抑止・offset の変更とは別の既存の不整合で、PRD918 の残件には含めない。

## 事象

- [config_baseline_test.cpp](../../../core/anet-core/src/config_baseline_test.cpp) の `PRD103 skip profiles expose greedy session and padded metric tags` は、`metrics.scalar.[50_agent_skip/19_primary_clip_ratio_ema]` が空でないことを断定する。
- [metrics_scalar.txt](../../../apps/runner/config/metrics_scalar.txt) の現用定義は `metrics.scalar.@skip : [50_agent_skip/19_skip_primary_clip_ratio_ema] ?= skip_primary_clip_ratio @learn $learn_step $update_result $ema` で、検査が要求する `19_primary_clip_ratio_ema` の定義はない。
- GridMaze・LunarLander・Atari・DropMerge の4環境で同じ断定が失敗した。同時実行は2テスト中 PRD918 が成功、PRD103 が失敗し、9867 assertions 中4件が失敗、終了コードは42だった。証跡は `.scratch/prd918/green-config-only.log` と `.scratch/prd918/prd103-config/` の解決結果。
- PRD918 で更新した schedule の断定は成功している。通常の既定スイートと `[shipped_config]` も成功しており、本件は hidden 検査を明示的に選んだときに表面化する。

## 影響

既存の検証資材を使うと、発火スケジュールなどの変更と関係のない失敗が混ざり、設定移行の回帰判定を妨げる。検査の期待と出荷定義の食い違いを残すと、同じ検査を行うたびに切り分けが必要になる。

## 対応方針

PRD103 と現用の指標定義を照合し、期待キーと出荷定義をどちらへそろえるべきかを確認する。その結果に沿って検査または定義を直し、`[prd103-config]` の4環境の断定を通す。PRD918 の初回発火の抑止と offset の契約は変更しない。

確認コマンドは、リポジトリルートの PowerShell で次を使う。

```bash
$env:ANET_PRD918_OUTPUT = Join-Path (Get-Location) '.scratch/prd918/config-check'; $env:ANET_PRD103_OUTPUT = Join-Path (Get-Location) '.scratch/prd918/prd103-config'; & core\anet-core\bin\Debug\anet-core-test.exe '[prd918-config],[prd103-config]' > .scratch\prd918\green-config-only.log 2>&1
```
