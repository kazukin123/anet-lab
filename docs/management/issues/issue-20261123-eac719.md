## 背景

2026-11-23 の定常整備（anet-audit、観点 architecture・範囲 318_rl_core）で見つけた。観点は依存（循環）。ファイルの置き場やライブラリの分け方の提案ではなく（issue-20261103-785e68・RFD0182 が扱った）、依存を一方向にする提案である。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `observers.cpp`（churn90 が 15）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- observers から image を読む: [observers.hpp](../../../src/core/base/include/anet/observers.hpp) 10 行が image.hpp を読み、HeatMapVector（73 行）・TimeHistogram（121 行）・SweepedHeatMap（186 行）・Conv2dVisualization（287 行）の 4 クラスが `ImageProvider`・`ImageData`・`Conv2dVisualizer`（image.hpp 281〜305 行）を使う。HeatMap と TimeFrameMode は heat_map.hpp から来る。
- image から observers を読む: image.cpp 6 行が observers.hpp を読み、`Make*Observer`（169・196・278・337 行）で 4 クラスを作り、`MakeBundle`（622〜634 行）と `CreateImageProvider`（637〜659 行）が Notifier へ付ける。image.hpp 83・97 行には、observers 側にある設定の struct をコメントアウトした写しが残る。
- image.hpp は画像の型と、Notifier・Agent・Runner を受け取る配線（312〜354 行）の両方を持つ。そのため metrics_logger.hpp → heat_map.hpp → image.hpp → rl.hpp とたどって、保存を受け持つ MetricsLogger のヘッダが RL の契約全体を読む。
- 配線する場所も分かれ、metrics.image はアプリ（RunnerApp.cpp 530〜536 行）、scalar・trace・graph は core の RunManager（trainer.cpp 856〜880 行）が配線する。
- 本番で 4 クラスを組み立てるのは image.cpp だけで、SweepedHeatMap だけは HeatMapPanel.cpp 485 行も作る。observers.hpp を読むアプリのファイルは 8 つで、画像の Observer を使うのは HeatMapPanel だけである。
- テストは observers_test.cpp 1520〜1590 行が 4 クラスを直接作り、image_test.cpp 108〜171 行が Manager を作る。

## 影響

画像の種類を 1 つ足すたびに、image と observers の 2 つの module を行き来する。image.hpp や heat_map.hpp を変えると、画像を使わない observers.hpp の利用者（trainer.cpp とアプリの 7 ファイル）もビルドし直しになる。依存が双方向なので、どちらかを切り出すことができない。

## 対応方針

未定。(a) 4 クラスと設定の struct を image の module へ移すか、(b) 作って付ける配線（Factory と Manager）を observers の側へ移し、image.hpp を画像の型だけにするかを決める。配線を RunManager にそろえるかも一緒に決める。どちらでも 140 §3 のコードマップを直す。issue-20261111-d1d12b の群 4（画像の種類の表）と同じ場所を触る。確かめは、トピック別まとめの「変えるときの条件」の RFD0182 §4.1 D24・§6 C3・S3-6（保存した実行体と比べ、全 scalar・設定の記録・WARN と ERROR の行を一致させ、テストのケース数をそろえる）と RFD0122 §4 D8 による。性能には関わらない。
