## 背景

forward から名前付き tensor を外へ出す口を `NetworkForwardCapture` の 1 つにし、`TraceCallback` を無くす。

## 事象

対応するPRD: [170_nn_trace_capture_unification_10prd.md](../../memo/170_nn_trace_capture_unification_10prd.md)

## 影響

このPRDの作業の状態・優先度・順序をissueで管理する。

## 対応方針

対応するPRDと保存済み実装計画に従う。

- 2026-11-11 リファクタリング候補の抽出: PRD170 の題材の capture の経路に、次の持ち回りがある。Forward の経路で、既定と準備済みの切り替え（呼び先の表 `calls`）と capture を、3〜4 層の引数で持ち回っている。`calls` は `NetworkBody::Forward`（nn_impl.cpp:1547）・`NetworkBranch::Execute`（素通し）・`NetworkStruct::Forward`（1265）の 3 層で「null なら既定」になり、`NetworkForwardExecutor::Impl` は表 `body_calls`（2036）とそれを指す `call_table`（2037）の 2 つを持つ。capture は `Network::Forward` → `RunForward`（1956 の引数）→ `NetworkBody::Forward` の引数 → `context.WithCapture(capture)`（1543、1576）と運ばれ、`NetworkForwardContext` 自身が capture を持てるのに Body の入口までは別の引数である。`NetworkBody::Forward` の引数は 5 つ、`RunForward` は 7 つ。capture を入口で context に入れれば、Body の capture の引数を消せる。確かめ: 引数と表の位置を今のコードで確かめた。PRD170 は再グリル中なので、その場でこの追記を拾うかを決める。

## 対応内容

- 2026-11-12 PRD170 の再グリル: グリルを行って暫定の印を外した（確定事項 D1〜D18、受入 A1〜A13、ADR 0072）。2026-11-11 の追記のうち、capture の受け渡しは D10 で取り込んだ（forward の公開の口で Context に入れ、内部の capture の引数を消す）。呼び先の表（`calls`）の受け渡しは直さない。170 を実装すると内部の引数は 3 つと 5 つに減り、残るのは引数 1 つを 3 つの関数が順に渡すことだけで、開発者が必要性は無いと判断した。確かめ: PRD のレビューは OK。[PRD](../../memo/170_nn_trace_capture_unification_10prd.md)

- 2026-11-17 PRD170: forward の名前付き出力を capture に統合し、MakeActionOptions の要求を Runner から Actor へ都度渡す経路へ移行した。要求なしでは nn_trace を作らず、GUI の pane と学習側の有効な Conv2d 画像記録が要求を決める。設計100・110・130・140の日英の契約・図も移行した。確かめ: Debug ビルド、core 通常テスト 1028 件（1027 成功・1 skip）、trace 7 構成と scalar 6 構成の完全一致、GUI の要求経路と画像登録3条件が成功。通常 GUI 一式は変更前後とも同じ既存1件が失敗し、新規失敗は無し。throughput を3巡、GPU allocator を各100 step測定した。実画面と pane 開閉前後の GPU 測定は操作許可 timeout のため未実施として記録した。[実装記録](../../memo/170_nn_trace_capture_unification_20impl.md)
