## 背景

2026-11-25、開発者と、LLM-Wiki の本家（[Karpathy の gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)）と紹介記事（[Zenn](https://zenn.dev/tsurubee/articles/llm-wiki-connecting-knowledge)）を、anet の wiki と比べた。開発者の発言は次のとおり。

- 本家で定義されている Query というオペレーションが、anet には無いのか。
- 本家の定義では、Query の役割として、価値ある回答を query ページにまとめて資産化する。この点は anet ではどうか。
- 紹介記事では、情報を集約する中で、概念ページに「横断的知見」として統合概念が生成される。この点は anet ではどうか。この軸で改善するとしたらどうするか。
- サーベイの結果は、今は wiki にあまり活用できていないようである。由来は区別するとしても、サーベイというか一般事例の結果も引けるようにしたら有用な気がする。

起票の候補を 10 件示し、開発者は、新規の 4 件（質疑の答え、題材をまたぐ知見、外の事例、「今の結論」と目録の長さ）と、見送りを勧めた「問いの記録を正本の新しい種類にする」を、1 件の課題にまとめるよう指示した。前の 3 件は起票するかを質問し（続けてから整理するとの答え）、長さの件は質問していない。「RFD づくりの事例の段で、web より先にサーベイを見る」は、同じ会話でその場で直した（この課題の範囲ではない）。

- 本家の Query は、wiki のページを読んで出典つきで答え、良い答えを新しいページとして wiki に戻せる、というものである。専用の query ページの種類、残す基準、決める人、新しく保つ方法は書かれていない（2026-11-25 に原文を読んで確かめた）。
- 紹介記事は、query ページを wiki のページの 1 種類に挙げる。「横断的知見」は、資料を取り込むたびに既存の資料との共通点・対立点・補完関係を書かせるもので、著者がスキルに足した指示である。書かれた知見の真偽を確かめる方法は記載が無い（同）。
- anet は、資料ごとの要約ページを作らず、「wiki だけにある知見を作らない」を原則にする（[RFD0095](../../memo/done/0095_llm_wiki_10rfd.md) §2・§4.1、[ADR 0056](../../adr/0056-wiki-is-derived-summary-and-readme-keeps-original-analysis.md)）。
- 関係する課題: [issue-20261103-58696c](issue-20261103-58696c.md)（Claude Code の memory の定期整備）、[issue-20261114-fbcbca](issue-20261114-fbcbca.md)（ADR へのたどり方。wiki の引き方の案はこちらに足した）。

## 事象

数は 2026-11-25 の作業ツリーを機械的に数えた目安である。会話の数は、2026-10-19 以降の手元の Claude の会話記録だけで、Codex は入っていない。

**質疑の答えを残す経路**

- wiki の作業に名前があるのは取り込みと点検の 2 つで、問い合わせ（Query）に当たるスキルは無い。[作業の記録](../../wiki/log.md)の種別は `start`・`ingest`・`writeback`・`fix`・`lint` で、質問は記録されない。RFD0095 §2 の対応表は「問い合わせと書き戻し」に当たるものを「PRD づくり、Run 分析」とする。スキルを作らないと決めた記述は、RFD0095 の検索（問い合わせ・クエリ・query）で見つからなかった。
- [AGENTS.md](../../../AGENTS.md) の「wiki(docs/wiki)を引く条件」が wiki を引くとするのは、RFD を起こす・グリルする前、知見を別の Env へ持ち込む前、Run 分析の結論を出す前、既存の契約・構造を変える提案の前である。ふだんの質問は入っていない。
- 実験記録を書いた 11 セッションのうち、書く前に wiki を開いたのは 7 だった。
- RFD にも Run 分析にも当たらない質疑の答えは、一部が Claude Code の memory に入る。memory は wiki の出典にしない（RFD0095 D2）。例: 2026-11-21 に、Run 間のぶれの原因についての開発者の見立てを完走した Run で確かめた答え（Breakout は後半の頭打ちで、Montezuma は突破の時期で分かれる）は、memory にある。実験記録・wiki・RFD を「跳ぶ時期」「突破の時期」「立ち上がり」「頭打ち」などの語で検索して、同じ中身は見つからなかった。memory の値は Run で確かめ直していない。

**題材をまたぐ知見**

- 機構のページは 15 枚・249 項目（「分かっていること」）で、項目の文に題材名を 2 つ以上含むのは 4 項目である。「分かっていないこと」は 32 件で、出典が 2 つ以上なのは 5 件である。
- [wiki の規約](../../wiki/README.md)は、「今の結論」を「分かっていること」の言い換えに限り、「分かっていないこと」に書く問いを、出典に書かれた未解決の問いと出典どうしの食い違いに限る。題材をまたぐ対立点には置き場があるが、共通点と補完には無い。
- つながっていない例（どれも[評価と比較の条件](../../wiki/mechanisms/evaluation.md)の項目）: qbert の TempoRL 分割の full では、Greedy から Q 側の τ だけを乱数にしても 35 本中 33 本が同じ得点だった。Montezuma の 30M の重みでは、ε=0 のまま τ を乱数にすると、400 点以上が 32 ゲーム中 19 から 29 になった。Breakout では、ε=0.01 で見えない群の差が ε=0 で現れた。条件（TempoRL・RND の有無など）は違う。

**サーベイと公開実装の事例**

- [サーベイ](../../../reports/INDEX.md)は 45 本・約 2.1MB で、1 本から wiki に入った項目は中央値 1、30 本は 1 以下である。題材・機構のページの 529 項目のうち、サーベイを出典に持つのは 70 である。
- トピック別まとめの書く節の材料は設計文書・ADR・RFD で、サーベイは入らない。`torchrl_survey_2026-11-20.md`（85KB）は「関係する知見のページなし（ライブラリの設計の調査）」として取り込まれ、RFD・課題・wiki のページから名前で引かれていない。
- RFD づくりの 72 セッションのうち、サーベイの本文を開いたのは 14、web を引いたのは 26（うち web だけが 17）である。
- RFD 190 本が引く論文・公開実装の URL（arXiv・OpenReview・GitHub）は 55 種類で、15 種類は 2 本以上の RFD が引き、24 種類はサーベイに出てこない。「記憶による」と書いた RFD は 5 本ある。
- 機構のページでは、外の事例を指す語が「調査」38・「論文」30・「文献」22・「公開実装」12 とばらばらで、anet の実測と同じ並びに置かれている。
- サーベイの見出し（2 段目と 3 段目）は 1,212 個・約 2.8 万文字である。

**「今の結論」と目録の長さ**

- 規約は「今の結論」を 1〜5 行とするが、行の長さは決めていない。Montezuma's Revenge は 1 行 3,318 文字（37 文）、内的報酬による探索の比較は 1 行 3,313 文字、行動の時間尺度は 6 行 2,905 文字、評価と比較の条件は 1 行 1,847 文字である。
- 目録（`docs/wiki/index.md`、約 32KB）の 46 行のうち 25 行が 200 文字を超え、最長は 2,151 文字である。

## 影響

- 手間をかけて調べた答えが共有されず、同じ調べを繰り返す。memory に入った答えは、Codex と別の環境から読めない。
- 題材をまたぐ見立てが書かれず、確かめる実験の候補にならない。
- サーベイで済む事例を web で調べ直し、記憶で書く。外の事例と anet の実測の区別が、出典のリンク先を見ないと付かない。
- 「今の結論」と目録から要点を先に読めず、RFD づくりの最初に読む量が増える。
- 放置すると、ページと memory が太り、仕分けと書き直しの量が増える。

## 対応方針

未定。案は次のとおり（2026-11-25 の会話で AI が出した案。決定ではない）。

- 質疑の答え: ふだんの質疑と Run 分析に使うスキルを足し、「wiki を引く → 答える → 残すかを 1 問で聞く → 書く → log.md に問いと行き先を 1 行」とする。持ちかけるのは、調べ直しに手間がかかり、次の判断に使う答えだけにする。行き先は、Run の集計や分析なら実験記録、それ以外の調べものなら `reports/` の報告（前例: [metrics_viewer_resolution_investigation_2026-10-10.md](../../../reports/metrics_viewer_resolution_investigation_2026-10-10.md)）、今の正本だけから出る答えなら関係ページの 1 項目、直す話なら課題、判断なら RFD か ADR とし、一度きりの説明は残さない。RFD づくりは今のまま直接読む。
- 問いの記録（質疑の答えの別の形。AI は、上の行き先で足りるかを先に見るとして推さず、開発者が課題に含めることを選んだ）: 正本の新しい種類として `docs/queries/<日付>_<題>.md` を置き、問い・答え・根拠・確かめた日を 10〜30 行で書く。あとから書き換えず、wiki はここを出典にする。失うものは、正本の種類が 1 つ増えること（wiki の規約の材料の集合、点検の道具、実験記録・`reports/` との線引き）である。最初の一手は、上の「Run 間のぶれ」の答えを、この形と実験記録への追記の 2 通りで `.scratch/` に草案にして並べること（memory の値は未確認と書く）。追記で足りるならやめる。
- 題材をまたぐ知見: 「分かっていないこと」に、題材をまたぐ共通点・対立点・補完から出る問いも書けるようにし、つないだ項目と条件の違いを必ず添える。作るのは取り込みのたびではなく点検で、前回から変わった機構のページだけを見て、1 枚 3 件までにする。人が選んだ問いを Run か再集計で確かめ、実験記録か `reports/` に書いてから「分かっていること」に入れる。確かめたものがまとまったら、「現象」の機構のページを作る（規約は現象のページを認めている）。
- 外の事例: 「分かっていること」を「anet の実測」と「外の事例」の小見出しに分け、外の事例には、確かめた日と、原文か解説かを添える。トピック別まとめにも「外の事例」の節を足し、材料にサーベイを加える。外の主張ごとに「一致・逆・条件が違う・anet では未測定」を付け、題材をまたぐ問いの 1 つの型にする。web で分かった事例は、RFD の本文を正本にして「外の事例」へ取り込む。
- 外の事例（先に試す案）: サーベイの章見出しをリンク付きで並べた索引を道具が作り直す。RFD0095 の「索引は目録だけ」と当たる。最初の一手は、索引を `.scratch/` に 1 枚作り、過去の RFD 3 本の事例の問いで引いて、必要な章に当たるかを見ること。2 本で外れたらやめる。
- 「今の結論」と目録の長さ: 会話では案を出していない。
- 題材をまたぐ知見、外の事例、「今の結論」と目録の長さは、同じ wiki の規約の書式を変えるので、RFD を起こすなら 1 本にまとめるのがよさそうである。
