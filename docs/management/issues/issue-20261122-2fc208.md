## 背景

[PRD191](../../memo/0191_rnd_raw_error_and_recent_learning_10rfd.md) の再グリル（2026-11-21〜22）で、AI は、選ばれていないモードの設定が既定と違うときに WARN（のちに INFO）を出す案と、モードをまたいで同じ設定キーを共用する案を示した。開発者は、どちらも退けた。あわせて、設定を、段階ごとのスコープとモード別の名前空間で持つ形を示した（PRD191 §12 の発言 5〜10）。

PRD191 は、RND と補助学習の設定だけをこの形にし（D7、[ADR 0088](../../adr/0088-rnd-config-is-scoped-by-stage-with-per-mode-namespaces.md)）、`rnd` の下の通知だけを無くす（D12）。決まりそのものの見直しは範囲外とし、未決表の U2 に置いた。グリルでは、決まりを見直すかを開発者に問うていない。工程の終わりに起票の候補として示し、開発者が起票を選んだ。

## 事象

- [AGENTS.md](../../../AGENTS.md) の Fail-Fast 原則の表（207 行）は、「ほかの設定で値が使われない」状態の通知を WARN とする。[PRD117](../../memo/0117_warn_policy_and_unread_config_10rfd.md) は、書いた値が今のモードで効かないことを知らせる既存の WARN を、D1 の線引きに当たるものとして残すとした（同 243 行）。
- 開発者は 2026-11-21 に、使わない設定が既定と違うときの WARN は要らず、INFO も要らないと述べた。モードを変えたいだけなのに、関係のない設定まで同時に変える形は想定していない、という理由である（PRD191 の P46）。
- 開発者は同じ日に、有効・無効やモードの値を変えても、ほかの設定の意味がつられて切り替わらないようにし、そうなる場合はモードごとに別の設定キーにすると述べた（PRD191 の P48）。この考え方は、決まりのどこにも書かれていない。
- 表の前文は、通知が知らせる状態からログのレベルを決めると書く。通知を出すかどうかは書いていない。PRD191 は「表は通知を義務づけていない」という読みを置いた（P49）が、これは AI の読みである。
- [実装の品質確認観点](../../quality/impl.md) の「名前の付け方」の 4 は、モードのキーに、何のモードかが分かる名を求め、`skip.mode` を悪い例に挙げる。段階ごとのスコープに `mode` を置き、モードの名前の名前空間にそのモードの設定を置く形（`rnd.error_norm.mode` と `rnd.error_norm.standardize.*`）は書かれていない。PRD191 は、スコープの名が何のモードかを言うという読みを置いて（P61・P62）、この形を RND と補助学習に限って採った。
- 1 つの設定キーが 2 つの関心を束ねる形（PRD191 が分けた `warmup_mode` と `warmup_steps`）を避けることも、決まりに書かれていない。

## 影響

- 設定を足す PRD のグリルで、AI が今の決まりに沿って、使われない設定の WARN や、モードをまたぐ共用のキーを推す。PRD191 のグリルでは、その推奨が続けて退けられ、設定の持ち方を問う選択肢が開発者に伝わらなかった。
- 設定の形の決まりが RND の ADR にしか無い。ほかの設定を同じ形にそろえるときの基準が無い。
- PRD191 を実装すると、RND の設定（`rnd.statistics.mode`、`learn.mode`）と、名前の決まりの例（`skip.mode` は悪い例）が並び、どちらに合わせるかを決まりから読めない。

## 対応方針

未定。決めることは次のとおり。

- 「ほかの設定で値が使われない」状態を知らせるか。知らせないなら、AGENTS.md の表の行、PRD117 の D1、ADR 0071 との関係をどう書くか。
- 段階ごとのスコープとモード別の名前空間の形を、名前の決まりに書くか。書くなら、当てはめる範囲（新しく足す設定だけか、今ある設定もか）と、「名前の付け方」の 4 との関係をどうするか。
- モードで意味・単位・適した値が変わる設定キーをモードごとに分けることと、束ねた設定を関心ごとに分けることを、決まりに書くか。

材料は、PRD191 §12 の発言 5〜10、D7〜D9・D12、ADR 0088 である。

- 2026-11-22 anet-improve（PRD191 の会話の手戻り）: 手戻りの 1 件として、この課題と同じ問題を挙げた。AI が、モードをまたぐ設定キーの共用と、使われない設定への WARN・INFO を、同じグリルの中で 4 回推して退けられた。対策の案として、実装の品質確認観点の「名前の付け方」に「有効フラグやモードで、意味・単位・適した値が変わる設定キーは、モードごとに別のキーにする。1 つのキーに 2 つの関心を束ねない」を足す形を示した。開発者は、この課題で扱うとし、その場では反映しなかった。PRD づくりの手順（`anet-create-prd` の「選択肢の示し方」）の「同じ役の既存の設定キーを流用できるかを比べる」文が、共用の側へ寄ることも材料である。[PRD191](../../memo/0191_rnd_raw_error_and_recent_learning_10rfd.md)

## 対応内容

- 2026-11-22 この場で直す（グリルを経て）: 使われない設定キーの通知の決まりと、設定キーの形の決まりを直した。AGENTS.md の Fail-Fast 原則の表に、選んだモードや意図した休止（有効フラグの偽・間隔 0・schedule の無い評価タグ）のために書いた値が結果を何も変えない設定キーは知らせない行を、ERROR の行と WARN の行の間に足し、WARN の行の「ほかの設定で値が使われない、効き目が弱まる」を「ほかの設定や Run の形との組み合わせで効き目が無くなるか弱まる」に改め、INFO の行の「その参照」を、休止したものをほかの設定（metrics など）が名指す参照に限り、表の前文と、「汎用機構と利用側の責任境界」の WARN してよい構成の文を合わせた。「設定値の扱い」に、使われない側の設定キーも読んで値域を検証し、ほかの設定と突き合わせる検査は使われるときだけ当てる項を足し、すぐ上の項の例を、`rotating.size` と、選んだモードで成り立たない組み合わせを止める形に直した。実装の品質確認観点の「名前の付け方」の 4 に 1 文と、10（モードのスコープと名前空間。沿わないまとまりにキーを足す・変えるときは、まとまりごと移す）・11（関心ごとのキー）を足し、項番 24・69・77 を合わせた。PRD づくりの skill（`anet-create-prd`）の、既存の設定キーの流用を比べる文に、モードや有効フラグを切り替えると意味・単位・適した値が変わる量は別のキーにし、モードによって使う設定キーが変わるときはモードの名前空間に置く推奨を足した。PRD117 と ADR 0071 は書き換えていない。あわせて、CONTEXT.md の `eval_window.rotating.size` を実際のキー `eval_window.rotating_size` に直し、PRD191 の P62・D7 の前例の記述を事実に合わせ、d9499f の事象に決まった判定を足した。確かめ: 実装の品質確認観点の全項目で自己点検し、機械検査（項番 6・7・8・62・76）を通した。`anet-review` は 3 往復めで OK（1 往復めの 5 件と 2 往復めの 1 件を直した）。
- 2026-11-22 ADR を起こした（開発者が候補から選んだ）: 通知の決まりを [ADR 0091](../../adr/0091-config-keys-idle-under-chosen-mode-or-intended-pause-are-range-checked-not-notified.md)、設定キーの形の決まりを [ADR 0092](../../adr/0092-mode-dependent-config-keys-live-in-per-mode-namespaces-under-concern-scopes.md) に記録した。ADR 0071 と ADR 0088 は書き換えていない。確かめ: ADR 2 本で機械検査（項番 7・62・76）を通した。`anet-review` は 2 往復めで OK（1 往復めの 2 件を直した）。
