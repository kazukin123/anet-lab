## 背景

2026-11-12 の PRD170（nn_trace を capture に統合）の再グリルで、Learner の購読の見直し案が出た。PRD170 は別の関心として範囲に入れず、案を課題 24d885（診断指標の群を足すたびに同じ形を繰り返している）の対応内容へ材料として残した（[PRD170](../../memo/0170_nn_trace_capture_unification_10rfd.md) の §8 の 1）。

2026-11-13 の PRD128（DQN 系 Agent まわりのリファクタリング 5 件）の再グリルでも、購読の口を変える別の関心として範囲から外した（[PRD128](../../memo/0128_dqn_agent_refactor_bundle_10rfd.md) の §1.3）。24d885 は PRD128 の実装で解決するので、そのままだと材料が埋もれる。PRD128 の工程の終わりの起票の候補として示し、開発者が記録を選んだ。案の中身について、開発者への質問はしていない。

## 事象

- Learner の診断の購読は、学習を始める前に 1 回、鍵と間隔の一覧として渡される（[trainer.cpp](../../../src/core/base/src/trainer.cpp) の `ConfigureSubscriptions`、[dqn_based_agent.cpp](../../../src/core/base/src/dqn_based_agent.cpp) の `Learner::ConfigureScalarMetricSubscriptions`）。この 1 つの口が、「この Run で使う診断の宣言（準備と開始前の検査に使う）」と、「どの学習の回でどの指標を測るかの要求」の両方を兼ねている。
- 購読の鍵は文字列で、Agent と Learner の 2 層がそれぞれ解釈している。間隔の規則も、読む側（メトリクスの定義）と計算する側（Learner の群ごとの間隔）が別々に持つ。
- `UpdateFromBatch` は 1 回の呼び出しで学習を複数回走らせるので、呼ぶ側は学習の回ごとの要否を決められない。渡す時機を呼び出しごとに変えるだけでは解けず、呼び出しごとの入力にしても中身は「鍵と間隔の一覧」になる（課題 24d885 の対応内容）。
- PRD170 の案は、購読を「開始前の宣言」と「今回の呼び出しで足す要求（`UpdateFromBatchOptions`。Actor の `MakeActionOptions` と対になる）」に役割で分ける形である。
- PRD128 の実装で、probe 用の乱数は Learner が自分で作るようになり（D13）、乱数のための購読の判断は Agent から消える。replay fit と Thompson の方策の組の検査は、Agent の購読の設定に残る。

## 影響

- 診断を足すたびに、鍵の解釈を Agent と Learner の両方で確かめることになり、間隔の規則の食い違いも起きうる。
- PRD096（横軸と間隔の単位）で間隔の単位を変えるとき、間隔の規則を持つ場所が 2 つあるので、両方を直すことになる。
- 今の Run の挙動には効かない。保守と、診断を足すときの手間の問題である。

## 対応方針

未定。PRD170 の §8 の 1 の案（宣言と呼び出しごとの要求に分ける）を出発点に、購読の口を変える要求が出たときに PRD を起こしてグリルする。課題 24d885（PRD128 の D12 の診断の群の共通の型）を先に片づけ、その共通の型の上で考える。
