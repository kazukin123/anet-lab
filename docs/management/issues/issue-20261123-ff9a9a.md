## 背景

2026-11-23 の定常整備（anet-audit、観点 defect・範囲 318_rl_core）で見つけた。分類は例外。コードを読んだ見立てで、実行では確かめていない。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `replay_buffer_impl.cpp`（churn90 が 16）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- [replay_buffer_impl.cpp](../../../src/core/base/src/replay_buffer_impl.cpp) 2329〜2337 行の `PrefetchingReplayBuffer::State::PruneCompletedPushesLocked` は、`front.get(); push_futures.pop_front();` の順に書く。2339〜2345 行の `WaitForQueuedPushesLocked` も `push_futures.front().get(); push_futures.pop_front();` の順である。
- `get()` が worker 側の例外を投げ直すと `pop_front` が飛ばされ、状態を使い終わった future が列の先頭に残る。次にこの列に触る箇所（Sample の中の Prune 2410 行、UpdatePriorities 2486 行、SampleUniqueUniform 2453 行、ProbeSamplingHistory 2464 行、デストラクタ 2370〜2375 行から呼ぶ StopPrefetch 2352 行）は、その future に `wait_for` か `get` を呼ぶ。状態の無い future への呼び出しは、標準では未定義の動作で、MSVC の実装は `future_error`（no_state）を投げると読める（確度は中）。
- 遅らせた Push が例外になるのは、`DefaultReplayBuffer::Push` の fail-fast（episode_start の不一致 1497〜1502 行、decision の形 1508〜1510 行、hint の行数 1524〜1527 行、actor_approx の契約違反 395〜462 行など）のときである。
- `use_rb_prefetch = true` は Atari.txt 813 行・DropMerge.txt 216 行・GridMaze.txt 96 行にある。
- 失敗する Push を prefetch で試すテストは無い（`replay_buffer_test.cpp` の prefetch 系 9 件はどれも正常系）。

## 影響

Atari などの prefetch の構成で Push の fail-fast が worker 側で起きると、次の Sample が元の例外を返して Run が止まる。そのあとアプリを閉じると、`~PrefetchingReplayBuffer` の StopPrefetch が残った future に `get` し、例外がデストラクタ（noexcept）から出て `std::terminate` になる見込みである。元のエラーの報告のあとに異常終了とクラッシュダンプが重なり、原因の切り分けを妨げる。

## 対応方針

future を列から取り出してから（move して pop したあとで）`get` する。2 か所とも同じに直し、投入の順と 1-deep の先読みの契約は変えない。worker の Push を失敗させる特性テスト（2 回目の同期とデストラクタで落ちないこと）を先に足す。確かめは、トピック別まとめの「変えるときの条件」の RFD0014 1.2（Push と Extract の lock を維持する）、RFD0020 の設計判断 5（in-flight を blocking cap で抑えない）、150 §6.1.1・§8（prefetch を消費するときの γ の確定）による。Sample と Push の経路なので、perf-neutral と同 seed の再現性も確かめる（性能の区分は中立。RNG と抽選の順には触れない）。
