## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

PRD919（評価 session の step trace）、[issue-20261107-1226e5](issue-20261107-1226e5.md)（Evaluation Trace で内的報酬を見る）、PRD081（EvalPanel の trace）は、Trace の列を足す。

## 事象

- `StepTraceColumnSpec`（core/anet-core/include/anet/metrics.hpp）は `std::string target` と `std::string display = "value"` を持つ。
- target と display の文字列の比較が、core/anet-core/src/metrics.cpp（149、153、154、168、169、225-228）、core/anet-core/src/gui.cpp（791、797、798 ほか）、apps/runner/src/EvalTracePanel.cpp（58、297、309、310、433、607）の 3 ファイルに散っている。文字列で spec を組み立てる箇所も EvalPanel.cpp とテストにある。
- metrics.cpp:225-228 は、target を EventField へ直す 4 段の三項演算で、lane ごと・列ごとに毎回走る。Parse の時点で値は決まっている。4 つの語に当たらなければ ENV_STEP とみなすので、Parse を通さずに直接作った spec で綴りを誤ると、黙って ENV_STEP として読む。
- 「離散 action の列か」の判定（target が `$action_info` で key が `action`）が 3 か所にある（metrics.cpp:153、gui.cpp:791、EvalTracePanel.cpp:607）。

## 影響

- 取り得る値（target 5 種、display 4 種）が型から読めず、綴りの誤りがコンパイルで止まらない。
- Trace の列を足す PRD919・1226e5・PRD081 は、この文字列の比較の上に足すことになる。display を 1 種足すと 5 か所以上を見直す。

## 対応方針

spec に `EventField` と display の enum（Value・Name・ValueName・Pct）を持たせ、Parse で 1 回だけ決める。エラーの文言に使う語は、enum から語へ戻す関数から引く（語と enum の表は [issue-20261111-645ecc](issue-20261111-645ecc.md) で 1 つにする）。「離散 action の列か」は spec の関数 1 つにまとめる。設定キーと設定の語（`display:pct` など）、エラーの文言は変えない。公開ヘッダの struct のメンバの型が変わる。
