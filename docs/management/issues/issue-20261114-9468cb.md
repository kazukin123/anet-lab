## 背景

PRD127 で、Evaluation Trace に RND の 3 列（`rnd_bonus`・`rnd_err`・`rnd_norm`）を足した。写しを持つ Actor では、定期の Actor の同期（EvalPanel の既定で 10 秒ごと）と同じロックの中で、推定器と β も写す（PRD127 の D4）。PRD127 の §7 の 14 で、その費用を測った。

測定の結果は、PRD127 の U1 の分かれ方では「3 列を `run.@rnd` の既定から外す」側に当たった。開発者は 2026-11-14 に、3 列を既定に残し、写しを減らす直しを別の課題にすると決めた。開発者は、Trace を開いている間の学習の遅れ（通常 RND で −13%）を許容とみている。

## 事象

- KFM の実時間優先＋`run.@rnd`（128 lane、CUDA、Release）で、推定器と β の写しは 1 回 166〜176 ms だった。`run.@rainbow_like`・`run.@rnd_taiga` を重ねた構成では 152〜189 ms だった。PRD127 の見積もり（数ミリ秒）の約 50 倍である（[設計文書 212](../../design/212_rnd_lifelong_novelty.jp.md) の §4.6 の測定表）。
- 写しの時間のほぼ全部が `RndNoveltyEstimator::Clone` だった。
- `Clone` は複製コンストラクタを呼ぶ。複製コンストラクタは target と predictor の network を device の中で複製し、AdamW を作り直す。さらに、観測の統計・誤差の統計・target の特徴の統計・optimizer の状態を stringstream に書いて読み戻す（[intrinsic_rnd.cpp](../../../src/core/base/src/intrinsic_rnd.cpp) の 463〜496 行）。
- 同じ測定で、pane を開いた状態の学習の速さは、閉じた状態より通常 RND で 13%（3,633 → 3,164 exp step/s）、Taiga 式で 6%（249 → 233）遅かった。開いた状態の Observe は 1 回 2.15〜2.25 ms で、うち採点は 1.35〜1.39 ms、行は 1 秒に約 50 行できた。学習の遅れのうち、写しの分と採点の分は分けていない。
- 複製のどの部分（network の複製、optimizer の作り直し、状態の直列化）に時間がかかっているかは、Tracy で分けていない。

## 影響

- Trace を開いている間、10 秒ごとに約 170 ms、定期の同期のロックを持つ時間が延びる。
- pane を開いて写しが無いときも同期が 1 回入って推定器を写し、その間は学習の入口 1 回の終わりを待つ（設計文書 212 の §4.6）。
- 開発者は今の遅れを許容とみているので、困りは小さい。

## 対応方針

未定。

案として、採点（`EstimateWithoutUpdate`）に要らない optimizer とその状態を写さない、読むだけの写しの形がある。ほかに、統計を stringstream を通さずに複製する形もある。先に、複製のどこに時間がかかっているかを Tracy で分ける。
