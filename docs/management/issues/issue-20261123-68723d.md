## 背景

2026-11-23 の定常整備（anet-audit、観点 architecture・範囲 318_rl_core）で見つけた。観点は seam（利用者のいない汎用の口）で、hot path の性能と同じ値の二重持ちが付随する。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `replay_buffer_impl.cpp`（churn90 が 16）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 3 から 5 へ 1 段上げた。

## 事象

- 保存: `DefaultReplayBuffer::Push`（[replay_buffer_impl.cpp](../../../src/core/base/src/replay_buffer_impl.cpp) 1506 行）が `GetInfo()` を丸ごと受け取り、lane ごとに `action_info[b]` を作って（1538 行）Storage へ渡す（1543〜1544 行）。Storage は最初の Push で info の鍵ごとに `[lane, capacity]` の置き場を確保し（543〜550 行）、lane ごとに `copy_` する（556〜558 行）。
- 判断の旗: TempoRL の Actor が info に `decision` を入れる（`src/algo/dqn/src/dqn_actor.cpp` 1731 行）。Push はこの値を step の旗 kDecision として `RecordStep` に渡し（1565 行）、さらに保存先の device の版に差し替えて（1516 行）info の置き場にも書く。3 つの窓の規則が読むのは `GetStepFlags` の kDecision だけである。
- 抽出: info の置き場が空でなければ、行ごとに `RingSliceDict` で切り出し（1337〜1340 行）、`out.info` へ積む（1407〜1409 行）。`ExperienceSamples::To` は info も転送する（rl.hpp 969 行）。DQN の Learner は Sample のたびに `samples.To(device_)` を呼ぶ（dqn_learner.cpp 1714〜1715 行）。
- 本番で `ExperienceSamples::info` を読む箇所は無い（検索語 `samples.info`・`.info.At`・`.info.Get`。dqn_learner の `evaluation.info` は別の型）。共通の Replay を本番で作るのは dqn_learner.cpp 960 行だけで、MuZero は自前の `MuZeroReplayBuffer` が info を読む（muzero_rb.cpp 292〜294 行）。
- Storage から出てくる info を確かめるテストは、unroll のテスト（replay_buffer_test.cpp 3506〜3540 行）だけである。

## 影響

`run.@skip` を有効にした Run（Atari.txt 402 行、DropMerge.txt 491 行、GridMaze.txt 56 行、LunarLander.txt 82 行）では、読まれない値のために、Push で 1 step あたり lane の数（Atari の主構成で 128）の小さな tensor 操作と、Sample で行ごとの切り出しと stack、学習 device への転送が走る。量は測っていない。Actor が info に鍵を 1 つ足すと、Replay のメモリ（capacity × lane）と抽選・転送の量が黙って増える。

## 対応方針

decision の受け渡し（info の鍵。RFD0098 の D11・D13）は今のままにし、Replay が info を保存も抽出もしない形にするか、最小限として decision だけを info の置き場から外すかを決める。前者は unroll のテストと `ExperienceSamples::info` の扱いを決める必要があり、2026-11-10 のリファクタリング候補の洗い出しで見送った 03-C2（共通 Replay の muzero の unroll）に触れる。issue-20261111-d1d12b の群 16（抽出関数）と同じ関数を触る。hot path なので、perf-neutral の確認（交互 3 巡以上）と、skip の有効・無効それぞれで同 seed の全 scalar の一致を確かめる。確かめは、トピック別まとめの「変えるときの条件」の 150 §2・§6.1.1・§8（窓を使わない経路の乱数の消費と sample の列を保ち、通常の転送・prefetch・probe も確かめる）、RFD0098 §5.1・§6 の 11（抽選の分布・item key・PER の ready・lock・index の昇順を変えない）、RFD0128 §5 D16・D18・§6.4（CPU と CUDA の両経路で保存した実行体と比べる）、RFD0104 §5.7・§7 の 1、RFD0014 1.2 による。
