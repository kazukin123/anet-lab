## 背景

2026-11-10〜11 のリファクタリング候補の抽出（C++ の本体を 16 単位に分けて読み、観点は docs/quality/refactor.md による）で見つかった。開発者が候補の一覧から選び、起票を指示した。2026-11-11 に今のコードで場所を確かめ直した。

PRD919（評価 session の step trace）は `MetricsWiring` を、PRD081（EvalPanel の trace）は `CreateEvalRunner` を触る。

## 事象

- `RunManager::RunManager`（core/anet-core/src/trainer.cpp:925-1201）の 1 関数の中に、評価スケジュールの読み取りと検証、seed、Env、Agent、TrainRunner、評価ごとのループ（約 120 行）、メトリクスの配線がある。
- 名前の重複の検査が 2 つあり、エラーの文言 2 つが同じ文である（lambda `validate_planned_name` の trainer.cpp:943-953 と、`EnsureEnvNameAvailable` の 1209-1219）。
- 「definition-only」の数行が同じ文で 2 回ある（trainer.cpp:1108-1116 と 1125-1130 の付近）。
- 関数内の `EvalScheduleConfig`（trainer.cpp:934）に 5 項目を詰め、評価ごとのループで 5 つのローカルへ取り出し直す。
- 「読む → 負なら `ANET_SYSTEM_ERROR`」の範囲検査が同じ形で 5 回ある（974・981・987・1096・1103 の付近）。
- EvalRunner を作る手順（名前の検査 → seed → `CreateBatchEnv` → ログ → `ActorRequest` → 構築 → 登録 → 名前の予約）が、コンストラクタの中と `CreateEvalRunner`（trainer.cpp:1251 から）に 2 回ある。
- コンストラクタの中でしか使わないものがメンバになっている。`metrics_wiring_`（core/anet-core/include/anet/trainer.hpp:290）は 1196 行の代入だけで、作ったあとは誰も触らない。`dormant_eval_tags_`（trainer.hpp:289）も使うのはコンストラクタの中の 3 か所（1113・1127・1197）だけである。
- `RunManager::Config` は run の数項目だけを読み、`run.eval`・`run.eval_schedule` の項目はコンストラクタの本体で 1 つずつ読む。

## 影響

- 評価の設定項目を 1 つ足すと、読み取り・検証・`EvalScheduleConfig`・取り出し・ログの 5 か所を 277 行の中から探して直すことになる。名前の検査の文言を直すと 2 か所を直す。
- `MetricsWiring` は「あとで使うオブジェクト」に見えるが、構築中にしか仕事をしない。読み手が役割を読み違える。

## 対応方針

評価 1 件の設定を 1 つの struct に読み（検証もそこで行う）、コンストラクタは「読む → 名前を予約する → Train 側を作る → 評価ごとに作る → 配線する」の呼び出しだけにする。EvalRunner を作る手順は 1 つの関数にして 2 か所から呼ぶ。`MetricsWiring` は trainer.cpp の中の関数にし、`dormant_eval_tags_` はローカルにする。設定キー・ログの文言・メトリクスへ書く順は変えない。seed を引く順が変わるなら、同じ seed で前後の結果が一致することを確かめる。
