## 背景

2026-11-23 の監査（観点 test-gap、範囲 324_dqn）で見つけた。定点統計（`reports/stats/trend.md` の「テスト負債」）では、324 の本体のファイルはどれも直接か間接に被テストで、未テストの一覧に 324 のファイルは無い。そこで、関数の単位で、本番の呼び手があるのにテストが名指しで通していない経路を探した。開発者には質問していない。

RFD0161（観測パイプライン。課題 [issue-20261103-aa5758](issue-20261103-aa5758.md) が対応中）は、状態スイープの入力の作り方を「並びから関数を作る。1 枚でも長さ 1 の軸を足す」形へ変えると決めている（同書の整合の表の 26 行）。

## 事象

- `src/algo/dqn/src/default_dqn_agent.cpp:797` の `DefaultDQNAgent::GetTensorDictFunction` が返す関数は、`stucker.use_stacker` が true のとき、stack の対象のキー（`stucker.stack_keys` が空なら全部、空でなければ並びにあるものだけ）の観測に `unsqueeze(1)` で長さ 1 の軸を足し、`expand` で `stack_count` まで複製してから、観測の正規化と forward に渡す（818〜839 行）。
- stack の対象を決める判定（`stack_keys` が空なら全部、空でなければ並びにあるものだけ）は、NN の入力の spec を作る `MakeNetworkInputSpec`（591〜612 行）にも同じ形で別に書かれている。
- 本番の呼び手は、Runner の HeatMap（`src/apps/runner/src/HeatMapPanel.cpp:481`）と、メトリクスの画像の状態スイープ（`src/core/base/src/image.cpp:267`）である。出荷設定の既定は `DefaultDQNAgent.@baseline.stucker.use_stacker ?= true`・`stack_count ?= 4`（`apps/runner/config/agent.txt:193`）で、既定の構成ではこの複製の経路を通る。設定の型の既定は `use_stacker = false`（`src/algo/dqn/src/dqn_config.hpp:197`）である。
- `GetTensorDictFunction` を呼ぶ DQN のテスト（`dqn_concrete_test.cpp` の 396・1201・1882・1956・2031・3481 行、`dqn_intrinsic_test.cpp` の 1361・1410・1475 行、`dqn_learner_test.cpp:1383`）は、どれも `stucker.use_stacker` を false にした設定か、stacker を書かない設定（型の既定の false）で呼ぶ。stacker を有効にする fixture（`dqn_fixture_test.hpp` の `MakeNativeStackConfigData`）を使うテストは、Actor の行動選択だけを通し、`GetTensorDictFunction` を呼ばない。検索語 `GetTensorDictFunction` と `use_stacker` でテストを引いて確かめた。Runner の `QValuePanel_test.cpp` は HeatMap の計算（`ComputeQValueHeatMap`）だけを通し、Agent を呼ばない。

## 影響

- 複製する軸（`unsqueeze(1)` の位置）や `stack_keys` の選別を取り違える直しを入れても、どのテストも落ちない。その直しが入ると、既定の構成で状態スイープのメトリクスを有効にした Run は、入力の形が Network の spec と合わずに止まり、HeatMap を開くと forward で止まる。
- RFD0161 の実装は、この経路の入力の作り方を変える。今の振る舞い（stack 対象のキーだけを複製し、対象外のキーは元の rank のまま渡す）を固定するテストが無いと、移行の前後で同じ入力になるかを確かめられない。

## 対応方針

- stacker を有効にした DefaultDQNAgent で `GetTensorDictFunction("policy-net.forward")` を呼び、Network へ渡る入力の形（stack 対象のキーは `(B, stack_count, ...)`、対象外のキーは元の形）と、複製した各 stack の位置が同じ値であることを確かめる特性テストを足す。`stack_keys` が空の場合と、一部のキーだけを並べた場合の 2 通りにする。既存の `MakeNativeStackConfigData` と、Actor のテスト（`DefaultDQNAgent leaves stack_keys exclusions unstacked`）の env spec を使える。
- RFD0161 の実装の前に入れ、実装ではこのテストの期待値を変えずに通すことを確かめに使う。
- hot path ではなく（HeatMap と状態スイープだけが呼ぶ）、乱数も使わないので、性能と同 seed の再現性の確かめは要らない。
