## 背景

2026-11-23 の定常整備（anet-audit、観点 defect・範囲 318_rl_core）で見つけた。分類は境界と例外。工程の中で開発者に質問はしていない。

ホットスポット補正: 直す場所の `observers.cpp`（churn90 が 15）は、2026-11-18 の定点統計でコードのファイルの上位 5%（churn90 が 15 以上）に入るので、`urgency` を 2 から 3 へ 1 段上げた。

## 事象

- ObserverFactory の scalar の節は、`interval`（[observers.cpp](../../../src/core/base/src/observers.cpp) 1435 行）を `std::stoi`、`ema_alpha`（1436 行）と `clip`（1437 行）を `std::stof` で読む。graph の節の `interval`・`step_interval`（1666 行）と `episode_interval`（1668 行）も `std::stoi` である。
- これらは先頭の数だけを読み、残りを捨てる。`interval:1O0`（数字の 0 の代わりに英字の O）は 1、`interval:2.5` は 2、`ema_alpha:0.1x` は 0.1 になる。
- 数で始まらない値は `std::invalid_argument`、桁あふれは `std::out_of_range` になり、文言に設定キーが入らない（例: "invalid stoi argument"）。
- `ParseMetricTokens`（metrics.cpp 63〜71 行）は属性の値を文字列のまま渡し、数かどうかを見ない。
- 範囲の中のほかの数の読み取りは、全体を読み切ったかを確かめる（`tensor_util.cpp` の ParseDevice の `from_chars`、`BatchActionInfo::GetScalar` の rl.cpp 428〜433 行）。
- 数値の属性の誤りを試すテストは、scalar・graph とも無い。

## 影響

`interval:1O0` のような打ち間違いで、記録の間隔が黙って 1（毎回の記録）になり、metrics の量と Run の速さが変わっても、Run は止まらない。数でない値では、Run の構築がどの宣言か分からない文言で止まる。RFD0194 でそろえた「エラーやログが示す設定キーを完全キーにする」契約から外れている。

## 対応方針

全体を読み切る変換（`from_chars` など）にし、読み残しと範囲外を、`config_key` と値を添えた `ANET_SYSTEM_ERROR` にする。正しい値の宣言の挙動は変わらない。確かめは、トピック別まとめの「変えるときの条件」の RFD0094 §4.1 D3（既存の文言と時機を変えない）と、RFD0117 §4 D7（不正な宣言は構築時に止める）による。性能には関わらない（構築時だけ）。graph の節の独自の読み取りは issue-20261103-78c643 が扱っており、一緒に直すと手間が減る。

## 対応内容

- 2026-11-27 scalar・graph の数値属性を末尾まで読み、空値と余分な文字を完全キー付きで拒否する。数字の符号・指数表記も含む 22 アサーションが通った。 [RFD0206 実装メモ](../../memo/0206_core_and_app_small_fixes_20impl.md)
$1
- 2026-11-28 状態を `対応中` から `解決` へ変更。コミットの準備で解決の候補を選んだ。AI 判定は「残件無し」。メトリクス宣言の数値属性を末尾まで読み、空値や余分な文字を完全キー付きで拒否することを確認した。
