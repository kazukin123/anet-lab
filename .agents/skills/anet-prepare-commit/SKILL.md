# ANET Prepare Commit

現在の会話全体と実際の Git 差分を照合し、コミットメッセージ案と対象ファイルを整理する。整理のあと、`コミット対象` と `コミット対象(一部)` の対象の hunk をステージするかをボタン 1 つで聞き、選ばれたときだけステージする。

## 禁止事項

- commit、push を実行しない。
- Git index を変更するのは、「ステージ」の節でユーザーがステージの選択肢を選んだ（プランモードでは、そのあとステージの計画も承認した）直後の、「ステージ」の節の手順による `git add -- <対象>` と部分 stage（`git apply --cached`）だけ。それ以外は読み取り専用の Git コマンドだけを使い、working tree と履歴を変更しない。
- コミットメッセージ規約をこのスキル内へ複製しない。

## 手順

1. `git rev-parse --show-toplevel` でリポジトリルートを特定し、実行時点の `AGENTS.md` を読む。コミットメッセージは、そこに記載された現在の Git・コミットメッセージ規約に従う。
2. 現在の会話全体から、今回コミットしようとしている目的と作業内容を整理する。直近のメッセージだけに限定しない。
3. ユーザーが追加対象、除外対象、分割方法を指定している場合は、その指定を会話からの推定より優先する。指定が矛盾している場合だけ確認する。
4. staged、unstaged、untracked の全変更を調査する。`git status` だけで判断せず、`git diff --cached`、`git diff`、必要な未追跡ファイルの内容を確認する。
5. 各差分が `コミット対象`、`コミット対象(一部)`、`コミット候補`、対象外のどれに当たるか判断する。同じファイル内に複数作業の hunk があるかも確認する。
6. `コミット対象` と `コミット対象(一部)` の全体を表すコミットメッセージ案を、原則として1件作る。`コミット候補` は既定のコミットへ含めない。
7. 複数の意味的な作業単位へ分割できる場合も確認質問は行わず、基本案は1コミットのままとする。分割案が有用なら概要だけを付記する。
8. ユーザーが分割方法を指定している場合は、その単位ごとにコミットメッセージ案と対象ファイルを作る。
9. 「ステージ」の節に従って、出力に続けてステージするかを聞く。

## 分類

### コミット対象

会話全体の作業内容へ直接対応する変更、またはユーザーが明示的に追加した変更を置く。対象ファイルはリポジトリルートからの相対パスで列挙する。

### コミット対象(一部)

同じファイル内に対象作業と対象外作業の hunk が混在する変更を置く。ファイルパスに加えて、含める hunk を識別できる短い要約と、部分 stage が必要な旨を書く。ファイル全体を対象として扱わない。

### コミット候補

内容から現在の作業との関連を推定できるが、対象と断定できない変更を置く。ファイルパスごとに、推定した関連性と根拠を書く。ユーザーが追加を指示しない限り、コミットメッセージ案の対象には含めない。

## 出力

出力は、そのターンの最終メッセージに置く。ステージの問いより前の途中の文にしない。途中の文は、問いの表示や応答の終わりで画面に残らないことがあり、このスキルの主な成果はコミット情報だからである。プランモードでも同じにする。

Git 状態は併記しない。対象外と判断した変更は出力しない。項目が1件もない分類は、`なし` と書かず見出しごと省略する。

`コミット対象` または `コミット対象(一部)` がある場合は、最初に次を出力する。

```markdown
## コミットメッセージ案

<AGENTS.md に従った案>
```

続けて、項目がある分類だけを次の順序で出力する。

```markdown
## コミット対象

- <repo-relative path>

## コミット対象(一部)

- <repo-relative path> — 対象: <hunk の要約>。部分 stage が必要

## コミット候補

- <repo-relative path> — 推定: <関連性と根拠>
```

分割案がある場合だけ、末尾へ次を追加する。個別のコミットメッセージは作らない。

```markdown
## 分割案

- <作業テーマ>: <大まかなファイル群>
```

ユーザーが分割を指示した場合は、各コミット単位について `コミットメッセージ案` と、項目がある対象分類だけを提示する。`コミット候補` がある場合は最後にまとめて提示する。対象外の変更は提示しない。

## ステージ

コミット情報の出力が主で、ステージはそのついでに聞く。`コミット対象` か `コミット対象(一部)` が 1 件以上あれば、出力に続けてステージするかを聞く。人間の判断をボタン 1 つで受けるためである。どちらも無ければ聞かない。

対象は、`コミット対象` のファイル全体と、`コミット対象(一部)` の対象の hunk にする。

- `コミット候補` は含めない。
- 未追跡のファイルの一部は部分 stage できないので含めず、人間が行う。
- ユーザーが分割を指示した場合は、最初のコミット単位の対象だけにする。

問いの文には、ファイル全体と一部のそれぞれの件数と、含めないもの（`コミット候補`、未追跡のファイルの一部）と、commit はしないことを書く。選択肢は「ステージする」を先頭に、「しない」を次に置く。問いと、コマンドの実行承認は別のものである。実行承認の画面が出るかどうかに依らず問いを出し、実行承認の画面を問いの代わりにしない。

Claude Code は、次のうち使える最初の方法で聞く。どの方法でも、問いの前に出力を途中の文として書かない。

1. `mcp__ccd_turn__wrap_up` があれば、その `ask` と `actions` で聞き、出力を最終メッセージにする。このツールは Claude デスクトップアプリが渡すもので、最終メッセージの下に問いとボタンの枠を出す。押したボタンのラベルが次のメッセージで届く。ツールの結果が「枠が見えないかもしれない」と返したときだけ、最終メッセージの末尾にも問いと選択肢を 1 行で書く。Remote Control などの環境の名前で、このツールを省かない。
2. `mcp__ccd_turn__wrap_up` が無ければ、`AskUserQuestion` で聞く。出力は、「ステージする」の選択肢の `preview` に載せる。答えのあとの最終メッセージにも出力を載せる。選択肢が返らなかったとき（No preference など）は実行せず、最終メッセージの末尾に問いと選択肢を 1 行で書く。
3. どちらも無ければ、出力を最終メッセージにし、その末尾に問いと選択肢を 1 行で書く。

Codex は、先に `request_user_input_async` で聞き、そのあと出力を最終メッセージとして書いて応答を終える。この道具は答えを待たずに戻るので、出力が最後に残る。答えは次のメッセージで届く。

プランモードでも、最初の応答は上と同じにし、計画を出さない。

「ステージする」が返ったら、実行の前に、いまプランモードかを確かめる。そのうえで次のどちらか 1 つだけを行う。

- プランモードなら、まだ実行しない。index に触らず、ステージだけを、コミット情報のあとの別の段として計画にする。計画には対象の一覧（一部は対象の hunk の要約つき）と「ステージする。commit はしない」だけを書き、コミットメッセージ案は再掲しない。Claude Code は ExitPlanMode で出し、承認されたら聞き直さずに実行する。Codex は計画を出して終え、計画の実行に切り替わったら聞き直さずに実行する。
- プランモードでなければ、そのまま実行する。

実行は、ファイル全体、部分 stage の順にする。

ファイル全体は `git add -- <path> ...` で、`コミット対象` のパスを 1 つずつ明示する。`-A`、`-u`、`.` は使わない。パスは引用符で囲む。

部分 stage は、`git add -p` が対話式で使えないので、対象の hunk だけのパッチを index に当てる。`コミット対象(一部)` の 1 ファイルごとに次を行う。

1. `git diff --no-color --no-ext-diff -- <path>` の出力を、そのままパッチとして一時ファイルに保存する。置き場は Git が追跡しない場所にする（Claude Code はスクラッチパッド、Codex は `.scratch/anet-prepare-commit/`）。パッチを手で打ち直さない。空白や改行が変わると当たらない。
2. パッチを対象の分だけに削る。対象を含まない hunk は消す。対象と対象外が混じる hunk では、対象外の `+` 行を消し、対象外の `-` 行は先頭の `-` を空白に変えて文脈の行にする。`diff --git`・`index`・`---`・`+++` の行と、残す hunk の `@@` の行はそのまま残す。
3. `git apply --cached --recount --check <パッチ>` で当たることを確かめてから、`git apply --cached --recount <パッチ>` で当てる。working tree は変わらない。
4. `git diff --cached -- <path>` に対象だけが入り、`git diff -- <path>` に対象外が残っていることを確かめる。

終わったら `git diff --cached --name-status` の結果が `コミット対象` と `コミット対象(一部)` のファイルと一致することを確かめ、一致した旨か差を短く知らせる。commit は人間が行う。

- 答えが自由入力で対象の追加・除外を含むなら、反映した一覧を示して実行する。
- 「しない」か、ステージと関係の無い答え（質問や別の話）なら、実行せずにその中身へ応じる。
- `git add` が失敗したら、index を直そうとせず、失敗の出力をそのまま知らせる。
- 部分 stage の `--check` が通らなければ、そのファイルは当てずに人間へ回し、理由を知らせる。当てたあとに対象外が入っていたら、index を直そうとせず、そのまま知らせる。

## 失敗時

- Git リポジトリでない場合は、コミット案を作れない理由を返す。
- 対象となる実差分がない場合は、メッセージやファイルを捏造せず、見出しを使わずに `コミット対象はありません。` とだけ返す。ステージも聞かない。
- 明示されたファイルに差分がない場合は対象へ追加せず、その事実を短く知らせる。
