# 課題の起票

開発対象システムの課題を **1 課題 1 ファイル**で起票する。

## 出力先とファイル名

| 項目 | 内容 |
| --- | --- |
| 出力先 | `docs/management/issues/`（`docs/process/registry.md` の成果物キー `issue-record`） |
| ファイル名 | 発番で得た ID に `.md` を付けたもの |

## 起票の手順

1. `docs/process/registry.md` から成果物キー `issue-record` の行を引き、出力先を確認する（`Read`）
2. `docs/process/numbering.md` の手順で、接頭辞 `issue` の **ID を得る**（`Bash`）
3. 出力先に既存の `issue-*.md` があるかを確かめる。**無ければ出力先ごと作る**（`Glob`）
4. ID に `.md` を付けた名前で、下のテンプレートに従って 1 ファイル書く（`Write`）
5. 起票したファイル名を呼び出し元へ返す

## テンプレート

```markdown
---
id: issue-YYYYMMDD-xxxxxx
title: <一行で言い切る。ファイルを開かずに何の課題か分かること>
status: 未着手
raised: YYYY-MM-DD
phase: <PRD / 実装 / 監査 / ハーネス保守 / その他>
scope: <影響範囲。どの成果物・どの機能に及ぶか>
kind: <成果物 / ハーネス>
area: []
type: <不具合 / ずれ / 改善 / 案 / 調査 / 索引>
ai_judge:
ai_judged:
docs: []
priority: <高 / 中 / 低>
depends: []
parent:
value: <1 / 2 / 3 / 5 / 8 / 13>
urgency: <1 / 2 / 3 / 5 / 8 / 13>
risk: <1 / 2 / 3 / 5 / 8 / 13>
size: <1 / 2 / 3 / 5 / 8 / 13>
wsjf: <（value ＋ urgency ＋ risk）÷ size>
resolved:
---

## 背景

<なぜこの課題が出てきたか。前提となる状況>

## 事象

<何が起きているか。観測できた事実だけを書く>

## 影響

<それによって何が困るか。放置した場合に何が起きるか>

## 対応方針

<どう対応するつもりか。未定なら「未定」と書く>

## 対応内容

<実際に行ったこと。起票時は空でよい>
```

## 各項目の書き方

| 項目 | 指針 |
| --- | --- |
| `title` | 一覧で読んで判別できること。「エラーが出る」のような曖昧な表現を避ける |
| `status` | 下の状態の定義から選ぶ |
| `raised` | 起票日。取得した現在時刻の日付部分 |
| `phase` | どの工程で見つかったか |
| `scope` | 影響が及ぶ範囲。不明なら「調査中」 |
| `kind` | 何についての課題か。下の「監理の項目」の定義から選ぶ |
| `area` | `reports/tools/categories.json` の `categories` にある key の並び。先頭が主なカテゴリ。当たらなければ `[]`。アプリケーション自身の key も使える |
| `type` | 不具合＝現行契約どおりに動かない、ずれ＝文書・規約と実物の食い違い、改善＝振る舞いを変えない作りの直し、案＝新しい振る舞い、調査＝測る・調べる、索引＝対応文書の仕事の単位として子を束ねる |
| `ai_judge` | 残っている / 直った見込み / 判断できない / 実装済み。空は未確認。`実装済み` は PRD の索引 issue に使い、題材の課題には `直った見込み` を使う |
| `ai_judged` | AI が判定した日付。未確認なら空。AI の自発的な更新は `anet-update-issue` の「判定」だけを使う |
| `docs` | 対応する指示・設計文書の repo 相対パスの並び。実在するファイルだけを書く。無ければ `[]`。PRD は `docs/memo/**/*_10prd.md` |
| `priority` | 下の「監理の項目」の定義から選ぶ。起票時の見立てでよく、棚卸し（`anet-list-issues`）で見直す |
| `depends` | 先に解決しないと直せない、または直し方が決まらない課題の ID を、`[issue-…, issue-…]` の形で並べる。無ければ `[]` |
| `parent` | 親の課題の ID（下の「分け方」）。無ければ空 |
| `value` `urgency` `risk` `size` | 下の「監理の項目」の目安から選ぶ。`priority` と同じく起票時の見立てでよく、棚卸しで見直す |
| `wsjf` | `value` `urgency` `risk` `size` から計算した値を書く。目分量で書かない |
| `resolved` | 解決したときだけ日付を書く。起票時は空 |
| 背景 | 前提となる状況。読み手が経緯を知らなくても事象を理解できること。工程の中で見つかった事項は、開発者に質問したかを事実どおりに書く（候補の根拠から引き継ぐ。質問していないのに「質疑で決まらず」と書かない） |
| 事象 / 影響 | **必ず分けて書く。** 原因が未特定でも起票してよい |
| 対応方針 | これからどうするか。未定なら「未定」 |
| 対応内容 | 実際に行ったこと。**起票時は空**。対応した工程が、このファイルへ直接追記する（いつ書くかは各工程の手順による）。前の工程が書いた行は書き換えない。今回の工程が書いた行は、完了を報告するまで直してよく、直しを戻したら消す。形は `- YYYY-MM-DD <PRD の番号か工程>: <この課題について行ったこと>。確かめ: <結果>。[PRD](…)・[実装記録](…)` とし、当たらない要素は省く。コミットのハッシュは書かない（書く時点でまだ無い） |

## 状態の定義

| 状態 | 意味 |
| --- | --- |
| `未着手` | 起票のみ |
| `調査中` | 原因や影響を調べている |
| `対応中` | 解決方法が決まり作業している |
| `中断中` | 着手して一部を済ませたが、手を止めている。外部要因を待っているのではない（外部要因なら `保留`）。**再開すれば本版で対応する** |
| `保留` | 外部要因待ち（実働環境・他部門の判断など）。**条件が整えば本版で対応する** |
| `次版` | **当面は扱わないと決めた。** 外部要因待ちではなく、開発者が意図して先送りした状態 |
| `解決` | 対応完了。`resolved` に日付を記入する |

## 監理の項目

どの課題から手を付けるかを考えるための項目である。**`priority` と `wsjf` は目安であり、作業の順を決めるものではない。** どれから手を付けるかは、開発者がそのときの事情（担当、時期、ほかの作業）で決める。一覧での並べ方は `anet-list-issues` が定める。 値を変えるのは `anet-update-issue` で、開発者の指示（棚卸しの提案を採ることを含む）があるときだけである。

| 項目 | 値 | 意味 |
| --- | --- | --- |
| `kind` | `成果物` | フレームワーク・アプリ・設定・設計文書についての課題 |
| | `ハーネス` | AGENTS.md・skill・品質確認観点・プロセス・エージェント定義についての課題 |
| `priority` | `高` | 放置すると、工程が止まる、誤った成果物ができる、または配布・リリースができない（種別が `ハーネス` ならハーネスの配布、`成果物` なら開発対象システムのリリースや引き渡し）。例: 主要な流れが動かない、レビューが収束しない、ハーネスの再配布の可否が決まっていない |
| | `中` | 手間や費用が増えるが、工程は進められる |
| | `低` | 記述の整合や表記など、放置しても工程の結果が変わらない |
| `depends` | 課題 ID の並び | 先に片づける課題。これらの状態が `解決` でない間、この課題は一覧で「待ち」として示す。**依存は循環させない** |
| `parent` | 課題 ID | この課題を束ねる親。親は子を束ねるだけで、直すのは子である。**親子の対応は子の `parent` だけで持ち、親の本文には書かない**（子の一覧は `anet-list-issues` に親の ID を渡して引く） |
| `value` `urgency` `risk` `size` `wsjf` | 下の「WSJF」 | 効果・時間・リスク・手間と、そこから計算した値 |

`priority` は効果だけから見た目安であり、手間や期日を含まない。並べるときは `wsjf` を使う。

anet の「本版」は今の開発で扱うこと、「次版」は当面は扱わないことを表す。版で区切って開発しているという意味ではない。`area`・`type`・`docs` も監理の項目で、起票後は開発者の指示により `anet-update-issue` が変える。

### WSJF

`wsjf` は WSJF（Weighted Shortest Job First）の値である。遅らせたときに失うもの（`value` ＋ `urgency` ＋ `risk`）を、直す手間（`size`）で割る。**大きいほど、先に片づける値打ちがある。** 元になる 4 つの値は 1・2・3・5・8・13 から選ぶ。間の値は使わない。見立ての細かさに見合わないためである。

| 項目 | 何を見るか | 目安 |
| --- | --- | --- |
| `value` | 効果。直したときに得られるもの（成果物の品質、開発の時間と費用、作業の効率。種別が `ハーネス` ならハーネス自体の開発の効率も） | 13 配布・リリースや稼働ができない ／ 8 毎回の実行で品質か時間に大きく効く ／ 5 目に見えて効く ／ 3 少し効く ／ 2 わずか ／ 1 体裁 |
| `urgency` | 時間。遅らせるほど高くつくか | 13 決まった期日（配布・リリース・引き渡し・試行など）の前に要る ／ 8 次の実行で毎回当たる、または遅らせるほど直す量が増える ／ 5 使い始めると当たる（ハーネスならそれを使う開発者、開発対象システムなら利用者） ／ 3 いずれ当たる ／ 2 当たる場面が限られる ／ 1 急がない |
| `risk` | リスク・機会。危険・取り返しがつかないか、ほかの課題の前提になるか | 13 権利・情報の漏れ ／ 8 誤った成果物が気づかれずに残る ／ 5 ほかの課題の `depends` に挙がっている、または監査や保護に効く ／ 3 ほかの課題の前提になる（`depends` にはまだ挙がっていない） ／ 2 少しある ／ 1 無い |
| `size` | 手間。直す材料（実測・工程を動かした結果など）が揃っていなければ重くする | 1 文書の数行 ／ 2 小さな変更 ／ 3 1 か所の変更とレビュー（成果物 1 つ、または SKILL・Agent 1 本） ／ 5 複数の成果物・資材の変更と判断 ／ 8 設計を含む大きな変更 ／ 13 外部の判断や大量の作業 |
| `wsjf` | （`value` ＋ `urgency` ＋ `risk`）÷ `size` | 小数第 2 位を四捨五入し、小数 1 桁で書く |

- **`urgency` は予定で変わる。** 期日が決まったり動いたりしたら、棚卸しで見直す
- 手間が 1 の課題は値が大きくなりやすい。文書の数行の直しなどは、まとめて片づけるとよい
- 状態が `次版` と `解決` の課題は、5 つとも空でよい

## 分け方

**1 課題は、1 つの判断で閉じられる問題とする。** 直し方の方針が 1 つに決まる単位であり、症状の数では分けない。

| 場合 | 扱い |
| --- | --- |
| 同じ原因で、直す場所も同じ | **新しく起票せず、既存の課題へ追記する。** 工程を動かして見つかった事例・実測・新しい根拠もここに当たる |
| 直す時期が違う（本版／次版）、判断の前提が違う、別々に直せる | 分ける |
| 決めることが 3 つ以上あり、それぞれ別々に決めて直せる | 親と子に分ける。子の `parent` に親の ID を書く |
| 片方を直さないと、もう片方を直せない、または直し方が決まらない | 分けたうえで、後のほうの `depends` に前のほうを書く |

工程末の候補で「新規」か「既存へ追記」かを決めるときも、この表による（`docs/process/protocol.md` 7 節）。

## いつ起票するか

**起票する時機は `docs/process/protocol.md` 7 節による。**

要点だけ再掲する。**本 SKILL が呼ばれるのは、開発者が採用を決めたあとである。**

| 呼ばれ方 | |
| --- | --- |
| 工程末 | 候補を提示し、**開発者が選んだものについて**本 SKILL が呼ばれる |
| 工程の途中で止まるとき | 上流の成果物の食い違いや誤りで止まるときは、候補を提示し、開発者が選んだものについて呼ばれる（`docs/process/protocol.md` 5 節） |
| 開発者の指示 | 候補の提示を省いて直接呼ばれる |

**自分の判断で書き始めないこと。** 候補の挙げ方と判定は `docs/process/protocol.md` 7 節が定める。`anet-audit` の起動（housekeeping の了承を含む）は新しい指摘を記録する指示とみなす。PRD 起票の指示には索引 issue の作成が含まれる。

## 起票の指針

- 原因が分からなくても書いてよい。`status` を `調査中` にする
- 課題から PRD を起こすときは `anet-create-prd` に ID を渡す。統合・分割は、開発者の指示で本 skill と `anet-update-issue` が記録する
- **1 ファイルに 1 課題だけ書く。** 関連する課題でもファイルを分け、本文で相互に参照する（親子の対応は除く。子の `parent` だけで持つ）。単位は「分け方」による
