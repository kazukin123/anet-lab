# ANET Improve

この会話で起きた手戻りを拾い、なぜ今のハーネスで防げなかったかを分けて、改善策の候補を示す。ユーザーが選んだものをその場で反映し、確かめて止まる。

動くのは、ユーザーが `/anet-improve` か `$anet-improve` で呼んだときと、`anet-create-prd`・`implement-prd-with-docs` の完了報告で、この skill の候補を選んだときだけである。

ハーネスは、AI エージェントが読んで従う決まりと手順である。直す先は次に限る。

- `AGENTS.md`
- `docs/quality/*.md`（品質確認観点）と `docs/process/*.md`（プロセス契約とレジストリ）
- `.agents/skills/` と `.claude/skills/`（同じ内容の 2 つのコピー）
- `.claude/agents/` と `.codex/agents/`（エージェント定義）

## 禁止事項

- ハーネスの外（wiki、`CONTEXT.md`、`docs/design/`、ADR、コード、設定）は直さない。手戻りの原因がそこにあると分かったら、報告に書く。ただし、8 の台帳の作り直し（`build`）が書き換える `docs/wiki/` の地図の「台帳の指摘」の区画は、台帳から作る一覧として扱い、この禁止に当たらない。
- git の書き込み操作をしない。
- 作業領域の外にある会話の履歴（会話の記録ファイル）を読まない。作業の正本ではなく、指示を取り違えるおそれがあるためである。
- 覚えていないことを推測で埋めない。
- 書く内容に、ほかのリポジトリ・会社・個人の情報を入れない。このリポジトリは公開される。
- ユーザーへの頼み方の提案を候補にしない。直すのはハーネスである。
- [プロセス契約](../../../docs/process/protocol.md) は、3.3 節と、手戻りの原因として当たる節（2 で確かめる節と、6 で直す節）だけを読む。全体は読まない。大きいためである。
- ユーザーに示す文は、プロセス契約の 3.3 節（見出し `### 3.3 開発者へ提示する文言` から、次の `## 4.` の見出しの前まで）に従う。

## 1. 材料を集める

| 材料 | 見るもの |
| --- | --- |
| この会話のやり取り（覚えている範囲） | レビューの指摘、ユーザーの訂正・差し戻し・不満、やり直した作業、取り違え、ツールとコマンドの失敗 |
| この会話で保存したレビュー応答の原文（`.scratch/prdNNN/review-*.md`、`.scratch/review/review-*.md`） | 指摘の 1 件ずつの中身 |
| この会話で変えたファイルと、その差分 | 手戻りの前後で、何をどう直したか |
| この会話で書いた・直した feedback memory（Claude Code だけ） | ユーザーの訂正の記録 |
| 台帳 `reports/registry/findings.jsonl` のうち、`"lens": "process"` の行（状態を問わない）。1 行 1 件なので、検索で引く（例: `rg '"lens": "process"' reports/registry/findings.jsonl`） | 前にも出た問題。初出（`first_seen`）、最終確認日（`last_seen`）、状態（`status`）、履歴（`history`） |

- 同じ会話で 2 回目以降に起動されたときは、この会話で書いた前回の記録（8 の置き場）より後だけを見る。
- 会話が圧縮されて覚えていない部分は、「覚えていないこと」として、4 の一覧の末尾に書く。
- 手戻りが無ければ、その旨を示して止まる。記録も書かない。

## 2. 問題に分ける

同じ原因から出た手戻りを 1 件にまとめ、「問題」とする。レビューで拾えて直した指摘も、問題に数える。書く側が防げたものを防ぐと、レビューの往復が減るためである。

問題ごとに、当たる決まりと手順を読んで確かめてから、なぜ防げなかったかを次の 6 つに分ける。分類から、対策の種類と置き場が決まる。

| 分類 | 当てはまるとき | 対策の種類 | 置き場 |
| --- | --- | --- | --- |
| 決まりが無い | 守ることが、どこにも書かれていない | 規約を足し、観点に項目を足す | 原則は `AGENTS.md`、作業の種類でだけ要る細則は観点の節の「規約」。項目は `docs/quality/` の該当節 |
| 読まれなかった | 決まりはあるが、書く前・作業の前に読まれなかった | 読む導線を足す | `AGENTS.md` の「作業ごとに読むもの」、skill の読む段 |
| 曖昧 | 決まりを読んだが、読みが割れた | 文言を直す、例を足す | その規約の本文 |
| 点検で見落とした | 決まりがあり読んでもいたが、書いたあとの点検で拾えなかった | 観点の項目か、機械検査を足す | `docs/quality/` |
| 進め方の抜け | 工程の手順（質疑、起草、実装、レビューの出し方など）に段が無い | 手順を足す | 該当の skill |
| 1 回限り | 一時的な失敗や、ほかの場面では起きない事情 | 候補にしない | — |

- 新しい規約を足す前に、既存の規約で防げたかを確かめる。「読まれなかった」「曖昧」に当たるなら、規約は増やさない。
- 規約の本文を持つのは、`AGENTS.md`（原則）と、観点の節の「規約」（細則）だけである。工程の手順は skill が持つ。観点の項目は、規約か手順を根拠として指す。
- `docs/process/protocol.md` と `.claude/agents/an-review.md` は、プロジェクトに依らない文面に保つ（[ADR 0049](../../../docs/adr/0049-process-contract-kept-project-neutral-anet-specifics-in-registry-and-viewpoints.md)）。anet 固有のことは、`docs/process/registry.md` か観点へ置く。

## 3. 対策の候補を作る

問題ごとに、対策を 3 つまで作る。1 つの対策が、2 つ以上の問題に効いてよい。

| 欄 | 書くこと |
| --- | --- |
| 記号 | A、B、C…。1 回の起動の中で通しで振る |
| 中身 | 足す・直す文の要旨 |
| 置き場 | ファイルと節 |
| 効く問題 | 問題の番号 |
| 費用 | 毎回読む量が増えるか（`AGENTS.md` は、すべての作業で読む）、レビューの時間が増えるか（観点の項目）、問いの数が増えるか |
| 推し | 推す対策に ★ を付ける。同じ効き目なら、毎回読む量とレビューの時間が増えないものを推す |
| PRD が要る | 次のどれかに当たる対策に、印を付ける。新しいファイルとしてスクリプト・skill・エージェントを足すもの、既存の ADR の判断と食い違うもの、工程の順序を組み替えるもの。品質確認観点の検査の表に 1 行のコマンドを足すのは、これに当たらない |

台帳に同じ問題があれば、「前回も出た」と、初出の日付、今の状態、履歴にある再発の回数を添える。前回に採らなかった問題が再び起きたことは、推しの理由に足す。

## 4. 全体の一覧を示す

次の順で示す。

1. 問題の表: 番号、何が起きたか、分類、なぜ防げなかったか、対策（記号と短い名前。★ と「PRD が要る」の印を付ける）、前回も出たか。影響の大きい順に、すべて並べる。
2. 対策の表: 記号、中身、置き場、効く問題、費用、PRD が要るか。
3. 見送り（1 回限り）: 1 件ずつ、何が起きたかと、候補にしない理由。ユーザーが拾えるようにするためである。
4. 覚えていないこと。

示したら、「推しのまま全部採る」か「問題ごとに選ぶ」かを聞く。推しのまま全部採るなら、5 を飛ばして 6 へ進む。

## 5. 問題ごとに選ぶ

問題 1 件を 1 問にする。

- 問いの文に、問題の要旨と、対策ごとの中身・置き場・費用を書く。Codex の質問ツールは、選択肢に説明を書けないためである。
- 選択肢は、対策（記号と短い名前。推しには「（推奨）」を付けて先頭に置く）と「採らない」にする。
- 2 つの問題に効く対策は、両方の問いに出す。どちらかで採れば、採ったことにする。

| | 問いの出し方 |
| --- | --- |
| Claude Code | 質問欄（AskUserQuestion）で、複数選択にする。1 回に 4 問まで出し、問題が 5 件以上なら分けて出す |
| Codex | `request_user_input_async` で出す。1 問で 1 つしか選べないので、選択肢は単独の対策と「採らない」にし、複数を採るときは自由入力で「A,B」と書けばよいと問いの文に書く。推しが 2 つ以上の組なら、その組を先頭の選択肢にする。答えは次のユーザーのメッセージで届くので、出したら応答を終えて待つ |

次の答えは、そのまま採らずに意図を確かめる。

- 「採らない」と対策を、同時に選んだ答え。
- 問いと関係の無い答え（質問や、別の話）。
- 推しがそのまま返り、直前のやり取りから見て唐突な答え。

## 6. 反映する

- 「PRD が要る」の対策は、採っても書かない。8 で、その問題を台帳へ積む。同じ問題のほかの対策を反映しても、積む。報告で、PRD の題材として示す。
- それ以外の採った対策を、置き場へ書く。書く前に、`AGENTS.md` の「作業ごとに読むもの」の表で置き場に当たる行（skill は「skill を書く・直す」、それ以外のハーネスは `AGENTS.md`・品質確認観点・プロセス契約とレジストリ・エージェント定義の行）の節を読み、読んだ節の名前を応答に 1 行で示す。
- 観点に項目を足すときは、その観点ファイルの「位置づけ」の決まり（項番の振り方など）に従う。節の規約を直したら、同じ節の項目も見直す。
- skill を直したら、`.agents/skills/` と `.claude/skills/` の両方を同じにする。用途・起動・出力先が変わったら、[skills README](../README.md) の表を両方で直す。
- `docs/process/protocol.md` か `.claude/agents/an-review.md` を直したら、報告に「共有の契約を直したので、揃える手順が要る」と書く。

## 7. 確かめる

- 6 で読んだ観点ファイルの全項目を、節の適用範囲に従って通す（`AGENTS.md` の「作業ごとに読むもの」の表の下の決まり）。
- [実装 品質確認観点](../../../docs/quality/impl.md) の機械検査を、次のとおり実行する。7（改行コード）と 62（既存ファイルの BOM）は、変えたファイルに。8（skill の実体コピーの同期）は、skill を変えたときに。4（共有する契約の非依存）は、`protocol.md` か `an-review.md` を変えたときに。
- 機械検査を足したら、今回の手戻りの形に当てて、捕まえられることを確かめる。当てる材料が作業ツリーに無ければ、`.scratch/anet-improve/` に作って当てる。
- 観点の項目、手順、規約を足したら、今回の場面に当てると、どの文で止まるかを 1 行で示す。止まらなければ直す。

## 8. 記録する

### 1 回分の記録

`.scratch/anet-improve/<YYYYMMDD-HHMM>_<題>.md` に、4 の一覧、選んだ結果、反映したファイルと節、7 の結果、PRD 送りと見送りを書く。`<題>` は、この会話の作業を表す短い英小文字の語にする。

### 台帳

問題ごとに、台帳 `reports/registry/findings.jsonl` での扱いを次で決める。項目と CLI は `reports/tools/registry.py` 冒頭の docstring が正本である。

| 問題 | 台帳 |
| --- | --- |
| 「PRD が要る」の対策を採った問題（同じ問題のほかの対策を反映していても） | `open` で積む |
| 対策をすべて採らなかった問題 | `wontfix` で積む |
| 採った対策を反映し、「PRD が要る」の対策を採っていない問題 | 積まない。反映した差分が記録になるためである。台帳に同じ問題があれば、`fixed` にする |
| 1 回限りの問題 | 積まない |

新しく積む記録の項目（台帳に同じ問題がすでにある記録には及ばない。下の手順 2 による）:

| 項目 | 値 |
| --- | --- |
| `lens` | `process` |
| `category` | 2 の分類の名前 |
| `title` | 問題の 1 行 |
| `file`、`symbol` | 書く対策の置き場のファイルと、「節名: 問題の短い名前」。書く対策は、`open` なら採った「PRD が要る」の対策（2 つ以上採ったときは、推しがあれば推し、無ければ記号が最初のもの）、`wontfix` なら推しの対策である。「節名: 問題の短い名前」にするのは、同じ節の別の問題が、1 件に潰れないようにするためである |
| `evidence` | 書く対策の置き場の、節の見出しの行 |
| `summary` | 何が起きたか |
| `scenario` | 対策が無いまま同じ場面になると、何が起きるか |
| `fix_hint` | `open` なら「PRD が要る: 」で始め、採った「PRD が要る」の対策の中身をすべて並べる。`wontfix` なら推しの対策の中身 |
| `priority` | `P2`。再発は、優先度ではなく履歴で表す |
| `confidence` | `high` は会話かファイルで確かめたもの、`med` は覚えている範囲だけのもの |

手順（`<run_id>` は `<YYYY-MM-DD>-improve-<claude|codex>`、台帳の CLI は `./.venv/Scripts/python.exe reports/tools/registry.py`）:

1. 台帳に同じ問題が無い問題は、新しく積む記録を `.scratch/anet-improve/` の JSONL に書き、`add --file <JSONL> --run <run_id>` を実行する。`wontfix` で積む記録は、続けて `set --id <id> --status wontfix --note "anet-improve で採らなかった"` を実行する。
2. 台帳に同じ問題がある問題は、新しく積まない。既存の記録の本文（`title`、`summary`、`scenario`）と、`file`・`symbol`・`fix_hint` は書き換えない。`file`・`symbol` を変えると、次に同じ問題を突き合わせられなくなるためである。`touch --ids <id> --run <run_id>` で最終確認日を更新し、`set --id <id> --status <上の表の状態> --note "再発。<今回の扱い>: <今回の対策>" --run <run_id>` を実行する。
   - `<今回の扱い>` は「PRD 送り」「採らなかった」「反映した」のどれかにする。
   - `<今回の対策>` は、PRD 送りなら採った「PRD が要る」の対策すべての置き場と中身、採らなかったなら推しの対策の置き場と中身、反映したなら反映した置き場にする。
   - 状態が前と同じでも実行する。履歴の「再発」の注記が、再発と今回の対策の記録になるためである。
3. `build` と `validate` を実行する。`build` は、台帳の派生一覧と、`docs/wiki/` の地図の「台帳の指摘」の区画を書き換える。

### memory（Claude Code だけ）

この会話で書いた・直した feedback memory のうち、中身を規約へ移したものを一覧にして示す（memory の名前、移した先、外す部分）。ユーザーの了承を得てから、移した分を外す。全部を移した memory は消し、`MEMORY.md` の行も消す。Codex では行わない。

## 9. 報告して止まる

次を示す。

- 反映したファイルと節。
- 7 の結果（自己点検、機械検査、今回の形に当てた結果）。
- PRD 送りの対策と、台帳の id。`/anet-create-prd`（Codex は `$anet-create-prd`）の題材になる。台帳に同じ問題があった記録では、今回の対策は履歴の最後の注記にあると添える。
- 見送りと、台帳に積んだもの・状態を変えたもの。
- 1 回分の記録の置き場。
- 変えたファイルの一覧。ほかの作業と別のコミットにできるようにする。Topic は `#7`。コミットの文案は `prepare-commit` に任せる。

最後に、反映した変更をレビューに出すかを 1 問で聞く。出すと答えたら、[anet-review](../anet-review/SKILL.md) の「2. 依頼を組み立てる」以降に従って出す。対象は 6 で変えたファイル、成果物キーは `impl`、入力元は「なし」、変更の目的は「この会話の手戻りの再発防止」と書く。出さないと答えたら、止まる。
