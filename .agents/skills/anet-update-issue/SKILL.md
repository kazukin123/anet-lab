**開発者の指示を受けて、課題記録の状態と監理の項目を変える。**

## 判定

AI が自分の判断で書くときのモード。対象の ID、判定、根拠を受け取り、`ai_judge` と `ai_judged` だけを更新する。判定は「残っている」「直った見込み」「判断できない」「実装済み」の4値で、日付は現在の日付とする。`status`、監理の項目、背景・事象・影響・対応方針・対応内容は変えない。対応内容は、対応した工程がファイルへ直接追記する（`anet-create-issue` の「各項目の書き方」）。

監査の確かめ直しは索引以外に前の3値を使う。PRD 実装完了は PRD の索引 issue を「実装済み」、その子のうち今回の実装の範囲に当たる課題を「直った見込み」にする。この場で直した既存の課題も「直った見込み」にする。AI の判定に合わせた状態変更を開発者へ求めない。

以下は開発者の指示のモードである。issue の ID を題材に PRD を起こす指示、またはグリルで課題を範囲に取り込む選択は、その課題の `parent` を書く指示を含む。`area`・`type`・`docs` も、このモードでだけ変更する。

## 使う場面

| 指示の例 | 変える先 |
| --- | --- |
| 「解決にして」「終わった」 | 解決 |
| 「保留にして」「環境待ち」 | 保留 |
| 「中断して」「いったん手を止める」 | 中断中 |
| 「次版で」「次の版に回す」「今はやらない」 | 次版 |
| 「着手した」「調べ始めた」 | 調査中 / 対応中 |
| 「優先度を上げて」「手間を見直して」「これはあれを待つ」「この親の下に入れて」 | 監理の項目（`priority` `value` `urgency` `risk` `size` `depends` `parent` `kind`） |
| 「棚卸しの 1・3 を採用」 | `anet-list-issues` の棚卸しが提案した監理の項目の値。**統合・分割は課題解決 Agent が行う** |

## 使わない場面

- **AI が自分の判断で状態や監理の項目を変えるとき。** AI が自分で更新してよいのは「判定」の2欄だけである
- 課題を新しく起こすとき（`anet-create-issue`）
- 課題を見渡すとき（`anet-list-issues`）
- 課題に対応するとき（課題解決 Agent）。**対応と状態変更は別の操作である**
- 対応内容を書き足すだけのとき。ファイルへ直接追記する（`anet-create-issue` の「各項目の書き方」）

## 手順

### 1. 対象を決める

| 指示の形 | どう決めるか |
| --- | --- |
| 課題 ID が示された | その課題 |
| 「さっきの」「これ」 | 直前に扱った課題。**1 件に絞れる場合だけ** |
| 指定が無い | 状態が「解決」でない課題を候補として示す |

**候補が複数あるときは必ず示して選ばせる。** 直前に複数の課題をまとめて扱っていた場合、「解決にして」がどれを指すかは決まらない。**推測で 1 件に決めない。**

候補は次の形で示す。

| # | 課題 | 概要 | 現在の状態 | 発生工程 |
| --- | --- | --- | --- | --- |

`課題` は課題記録のファイルへのリンク（リンクにできない環境ではパス）にし、`概要` には題名（長ければ要点だけ）を書く。

**複数を同時に選べる。** まとめて対応した課題は、まとめて状態を変えられる。

### 2. 変える先を確かめる

指示から変える先が読み取れない場合は聞く。**状態と監理の項目の意味は `anet-create-issue` SKILL の定義による。**

`depends` を変えるときは、循環しないこと（変えた結果、待ちの関係がたどって自分に戻らないこと）を確かめる。循環するなら変えずに、その旨を返す（循環に挙がる課題は、候補と同じ形で示す）。

### 3. 記録を更新する

| 変えるもの | 内容 |
| --- | --- |
| 状態 | 指示された状態 |
| 監理の項目 | 指示された値。**監理の項目だけを変えるときは、対応内容と備考は書かない**（frontmatter の値そのものが記録になる）。`value` `urgency` `risk` `size` のどれかを変えたら、`wsjf` を計算し直して書く（`anet-create-issue` の「監理の項目」） |
| 解決の日付 | **「解決」にするときだけ**記入する |
| 対応内容 | 状態を変えるときに残す、何をしたか。開発者が述べた内容を書く。工程が書いた行にすでにあることは繰り返さない |
| 備考 | 変更した日付、変更前後の状態、そう判断した理由 |

**対応内容が分からないまま「解決」にしない。** 何をして解決したのかが記録に残らないと、後から追えない。まず対応内容の既存の行を読み、それでも分からなければ開発者に聞く。

**「保留」にするときは、何を待っているかと、再開できる条件を書く。** それが無いと、いつ見直せばよいか分からなくなる。

**「中断中」にするときは、済んだことと残っていることを、対応内容に書く。** 再開するときに、どこから始めればよいかが分かるようにするためである。

**「次版」にするときは、なぜ本版でやらないと決めたかを書く。** 判断の理由が残らないと、次版で見たときに前提が変わったかどうかを確かめられない。

### 4. 報告する

変えた課題と、変更前後の状態と監理の項目の値、記録した対応内容を返す。課題は、候補と同じく、課題記録のファイルへのリンクに題名（長ければ要点だけ）を添えて示す。変更前後の値に出る課題（`depends` と `parent`）も、同じ形で示す。複数ある場合は一覧で返す。

## 守ること

| # | 内容 |
| --- | --- |
| 1 | **AI は自分の判断では状態も監理の項目も変えない。** AI の判定の欄だけを「判定」で変える。開発者の指示に当たる操作では、指示された欄を書く |
| 2 | **「解決」にしてよいかを判断しない。** 成果物の妥当性の判断は開発者が行う（`docs/process/protocol.md` 6 節）。本 SKILL は開発者の判断を記録するだけである |
| 3 | **対象が曖昧なまま更新しない。** 候補を示して選ばせる |
| 4 | 課題記録の本文（背景・事象・影響）を書き換えない。**変えるのは状態・監理の項目・対応内容・備考だけ** |
| 5 | 出力先を推測で書かない。`docs/process/registry.md` の `issue-record` を引く |
