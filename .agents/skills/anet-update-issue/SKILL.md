**開発者の指示を受けて、課題記録の状態と監理の項目を変える。AI の判定と、工程の出来事に合わせた解決以外の状態は、AI が書く。**

## 判定

AI が自分の判断で書くときのモード。対象の ID、判定、根拠を受け取り、`ai_judge` と `ai_judged` だけを更新する。判定は「残件有り」「残件無し」「判定不能」の3値で、日付は現在の日付とする。「未確認」へは戻さない。`status`、監理の項目、背景・事象・影響・対応方針・対応内容は変えない。対応内容は、対応した工程がファイルへ直接追記する（`anet-create-issue` の「各項目の書き方」）。

監査の確かめ直しは、PRD の課題（`prd` で PRD を指す課題）も含めて同じ 3 値を使う。PRD の実装完了は、その PRD の課題のうち今回の実装の範囲に当たる課題を「残件無し」にし、段階の途中で終えたときは、残りの段階を持つ課題を「残件有り」にする。PRD の実装済みは判定の値で表さず、その PRD の課題の判定と状態から一覧の道具が導く。この場で直した既存の課題も「残件無し」にする。ただし、どの場合も、直したあとに課題の事象が残っていれば「残件無し」にせず「残件有り」にする（直した事象は対応内容に書く）。判定に合わせた状態の扱いは、下の「工程の出来事」と「解決を持ちかける」による。

判定を書き終えたら、開発者の指示のモードと同じく `reports/tools/wiki_support.py maps` を回す（手順の「3. 記録を更新する」の末尾。`Bash`）。`ai_judge`・`ai_judged` も検証と一覧の対象である。複数の判定を書くときは、書き終えてから 1 回回す。

## 工程の出来事

AI が工程の出来事に合わせて `status` を書くときのモード。開発者の承認は要らない。出来事を担う工程が、その時点で次の表のとおりに書く。

| 出来事 | 書く工程 | 対象 | 書く状態 |
| --- | --- | --- | --- |
| PRD のグリルを始めた（新規・改訂・再グリル。質疑の無い暫定の起票は当たらない） | `anet-create-prd` | 題材の課題。改訂と再グリルでは、その PRD の課題も | 調査中 |
| 実装計画（`*_2ximpl.md`）を保存した | `implement-prd-with-docs` | その PRD の課題のうち、今回の実装の範囲に当たる課題 | 対応中 |
| 開発者が「この場で直す」を選んだ | 各工程（`docs/process/registry.md` の「この場で直す」） | 同じ課題の既存の課題 | 対応中 |
| 開発者が選んだ「この場で直す」を、設計の判断が要ると分かって取りやめた（`docs/process/registry.md` の「この場で直す」の手順 2） | 各工程 | 上の行で対応中にした課題 | 対応中にする前の状態 |
| 工程を止めた（`docs/process/protocol.md` 5 節の停止条件 8・9） | 各工程 | その工程の対象（グリル・実装計画・「この場で直す」の行の対象に当たる課題。今回の実行で状態を書いたかは問わない）のうち、今が調査中か対応中のもの | 中断中。実働環境や他部門の判断など、外部を待つなら保留 |
| 止まった工程を再開した | 各工程 | 上の行で中断中・保留にした課題（備考の行で分かる） | 止める前の状態（調査中か対応中） |

- **`解決` にはしない。** 解決は開発者が選ぶ（下の「解決を持ちかける」）。
- **表の行は、今の状態が未着手・調査中・対応中・中断中の課題に当てる。** `保留` は停止と再開の行のほかでは変えない。外部を待つ状態は、工程の出来事では解けないからである。`解決` と `次版` は、どの行でも変えない。どちらも開発者が決めた状態だからである。`次版` は出来事から決まらないので、開発者の指示のモードでだけ書く。
- 今の状態が書く状態と同じなら書かない。
- 書いたら、本文の末尾の「## 備考」（無ければ作る）に、開発者の指示で変えたときと同じ形で 1 行足し、理由の代わりに出来事を書く。前の状態へ戻したときも、前の行は消さずに 1 行足す。対応内容は書かない。対応した中身は、その工程が対応内容へ書く行に残るためである。ただし中断中・保留にするときは、手順の「3. 記録を更新する」のとおり、済んだことと残っていること、または待っているものと再開できる条件を対応内容に書く。

```markdown
- 2026-11-09 状態を `未着手` から `対応中` へ変更。工程の出来事による（PRD116 の実装計画を保存した）。
```

- Plan Mode の間は書かない。Plan Mode で始めた工程は、Plan Mode を抜けて作業に入るときに、それまでの出来事の分をまとめて書く。
- 書き終えたら `reports/tools/wiki_support.py maps` を回す（判定と同じ）。判定と同じ時点で書くときは、両方を書き終えてから 1 回回す。

## 解決を持ちかける

AI は「解決」を書かず、持ちかけるだけにする。`anet-prepare-commit` が、コミットが対応した課題のうち、AI の判定が「残件無し」で `status` が解決でないものを、解決の候補として示す（同 skill の「解決の候補」）。開発者が選んだものを、開発者の指示のモードで「解決」にし、完了の理由（`resolution`）を「対応済み」にする。選ばれなかった課題と、コミットを通らずに判定が付いた課題は、`docs/management/issues/INDEX.md` の「解決待ち」に残る。

**解決の課題に「残件有り」の判定を書いても、状態は戻さない。** 解決の日付以後に「残件有り」になった課題（解決の日付が無い解決の課題も含む）は、`INDEX.md` の「再開候補」に出る。戻すかと戻す先は、開発者が指示する。

## 開発者の指示

開発者の指示で書くときのモード。issue の ID を題材に PRD を起こす指示、またはグリルで課題を範囲に取り込む選択は、その課題の `prd` を書く指示を含む。既存の課題の `depends` に課題を足す指示は、待たれている側の `risk` が 5 未満なら 5 に上げて `wsjf` を計算し直す指示を含む（`anet-create-issue` の「anet での当てはめ」）。起票で書いた `depends` の待たれている側は、ここでは変えない（棚卸しで見直す）。`area`・`type`・`docs`・`prd` も、このモードでだけ変更する。`domain` もこのモードで変えるが、開発者が Obsidian などで直接書き換えてもよい。

## 使う場面

| 指示の例 | 変える先 |
| --- | --- |
| 「解決にして」「終わった」、`anet-prepare-commit` の解決の候補を選んだ | 解決 |
| 「再開して」（`INDEX.md` の再開候補） | 指示された状態 |
| 「保留にして」「環境待ち」 | 保留 |
| 「中断して」「いったん手を止める」 | 中断中 |
| 「次版で」「次の版に回す」「今はやらない」 | 次版 |
| 「着手した」「調べ始めた」 | 調査中 / 対応中 |
| 「手間を見直して」「これはあれを待つ」「この親の下に入れて」 | 監理の項目（`value` `urgency` `risk` `size` `depends` `parent` `kind` `prd` `domain`） |
| 「棚卸しの 1・3 を採用」 | `anet-list-issues` の棚卸しが提案した監理の項目の値。**統合・分割は課題解決 Agent が行う** |

## 使わない場面

- **AI が自分の判断で監理の項目を変えるとき、「解決」か「次版」にするとき、解決の課題を戻すとき。** AI が自分で更新してよいのは、「判定」の2欄と、「工程の出来事」の状態だけである
- `priority` と `memo` を変えるとき。開発者が直接書き換える管理外のメモで、開発者に頼まれたときも、このスキルを通さずに頼まれた欄の値だけをファイルで書き換える（`anet-create-issue` の「管理外のメモ」）
- 課題を新しく起こすとき（`anet-create-issue`）
- 課題を見渡すとき（`anet-list-issues`）
- 課題に対応するとき（課題解決 Agent）。**対応と状態変更は別の操作である**
- 対応内容を書き足すだけのとき。ファイルへ直接追記する（`anet-create-issue` の「各項目の書き方」）

## 手順

### 1. 対象を決める

| 指示の形 | どう決めるか |
| --- | --- |
| 課題 ID が示された | その課題 |
| 「さっきの」「これ」 | 直前に扱った課題。**1 件に絞れる場合だけ** |
| 指定が無い | 状態が「解決」でない課題を候補として示す |

**候補が複数あるときは必ず示して選ばせる。** 直前に複数の課題をまとめて扱っていた場合、「解決にして」がどれを指すかは決まらない。**推測で 1 件に決めない。**

候補は次の形で示す。

| # | 課題 | 概要 | 現在の状態 | 発生工程 |
| --- | --- | --- | --- | --- |

`課題` は課題記録のファイルへのリンク（リンクにできない環境ではパス）にし、`概要` には題名（長ければ要点だけ）を書く。

**複数を同時に選べる。** まとめて対応した課題は、まとめて状態を変えられる。

### 2. 変える先を確かめる

指示から変える先が読み取れない場合は聞く。**状態と監理の項目の意味は `anet-create-issue` SKILL の定義による。**

`depends` を変えるときは、循環しないこと（変えた結果、待ちの関係がたどって自分に戻らないこと）を確かめる。循環するなら変えずに、その旨を返す（循環に挙がる課題は、候補と同じ形で示す）。

### 3. 記録を更新する

| 変えるもの | 内容 |
| --- | --- |
| 状態 | 指示された状態 |
| 監理の項目 | 指示された値。**監理の項目だけを変えるときは、対応内容と備考は書かない**（frontmatter の値そのものが記録になる）。`value` `urgency` `risk` `size` のどれかを変えたら、`wsjf` を計算し直して書く（`anet-create-issue` の「監理の項目」） |
| 解決の日付 | **「解決」にするときだけ**記入する。解決から戻すときは空にし、元の日付を備考に書く |
| 完了の理由 | **「解決」にするときだけ** `resolution` に書く（対応済み / 対応しない / 重複 / 再現しない / 不要になった）。開発者の指示に理由が無ければ聞く。`anet-prepare-commit` の解決の候補を選んだときは「対応済み」。解決から戻すときは空にし、元の理由を備考に書く |
| 対応内容 | 状態を変えるときに残す、何をしたか。開発者が述べた内容を書く。工程が書いた行にすでにあることは繰り返さない |
| 備考 | 変更した日付、変更前後の状態、そう判断した理由 |

frontmatter の値は、`anet-create-issue` の「テンプレート」の下の決まり（Obsidian と同じ書き方）で書く。

**対応内容が分からないまま「解決」にしない。** 何をして解決したのかが記録に残らないと、後から追えない。まず対応内容の既存の行を読み、それでも分からなければ開発者に聞く。

**「保留」にするときは、何を待っているかと、再開できる条件を書く。** それが無いと、いつ見直せばよいか分からなくなる。

**「中断中」にするときは、済んだことと残っていることを、対応内容に書く。** 再開するときに、どこから始めればよいかが分かるようにするためである。

**「次版」にするときは、なぜ本版でやらないと決めたかを書く。** 判断の理由が残らないと、次版で見たときに前提が変わったかどうかを確かめられない。

**書き終えたら、`anet-create-issue` の「起票の手順」の 5 と同じく `reports/tools/wiki_support.py maps` を回す（`Bash`）。** frontmatter を検証し、一覧と地図の「課題」の区画を作り直す。止まったときの扱いも同じである（今回変えた課題なら直して回し直し、ほかの課題なら直さずに知らせる）。判定のモードでも回す。

### 4. 報告する

変えた課題と、変更前後の状態と監理の項目の値、記録した対応内容を返す。課題は、候補と同じく、課題記録のファイルへのリンクに題名（長ければ要点だけ）を添えて示す。変更前後の値に出る課題（`depends` と `parent`）も、同じ形で示す。複数ある場合は一覧で返す。

## 守ること

| # | 内容 |
| --- | --- |
| 1 | **AI は自分の判断では監理の項目を変えず、「解決」と「次版」にもせず、解決の課題を戻さない。** AI が自分で書くのは、「判定」の 2 欄と、「工程の出来事」の状態だけである。開発者の指示に当たる操作では、指示された欄を書く |
| 2 | **「解決」にしてよいかを判断しない。** 成果物の妥当性の判断は開発者が行う（`docs/process/protocol.md` 6 節）。AI は候補を持ちかけ（「解決を持ちかける」）、本 SKILL は開発者の選択を記録するだけである |
| 3 | **対象が曖昧なまま更新しない。** 候補を示して選ばせる |
| 4 | 課題記録の本文（背景・事象・影響）を書き換えない。**変えるのは状態・監理の項目・対応内容・備考だけ** |
| 5 | 出力先を推測で書かない。`docs/process/registry.md` の `issue-record` を引く |
