# 課題の一覧

`anet-create-issue` で起票された単票を集め、依存と WSJF を目安に並べて提示する。**記録は変更しない。** 値を変えるのは `anet-update-issue` である。

## 手順

1. `docs/process/registry.md` から成果物キー `issue-record` の行を引き、課題記録の置き場所を確認する
2. その配下の `issue-*.md` を Glob で集める（`README.md` は対象外）
3. 各ファイルの frontmatter を Read で読む（引数が `棚卸し` のときは本文も読む。下記「棚卸し」）
4. 引数があれば絞り込む
5. 下の「並び順」で並べ、下の形式で表にする

**シェルコマンドに依存しない。** 環境によって `grep` などが解決できないことがあるため、Glob と Read で完結させる。

## 引数

引数は省略できる。省略時は本版（次版・解決を除く）を出す。閉じた課題は状態を指定して見る。

| 引数の例 | 動き |
| --- | --- |
| `未着手` `調査中` `対応中` `中断中` `保留` `次版` `解決` | その `status` だけに絞る |
| `未解決` | `解決` 以外に絞る |
| `本版` | **`次版` と `解決` を除く。** 本版で扱うものだけを見る |
| 工程名（`PRD` など） | その `phase` だけに絞る |
| `成果物` `ハーネス` | その `kind` だけに絞る |
| 課題 ID（`issue-…`） | その課題を `parent` に持つ課題（子）だけに絞る |
| `棚卸し` | 本版の課題（`次版` と `解決` を除く）の本文まで読み、監理の項目の値と、統合・分割の候補を提案する（下記「棚卸し」） |
| `318_rl_core` などの `area` | 並びのどれかにその key を含む課題に絞る。受け付ける key は `reports/tools/categories.json` の `categories` |
| `不具合` `ずれ` `改善` `案` `調査` `索引` | その `type` に絞る |
| `束ね [area] [max=n]` | 下の「束ね」の提案を出す |

指定した `area` が categories の key に無い、`type` が上の6値に無い、束ねの `max` が正の整数でない場合は、一覧や提案を出さずに止まり、指定値と受け付ける値を示す。

## 出力形式

```
課題 N 件（絞り込み: <条件 / なし>）

| # | ID | 状態 | WSJF | 優先度 | 待ち | 種別 | 工程 | 課題 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | [issue-20260907-39e29e](<課題記録のパス>) | 未着手 | 7.5（引継ぎ） | 高 | — | ハーネス | PRD | <title> |
| 2 | [issue-20260908-0a1b2c](<課題記録のパス>) | 未着手 | 7.5 | 中 | [issue-20260907-39e29e](<課題記録のパス>) | ハーネス | 実装 | <title> |
```

表には `area`（領域）・`type`（性質）・AI の判定の列も加える。`docs/management/issues/INDEX.md` は `reports/tools/wiki_support.py maps` が、同じ並びと列、本版の既定で作り直す。引数付きの一覧はこの skill が読み取りだけで出す。

- 課題 ID は、`ID` と `待ち` を含めてどれも、課題記録のファイルへのリンクにする（リンクにできない環境ではパス。実在しない ID はリンクにしない）。表の行に無い課題（絞り込みで表から外れた `待ち` の課題、子に絞るときの親の課題、下の「注意」で別立てに報告する課題）は、表のあとに「関連する課題」として、リンクと題名（長ければ要点だけ）を並べる。開発者が、どの課題かを応答の中で分かり、課題記録を開けるようにするためである
- `WSJF` は、並べるのに使った値（下の「並び順」で引き継いだあとの値）を書く。引き継いだときは `7.5（引継ぎ）` と書く。値が無ければ `—`
- `優先度` は課題に書かれた値をそのまま書く
- `待ち` には、`depends` に挙がった課題のうち、まだ `解決` でないものの ID を書く。実在しない ID は `（無い）` を添えて書く。無ければ `—`

### 並び順

課題を次の区分に分け、区分の順に並べる。**並びは目安である。** どれから手を付けるかは、開発者がそのときの事情で決める（`anet-create-issue` の「監理の項目」）。

| 順 | 区分 | 条件 |
| --- | --- | --- |
| 1 | 着手できる | `status` が `対応中` `調査中` `中断中` `未着手` で、`depends` の課題がすべて `解決` である |
| 2 | 待ち | `status` が `対応中` `調査中` `中断中` `未着手` で、`depends` に `解決` でない課題が残る。`depends` が実在しない ID を指す、または循環しているものもここに置く |
| 3 | 保留 | `status` が `保留` |
| 4 | 次版 | `status` が `次版` |
| 5 | 解決 | `status` が `解決` |

区分の中は、次の順で並べる。

1. `status` が `対応中` `調査中` のもの（手が付いているもの）を先に置く。`中断中` は含めない
2. `wsjf` の大きい順。**`wsjf` は引き継ぐ。** ある課題を `depends` で待っている課題（待っている課題を待つものも含む）のうち、最も大きい `wsjf` が自分より大きければ、その値を使う。自分の `wsjf` が無いときも、待っている課題の値を引き継ぐ。前提になっている課題を先に片づけるためである。引き継ぎの元にするのは、`status` が `対応中` `調査中` `中断中` `未着手` の課題だけとし、絞り込みの前に全件で決める。自分の値も引き継いだ値も無いものは、あるものの後ろに置く
3. 優先度の高い順（`高` → `中` → `低`）
4. `raised` の古い順
5. ID の順

### 件数の内訳

表の後に、区分ごとの件数を 1 行で添える。

```
着手できる 5 / 待ち 3 / 保留 1 / 次版 4 / 解決 12
```

## 棚卸し

引数が `棚卸し` のとき、本版の課題の本文まで読み、次を提案する。**提案するだけで、記録は変えない。** 開発者が採るものを選び、`anet-update-issue` が値を書く。統合や分割の実施は課題解決 Agent が記録を直す。

| 提案 | 判断のよりどころ |
| --- | --- |
| 監理の項目の値（`kind` `value` `urgency` `risk` `size` `depends` `parent`）。`priority` は開発者のメモなので提案しない | `anet-create-issue` の「監理の項目」の定義。値が無いもの、または本文と食い違うものだけを挙げる。追記で範囲や実例が増えたもの、期日が決まった・動いたものは、`value` `urgency` `size` を見直す |
| 統合の候補 | `anet-create-issue` の「分け方」。同じ原因で直す場所も同じ課題どうし |
| 分割の候補 | 同じく「分け方」。決めることが 3 つ以上あり、それぞれ別々に決めて直せる課題 |
| 状態の見直しの候補 | 対応内容が済んでいるのに `解決` でないもの、本文が次版で扱うとしているのに `次版` でないもの。**状態は開発者が決める** |

AI の判定が「直った見込み」か「実装済み」で `status` が解決でない課題も、状態の見直しの候補に加える。`area`・`type`・`docs` の値も監理の項目として見直す。100件を超える移行後の棚卸しは `area` ごとに分けて行う。

## 束ね

次版・解決でなく、`docs` に PRD を持たず、`parent` が空で、`type` が索引でない課題を対象にする。`docs` が PRD 以外の文書だけを指す課題は対象になりうる。

- `area` の先頭ごとに分け、空は1組にまとめる。`area` を指定した場合は、その値を並びに含む課題だけを、その値の1列にする。
- 分けた中を通常の一覧の並びで、既定5件ずつ（`max=n` があればその件数ずつ）区切る。
- 組の中で最も大きい WSJF の順に、最大3組を示す。同値なら area と先頭の ID の順とする。
- 組の issue の ID と題、area、束ねる理由、`anet-create-prd` へ渡すカンマ区切りの ID を示す。記録は変えない。

```
棚卸しの提案 N 件

| # | 課題 | 項目 | 今 | 提案 | 理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | [issue-…](<課題記録のパス>)（<題名の短い言い方>） | risk | 3 | 5 | <本文のどの事象から> |
| 2 | [issue-…](<課題記録のパス>)（<題名の短い言い方>） / [issue-…](<課題記録のパス>)（<題名の短い言い方>） | 統合 | — | issue-… へ統合 | <同じ原因・同じ直す場所> |

採用するものを番号で指定してください。すべて見送る場合はその旨を。
```

`課題` の列は、課題記録のファイルへのリンク（リンクにできない環境ではパス）にし、題名（長ければ要点だけ）を添える。`今` と `提案` に出る課題（`depends` と `parent` の値）で `課題` の列に無いものは、表のあとに「関連する課題」として、同じ形で並べる。

**本文まで読むため、通常の一覧より重い。** 課題がたまったとき、また工程を動かして課題をまとめて起票したあとに行う。

## 注意

- **1 件も無い場合は「課題はありません」と返す。** 空の表を出さない
- frontmatter が壊れている、または必須項目が欠けているファイルがあれば、**一覧の後に別立てで報告する**。黙って飛ばさない。監理の項目のうち `kind` `priority` `depends` `parent` が無いものは、優先度を `中`、`depends` を空として並べ、報告に挙げる
- `type`・`ai_judge`・`area`・`docs` の不正値も同じく一覧のあとに報告する。AI の判定が空なら未確認であり、不正値ではない
- **状態が `次版` と `解決` でない課題で、`value` `urgency` `risk` `size` `wsjf` のどれかが無いもの、元になる値が `anet-create-issue` の「WSJF」の定める値でないもの、または `wsjf` が計算した値と食い違うものは、一覧の後に別立てで報告する。** 元になる値がそろっていれば、計算した値で並べる
- **`depends` が循環している、または実在しない ID を指している場合は、一覧の後に別立てで報告する。** どちらも区分 2（待ち）に置く
- 本文（事象 / 影響 / 対応方針）は一覧に含めない。詳細が要るときは該当ファイルを開く
